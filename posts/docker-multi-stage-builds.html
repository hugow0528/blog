Docker Multi-Stage Builds: Smaller, Faster, Safer Containers

July 1, 2026 11 min read New

You build a Node.js app, Dockerize it, and check the image size: 1.2 GB. Your actual app is maybe 500 KB. Where did the rest go? Build tools, compilers, source code, npm packages — all sitting in your production container, unused and potentially dangerous.

Docker multi-stage builds solve this elegantly. They let you use a full-featured image for building, then copy only the result into a minimal runtime image. The final image contains only what your app needs to run.

In this tutorial, we'll transform bloated containers into lean, fast, and secure images using real-world examples with Node.js, Python, and Go.

The Problem: Everything in One Image

Before multi-stage builds, Dockerfiles looked like this:

# BEFORE: Single-stage, bloated Dockerfile
FROM node:18
WORKDIR /app

# Install everything — build tools AND runtime
COPY package*.json ./
RUN npm install

# Copy source code
COPY . .

# Build the app
RUN npm run build

# Everything stays in the image
EXPOSE 3000
CMD ["node", "dist/server.js"]

This image contains:

  • The full Node.js runtime (~300 MB base image)
  • npm and all package management tools
  • Your source code (including local secrets if you weren't careful)
  • All devDependencies — testing frameworks, linters, bundlers
  • Any build tools installed via apt-get

Total? Often 800 MB to 1.5 GB. That means slower pushes to registries, slower pulls to production, higher storage costs, and a larger attack surface.

The Solution: Multi-Stage Builds

Multi-stage builds use multiple FROM statements in a single Dockerfile. Each FROM starts a new build stage. You copy artifacts between stages using the FROM name or stage number.

Here's the same app, multi-stage:

# AFTER: Multi-stage build
# Stage 1: Build
FROM node:18 AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production
RUN npm ci
COPY . .
RUN npm run build

# Stage 2: Production (only what's needed)
FROM node:18-slim AS production
WORKDIR /app
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/node_modules ./node_modules
COPY --from=builder /app/package*.json ./
EXPOSE 3000
USER node
CMD ["node", "dist/server.js"]

Result? A production image around 150 MB instead of 1.2 GB. That's an 87% reduction.

How It Works: The Anatomy of a Multi-Stage Dockerfile

Let's break down each piece:

Naming Stages

FROM node:18 AS builder

The AS builder part gives the stage a name. Without AS, stages are numbered (0, 1, 2...). Named stages make your Dockerfile self-documenting and easier to reference.

Copying Between Stages

COPY --from=builder /app/dist ./dist

The --from=builder flag tells Docker to copy from the builder stage, not from your build context on disk. Only the specified files are copied — everything else in the builder stage is discarded.

Using Slim/Runtime Bases

FROM node:18-slim AS production

Most official images offer multiple variants:

  • node:18 — Full image with all tools (~300 MB)
  • node:18-slim — Minimal Debian-based image (~180 MB)
  • node:18-alpine — Alpine Linux, even smaller (~140 MB)
  • node:18-distless — Just Node.js, no shell (~40 MB)

For production, -slim is usually the best balance of small size and compatibility. Use distless when you want absolute minimal size and don't need a shell for debugging.

Real Example 1: Python Web App with Flask

Python apps benefit enormously from multi-stage builds because compilation and virtual environments are heavy:

# Stage 1: Build dependencies
FROM python:3.12 AS builder
WORKDIR /build
COPY requirements.txt .
RUN pip install --user --no-cache-dir -r requirements.txt

# Stage 2: Production
FROM python:3.12-slim AS production
WORKDIR /app

# Copy installed packages from builder
COPY --from=builder /root/.local /root/.local

# Copy application code
COPY . .

# Add pip-installed binaries to PATH
ENV PATH=/root/.local/bin:$PATH

# Run as non-root user
RUN useradd --create-home appuser
USER appuser

EXPOSE 5000
CMD ["gunicorn", "--bind", "0.0.0.0:5000", "app:app"]

Key technique: We install packages into --user directory in the builder, then copy just /root/.local into the slim production image. This avoids needing pip in production at all.

Real Example 2: Go Application (Maximum Optimization)

Go is the poster child for multi-stage builds because it compiles to a single static binary:

# Stage 1: Build
FROM golang:1.22 AS builder
WORKDIR /build
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-s -w" -o server .

# Stage 2: Production — scratch image!
FROM scratch
COPY --from=builder /build/server /server
COPY --from=builder /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/

EXPOSE 8080
CMD ["/server"]

The production stage uses FROM scratch — a completely empty image with zero layers. It contains only the compiled binary and SSL certificates (needed for HTTPS calls). Total size: about 15 MB.

The -ldflags="-s -w" strips debug symbols from the binary, saving another few megabytes. CGO_ENABLED=0 ensures a fully static binary with no C library dependencies.

Real Example 3: Frontend App with a Reverse Proxy

For React/Vue/Angular apps, the pattern combines build + serve stages:

# Stage 1: Build the frontend
FROM node:18 AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# Stage 2: Serve with Nginx
FROM nginx:alpine AS production
COPY --from=builder /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf

EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]

Here we build the JavaScript bundle in Node, then serve it with Nginx in a completely separate stage. The Nginx image handles compression, caching headers, and static file serving — all in a 25 MB image.

Optimization Tips

1. Order Matters: Cache Layers Wisely

Docker caches each layer. Put files that change less frequently first:

# ✅ Good: package.json changes less than source code
COPY package*.json ./
RUN npm ci
COPY . .

# ❌ Bad: Invalidates cache on every code change
COPY . .
RUN npm ci

2. Use npm ci Instead of npm install

npm ci is designed for CI/build environments. It:

  • Reads package-lock.json for exact versions
  • Deletes node_modules before installing (no partial states)
  • Fails if package-lock.json is out of sync
  • Is faster because it skips version resolution

3. Add .dockerignore to Reduce Build Context

# .dockerignore
node_modules
.git
.env
*.md
tests/
coverage/
.DS_Store

Without .dockerignore, Docker sends your entire project directory to the build daemon. With it, you send only what's needed, making builds faster and avoiding accidental secret leaks.

4. Run as Non-Root in Production

# Option A: Use a pre-existing non-root user (Node.js images have 'node')
USER node

# Option B: Create your own user
RUN adduser --disabled-password --gecos '' appuser
USER appuser

If your container is compromised, a non-root user limits what an attacker can do. It's one of the simplest and most impactful security hardening steps.

5. Use --platform for Cross-Platform Builds

docker build --platform linux/amd64 -t myapp:latest .

Build amd64 images on Apple Silicon Macs, or arm64 images on Linux servers. Essential for M1/M2/M3 Mac developers deploying to x86 servers.

Measure the Impact

Compare your image sizes before and after:

# Single-stage
docker build -t myapp:single .
docker images myapp:single
# myapp:single    latest    a1b2c3d4e5f6   1.2GB

# Multi-stage
docker build -t myapp:multi .
docker images myapp:multi
# myapp:multi     latest    f6e5d4c3b2a1   150MB

# Compare layer by layer
docker history myapp:single
docker history myapp:multi

When NOT to Use Multi-Stage Builds

Multi-stage builds aren't always necessary:

  • Simple scripts — A single Python script with no dependencies needs no optimization
  • Development environments — Your dev image should have all tools available
  • Images under 100 MB — If you're already small, don't complicate things
  • Debugging — During active debugging, a full-image gives you ssh, curl, strace, etc.

For dev images, keep a separate Dockerfile or use Docker Compose profiles:

# docker-compose.yml
services:
  app:
    build:
      dockerfile: Dockerfile.prod
      target: production
    # For dev, override the target
    # docker-compose -f docker-compose.dev.yml up

Summary

Docker multi-stage builds are one of the highest-ROI improvements you can make to your container workflow:

  • Smaller images — 80-95% size reduction is common
  • Faster deployments — Less to push and pull from registries
  • Improved security — No build tools, no source code, no dev dependencies in production
  • Single Dockerfile — No need for separate build and production Dockerfiles

The syntax is simple — multiple FROM statements and COPY --from=stagename. Start with the patterns in this guide, measure your before/after sizes, and iterate. Your container images (and your team) will thank you.
