Python Packaging & Publishing to PyPI: Share Your Code with the World — Complete Beginner's Guide

July 17, 2026 11 min read

You've written a Python module that's genuinely useful. Maybe it's a utility for parsing logs, a helper for Cloudflare API calls, or a data transformation library. Every time you work on a new project, you copy and paste the same code. Sound familiar? It's time to package it properly and share it with the world.

Python packaging can feel overwhelming at first. There are setup.py, setup.cfg, pyproject.toml, MANIFEST.in, sdist, wheels, Twine, setuptools, and more. This guide walks you through every piece — from your first packaged module to publishing a real package on PyPI that anyone can install with pip install your-package.

How Python Packaging Works

At its core, packaging turns your Python source code into something installable. Here's the flow:

  1. You write Python code in a proper directory structure
  2. You create a configuration file (pyproject.toml) describing your package
  3. A build tool (like build) creates distribution files (sdist and wheel)
  4. You upload those files to PyPI using twine
  5. Anyone can install your package with pip install your-package

Step 1: Set Up the Project Structure

Every Python package follows a standard directory structure. Let's create one for a sample package called myutils:

# Create the project directory
mkdir myutils && cd myutils

# Create the package structure
mkdir -p myutils/tests
mkdir -p docs

# Create necessary files
touch myutils/__init__.py
touch myutils/__about__.py
touch myutils/tests/__init__.py
touch pyproject.toml
touch README.md
touch LICENSE

# Your directory should look like:
# myutils/
# ├── pyproject.toml
# ├── README.md
# ├── LICENSE
# └── myutils/
#     ├── __init__.py
#     ├── __about__.py
#     └── tests/
#         └── __init__.py

The inner myutils/ directory is your package — the code that gets imported. The outer myutils/ is your project — containing config, docs, and the source.

Step 2: Write Your Code

Let's build a simple utility package with two modules:

# myutils/__about__.py
"""Package metadata"""
__version__ = "0.1.0"
__author__ = "Hugo Wong"
__email__ = "hugo@example.com"

# myutils/core.py
"""Core utility functions for common tasks."""

import re
import os
from pathlib import Path
from typing import Optional


def slugify(text: str, separator: str = "-") -> str:
    """Convert text to a URL-friendly slug.

    >>> slugify("Hello World!")
    'hello-world'
    >>> slugify("Python 3.11 Features", separator="_")
    'python_3_11_features'
    """
    text = text.strip().lower()
    text = re.sub(r"[^\w\s-]", "", text)
    text = re.sub(r"[\s]+", separator, text)
    return text.strip(separator)


def find_files(
    directory: str,
    pattern: str = "*.py",
    recursive: bool = True,
) -> list[str]:
    """Find files matching a glob pattern in a directory.

    >>> files = find_files("/tmp", "*.log", recursive=False)
    >>> all(f.endswith(".log") for f in files)
    True
    """
    path = Path(directory)
    method = path.rglob if recursive else path.glob
    return [str(f) for f in method(pattern)]


def read_json(path: str) -> dict:
    """Read and parse a JSON file.

    Raises:
        FileNotFoundError: If the file doesn't exist.
        json.JSONDecodeError: If the file contains invalid JSON.
    """
    import json

    with open(path, "r", encoding="utf-8") as f:
        return json.load(f)


def write_json(path: str, data: dict, indent: int = 2) -> None:
    """Write a dictionary to a JSON file."""
    import json

    with open(path, "w", encoding="utf-8") as f:
        json.dump(data, f, indent=indent, ensure_ascii=False)

# myutils/__init__.py
"""myutils - A collection of Python utility functions."""

from myutils.__about__ import __version__, __author__
from myutils.core import slugify, find_files, read_json, write_json

__all__ = [
    "__version__",
    "__author__",
    "slugify",
    "find_files",
    "read_json",
    "write_json",
]

Step 3: Configure pyproject.toml

The pyproject.toml file is the modern standard for Python packaging. It replaces setup.py for most use cases and is required for PEP 517/518 compatibility.

# pyproject.toml
[build-system]
requires = ["setuptools>=68.0", "wheel"]
build-backend = "setuptools.build_meta"

[project]
name = "myutils"
version = "0.1.0"
description = "A collection of useful Python utility functions"
readme = "README.md"
license = {text = "MIT"}
requires-python = ">=3.10"
authors = [
    {name = "Hugo Wong", email = "hugo@example.com"},
]
keywords = [
    "utilities",
    "python",
    "helpers",
]
classifiers = [
    "Development Status :: 3 - Alpha",
    "Intended Audience :: Developers",
    "License :: OSI Approved :: MIT License",
    "Programming Language :: Python :: 3",
    "Programming Language :: Python :: 3.10",
    "Programming Language :: Python :: 3.11",
    "Programming Language :: Python :: 3.12",
    "Topic :: Software Development :: Libraries",
]

# Optional dependencies
[project.optional-dependencies]
dev = [
    "pytest>=7.0",
    "pytest-cov>=4.0",
    "black>=23.0",
    "mypy>=1.0",
]
docs = [
    "sphinx>=7.0",
]

[project.urls]
Homepage = "https://github.com/hugow0528/myutils"
Repository = "https://github.com/hugow0528/myutils"
Issues = "https://github.com/hugow0528/myutils/issues"

[tool.setuptools.packages.find]
where = ["."]
include = ["myutils*"]

[tool.black]
line-length = 88
target-version = ["py310", "py311", "py312"]

Understanding the key fields:

  • [build-system]: Declares which tools build the package. setuptools is the most common choice.
  • [project]: All the metadata — name, version, description, authors, Python version requirements, and classifiers that help users find your package on PyPI.
  • [project.optional-dependencies]: Named dependency groups. Users can run pip install myutils[dev] to get development tools.
  • [tool.setuptools.packages.find]: Tells setuptools which directories contain your package code.

Step 4: Write a README.md

Your README is the landing page for your package on PyPI. Make it count:

# myutils

A collection of useful Python utility functions.

## Installation

```bash
pip install myutils
```

## Quick Start

```python
from myutils import slugify, find_files

# Convert text to slugs
slug = slugify("Hello World!")
print(slug)  # "hello-world"

# Find Python files
files = find_files("/path/to/project", "*.py")
print(files)  # ["/path/to/project/app.py", ...]
```

## API Reference

- `slugify(text, separator="-")` — Convert text to URL-friendly slug
- `find_files(directory, pattern="*.py", recursive=True)` — Glob file finder
- `read_json(path)` — Read and parse JSON files
- `write_json(path, data, indent=2)` — Write data to JSON files

## License

MIT License

Step 5: Build the Distribution

Now build your package into distributable formats:

# Install the build tool
pip install build

# Build the package
python -m build

# This creates:
# dist/
# ├── myutils-0.1.0.tar.gz        (sdist - source distribution)
# └── myutils-0.1.0-py3-none-any.whl  (wheel - built distribution)

Two files are created:

  • sdist (.tar.gz): The raw source code. Anyone can download and build it. Required by PyPI.
  • wheel (.whl): A pre-built, optimized distribution. Users get this when they run pip install. Much faster to install than sdist.

Test Install Locally

Before publishing, test your package in a clean virtual environment:

# Create a clean virtual environment
python -m venv test-env
source test-env/bin/activate  # On Windows: test-env\Scripts\activate

# Install from the wheel
pip install dist/myutils-0.1.0-py3-none-any.whl

# Test it works
python -c "from myutils import slugify; print(slugify('Hello World!'))"
# Output: hello-world

# Clean up
deactivate
rm -rf test-env

Step 6: Add Tests (Before Publishing!)

Even a small package should have basic tests:

# myutils/tests/test_core.py
import pytest
from myutils import slugify, find_files


def test_slugify_basic():
    assert slugify("Hello World") == "hello-world"


def test_slugify_special_chars():
    assert slugify("What's Up??!") == "whats-up"


def test_slugify_custom_separator():
    assert slugify("One Two Three", separator="_") == "one_two_three"


def test_slugify_empty():
    assert slugify("") == ""


def test_slugify_numbers():
    assert slugify("Python 3.12") == "python-3-12"


def test_find_files(tmp_path):
    # Create test files
    (tmp_path / "app.py").touch()
    (tmp_path / "data.txt").touch()
    (tmp_path / "config.yaml").touch()

    files = find_files(str(tmp_path), "*.py", recursive=False)
    assert len(files) == 1
    assert "app.py" in files[0]


def test_find_files_recursive(tmp_path):
    # Create nested directory
    subdir = tmp_path / "src"
    subdir.mkdir()
    (subdir / "main.py").touch()
    (tmp_path / "test.py").touch()

    files = find_files(str(tmp_path), "*.py", recursive=True)
    assert len(files) == 2


def test_find_files_no_match(tmp_path):
    (tmp_path / "file.txt").touch()
    files = find_files(str(tmp_path), "*.py")
    assert files == []

# Run tests
pip install pytest
pytest myutils/tests/ -v --tb=short

Step 7: Publish to TestPyPI First

Never publish directly to PyPI on your first attempt. Use TestPyPI — a mirror for testing uploads — before going live.

Create a TestPyPI Account

# 1. Go to https://test.pypi.org/account/register/
# 2. Create an account with your email
# 3. Verify your email address

Generate an API Token

# Go to https://test.pypi.org/manage/account/token/
# Click "Add API token"
# Set scope to "Entire account" (for testing)
# Copy the token — it starts with pypi-

Upload with Twine

# Install twine
pip install twine

# Upload to TestPyPI
twine upload --repository testpypi dist/*
# Username: __token__
# Password: pypi-XXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX

# Verify by installing from TestPyPI
pip install --index-url https://test.pypi.org/simple/ --no-deps myutils

Step 8: Publish to Real PyPI

Once your package works perfectly on TestPyPI, publish for real:

# 1. Create account at https://pypi.org/account/register/
# 2. Verify your email
# 3. Generate token at https://pypi.org/manage/account/token/

# Upload to production PyPI
twine upload dist/*
# Username: __token__
# Password: pypi-XXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX

# Done! Your package is now at:
# https://pypi.org/project/myutils/
# And installable with:
# pip install myutils

Versioning: Semantic Versioning

Follow SemVer (MAJOR.MINOR.PATCH) for your version numbers:

  • MAJOR (1.0.0 → 2.0.0): Breaking changes. Users' code might stop working.
  • MINOR (0.1.0 → 0.2.0): New features, backward compatible.
  • PATCH (0.1.0 → 0.1.1): Bug fixes only, no new features.

You can use bump-my-version to automate version bumps:

# Install
pip install bump-my-version

# Bump version
bump-my-version bump patch  # 0.1.0 → 0.1.1
bump-my-version bump minor  # 0.1.1 → 0.2.0
bump-my-version bump major  # 0.2.0 → 1.0.0

# Rebuild and re-upload
python -m build
twine upload dist/*

Automate with GitHub Actions

Set up a CI workflow that tests and publishes automatically:

# .github/workflows/publish.yml
name: Publish to PyPI

on:
  release:
    types: [published]

jobs:
  publish:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.12"

      - name: Install dependencies
        run: |
          pip install build twine pytest

      - name: Run tests
        run: pytest myutils/tests/ -v

      - name: Build package
        run: python -m build

      - name: Publish to PyPI
        env:
          TWINE_USERNAME: __token__
          TWINE_PASSWORD: ${{ secrets.PYPI_API_TOKEN }}
        run: twine upload dist/

Store your PyPI token as a GitHub secret at Settings → Secrets → PYPI_API_TOKEN. Now every time you create a release on GitHub, the package gets tested and published automatically!

Common Pitfalls and Tips

  • Package name already taken: Check https://pypi.org/project/your-name/ before starting. If it exists, pick a different name — you can't claim it.
  • Forgetting __init__.py: Without this file, Python won't recognize your directory as a package.
  • Version mismatch: Ensure the version in pyproject.toml matches __about__.py. Use the same source of truth.
  • Dependencies in [project] vs [project.optional-dependencies]: Put runtime dependencies in [project].dependencies and dev tools in optional-dependencies.
  • Never delete a version from PyPI: Once published, versions are permanent. Fix bugs with a new version instead.
  • Add a LICENSE file: Most open source packages use MIT or Apache 2.0. Without one, users can't legally use your code.
