Docker HEALTHCHECK: Monitor Container Health and Auto-Restart — Complete Guide

July 14, 2026

By default, Docker considers a container "healthy" if its main process is running. That's dangerously incomplete. Your web server might be running but returning 500 errors, your database might be accepting connections but failing queries, or your API might be stuck in an infinite loop. Docker doesn't know any of this — it only sees that the process hasn't exited.

The HEALTHCHECK instruction changes everything. It lets Docker run a command inside your container at regular intervals to verify it's actually working. When the check fails enough times, Docker marks the container as unhealthy — and when paired with the right restart policy, it will automatically restart it.

In this guide, you'll learn how to add health checks to every type of application, configure Docker Compose to wait for healthy dependencies, and build production-ready monitoring patterns. Every example includes working code you can copy into your own projects.

What Is a Docker HEALTHCHECK?

A HEALTHCHECK is a Dockerfile instruction that tells Docker how to check if your container is working properly. Docker runs the specified command periodically and classifies the container as one of three states:

  • starting — the container hasn't been checked yet or is within the startup grace period
  • healthy — the last health check command returned exit code 0 (success)
  • unhealthy — the health check command has failed enough consecutive times

Check the state anytime with:

# See health status of all containers
docker ps

# Output includes a STATUS column:
# CONTAINER ID   IMAGE          STATUS                    PORTS
# abc123         my-api         Up 2 hours (healthy)      0.0.0.0:8080->8080/tcp
# def456         postgres       Up 2 hours (unhealthy)    0.0.0.0:5432->5432/tcp

# Detailed health information
docker inspect --format='{{json .State.Health}}' <container_id>

The HEALTHCHECK Syntax

The HEALTHCHECK instruction goes in your Dockerfile with these options:

HEALTHCHECK [OPTIONS] CMD command

# Available options:
# --interval=DURATION    How often to run the check (default: 30s)
# --timeout=DURATION     How long to wait for the check to complete (default: 30s)
# --start-period=DURATION Grace period before failing starts count (default: 0s)
# --start-interval=DURATION Check interval during start-period (default: start-period/10, min 1s)
# --retries=N            Consecutive failures before unhealthy (default: 3)

The command runs inside the container. If it returns exit code 0, the container is healthy. Any other exit code means unhealthy.

You can also disable a health check inherited from a base image:

HEALTHCHECK NONE  # Disables any healthcheck from the parent image

Health Checks by Application Type

1. HTTP/HTTPS Web Servers (Python, Node.js, Go, etc.)

The most common pattern: use curl to hit a health endpoint and check the HTTP status code.

# Dockerfile
FROM python:3.12-slim

WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

EXPOSE 8000

# Health check: curl returns 0 if status is 200-399, non-zero otherwise
HEALTHCHECK --interval=15s --timeout=5s --start-period=10s --retries=3 \
    CMD curl -f http://localhost:8000/health || exit 1

CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]

Note that we need curl installed in the image. If your base image doesn't include it (like Python slim images), add it:

# Dockerfile — add curl for health checks
FROM python:3.12-slim

RUN apt-get update && apt-get install -y --no-install-recommends curl \
    && rm -rf /var/lib/apt/lists/*

# ... rest of Dockerfile ...

On the Python side, add a simple health endpoint:

# main.py — FastAPI health endpoint
from fastapi import FastAPI, HTTPException
import psutil

app = FastAPI()

@app.get("/health")
async def health():
    # Basic check — this endpoint existing means the app started
    return {"status": "ok"}

@app.get("/health/deep")
async def deep_health():
    """Check downstream dependencies too"""
    issues = []

    # Check memory usage
    memory = psutil.virtual_memory()
    if memory.percent > 90:
        issues.append(f"High memory: {memory.percent}%")

    # Check your database connection
    # try:
    #     await db.pool.acquire()
    # except Exception as e:
    #     issues.append(f"Database: {e}")

    if issues:
        raise HTTPException(status_code=503, detail={
            "status": "degraded",
            "issues": issues
        })

    return {"status": "ok"}

2. Node.js Applications

Node.js images often don't include curl. Use the built-in node to make HTTP requests:

# Dockerfile — Node.js without installing curl
FROM node:20-slim

WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production
COPY . .

EXPOSE 3000

# Use node itself to check health — no curl needed
HEALTHCHECK --interval=15s --timeout=5s --start-period=10s --retries=3 \
    CMD node -e "const http = require('http'); \
        const req = http.get('http://localhost:3000/health', (res) => { \
            process.exit(res.statusCode === 200 ? 0 : 1); \
        }).on('error', () => process.exit(1));"

CMD ["node", "server.js"]

3. Database Containers (PostgreSQL, MySQL, Redis)

Database containers need application-specific health checks that verify actual connectivity and query ability, not just port listening.

# PostgreSQL Dockerfile with health check
FROM postgres:16-alpine

# Set environment for health check user
ENV POSTGRES_USER=admin
ENV POSTGRES_PASSWORD=secret
ENV POSTGRES_DB=myapp

HEALTHCHECK --interval=10s --timeout=5s --start-period=30s --retries=5 \
    CMD pg_isready -U admin -d myapp || exit 1

# MySQL alternative
# FROM mysql:8.0
# HEALTHCHECK --interval=10s --timeout=5s --start-period=30s --retries=5 \
#     CMD mysqladmin ping -u root -p${MYSQL_ROOT_PASSWORD} || exit 1

# Redis alternative

4. Go Applications (No Dependencies Needed)

Go binaries are self-contained — you don't need curl or any tools. Use the binary itself or wget:

# Dockerfile — Go with minimal dependencies
FROM golang:1.22-alpine AS builder

WORKDIR /build
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /app/server ./cmd/server

# Minimal runtime image — no curl needed
FROM alpine:3.19
RUN apk add --no-cache wget

COPY --from=builder /app/server /server

EXPOSE 8080

HEALTHCHECK --interval=10s --timeout=3s --start-period=5s --retries=3 \
    CMD wget --no-verbose --tries=1 --spider http://localhost:8080/health || exit 1

CMD ["/server"]

5. Python Scripts (Non-Web Applications)

For background workers, Celery, or scripts that don't serve HTTP, check process activity or use a PID file:

# Dockerfile — Python worker with file-based health check
FROM python:3.12-slim

WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .

# Worker writes a heartbeat file every 5 seconds
HEALTHCHECK --interval=15s --timeout=5s --start-period=30s --retries=3 \
    CMD python -c "import time, os; \
        heart = '/tmp/worker_heartbeat.txt'; \
        exit(0 if os.path.exists(heart) and (time.time() - os.path.getmtime(heart)) < 20 else 1)"

CMD ["python", "worker.py"]
# worker.py — heartbeat file
import time
import os
import threading

def write_heartbeat():
    """Write a heartbeat file every 5 seconds"""
    while True:
        with open('/tmp/worker_heartbeat.txt', 'w') as f:
            f.write(str(time.time()))
        time.sleep(5)

# Start heartbeat in a background thread
threading.Thread(target=write_heartbeat, daemon=True).start()

# Your actual worker logic here
def process_tasks():
    while True:
        task = queue.get_task()
        if task:
            process(task)
        time.sleep(1)

process_tasks()

Restart Policies: Auto-Recover from Failures

A health check alone doesn't restart a container — it just marks it unhealthy. Pair it with a restart policy for automatic recovery:

# Docker CLI restart policies
docker run --restart=always my-image          # Always restart unless explicitly stopped
docker run --restart=on-failure:5 my-image    # Restart on failure, max 5 retries
docker run --restart=unless-stopped my-image  # Restart unless you manually stop it

# ⚠️ Important: Docker restart policies do NOT trigger on "unhealthy" status.
# They only restart when the container EXITS (exit code != 0).
# For health-based restarts, you need orchestration (Swarm, Kubernetes, or a wrapper).

Automatic Restart on Unhealthy Status

Since Docker restart policies don't respond to health status, here are the production approaches:

Option A: Docker Compose with Condition-Based Dependencies

# docker-compose.yml — wait for healthy dependencies
version: "3.8"

services:
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: admin
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: myapp
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U admin -d myapp"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 30s

  redis:
    image: redis:7-alpine
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 3s
      retries: 3

  api:
    build: .
    ports:
      - "8000:8000"
    depends_on:
      db:
        condition: service_healthy    # Wait until db is healthy
      redis:
        condition: service_healthy    # Wait until redis is healthy
    healthcheck:
      test: ["CMD-SHELL", "curl -f http://localhost:8000/health || exit 1"]
      interval: 15s
      timeout: 5s
      retries: 3
      start_period: 10s
    deploy:
      restart_policy:
        condition: on-failure
        delay: 5s
        max_attempts: 5
        window: 120s

  # Worker depends on both API and DB being healthy
  worker:
    build:
      context: .
      dockerfile: Dockerfile.worker
    depends_on:
      api:
        condition: service_healthy
      db:
        condition: service_healthy
    restart: on-failure

Option B: Health Check Wrapper Script

For standalone containers (not in Swarm/Kubernetes), use a wrapper that monitors health and restarts:

# health_restart.sh
#!/bin/sh
# Auto-restart container when health check fails

MAX_FAILURES=5
FAILURE_COUNT=0
CHECK_INTERVAL=15

while true; do
    # Run the health check command
    curl -f http://localhost:8000/health >/dev/null 2>&1

    if [ $? -eq 0 ]; then
        FAILURE_COUNT=0
        echo "$(date): HEALTHY"
    else
        FAILURE_COUNT=$((FAILURE_COUNT + 1))
        echo "$(date): UNHEALTHY (failure $FAILURE_COUNT/$MAX_FAILURES)"

        if [ $FAILURE_COUNT -ge $MAX_FAILURES ]; then
            echo "$(date): Too many failures, restarting..."
            exit 1  # This triggers Docker's restart policy
        fi
    fi

    sleep $CHECK_INTERVAL
done
# Dockerfile with health wrapper
FROM python:3.12-slim

RUN apt-get update && apt-get install -y curl

WORKDIR /app
COPY . .
RUN pip install --no-cache-dir -r requirements.txt

COPY health_restart.sh /health_restart.sh
RUN chmod +x /health_restart.sh

# Run the wrapper as the main process
CMD ["/health_restart.sh"]

# Note: Your actual app runs in the background, started by the wrapper
# Or use a multi-stage approach with supervisord

Option C: Docker Swarm Mode (Production)

Docker Swarm automatically handles unhealthy containers:

# Swarm deploys ALWAYS restart unhealthy containers
docker service create \
    --name my-api \
    --replicas 3 \
    --health-cmd "curl -f http://localhost:8000/health || exit 1" \
    --health-interval 15s \
    --health-timeout 5s \
    --health-retries 3 \
    --health-start-period 10s \
    --restart-condition any \
    my-api:latest

# Swarm will kill and replace unhealthy replicas automatically

Best Practices for Production

1. Start Period Matters

Databases and heavy applications take time to initialize. Always set a --start-period so Docker doesn't mark your container unhealthy during startup:

# Good: generous start period for a database
HEALTHCHECK --interval=10s --timeout=5s --start-period=60s --retries=5 \
    CMD pg_isready -U admin || exit 1

# Bad: no start period — fails during initialization
HEALTHCHECK --interval=10s --timeout=5s \
    CMD pg_isready -U admin || exit 1
# This container will be marked unhealthy for ~30-60 seconds at startup

2. Make Health Checks Fast and Reliable

  • Time out quickly — set --timeout to 3-5 seconds. A slow health check blocks Docker
  • Check one thing — your /health endpoint should verify the app is responding, not run complex queries
  • Separate deep checks — create /health/deep for dependency verification; use it for monitoring, not Docker HEALTHCHECK
  • Handle startup gracefully — don't fail health checks during normal initialization

3. Keep Health Check Images Small

If your health check needs curl or wget, install them efficiently:

# ✅ Good: install and clean up in one layer
RUN apt-get update && apt-get install -y --no-install-recommends curl \
    && rm -rf /var/lib/apt/lists/*

# ❌ Bad: unnecessary packages increase image size
RUN apt-get update && apt-get install -y curl

4. Monitor Health Check Failures

Even with auto-restarts, you need to know when containers are failing:

# Check health status of all running containers
docker ps --format "table {{.Names}}\t{{.Status}}"

# Get detailed health log
docker inspect --format='{{json .State.Health.Log}}' my-container

# Count unhealthy containers
docker ps --filter "health=unhealthy" --format "{{.Names}}"

# Alerting script — check all containers
#!/bin/bash
UNHEALTHY=$(docker ps --filter "health=unhealthy" -q | wc -l)
if [ "$UNHEALTHY" -gt 0 ]; then
    echo "🚨 $UNHEALTHY unhealthy containers detected!"
    docker ps --filter "health=unhealthy" --format "{{.Names}}: {{.Status}}"
    # Send alert to Slack/PagerDuty here
fi

Summary

Docker HEALTHCHECK transforms your containers from "running" to "working." Here's the production recipe:

  1. Add HEALTHCHECK to every Dockerfile — HTTP for web apps, native tools for databases
  2. Set --start-period — prevent false negatives during initialization
  3. Use Docker Compose service_healthy conditions — ensure dependency ordering
  4. Pair with restart policies — automatic recovery from transient failures
  5. Monitor health status — alert on unhealthy containers

A container without a health check is a container you're praying to. Add them to every production image — your future self will thank you at 3 AM when something goes wrong.
