Python Context Managers: The "with" Statement Explained — Clean Resource Management

July 3, 2026 · 9 min read

If you've written Python for any amount of time, you've used the with statement — probably for opening files:

with open("data.txt", "r") as f:
    content = f.read()
# File is automatically closed here — even if an error occurred!

That one line does three things behind the scenes: it acquires a resource (opens the file), lets you use it, and cleans up afterward — even if something goes wrong. That pattern is called a context manager, and it's one of Python's most powerful features for writing safe, clean code.

In this tutorial, you'll learn how context managers work under the hood, how to build your own, and the real-world patterns that make them indispensable.

Why Context Managers Matter

Before Python 2.5, managing resources looked like this:

# The old, fragile way
f = open("data.txt", "r")
try:
    content = f.read()
    process(content)  # What if this raises an error?
finally:
    f.close()  # This always runs — good! But verbose.

It works, but it's verbose. And developers forgot the finally block. A lot. Files leaked. Database connections hung. Locks never released.

Context managers solve this with a clean, readable pattern that guarantees cleanup:

# The Pythonic way
with open("data.txt", "r") as f:
    content = f.read()
    process(content)  # Error here? No problem — file still closes.
# File is guaranteed closed at this point.

How Context Managers Work Under the Hood

When Python sees a with statement, it translates it into __enter__ and __exit__ method calls. Here's the exact translation:

# This:
with open("data.txt") as f:
    content = f.read()

# Becomes:
f = open("data.txt")          # Create the context manager
f.__enter__()                  # Acquire resource → return value bound to 'f'
try:
    content = f.read()         # Your code block
finally:
    f.__exit__(None, None, None)  # Clean up (args are exception info)

The __exit__ method receives three arguments: exc_type, exc_value, and exc_traceback. If an exception occurred in the with block, these contain the exception details. If no exception, they're all None.

Building Your Own Context Manager (Class-Based)

Any class with __enter__ and __exit__ methods is a context manager:

class Timer:
    """A context manager that measures execution time."""
    def __init__(self, label="Block"):
        self.label = label
        self.start_time = None

    def __enter__(self):
        import time
        self.start_time = time.time()
        return self  # This is what gets bound to 'as timer'

    def __exit__(self, exc_type, exc_val, exc_tb):
        import time
        elapsed = time.time() - self.start_time
        print(f"{self.label}: {elapsed:.4f} seconds")
        return False  # Don't suppress exceptions

# Use it:
with Timer("Counting to 1M"):
    total = sum(range(1_000_000))
# Output: Counting to 1M: 0.0423 seconds

Key points:

  • __enter__ runs before the block. Its return value binds to the as variable.
  • __exit__ runs after the block, even if an exception occurred.
  • Return False (or None) from __exit__ to let exceptions propagate. Return True to suppress them.

Function-Based Context Managers with contextlib

Writing a full class for simple context managers is overkill. Enter the contextlib module — specifically @contextmanager:

from contextlib import contextmanager
import time

@contextmanager
def timer(label="Block"):
    """Same as the class above, but much shorter."""
    start = time.time()
    yield  # Everything before 'yield' is __enter__
           # Everything after 'yield' is __exit__
    elapsed = time.time() - start
    print(f"{label}: {elapsed:.4f} seconds")

# Use it exactly the same:
with timer("Counting to 1M"):
    total = sum(range(1_000_000))
# Output: Counting to 1M: 0.0423 seconds

The yield keyword is the dividing line: code before it runs as __enter__, code after runs as __exit__. If the block raises an exception, it re-raises at the yield point.

Real-World Pattern: Database Connection Manager

One of the most common use cases: managing database connections safely:

from contextlib import contextmanager
import sqlite3

@contextmanager
def get_db_connection(db_path="app.db"):
    """Open a database connection and ensure it's closed afterward."""
    conn = sqlite3.connect(db_path)
    conn.row_factory = sqlite3.Row  # Access columns by name
    try:
        yield conn
        conn.commit()  # Auto-commit if no exception
    except Exception:
        conn.rollback()  # Rollback on error
        raise
    finally:
        conn.close()  # Always close

# Usage:
with get_db_connection() as conn:
    cursor = conn.execute("SELECT * FROM users WHERE active = ?", (1,))
    users = cursor.fetchall()
    print(f"Found {len(users)} active users")

# Connection is guaranteed closed, even if fetchAll() fails

This pattern — try/except/finally inside the context manager — is the gold standard for resource management. Commit on success, rollback on failure, always close.

Real-World Pattern: Temporary Directory

Create a temporary directory that auto-cleans up:

from contextlib import contextmanager
import tempfile
import shutil
import os

@contextmanager
def temp_directory(prefix="myapp_"):
    """Create a temp directory that gets cleaned up automatically."""
    path = tempfile.mkdtemp(prefix=prefix)
    try:
        yield path
    finally:
        shutil.rmtree(path)  # Clean up everything

# Usage:
with temp_directory() as tmpdir:
    # Create files in the temp directory
    filepath = os.path.join(tmpdir, "output.txt")
    with open(filepath, "w") as f:
        f.write("Processing data...")
    print(f"Working in: {tmpdir}")

# tmpdir is deleted here, including all files inside it

Real-World Pattern: Directory Changer

Safely change directories and return to the original:

from contextlib import contextmanager
import os

@contextmanager
def change_directory(path):
    """Change to a directory and return to the original afterward."""
    original = os.getcwd()
    os.chdir(path)
    try:
        yield
    finally:
        os.chdir(original)

# Usage:
print(os.getcwd())  # /home/user
with change_directory("/tmp"):
    print(os.getcwd())  # /tmp
    # Do stuff in /tmp...
print(os.getcwd())  # /home/user — back where we started!

Nested Context Managers

You can combine multiple context managers. Python 3.1+ lets you stack them with commas:

# Open two files at once (Python 3.1+)
with open("input.txt", "r") as src, open("output.txt", "w") as dst:
    for line in src:
        dst.write(line.upper())
# Both files closed automatically

# Combine custom managers
with get_db_connection() as conn, timer("DB Query"):
    results = conn.execute("SELECT * FROM large_table").fetchall()
    print(f"Got {len(results)} rows")

Suppressing Exceptions

Sometimes you want to catch and handle an exception inside a context manager. Return True from __exit__:

from contextlib import contextmanager

@contextmanager
def suppress_errors(error_types=(Exception,)):
    """Silently catch specified exceptions."""
    try:
        yield
    except error_types as e:
        print(f"Caught and suppressed: {e}")
        return  # Suppress the exception

# Usage:
with suppress_errors():
    result = 10 / 0  # ZeroDivisionError — caught!
# No crash — execution continues normally

# With custom types:
with suppress_errors((ValueError, TypeError)):
    int("not a number")  # ValueError — suppressed
print("Still running!")

Python actually has a built-in version of this: contextlib.suppress():

from contextlib import suppress

with suppress(FileNotFoundError):
    with open("missing.txt") as f:
        data = f.read()
# FileNotFoundError silently swallowed

Real-World Pattern: HTTP Request with Retry

A more advanced example — automatic retry on failure:

from contextlib import contextmanager
import requests
import time

@contextmanager
def http_session(base_url, retries=3, delay=1.0):
    """Create an HTTP session with automatic retry logic."""
    session = requests.Session()
    session.headers.update({"User-Agent": "MyApp/1.0"})
    
    for attempt in range(1, retries + 1):
        try:
            yield session
            break  # Success — exit retry loop
        except requests.RequestException as e:
            if attempt < retries:
                print(f"Attempt {attempt} failed: {e}. Retrying in {delay}s...")
                time.sleep(delay)
            else:
                raise  # Last attempt — re-raise

# Usage:
with http_session("https://api.example.com") as session:
    response = session.get("/users")
    users = response.json()  # Auto-retries if the server is down

ExitStack: Dynamic Context Manager Composition

When you don't know how many context managers you need until runtime:

from contextlib import ExitStack

def process_files(file_paths):
    """Open any number of files and ensure all are closed."""
    with ExitStack() as stack:
        files = [stack.enter_context(open(path, "r")) for path in file_paths]
        # All files are open now
        all_content = [f.read() for f in files]
    # ExitStack closes ALL files in reverse order

# Usage — works with 0 files, 1 file, or 100:
content = process_files(["a.txt", "b.txt", "c.txt"])

Common Mistakes

  1. Forgetting to yield a value: If your @contextmanager doesn't yield, the as variable gets None.
  2. Swallowing exceptions silently: Only suppress exceptions you've explicitly planned for. Returning True from __exit__ hides bugs.
  3. Not cleaning up on exceptions: Always use try/finally in your @contextmanager to guarantee cleanup.
  4. Using context managers for logic: They're for resources, not control flow. Don't put business logic in __enter__.

Summary

# Class-based (full control)
class MyResource:
    def __enter__(self): ...
    def __exit__(self, exc_type, exc_val, exc_tb): ...

# Function-based (concise)
from contextlib import contextmanager

@contextmanager
def my_resource():
    setup()
    yield resource
    cleanup()

# Built-in helpers
from contextlib import suppress, chdir, redirect_stdout, ExitStack

Context managers are Python's answer to "how do I guarantee cleanup?" Whether it's files, databases, locks, temp directories, or HTTP sessions — the with statement gives you a clean, safe, readable pattern that works every time.
