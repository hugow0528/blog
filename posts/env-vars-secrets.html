Environment Variables and Secrets Management for Developers

June 23, 2026 · 9 min read

You've probably seen this before — an API key or database password hardcoded right in the source code:

# WRONG — Never do this
DATABASE_URL = "postgresql://user:***@db.example.com/myapp"
API_KEY = "PLACEHOLDER-KEY"

# This code is about to be pushed to GitHub.
# And then the internet will find your keys.

This is the number one mistake beginners make. Hardcoded credentials end up in Git history, are exposed to everyone with repo access, and become one of the most common sources of real security breaches. Let's learn the right way to handle sensitive configuration data using environment variables and proper secrets management.

What Are Environment Variables?

Environment variables are key-value pairs stored by your operating system. They exist outside your code, in the environment where your application runs. Your program reads them at runtime, so credentials never live in source files.

# Set an environment variable in bash
export API_KEY="my-secret-key-here"

# Read it in bash
echo $API_KEY
# Output: my-secret-key-here

# Read it in Python
import os
api_key = os.environ["API_KEY"]
print(api_key)
# Output: my-secret-key-here

# Read it in JavaScript
const apiKey = process.env.API_KEY;
console.log(apiKey);
# Output: my-secret-key-here

Why this is better:

  • Secrets are never in your source code or version control
  • Different environments (dev, staging, production) use different values
  • Rotate credentials without changing or redeploying code
  • Team members share code without sharing secrets

The .env File Pattern (12-Factor App)

The 12-Factor App methodology recommends storing configuration in environment variables. But typing export commands every time you restart your terminal is painful. Enter the .env file — a local file that your application reads at startup.

Create a .env file in your project root:

# .env file (at project root)
DATABASE_URL=postgresql://user:***@localhost:5432/myapp
API_KEY=your-api-key-here
DEBUG=true
PORT=8000

Load it in Python using the python-dotenv library:

# Install the library
pip install python-dotenv

# app.py
from dotenv import load_dotenv
import os

# Load variables from .env file
load_dotenv()

# Use them
db_url = os.environ["DATABASE_URL"]
api_key = os.environ["API_KEY"]
port = int(os.environ.get("PORT", "8000"))  # default to 8000

print(f"Connecting to: {db_url}")
print(f"Running on port: {port}")

In Node.js, use dotenv:

# Install
npm install dotenv

# index.js
require('dotenv').config();

const dbUrl = process.env.DATABASE_URL;
const apiKey = process.env.API_KEY;
const port = process.env.PORT || 3000;

console.log(`Running on port ${port}`);

CRITICAL: Always Add .env to .gitignore

# .gitignore
# Environment files — NEVER commit these
.env
.env.local
.env.production
.env.staging

# Also ignore common secret files
*.pem
*.key
secrets.*
credentials.*

Add a .env.example file instead — it shows teammates what variables are needed without exposing real values:

# .env.example (this IS committed to Git)
DATABASE_URL=postgresql://user:***@localhost:5432/myapp
API_KEY=your-api-key-here
DEBUG=true
PORT=8000
⚠️ Accidentally committed a .env file? If you accidentally pushed a .env file to Git, the secret is in your repository's history forever. Rotate that key immediately. Use git filter-branch or git filter-repo to remove it from history, but the safest approach is to generate a new secret.

Different Environments, Different Values

A good rule: never use the same credentials for development, staging, and production. Here's the typical setup:

# Project structure with environment files
my-project/
├── .env.example          # Template (committed)
├── .env                  # Local dev (in .gitignore)
├── .env.staging          # Staging (in .gitignore)
├── .env.production       # Production (server only)
├── .gitignore
├── app.py
└── requirements.txt

.env (development — on your laptop):

DATABASE_URL=postgresql://dev:***@localhost:5432/myapp_dev
API_KEY=dev-api-key-placeholder
DEBUG=true
PORT=8000

.env.production (production — on the server only):

DATABASE_URL=postgresql://app:***@prod-db.internal:5432/myapp_prod
API_KEY=prod-api-key-placeholder
DEBUG=false
PORT=80

Managing Secrets in CI/CD (GitHub Actions)

When you automate deployments with CI/CD, your pipeline also needs access to secrets. Never hardcode them in your workflow YAML files.

GitHub Actions approach:

  1. Go to your GitHub repository → Settings → Secrets and variables → Actions
  2. Click "New repository secret"
  3. Add your secrets: DATABASE_URL, API_KEY, etc.
  4. Reference them in your workflow YAML
# .github/workflows/deploy.yml
name: Deploy
on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.12"

      - name: Install dependencies
        run: pip install -r requirements.txt

      - name: Run tests
        run: pytest
        env:
          DATABASE_URL: ${{ secrets.DATABASE_URL }}
          API_KEY: ${{ secrets.API_KEY }}

      - name: Deploy to production
        run: python deploy.py
        env:
          DATABASE_URL: ${{ secrets.DATABASE_URL }}
          API_KEY: ${{ secrets.API_KEY }}

Notice how ${{ secrets.SECRET_NAME }} injects the value at runtime — the actual secret never appears in the YAML file or the commit history.

Docker and Environment Variables

Docker containers also use environment variables. Pass them when running a container:

# Pass a single variable
docker run -e API_KEY=my-key-here myapp

# Pass all variables from a .env file
docker run --env-file .env.production myapp

# In a Dockerfile, set defaults (still overridable at runtime)
FROM python:3.12-slim
WORKDIR /app
COPY . .
RUN pip install -r requirements.txt
ENV DEBUG=false PORT=8000
CMD ["python", "app.py"]

Docker Compose:

# docker-compose.yml
version: "3.9"
services:
  web:
    build: .
    ports:
      - "8000:8000"
    environment:
      - DATABASE_URL=${DATABASE_URL}
      - API_KEY=${API_KEY}
      - DEBUG=${DEBUG}
    env_file:
      - .env

  db:
    image: postgres:16
    environment:
      POSTGRES_USER: ${DB_USER}
      POSTGRES_PASSWORD: ${DB_PASSWORD}
      POSTGRES_DB: ${DB_NAME}

Production-Grade Secrets Management

For serious applications, .env files aren't enough. Consider these tools as you scale:

1. HashiCorp Vault

Enterprise secrets management. Stores, encrypts, and rotates secrets. Integrates with AWS, Kubernetes, and cloud providers.

# Example: Read a secret from Vault in Python
from hvac import Client

vault = Client(url="https://vault.example.com")
secret = vault.secrets.kv.v2.read_secret_version(
    path="production/api",
    mount_point="secret"
)
api_key = secret["data"]["data"]["API_KEY"]

2. AWS Secrets Manager

If you're on AWS, use their built-in secrets manager:

# Retrieve a secret using AWS CLI
aws secretsmanager get-secret-value \
    --secret-name myapp/api-key \
    --query SecretString \
    --output text

# In Python with boto3
import boto3, json

client = boto3.client('secretsmanager')
response = client.get_secret_value(SecretId='myapp/api-key')
api_key = json.loads(response['SecretString'])['API_KEY']

3. Cloudflare Workers Secrets

For edge computing with Cloudflare Workers:

# Add a secret via Wrangler CLI
wrangler secret put API_KEY
# Wrangler will prompt you to type the value securely

# Read it in your Worker code
export default {
    async fetch(request, env) {
        const apiKey = env.API_KEY;
        return new Response(`Key loaded successfully`);
    }
}

Best Practices Checklist

  1. ✅ Never hardcode secrets in source code
  2. ✅ Use environment variables for all sensitive configuration
  3. ✅ .gitignore your .env files — always
  4. ✅ Commit .env.example as a template
  5. ✅ Use different secrets per environment (dev, staging, prod)
  6. ✅ Use CI/CD secret stores (GitHub Secrets, etc.) in pipelines
  7. ✅ Rotate credentials regularly — especially after any potential leak
  8. ✅ Apply least privilege — each secret should have minimum required permissions
  9. ✅ Use a secrets manager (Vault, AWS Secrets Manager) for production
  10. ✅ Scan your repo with tools like gitleaks to detect accidentally committed secrets

Quick gitleaks setup:

# Install gitleaks
pip install gitleaks

# Scan your repository
gitleaks detect --source . --report-format json --report-path leaks.json

# Or as a pre-commit hook to prevent secrets from being committed
pre-commit install --hook-type pre-commit

Summary

Environment variables and proper secrets management separate configuration from code. This isn't just a best practice — it's essential for any application that touches the internet. Start with .env files and .gitignore, graduate to CI/CD secret stores, and eventually adopt a dedicated secrets manager for production workloads.

Remember: every leaked credential in your Git history is a potential breach. Treat secrets with the same care you'd treat money in your wallet.
