Git Rebasing vs Merging: Clean History for Your Projects

July 1, 2026 10 min read New

You've been using git merge for months. It works. But your commit history looks like a tangled spiderweb of merge commits. You've seen other projects with beautiful, linear histories and wondered how they did it.

Enter git rebase — the tool that rewrites your commit history to be clean and linear. But rebase has a reputation for being dangerous. Let's clear that up with practical examples you can run today.

The Two Ways to Combine Branches

Git offers two primary ways to integrate changes from one branch into another:

  • Merge — Creates a new "merge commit" that preserves the full history of both branches
  • Rebase — Moves your commits to "play on top" of the target branch, creating a linear history

Merge: The Safe, Explicit Approach

Let's say you're working on a feature branch called feature/login. Meanwhile, the main branch has received new commits.

# Scenario: main has new commits, you're on feature/login
git checkout feature/login
git merge main

This creates a merge commit:

   feature/login
   A — B — C
          \
main:  D — E — F — M (merge commit)

The merge commit M connects both histories. You can see exactly when and how branches diverged and converged. This is the safer default because it never rewrites history.

When to use merge:

  • Merging a main branch in a shared repository
  • You need to preserve the exact timeline of events
  • Working on public/shared branches where others may have based their work on your commits

Rebase: The Clean History Approach

Now the same scenario, but with rebase:

git checkout feature/login
git rebase main

Git takes your commits (A, B, C), temporarily removes them, fast-forwards to main, then reapplies your commits on top:

   feature/login
               A' — B' — C'
              /
main:  D — E — F

Notice A', B', C' — these are new commits with new hashes. Your history is now perfectly linear. No merge commits cluttering the log.

$ git log --oneline --graph
* C' (feature/login) Fix button styling
* B' Add login form
* A' Create auth module
* F Update dependencies
* E Add user profiles
* D Initial commit

Hands-On: Rebase a Feature Branch

Let's walk through a real example. Create a test repo:

# Create a test project
mkdir git-rebase-demo && cd git-rebase-demo
git init

# Simulate main branch history
echo "# My Project" > README.md
git add README.md
git commit -m "Initial commit"

echo "version 1.0" > version.txt
git add version.txt
git commit -m "Add version file"

# Create feature branch
git checkout -b feature/user-auth
echo "def login(): pass" > auth.py
git add auth.py
git commit -m "Add login function"

echo "def register(): pass" >> auth.py
git add auth.py
git commit -m "Add registration function"

# Go back to main and add more commits
git checkout main
echo "def dashboard(): pass" > views.py
git add views.py
git commit -m "Add dashboard view"

echo "DATABASE_URL=sqlite:///db.sqlite3" > .env
git add .env
git commit -m "Add environment config"

Now rebase your feature branch onto the updated main:

git checkout feature/user-auth
git rebase main

# Check the clean history
git log --oneline --graph

Handling Conflicts During Rebase

Rebase can cause conflicts — just like merge — but the experience is different. With merge, you resolve once. With rebase, you may resolve the same conflict multiple times (once per commit being replayed).

# During a rebase, if a conflict occurs:
# 1. Git stops and tells you which files conflict
# 2. Fix the conflicts in the files
# 3. Tell Git you resolved it:
git add <resolved-file>
git rebase --continue

# If you want to skip this commit entirely:
git rebase --skip

# If you want to abandon the whole rebase:
git rebase --abort

Interactive Rebase: Rewrite Your Commits

This is where rebase becomes a superpower. Interactive rebase lets you edit, squash, reorder, and rewrite your commits before sharing them.

# Rebase the last 3 commits interactively
git rebase -i HEAD~3

Git opens an editor with a list of your commits:

pick a1b2c3d Add login function
pick e4f5g6h Fix login typo
pick i7j8k9l Add registration function

# Rebase onto main (3 commands)
# Commands:
#  pick, reword, edit, squash, fixup, drop

Common interactive rebase operations:

Command What It Does
pick Keep the commit as-is (default)
reword Keep the commit but edit the message
squash Combine with previous commit, merge messages
fixup Combine with previous commit, discard this message
drop Delete this commit entirely

Practical Example: Squash Tiny Commits

Say your branch looks messy with tiny "fix typo" commits:

pick a1b2c3d Add login function
fixup e4f5g6h Fix login typo       # ← squash this away
pick i7j8k9l Add registration function
fixup m3n4o5p Fix registration typo  # ← squash this too

After the interactive rebase, your history becomes:

$ git log --oneline
a1b2c3d Add login function
i7j8k9l Add registration function

Clean, readable, professional. This is what senior developers do before opening a Pull Request.

The Golden Rule: Never Rebase Public Branches

This is the most important rule about rebasing:

Only rebase commits that no one else has based their work on.

If you rebase a shared branch (like main), you rewrite commit hashes that your teammates are already referencing. When they try to push, Git rejects it. When they force-pull, their local history diverges from everyone else's. Chaos ensues.

# ✅ Safe to rebase: your private feature branches
git checkout feature/my-work
git rebase main

# ❌ NEVER do this on shared branches
git checkout main
git rebase origin/old-main  # THIS WILL MAKE YOUR TEAMMATES HATE YOU

My Recommended Workflow

Here's the workflow I use for every project:

# 1. Start your feature branch from main
git checkout main
git pull origin main
git checkout -b feature/user-auth

# 2. Work and commit frequently
echo "login code..." > auth.py
git add auth.py
git commit -m "Add login function"

# 3. Before pushing, clean up your history
git rebase -i HEAD~5
# → squash tiny commits, reword messages, drop WIP commits

# 4. Rebase onto latest main to stay current
git fetch origin
git rebase origin/main

# 5. Push (use --force-with-lease, never --force)
git push origin feature/user-auth --force-with-lease

Notice --force-with-lease instead of --force. The "with-lease" part checks that nobody else has pushed new commits since you last fetched. If they have, Git refuses the push — protecting you from accidentally overwriting someone else's work.

Quick Comparison Cheat Sheet

Merge Rebase
History Branching (graph) Linear
Commit hashes Preserved Changed (rewritten)
Safety Always safe Dangerous on shared branches
Best for Shared/integrated branches Personal feature branches
PR/GitHub Default merge button "Squash and merge" option

Summary

Use merge when integrating into shared branches like main or develop. It's safe, preserves history, and everyone understands it.

Use rebase when cleaning up your personal feature branches before sharing them. Interactive rebase is your best friend for creating clean, professional commit histories.

Never rebase a branch that others have pulled. This is the cardinal sin of Git.

Start by practicing interactive rebase on personal projects. Once you're comfortable, try rebasing feature branches in team projects. Your future self — and your code reviewers — will thank you.
