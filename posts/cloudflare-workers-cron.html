Cloudflare Workers Cron Triggers: Scheduled Tasks on the Edge

2026-06-30 10 min read Cloudflare DevOps

Learn how to schedule automated tasks with Cloudflare Workers Cron Triggers — no server to maintain, no cron daemon to manage. Build periodic API calls, data cleanup jobs, health checks, and automated workflows that run on the global edge.

What Are Cron Triggers?

Cloudflare Workers Cron Triggers let you schedule your Workers to run on a timetable — just like the cron scheduler on Linux, but running on Cloudflare's global network. Instead of maintaining a server just to run scheduled tasks, your code executes on the edge with zero infrastructure overhead.

Cron Triggers are part of the Cloudflare Workers platform and work with any Worker script. You define when the task should run, and Cloudflare invokes your Worker at those times. The Worker receives a special ScheduledEvent instead of an HTTP request.

When to Use Cron Triggers

Before spinning up a separate server or Lambda function for scheduled tasks, consider Workers Cron Triggers for these scenarios:

  • Periodic API polling — check external services, sync data, or fetch updates
  • Data cleanup — expire old records in Workers KV or D1
  • Health monitoring — ping endpoints and send alerts
  • Report generation — aggregate data and send daily summaries
  • Cache warming — pre-fetch and cache frequently accessed content
  • Webhook dispatching — send scheduled notifications to Discord, Slack, or email

Setting Up Your First Cron Worker

Let's build a Worker that runs every 15 minutes to check a service's health and log the result.

Step 1: Create the Project

Initialize a new Worker project using Wrangler:

npx wrangler init health-checker
cd health-checker

Step 2: Write the Worker Code

Edit src/index.js to handle both HTTP requests and scheduled events:

export default {
  // Handle scheduled (cron) invocations
  async scheduled(event, env, ctx) {
    console.log(`Cron triggered at: ${new Date().toISOString()}`);
    console.log(`Cron pattern: ${event.cron}`);

    // Health check your service
    const url = "https://api.example.com/health";
    const response = await fetch(url);
    const status = response.status;

    // Store the result in KV for history
    const timestamp = new Date().toISOString();
    await env.HEALTH_LOG.put(timestamp, JSON.stringify({
      status,
      timestamp,
      uptime: status === 200
    }));

    // Alert if down
    if (status !== 200) {
      await fetch("https://discord.com/api/webhooks/YOUR_WEBHOOK", {
        method: "POST",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify({
          content: `⚠️ Service DOWN! Status: ${status}`
        })
      });
    }
  },

  // Handle regular HTTP requests (optional)
  async fetch(request, env) {
    const url = new URL(request.url);
    if (url.pathname === "/status") {
      // Return the last health check result
      const keys = await env.HEALTH_LOG.list({ limit: 1 });
      const lastCheck = keys.keys[0]?.value;
      return new Response(JSON.stringify(lastCheck), {
        headers: { "Content-Type": "application/json" }
      });
    }
    return new Response("Health Checker Worker", { status: 200 });
  }
};

Step 3: Configure wrangler.toml

Add the cron trigger and KV namespace to your wrangler.toml:

[triggers]
crons = ["*/15 * * * *"]

[[kv_namespaces]]
binding = "HEALTH_LOG"
id = "your-kv-namespace-id"
preview_id = "your-preview-kv-id"

The cron expression */15 * * * * means "every 15 minutes." You can also use human-readable formats like:

  • 0 0 * * * — every day at midnight UTC
  • 0 9 * * 1 — every Monday at 9 AM UTC
  • */5 * * * * — every 5 minutes (min: every minute, max: every minute)

Step 4: Deploy

npx wrangler deploy

That's it! Your cron job is now running on Cloudflare's edge, every 15 minutes, without you managing a single server.

Understanding ScheduledEvent

When a cron trigger fires, your Worker receives a ScheduledEvent with these properties:

// event structure
{
  cron: "*/15 * * * *",      // the cron expression
  scheduledTime: 1234567890  // Unix timestamp of scheduled run
}

Unlike HTTP requests, scheduled events:

  • Have no request object
  • Cannot return HTTP responses
  • Run for up to 15 minutes (Workers execution limit)
  • Have a budget of 500 minutes per account per month (free tier)

Real-World Example: Daily Data Report

Let's build a more practical Worker that generates a daily summary report:

export default {
  async scheduled(event, env, ctx) {
    // Only run on the daily cron (not on preview/manual triggers)
    if (event.cron !== "0 6 * * *") return;

    // Fetch yesterday's data from D1
    const { results } = await env.DB.prepare(
      "SELECT date, COUNT(*) as visits, AVG(response_time) as avg_time \
       FROM analytics \
       WHERE date = date('now', '-1 day') \
       GROUP BY date"
    ).all();

    // Build a summary
    const report = results.map(r =>
      `📊 ${r.date}: ${r.visits} visits, avg ${r.avg_time}ms`
    ).join("\n");

    // Send to Slack/Discord
    await fetch("https://hooks.slack.com/services/YOUR/WEBHOOK", {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({
        text: `Daily Analytics Report:\n${report || "No data today"}`
      })
    });

    // Also store in KV for the dashboard
    await env.REPORTS.put(
      new Date().toISOString().slice(0, 10),
      JSON.stringify({ results, generated_at: new Date().toISOString() })
    );
  }
};

Integrating with Python Backends

If you have a Python backend, your Cron Worker can trigger scheduled jobs:

export default {
  async scheduled(event, env, ctx) {
    // Trigger a Python microservice
    await fetch(`${env.API_URL}/api/daily-tasks`, {
      method: "POST",
      headers: {
        "Authorization": `Bearer ${env.API_TOKEN}`,
        "Content-Type": "application/json"
      },
      body: JSON.stringify({
        triggered_at: new Date().toISOString(),
        cron: event.cron
      })
    });
  }
};

Your Python Flask/FastAPI endpoint then handles the actual work:

# Python FastAPI endpoint
from fastapi import FastAPI, Header

app = FastAPI()

@app.post("/api/daily-tasks")
async def daily_tasks(authorization: str = Header(None)):
    if authorization != f"Bearer {os.environ['API_TOKEN']}":
        raise HTTPException(403)
    
    # Run your scheduled Python tasks
    cleanup_expired_records()
    send_daily_digests()
    update_leaderboard()
    
    return {"status": "ok"}

Error Handling Best Practices

Cron workers can fail silently. Always add proper error handling:

export default {
  async scheduled(event, env, ctx) {
    try {
      await doTheThing(env);
    } catch (error) {
      console.error(`Cron job failed: ${error.message}`);
      
      // Log to KV for debugging
      await env.ERRORS.put(
        new Date().toISOString(),
        JSON.stringify({
          error: error.message,
          stack: error.stack,
          cron: event.cron,
          timestamp: Date.now()
        })
      );

      // Send alert
      await sendAlert(`Cron failed: ${error.message}`);
    }
  }
};

Testing Cron Triggers Locally

You can simulate cron triggers during local development:

# Start the dev server
npx wrangler dev

# In another terminal, trigger the scheduled handler
npx wrangler trigger:scheduled "*/15 * * * *"

Summary

Cloudflare Workers Cron Triggers give you serverless scheduling without managing infrastructure. Key takeaways:

  1. Define cron schedules in wrangler.toml under [triggers]
  2. Handle the scheduled() method in your Worker
  3. Use KV, D1, or external APIs to store results
  4. Add error handling and alerting for reliability
  5. Test locally with wrangler trigger:scheduled

Next time you need a scheduled task, skip the EC2 instance and spin up a cron Worker instead. Deploy in minutes, not hours.
