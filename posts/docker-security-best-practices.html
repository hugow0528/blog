Docker Security Best Practices: Hardening Containers for Production

July 2, 2026 11 min read New

Running Docker containers is convenient, but "it runs" doesn't mean "it's safe." Attackers exploit misconfigured containers every day — from vulnerable base images to privileged containers running as root. This guide covers the essential security practices you need before deploying containers to production.

Why Container Security Matters

Containers share the host kernel. If an attacker escapes a container (through a kernel vulnerability, misconfiguration, or exploit), they have access to the entire host machine. A single vulnerable container can compromise your entire infrastructure. Security isn't optional — it's the difference between "my container got hacked" and "my entire server got hacked."

1. Run Containers as Non-Root Users

By default, containers run as root. This means if someone breaks into the container, they're root inside it — and possibly on the host.

Bad Dockerfile:

FROM python:3.12-slim
COPY app.py /app/
WORKDIR /app
RUN pip install -r requirements.txt
CMD ["python", "app.py"]

This runs as root. Fix it by creating a dedicated user:

FROM python:3.12-slim

# Create a non-root user
RUN groupadd -r appuser && useradd -r -g appuser -d /home/appuser -s /sbin/nologin appuser

# Set ownership
WORKDIR /app
COPY --chown=appuser:appuser . .
RUN pip install --no-cache-dir -r requirements.txt

# Switch to non-root user
USER appuser

CMD ["python", "app.py"]

The --chown flag on COPY ensures files belong to the non-root user. The USER directive switches the container's default user.

Verify it works:

$ docker run --rm myapp id
uid=1001(appuser) gid=1001(appuser) groups=1001(appuser)

2. Use Minimal Base Images

Every package in your image is a potential vulnerability. Choose the smallest base image that works:

# ❌ Full Ubuntu image (~77 MB just for the OS)
FROM python:3.12

# ✅ Slim variant (~150 MB total)
FROM python:3.12-slim

# ✅ Distroless - only your app and runtime (~60 MB)
FROM gcr.io/distroless/python3

The -slim variants remove development tools, documentation, and unnecessary packages. distroless images contain only your application and its runtime — no shell, no package manager, no extra surface area to exploit.

3. Scan Images for Vulnerabilities

Use automated tools to check your images before deploying. Trivy is fast, easy, and catches known CVEs:

# Install Trivy
brew install aquasecurity/trivy/trivy  # macOS
sudo apt install trivy                 # Ubuntu

# Scan your image
trivy image myapp:latest

# Scan in CI/CD with severity filter (fail on HIGH or above)
trivy image --severity HIGH,CRITICAL --exit-code 1 myapp:latest

# Scan Dockerfiles for misconfigurations
trivy config Dockerfile

Example output showing vulnerabilities:

myapp:latest (debian 12.x)
=====================================
Total: 12 (UNKNOWN: 0, LOW: 5, MEDIUM: 4, HIGH: 2, CRITICAL: 1)

CVE-2024-1234  CRITICAL  libssl3
CVE-2024-5678  HIGH      libsystemd0
...

Add scanning to your CI pipeline so vulnerabilities are caught before deployment:

# .github/workflows/security.yml
name: Security Scan
on: [push, pull_request]
jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Build image
        run: docker build -t myapp:test .
      - name: Scan with Trivy
        uses: aquasecurity/trivy-action@master
        with:
          image-ref: "myapp:test"
          format: "table"
          exit-code: "1"
          severity: "HIGH,CRITICAL"

4. Pin Base Image Versions

Never use latest or unpinned tags in production Dockerfiles. They can change unexpectedly and introduce breaking changes or vulnerabilities:

# ❌ Unpinned - could change at any time
FROM python:3.12-slim

# ✅ Pinned to a specific version
FROM python:3.12.4-slim@sha256:abc123def456...

# ✅ At minimum, pin to minor version
FROM python:3.12-slim@sha256:abc123def456...

Use the @sha256: digest for maximum reproducibility. You can find the digest with:

docker pull python:3.12-slim
docker inspect python:3.12-slim --format='{{index .RepoDigests 0}}'

5. Don't Hardcode Secrets

This is the most common and most dangerous mistake. Secrets in Dockerfiles are baked into image layers and visible to anyone with access to the image:

# ❌ NEVER DO THIS
FROM python:3.12-slim
ENV DATABASE_URL="postgresql://user:password123@db.example.com/mydb"
ENV API_KEY="sk-123456789abcdef"

# ❌ Also bad - visible in docker inspect
FROM python:3.12-slim
ARG DB_PASSWORD="password123"
ENV DB_PASSWORD=$DB_PASSWORD

Correct approach: Pass secrets at runtime via environment variables:

# docker-compose.yml
services:
  app:
    build: .
    environment:
      - DATABASE_URL=${DATABASE_URL}
      - API_KEY=${API_KEY}
    # Or mount as files for better security:
    secrets:
      - db_password
      - api_key

secrets:
  db_password:
    file: ./secrets/db_password.txt
  api_key:
    file: ./secrets/api_key.txt

Access mounted secrets in your application:

# In your Python app:
import os

# From environment variable
db_url = os.environ["DATABASE_URL"]

# From mounted secret file
with open("/run/secrets/db_password") as f:
    db_password = f.read().strip()

In production, use a secrets manager (HashiCorp Vault, AWS Secrets Manager, or your cloud provider's equivalent) instead of files.

6. Apply Runtime Security Options

Docker provides runtime flags that restrict what a container can do. Use them aggressively:

# docker-compose.yml
services:
  app:
    build: .
    read_only: true              # Make filesystem read-only
    security_opt:
      - no-new-privileges:true   # Prevent privilege escalation
    cap_drop:
      - ALL                      # Drop ALL Linux capabilities
    cap_add:
      - NET_BIND_SERVICE         # Only add back what's needed
    tmpfs:
      - /tmp:size=64m            # Mount a writable temp directory
    mem_limit: 512m              # Memory limit
    cpus: 1.0                    # CPU limit
    pids_limit: 100              # Process limit (prevents fork bombs)

What each option does:

  • read_only: true — Prevents the container from writing to its filesystem. Attackers can't plant malware or modify configs.
  • no-new-privileges — Blocks setuid/setgid binaries from elevating privileges.
  • cap_drop: ALL — Removes all 39 Linux capabilities. Most apps don't need any.
  • cap_add — Add back only what's needed. Common ones: NET_BIND_SERVICE (ports below 1024), CHOWN (change file ownership).
  • mem_limit and cpus — Prevent resource exhaustion attacks.
  • pids_limit — Limits the number of processes. A fork bomb becomes harmless.

Note: With read_only: true, you need to mount writable directories for any files your app creates (logs, uploads, caches):

volumes:
  - ./data:/app/data
tmpfs:
  - /tmp
  - /run

7. Health Checks for Fast Failure Detection

Health checks let Docker know if your container is actually working, not just running:

# In Dockerfile
HEALTHCHECK --interval=30s --timeout=5s --retries=3 \
  CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:8000/health')" || exit 1

# Or in docker-compose.yml
healthcheck:
  test: ["CMD", "curl", "-f", "http://localhost:8000/health"]
  interval: 30s
  timeout: 5s
  retries: 3
  start_period: 10s

A failing health check doesn't mean your container is hacked — but it means something is wrong and Docker can restart it automatically:

restart: unless-stopped

8. Keep the Docker Daemon Secure

Container security also means securing the Docker daemon itself:

# /etc/docker/daemon.json
{
  "no-new-privileges": true,
  "userns-remap": "default",
  "live-restore": true,
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  }
}

Key daemon settings:

  • no-new-privileges — Default for all containers
  • userns-remap — Maps root inside containers to a non-root user on the host (container escape protection)
  • live-restore — Keeps containers running even if the daemon restarts
  • log-opts — Prevents log files from filling up your disk

Never expose the Docker socket:

# ❌ DANGEROUS - gives root access to the host!
-v /var/run/docker.sock:/var/run/docker.sock

# ✅ Better: use Docker context or a restricted proxy like Tini

Complete Secure Dockerfile Example

Putting it all together:

# syntax=docker/dockerfile:1

FROM python:3.12.4-slim AS builder

WORKDIR /build
COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

FROM python:3.12.4-slim

# Create non-root user
RUN groupadd -r appuser && \
    useradd -r -g appuser -d /home/appuser -s /sbin/nologin appuser

# Install only needed system packages
RUN apt-get update && \
    apt-get install -y --no-install-recommends curl && \
    rm -rf /var/lib/apt/lists/*

# Copy installed packages
COPY --from=builder /install /usr/local

# Copy application
WORKDIR /app
COPY --chown=appuser:appuser . .

# Add health check
HEALTHCHECK --interval=30s --timeout=5s --retries=3 \
  CMD curl -f http://localhost:8000/health || exit 1

# Run as non-root
USER appuser

EXPOSE 8000

CMD ["python", "app.py"]

Summary

Container security boils down to defense in depth: assume your container will be compromised and limit the damage. Run as non-root, scan for vulnerabilities, remove unnecessary capabilities, pin your dependencies, and never bake secrets into images. These practices take about 30 minutes to implement and can save you from a production breach.

Start with the critical items (non-root, no secrets, pinned images), then layer on the rest as you build your pipeline. Secure containers aren't harder to maintain — they're more reliable because they have fewer moving parts to break.
