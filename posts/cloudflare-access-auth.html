Cloudflare Access: Secure Your Apps with Identity-Based Authentication

2026-06-28 11 min read

Cloudflare Access replaces traditional VPNs with a modern, identity-based approach to application security. Instead of trusting users based on their network location (which is unreliable in the age of remote work), Access trusts users based on who they are and what they're authorized to do. It sits between your users and your applications, requiring authentication before anyone can reach your internal tools, admin panels, or APIs.

How Cloudflare Access Works

The architecture is simpler than you might expect. Here's the flow:

  1. User navigates to your protected application (e.g., admin.example.com)
  2. Cloudflare intercepts the request at the edge
  3. Cloudflare checks if the user has a valid session token (Cf-Access-Jwt-Claim)
  4. If not authenticated, the user is redirected to a login page hosted by Cloudflare
  5. User authenticates via your chosen identity provider (email, Google, GitHub, Okta, etc.)
  6. Cloudflare issues a JWT (JSON Web Token) and forwards the request with auth headers
  7. Your app sees the authenticated user via the Cf-Access-Jwt-Assertion header
Key concept: Cloudflare Access runs entirely on Cloudflare's edge network. No agents to install, no servers to manage, no certificates to maintain. Your application doesn't need to know about authentication at all.

Setting Up Your First Access Application

Let's walk through protecting a web application step by step. You'll need a Cloudflare account with Access enabled (free for up to 50 users).

Step 1: Configure DNS

Your application's domain must be proxied through Cloudflare (orange cloud enabled):

# In your Cloudflare dashboard, ensure your DNS record looks like:
# Type: CNAME
# Name: admin
# Target: your-server-ip or your-hostname.com
# Proxy status: Proxied (orange cloud ON)

# Verify with DNS
dig admin.example.com +short
# Should return a Cloudflare IP (e.g., 104.x.x.x)

Step 2: Add an Application in the Dashboard

Navigate to Zero Trust → Access → Applications → Add an Application:

  • Application name: Internal Admin Panel
  • Domain: admin.example.com
  • Public URL: Leave blank (this is an internal app)
  • Session duration: 24 hours (adjust based on your security needs)

Step 3: Configure an Identity Provider

Before you can set up policies, you need an identity provider. Let's use Google as an example:

  • Go to Zero Trust → Access → Settings → Identity Providers
  • Click Add Identity Provider → Google Workspace
  • Follow the OAuth 2.0 setup instructions (Google gives you Client ID and Client Secret)
  • Paste the credentials into Cloudflare

You can also use other providers:

  • One-Time PIN — no setup needed, users get a code via email
  • GitHub — authenticate with GitHub OAuth
  • Okta / Azure AD / SAML — enterprise SSO integration
  • LDAP — connect to your existing directory

Step 4: Create a Policy

Policies define who gets access. Here are common policy types:

Email Policy (Simplest)

# Allow anyone with a specific email domain
# Policy name: Company Employees
# Effect: Allow
# Condition: Email → Email ends with → @company.com

Group Policy (Team-Based)

# Allow members of a specific group (e.g., from Okta or GitHub)
# Policy name: Dev Team Access
# Effect: Allow
# Condition: Groups → Group is one of → dev-team

IP Policy (Network-Based Fallback)

# Allow access from specific IPs (e.g., office network)
# Policy name: Office Network
# Effect: Allow
# Condition: IP address → IP address is one of → 203.0.113.0/24

Using the Cloudflare API for Access Setup

You can manage Access applications programmatically using the Cloudflare API. This is especially useful for Infrastructure-as-Code workflows:

import requests
import json

CF_ACCOUNT_ID = "your_account_id"
CF_API_TOKEN = "your_api_token"

headers = {
    "Authorization": f"Bearer {CF_API_TOKEN}",
    "Content-Type": "application/json"
}

# Create a new Access Application
app_data = {
    "name": "Internal Dashboard",
    "domain": "dashboard.example.com",
    "type": "self_hosted",
    "session_duration": "24h"
}

response = requests.post(
    f"https://api.cloudflare.com/client/v4/accounts/{CF_ACCOUNT_ID}/access/apps",
    headers=headers,
    json=app_data
)

app = response.json()
if app["success"]:
    print(f"✅ Created app: {app['result']['id']}")
    print(f"   Domain: {app['result']['domain']}")
else:
    print(f"❌ Error: {app['errors']}")

# Create a policy for the application
policy_data = {
    "name": "Email Domain Policy",
    "preference": "order",
    "decision": "allow",
    "include": {
        "email": [
            {"email": "name@company.com", "email_status": "verified"}
        ]
    }
}

response = requests.post(
    f"https://api.cloudflare.com/client/v4/accounts/{CF_ACCOUNT_ID}/access/apps/{app['result']['id']}/policies",
    headers=headers,
    json=policy_data
)

if response.json()["success"]:
    print("✅ Policy created successfully")

Reading Access JWT Tokens in Your Application

When a user passes Cloudflare Access authentication, Cloudflare adds JWT headers to every request. Your application can read these to know who the user is:

import re
import jwt  # pip install pyjwt
from flask import Flask, request, jsonify

app = Flask(__name__)

# Base64-encoded public key from Cloudflare dashboard
# (Zero Trust → Access → Service Auth → Public Key)
PEM_KEY = """-----BEGIN CERTIFICATE-----
MIICIjANBgkqhkiG9w0BAQE...
-----END CERTIFICATE-----"""

def decode_access_token():
    """Decode the Cloudflare Access JWT from request headers."""
    token = request.headers.get("Cf-Access-Jwt-Assertion")
    if not token:
        return None

    try:
        decoded = jwt.decode(
            token,
            PEM_KEY,
            algorithms=["RS256"],
            options={"verify_exp": False}  # Cloudflare handles expiration
        )
        return decoded
    except Exception as e:
        print(f"JWT decode error: {e}")
        return None

@app.route("/api/dashboard")
def dashboard():
    """Protected endpoint that requires Cloudflare Access authentication."""
    claims = decode_access_token()

    if not claims:
        return jsonify({"error": "Authentication required"}), 401

    return jsonify({
        "message": "Welcome!",
        "email": claims.get("email"),
        "groups": claims.get("https://cloudflare.com/access/groups", []),
        "expiry": claims.get("exp")
    })

@app.route("/api/admin")
def admin():
    """Protected endpoint with role-based access control."""
    claims = decode_access_token()

    if not claims:
        return jsonify({"error": "Authentication required"}), 401

    # Check for admin group membership
    groups = claims.get("https://cloudflare.com/access/groups", [])
    if "admin" not in groups:
        return jsonify({"error": "Admin access required"}), 403

    return jsonify({"message": "Admin dashboard", "user": claims.get("email")})

if __name__ == "__main__":
    app.run(port=8080)

Service-to-Service Authentication

When a script or service needs to access a protected application (e.g., CI/CD pipelines, monitoring tools), use Service Tokens instead of human authentication:

import requests

# 1. Get a service token (configured in Cloudflare dashboard)
# Zero Trust → Access → Service Auth → Create Service Token

SERVICE_TOKEN_ID = "your_service_token_id"
SERVICE_TOKEN_SECRET = "your_service_token_secret"
CF_ACCOUNT_ID = "your_account_id"

# 2. Exchange the service token for a session cookie
response = requests.post(
    f"https://{CF_ACCOUNT_ID}.cloudflareaccess.com/cdn-cgi/access/login",
    json={
        "service_token": SERVICE_TOKEN_SECRET
    }
)

cookies = response.cookies

# 3. Use the cookies to access the protected application
app_response = requests.get(
    "https://admin.example.com/api/health",
    cookies=cookies
)

print(f"Status: {app_response.status_code}")
print(f"Response: {app_response.text}")

Command-Line Access with cloudflared

For developers who work with CLI tools, the cloudflared browser login allows you to authenticate from the command line:

# Install cloudflared (Linux)
curl -L https://github.com/cloudflare/cloudflared/releases/latest/download/cloudflared-linux-amd64 -o cloudflared
chmod +x cloudflared
sudo mv cloudflared /usr/local/bin

# Browse-login to authenticate (opens browser)
cloudflared access browse admin.example.com

# After authentication, use the token for CLI access
cloudflared access token admin.example.com

# Use with curl by adding the JWT header
TOKEN=$(cloudflared access token admin.example.com)
curl -H "Cf-Access-Jwt-Assertion: $TOKEN" https://admin.example.com/api/users

# Proxy tunnel through cloudflared for direct access
cloudflared access ssh --hostname admin.example.com

Security Best Practices

Getting Access right means thinking about more than just authentication. Here are critical best practices:

1. Use the Principle of Least Privilege

# ❌ Bad: One policy that gives everyone access
# Policy: Everyone → Allow → All company email

# ✅ Good: Separate policies per role
# Policy: Devs → Allow → dev@company.com
# Policy: Admins → Allow → admin@company.com
# Policy: Everyone → Deny (catch-all)

2. Set Reasonable Session Durations

  • High-security apps (financial data, PII): 1–4 hours
  • Internal tools (dashboards, wikis): 8–24 hours
  • Public-facing apps (documentation): 7 days

3. Enable MFA Where Possible

# In your policy conditions, add MFA requirement:
# Condition → MFA → Require MFA

# This forces users to verify with an authenticator app,
# SMS, or hardware token — even after email/SAML login.

4. Audit and Review Policies Regularly

# Use the Cloudflare API to list all policies and review
import requests

headers = {"Authorization": f"Bearer {API_TOKEN}"}

# List all access applications
apps = requests.get(
    f"https://api.cloudflare.com/client/v4/accounts/{CF_ACCOUNT_ID}/access/apps",
    headers=headers
).json()

for app in apps.get("result", []):
    print(f"App: {app['name']}")
    print(f"  Domain: {app['domain']}")
    print(f"  Created: {app.get('created_at', 'N/A')}")

    # List policies for this app
    policies = requests.get(
        f"https://api.cloudflare.com/client/v4/accounts/{CF_ACCOUNT_ID}/access/apps/{app['id']}/policies",
        headers=headers
    ).json()

    for policy in policies.get("result", []):
        print(f"  → Policy: {policy['name']} ({policy['decision']})")

5. Monitor Access Logs

Cloudflare logs every authentication attempt. Use these logs for:

  • Detecting failed login attempts (possible brute force)
  • Auditing who accessed what and when
  • Investigating security incidents
# Query Access logs via the Cloudflare API
response = requests.get(
    f"https://api.cloudflare.com/client/v4/accounts/{CF_ACCOUNT_ID}/access/logs",
    headers=headers,
    params={
        "limit": 50,
        "filter": '{"event_type": ["authentication_failed"]}'
    }
)

for log in response.json().get("result", []):
    print(f"Failed auth: {log.get('email')} at {log.get('timestamp')}")

Cloudflare Access vs Traditional VPN

Here's why Access is often a better choice:

Feature VPN Cloudflare Access
Setup Complex — servers, tunnels, certificates Dashboard configuration only
Granularity Network-wide (all or nothing) Per-app, per-user, per-group
Performance Tunnels all traffic (slow) Only authenticates, doesn't tunnel
Free tier Usually requires paid service Up to 50 users free

Summary

Cloudflare Access gives you enterprise-grade application security without the complexity of VPNs or custom auth systems. The key takeaways:

  • No infrastructure — Access runs on Cloudflare's edge, no servers or agents needed
  • Flexible identity providers — email, Google, GitHub, Okta, SAML, or any combination
  • Fine-grained policies — control access by email, group, IP, or MFA requirement
  • JWT integration — your apps receive structured auth data via standard headers
  • Service tokens — machine-to-machine auth for CI/CD and automation

Start with a simple email policy on one app, then gradually expand to more providers and more granular policies. The free tier (50 users) is generous enough to get started and prove the value.
