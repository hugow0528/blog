Cloudflare Load Balancing: Distribute Traffic Across Multiple Servers

2026-06-28 11 min read New

When your application grows beyond a single server, you need a way to distribute incoming traffic across multiple machines. That's exactly what a load balancer does — it sits in front of your servers and routes each request to the healthiest, most available backend. Cloudflare Load Balancing gives you this capability at the edge, without requiring you to manage dedicated load balancer hardware or software. This guide walks you through the concepts and practical setup from scratch.

Why Use Cloudflare Load Balancing?

Traditional load balancers (like NGINX, HAProxy, or AWS ALB) sit between the user and your servers, making routing decisions based on their own view of health. Cloudflare Load Balancing takes a different approach — it runs at the edge, meaning:

  • Lower latency: Routing decisions happen at the nearest edge location, not at a single data center
  • Better resilience: If one region goes down, traffic automatically shifts to healthy regions worldwide
  • Simpler setup: No infrastructure to provision, patch, or monitor — it's all in the Cloudflare dashboard or API
  • Geographic awareness: Route users to the closest healthy server automatically

Cloudflare Load Balancing is available on the Business plan and above. The free and Pro plans don't include this feature.

Core Concepts: Pools, Monitors, and Load Balancers

Cloudflare Load Balancing has three building blocks. Think of them as a team:

  • Pool — A group of origin servers (your backends) that handle traffic
  • Monitor — Health checks that continuously verify your servers are responding
  • Load Balancer — The routing rule that decides how traffic flows between pools
User → [Cloudflare Edge] → [Load Balancer] → [Pool A: US Servers]
                                               → [Pool B: EU Servers]
                                                       ↑
                                        [Monitor checks every 30s]

Setting Up Your First Pool

A pool is simply a named group of origin servers. Each server needs an IP address, port, and weight (determines traffic share).

In the Cloudflare Dashboard:

  1. Go to your domain → Load Balancing → Pools
  2. Click "Create Pool"
  3. Name it (e.g., us-east-pool)
  4. Set the load balancing method (described below)
  5. Add your origin servers with IP, port, and weight

Using the Cloudflare API with Python:

import requests

API_TOKEN = "your_api_token_here"
ACCOUNT_ID = "your_account_id"

headers = {
    "Authorization": f"Bearer {API_TOKEN}",
    "Content-Type": "application/json"
}

# Create a pool
pool_payload = {
    "name": "us-east-pool",
    "description": "US East Region Servers",
    "minimum_origins": 1,
    "load_balancing_method": "least_connections",
    "origins": [
        {
            "name": "server-1",
            "address": "203.0.113.10",
            "port": 443,
            "weight": 1,
            "enabled": True
        },
        {
            "name": "server-2",
            "address": "203.0.113.11",
            "port": 443,
            "weight": 1,
            "enabled": True
        }
    ]
}

resp = requests.post(
    f"https://api.cloudflare.com/client/v4/accounts/{ACCOUNT_ID}/load_balancers/pools",
    headers=headers,
    json=pool_payload
)

pool = resp.json()["result"]
print(f"Pool created: {pool['id']} ({pool['name']})")
# Save the pool ID for later use
POOL_ID = pool["id"]

Load Balancing Methods

Cloudflare supports several strategies for distributing traffic within a pool:

# 1. round_robin (default)
# Cycles through servers equally: A → B → C → A → B → ...

# 2. least_connections
# Sends traffic to the server with fewest active connections
# Best for: long-lived connections, database connections

# 3. random
# Randomly picks a server
# Best for: stateless APIs, simple web apps

# 4. least_response_time
# Sends traffic to the fastest-responding server
# Best for: performance-critical applications

# 5. observable
# Adaptive — combines latency and connection count
# Best for: production workloads with varying traffic

Setting Up Health Monitors

Monitors continuously check whether your origin servers are healthy. Without monitors, Cloudflare has no way to know if a server has crashed.

Using the API:

# Create a health monitor
monitor_payload = {
    "name": "https-200-check",
    "type": "https",
    "interval": 30,        # Check every 30 seconds
    "timeout": 5,          # Timeout after 5 seconds
    "retries": 3,          # Consider failed after 3 consecutive failures
    "path": "/health",     # URL path to check
    "expected_codes": "2xx",  # Accept any 2xx response
    "expected_body": "OK"    # Optional: check response body
}

resp = requests.post(
    f"https://api.cloudflare.com/client/v4/accounts/{ACCOUNT_ID}/load_balancers/monitors",
    headers=headers,
    json=monitor_payload
)

monitor = resp.json()["result"]
print(f"Monitor created: {monitor['id']}")
MONITOR_ID = monitor["id"]

Monitor types:

  • https — Full HTTPS connection check (recommended)
  • http — HTTP connection check (less secure)
  • tcp — TCP connection check only (fastest, least detailed)
  • ip_ping — ICMP ping check

Important: Make sure your origin servers respond to the health check path. Add a simple /health endpoint:

# Python Flask example
from flask import Flask
app = Flask(__name__)

@app.route("/health")
def health_check():
    return "OK", 200

@app.route("/")
def index():
    return "Hello from my server!"

app.run(host="0.0.0.0", port=443)
# Node.js/Express example
const express = require("express");
const app = express();

app.get("/health", (req, res) => {
    res.status(200).send("OK");
});

app.get("/", (req, res) => {
    res.send("Hello from my server!");
});

app.listen(443, () => console.log("Server running on port 443"));

Creating the Load Balancer

The load balancer ties pools and monitors together and defines the routing rules:

# Create the load balancer
lb_payload = {
    "name": "app.example.com",
    "ttl": 0,          # 0 = always honor health checks
    "fallback_pool": "eu-west-pool-id",  # Used when all primary pools fail
    "proxied": True,    # Enable Cloudflare proxy (orange cloud)
    "steering_policy": "geo",  # Route to nearest healthy region
    "pop_pools": [],
    "regions_pools": [
        {
            "region": "us",
            "pools": [
                {"name": "us-east-pool", "pool_id": POOL_ID}
            ]
        }
    ],
    "monitors": [
        {"name": "https-200-check", "monitor_id": MONITOR_ID}
    ]
}

resp = requests.post(
    f"https://api.cloudflare.com/client/v4/accounts/{ACCOUNT_ID}/load_balancers",
    headers=headers,
    json=lb_payload
)

lb = resp.json()["result"]
print(f"Load balancer created: {lb['id']}")

Steering Policies

The steering_policy determines how Cloudflare picks a pool for each request:

# "off" — Use pool weights only, no geographic steering
# Simplest option — just distribute by weight

# "geo" — Route to the nearest healthy pool based on user location
# Best for: global applications with regional data centers

# "dynamic_latency" — Route to the pool with lowest measured latency
# Best for: performance-first applications

# "off" with weighted pools example:
# Pool A: weight 3 (gets 75% of traffic)
# Pool B: weight 1 (gets 25% of traffic)

Failover Scenarios

Cloudflare Load Balancing handles failures automatically. Here's what happens:

Scenario 1: Single server down
  → Monitor detects failure after 3 retries
  → Traffic shifts to remaining healthy servers in the pool
  → User sees no disruption

Scenario 2: Entire pool goes down
  → Load balancer routes to next pool in priority order
  → If a fallback pool is defined, it handles all traffic
  → You get a dashboard notification

Scenario 3: All pools go down
  → Returns a 522 (Connection Timed Out) or 521 (Web Server Down)
  → Consider setting up a maintenance page as a fallback

You can configure minimum_origins on each pool to define the minimum number of servers needed before the pool is considered healthy:

pool_payload = {
    "name": "us-east-pool",
    "minimum_origins": 2,  # Pool is unhealthy if fewer than 2 servers respond
    "origins": [...]
}

Advanced: Session Affinity (Sticky Sessions)

Some applications need a user to always hit the same server (e.g., shopping carts, login sessions). Cloudflare supports sticky sessions via cookies:

# Add to your load balancer config
lb_payload = {
    ...,
    "session_affinity": "cookie",
    "session_affinity_ttl": 1800,       # Cookie lasts 30 minutes (in seconds)
    "session_affinity_attributes": {
        "samesite": "lax",
        "secure": True,
        "drain": 300                     # Continue honoring cookie for 5 min after creation
    }
}

With sticky sessions enabled, Cloudflare sets a cf_lb_wiz cookie on the client. Subsequent requests with this cookie are routed to the same origin server until the cookie expires.

Real-World Setup: Multi-Region Application

Here's a complete setup for a production application running in two regions:

import requests

ACCOUNT_ID = "your_account_id"
headers = {
    "Authorization": "Bearer your_api_token",
    "Content-Type": "application/json"
}

base_url = f"https://api.cloudflare.com/client/v4/accounts/{ACCOUNT_ID}/load_balancers"

# 1. Create US pool
us_pool = requests.post(f"{base_url}/pools", headers=headers, json={
    "name": "us-pool",
    "minimum_origins": 2,
    "load_balancing_method": "least_connections",
    "origins": [
        {"name": "us-1", "address": "203.0.113.10", "port": 443, "weight": 1, "enabled": True},
        {"name": "us-2", "address": "203.0.113.11", "port": 443, "weight": 1, "enabled": True},
        {"name": "us-3", "address": "203.0.113.12", "port": 443, "weight": 1, "enabled": True}
    ]
}).json()["result"]

# 2. Create EU pool
eu_pool = requests.post(f"{base_url}/pools", headers=headers, json={
    "name": "eu-pool",
    "minimum_origins": 1,
    "load_balancing_method": "least_connections",
    "origins": [
        {"name": "eu-1", "address": "198.51.100.10", "port": 443, "weight": 1, "enabled": True},
        {"name": "eu-2", "address": "198.51.100.11", "port": 443, "weight": 1, "enabled": True}
    ]
}).json()["result"]

# 3. Create health monitor
monitor = requests.post(f"{base_url}/monitors", headers=headers, json={
    "name": "app-health-check",
    "type": "https",
    "interval": 15,
    "timeout": 5,
    "retries": 2,
    "path": "/health",
    "expected_codes": "200-299"
}).json()["result"]

# 4. Create load balancer with geo steering
lb = requests.post(f"{base_url}", headers=headers, json={
    "name": "app.example.com",
    "ttl": 0,
    "proxied": True,
    "fallback_pool": eu_pool["id"],
    "steering_policy": "geo",
    "regions_pools": [
        {"region": "us", "pools": [{"pool_id": us_pool["id"]}]},
        {"region": "eu", "pools": [{"pool_id": eu_pool["id"]}]},
        {"region": "af", "pools": [{"pool_id": eu_pool["id"]}]},
        {"region": "oc", "pools": [{"pool_id": us_pool["id"]}]}
    ],
    "monitors": [{"monitor_id": monitor["id"]}]
}).json()["result"]

print(f"✅ Load balancer ready: {lb['name']}")
print(f"   US Pool: {us_pool['name']} ({len(us_pool['origins'])} servers)")
print(f"   EU Pool: {eu_pool['name']} ({len(eu_pool['origins'])} servers)")
print(f"   Monitor: {monitor['name']} (every {monitor['interval']}s)")

Monitoring & Analytics

Cloudflare provides built-in analytics for your load balancer:

# Query load balancer analytics via API
import requests

# Get pool analytics
resp = requests.get(
    f"{base_url}/analytics",
    headers=headers,
    params={
        "since": "2026-06-27T00:00:00Z",
        "until": "2026-06-28T00:00:00Z"
    }
)

analytics = resp.json()["result"]
for pool in analytics["pools"]:
    print(f"Pool: {pool['pool_id']}")
    print(f"  Total requests: {pool['total_request_count']}")
    print(f"  Success rate: {pool['success']['count']}")
    print(f"  Failures: {pool['failures']['count']}\n")

In the dashboard, you'll also see:

  • Real-time request distribution across pools
  • Health check status for each origin server
  • Error rates by region and pool
  • Latency metrics per pool

Best Practices

1. Always define a fallback pool — your last line of defense
2. Set minimum_origins so a pool with 1 server isn't considered healthy
3. Use HTTPS monitors — they verify the full connection, not just TCP
4. Keep health check paths lightweight — /health should respond in <100ms
5. Use "off" TTL to ensure health checks are always honored
6. Monitor error rates — don't just rely on health checks
7. Test failover — periodically take down a server to verify switching works
8. Use geo steering for global apps, least_response_time for speed
9. Enable sticky sessions only when your app actually needs them
10. Log load balancer decisions for debugging routing issues

Common Issues & Solutions

Problem: "No healthy servers in the pool"
→ Check your origin server IPs are correct
→ Verify the server responds on the expected port
→ Confirm the server isn't blocking Cloudflare IPs

Problem: Health checks failing intermittently
→ Increase the timeout (5s might be too low for slow responses)
→ Add more retries (3 is a good default)
→ Check your server logs for slow responses on /health

Problem: Traffic not splitting as expected
→ Verify pool weights are configured correctly
→ Check steering_policy matches your intent
→ Review the dashboard analytics for actual distribution

Problem: 522 errors appearing
→ This means Cloudflare can't connect to any origin
→ Check all pools and fallback pools are reachable
→ Verify firewall rules allow Cloudflare IP ranges
