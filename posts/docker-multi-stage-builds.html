Docker Multi-Stage Builds: Smaller, Safer Images — Complete Beginner's Guide

July 20, 2026 10 min read

Most beginners create Docker images that are way too large. A Python app running in a full Ubuntu image? That's 700+ MB of OS, compilers, and build tools that your app doesn't need at runtime. Multi-stage builds let you use a fat image for building and a tiny image for running — keeping only what matters. You'll shrink images by 80-90% while improving security and startup time.

The Problem: Bloated Docker Images

Consider this common "first Dockerfile" for a Python web app:

# BEFORE: Single-stage, bloated image
FROM python:3.12

WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

CMD ["python", "app.py"]

This creates an image around 950 MB. Why so big? The python:3.12 base image is built on Debian and includes the entire Python package ecosystem. When you run pip install, you pull in build dependencies (compilers, headers, tools) that are never needed at runtime.

The Solution: Multi-Stage Builds

Multi-stage builds let you use multiple FROM statements in one Dockerfile. Each FROM starts a new "stage." You can copy files between stages with COPY --from=stage_name. The final image only contains the last stage — all intermediate stages are discarded.

# AFTER: Multi-stage, lean image
# Stage 1: Build dependencies
FROM python:3.12-slim AS builder

WORKDIR /build
COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

# Stage 2: Runtime
FROM python:3.12-slim AS runtime

WORKDIR /app
COPY --from=builder /install /usr/local
COPY app.py .

RUN useradd --create-home appuser
USER appuser

CMD ["python", "app.py"]

The runtime image is now around 180 MB — an 80% reduction. The build tools and temporary files from Stage 1 never make it into the final image.

Understanding Stage Names and References

Each stage gets a name with AS <name>. If you don't name a stage, Docker numbers them 0, 1, 2, etc. Named stages are much more readable:

FROM node:20 AS frontend-builder
# Build React/Vue/Angular frontend
WORKDIR /web
COPY package.json package-lock.json ./
RUN npm ci
COPY src/ ./src/
RUN npm run build

FROM python:3.12-slim AS backend-builder
# Install Python dependencies
WORKDIR /api
COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

FROM python:3.12-slim AS runtime
# Assemble final image
WORKDIR /app
COPY --from=backend-builder /install /usr/local
COPY --from=frontend-builder /web/dist ./static
COPY app.py .

CMD ["python", "app.py"]

Here, the runtime stage copies the compiled frontend from frontend-builder and the Python packages from backend-builder. The Node.js image and build tools are completely gone from the final image.

Real-World Example: Go Application

Go is a great example where multi-stage builds shine, because the Go compiler is 300+ MB but the final binary is just a few MB:

# Stage 1: Build the Go binary
FROM golang:1.22-alpine AS builder

WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download

COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -a -installsuffix cgo -o server .

# Stage 2: Tiny runtime
FROM scratch

COPY --from=builder /src/server /server
COPY --from=builder /src/config.yaml /config.yaml

EXPOSE 8080
ENTRYPOINT ["/server"]

The scratch base is literally an empty image. The final image is 15 MB instead of 500+ MB. The binary is fully static (compiled with CGO_ENABLED=0) so it doesn't need any libraries at runtime.

Real-World Example: Node.js API

Node.js apps benefit from separating development dependencies (TypeScript compiler, testing tools) from production dependencies:

# Stage 1: Full build environment
FROM node:20 AS builder

WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci  # Install ALL dependencies (dev + prod)

COPY tsconfig.json ./
COPY src/ ./src/
RUN npm run build  # Compile TypeScript to JavaScript

# Stage 2: Production runtime
FROM node:20-slim AS production

WORKDIR /app

# Copy only production dependencies
COPY package.json package-lock.json ./
RUN npm ci --omit=dev  # Production-only packages

# Copy compiled code from builder
COPY --from=builder /app/dist ./dist

RUN addgroup --system appgroup && \
    adduser --system --ingroup appgroup appuser
USER appuser

EXPOSE 3000
CMD ["node", "dist/index.js"]

The npm ci --omit=dev command installs only production dependencies, skipping TypeScript, testing frameworks, and other dev tools. The dist folder contains the compiled JavaScript from the builder stage.

Security Benefits

Multi-stage builds aren't just about size — they're a security feature:

  1. Smaller attack surface — fewer packages means fewer vulnerabilities
  2. No build tools at runtime — attackers can't use compilers or package managers if they breach your container
  3. Non-root user — the runtime stage can add a dedicated user
  4. Read-only filesystem — without build tools, you can safely run with --read-only
# Security-focused multi-stage build
FROM python:3.12-slim AS builder

WORKDIR /build
COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt
# Optional: run security scan during build
RUN pip install safety && safety check -r requirements.txt

FROM python:3.12-slim AS runtime

# Create non-root user
RUN groupadd --gid 1000 appuser && \
    useradd --uid 1000 --gid 1000 --create-home appuser

WORKDIR /app

# Copy only the installed packages
COPY --from=builder --chown=appuser:appuser /install /usr/local

# Copy application code
COPY --chown=appuser:appuser . .

# Drop root privileges
USER appuser

# Health check
HEALTHCHECK --interval=30s --timeout=5s --retries=3 \
    CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:8000/health')" || exit 1

CMD ["python", "app.py"]

Key security patterns here: the --chown flag on COPY ensures files are owned by the non-root user. The HEALTHCHECK lets Docker monitor if your app is actually running. The safety tool scans for known vulnerable packages during build.

Layer Caching Strategy

Multi-stage builds work with Docker's layer caching, but you need to order your commands carefully for maximum cache hits:

FROM python:3.12-slim AS builder

WORKDIR /build

# 1. Copy only dependency files FIRST (changes rarely)
COPY requirements.txt .

# 2. Install dependencies (cached unless requirements.txt changes)
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

# 3. Copy application code LAST (changes frequently)
COPY . .

FROM python:3.12-slim AS runtime

WORKDIR /app
COPY --from=builder /install /usr/local
COPY --from=builder /build .  # Copy the app code

CMD ["python", "app.py"]

When you change your Python code, Docker reuses the cached dependency installation layer. When you change requirements.txt, it rebuilds from that point. This makes development builds fast.

Debugging Multi-Stage Builds

Sometimes things go wrong. Here's how to debug:

# 1. Build a specific stage to inspect it
docker build --target builder -t myapp-builder .

# 2. Run the intermediate stage to check files
docker run --rm myapp-builder ls -la /install/lib/python3.12/site-packages/

# 3. Build with no cache to force a clean build
docker build --no-cache -t myapp .

# 4. Inspect image layers and size
docker history myapp --no-trunc

# 5. Check final image size
docker images myapp

The --target flag lets you build and run any intermediate stage. This is invaluable when debugging why a file isn't being copied correctly or a dependency isn't available.

Common Patterns and Recipes

Pattern 1: Copy from Multiple Stages

FROM node:20 AS web-builder
WORKDIR /web && COPY web/ ./ && npm ci && npm run build

FROM python:3.12-slim AS api-builder
WORKDIR /api && COPY api/requirements.txt . && \
    pip install --no-cache-dir --prefix=/install -r requirements.txt

FROM python:3.12-slim
COPY --from=api-builder /install /usr/local
COPY --from=web-builder /web/dist ./static
COPY api/ .
CMD ["python", "server.py"]

Pattern 2: Build Tools Stage + Compile + Runtime

# 3-stage: tools → compile → run
FROM gcc:12 AS compiler
WORKDIR /src
COPY Makefile src/ ./
RUN make all

FROM python:3.12-slim AS deps
COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

FROM python:3.12-slim
COPY --from=deps /install /usr/local
COPY --from=compiler /src/my_binary /usr/local/bin/
COPY app.py .
CMD ["python", "app.py"]

Summary

Multi-stage builds are one of the most impactful Docker techniques you can learn. By separating your build environment from your runtime environment, you get images that are smaller (80-90% reduction), safer (no compilers or build tools), and faster to start (less to extract and load). The pattern is simple: use FROM ... AS <name> to define stages, and COPY --from=<name> to move artifacts between them. Your final image only contains the last stage, so everything before it is free.
