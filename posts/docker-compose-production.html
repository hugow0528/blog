Docker Compose for Production: Healthchecks, Logging, Restart Policies & Resource Limits

July 4, 2026 · 11 min read

Your Docker Compose stack works great in development. But production demands more: automatic recovery when containers crash, resource limits to prevent a runaway process from killing the host, log rotation so your disk doesn't fill up, health monitoring so you know when things are down, and secrets management so credentials never end up in plain text.

This guide walks through every production-grade feature of docker-compose.yml with a real-world example that ties everything together. We'll go from a basic dev stack to a hardened production configuration step by step.

1. Start: A Basic Development Stack

Here's a typical development setup — functional but not production-ready:

# docker-compose.yml (dev version)
version: "3.9"
services:
  app:
    build: .
    ports:
      - "8000:8000"
    environment:
      - DATABASE_URL=postgres://user:password@db:5432/myapp
      - SECRET_KEY=mysecretkey123
    depends_on:
      - db
      - redis

  db:
    image: postgres:16
    environment:
      - POSTGRES_USER=user
      - POSTGRES_PASSWORD=password
      - POSTGRES_DB=myapp
    volumes:
      - db_data:/var/lib/postgresql/data

  redis:
    image: redis:7-alpine

volumes:
  db_data:

What's wrong with this for production?

  • No healthchecks — Docker doesn't know if services are actually responding
  • No restart policy — if a container crashes, it stays dead
  • No resource limits — a memory leak will OOM the entire server
  • Secrets in plain text — credentials are visible in environment variables
  • No log rotation — logs grow forever until disk is full
  • No network isolation — all containers on the same default network
  • No read-only filesystems — a compromised container can write anywhere
  • No update strategy — zero-downtime deployments aren't possible

Let's fix every one of these.

2. Healthchecks — Know When Your Services Are Actually Working

A container can be "running" but completely broken. Healthchecks let Docker probe each service and restart it if it's unresponsive:

services:
  app:
    build: .
    healthcheck:
      test: ["CMD", "python", "-c", "import urllib.request; urllib.request.urlopen('http://localhost:8000/health')"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 40s

  db:
    image: postgres:16
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER} -d ${POSTGRES_DB}"]
      interval: 15s
      timeout: 5s
      retries: 5
      start_period: 30s

  redis:
    image: redis:7-alpine
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 15s
      timeout: 5s
      retries: 5

Each parameter explained:

  • test — the command to run. Exit 0 = healthy, exit 1 = unhealthy
  • interval — how often to check (default: 30s)
  • timeout — max time for the check command (default: 30s)
  • retries — failures before marking unhealthy (default: 3)
  • start_period — grace period at startup (service isn't checked during this window)

Key insight: start_period is critical. Without it, your database container might fail the first few healthchecks while it's initializing, get marked unhealthy, restart, and enter a crash loop. Set start_period longer than your service's typical startup time.

Check Health Status

# See health status of all containers
docker compose ps

# Check a specific container's health
docker inspect --format='{{.State.Health.Status}}' myapp_app_1
# → healthy | unhealthy | starting | none

# Get detailed health logs
docker inspect --format='{{json .State.Health}}' myapp_app_1 | python -m json.tool

3. Restart Policies — Automatic Recovery

When a container exits, should Docker restart it? Restart policies control this:

services:
  app:
    restart: unless-stopped

  db:
    restart: unless-stopped

  redis:
    restart: unless-stopped

Restart policy options:

  • no — never restart (default)
  • always — always restart, even if the exit code indicates success
  • on-failure[:max-retries] — restart only on non-zero exit, optionally with a max retry count
  • unless-stopped — always restart unless someone explicitly stopped it (recommended for production)

For production, unless-stopped is usually the right choice. It recovers from crashes and reboots but respects manual stop commands.

4. Resource Limits — Prevent Runaway Processes

Without limits, a single container can consume all CPU or memory on your host, taking down every other service. Set hard boundaries:

services:
  app:
    deploy:
      resources:
        limits:
          cpus: "1.0"
          memory: 512M
        reservations:
          cpus: "0.25"
          memory: 128M

  db:
    deploy:
      resources:
        limits:
          cpus: "2.0"
          memory: 1G
        reservations:
          cpus: "0.5"
          memory: 256M

  redis:
    deploy:
      resources:
        limits:
          cpus: "0.5"
          memory: 256M
        reservations:
          cpus: "0.1"
          memory: 64M

Notes:

  • limits are hard caps — Docker kills the container if exceeded (OOMKilled)
  • reservations are minimums guaranteed to be available
  • CPU values: "0.5" = half a core, "2.0" = two full cores
  • Memory: 256M, 1G, 2G etc.
  • For Docker Compose run (not Swarm), use the mem_limit / cpus top-level keys instead of deploy.resources if you get errors

Alternative (Docker Compose v2 / Compose standalone):

services:
  app:
    mem_limit: 512m
    memswap_limit: 512m  # no swap = hard limit
    cpus: 1.0

5. Logging — Don't Let Logs Fill Your Disk

By default, Docker stores all container logs on disk with no rotation. A single verbose service can fill a 100 GB disk in hours. Configure the JSON file logging driver with rotation:

services:
  app:
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "5"
        compress: "true"
        tag: "{{.Name}}/{{.ID}}"

  db:
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "5"
        compress: "true"

  redis:
    logging:
      driver: json-file
      options:
        max-size: "5m"
        max-file: "3"
        compress: "true"

Options explained:

  • max-size — rotate after this size (e.g., "10m" = 10 megabytes)
  • max-file — keep this many log files
  • compress — gzip rotated logs to save disk space
  • tag — customize the log tag format

For centralized logging (e.g., sending to a log aggregator), you can use alternative drivers:

# Send logs to syslog
logging:
  driver: syslog
  options:
    syslog-address: "tcp://log-server:514"
    tag: "{{.Name}}"

# Send logs to Loki (Grafana)
logging:
  driver: gelf
  options:
    gelf-address: "tcp://loki:3514"
    tag: "{{.Name}}"

6. Secrets Management — Never Hardcode Credentials

Environment variables are visible in docker inspect and can leak in logs. Use Docker secrets instead:

# First, create secret files (these go in .gitignore!)
echo "my-really-secure-password" > ./secrets/postgres_password.txt
echo "super-secret-api-key-abc123" > ./secrets/secret_key.txt
# docker-compose.yml
version: "3.9"
services:
  app:
    build: .
    secrets:
      - secret_key
      - db_password
    # Use secrets as environment variables
    environment:
      - DATABASE_URL=postgres://user:/run/secrets/db_password@db:5432/myapp
      # Or read the file directly in your app code

  db:
    image: postgres:16
    secrets:
      - db_password
    environment:
      - POSTGRES_USER=user
      - POSTGRES_DB=myapp
    # Postgres can read password from file
    # command: ["postgres", "-c", "password_file=/run/secrets/db_password"]

  redis:
    image: redis:7-alpine
    # No password needed for Redis in internal network

secrets:
  secret_key:
    file: ./secrets/secret_key.txt
  db_password:
    file: ./secrets/postgres_password.txt

Inside the container, secrets are mounted at /run/secrets/secret_name as files with 0400 permissions (read-only, owner only). Your application reads them like any file:

# In your Python app
with open("/run/secrets/db_password") as f:
    db_password = f.read().strip()

with open("/run/secrets/secret_key") as f:
    secret_key = f.read().strip()

7. Network Isolation — Don't Let Everything Talk to Everything

By default, all services share the same network. In production, restrict communication:

networks:
  frontend:
    driver: bridge
  backend:
    driver: bridge
    internal: true  # no internet access

services:
  nginx:
    image: nginx:alpine
    ports:
      - "80:80"
      - "443:443"
    networks:
      - frontend
    depends_on:
      - app

  app:
    build: .
    networks:
      - frontend
      - backend
    # App talks to both web (frontend) and database (backend)

  db:
    image: postgres:16
    networks:
      - backend
    # Database has NO internet access - only app can reach it

  redis:
    image: redis:7-alpine
    networks:
      - backend
    # Redis also isolated to backend only

With internal: true on the backend network, the database and Redis cannot access the internet — even if compromised, they can't exfiltrate data or call home. Only the app and nginx touch the frontend network.

8. Read-Only Filesystem — Defense in Depth

By default, containers have full read-write access to their filesystem. Lock it down:

services:
  app:
    read_only: true
    # Allow writes only to specific directories
    tmpfs:
      - /tmp:size=64M
      - /var/run:size=16M
    # If your app needs to write files
    volumes:
      - app_uploads:/app/uploads
      - app_cache:/tmp/cache

  redis:
    read_only: true
    tmpfs:
      - /tmp:size=32M
      - /data:size=128M  # Redis RDB snapshots

With read_only: true, the container's filesystem cannot be modified. If an attacker exploits your app, they can't install tools, modify configs, or drop persistence mechanisms. tmpfs mounts create temporary RAM-based filesystems for directories that legitimately need to write.

9. Complete Production docker-compose.yml

Putting it all together:

# docker-compose.prod.yml
version: "3.9"

services:
  nginx:
    image: nginx:1.25-alpine
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./nginx/conf.d:/etc/nginx/conf.d:ro
      - ./nginx/ssl:/etc/nginx/ssl:ro
    read_only: true
    restart: unless-stopped
    networks:
      - frontend
    depends_on:
      app:
        condition: service_healthy
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"
        compress: "true"
    deploy:
      resources:
        limits:
          cpus: "0.5"
          memory: 128M

  app:
    build:
      context: .
      dockerfile: Dockerfile.prod
    restart: unless-stopped
    read_only: true
    networks:
      - frontend
      - backend
    secrets:
      - secret_key
      - db_password
      - redis_password
    environment:
      - DATABASE_URL=postgres://user@db:5432/myapp
      - REDIS_URL=redis://:default@redis:6379/0
      - PYTHON_ENV=production
      - WORKERS=4
    tmpfs:
      - /tmp:size=64M
    volumes:
      - app_uploads:/app/uploads
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_healthy
    healthcheck:
      test: ["CMD", "python", "-c", "import urllib.request; urllib.request.urlopen('http://localhost:8000/health')"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 40s
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "5"
        compress: "true"
    deploy:
      resources:
        limits:
          cpus: "2.0"
          memory: 512M
        reservations:
          cpus: "0.25"
          memory: 128M

  db:
    image: postgres:16-alpine
    restart: unless-stopped
    networks:
      - backend
    secrets:
      - db_password
    environment:
      - POSTGRES_USER=user
      - POSTGRES_DB=myapp
    volumes:
      - db_data:/var/lib/postgresql/data
    command: ["postgres", "-c", "password_file=/run/secrets/db_password"]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U user -d myapp"]
      interval: 15s
      timeout: 5s
      retries: 5
      start_period: 30s
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "5"
        compress: "true"
    deploy:
      resources:
        limits:
          cpus: "2.0"
          memory: 1G
        reservations:
          cpus: "0.5"
          memory: 256M

  redis:
    image: redis:7-alpine
    restart: unless-stopped
    read_only: true
    networks:
      - backend
    command: ["redis-server", "--requirepass", "$(cat /run/secrets/redis_password)", "--maxmemory", "128mb", "--maxmemory-policy", "allkeys-lru"]
    tmpfs:
      - /data:size=128M
    secrets:
      - redis_password
    healthcheck:
      test: ["CMD", "redis-cli", "-a", "$(cat /run/secrets/redis_password)", "ping"]
      interval: 15s
      timeout: 5s
      retries: 5
    logging:
      driver: json-file
      options:
        max-size: "5m"
        max-file: "3"
        compress: "true"
    deploy:
      resources:
        limits:
          cpus: "0.5"
          memory: 256M
        reservations:
          cpus: "0.1"
          memory: 64M

networks:
  frontend:
    driver: bridge
  backend:
    driver: bridge
    internal: true

volumes:
  db_data:
    driver: local
  app_uploads:
    driver: local

secrets:
  secret_key:
    file: ./secrets/secret_key.txt
  db_password:
    file: ./secrets/postgres_password.txt
  redis_password:
    file: ./secrets/redis_password.txt

10. Deploying and Managing

# Start the production stack
docker compose -f docker-compose.prod.yml up -d

# Check health of all services
docker compose -f docker-compose.prod.yml ps

# View combined logs (with follow)
docker compose -f docker-compose.prod.yml logs -f --tail=100

# Update to new code (zero downtime if healthchecks pass)
docker compose -f docker-compose.prod.yml up -d --build --no-deps app

# Graceful shutdown (waits for healthchecks to go unhealthy)
docker compose -f docker-compose.prod.yml down

# Monitor resource usage
docker stats

11. Production Checklist

Before deploying to production, verify:

✅ Healthchecks configured for every service
✅ Restart policies set (unless-stopped recommended)
✅ Resource limits defined (CPU + memory)
✅ Log rotation enabled (max-size + max-file)
✅ Secrets used instead of hardcoded passwords
✅ Network isolation (frontend vs backend)
✅ Read-only filesystems where possible
✅ depends_on with healthcheck conditions
✅ Non-root user in Dockerfile (USER directive)
✅ Specific image tags (not "latest")
✅ TLS/SSL configured (nginx reverse proxy)
✅ Backup strategy for volumes (database snapshots)
✅ Monitoring/alerting set up (Prometheus, health check dashboards)
✅ .gitignore excludes secrets/ directory

Summary

A production-ready Docker Compose stack is built layer by layer. Start with the basics — your containers work. Then add healthchecks so you know when they're broken. Add restart policies so they recover automatically. Add resource limits so one container can't starve the others. Add logging configuration so your disk survives. Add secrets so credentials stay safe. Add networks so compromise doesn't spread.

Each layer independently makes your stack more resilient. Together, they turn a dev toy into production infrastructure that runs reliably for months without intervention.
