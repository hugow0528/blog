Penetration Testing Basics: How to Hack Your Own Applications Safely

July 9, 2026 · 12 min read

Penetration testing — also called ethical hacking or "pentesting" — is the practice of deliberately trying to break into your own systems to find security weaknesses before malicious attackers do. Think of it as hiring a burglar to test your locks, so you know exactly which ones need reinforcing.

Whether you're a developer, sysadmin, or security beginner, understanding the pentesting process will make you write more secure code and configure safer infrastructure. This guide walks through the five phases of penetration testing with hands-on examples using real, freely available tools.

The Five Phases of Penetration Testing

Every professional penetration test follows a structured methodology. The most common framework includes five phases:

  1. Reconnaissance — Gather information about the target
  2. Scanning — Discover open ports, services, and vulnerabilities
  3. Gaining Access — Exploit found vulnerabilities
  4. Maintaining Access — Test persistence mechanisms
  5. Covering Tracks & Reporting — Clean up and document findings
Golden rule: Never test a system you don't own or have written permission to test. Unauthorized access is illegal everywhere. Practice only on your own labs or platforms designed for learning (TryHackMe, HackTheBox, OverTheWire).

Phase 1: Reconnaissance (Information Gathering)

Reconnaissance is about collecting as much information as possible about your target. The more you know, the easier it becomes to find weak points. There are two types:

Passive Reconnaissance

Gathering info without touching the target's systems — everything comes from public sources.

# Who owns this domain?
whois example.com

# What DNS records exist?
dig example.com ANY

# Find subdomains using public data
subfinder -d example.com

# Search for leaked credentials
# (Check Have I Been Pwned or BreachDirectory)

Active Reconnaissance

Directly interacting with the target to gather information. This is more detectable but more accurate.

# Enumerate open ports (quick scan)
nmap -sV -T4 --top-ports 100 192.168.1.100

# Full scan with OS detection
nmap -A -T4 192.168.1.100

# Scan entire subnet
nmap -sn 192.168.1.0/24

# Detect specific services in detail
nmap -sC -p 80,443,22,3306 example.com

Here's what a typical nmap output looks like and how to read it:

PORT     STATE  SERVICE  VERSION
22/tcp   open   ssh      OpenSSH 8.9p1 Ubuntu
80/tcp   open   http     Apache httpd 2.4.54
443/tcp  open   ssl/http Apache httpd 2.4.54
3306/tcp open   mysql    MySQL 8.0.32
8080/tcp open   http     Node.js Express

# Translation: This server runs SSH, Apache web server,
# MySQL database (exposed! bad practice), and an
# application on port 8080. That's 5 attack surfaces.

Phase 2: Scanning for Vulnerabilities

Once you know what services are running, the next step is checking for known vulnerabilities in those services. Automated vulnerability scanners make this easier.

Web Application Scanning with Nikto

# Install (Kali Linux / Parrot OS)
sudo apt install nikto

# Scan a web application
nikto -h https://example.com

# Scan with specific SSL check
nikto -h https://example.com -ssl

# Save results to file
nikto -h https://example.com -o report.txt -Format txt

Nikto checks for common issues like outdated software versions, misconfigured headers, default admin pages, and known CVEs (Common Vulnerabilities and Exposures).

Directory Enumeration

Web apps often have hidden pages or directories that aren't linked from the main site. These can expose admin panels, API endpoints, or sensitive files.

# Gobuster - directory brute force
gobuster dir -u https://example.com -w /usr/share/wordlists/dirb/common.txt

# ffuf - faster alternative
ffuf -u https://example.com/FUZZ -w /usr/share/wordlists/dirb/common.txt

# Find specific file types
gobuster dir -u https://example.com -w common.txt -x php,html,txt,json,env

Manual Security Header Check

Always check your web app's security headers. Missing headers are an easy win for attackers.

# Python script to check security headers
import requests

url = "https://example.com"
headers = requests.get(url).headers

security_headers = {
    "Strict-Transport-Security": "Forces HTTPS connections",
    "Content-Security-Policy": "Blocks unauthorized scripts",
    "X-Content-Type-Options": "Prevents MIME type sniffing",
    "X-Frame-Options": "Prevents clickjacking",
    "X-XSS-Protection": "Legacy XSS protection",
    "Referrer-Policy": "Controls referrer information",
    "Permissions-Policy": "Restricts browser features",
    "Cache-Control": "Controls caching behavior"
}

print("Security Header Report:")
print("-" * 50)
for header, description in security_headers.items():
    status = "✅" if header in headers else "❌"
    print(f"{status} {header}: {description}")

Phase 3: Gaining Access (Exploitation)

This phase involves actually exploiting the vulnerabilities you found. In ethical hacking, you stop as soon as you prove access — you don't go deeper than necessary.

Common Web Vulnerabilities

The OWASP Top 10 lists the most critical web security risks. Here are the ones beginners encounter most:

1. SQL Injection

Occurs when user input is directly inserted into SQL queries without sanitization.

# ❌ VULNERABLE - Python Flask example
@app.route('/login')
def login():
    username = request.args.get('username')
    query = f"SELECT * FROM users WHERE name = '{username}'"
    # Attacker sends: username = admin'--
    # Query becomes: SELECT * FROM users WHERE name = 'admin'--'
    # The -- comments out the rest, bypassing authentication!
    results = db.execute(query)

# ✅ SECURE - Parameterized query
@app.route('/login')
def login():
    username = request.args.get('username')
    # Parameters are properly escaped
    results = db.execute(
        "SELECT * FROM users WHERE name = ?",
        (username,)
    )

2. Cross-Site Scripting (XSS)

Occurs when user input is rendered as HTML/JavaScript without escaping.

# ❌ VULNERABLE
@app.route('/search')
def search():
    query = request.args.get('q', '')
    return f'<h1>Results for: {query}</h1>'
    # Attacker sends: ?q=<script>alert('XSS')</script>

# ✅ SECURE - Escape HTML output
from markupsafe import escape

@app.route('/search')
def search():
    query = request.args.get('q', '')
    return f'<h1>Results for: {escape(query)}</h1>'
    # Output: Results for: <script>alert('XSS')</script>
    # Displayed as text, not executed as code

3. Broken Authentication

# ❌ VULNERABLE - Weak password requirements
def register(username, password):
    # No validation! User can set password as "1"
    hash_password(password)
    save_user(username, hash_password)

# ✅ SECURE - Password validation
import re

PASSWORD_PATTERN = re.compile(
    r'^(?=.*[a-z])'       # at least one lowercase
    r'(?=.*[A-Z])'       # at least one uppercase
    r'(?=.*\d)'          # at least one digit
    r'(?=.*[@$!%*?&])'  # at least one special char
    r'.{8,}$'             # at least 8 characters
)

def validate_password(password):
    if not PASSWORD_PATTERN.match(password):
        raise ValueError(
            "Password must be 8+ chars with upper, "
            "lower, digit, and special character"
        )

Phase 4: Maintaining Access

In a real pentest, you'd test whether an attacker could establish persistent access. For learning, you can simulate this with simple techniques:

Check for Backdoors

# Look for unauthorized cron jobs
crontab -l
sudo cat /etc/crontab

# Check for unknown SSH keys
cat ~/.ssh/authorized_keys

# Look for suspicious processes
ps aux | grep -i backdoor
netstat -tlnp  # check for unusual listening ports

# Check for recently modified files
find /var/www -mtime -7 -type f
find /etc -mtime -7 -type f

Test Default Credentials

# Many services ship with default credentials
# Common defaults to check:

# WordPress: admin / admin or admin / password
# MySQL: root / (blank)
# Tomcat: admin / admin
# Redis: no password by default
# Elasticsearch: elastic / changeme

# Python script to test common credentials
import requests

def test_default_credentials(url, username, password):
    try:
        response = requests.get(url, auth=(username, password), timeout=5)
        if response.status_code == 200:
            print(f"⚠️  DEFAULT ACCESS: {username}:{password}")
            return True
    except requests.RequestException:
        pass
    return False

# Test common combinations
defaults = [
    ("admin", "admin"),
    ("admin", "password"),
    ("root", "toor"),
    ("user", "user"),
]

for user, pwd in defaults:
    test_default_credentials(
        "http://192.168.1.100:8080/admin",
        user, pwd
    )

Phase 5: Reporting

A penetration test is worthless without a clear report. Every finding should include:

  • Vulnerability name — e.g., "SQL Injection on Login Form"
  • Severity — Critical, High, Medium, Low, Informational
  • Proof of concept — The exact steps to reproduce
  • Impact — What could an attacker do with this?
  • Remediation — How to fix it (with code examples)
# Example report entry:
## [HIGH] SQL Injection on /api/users endpoint

**Location:** GET /api/users?id=1
**Severity:** HIGH (CVSS 8.6)

**Proof of Concept:**
1. Send request: GET /api/users?id=1' UNION SELECT password FROM admin--
2. Server returns admin password in JSON response

**Impact:** Full database access, including admin credentials
**CVSS Vector:** CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:N

**Remediation:**
Use parameterized queries in all database operations:
    cursor.execute("SELECT * FROM users WHERE id = %s", (user_id,))

**Status:** Pending Fix

Build a Home Lab for Practice

You need safe environments to practice. Here's how to set one up with Docker:

# docker-compose.yml for a security lab
version: '3.8'
services:
  # OWASP Juice Shop - intentionally vulnerable web app
  juice-shop:
    image: bkimminich/juice-shop
    ports:
      - "3000:3000"
    restart: unless-stopped

  # OWASP WebGoat - interactive security lessons
  webgoat:
    image: webgoat/webgoat
    ports:
      - "8080:8080"
    restart: unless-stopped

  # DVWA - Damn Vulnerable Web Application
  dvwa:
    image: vulnerables/web-dvwa
    ports:
      - "8888:80"
    environment:
      - DB_PASSWORD=p@ssw0rd
    restart: unless-stopped

  # Metasploitable2 - vulnerable VM for practice
  metasploitable:
    image: cibuilds/metasploitable2
    ports:
      - "2222:22"
      - "4444:4444"
      - "8000:80"
      - "33060:3306"
# Start your lab
docker compose up -d

# Verify everything is running
docker compose ps

# Now practice!
# - Juice Shop (port 3000): Browse and exploit vulnerabilities
# - WebGoat (port 8080): Follow guided security lessons
# - DVWA (port 8888): Practice OWASP Top 10 attacks
# - Metasploitable (port 2222): Practice network penetration

Legal and Ethical Considerations

Before you start pentesting, understand the rules:

  • Get written permission — A "verbal yes" isn't enough. Have a signed engagement letter.
  • Define scope — Which systems? What tests? Time limits?
  • Don't harm production — Never run destructive tests on live systems.
  • Protect your data — If you find real credentials, treat them confidentially.
  • Report responsibly — Share findings only with authorized parties.
  • Know your local laws — Computer fraud laws vary by country but unauthorized access is nearly always criminal.
