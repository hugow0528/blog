Docker Volumes & Data Persistence: Don't Lose Your Data

June 26, 2026 · 12 min read

Here's the biggest Docker trap for beginners: everything inside a container is temporary. When you run docker rm -f mydb, every file, every database record, every config file disappears. Gone forever.

Docker volumes solve this. They let you store data outside the container, so it survives restarts, upgrades, and even container deletion. This guide covers all three persistence methods: named volumes, bind mounts, and tmpfs mounts.

The Problem: Ephemeral Containers

Run a database container and create data:

# Start a Redis container
docker run --name myredis -d redis:7

# Write data to it
docker exec myredis redis-cli SET greeting "hello from docker"
docker exec myredis redis-cli GET greeting
# "hello from docker"

# Remove the container
docker rm -f myredis

# Start a fresh container
docker run --name myredis -d redis:7
docker exec myredis redis-cli GET greeting
# (nil)  ← Data is gone!

This happens because container storage lives on a temporary filesystem layer. Remove the container, remove the data. For databases, logs, and uploads — this is a disaster waiting to happen.

Solution 1: Named Volumes (Recommended for Databases)

Named volumes are Docker-managed storage. Docker stores them in /var/lib/docker/volumes/ on Linux. You reference them by name — Docker handles the rest.

Create and use a named volume

# Create a named volume (Docker manages it)
docker volume create redis_data

# Mount it to the container
docker run --name myredis \
    -d \
    -v redis_data:/data \
    redis:7

# Write data
docker exec myredis redis-cli SET greeting "hello again"

# Remove and recreate the container
docker rm -f myredis

docker run --name myredis \
    -d \
    -v redis_data:/data \
    redis:7

# Data is still there!
docker exec myredis redis-cli GET greeting
# "hello again"  ✅

The -v redis_data:/data flag maps the named volume redis_data to the /data path inside the container. Docker creates the volume automatically if it doesn't exist.

Manage volumes

# List all volumes
docker volume ls
# local   redis_data

# Inspect a volume (see mount location)
docker volume inspect redis_data
# "Mountpoint": "/var/lib/docker/volumes/redis_data/_data"

# Remove unused volumes
docker volume prune

# Remove a specific volume
docker volume rm redis_data

Share data between containers

# Container 1 writes data
docker run --name writer \
    -v shared_data:/shared \
    -d alpine sh -c "echo 'from writer' > /shared/data.txt && sleep 3600"

# Container 2 reads the same data
docker run --name reader \
    -v shared_data:/shared \
    alpine cat /shared/data.txt
# from writer

Solution 2: Bind Mounts (For Development)

Bind mounts map a specific host directory into the container. You pick the exact path. This is perfect for development — edit code on your host, see changes instantly in the container.

# Mount your project directory
docker run --name webapp \
    -p 8080:8080 \
    -v $(pwd)/app:/usr/src/app \
    -v $(pwd)/app/node_modules:/usr/src/app/node_modules \
    node:20-alpine \
    sh -c "cd /usr/src/app && npm start"

Now any file change in your local app/ directory is visible inside the container immediately. No rebuild needed.

Bind mount with docker-compose.yml

services:
  webapp:
    build: .
    ports:
      - "8080:8080"
    volumes:
      - ./src:/usr/src/app      # Mount source code
      - node_modules:/usr/src/app/node_modules  # Named vol for deps
    environment:
      - NODE_ENV=development

volumes:
  node_modules:

Why use a named volume for node_modules? Because if you bind mount ./src, your host's node_modules (built for your OS) would overwrite the container's (built for Linux), breaking things. The named volume keeps dependencies container-native.

Solution 3: tmpfs Mounts (In-Memory, for Secrets)

tmpfs mounts store data in RAM only — fast, but lost when the container stops. Perfect for sensitive data like passwords, API keys, or temporary session data.

# Mount /secrets as tmpfs (in RAM, not on disk)
docker run --name secure_app \
    --tmpfs /secrets:rw,noexec,nosuid,size=100m \
    my-app:latest

Benefits:

  • No disk writes — secrets never touch the filesystem
  • Auto-deleted — data gone when container stops
  • Fast — RAM is faster than disk

Comparison: When to Use What

┌──────────────────┬──────────────┬──────────────┬──────────────┐
│                  │ Named Volume │ Bind Mount   │ tmpfs Mount  │
├──────────────────┼──────────────┼──────────────┼──────────────┤
│ Managed by       │ Docker       │ You          │ Docker       │
│ Persistence      │ ✅ Persistent│ ✅ Persistent│ ❌ In-memory │
│ Best for         │ Databases    │ Dev source   │ Secrets      │
│ Backup           │ docker cp    │ cp on host   │ N/A          │
│ Cross-platform   │ ✅ Yes       │ ⚠️ Path diffs│ ✅ Yes       │
│ Performance      │ Good         │ Good         │ Best (RAM)   │
└──────────────────┴──────────────┴──────────────┴──────────────┘

Real-World Example: Full-Stack App with Docker Compose

Let's build a complete app stack with proper data persistence:

# docker-compose.yml
services:
  # Web app
  web:
    build: ./web
    ports:
      - "3000:3000"
    volumes:
      - ./web/src:/app/src        # Live code reload
      - uploads:/app/uploads      # User file uploads
    depends_on:
      - db
      - cache
    environment:
      - DATABASE_URL=postgresql://user:pass@db:5432/myapp
      - REDIS_URL=redis://cache:6379

  # PostgreSQL database
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: user
      POSTGRES_PASSWORD: pass
      POSTGRES_DB: myapp
    volumes:
      - pgdata:/var/lib/postgresql/data   # Persistent DB
      - ./db/init.sql:/docker-entrypoint-initdb.d/init.sql  # Seed data
    ports:
      - "5432:5432"

  # Redis cache
  cache:
    image: redis:7-alpine
    volumes:
      - redis_data:/data
    ports:
      - "6379:6379"

volumes:
  pgdata:         # Database files survive restarts
  redis_data:     # Cache survives restarts
  uploads:        # User uploads survive restarts

Create a seed script db/init.sql:

-- db/init.sql
CREATE TABLE IF NOT EXISTS users (
    id SERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(255) UNIQUE NOT NULL,
    created_at TIMESTAMP DEFAULT NOW()
);

INSERT INTO users (name, email) VALUES
    ('Hugo', 'hugo@example.com'),
    ('Alice', 'alice@example.com');

Start everything:

docker compose up -d

# Check all containers are running
docker compose ps
# NAME      STATUS    PORTS
# web       Up        0.0.0.0:3000->3000
# db        Up        0.0.0.0:5432->5432
# cache     Up        0.0.0.0:6379->6379

# Test database connection
docker compose exec db psql -U user -d myapp -c "SELECT * FROM users;"

# Stop and restart — data survives
docker compose down
docker compose up -d
docker compose exec db psql -U user -d myapp -c "SELECT count(*) FROM users;"
# count = 2  ✅

Back Up and Restore Volumes

Named volumes need backups too. Here's how:

Backup a volume

# Backup PostgreSQL volume to a tar file
docker run --rm \
    -v pgdata:/db \
    -v $(pwd):/backup \
    alpine \
    tar czf /backup/pg_backup_$(date +%Y%m%d).tar.gz -C /db .

# Check the backup
ls -lh pg_backup_*.tar.gz
# -rw-r--r-- 1 user user 2.4M Jun 26 pg_backup_20260626.tar.gz

Restore a volume

# Stop containers using the volume
docker compose down

# Remove existing volume
docker volume rm pgdata

# Restore from backup
docker run --rm \
    -v pgdata:/db \
    -v $(pwd):/backup \
    alpine \
    sh -c "cd /db && tar xzf /backup/pg_backup_20260626.tar.gz"

# Restart
docker compose up -d

Automated daily backups

Create backup.sh:

#!/bin/bash
BACKUP_DIR="$HOME/docker-backups"
DATE=$(date +%Y%m%d_%H%M%S)

mkdir -p "$BACKUP_DIR"

# Backup PostgreSQL
docker run --rm \
    -v pgdata:/db \
    -v "$BACKUP_DIR":/backup \
    alpine tar czf "/backup/pg_$DATE.tar.gz" -C /db .

# Backup Redis
docker run --rm \
    -v redis_data:/data \
    -v "$BACKUP_DIR":/backup \
    alpine tar czf "/backup/redis_$DATE.tar.gz" -C /data .

# Keep only last 7 days
find "$BACKUP_DIR" -name "*.tar.gz" -mtime +7 -delete

echo "✅ Backed up at $DATE"

Add to crontab for daily backups at 2 AM:

0 2 * * * /path/to/backup.sh >> /var/log/docker-backup.log 2>&1

Volume Permissions: The #1 Gotcha

Permission errors are the most common volume issue. Docker containers often run as root (UID 0), but your host directory might be owned by your user (UID 1000).

# The error you'll see:
# EACCES: permission denied, open '/usr/src/app/config.yml'

# Fix: Set the correct ownership
sudo chown -R 1000:1000 ./my-project

# Or run the container with matching UID
docker run -u $(id -u):$(id -g) -v $(pwd):/app myapp

# In docker-compose.yml:
services:
  web:
    user: "${UID:-1000}:${GID:-1000}"
    volumes:
      - .:/app

Docker Volume Drivers

Docker supports volume drivers for advanced scenarios:

# Local driver (default)
docker volume create --driver local my_vol

# NFS driver for shared storage across hosts
docker volume create --driver local \
    --opt type=nfs \
    --opt o=addr=192.168.1.100,rw \
    --opt device=:/srv/nfs \
    nfs_shared

# AWS EBS driver (via Docker plugin)
docker volume create --driver ebs my_ebs_vol
Rule of thumb: Use named volumes for databases and any data you can't afford to lose. Use bind mounts for development code. Use tmpfs for secrets and temporary data.

Quick Commands Reference

# Volume basics
docker volume create my_vol         # Create
docker volume ls                     # List all
docker volume inspect my_vol        # Details + location
docker volume rm my_vol             # Remove one
docker volume prune                 # Remove all unused

# Container with volume
docker run -v my_vol:/data container  # Named volume
docker run -v ./host:/data container   # Bind mount
docker run --tmpfs /tmp container      # In-memory

# Backup
docker run --rm -v my_vol:/src -v $(pwd):/dst alpine tar czf /dst/backup.tar.gz -C /src .

# Docker Compose
docker compose up -d                 # Start with volumes
docker compose down -v              # Stop AND remove volumes!
