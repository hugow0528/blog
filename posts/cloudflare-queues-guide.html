Cloudflare Queues: Decouple Workers with Asynchronous Message Passing

July 4, 2026 10 min read

When you build with Cloudflare Workers, you get blazing-fast edge compute — but sometimes your job takes too long. Processing an image, sending an email notification, or writing analytics data all need time beyond a Worker's 50ms–30s execution window.

Cloudflare Queues solve this problem. They let you decouple your request-handling Worker from the heavy-lifting Worker. Your first Worker acknowledges the request immediately, then pushes a message to a queue. A separate consumer Worker picks it up and processes it at its own pace.

This is the producer-consumer pattern, and it's one of the most important architectural patterns for building scalable systems.

How Cloudflare Queues Work

Cloudflare Queues has two components:

  1. Producer: A Worker that sends messages to a queue. This runs in the context of the original HTTP request and returns quickly.
  2. Consumer: A Worker that receives messages from a queue. This runs asynchronously, in batches, with automatic retries.

The flow looks like this:

Client Request
      │
      ▼
┌──────────────┐
│  Producer    │── Send message →┐
│  Worker      │                 │
│  (fast)      │                 ▼
└──────────────┐         ┌──────────────┐
               │         │   Queue      │
               │         │  (buffer)    │
               │         └──────┬───────┘
               │                │
               │         ┌──────▼───────┐
               │         │  Consumer    │
               │         │  Worker      │
               │         │  (async)     │
               │         └──────────────┘
               │                │
               ▼                ▼
          Response          Side Effect
         (immediate)       (eventually)

Setting Up a Queue

First, create a queue through the Cloudflare dashboard or with the Wrangler CLI:

# Create a queue named "notifications"
npx wrangler queues create notifications

Then configure your wrangler.toml file to bind the queue to your Worker:

# wrangler.toml
name = "my-app"
main = "src/index.js"
compatibility_date = "2026-07-01"

# Producer binding
[[queues.producers]]
  queue = "notifications"
  binding = "notificationQueue"

# Consumer binding
[[queues.consumers]]
  queue = "notifications"
  max_batch_size = 100
  max_batch_timeout = 5
  max_retries = 3
  dead_letter_queue = "notifications-dlq"

The consumer configuration is where the power lives:

  • max_batch_size: Maximum messages delivered per invocation (1–100)
  • max_batch_timeout: How long to wait for messages before invoking (1–30 seconds)
  • max_retries: How many times to retry failed messages before sending to DLQ
  • dead_letter_queue: Where failed messages go after exhausting retries

Writing the Producer Worker

The producer is straightforward — you send messages to the queue and return immediately:

// src/index.js — Producer Worker

export default {
  async fetch(request, env) {
    if (request.method !== "POST") {
      return new Response("Method Not Allowed", { status: 405 });
    }

    const body = await request.json();
    const { email, name, template } = body;

    // Validate input
    if (!email || !name) {
      return new Response(JSON.stringify({ error: "email and name required" }), {
        status: 400,
        headers: { "Content-Type": "application/json" }
      });
    }

    // Push message to queue — this returns immediately
    await env.notificationQueue.send({
      email,
      name,
      template: template || "welcome",
      timestamp: new Date().toISOString()
    });

    // Respond immediately — user doesn't wait for email to send
    return new Response(JSON.stringify({
      status: "queued",
      message: `Email will be sent to ${email}`
    }), {
      status: 202,  // 202 Accepted = "we got it, processing async"
      headers: { "Content-Type": "application/json" }
    });
  }
};

Key points:

  • The send() call is synchronous but fast — it just puts data in the queue
  • Return 202 Accepted to signal async processing
  • The user gets a response in milliseconds, not seconds

Batching Messages

For high-throughput scenarios, batch multiple messages into one send:

// Send multiple messages at once
const messages = [
  { email: "user1@example.com", name: "Alice" },
  { email: "user2@example.com", name: "Bob" },
  { email: "user3@example.com", name: "Charlie" },
];

// SendBatch delivers them as one atomic batch
await env.notificationQueue.sendBatch(messages.map(msg => ({
  body: msg,
  delaySeconds: 0  // optional: delay delivery by N seconds
})));

Writing the Consumer Worker

The consumer receives messages in batches and processes them:

// src/consumer.js — Consumer Worker

export default {
  async queue(batch, env) {
    console.log(`Processing batch of ${batch.messages.length} messages`);

    for (const message of batch.messages) {
      try {
        const { email, name, template, timestamp } = message.body;

        // Process the message (send email, write to DB, etc.)
        await sendEmail({ email, name, template });

        console.log(`✅ Sent ${template} email to ${email}`);

      } catch (error) {
        // If processing fails, the queue will retry up to max_retries times
        console.error(`❌ Failed for ${message.body.email}: ${error.message}`);
        throw error;  // Re-throw to trigger retry
      }
    }
  }
};

// Mock email function — replace with real SMTP/SendGrid/etc.
async function sendEmail({ email, name, template }) {
  console.log(`[Email] To: ${email}, Name: ${name}, Template: ${template}`);
  // await sendgrid.send(...)
  // await smtp.send(...)
}

Important behaviors:

  • Batch delivery: You get 1 to max_batch_size messages per invocation
  • Automatic retries: If your consumer throws an error, the queue retries up to max_retries times (with exponential backoff)
  • Dead letter queue: After exhausting retries, messages go to your DLQ for manual inspection
  • Exactly-once semantics: Cloudflare Queues guarantees at-least-once delivery. You may get duplicates, so make your processing idempotent

Real-World Use Cases

1. Analytics Event Tracking

// Producer: capture events immediately
export default {
  async fetch(request, env) {
    const { event, userId, data } = await request.json();

    await env.analyticsQueue.send({
      event,
      userId,
      data,
      timestamp: Date.now(),
      userAgent: request.headers.get("User-Agent")
    });

    return new Response("OK", { status: 200 });
  }
};

// Consumer: batch-write to database
export default {
  async queue(batch, env) {
    const events = batch.messages.map(m => m.body);

    // Batch insert into D1 database
    const stmt = env.DB.prepare(
      "INSERT INTO events (event, user_id, data, timestamp, user_agent) " +
      "VALUES (?, ?, ?, ?, ?)"
    );

    const batchStmt = env.DB.batch(
      events.map(e => stmt.bind(e.event, e.userId, JSON.stringify(e.data), e.timestamp, e.userAgent))
    );

    await batchStmt;
    console.log(`Wrote ${events.length} events to DB`);
  }
};

2. Image Processing Pipeline

// Producer: receive image upload, queue for processing
export default {
  async fetch(request, env) {
    const formData = await request.formData();
    const image = formData.get("image");

    // Store original in R2
    await env.R2.put(`originals/${crypto.randomUUID()}.webp`, image);

    // Queue the processing job
    await env.processQueue.send({
      action: "resize",
      sizes: [320, 640, 1024, 1920],
      format: "webp"
    });

    return new Response(JSON.stringify({ status: "processing" }), {
      headers: { "Content-Type": "application/json" }
    });
  }
};

// Consumer: process images in batches
export default {
  async queue(batch, env) {
    for (const message of batch.messages) {
      const { action, sizes, format } = message.body;

      for (const size of sizes) {
        // Download original, resize, upload to R2
        // Use image resizing API or external service
        await resizeAndUpload(env, size, format);
      }
    }
  }
};

3. Webhook Delivery with Retry

// Producer: queue webhook after order placement
await env.webhooks.send({
  type: "order.created",
  payload: { orderId: "ord_123", total: 99.99 },
  retries: 0
});

// Consumer: deliver webhooks with retry logic
export default {
  async queue(batch, env) {
    for (const message of batch.messages) {
      const { type, payload, retries } = message.body;

      try {
        const response = await fetch("https://customer-api.com/webhooks", {
          method: "POST",
          headers: {
            "Content-Type": "application/json",
            "X-Webhook-Signature": generateSignature(payload)
          },
          body: JSON.stringify({ type, payload })
        });

        if (!response.ok) {
          throw new Error(`HTTP ${response.status}`);
        }

        console.log(`Webhook delivered: ${type}`);

      } catch (error) {
        if (retries < 3) {
          // Re-queue with incremented retry count
          await env.webhooks.send({
            ...message.body,
            retries: retries + 1
          });
        } else {
          // Send to dead letter queue for manual review
          await env.dlq.send(message.body);
        }
      }
    }
  }
};

Monitoring and Debugging

Cloudflare provides observability for your queues:

# View queue metrics via Wrangler CLI
npx wrangler queues info notifications

# Sample output:
# Messages in queue: 42
# Messages waiting: 8
# Messages in-flight: 34
# Overages: 0

Check the Cloudflare Dashboard for:

  • Queue length: Messages waiting to be consumed
  • Consumer invocations: How often the consumer runs
  • Success/failure rates: Track message processing reliability
  • Dead letter queue: Messages that failed after all retries

Common Pitfalls

1. Non-Idempotent Consumers

Queues guarantee at-least-once delivery. Your consumer might process the same message twice. Make it idempotent:

// ✅ Idempotent: use a unique message ID
const messageId = crypto.randomUUID();

// Producer
await env.myQueue.send({ messageId, email, action: "send_welcome" });

// Consumer — track processed IDs in KV
const { messageId } = message.body;
const alreadyProcessed = await env.PROCESSED.get(messageId);
if (alreadyProcessed) {
  console.log(`Skipping duplicate: ${messageId}`);
  return;
}

await sendWelcomeEmail(message.body.email);
await env.PROCESSED.put(messageId, "done", { expirationTtl: 86400 }); // 24h TTL

2. Blocking the Consumer

The entire batch fails if any message throws an error. Handle errors per-message:

// ❌ Bad: one failure kills the whole batch
for (const msg of batch.messages) {
  await process(msg);  // If this throws, all remaining messages retry
}

// ✅ Good: handle errors per message
for (const msg of batch.messages) {
  try {
    await process(msg);
  } catch (err) {
    console.error(`Message ${msg.id} failed: ${err.message}`);
    // Other messages continue processing
  }
}

3. Forgetting the Consumer Binding

If your consumer Worker isn't properly bound to the queue in wrangler.toml, messages accumulate but never get processed. Always verify both bindings exist.

Summary

Cloudflare Queues let you build decoupled, asynchronous architectures on the edge:

  1. Use producers to push messages and respond immediately
  2. Use consumers to process messages in batches with automatic retries
  3. Configure dead letter queues for failed message inspection
  4. Make consumers idempotent to handle duplicate deliveries
  5. Handle errors per-message to avoid blocking entire batches
  6. Monitor queue depth and consumer health in the dashboard

Queues transform Cloudflare Workers from simple request-response handlers into full asynchronous processing pipelines — all running on Cloudflare's global edge network.
