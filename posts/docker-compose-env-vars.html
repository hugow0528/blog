Docker Compose Environment Variables & .env Files — Complete Beginner's Guide

July 20, 2026 11 min read

Environment variables are the backbone of configuration in Docker Compose. They control database passwords, API keys, feature flags, and everything that changes between development, staging, and production. This guide covers every pattern you'll need — from a simple .env file to advanced variable interpolation with defaults, environment files, and multi-environment setups.

Why Environment Variables in Docker?

The 12-factor app methodology says: Store config in the environment. Hardcoding passwords, database URLs, or API keys in your docker-compose.yml or Dockerfile is dangerous — those values leak into version control, get shared accidentally, and are nearly impossible to rotate. Environment variables keep secrets out of your code and let you configure the same container for any environment.

The .env File: Docker Compose's Best Friend

Docker Compose automatically loads a file called .env from the same directory as your docker-compose.yml. Every line in this file follows the format KEY=VALUE:

# .env
DB_HOST=db
DB_PORT=5432
DB_NAME=myapp
DB_USER=app_user
DB_PASSWORD=super_secret_password
DEBUG=true
LOG_LEVEL=info

Now reference these variables in your compose file using ${} syntax:

# docker-compose.yml
services:
  web:
    image: myapp:latest
    environment:
      - DATABASE_URL=postgresql://${DB_USER}:${DB_PASSWORD}@${DB_HOST}:${DB_PORT}/${DB_NAME}
      - DEBUG=${DEBUG}
      - LOG_LEVEL=${LOG_LEVEL}
    depends_on:
      - db

  db:
    image: postgres:16
    environment:
      - POSTGRES_DB=${DB_NAME}
      - POSTGRES_USER=${DB_USER}
      - POSTGRES_PASSWORD=${DB_PASSWORD}

When you run docker compose up, Compose reads the .env file and substitutes every ${VAR} with its value. The resulting container sees the resolved strings, not the variable references.

Variable Interpolation Syntax

Docker Compose supports several interpolation formats. Understanding these prevents subtle bugs:

# Basic interpolation — errors if VAR is unset
VAR=${UNSET_VAR}  # ❌ "required variable UNSET_VAR is missing a value"

# Default value — uses "fallback" if VAR is unset
VAR=${UNSET_VAR:-fallback}  # ✅ resolves to "fallback"

# Default value only when empty — uses "fallback" if VAR is ""
VAR=${EMPTY_VAR:-fallback}  # ✅ resolves to "fallback"
VAR=${SET_VAR:-fallback}    # ✅ resolves to the actual value

# Required variable with custom error message
VAR=${REQUIRED_VAR?Error: REQUIRED_VAR must be set}

The :- syntax is the most commonly used pattern. It lets you provide sensible defaults while still requiring critical secrets to be explicitly set:

environment:
  # Optional config with defaults
  - LOG_LEVEL=${LOG_LEVEL:-info}
  - WORKERS=${WORKERS:-4}
  - DEBUG=${DEBUG:-"false"}
  
  # Required — will error if not set
  - DATABASE_URL=${DATABASE_URL?DATABASE_URL is required}
  - SECRET_KEY=${SECRET_KEY?SECRET_KEY is required}

Escaping Dollar Signs

What if you need a literal $ in your value? Docker Compose treats $ as the start of variable interpolation. To escape it, use $$:

environment:
  # This sets the literal string: 100% discount
  - PROMOTION=100$$ discount
  
  # This sets: $HOME/path
  - APP_PATH=$$HOME/myapp

Without escaping, $HOME would be interpreted as the host's HOME environment variable — which is rarely what you want.

Multiple Environment Files for Different Stages

In real projects, you need different configurations for development, testing, and production. Instead of editing one .env file, maintain separate files:

# Project structure:
project/
├── docker-compose.yml
├── .env                # Development defaults
├── .env.example        # Template with no real secrets
├── .env.staging        # Staging configuration
└── .env.production     # Production configuration

The .env.example file is crucial — it shows what variables are needed without exposing actual values:

# .env.example
DB_HOST=localhost
DB_PORT=5432
DB_NAME=myapp
DB_USER=change_me
DB_PASSWORD=change_me
SECRET_KEY=generate_a_random_string
DEBUG=true

Add .env to your .gitignore and commit only .env.example:

# .gitignore
.env
.env.staging
.env.production

To load a specific environment file, use the --env-file flag:

# Development (default)
docker compose up

# Staging
docker compose --env-file .env.staging up

# Production
docker compose --env-file .env.production up

You can specify multiple --env-file arguments — later files override earlier ones:

# Load defaults first, then override with staging values
docker compose --env-file .env.defaults --env-file .env.staging up

Passing Host Environment Variables Directly

Without a value after the =, Docker Compose passes through the host's environment variable:

environment:
  # If HOST_VAR is "hello", the container sees HOST_VAR=hello
  - HOST_VAR
  - HOME
  
  # Override a host var
  - PATH=/custom/path
  # Or use the host value with a fallback
  - API_KEY=${API_KEY:-default_key}

This pattern is useful for CI/CD pipelines where secrets are injected as environment variables at runtime:

# In GitHub Actions
- name: Deploy
  env:
    DATABASE_URL: ${{ secrets.DATABASE_URL }}
    SECRET_KEY: ${{ secrets.SECRET_KEY }}
  run: docker compose --env-file .env.production up -d

The env_file Directive vs environment

Docker Compose offers two ways to pass variables to containers:

services:
  web:
    image: myapp:latest
    
    # Method 1: environment — inline key-value pairs
    environment:
      - KEY1=value1
      - KEY2=${COMPOSE_VAR}
    
    # Method 2: env_file — load from a file
    env_file:
      - .env
      - .env.secrets

Key differences:

  • environment supports interpolation (${VAR}), env_file does not — values are passed literally
  • environment lists are visible in docker inspect and docker compose config
  • env_file is simpler for large sets of variables (no quoting/escaping needed)
  • If the same key appears in both, environment wins (it's applied last)

Python Script: Auto-Generate .env from Template

Here's a practical Python script that creates a .env file from .env.example, generating random passwords and API keys:

import os
import string
import secrets

def generate_password(length=24):
    """Generate a secure random password."""
    chars = string.ascii_letters + string.digits + "!@#$%^&*"
    return ''.join(secrets.choice(chars) for _ in range(length))

def generate_secret(length=48):
    """Generate a longer random secret key."""
    return secrets.token_urlsafe(length)

def load_template(path='.env.example'):
    """Read template and return dict of key=value pairs."""
    vars = {}
    with open(path) as f:
        for line in f:
            line = line.strip()
            if not line or line.startswith('#'):
                continue
            key, _, default = line.partition('=')
            vars[key] = default
    return vars

def fill_template(template_vars):
    """Replace placeholder values with real secrets."""
    filled = {}
    for key, default in template_vars.items():
        key_lower = key.lower()
        if 'password' in key_lower or 'secret' in key_lower or 'key' in key_lower:
            if default.startswith('change_me') or default == '':
                filled[key] = generate_password()
            else:
                filled[key] = default
        else:
            filled[key] = default
    return filled

def write_env(env_vars, path='.env'):
    """Write variables to .env file."""
    if os.path.exists(path):
        print(f"⚠️  {path} already exists, skipping")
        return
    with open(path, 'w') as f:
        f.write("# Auto-generated from .env.example\n")
        for key, value in env_vars.items():
            f.write(f"{key}={value}\n")
    print(f"✅ Created {path}")

# Usage
template = load_template('.env.example')
env_vars = fill_template(template)
write_env(env_vars)

# Print summary (NOT the secrets!)
print("\nEnvironment file created with:")
for key in env_vars:
    key_lower = key.lower()
    if 'password' in key_lower or 'secret' in key_lower:
        print(f"  {key}=**GENERATED**")
    else:
        print(f"  {key}={env_vars[key]}")

Running this script gives you a ready-to-use .env file with real secrets, while .env.example stays safe to commit.

Environment Variable Precedence

When multiple sources provide the same variable, Docker Compose resolves conflicts in this order (highest to lowest priority):

  1. Inline environment — values defined directly in docker-compose.yml
  2. Host environment variables — variables set in your shell/CI pipeline
  3. .env file — auto-loaded from the compose file directory
  4. --env-file flag — explicitly specified environment files
  5. Default values — ${VAR:-default} fallbacks in interpolation

Best Practices Summary

  • Never commit .env files — always use .gitignore
  • Commit .env.example as a template for new developers
  • Use ${VAR:-default} for optional config, ${VAR?error} for required secrets
  • Use $$ to escape literal dollar signs
  • Keep secrets out of environment — use Docker secrets for production
  • Separate env files per environment (.env.staging, .env.production)
  • Use --env-file in CI/CD to inject secrets at runtime
