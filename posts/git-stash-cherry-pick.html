Git Stash and Cherry-pick: Save Work and Selectively Apply Commits

July 5, 2026 · 8 min read

You're halfway through a feature when your manager says "production is broken, fix it now." You've made changes but aren't ready to commit — you can't switch branches with uncommitted work. Enter git stash. Then, after fixing the bug on a hotfix branch, you realize a useful commit from your feature branch could help — without merging the whole branch. Enter git cherry-pick.

These two commands are Git's Swiss Army knives for workflow flexibility. They solve real problems that happen to every developer, every day. Let's master them.

Git Stash: Park Your Work Without Committing

git stash saves your uncommitted changes (both staged and unstaged) onto a temporary stack, then reverts your working directory to match the last commit. Think of it as a clipboard for your entire workspace.

Basic Stash and Restore

# You're working on a feature, files are modified
$ git status
On branch feature/login
Changes not staged for commit:
  modified:   app.py
  modified:   templates/login.html

# Save everything and clean your working directory
$ git stash
Saved working directory and index state On feature/login: WIP on feature/login: a1b2c3d Add login form

# Your working directory is now clean
$ git status
On branch feature/login
nothing to commit, working tree clean

Now you can switch branches, pull changes, or whatever you need:

# Switch to fix the production bug
$ git checkout main
$ git checkout -b hotfix/fix-payment

# ... fix the bug, commit, push ...

# Go back to your feature
$ git checkout feature/login

# Restore your stashed changes
$ git stash pop
Dropped refs/stash@{0} (a1b2c3d...)

# Your changes are back
$ git status
On branch feature/login
Changes not staged for commit:
  modified:   app.py
  modified:   templates/login.html

git stash pop restores and removes the stash. git stash apply restores but keeps the stash (useful if you need to apply the same changes to multiple branches).

Listing and Managing Stashes

# See all your stashes (they form a stack)
$ git stash list
stash@{0}: WIP on feature/login: a1b2c3d Add login form
stash@{1}: WIP on main: 9f8e7d6 Update dependencies
stash@{2}: On main: experiment with dark theme

# Apply a specific stash (not the most recent)
$ git stash apply stash@{2}

# Drop (delete) a specific stash
$ git stash drop stash@{1}

# Remove all stashes
$ git stash clear

Stash with Messages

Without messages, your stash list is a mystery. Always add context:

$ git stash save "WIP: login form validation - need to add email format check"

$ git stash list
stash@{0}: WIP on feature/login: a1b2c3d WIP: login form validation - need to add email format check

Stash Only Staged Changes

What if you want to stash only specific files? Use the --keep-index flag:

# You have 5 modified files
# Stage the 2 you want to keep
$ git add app.py config.py

# Stash only the unstaged changes
$ git stash --keep-index
# app.py and config.py stay in your working directory
# The other 3 files are stashed

# Later, restore the stashed files
$ git stash pop

Stash a New Branch (Keep the Work)

Stash and immediately create a new branch from the stashed changes:

# You've been experimenting but it's not ready
$ git stash branch experimental-branch
Switched to a new branch 'experimental-branch'
Dropped refs/stash@{0}

# Your stashed changes are now committed on the new branch
# You can continue working or delete the branch later
$ git checkout main
$ git branch -d experimental-branch  # if you don't need it

Git Cherry-pick: Steal a Single Commit

git cherry-pick takes a specific commit from one branch and applies it to your current branch — as if you wrote it there originally. It's perfect for picking useful commits without merging entire branches.

Basic Cherry-pick

# You're on main and want a commit from a feature branch
$ git log feature/payment-api --oneline
a1b2c3d (feature/payment-api) Add payment validation
b3c4d5e Fix database connection timeout  ← we want this one
c4d5e6f Initial payment API scaffolding

# Cherry-pick that one fix
$ git cherry-pick b3c4d5e
[main d4e5f6a] Fix database connection timeout
 Date: Mon Jul 5 10:30:00 2026 +0000
 1 file changed, 3 insertions(+), 1 deletion(-)

The fix is now on main with a new commit hash. The original still exists on feature/payment-api.

Cherry-pick Multiple Commits

# Pick multiple specific commits
$ git cherry-pick b3c4d5e c4d5e6f

# Pick a range of commits (everything from a1 to b3, inclusive)
$ git cherry-pick a1b2c3d^..b3c4d5e

# Pick a range by commit message date or other criteria
# (first find the hashes, then cherry-pick them)

When cherry-picking a range, list them in chronological order (oldest first) to minimize conflicts.

Real-World Scenario: Hotfix from Feature Branch

# Scenario: You found a critical bug in your feature branch
# and need to get just that fix into production NOW

# 1. On your feature branch, commit the fix
$ git checkout feature/user-dashboard
$ # ... make the fix ...
$ git add -A
$ git commit -m "fix: resolve null pointer in user profile API"

# 2. Copy the commit hash
$ git log -1 --oneline
f1e2d3c fix: resolve null pointer in user profile API

# 3. Switch to main
$ git checkout main

# 4. Cherry-pick the fix
$ git cherry-pick f1e2d3c
[main a9b8c7d] fix: resolve null pointer in user profile API

# 5. Push to production
$ git push origin main

The fix is now in production. When you eventually merge feature/user-dashboard into main, Git will recognize the cherry-picked commit as already present and skip it.

Handling Cherry-pick Conflicts

# Cherry-pick hits a conflict
$ git cherry-pick abc123
Auto-merging src/utils.py
CONFLICT (content): Merge conflict in src/utils.py
error: could not apply abc123... Add input validation

# Option 1: Fix the conflict manually
$ vim src/utils.py  # resolve conflict markers
$ git add src/utils.py
$ git cherry-pick --continue

# Option 2: Abort and skip this commit
$ git cherry-pick --abort

# Option 3: Take the incoming changes (the cherry-picked version)
$ git checkout --theirs src/utils.py
$ git add src/utils.py
$ git cherry-pick --continue

Cherry-pick Without Committing

Apply the changes but don't create a commit yet (useful for reviewing or tweaking):

$ git cherry-pick -n abc123
# Changes applied to working directory but not committed
# Review them, make tweaks, then commit yourself
$ git status
$ git commit -m "Apply input validation from feature branch"

Stash + Cherry-pick: Powerful Combinations

Stash, Cherry-pick, Then Restore

# You're mid-feature, need to grab a fix from another branch
$ git stash save "WIP: half-done feature work"
$ git checkout other-branch
$ git log --oneline -5
# find the commit hash
$ git cherry-pick abc123
$ git checkout main
$ git cherry-pick abc123
$ git checkout feature/branch
$ git stash pop

Stash as a Git Commit (for Later Cherry-pick)

# You have experimental changes that might be useful later
$ git stash save "experiment: new caching strategy"

# Later, on a different branch where you want to try it
$ git stash apply stash@{0}
# Test it, if it works:
$ git add -A
$ git commit -m "feat: add new caching strategy"
$ git stash drop stash@{0}

# If it doesn't work:
$ git reset --hard HEAD
$ git stash drop stash@{0}

Common Mistakes and Pitfalls

Mistake 1: Forgetting About Stashes

# You forgot you stashed work weeks ago
$ git stash list
stash@{0}: WIP on feature/auth: 3a2b1c WIP: JWT token refresh
stash@{1}: WIP on main: 9z8y7x Experiment: new layout

# These stashes are orphaned — no branch references them
# Apply them to the right branch or delete them
$ git stash drop stash@{0}
$ git stash drop stash@{1}

Mistake 2: Cherry-picking in Wrong Order

# Commits on feature branch:
# A → B → C (C depends on changes from A and B)

# Cherry-picking C without A and B first causes conflicts
$ git cherry-pick C
CONFLICT ...

# Fix: cherry-pick in order
$ git cherry-pick A
$ git cherry-pick B
$ git cherry-pick C

Mistake 3: Cherry-picking Then Merging

If you cherry-pick a commit from a feature branch into main, and later merge that feature branch, the cherry-picked commit appears twice. Git usually detects this automatically and handles it. But if the cherry-picked commit was slightly modified (e.g., conflict resolution changed some lines), Git won't recognize it as the same commit — leading to duplicate changes.

Solution: When merging, use --no-commit to review before finalizing:

$ git merge feature/branch --no-commit
$ git diff --cached  # review all changes
$ git status          # check for duplicates
# If clean, commit. If not, resolve manually.
$ git commit

Best Practices

  1. Name your stashes — git stash save "WIP: describe what you were doing"
  2. Clean up stashes regularly — run git stash list weekly, delete old ones
  3. Use cherry-pick sparingly — it's great for hotfixes and isolated commits, but don't use it to rebuild branch history. Use rebase for that.
  4. Cherry-pick in chronological order — oldest first to minimize conflicts
  5. Consider git revert instead of git reset for shared branches — revert creates a new commit that undoes changes, preserving history
  6. Don't stash secrets or large files — stashes are local only; they won't be pushed to backup

Summary

git stash is your workspace clipboard — save work when you need to context-switch, restore it when you're ready. git cherry-pick is your surgical tool — grab exactly the commit you need without pulling in the whole branch.

  • git stash / git stash pop — save and restore quickly
  • git stash apply — restore without deleting the stash
  • git stash list / git stash drop — manage your stash stack
  • git stash --keep-index — stash only unstaged changes
  • git cherry-pick <hash> — apply a single commit
  • git cherry-pick -n <hash> — apply without committing
  • git cherry-pick --abort / --continue — handle conflicts

Master these two commands, and your Git workflow becomes dramatically more flexible. No more forced commits, no more messy merges, no more "I'll finish that tomorrow" becoming "I forgot what I was doing."
