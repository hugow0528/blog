Docker Healthchecks and Readiness Probes — Keep Your Containers Alive

July 7, 2026 10 min read

Here's a scenario that catches every DevOps engineer at some point: your Docker container is running, but the application inside is dead. The process didn't crash — it's just hanging, looping infinitely, or waiting on a dead database connection. Docker reports "healthy" because the PID is alive, but users are getting 502 errors.

Docker healthchecks solve this. They let you define what "healthy" actually means for your application — not just "is the process running?" but "is the app responding correctly?"

In this guide, you'll learn how to add healthchecks to Dockerfiles and docker-compose.yml, configure restart policies, set up monitoring with Prometheus, and build self-healing deployments that survive failures automatically.

Why Healthchecks Matter

Without healthchecks, Docker assumes any running container is healthy. This causes three common problems:

  • Silent failures: A web server process is running but not listening on the correct port. Docker doesn't know.
  • Cascading failures: A database container starts slowly. The app container connects before it's ready, fails, and keeps retrying in a broken state.
  • Zombie containers: An app enters an infinite retry loop that never succeeds. It uses resources but serves no requests.

With healthchecks, Docker can detect these states and trigger automatic recovery — restarting unhealthy containers, routing traffic away from broken instances, or alerting your team before users notice.

Healthchecks in Dockerfiles

The HEALTHCHECK instruction tells Docker how to verify your container is functioning:

# HEALTHCHECK instruction format
HEALTHCHECK [OPTIONS] CMD command

# Example: Check HTTP endpoint
FROM python:3.12-slim
WORKDIR /app
COPY . .
RUN pip install -r requirements.txt
EXPOSE 8000

HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
    CMD curl -f http://localhost:8000/health || exit 1

CMD ["python", "app.py"]

Let's break down the options:

Option Default Description
--interval 30s How often to run the check
--timeout 30s Max time to wait for the check command
--start-period 0s Grace period before starting checks (app startup time)
--retries 3 Failures before marking unhealthy

Common Healthcheck Patterns

Pattern 1: HTTP Health Endpoint

# Dockerfile
HEALTHCHECK --interval=15s --timeout=3s --start-period=10s --retries=3 \
    CMD curl -f http://localhost:8000/health || exit 1

# Python app (FastAPI example)
from fastapi import FastAPI

app = FastAPI()

@app.get("/health")
def health_check():
    return {"status": "ok", "version": "1.0.0"}

Pattern 2: Database Connectivity Check

# For a PostgreSQL container
HEALTHCHECK --interval=10s --timeout=5s --start-period=30s --retries=5 \
    CMD pg_isready -U postgres || exit 1

# For a Redis container
HEALTHCHECK --interval=10s --timeout=3s --start-period=5s --retries=3 \
    CMD redis-cli ping | grep PONG || exit 1

Pattern 3: Application-Level Check with Python

# healthcheck.py — a dedicated health check script
import sys
import httpx
from app.database import get_db

async def check_health():
    healthy = True

    # Check 1: Can we reach our own endpoint?
    try:
        async with httpx.AsyncClient() as client:
            resp = await client.get("http://localhost:8000/api/status", timeout=3.0)
            if resp.status_code != 200:
                healthy = False
    except Exception as e:
        print(f"HTTP check failed: {e}")
        healthy = False

    # Check 2: Can we connect to the database?
    try:
        async with get_db() as db:
            await db.execute("SELECT 1")
    except Exception as e:
        print(f"Database check failed: {e}")
        healthy = False

    # Check 3: Disk space (fail if less than 1GB free)
    import shutil
    total, used, free = shutil.disk_usage("/")
    if free < 1_000_000_000:  # 1GB
        print(f"Low disk space: {free / 1e9:.1f}GB free")
        healthy = False

    sys.exit(0 if healthy else 1)

if __name__ == "__main__":
    import asyncio
    asyncio.run(check_health())

# Dockerfile
HEALTHCHECK --interval=30s --timeout=10s --start-period=15s --retries=3 \
    CMD python /app/healthcheck.py || exit 1

Healthchecks in Docker Compose

Docker Compose lets you define healthchecks inline, making your entire stack self-aware:

# docker-compose.yml
services:
  web:
    build: .
    ports:
      - "8000:8000"
    depends_on:
      db:
        condition: service_healthy  # Wait for DB healthcheck!
      redis:
        condition: service_healthy  # Wait for Redis healthcheck!
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8000/health"]
      interval: 15s
      timeout: 5s
      retries: 3
      start_period: 10s
    restart: unless-stopped
    deploy:
      resources:
        limits:
          memory: 512M
          cpus: '1.0'

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: myapp
      POSTGRES_USER: admin
      POSTGRES_PASSWORD: secure_password
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U admin -d myapp"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 30s
    restart: unless-stopped

  redis:
    image: redis:7-alpine
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 3s
      retries: 3
      start_period: 5s
    restart: unless-stopped

volumes:
  postgres_data:

The condition: service_healthy directive is a game-changer. Your web container won't start until the database passes its healthcheck, eliminating the "connect before ready" race condition.

Restart Policies

Healthchecks tell Docker the state. Restart policies tell Docker what to do about it:

# In docker-compose.yml
restart: "no"           # Never restart (default)
restart: "always"       # Always restart, even after manual stop
restart: "on-failure"   # Restart only if exit code != 0
restart: "unless-stopped" # Restart unless manually stopped (RECOMMENDED)

# On the command line
docker run --restart unless-stopped myapp
docker run --restart on-failure:5 myapp  # Max 5 restart attempts

unless-stopped is the best default for most services. The container restarts on crash, on reboot, and when Docker daemon restarts — but respects your explicit docker stop commands.

Monitoring Container Health

Check current health status:

# List containers with health status
docker ps --format "table {{.Names}}\t{{.Status}}"

# Output:
# NAMES         STATUS
# web           Up 2 hours (healthy)
# db            Up 2 hours (healthy)
# redis         Up 1 hour (unhealthy)

# Inspect detailed health logs
docker inspect --format='{{json .State.Health}}' web

# Tail health check logs
docker inspect --format='{{range .LogFilePath}}{{.}}{{end}}' web
# Or use Docker events stream
docker events --filter 'health=healthy' --filter 'health=unhealthy'

Prometheus Integration

For production, export container health metrics to Prometheus:

# Add cadvisor for container metrics
services:
  cadvisor:
    image: gcr.io/cadvisor/cadvisor:latest
    container_name: cadvisor
    ports:
      - "8080:8080"
    volumes:
      - /:/rootfs:ro
      - /var/run:/var/run:ro
      - /sys:/sys:ro
      - /var/lib/docker/:/var/lib/docker:ro
    restart: unless-stopped

  prometheus:
    image: prom/prometheus:latest
    ports:
      - "9090:9090"
    volumes:
      - ./prometheus.yml:/etc/prometheus/prometheus.yml
      - prometheus_data:/prometheus
    restart: unless-stopped

# prometheus.yml
global:
  scrape_interval: 15s

scrape_configs:
  - job_name: 'cadvisor'
    static_configs:
      - targets: ['cadvisor:8080']

Query unhealthy containers in Prometheus:

# Containers in unhealthy state
container_last_seen_healthy * on (container_id) group_right container_healthy == 0

# Alert if container has been unhealthy for 5 minutes
ALERT ContainerUnhealthy
  IF container_last_seen_healthy == 0
  FOR 5m
  LABELS { severity = "critical" }
  ANNOTATIONS {
    summary = "Container {{ $labels.container_name }} is unhealthy",
    description = "{{ $labels.container_name }} has been unhealthy for 5 minutes"
  }

Common Mistakes to Avoid

  1. Missing --start-period: Your app takes 20 seconds to start. Without start_period, the first healthcheck fails immediately, counting toward the retry limit. Always set this to match your app's startup time.
  2. Too-aggressive intervals: Checking every 5 seconds on a slow database generates unnecessary load. Use 15-30 seconds for most apps.
  3. Not installing curl in minimal images: python:3.12-slim doesn't include curl. Either use python:3.12, install curl in your Dockerfile, or use a Python-based healthcheck.
  4. Healthcheck only checks the process: CMD pgrep python passes even if Python is stuck in an infinite loop. Check the actual service — HTTP endpoint, database query, or port connectivity.
  5. Forgetting to handle SIGTERM: Without graceful shutdown handling, your app might lose in-flight requests during restart. Python's signal module or FastAPI's shutdown events handle this.

Complete Production Example

# Final docker-compose.yml for a production-ready stack
services:
  app:
    build:
      context: .
      dockerfile: Dockerfile
    ports:
      - "8000:8000"
    environment:
      - DATABASE_URL=postgresql://admin:secret@db:5432/myapp
      - REDIS_URL=redis://redis:6379
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_healthy
    healthcheck:
      test: ["CMD", "python", "/app/healthcheck.py"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 15s
    restart: unless-stopped
    deploy:
      resources:
        limits:
          memory: 512M
        reservations:
          memory: 128M
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: myapp
      POSTGRES_USER: admin
      POSTGRES_PASSWORD: secret
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U admin"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 30s
    restart: unless-stopped

      driver: json-file

        max-size: "5m"

  pgdata:

Summary

Docker healthchecks transform your containers from "running but maybe broken" to "proven healthy or automatically restarted." The key takeaways:

  • Add HEALTHCHECK to every Dockerfile or compose service
  • Set --start-period to match your app's startup time
  • Use condition: service_healthy in depends_on for startup ordering
  • Pair with restart: unless-stopped for automatic recovery
  • Monitor with Prometheus for alerting and dashboards
  • Check the actual service, not just the process

A healthy container is one that responds correctly to requests — not one that simply has a running PID. Make that the standard.
