Git Branching Strategies and Merge Conflicts Explained

June 24, 2026 · 8 min read

You know the Git basics — init, add, commit, push. But how do teams of multiple developers work on the same codebase without stepping on each other's toes? The answer is branching strategies. And when things inevitably go wrong? That's where understanding merge conflicts saves your project.

This guide covers the most popular branching models, when to use each, and a step-by-step walkthrough of resolving merge conflicts like a pro.

What Is a Branch?

A branch in Git is simply a lightweight pointer to a specific commit. When you create a branch, you're creating an independent line of development that can evolve without affecting your main codebase.

# Create a new branch called "feature/login"
git branch feature/login

# Switch to it
git checkout feature/login

# Or do both in one command
git checkout -b feature/login

# See all branches
git branch -a

Think of branches like parallel universes. In the "feature/login" universe, you can make changes, test them, and experiment. When you're happy, you merge it back into the "main" universe.

Best practice: Never commit directly to main (or master). Always create a feature branch, test your changes there, then merge via a Pull Request (PR) or Merge Request (MR).

Popular Branching Strategies

1. Feature Branch Workflow (Simple & Popular)

The most straightforward strategy. Every new feature or bug fix gets its own branch, which is merged into main via a Pull Request.

# Your workflow:
git checkout main
git pull origin main
git checkout -b feature/add-search

# ... make changes, commit ...
git add .
git commit -m "Add search functionality"
git push origin feature/add-search

# Then create a Pull Request on GitHub/GitLab
# After review and approval, merge into main

When to use: Small teams, startups, or projects where rapid iteration matters more than strict release cycles. This is the default GitHub Flow.

2. GitFlow (Structured & Predictable)

GitFlow uses multiple branches with specific roles:

  • main — Production-ready code. Only receives merges from release or hotfix branches.
  • develop — Integration branch. All feature branches merge here first.
  • feature/* — One branch per new feature. Branch off from develop.
  • release/* — Preparation branch for an upcoming release. Branch off from develop.
  • hotfix/* — Quick fixes for production. Branch off from main.
# GitFlow example workflow:

# Start a new feature
git checkout develop
git checkout -b feature/user-profile

# Work, commit, push
git add .
git commit -m "Add user profile page"
git push origin feature/user-profile

# Merge feature into develop (via PR)
git checkout develop
git merge feature/user-profile
git branch -d feature/user-profile

# Prepare a release
git checkout develop
git checkout -b release/v1.2.0
# Final testing, version bump, changelog...
git merge release/v1.2.0 main
git merge release/v1.2.0 develop
git tag v1.2.0
git push origin main --tags

When to use: Larger teams with scheduled releases, enterprise projects, or when you need a clear separation between development and production code.

3. Trunk-Based Development (Fast & Modern)

Short-lived branches (lasting hours, not days) that merge into a single "trunk" (main) multiple times per day. Often paired with feature flags and CI/CD.

# Trunk-based workflow:
git checkout main
git pull origin main
git checkout -b fix/typo-readme

# Make quick fix
git add .
git commit -m "Fix typo in README"
git push origin fix/typo-readme

# Merge immediately (same day)
git checkout main
git merge fix/typo-readme --squash
git branch -d fix/typo-readme
git push origin main

When to use: Teams practicing continuous deployment, companies like Google and Netflix, projects with strong automated testing.

Understanding Merge Conflicts

A merge conflict happens when Git cannot automatically combine changes from two branches. This occurs when both branches modify the same lines in the same file.

How a Conflict Looks

Let's say two developers edit the same app.py file:

Developer A changes line 5:

def greet(name):
    return f"Hello, {name}! Welcome to our app."  # Changed by A

Developer B changes the same line 5:

def greet(name):
    return f"Hey, {name}! Nice to see you."  # Changed by B

When Developer A tries to merge Developer B's branch, Git marks the conflict:

def greet(name):
<<<<<<< main
    return f"Hello, {name}! Welcome to our app."
=======
    return f"Hey, {name}! Nice to see you."
>>>>>>> feature/new-greeting

Step-by-Step: Resolving Merge Conflicts

# 1. Try the merge (this will fail with conflicts)
git checkout main
git merge feature/new-greeting
# CONFLICT (content): Merge conflict in app.py

# 2. Find which files have conflicts
git status
# Both modified:   app.py

# 3. Open the conflicted file (app.py)
# Look for the <======= and ======= markers
# Decide which change to keep, or combine them

# 4. Edit the file to resolve:
# Option A: Keep Developer A's version (delete B's section)
# Option B: Keep Developer B's version (delete A's section)
# Option C: Combine both (write your own resolution)

def greet(name):
    return f"Hello, {name}! Nice to see you!"  # Combined!

# 5. Mark the conflict as resolved
git add app.py

# 6. Complete the merge
git commit -m "Merge feature/new-greeting: combine greeting styles"

Pro Tips for Avoiding Conflicts

  1. Pull before you branch: Always run git pull origin main before creating a new branch. This ensures you start from the latest code.
  2. Rebase frequently: Instead of merging main into your feature branch, rebase to keep a clean, linear history.
  3. Communicate: If you and a teammate are editing the same file, coordinate. A quick Slack message prevents hours of conflict resolution.
  4. Small, focused PRs: The fewer files you change per branch, the lower the conflict risk.
  5. Use merge tools: VS Code, GitHub Desktop, and tools like meld or kdiff3 provide visual conflict resolution.

Rebase vs Merge: What's the Difference?

Both combine branches, but they do it differently:

Merge (Preserves History)

# Creates a merge commit that records both histories
git checkout main
git merge feature/xyz
# Result: A "V" shape in your history with a merge commit

Rebase (Linear History)

# Rewrites your feature branch commits on top of main
git checkout feature/xyz
git rebase main
# Result: A straight line — as if you had worked on the latest main all along
# Then fast-forward merge:
git checkout main
git merge feature/xyz
Golden rule of rebasing: Never rebase commits that you've already pushed to a shared branch. Rebase only your local, unshared work. If you break someone else's history, they will not forgive you.

Essential Git Commands for Branching

# View branch history with a nice tree
git log --oneline --graph --all

# Compare two branches
git diff main...feature/xyz

# Stash your uncommitted work (to switch branches cleanly)
git stash
git checkout other-branch
git stash pop  # Retrieve your stashed work

# Abort a messy merge
git merge --abort

# Reset to a previous state (use with caution!)
git reset --hard HEAD~1  # Undo last commit
git reset --soft HEAD~1  # Undo commit but keep changes staged

Putting It All Together: A Real Workflow

Here's a complete workflow for contributing to a team project:

# 1. Update your local copy
git checkout main
git pull origin main

# 2. Create a feature branch with a descriptive name
git checkout -b feature/add-dark-mode

# 3. Work: edit files, test, commit often
git add src/theme.js
git commit -m "Add dark mode toggle component"

git add src/styles.css
git commit -m "Style dark mode colors"

# 4. Rebase on latest main (keeps history clean)
git fetch origin
git rebase origin/main

# 5. Push and create Pull Request
git push origin feature/add-dark-mode
# → Go to GitHub, create PR, request review

# 6. After review, squash-merge on GitHub
# (or handle it locally)
git checkout main
git merge --squash feature/add-dark-mode
git commit -m "Add dark mode support (#42)"
git branch -d feature/add-dark-mode
git push origin main

Summary

Branching is how teams collaborate without chaos. Start simple with the Feature Branch Workflow, and adopt GitFlow if your project grows complex. Always resolve merge conflicts by understanding the changes, not just deleting markers. And remember: a clean git history makes debugging easier six months from now.
