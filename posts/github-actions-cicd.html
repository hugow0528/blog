GitHub Actions CI/CD Pipeline: Automate Testing, Building & Deploying

July 3, 2026 · 11 min read

Every time you push code, something should happen automatically. Tests should run. Linters should check your code. If everything passes, it should build and deploy. That's CI/CD — Continuous Integration and Continuous Deployment — and GitHub Actions is the easiest way to set it up.

In this tutorial, you'll build a complete pipeline from scratch: automated testing, Docker image builds, and deployment to a production server — all triggered by a git push.

What Is GitHub Actions?

GitHub Actions lets you define workflows — automated processes that respond to events in your repository. The most common events:

  • push — someone pushes code to a branch
  • pull_request — someone opens or updates a PR
  • schedule — runs on a cron schedule
  • workflow_dispatch — manually triggered from the GitHub UI

Workflows are defined in YAML files under .github/workflows/ in your repo. That's it — no separate tool to install, no server to provision (GitHub provides the runners).

Your First Workflow: Run Tests on Every Push

Create this file: .github/workflows/test.yml

name: Run Tests

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.12"

      - name: Install dependencies
        run: |
          python -m pip install --upgrade pip
          pip install -r requirements.txt

      - name: Run linter (ruff)
        run: |
          pip install ruff
          ruff check .

      - name: Run tests (pytest)
        run: |
          pip install pytest pytest-cov
          pytest tests/ --cov=app --cov-report=xml

      - name: Upload coverage
        uses: codecov/codecov-action@v4
        with:
          file: coverage.xml

Let's break down each part:

  • name: Display name shown in the Actions tab
  • on: Triggers — runs on pushes to main and PRs against main
  • jobs: A set of tasks. Each job runs on a fresh virtual machine
  • runs-on: The OS for the runner. ubuntu-latest is free and fast
  • steps: Individual commands or actions (pre-built scripts)
  • uses: Reference a community action from the GitHub Marketplace
  • run: Run shell commands directly

Workflow Vocabulary

Before building more complex pipelines, understand the hierarchy:

Repository
  └── .github/workflows/
      └── my-workflow.yml
          ├── triggers (on:)
          ├── env: (shared environment variables)
          └── jobs:
              ├── job-1 (runs on its own VM)
              │   ├── step-1
              │   └── step-2
              └── job-2 (runs in parallel by default)
                  └── step-1
  • Workflow = one YAML file
  • Job = runs on a fresh VM (parallel by default)
  • Step = one command or action within a job
  • Action = a reusable script (like a function) from the Marketplace

Building and Pushing Docker Images

Once tests pass, build and push your Docker image. Create .github/workflows/docker.yml:

name: Build & Push Docker Image

on:
  push:
    branches: [main]
    tags: ['v*']

jobs:
  docker:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3

      - name: Login to Docker Hub
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKER_USERNAME }}
          password: ${{ secrets.DOCKER_PASSWORD }}

      - name: Extract metadata
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: myusername/myapp
          tags: |
            type=sha,prefix=
            type=ref,event=branch
            type=semver,pattern={{version}}
            type=raw,value=latest,enable=${{ github.ref == 'refs/heads/main' }}

      - name: Build & push
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

Key concepts:

  • ${{ secrets.* }}: GitHub encrypts sensitive values. Set them in Settings → Secrets and Variables → Actions. Never hardcode passwords in YAML!
  • Docker Buildx: Extended Docker builder with cache support and multi-platform builds
  • Metadata action: Automatically generates tags (SHA, branch name, version tags)
  • Cache: cache-from: type=gha and cache-to: type=gha,mode=max use GitHub's built-in cache — faster rebuilds

Job Dependencies: Sequential Pipelines

By default, jobs run in parallel. Use needs to create a pipeline:

name: Full CI/CD Pipeline

on:
  push:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install pytest
      - run: pytest tests/

  build:
    needs: test  # Wait for 'test' to pass first
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker build -t myapp:latest .
      - run: docker tag myapp:latest myusername/myapp:${{ github.sha }}

  deploy:
    needs: build  # Wait for 'build' to finish
    runs-on: ubuntu-latest
    steps:
      - name: Deploy to server
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.PROD_HOST }}
          username: ${{ secrets.PROD_USER }}
          key: ${{ secrets.PROD_SSH_KEY }}
          script: |
            docker pull myusername/myapp:${{ github.sha }}
            docker stop myapp || true
            docker rm myapp || true
            docker run -d --name myapp \
              -p 8080:8080 \
              -e DATABASE_URL=$DB_URL \
              myusername/myapp:${{ github.sha }}

The pipeline: test → build → deploy. If any step fails, the rest are skipped. This is the classic CI/CD flow.

Reusable Workflows

If you have multiple repos with similar pipelines, define a reusable workflow:

# .github/workflows/ci-template.yml (in a shared "tooling" repo)
name: Reusable CI Template

on:
  workflow_call:
    inputs:
      python-version:
        required: true
        type: string
        default: "3.12"
      test-command:
        required: false
        type: string
        default: "pytest tests/"

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ inputs.python-version }}
      - run: pip install -r requirements.txt
      - run: ${{ inputs.test-command }}
# .github/workflows/ci.yml (in your actual app repo)
name: Run CI

on:
  push:
    branches: [main]

jobs:
  test:
    uses: myorg/tooling/.github/workflows/ci-template.yml@main
    with:
      python-version: "3.12"
      test-command: "pytest tests/ --cov=app"

Conditional Execution

Run steps only under certain conditions:

name: Conditional Pipeline

on:
  push:
    branches: [main, staging]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      # Only build Docker on main branch
      - name: Build Docker
        if: github.ref == 'refs/heads/main'
        run: docker build -t myapp:latest .

      # Only deploy on tag pushes
      - name: Deploy to production
        if: startsWith(github.ref, 'refs/tags/v')
        run: |
          echo "Deploying version ${{ github.ref_name }}"
          # deploy commands here

      # Skip test on documentation-only changes
      - name: Run tests
        if: github.event.head_commit.message != 'docs: update'
        run: pytest tests/

Caching Dependencies for Speed

Install dependencies once, reuse them across runs:

name: Cached Tests

on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"

      # Cache pip packages
      - name: Cache pip
        uses: actions/cache@v4
        with:
          path: ~/.cache/pip
          key: ${{ runner.os }}-pip-${{ hashFiles('**/requirements.txt') }}
          restore-keys: |
            ${{ runner.os }}-pip-

      - run: pip install -r requirements.txt
      - run: pytest tests/

The cache key uses hashFiles('**/requirements.txt') — when your dependencies change, the cache invalidates and re-downloads. Saves minutes per workflow run.

Scheduled Workflows (Cron Jobs)

Run tasks on a schedule — like dependency updates or health checks:

name: Dependency Check

on:
  schedule:
    - cron: '0 6 * * 1'  # Every Monday at 6 AM UTC

jobs:
  check-updates:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - name: Check for outdated packages
        run: |
          pip install pip-review
          pip-review --local --outdated
        continue-on-error: true  # Don't fail the workflow

Managing Secrets

Never put sensitive values in your workflow YAML. Use GitHub Secrets:

  1. Go to your repo → Settings → Secrets and variables → Actions
  2. Click "New repository secret"
  3. Add your secrets (e.g., DOCKER_PASSWORD, PROD_SSH_KEY)
  4. Reference them in workflows: ${{ secrets.DOCKER_PASSWORD }}

For environments (staging vs production), use Environment secrets:

name: Deploy with Environments

on:
  push:
    branches: [main]

jobs:
  deploy-prod:
    runs-on: ubuntu-latest
    environment: production  # Requires approval + uses env-specific secrets
    steps:
      - uses: actions/checkout@v4
      - name: Deploy
        run: |
          echo "Deploying with ${{ secrets.DATABASE_URL }}"
          # This DATABASE_URL is specific to the 'production' environment

Environment protection rules let you require manual approval before deployment, add branch restrictions, or enforce required check runs.

Complete Production Example

Here's a real-world pipeline for a Python API:

name: Python API CI/CD

on:
  push:
    branches: [main, staging]
  pull_request:
    branches: [main]

env:
  PYTHON_VERSION: "3.12"
  REGISTRY: ghcr.io

jobs:
  # Job 1: Quality checks
  quality:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ env.PYTHON_VERSION }}
      - uses: actions/cache@v4
        with:
          path: ~/.cache/pip
          key: ${{ runner.os }}-pip-${{ hashFiles('**/requirements.txt') }}

      - run: pip install ruff mypy
      - name: Lint
        run: ruff check .
      - name: Type check
        run: mypy app/

  # Job 2: Test
  test:
    runs-on: ubuntu-latest
    needs: quality
    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_USER: test
          POSTGRES_PASSWORD: test
          POSTGRES_DB: testdb
        ports:
          - 5432:5432
        options: >-
          --health-cmd pg_isready
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5
      redis:
        image: redis:7
        ports:
          - 6379:6379

    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ env.PYTHON_VERSION }}
      - run: pip install -r requirements.txt
      - name: Run tests
        env:
          DATABASE_URL: postgresql://test:test@localhost:5432/testdb
          REDIS_URL: redis://localhost:6379
        run: |
          pytest tests/ \
            --cov=app \
            --cov-report=xml \
            -v

      - name: Upload coverage
        uses: codecov/codecov-action@v4

  # Job 3: Build & push image
  build:
    needs: test
    if: github.event_name == 'push'
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write

    steps:
      - uses: actions/checkout@v4

      - name: Login to GHCR
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - uses: docker/setup-buildx-action@v3
      - uses: docker/metadata-action@v5
        id: meta
        with:
          images: ${{ env.REGISTRY }}/${{ github.repository }}

      - uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

  # Job 4: Deploy
  deploy:
    needs: build
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: production

    steps:
      - uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.PROD_HOST }}
          username: deploy
          key: ${{ secrets.PROD_SSH_KEY }}
          script: |
            IMAGE="${{ env.REGISTRY }}/${{ github.repository }}:${{ github.sha }}"
            docker pull $IMAGE
            docker compose down
            IMAGE=$IMAGE docker compose up -d
            # Verify deployment
            sleep 5
            curl -f http://localhost:8080/health || exit 1

This pipeline: lints → type-checks → tests (with Postgres + Redis services) → builds Docker → deploys via SSH → health-checks. All automatic on push to main.

Common Pitfalls

  1. Forgetting continue-on-error: Non-critical steps (like notifications) shouldn't fail the whole workflow.
  2. Not caching: Without caching, every run downloads all dependencies from scratch. Minutes add up.
  3. Hardcoding secrets: GitHub will warn you and may reject the push. Always use ${{ secrets.* }}.
  4. Ignoring matrix builds: Test against multiple Python versions: strategy: matrix: { python-version: ["3.10", "3.11", "3.12"] }
  5. Slow deployments: Use rolling updates or blue-green deployment instead of stopping then starting containers.

Summary

# Workflow anatomy
name: My Pipeline          # Display name
on: [push, pull_request]   # Triggers
env:                       # Shared variables
  KEY: value

jobs:
  job-name:                # Runs on its own VM
    runs-on: ubuntu-latest
    needs: other-job       # Dependencies
    if: condition          # Conditional execution
    steps:
      - uses: action@v1    # Pre-built action
      - run: command       # Shell command

GitHub Actions gives you a powerful, free (for public repos, 2,000 minutes/month for private), and highly customizable CI/CD platform. Start with a simple test workflow, add Docker builds, then chain in deployment. Your code quality will improve immediately — every push gets validated automatically.
