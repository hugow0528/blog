Python Environment Variables & Secrets: Secure Configuration — Complete Guide

Learn how to manage environment variables and secrets in Python applications. From os.environ to dotenv, argparse configuration, secure credential handling, and production deployment patterns. Stop hardcoding API keys and build resilient, configurable applications.

July 10, 2026 10 min read

Why Environment Variables Matter

Every Python application needs configuration: database URLs, API keys, feature flags, logging levels. The biggest mistake beginners make is hardcoding these values directly into their source code. Once your code is committed to Git, your secrets are exposed to anyone with repository access.

Environment variables solve this problem by externalizing configuration. They let you run the same code in development, staging, and production with different settings — without changing a single line of code. This principle is called the twelve-factor app methodology, and it's an industry standard.

Reading Environment Variables with os.environ

Python's built-in os module gives you direct access to environment variables through the os.environ dictionary. This is the simplest approach and requires no external dependencies.

import os

# Read a single environment variable
api_key = os.environ["API_KEY"]

# Safer approach: provide a default value
debug_mode = os.environ.get("DEBUG", "false").lower() == "true"
port = int(os.environ.get("PORT", "8080"))

# Check if a variable exists before using it
if "DATABASE_URL" in os.environ:
    db_url = os.environ["DATABASE_URL"]
else:
    raise ValueError("DATABASE_URL environment variable is required")

The os.environ.get() method is safer than direct dictionary access because it returns None (or a default value) instead of raising a KeyError when the variable doesn't exist. Always use .get() for optional configuration and direct access [] for required values where a missing variable should crash your application.

Setting Environment Variables

Before your Python code can read environment variables, they need to be set in the shell. Here's how to do it across different operating systems:

# Linux / macOS — temporary (current session only)
export API_KEY="your-secret-key-here"
export DATABASE_URL="postgresql://localhost/mydb"

# Linux / macOS — run with env vars inline
API_KEY="secret" python app.py

# Windows (Command Prompt)
set API_KEY=your-secret-key-here
python app.py

# Windows (PowerShell)
$env:API_KEY="your-secret-key-here"
python app.py

For permanent configuration on Linux/macOS, add your exports to ~/.bashrc or ~/.zshrc. However, never store secrets in shell config files — those files are readable by any process running on the system.

The .env File Pattern with python-dotenv

During local development, typing export commands every time you restart your terminal is tedious. The python-dotenv library solves this by loading environment variables from a .env file automatically. Install it first:

pip install python-dotenv

Create a .env file in your project root:

# .env file — NEVER commit this to Git!
API_KEY=sk-1234567890abcdef
DATABASE_URL=postgresql://user:password@localhost:5432/mydb
DEBUG=true
LOG_LEVEL=DEBUG

Then load it in your Python application:

from dotenv import load_dotenv
import os

# Load .env file (must be called before reading env vars)
load_dotenv()

# Now os.environ contains all variables from .env
api_key = os.environ["API_KEY"]
database_url = os.environ["DATABASE_URL"]
debug = os.environ.get("DEBUG", "false").lower() == "true"

The load_dotenv() function searches for a .env file in the current directory and parent directories. It only sets variables that aren't already defined in the system, so system environment variables always take precedence — which is exactly what you want for production deployments.

Critical: Your .env file must be in your .gitignore. Add this line if it's not already there:

# .gitignore
.env
.env.local
.env.*.local

Building a Configuration Class

As your application grows, reading individual environment variables scattered across modules becomes unmanageable. A centralized configuration class keeps everything organized and adds validation:

import os
from dataclasses import dataclass, field

@dataclass
class Settings:
    """Centralized application configuration."""
    app_name: str = field(default="MyApp")
    debug: bool = field(default=False)
    port: int = field(default=8080)
    log_level: str = field(default="INFO")
    
    # Required settings — no defaults
    database_url: str = field(default=None)
    api_key: str = field(default=None)
    
    def __post_init__(self):
        """Load from environment variables and validate."""
        # Override defaults with environment variables
        self.app_name = os.environ.get("APP_NAME", self.app_name)
        self.debug = os.environ.get("DEBUG", str(self.debug)).lower() == "true"
        self.port = int(os.environ.get("PORT", self.port))
        self.log_level = os.environ.get("LOG_LEVEL", self.log_level)
        self.database_url = os.environ.get("DATABASE_URL", self.database_url)
        self.api_key = os.environ.get("API_KEY", self.api_key)
        
        # Validate required fields
        if not self.database_url:
            raise ValueError("DATABASE_URL is required")
        if not self.api_key:
            raise ValueError("API_KEY is required")
        
        # Validate log level
        valid_levels = ["DEBUG", "INFO", "WARNING", "ERROR", "CRITICAL"]
        if self.log_level.upper() not in valid_levels:
            raise ValueError(f"Invalid LOG_LEVEL: {self.log_level}")


# Usage
config = Settings()
print(f"Running {config.app_name} on port {config.port}")
print(f"Database: {config.database_url}")
print(f"Debug mode: {config.debug}")

This pattern gives you type hints for IDE autocomplete, validation at startup (fail fast), and a single source of truth for all configuration. Import config in any module instead of calling os.environ directly.

Type-Safe Configuration with Pydantic

For production applications, Pydantic provides superior validation, type coercion, and environment variable loading through its BaseSettings class:

from pydantic import Field, field_validator
from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    """Type-safe settings with automatic validation."""
    app_name: str = "MyApp"
    debug: bool = False
    port: int = Field(default=8080, ge=1, le=65535)
    database_url: str
    api_key: str = Field(min_length=10)
    allowed_hosts: list[str] = ["localhost", "127.0.0.1"]
    
    @field_validator("database_url")
    @classmethod
    def validate_db_url(cls, v: str) -> str:
        if not v.startswith(("postgresql://", "mysql://", "sqlite://")):
            raise ValueError("Unsupported database driver")
        return v
    
    # Model configuration
    model_config = {
        "env_file": ".env",       # Load from .env file
        "env_file_encoding": "utf-8",
        "extra": "ignore",        # Ignore extra env vars
    }


# Automatic validation and type coercion
settings = Settings()
print(settings.port)  # int, even though env var is a string
print(settings.allowed_hosts)  # parsed from comma-separated string

Pydantic settings automatically loads from environment variables and .env files, coerces types (strings to integers, booleans, lists), and validates values with custom validators. Install with pip install pydantic pydantic-settings.

Secrets in Production

Production environments use different tools for secret management:

  • Docker/Kubernetes: Use Docker secrets or Kubernetes Secret objects. Reference them as environment variables in your container spec.
  • AWS: Use AWS Secrets Manager or Parameter Store. The AWS SDK can retrieve secrets at application startup.
  • Cloudflare Workers: Use the Workers dashboard or wrangler secret put to store encrypted secrets.
  • GitHub Actions: Store secrets in repository settings and reference them as ${{ secrets.MY_SECRET }} in workflow files.

The key principle is the same everywhere: never commit secrets to version control. Use your platform's built-in secret management, and access them through environment variables in your Python code.

Command-Line Arguments with argparse

For CLI tools, environment variables complement (not replace) command-line arguments. Python's argparse module handles argument parsing:

import argparse

def parse_args():
    parser = argparse.ArgumentParser(
        description="My CLI tool with flexible configuration"
    )
    parser.add_argument("--host", default="localhost",
                        help="Server hostname")
    parser.add_argument("--port", type=int, default=8080,
                        help="Server port (1-65535)")
    parser.add_argument("--verbose", "-v", action="store_true",
                        help="Enable verbose logging")
    parser.add_argument("input_file", nargs="?",
                        help="Input file path (optional)")
    return parser.parse_args()


args = parse_args()
print(f"Connecting to {args.host}:{args.port}")
print(f"Verbose: {args.verbose}")

Combine argparse with environment variables for maximum flexibility: use environment variables for sensitive data (API keys, passwords) and command-line arguments for user preferences:

import os
import argparse

parser = argparse.ArgumentParser()
parser.add_argument("--output", default=os.environ.get("OUTPUT_DIR", "./output"))
parser.add_argument("--api-key", default=os.environ.get("API_KEY"))

args = parser.parse_args()

Common Pitfalls to Avoid

  1. Hardcoding secrets: Never write API keys, passwords, or tokens directly in your code. Even in example code that you plan to delete later.
  2. Missing .gitignore: Always add .env to .gitignore. Consider using git secrets or pre-commit hooks to prevent accidental commits.
  3. Using development secrets in production: Double-check that production deployments use production credentials. A common mistake is deploying a staging .env file to production.
  4. Logging sensitive data: Never log environment variables that contain secrets. Sanitize your log output to redact sensitive values.
  5. Assuming all env vars exist: Always use .get() with defaults for optional variables, or validate at startup and fail fast for required ones.

Summary

Environment variables are the standard way to configure Python applications across environments. Start with os.environ for simple projects, use python-dotenv for local development, and upgrade to Pydantic Settings for production applications. Remember the golden rule: configuration belongs in the environment, not in the code. Your future self (and your security team) will thank you.
