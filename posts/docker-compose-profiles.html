Docker Compose Profiles: Manage Multi-Environment Setups — Complete Beginner's Guide

July 17, 2026 · 10 min read

You've been using docker-compose.yml files to orchestrate multi-container applications. Your stack works great in development — your web app, database, and cache all spin up together. But now you want to run some services only during testing, skip the heavy analytics pipeline in local dev, or swap in a mock service for staging. Creating separate compose files for each scenario is messy and hard to maintain.

Docker Compose profiles solve this elegantly. With a single docker-compose.yml, you can define which services belong to which profile and selectively start them. No more juggling multiple compose files or commenting out services. This guide covers everything from your first profiles: declaration to production-grade multi-environment setups.

What Are Docker Compose Profiles?

Profiles are a way to group services in your Docker Compose file. When you run docker compose up without specifying a profile, only services without a profile (or with an empty profile list) start. Services assigned to a profile only launch when you explicitly enable that profile using --profile.

Think of profiles as environment switches baked into your compose file. One file, multiple environments, zero duplication.

Basic Profile Setup

Here's the simplest example — a web app with an optional Redis cache that you only want during performance testing:

# docker-compose.yml
services:
  web:
    image: myapp:latest
    ports:
      - "8000:8000"
    environment:
      - REDIS_URL=redis://cache:6379

  cache:
    image: redis:7-alpine
    profiles:
      - perf-test

Run the web app alone:

# Only 'web' starts (no profile assigned)
docker compose up -d

Run the full stack with Redis:

# Both 'web' and 'cache' start
docker compose --profile perf-test up -d

Real-World Example: Full Development Stack

Let's build a realistic compose file for a Python application. This stack includes your core services plus optional tools for different workflows:

# docker-compose.yml
services:
  # ── Core Services (always run) ──
  api:
    build:
      context: ./backend
      dockerfile: Dockerfile
    ports:
      - "8000:8000"
    environment:
      - DATABASE_URL=postgresql://app:secret@db:5432/app
      - REDIS_URL=redis://cache:6379
      - ENVIRONMENT=development
    depends_on:
      db:
        condition: service_healthy
      cache:
        condition: service_started
    volumes:
      - ./backend:/app
    profiles:
      - core
      - dev
      - staging

  db:
    image: postgres:16-alpine
    environment:
      - POSTGRES_USER=app
      - POSTGRES_PASSWORD=secret
      - POSTGRES_DB=app
    ports:
      - "5432:5432"
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app"]
      interval: 5s
      timeout: 3s
      retries: 5
    profiles:
      - core
      - dev
      - staging

  cache:
    image: redis:7-alpine
    ports:
      - "6379:6379"
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 3s
      retries: 3
    profiles:
      - core
      - dev
      - staging

  # ── Development Tools (only in dev) ──
  admin:
    image: adminer:latest
    ports:
      - "8080:8080"
    environment:
      - ADMINER_DEFAULT_SERVER=db
    profiles:
      - dev

  mailhog:
    image: mailhog/mailhog:latest
    ports:
      - "1025:1025"  # SMTP
      - "8025:8025"  # Web UI
    profiles:
      - dev

  # ── Testing Services ──
  test-db:
    image: postgres:16-alpine
    environment:
      - POSTGRES_USER=test
      - POSTGRES_PASSWORD=test
      - POSTGRES_DB=test_app
    profiles:
      - test

  # ── Monitoring (only for staging/production) ──
  prometheus:
    image: prom/prometheus:latest
    ports:
      - "9090:9090"
    volumes:
      - ./monitoring/prometheus.yml:/etc/prometheus/prometheus.yml
    profiles:
      - staging
      - monitoring

  grafana:
    image: grafana/grafana:latest
    ports:
      - "3000:3000"
    environment:
      - GF_SECURITY_ADMIN_PASSWORD=admin
    profiles:
      - staging
      - monitoring

volumes:
  pgdata:

This single file handles four different scenarios:

  • docker compose --profile dev up -d — Full development stack with Adminer and MailHog
  • docker compose --profile test up -d — Clean test database for running pytest
  • docker compose --profile staging up -d — Production-like stack with monitoring
  • docker compose --profile core up -d — Minimal stack, just the essentials

Multiple Profiles per Service

A service can belong to multiple profiles. If a service has profiles [dev, staging], it starts when you enable either profile. This is how the core services (api, db, cache) work in the example above — they're available in both core, dev, and staging.

You can also pass multiple profiles at once:

# Start dev + monitoring together
docker compose --profile dev --profile monitoring up -d

Using COMPOSE_PROFILES Environment Variable

Instead of passing --profile every time, set the COMPOSE_PROFILES environment variable. Docker Compose reads this and applies the profiles automatically:

# In your .env file
COMPOSE_PROFILES=dev

# Now this starts all dev services automatically
docker compose up -d

Or set it in your shell for a temporary session:

# Bash/Zsh
export COMPOSE_PROFILES="dev,monitoring"
docker compose up -d

Profiles with Dockerfile Multi-Stage Builds

Profiles pair beautifully with multi-stage Dockerfiles. You can define different build stages for different profiles:

services:
  api:
    build:
      context: ./backend
      target: ${BUILD_TARGET:-production}
    profiles:
      - core
      - dev

  api-debug:
    build:
      context: ./backend
      target: debug
    volumes:
      - ./backend:/app
    command: ["python", "-m", "flask", "run", "--debugger"]
    profiles:
      - dev

Now your dev profile gets the debug build with live code reloading, while staging gets the optimized production build.

Profile-Based Environment Overrides

Combine profiles with .env files for clean environment-specific configuration:

# .env.dev
COMPOSE_PROFILES=dev
DATABASE_URL=postgresql://app:secret@db:5432/app
ENVIRONMENT=development
DEBUG=true

# .env.staging
COMPOSE_PROFILES=staging
DATABASE_URL=postgresql://staging:***@staging-db:5432/app
ENVIRONMENT=staging
DEBUG=false

Then use them explicitly:

# Dev environment
docker compose --env-file .env.dev up -d

# Staging environment
docker compose --env-file .env.staging up -d

Python Integration: Automated Environment Switching

Write a simple Python script to switch between environments without remembering docker commands:

#!/usr/bin/env python3
"""switch-env.py — Switch Docker Compose environments with one command."""

import subprocess
import sys
import os

ENVIRONMENTS = {
    "dev": {
        "profiles": ["dev"],
        "env_file": ".env.dev",
        "description": "Development (Adminer, MailHog, hot reload)"
    },
    "test": {
        "profiles": ["test"],
        "env_file": ".env.test",
        "description": "Testing (clean test database)"
    },
    "staging": {
        "profiles": ["staging", "monitoring"],
        "env_file": ".env.staging",
        "description": "Staging (production-like + Prometheus + Grafana)"
    },
    "core": {
        "profiles": ["core"],
        "env_file": ".env.core",
        "description": "Core only (API, database, cache)"
    },
}

def list_envs():
    """Print available environments."""
    print("\nAvailable environments:\n")
    for name, config in ENVIRONMENTS.items():
        print(f"  {name:10} — {config['description']}")
    print()

def switch_env(env_name, action="up"):
    """Switch to an environment."""
    if env_name not in ENVIRONMENTS:
        print(f"❌ Unknown environment: {env_name}")
        print(f"Run '{sys.argv[0]} list' to see available environments")
        sys.exit(1)

    config = ENVIRONMENTS[env_name]
    profile_args = []
    for profile in config["profiles"]:
        profile_args.extend(["--profile", profile])

    # Stop current containers first
    subprocess.run(
        ["docker", "compose", "--env-file", config["env_file"], "down"],
        capture_output=True
    )

    # Start new environment
    cmd = ["docker", "compose", "--env-file", config["env_file"]] + profile_args + [action]
    print(f"🚀 Starting environment: {env_name}")
    print(f"   Profiles: {', '.join(config['profiles'])}")
    print(f"   Env file: {config['env_file']}")
    print()
    subprocess.run(cmd)

def run_tests():
    """Run tests against the test environment."""
    print("🧪 Starting test environment and running pytest...")
    subprocess.run(["python", sys.argv[0], "switch", "test"])
    subprocess.run(["python", "-m", "pytest", "tests/", "-v"])
    subprocess.run(["docker", "compose", "--env-file", ".env.test", "down"])

if __name__ == "__main__":
    if len(sys.argv) < 2:
        list_envs()
        sys.exit(0)

    command = sys.argv[1]

    if command == "list":
        list_envs()
    elif command == "switch":
        switch_env(sys.argv[2], action=sys.argv[3] if len(sys.argv) > 3 else "up")
    elif command == "test":
        run_tests()
    else:
        print(f"Usage: {sys.argv[0]} [list|switch|test]")

Usage is dead simple:

# List available environments
python switch-env.py list

# Switch to dev environment
python switch-env.py switch dev

# Switch to staging
python switch-env.py switch staging

# Run tests (starts test env, runs pytest, tears down)
python switch-env.py test

Common Profile Patterns

Here are patterns I use in every project:

Pattern Profile Name Services Included
Minimal dev dev API, database, cache + Adminer, MailHog
CI/CD testing ci API, test database (no ports exposed)
Load testing perf API + k6/Locust load generator
Debugging debug API with debugger, port-forwarded IDE
Staging staging API, database, cache, Prometheus, Grafana

Profiles in CI/CD (GitHub Actions)

Profiles shine in CI/CD pipelines where you only need specific services:

# .github/workflows/test.yml
name: Test
on: [push]
jobs:
  test:
    runs-on: ubuntu-latest
    services:
      # You can't use profiles directly in GHA services,
      # but you can start only what you need:
    steps:
      - uses: actions/checkout@v4
      - name: Start test services
        run: docker compose --profile test up -d --wait
      - name: Run tests
        run: python -m pytest tests/ -v
      - name: Collect coverage
        run: python -m pytest tests/ --cov=app --cov-report=xml
      - name: Teardown
        run: docker compose --profile test down

Best Practices and Gotchas

Keep these rules in mind when working with profiles:

  • No default profile: Services without a profiles key always start. This is intentional — use it for services that should run everywhere.
  • Profile is not a network: Profiles only control which services start. All running services still share the default network.
  • Depends_on works across profiles: A service in the dev profile can depend on a core service. It just won't start unless the dependency is also started.
  • Use --wait in CI: docker compose up -d --wait blocks until all services with healthchecks are healthy. Essential for CI pipelines.
  • Name profiles descriptively: dev, test, staging are clear. Avoid profile1, profile2.
  • Combine with env files: Profiles + --env-file give you complete environment control without duplicating compose files.

Pro tip: If you find yourself writing more than 3 profiles for similar environments, consider whether separate compose files (e.g., docker-compose.dev.yml) would be clearer. Profiles excel when you have 3-5 distinct scenarios in one project.

Complete Quick Reference

# Start default (no-profile) services
docker compose up -d

# Start with one profile
docker compose --profile dev up -d

# Start with multiple profiles
docker compose --profile dev --profile monitoring up -d

# Set profile via environment variable
export COMPOSE_PROFILES="dev,monitoring"
docker compose up -d

# Wait for health checks to pass
docker compose --profile dev up -d --wait

# Stop only dev profile services
docker compose --profile dev down

# List services in a profile
docker compose --profile dev config --services

Summary

Docker Compose profiles eliminate the need for multiple compose files while giving you precise control over which services run. The key concepts:

  1. Assign profiles: to services to make them conditional
  2. Use --profile or COMPOSE_PROFILES to enable them
  3. Combine with .env files for environment-specific config
  4. One service can belong to multiple profiles
  5. Services without profiles always start

Start with a simple dev and test profile split in your next project. Once you see how cleanly it replaces your commented-out services, you'll never go back.
