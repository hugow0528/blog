Vibe Coding with Cursor: Build a Full App in One Session — Complete Guide

July 13, 2026 · 13 min read

"Vibe coding" means writing software by describing what you want in plain English and letting an AI tool generate the code. Cursor — an AI-powered code editor based on VS Code — is currently one of the most capable tools for this workflow. But most people use it wrong: they ask tiny questions one at a time, getting scattered code fragments instead of a coherent application.

In this guide, I'll show you the complete workflow for building a full-stack Python task management API with Cursor in a single session. You'll learn how to structure prompts, review AI output, iterate on problems, and ship working code — not just experiments.

The Project: Task Management API

We'll build a REST API with these features:

  • Create, read, update, and delete tasks (CRUD)
  • SQLite database with SQLAlchemy ORM
  • Pydantic models for request/response validation
  • FastAPI as the web framework
  • Automated tests with pytest
  • Docker support

Normally this would take a developer 2-4 hours of coding. With Cursor and the right workflow, you can do it in 20-30 minutes.

Phase 1: Set the Context (The Most Important Step)

The biggest mistake beginners make is jumping straight into coding. Cursor doesn't know what you're building unless you tell it. The first prompt should establish the entire project context.

Open Cursor, create a new empty folder called task-api/, and open the Composer (Cmd+I on Mac, Ctrl+I on Windows). Here's your first prompt:

Build a task management REST API using FastAPI and SQLAlchemy.

Project structure requirements:
- main.py — FastAPI app with all endpoints
- models.py — SQLAlchemy database models
- schemas.py — Pydantic schemas for request/response validation
- database.py — SQLite database setup with async support
- tests/ — pytest test files
- requirements.txt — dependencies
- Dockerfile — production-ready container
- .env.example — environment variable template

Technical specifications:
- Use async SQLAlchemy with SQLite (aiosqlite)
- Use Pydantic v2 for all request/response models
- Implement CRUD: GET /tasks, POST /tasks, GET /tasks/{id}, PUT /tasks/{id}, DELETE /tasks/{id}
- Each task has: id (UUID), title (required, max 200 chars), description (optional), completed (boolean, default False), created_at, updated_at
- Return proper HTTP status codes (201 for created, 204 for deleted, 404 for not found, 422 for validation errors)
- Include health check endpoint at /health
- Database should initialize automatically on first request
- Use Alembic for migrations (include initial migration)

Why this prompt works:

  • Specific tech stack — FastAPI, SQLAlchemy, Pydantic v2, SQLite, aiosqlite
  • Explicit file structure — Cursor knows exactly which files to create
  • Technical constraints — async, UUID, validation rules, status codes
  • Complete feature list — no ambiguity about what "done" looks like

Cursor will generate multiple files at once. This is where it shines — it understands the relationships between files.

Phase 2: Review and Validate the Output

Never blindly accept AI-generated code. Review each file systematically:

Check the Database Model (models.py)

# What Cursor should generate:
from sqlalchemy import Column, String, Boolean, DateTime
from sqlalchemy.sql import func
from sqlalchemy.dialects.postgresql import UUID
import uuid
from database import Base

class Task(Base):
    __tablename__ = "tasks"

    id = Column(String(36), primary_key=True, default=lambda: str(uuid.uuid4()))
    title = Column(String(200), nullable=False)
    description = Column(String(1000), nullable=True)
    completed = Column(Boolean, default=False)
    created_at = Column(DateTime(timezone=True), server_default=func.now())
    updated_at = Column(DateTime(timezone=True), onupdate=func.now())

    def __repr__(self):
        return f"<Task {self.title}>"

What to verify:

  • Is id properly typed? (String(36) for SQLite, since SQLite doesn't have a native UUID type)
  • Are timestamps using timezone-aware datetimes?
  • Does updated_at update on every change?
  • Are nullable fields correct? (title is required, description is optional)

Check the Pydantic Schemas (schemas.py)

# What Cursor should generate:
from pydantic import BaseModel, Field
from typing import Optional
from datetime import datetime
from uuid import UUID

class TaskCreate(BaseModel):
    title: str = Field(..., min_length=1, max_length=200, description="Task title")
    description: Optional[str] = Field(None, max_length=1000, description="Task description")

class TaskUpdate(BaseModel):
    title: Optional[str] = Field(None, min_length=1, max_length=200)
    description: Optional[str] = Field(None, max_length=1000)
    completed: Optional[bool] = None

class TaskResponse(BaseModel):
    id: str
    title: str
    description: Optional[str]
    completed: bool
    created_at: datetime
    updated_at: Optional[datetime]

    model_config = {"from_attributes": True}

class TaskListResponse(BaseModel):
    tasks: list[TaskResponse]
    total: int

What to verify: The TaskUpdate schema should have all fields as optional — you only update what the client sends. The from_attributes: True config is critical for SQLAlchemy compatibility with Pydantic v2.

Phase 3: Run and Fix Issues

Start the app and you'll likely hit your first real-world issue. This is normal and expected — AI-generated code is a great draft, not a finished product.

Common issues and how to fix them with Cursor:

Issue 1: Dependency Conflicts

If you see ModuleNotFoundError or import errors, paste the full error into Cursor's chat:

I'm getting this error when running the app:

    ModuleNotFoundError: No module named 'aiosqlite'

Here's my requirements.txt: [paste contents]

Fix the requirements and ensure all imports are correct.

Issue 2: Database Schema Mismatches

If the database doesn't initialize properly:

The database tables aren't being created on startup. My database.py uses async SQLAlchemy with async engine. Fix the startup event to create tables properly using async metadata.create_all().

Issue 3: Pydantic Serialization Errors

If you get JSON serialization errors with UUID or datetime objects:

Getting a serialization error when returning TaskResponse. UUID objects aren't serializable by default in FastAPI. Fix the schema to handle UUID serialization properly.

Key principle: Always paste the full error message and relevant code when asking Cursor to fix something. Vague error descriptions get vague fixes.

Phase 4: Add Tests

Once the API works, add tests. This is where Cursor really accelerates development — it can generate comprehensive test suites from your existing code.

Select your main.py file in Cursor, then open Composer with Cmd+I:

Create a comprehensive test suite in tests/test_api.py for the task API. Use pytest with httpx AsyncClient for async testing.

Test requirements:
- Use a test SQLite database in memory
- Test all CRUD operations (create, read, update, delete)
- Test validation (empty title, title too long, invalid JSON)
- Test 404 responses for non-existent tasks
- Test the health check endpoint
- Test creating many tasks and listing them
- Use pytest fixtures for the test client and database setup
- Each test should be independent (clean database state)

Cursor will generate tests like this:

# tests/test_api.py
import pytest
import httpx
from main import app
from database import Base, engine
from sqlalchemy.ext.asyncio import AsyncSession

@pytest.fixture
async def client():
    async with httpx.AsyncClient(
        transport=httpx.ASGITransport(app=app),
        base_url="http://test"
    ) as c:
        yield c

async def test_health_check(client):
    response = await client.get("/health")
    assert response.status_code == 200
    assert response.json() == {"status": "ok"}

async def test_create_task(client):
    response = await client.post("/tasks", json={
        "title": "Learn Cursor AI",
        "description": "Read the vibe coding tutorial"
    })
    assert response.status_code == 201
    data = response.json()
    assert data["title"] == "Learn Cursor AI"
    assert data["completed"] is False
    assert "id" in data

async def test_create_task_validation_empty_title(client):
    response = await client.post("/tasks", json={"title": ""})
    assert response.status_code == 422

async def test_create_task_title_too_long(client):
    response = await client.post("/tasks", json={"title": "x" * 201})
    assert response.status_code == 422

async def test_get_nonexistent_task(client):
    response = await client.get("/tasks/nonexistent-uuid")
    assert response.status_code == 404

Run the tests with pytest tests/ -v. Fix any failures by pasting errors back into Cursor.

Phase 5: Dockerize

With the API working and tested, add Docker support. Select your project in Cursor:

Create a production-ready Dockerfile for this FastAPI application. Requirements:
- Use python:3.12-slim as base image
- Install dependencies in a separate layer for caching
- Use a non-root user for security
- Run with uvicorn in production mode
- Include a .dockerignore file
- Include a docker-compose.yml for local development with hot reload

Cursor generates:

# Dockerfile
FROM python:3.12-slim

WORKDIR /app

# Install dependencies first (for Docker layer caching)
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Copy application code
COPY . .

# Create non-root user
RUN useradd --create-home appuser
USER appuser

EXPOSE 8000

CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
# docker-compose.yml
version: "3.9"
services:
  api:
    build: .
    ports:
      - "8000:8000"
    volumes:
      - .:/app
    environment:
      - DATABASE_URL=sqlite+aiosqlite:///./tasks.db
    command: uvicorn main:app --host 0.0.0.0 --port 8000 --reload

Pro Tips for Cursor Workflow

1. Use @ References for Context

Cursor's @ feature lets you reference specific files, folders, or documentation in your prompts. When fixing a bug, reference the relevant files:

@models.py @schemas.py The TaskResponse schema is missing the updated_at field. Add it with Optional[datetime] type and update all related endpoints.

2. Iterate with "Also" Prompts

Instead of rewriting entire prompts, add to your existing context:

Also add a /tasks/completed endpoint that returns only completed tasks. Follow the same patterns used in the existing endpoints.

3. Use Cursor's Multi-File Edit

Cursor can edit multiple files in a single operation. When you need changes across files (like adding a new field), reference all affected files:

Add a "priority" field (integer, 1-5, default 3) to the task model. Update all related files:
@models.py — add column
@schemas.py — add to all schemas
@main.py — add to endpoints that create/update tasks

4. Keep a Project Brief

Create a PROJECT.md file at the root describing your architecture. Reference it at the start of every new session:

# Project Brief: Task API
# Stack: FastAPI, async SQLAlchemy, SQLite, Pydantic v2
# Testing: pytest + httpx
# Container: Docker with python:3.12-slim
# Convention: All responses are JSON, all IDs are UUIDs

5. When to Code Manually

Even with Cursor, you should write code yourself when:

  • The logic is domain-specific (business rules, industry knowledge)
  • You need to understand deeply (learning new patterns, debugging complex issues)
  • It's a critical security component (auth logic, encryption, key management)
  • The AI keeps getting it wrong after 3+ iterations — sometimes it's faster to write it yourself

The Full Session Recap

Here's the complete workflow timeline:

  1. Minute 0-3: Write the context prompt with full specs
  2. Minute 3-8: Cursor generates all files — review each one
  3. Minute 8-12: Run the app, fix import/dependency issues
  4. Minute 12-15: Test the API with curl or the browser
  5. Minute 15-20: Generate and run tests
  6. Minute 20-25: Dockerize the application
  7. Minute 25-30: Final review, commit to Git

30 minutes from empty folder to working, tested, containerized API. That's the power of vibe coding done right.

Common Pitfalls to Avoid

  • Too much code without reviewing — Always read generated code before accepting it. A small bug in the database model cascades into broken tests and endpoints.
  • Vague prompts — "Make it better" produces inconsistent results. "Add input validation to handle null values" produces exact results.
  • Skip testing — Just because the API responds with 200 doesn't mean it's correct. Write tests that assert specific values.
  • Ignoring error messages — Error messages are free debugging help. Paste them into Cursor with context, and you'll get fixes in seconds.
  • No Git commits between changes — Commit after each phase (setup, models, endpoints, tests, docker). When Cursor generates something broken, you can always revert.
