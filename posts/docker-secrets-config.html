Docker Secrets & Configuration Management: Keep Credentials Out of Your Images

July 13, 2026 11 min read

One of the most common mistakes in Docker is baking secrets directly into images or passing them as plain environment variables. Anyone who can run docker history or inspect the container can read them. This guide covers every method Docker provides for configuration and secrets — from simple env files to production-grade Swarm secrets — so you can choose the right level of security for your use case.

The Problem: Where Do Secrets Live?

Consider this common (but dangerous) Dockerfile:

# ❌ NEVER do this
FROM python:3.12-slim
ENV DATABASE_URL=postgresql://admin:supersecret@db:5432/myapp
ENV API_KEY=sk-1234567890abcdef
COPY . /app
RUN pip install -r requirements.txt

These secrets are now embedded in the image layers. Anyone who pulls the image can run docker history myimage and see them. Even if you use ARG and override at build time, the values persist in image metadata.

Another common anti-pattern:

# ⚠️ Less dangerous but still visible
docker run -e DATABASE_URL="postgresql://admin:supersecret@db:5432/myapp" myapp

The secret appears in docker inspect, /proc/1/environ, and any process listing. Let's fix this.

Level 1: Environment Files (.env) for Local Development

The simplest approach for local development is using .env files. Docker Compose reads these automatically:

# .env (add to .gitignore!)
DATABASE_HOST=db
DATABASE_PORT=5432
DATABASE_USER=app_user
DATABASE_PASSWORD=changeme_dev_only
DATABASE_NAME=myapp

# docker-compose.yml
services:
  web:
    build: .
    env_file: .env
    environment:
      - DATABASE_URL=postgresql://${DATABASE_USER}:${DATABASE_PASSWORD}@${DATABASE_HOST}:${DATABASE_PORT}/${DATABASE_NAME}

Docker Compose also auto-loads .env in the same directory, so you don't even need env_file for that one file. But never commit .env to version control.

# .gitignore
.env
.env.local
*.env

Level 2: Build-time ARGs (Non-sensitive Config)

For non-secret configuration that varies between builds, use ARG:

FROM python:3.12-slim

# Build arguments — NOT secrets!
ARG APP_ENV=production
ARG APP_PORT=8080

ENV APP_ENV=${APP_ENV}
ENV APP_PORT=${APP_PORT}

WORKDIR /app
COPY . .
RUN pip install -r requirements.txt

CMD ["python", "app.py"]

# Pass at build time
docker build --build-arg APP_ENV=staging --build-arg APP_PORT=9090 -t myapp .

Rule of thumb: Use ARG for build configuration (version, environment name, ports). Never for passwords, API keys, or tokens.

Level 3: Docker Secrets (Swarm Mode)

Docker Swarm secrets are the gold standard for containerized deployments. They are:

  • Encrypted at rest — stored in the Swarm's encrypted store
  • Not in image layers — injected at runtime
  • Not in environment — mounted as files under /run/secrets/
  • Accessible only to authorized services — fine-grained permissions

Creating and Using Secrets

# Create secrets from files or stdin
echo -n "supersecret_password" | docker secret create db_password -
echo -n "api_key_12345" | docker secret create api_key -

# Or from a file
docker secret create db_password ./password.txt

# List secrets
docker secret ls

# View a secret (requires admin)
docker secret inspect db_password

Using Secrets in a Stack

# docker-stack.yml
services:
  web:
    image: myapp:latest
    deploy:
      replicas: 3
    secrets:
      - api_key
      - db_password
    environment:
      - APP_ENV=production

  db:
    image: postgres:16
    environment:
      - POSTGRES_DB=myapp
    secrets:
      - source: db_password
        target: POSTGRES_PASSWORD

secrets:
  api_key:
    external: true
  db_password:
    external: true

Services access secrets as files:

# In your Python application
def get_secret(name):
    """Read a Docker secret from /run/secrets/"""
    path = f"/run/secrets/{name}"
    with open(path, "r") as f:
        return f.read().strip()

# Use in your app
db_password = get_secret("db_password")
api_key = get_secret("api_key")

Conditional Access in Dockerfile

You can declare secrets in your Dockerfile for access during build and runtime:

FROM python:3.12-slim

# Declare that this service needs this secret
SECRET api_key

# During build, the secret is available at /run/secrets/api_key
RUN if [ -f /run/secrets/api_key ]; then \
    echo "API key loaded for build"; \
    fi

# At runtime, it's also mounted at /run/secrets/api_key
CMD ["python", "app.py"]

Level 4: Docker Compose Secrets (No Swarm Needed)

Docker Compose v2+ supports secrets without Swarm mode. This is perfect for local development that mimics production:

# docker-compose.yml (version 3.1+)
services:
  web:
    build: .
    secrets:
      - db_password
      - api_key
    volumes:
      - .:/app

  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets:
      - db_password

secrets:
  db_password:
    file: ./secrets/db_password.txt
  api_key:
    file: ./secrets/api_key.txt

# Create the secret files
mkdir -p secrets
echo -n "changeme_dev_only" > secrets/db_password.txt
echo -n "sk_dev_key_12345" > secrets/api_key.txt

# Start — secrets are mounted from files
docker compose up

The secrets appear inside containers at /run/secrets/db_password and /run/secrets/api_key. They're not in environment variables, not in image layers, and not visible via docker inspect.

Level 5: Environment Variable File Mounts

A simpler alternative for Compose without Swarm — mount a file as an environment variable source:

services:
  web:
    build: .
    env_file:
      - .env.production  # Loaded at runtime, not baked in

# .env.production (NOT committed to git)
DATABASE_URL=postgresql://app_user:s3cret@db:5432/myapp
SECRET_KEY=django-insecure-change-me-in-production
API_KEY=sk-1234567890abcdef

The file contents are passed as environment variables at container start. They're not in the image, but they are visible via docker inspect and /proc/1/environ. Good enough for most dev/staging environments.

Level 6: External Secret Management (HashiCorp Vault)

For production deployments, consider integrating Docker with HashiCorp Vault:

# docker-compose.yml with Vault Agent
services:
  vault:
    image: vault:1.17
    cap_add:
      - IPC_LOCK
    environment:
      - VAULT_DEV_ROOT_TOKEN_ID=myroot
    ports:
      - "8200:8200"

  vault-agent:
    image: vault:1.17
    depends_on:
      - vault
    command: agent -config=/vault-agent/config.hcl
    volumes:
      - ./vault-agent:/vault-agent
      - vault-secrets:/vault/secrets

  web:
    build: .
    depends_on:
      - vault-agent
    volumes:
      - vault-secrets:/vault/secrets:ro
    environment:
      - DB_PASSWORD_FILE=/vault/secrets/db_password

volumes:
  vault-secrets:

# vault-agent/config.hcl
vault {
  address = "http://vault:8200"
}

auto_auth {
  method "token" {
    config = { token = "myroot" }
  }
}

listener "tcp" {
  address     = "127.0.0.1:8200"
  tls_disable = 1
}

cache {
  use_auto_auth_token = true
}

template {
  destination = "/vault/secrets/db_password"
  contents    = "{{ with secret \"secret/data/myapp\" }}{{ .Data.data.db_password }}{{ end }}"
}

The Vault Agent runs as a sidecar, authenticates to Vault, and injects secrets into shared volumes that your application reads. Secrets are never in environment variables, Docker images, or configuration files on disk.

Complete Project: Secure Docker Compose Setup

Here's a production-ready docker-compose.yml that uses secrets properly:

# docker-compose.prod.yml
services:
  web:
    build:
      context: .
      dockerfile: Dockerfile
    restart: unless-stopped
    ports:
      - "8080:8000"
    env_file:
      - .env.production  # Non-secret config
    secrets:
      - db_password
      - jwt_secret
      - api_key
    depends_on:
      db:
        condition: service_healthy
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8000/health"]
      interval: 30s
      timeout: 10s
      retries: 3

  db:
    image: postgres:16-alpine
    restart: unless-stopped
    environment:
      POSTGRES_DB: myapp
      POSTGRES_USER: app_user
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets:
      - db_password
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app_user -d myapp"]
      interval: 10s
      timeout: 5s
      retries: 5

  redis:
    image: redis:7-alpine
    restart: unless-stopped
    command: redis-server --requirepass "$(cat /run/secrets/redis_password)"
    secrets:
      - redis_password
    volumes:
      - redisdata:/data

volumes:
  pgdata:
  redisdata:

secrets:
  db_password:
    file: ./secrets/db_password.txt
  jwt_secret:
    file: ./secrets/jwt_secret.txt
  api_key:
    file: ./secrets/api_key.txt
  redis_password:
    file: ./secrets/redis_password.txt

And the corresponding Python code to read secrets:

# config.py
import os
import pathlib

SECRETS_DIR = pathlib.Path("/run/secrets")
FALLBACK_DIR = pathlib.Path(".secrets")  # For local dev

def read_secret(name: str) -> str:
    """Read a secret from Docker secrets or fallback to local file."""
    # Try Docker secrets first
    path = SECRETS_DIR / name
    if path.exists():
        return path.read_text().strip()

    # Fallback for local development
    path = FALLBACK_DIR / name
    if path.exists():
        return path.read_text().strip()

    # Last resort: environment variable
    value = os.environ.get(name.upper())
    if value:
        return value

    raise ValueError(f"Secret '{name}' not found in /run/secrets/, .secrets/, or environment")

# Usage
DB_PASSWORD = read_secret("db_password")
JWT_SECRET = read_secret("jwt_secret")
API_KEY = read_secret("api_key")

Best Practices Summary

  1. Never use ENV for secrets in Dockerfiles — they become part of the image
  2. Use ARG only for non-sensitive build configuration — versions, ports, feature flags
  3. Use .env files for local development — and always .gitignore them
  4. Use Docker Compose secrets for staging — file-based secrets that mount as files
  5. Use Swarm secrets or Vault for production — encrypted, auditable, rotating
  6. Read secrets as files, not env vars — /run/secrets/name in containers
  7. Use PASSWORD_FILE patterns — PostgreSQL, Redis, MySQL all support _FILE suffixes
  8. Rotate secrets regularly — automate with scripts or Vault's built-in rotation

Common Mistakes to Avoid

Mistake 1: ENV in Dockerfile for "temporary" secrets

# ❌ Still visible in image history
ENV AWS_SECRET_KEY=secret123
# ...
ENV AWS_SECRET_KEY=  # Doesn't remove it from history!

Mistake 2: Passing secrets via docker exec

# ❌ Visible in shell history and /proc
docker exec -e API_KEY=secret myapp python script.py

Mistake 3: Building with --secret but logging the value

# BuildKit secrets are safe:
docker build --secret id=api_key,src=./api_key.txt -t myapp .

# Dockerfile:
# RUN --mount=type=secret,id=api_key cat /run/secrets/api_key > /app/key.txt

Managing secrets properly in Docker is about choosing the right tool for your environment. Start with .env files for local development, graduate to Compose secrets for staging, and move to Swarm secrets or Vault for production. The key principle is the same across all levels: secrets should never be part of your container image.
