Python Error Handling: try, except, finally, raise — Complete Beginner's Guide

July 15, 2026 11 min read

Why Error Handling Matters

Every program encounters errors — a file that doesn't exist, a network that times out, user input that's malformed. Without proper error handling, your program crashes with a traceback that confuses users and hides the real problem. Python's try/except system lets you anticipate problems, handle them gracefully, and keep your application running smoothly.

Good error handling isn't about preventing all errors — it's about responding to them in a way that's clear, safe, and recoverable.

Your First try/except Block

Here's the basic structure:

try:
    result = 10 / 0
except ZeroDivisionError:
    print("You can't divide by zero!")

Without the try/except, this would crash. With it, the error is caught and handled. The except block only runs if an error occurs in the try block — otherwise it's skipped entirely.

Catching Specific Exception Types

Always catch specific exceptions rather than using bare except:. This prevents hiding bugs:

try:
    data = open("config.json", "r").read()
    import json
    settings = json.loads(data)
except FileNotFoundError:
    print("Config file not found. Using defaults.")
    settings = {"theme": "dark", "language": "en"}
except json.JSONDecodeError:
    print("Config file is corrupted. Using defaults.")
    settings = {"theme": "dark", "language": "en"}
except PermissionError:
    print("Permission denied. Check file permissions.")
    settings = {"theme": "dark", "language": "en"}

Notice how each except handles a different type of failure with a meaningful message. This makes debugging and user experience much better than a generic "something went wrong."

Accessing Exception Details

Use the as keyword to capture the exception object:

try:
    url = "https://api.example.com/data"
    import urllib.request
    response = urllib.request.urlopen(url)
except urllib.error.URLError as e:
    print(f"Network error: {e.reason}")
    print(f"Type: {type(e).__name__}")
except Exception as e:
    print(f"Unexpected error: {e}")
    print(f"Exception class: {type(e).__name__}")
    print(f"Arguments: {e.args}")

The exception object provides details like e.message, e.args, and e.__traceback__ that help you diagnose what went wrong.

Multiple Exceptions in One Block

Catch several exception types with the same handler using a tuple:

try:
    number = int(user_input)
    result = 100 / number
except (ValueError, ZeroDivisionError) as e:
    print(f"Invalid input: {e}")
    number = 1  # fallback

The else Clause

The else block runs only when NO exception occurs. Use it for code that should run on success but shouldn't accidentally be included in the try:

try:
    result = risky_operation()
except ValueError:
    print("Operation failed, using default.")
    result = default_value
else:
    # Runs only if no exception occurred
    print(f"Success! Result: {result}")
    save_to_database(result)

The finally Clause

finally always runs — whether an exception occurred or not. Use it for cleanup:

import tempfile
import os

temp_file = None
try:
    temp_file = tempfile.NamedTemporaryFile(delete=False)
    temp_file.write(b"important data")
    temp_file.flush()
    process_data(temp_file.name)
except Exception as e:
    print(f"Error processing: {e}")
finally:
    # Always cleanup, even if an error occurred
    if temp_file and os.path.exists(temp_file.name):
        os.unlink(temp_file.name)
        print("Temporary file cleaned up.")

Raising Custom Exceptions

Create your own exception classes for domain-specific errors:

class ValidationError(Exception):
    """Raised when input validation fails."""
    def __init__(self, field, message):
        self.field = field
        self.message = message
        super().__init__(f"Validation failed for '{field}': {message}")

class EmptyEmailError(ValidationError):
    def __init__(self):
        super().__init__("email", "Email cannot be empty")

class InvalidAgeError(ValidationError):
    def __init__(self, age):
        self.age = age
        super().__init__("age", f"Age must be positive, got {age}")

# Usage
def validate_user(email, age):
    if not email:
        raise EmptyEmailError()
    if age < 0:
        raise InvalidAgeError(age)
    return {"email": email, "age": age}

try:
    user = validate_user("", -5)
except ValidationError as e:
    print(f"Field '{e.field}': {e.message}")

The raise Statement

Re-raise an exception after logging or partial handling:

try:
    result = connect_to_database()
except ConnectionError as e:
    print(f"DB connection failed: {e}")
    # Log to monitoring, then re-raise
    log_to_sentry(e)
    raise  # re-raises the same exception with full traceback

You can also chain exceptions to add context:

try:
    config = load_config()
except FileNotFoundError as e:
    raise RuntimeError("Application cannot start without config") from e

The from e preserves the original traceback, so you see both errors in the stack trace.

Assertions for Debugging

assert checks that a condition is true during development. Don't use it for user input — use it for internal invariants:

def calculate_average(numbers):
    assert len(numbers) > 0, "Cannot average an empty list"
    assert all(isinstance(n, (int, float)) for n in numbers), "All items must be numbers"
    return sum(numbers) / len(numbers)

# Raises AssertionError with our message if the list is empty
avg = calculate_average([])  # AssertionError: Cannot average an empty list

Complete Project: Safe File Processor

Here's a real-world example combining everything:

import json
import os
import logging

logger = logging.getLogger(__name__)

class ProcessingError(Exception):
    """Raised when data processing fails."""
    pass

class FileReadError(ProcessingError):
    """Raised when a file cannot be read."""
    def __init__(self, filepath, reason):
        self.filepath = filepath
        self.reason = reason
        super().__init__(f"Cannot read '{filepath}': {reason}")

def load_and_process(filepath):
    """Load a JSON file and process its contents."""
    if not os.path.exists(filepath):
        raise FileReadError(filepath, "File does not exist")

    try:
        with open(filepath, "r", encoding="utf-8") as f:
            data = json.load(f)
    except PermissionError as e:
        raise FileReadError(filepath, f"Permission denied: {e}") from e
    except json.JSONDecodeError as e:
        raise FileReadError(filepath, f"Invalid JSON: {e.msg} at line {e.lineno}") from e

    if not isinstance(data, dict):
        raise ProcessingError(f"Expected dict, got {type(data).__name__}")

    # Process the data
    items = data.get("items", [])
    total = sum(item.get("value", 0) for item in items)

    return {
        "filepath": filepath,
        "item_count": len(items),
        "total_value": total
    }

# Usage in a batch processor
def process_all(filepaths):
    results = []
    errors = []

    for filepath in filepaths:
        try:
            result = load_and_process(filepath)
            results.append(result)
            print(f"✓ Processed: {filepath}")
        except ProcessingError as e:
            errors.append({"file": filepath, "error": str(e)})
            logger.warning(f"✗ Skipped {filepath}: {e}")

    return {"successes": results, "failures": errors}

# Run it
files = ["data/report1.json", "data/report2.json", "data/missing.json"]
report = process_all(files)
print(f"\nProcessed {len(report['successes'])} files, "
      f"{len(report['failures'])} errors")

Best Practices Summary

  • Catch specific exceptions — never use bare except: in production code
  • Keep try blocks small — only wrap code that can actually fail
  • Use else for success path — separates success logic from the risky code
  • Use finally for cleanup — files, connections, temp resources
  • Chain exceptions with from — preserve the original traceback
  • Create custom exceptions — for domain-specific errors that callers can catch
  • Log before re-raising — capture context that won't be available at the top level
  • Don't swallow exceptions — empty except: pass hides real bugs

Summary

Python's error handling system is powerful and flexible. Start with try/except for the basics, add else and finally as your code grows, create custom exceptions for your domain, and always catch specific error types. The goal isn't to eliminate errors — it's to handle them in a way that's clear to users, actionable for developers, and safe for the system.
