Docker Networking & Multi-Stage Builds

2026-06-24 10 min read New

You've built your first Docker container and maybe even used Docker Compose. But how do containers talk to each other? And why are some images 100 MB while others are 1 GB? This guide covers Docker networking fundamentals and multi-stage builds — two skills that separate hobbyists from professionals.

Part 1: Docker Networking

Why Do Containers Need Networks?

By default, each Docker container runs in its own isolated network namespace. This means a container can't reach other containers, your host machine, or external services — unless you connect them to a network. Understanding Docker's built-in network drivers is essential for building real applications.

The Three Built-in Network Drivers

1. Bridge (default) — The most common driver. Docker creates a virtual network bridge, and containers connect to it. Each container gets its own IP address and can reach the internet, but other containers need explicit configuration to reach each other.

# Check existing networks
docker network ls
# OUTPUT:
# NETWORK ID   NAME      DRIVER   SCOPE
# abc123       bridge    bridge   local
# def456       host      host     local
# ghi789       none      null     local

# Create a custom bridge network
docker network create my-app-net

# Run two containers on the same network
docker run -d --name web --network my-app-net nginx:latest
docker run -d --name db --network my-app-net postgres:15

# The "web" container can now reach "db" by name:
docker exec web ping db  # Works! Docker DNS resolves names.

2. Host — The container shares the host machine's network stack. No port mapping needed, but less isolation. Useful for performance-critical apps:

# Container uses host's network directly
docker run -d --name monitoring --network host prom/prometheus

# Access it directly at http://localhost:9090 (no -p mapping needed)
# But: you can't use the same port as another container or the host

3. None — Completely isolated. No network access at all. Use this for containers that only process local files:

docker run --network none python:3.11 python /app/process_data.py

Custom Bridge Networks — Why They Matter

The default bridge network has a major limitation: containers cannot resolve each other by name. Custom bridge networks add built-in DNS resolution:

# ❌ Default bridge — name resolution doesn't work
docker run -d --name web1 nginx        # on default bridge
docker run -d --name web2 nginx        # on default bridge
docker exec web2 curl http://web1      # FAILS — "web1" unknown

# ✅ Custom bridge — name resolution works
docker network create app-net
docker run -d --name web1 --network app-net nginx
docker run -d --name web2 --network app-net nginx
docker exec web2 curl http://web1      # SUCCESS!

Port Mapping vs Internal Communication

Understand the difference between exposing ports externally and internal container-to-container communication:

# -p 8080:80 exposes port 80 to the HOST (http://localhost:8080)
docker run -d --name web -p 8080:80 --network app-net nginx

# Containers on the same network reach each other via internal port
# (not the mapped host port)
docker run --rm --network app-net alpine wget -q -O- http://web

# This uses port 80 (the container port), NOT 8080

Networking with Docker Compose

Docker Compose automatically creates a network for your services. Services can reach each other by their service name:

# docker-compose.yml
services:
  web:
    image: nginx:latest
    ports:
      - "8080:80"
    networks:
      - frontend
      - backend

  api:
    build: ./api
    networks:
      - backend

  db:
    image: postgres:15
    environment:
      POSTGRES_PASSWORD: secret
    networks:
      - backend

networks:
  frontend:
  backend:

In this setup: web can reach both api and db, but db cannot reach web (different networks). This is a security best practice — only expose what's necessary.

Part 2: Multi-Stage Builds

The Problem: Bloated Docker Images

Build tools (compilers, package managers, build dependencies) make your image huge. But you don't need them at runtime. Multi-stage builds solve this by separating build and runtime stages:

# ❌ Single-stage build — everything in one image
FROM node:18
WORKDIR /app
COPY package*.json ./
RUN npm install              # Installs ALL dependencies including dev deps
COPY . .
RUN npm run build            # Compiles the app
EXPOSE 3000
CMD ["node", "dist/main.js"]

# Image size: ~900 MB (includes Node.js, npm, all dev tools)
# ✅ Multi-stage build — tiny production image
# Stage 1: Build
FROM node:18 AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci                    # Deterministic install
COPY . .
RUN npm run build             # Compile to /dist

# Stage 2: Production runtime
FROM node:18-slim AS production
WORKDIR /app
# Copy ONLY production dependencies
COPY --from=builder /app/package*.json ./
RUN npm ci --only=production --ignore-scripts
# Copy ONLY the built output (not source code, not dev tools)
COPY --from=builder /app/dist ./dist
EXPOSE 3000
USER node                     # Run as non-root (security!)
CMD ["node", "dist/main.js"]

# Image size: ~200 MB (75% smaller!)

Multi-Stage for Compiled Languages

The savings are even more dramatic with compiled languages like Go, Rust, or Java:

# Stage 1: Build with Go toolchain (1 GB+)
FROM golang:1.22 AS builder
WORKDIR /app
COPY go.* ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -o server .

# Stage 2: Zero dependencies — just the binary
FROM scratch AS production
COPY --from=builder /app/server /server
EXPOSE 8080
CMD ["/server"]

# Image size: ~10-20 MB (compared to 1+ GB!)

The scratch image is completely empty — no OS, no shell, nothing. Just your binary. This is the gold standard for Go microservices.

Python Multi-Stage Example

# Stage 1: Install dependencies (cached layer!)
FROM python:3.12-slim AS builder
WORKDIR /app
COPY requirements.txt .
RUN pip install --user --no-cache-dir -r requirements.txt

# Stage 2: Runtime image
FROM python:3.12-slim AS production
WORKDIR /app
# Copy installed packages from builder
COPY --from=builder /root/.local /root/.local
# Make sure pip installs are in PATH
ENV PATH=/root/.local/bin:$PATH
# Copy application code last (changes often = better caching)
COPY . .
USER nobody                  # Security: don't run as root
CMD ["python", "app.py"]

Layer Caching Tips

The order of COPY and RUN commands affects build speed. Put stable layers first:

# ❌ Bad order — rebuilds every time code changes
COPY . .
RUN pip install -r requirements.txt   # Always re-runs because COPY invalidated the cache

# ✅ Good order — only rebuilds when dependencies change
COPY requirements.txt .
RUN pip install -r requirements.txt   # Cached unless requirements.txt changes
COPY . .                              # Last layer — always runs but is fast

Part 3: Combining Networking + Builds

Here's a complete multi-stage Docker Compose setup with proper networking:

# docker-compose.yml
services:
  web:
    build:
      context: ./web
      dockerfile: Dockerfile
      target: production   # Use specific stage
    ports:
      - "8080:80"
    networks:
      - public
      - internal
    depends_on:
      - api

  api:
    build:
      context: ./api
      dockerfile: Dockerfile
      target: production
    networks:
      - internal
    environment:
      DATABASE_URL: postgres://user:pass@db:5432/myapp
    depends_on:
      - db

  db:
    image: postgres:15-alpine
    networks:
      - internal
    environment:
      POSTGRES_DB: myapp
      POSTGRES_USER: user
      POSTGRES_PASSWORD: pass
    volumes:
      - pgdata:/var/lib/postgresql/data

networks:
  public:   # Only web connects here (exposed to host via ports)
  internal: # api and db live here (not accessible from outside)

volumes:
  pgdata:

Common Networking Troubleshooting

# Check a container's network configuration
docker inspect web --format '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}'

# View all networks
docker network ls

# Inspect a network's details (connected containers, IPs)
docker network inspect my-app-net

# Connect a running container to a network
docker network connect my-app-net existing_container

# Test connectivity between containers
docker exec web curl -v http://api:3000/health

Summary & Best Practices

  • Always use custom bridge networks instead of the default — you get DNS resolution for free.
  • Use multi-stage builds to reduce image size. Aim for small runtime images (under 200 MB when possible).
  • Run containers as non-root with USER — a simple security improvement.
  • Order Dockerfile commands by frequency of change — stable layers first for better caching.
  • Segregate networks — don't give every container access to every other container.
  • Use scratch or distroless images for compiled languages to minimize attack surface.
