Docker Volumes and Bind Mounts: Persist Data Beyond Container Lifecycles

July 4, 2026 · 9 min read

Here's a harsh Docker reality: when a container stops, everything inside it disappears. Logs, databases, uploaded files — all gone. Unless you use volumes or bind mounts. This guide walks you through every approach to data persistence in Docker, from simple bind mounts to production-ready named volumes.

Why Data Persistence Matters

Containers are ephemeral by design. The writable container layer exists only as long as the container lives. Once you run docker rm, that layer is destroyed. This is intentional — it keeps containers lightweight and reproducible. But databases, config files, and user uploads need to survive container restarts.

The Three Types of Mounts

Docker offers three ways to persist or share data:

  • Volumes — Managed by Docker, stored in /var/lib/docker/volumes/. Best for production.
  • Bind mounts — Map a specific host path into the container. Great for local development.
  • tmpfs mounts — Stored in host memory only. Ephemeral, never written to disk. Good for sensitive data.

Docker Volumes: The Production-Ready Choice

Volumes are Docker's recommended way to persist data. Docker manages them, making them portable across machines and easy to back up.

Creating a Named Volume

# Create a volume manually
docker volume create my_db_data

# List all volumes
docker volume ls

# Inspect a volume (see where it lives on disk)
docker volume inspect my_db_data

# Remove a volume
docker volume rm my_db_data

Using a Volume with Docker Run

# Run PostgreSQL with a persistent volume
docker run -d \
  --name postgres \
  -e POSTGRES_PASSWORD=secret123 \
  -v my_db_data:/var/lib/postgresql/data \
  postgres:16

# Even if you remove the container, data survives:
docker rm -f postgres
docker run -d \
  --name postgres \
  -e POSTGRES_PASSWORD=secret123 \
  -v my_db_data:/var/lib/postgresql/data \
  postgres:16

# Your databases are still there! 🎉

The -v flag uses the format VOLUME_NAME:CONTAINER_PATH. Docker automatically creates the volume if it doesn't exist. The container path /var/lib/postgresql/data is where PostgreSQL stores its data files.

Volumes with Docker Compose

In docker-compose.yml, volumes are declared at the top level:

# docker-compose.yml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: secret123
    volumes:
      - db_data:/var/lib/postgresql/data
    ports:
      - "5432:5432"

  redis:
    image: redis:7-alpine
    volumes:
      - redis_data:/data

volumes:
  db_data:    # Named volume for PostgreSQL
  redis_data: # Named volume for Redis

Running docker compose up -d creates both volumes automatically. They persist across docker compose down — only docker compose down -v removes them.

Bind Mounts: Developer's Best Friend

Bind mounts map a specific file or directory from your host machine into the container. This is the default way to do hot-reload development.

Development Workflow with Bind Mounts

# Mount your entire project directory
docker run -d \
  --name myapp \
  -v $(pwd):/app \
  -w /app \
  python:3.12-slim \
  python app.py

# Edit app.py on your host → see changes instantly in container

The $(pwd) maps your current directory to /app inside the container. The -w /app sets the working directory. Every file change on your host is immediately reflected in the container — no rebuild needed.

Bind Mount in Docker Compose

services:
  web:
    build: .
    volumes:
      - ./src:/app/src        # Mount only the source directory
      - ./config:/app/config  # Mount config separately
    ports:
      - "8000:8000"

Bind mount paths starting with . or / are treated as host paths. Relative paths are resolved from the docker-compose.yml location.

Read-Only Bind Mounts

Prevent containers from modifying host files by adding :ro:

# Mount config as read-only
docker run -d \
  --name nginx \
  -v /etc/nginx/conf.d:/etc/nginx/conf.d:ro \
  nginx:latest

# Container can read configs but cannot modify host files

tmpfs Mounts: In-Memory Storage

tmpfs mounts store data in the host's memory. They never hit disk and disappear when the container stops. Perfect for temporary files, session data, or sensitive info.

# Mount /tmp as tmpfs
docker run -d \
  --name app \
  --tmpfs /tmp:rw,noexec,nosuid,size=100m \
  python:3.12-slim

# In docker-compose.yml:
services:
  app:
    image: python:3.12-slim
    tmpfs:
      - /tmp:rw,noexec,nosuid,size=100m

Volumes vs Bind Mounts: When to Use Which

Factor Volumes Bind Mounts
Managed by Docker ✅ Yes ❌ No
Works on Windows/Mac/Linux ✅ Yes ⚠️ Path quirks
Easy to back up ✅ Yes ❌ Manual
Hot-reload development ❌ Slow for many files ✅ Instant
Production databases ✅ Recommended ❌ Not recommended
Performance (Linux) ✅ Native ✅ Native

Rule of thumb: Use volumes for production data (databases, uploads). Use bind mounts for development (source code, configs). Use tmpfs for temporary or sensitive data.

Backing Up and Restoring Volumes

Docker volumes are just directories on the host. You can back them up with standard tools:

# Backup a volume using a temporary container
docker run --rm \
  -v my_db_data:/data:ro \
  -v $(pwd):/backup \
  alpine \
  tar czf /backup/db-backup.tar.gz -C /data .

# Restore from backup
docker run --rm \
  -v my_db_data:/data \
  -v $(pwd):/backup:ro \
  alpine \
  sh -c "cd /data && tar xzf /backup/db-backup.tar.gz"

This technique works with any volume — just change the volume name and backup path. Run it as a cron job for automated backups.

Volume Drivers: Storage Beyond Local Disk

By default, Docker uses the local volume driver. But you can install plugins for cloud storage:

# Create a volume with a custom driver
docker volume create \
  -d flocker \
  --opt size=100 \
  my_flocker_volume

# Use it with your container
docker run -d \
  --name postgres \
  -v my_flocker_volume:/var/lib/postgresql/data \
  postgres:16

Popular drivers include Portworx, Flocker, and CSI drivers for AWS EBS, GCP Persistent Disks, and Azure Disks. These let you share volumes across machines in a cluster.

Common Gotchas

Permission Issues

If your container can't write to a bind-mounted directory, check ownership:

# Fix permissions inside the container
docker run --rm -v $(pwd):/app alpine chown 1000:1000 /app

# Or specify the user in your Dockerfile
USER 1000

Docker Creates Directories Instead of Mounting

If the container path already exists as a directory, Docker fills the volume contents into it — it doesn't replace it. This can cause confusion:

# Bad: /data already exists in the image with files
docker run -v my_vol:/data nginx  # Volume contents merged with existing

# Good: mount into a clean directory
docker run -v my_vol:/custom/data nginx

Volume Doesn't Exist, Docker Creates It Anyway

When you use -v name:/path and name isn't an absolute path, Docker creates a volume named name. This is often unexpected:

# This creates a VOLUME called "mydata", not a bind mount!
docker run -v mydata:/app nginx

# This is a bind mount (absolute path)
docker run -v /home/user/mydata:/app nginx

Using Docker Compose avoids this ambiguity — named volumes must be declared in the volumes: section.

Real-World Example: Full Stack App

Here's a complete docker-compose.yml showing all three mount types:

services:
  # Database: named volume for persistence
  postgres:
    image: postgres:16
    environment:
      POSTGRES_DB: myapp
      POSTGRES_USER: admin
      POSTGRES_PASSWORD: ${DB_PASSWORD}
    volumes:
      - pg_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U admin"]
      interval: 10s
      timeout: 5s
      retries: 5

  # App server: bind mount for development
  web:
    build: .
    volumes:
      - ./app:/app        # Source code (bind mount)
      - ./uploads:/uploads # User uploads (bind mount)
    environment:
      DATABASE_URL: postgresql://admin:${DB_PASSWORD}@postgres:5432/myapp
    tmpfs:
      - /tmp:noexec,size=50m  # Temp files in memory
    depends_on:
      postgres:
        condition: service_healthy

  # Backup runner: mounts database volume as read-only
  backup:
    image: alpine
    volumes:
      - pg_data:/source:ro     # Read-only access to DB data
      - ./backups:/backup      # Store backups on host
    command: >
      sh -c "sleep 3600 &&
             tar czf /backup/db-$(date +%Y%m%d).tar.gz -C /source ."

Summary

  • Volumes are Docker-managed, portable, and ideal for production data
  • Bind mounts map host paths into containers, perfect for development
  • tmpfs mounts keep data in memory — great for sensitive or temporary files
  • Always use named volumes for databases in production
  • Use bind mounts with source code for instant hot-reload
  • Back up volumes with docker run + tar

Understanding these three mount types is the key to building reliable, data-driven Docker applications. Start with volumes for your databases, bind mounts for your code, and you'll never lose data when a container restarts.
