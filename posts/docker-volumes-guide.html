Docker Volumes and Persistent Data: Never Lose Your Data — Complete Beginner's Guide

July 17, 2026 10 min read

Containers are ephemeral by design. When a container stops and restarts, everything inside it resets. If your app writes a database, uploads a file, or caches data inside the container, all of that is lost on the next restart. Docker volumes solve this problem by creating persistent storage that survives container lifecycle events. Let's learn every way Docker handles persistent data.

The Problem: Containers Are Temporary

Run this and watch the data disappear:

# Create a container with some data
docker run --name demo -d alpine sh -c "echo 'hello' > /data.txt && tail -f /dev/null"

# Check the file exists
docker exec demo cat /data.txt
# Output: hello

# Remove and recreate the container
docker rm -f demo
docker run --name demo -d alpine sh -c "tail -f /dev/null"

# Check again — it's gone!
docker exec demo cat /data.txt
# Output: cat: can't open '/data.txt': No such file or directory

The filesystem inside a container is built from the image layers + a thin writable layer. When the container is removed, that writable layer is destroyed. Volumes exist outside the container — on the host machine or a managed storage system.

Three Types of Docker Storage

Docker provides three mechanisms for persistent data, each with different tradeoffs:

  1. Named Volumes — Docker manages the storage location. Best for most use cases.
  2. Bind Mounts — You specify an exact host path. Great for development and config files.
  3. tmpfs Mounts — RAM-only storage. Fast, but lost on restart. Good for secrets and caches.

Named Volumes: The Docker Way

Docker creates and manages the storage directory. You don't worry about the host path.

# Create a volume explicitly
docker volume create mydata

# Use it in a container
docker run -d \
  --name db \
  -v mydata:/var/lib/postgresql/data \
  postgres:16

# The volume persists even if you delete the container
docker rm -f db
docker run -d \
  --name db2 \
  -v mydata:/var/lib/postgresql/data \
  postgres:16
# Data is still there! ✅

The -v mydata:/var/lib/postgresql/data flag maps the volume named mydata to the path inside the container. Docker stores named volumes under /var/lib/docker/volumes/mydata/_data on Linux.

Use named volumes in docker-compose.yml:

# docker-compose.yml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: secret
    volumes:
      - pgdata:/var/lib/postgresql/data

  app:
    image: my-app:latest
    depends_on:
      - db
    volumes:
      - uploads:/app/uploads

volumes:
  pgdata:        # Named volume for database
  uploads:       # Named volume for user uploads

Named volumes are the recommended default for production databases and any data that must survive container restarts.

Bind Mounts: Direct Host Access

Instead of a Docker-managed name, you point to an exact path on your host filesystem:

# Mount your local project code into the container
docker run -d \
  --name myapp \
  -v /home/hugo/projects/myapp:/app \
  python:3.12 \
  python /app/main.py

In docker-compose, use absolute paths or ./ relative to the compose file:

# docker-compose.yml
services:
  web:
    build: .
    volumes:
      - ./src:/app/src          # Live code sync for development
      - ./config:/app/config    # Config files
      - static_data:/app/data   # Named volume (mixed usage!)

Bind mounts are ideal for development because changes to files on your host are immediately visible inside the container. No rebuild, no restart — edit and reload.

Bind Mount: read_only for Security

Prevent containers from modifying host files:

volumes:
  - ./config/app.env:/app/config.env:ro  # read-only mount

The :ro suffix makes the mount read-only inside the container. Use this for config files, certificates, and anything the container should read but never write.

tmpfs: RAM-Only Storage

tmpfs stores data in the host's RAM. It's incredibly fast but completely lost when the container stops:

# Mount /run/secrets as tmpfs
docker run -d \
  --tmpfs /run/secrets:rw,noexec,nosuid,size=64m \
  my-app:latest

Use tmpfs for:

  • Sensitive data you never want on disk (tokens, keys)
  • High-speed cache that doesn't need persistence
  • Database temp directories for performance

Docker Volume Commands: The Essential Toolkit

# List all volumes
docker volume ls
# local   mydb_data
# local   uploads

# Inspect a volume (see mountpoint, driver, labels)
docker volume inspect mydb_data
# [{
#   "CreatedAt": "2026-07-17T10:30:00Z",
#   "Mountpoint": "/var/lib/docker/volumes/mydb_data/_data",
#   "Name": "mydb_data",
#   "Driver": "local"
# }]

# Remove unused volumes
docker volume prune
# WARNING! This removes all volumes not attached to a container.

# Remove a specific volume
docker volume rm mydb_data

Back Up and Restore Docker Volumes

This is the most important skill for Docker volumes. Here's a production-ready backup pattern:

# Step 1: Stop the container to ensure data consistency
docker stop db

# Step 2: Run a temporary container to copy volume data
docker run --rm \
  -v mydb_data:/source:ro \
  -v $(pwd)/backups:/backup \
  alpine \
  tar czf /backup/db-$(date +%Y%m%d).tar.gz -C /source .

# Step 3: Restart the container
docker start db

# Your backup is at: ./backups/db-20260717.tar.gz

Restore from backup:

# Stop the running container
docker stop db

# Remove the old volume
docker volume rm mydb_data

# Create a fresh volume
docker volume create mydb_data

# Extract backup into the new volume
docker run --rm \
  -v mydb_data:/data \
  -v $(pwd)/backups:/backup \
  alpine \
  tar xzf /backup/db-20260717.tar.gz -C /data

# Start the container
docker start db

Automated Backup with Python

Schedule backups using a Python script that integrates with Docker:

import subprocess
import datetime
import os
from pathlib import Path

BACKUP_DIR = Path("/home/hugo/backups/docker")
MAX_BACKUPS = 7  # Keep last 7 days

def backup_volume(volume_name, container_name=None):
    """Create a timestamped backup of a Docker volume."""
    BACKUP_DIR.mkdir(parents=True, exist_ok=True)

    timestamp = datetime.datetime.now().strftime("%Y%m%d_%H%M")
    backup_file = BACKUP_DIR / f"{volume_name}_{timestamp}.tar.gz"

    # Stop container if provided (for consistent backups)
    if container_name:
        print(f"Stopping {container_name}...")
        subprocess.run(["docker", "stop", container_name], check=True)

    try:
        # Create backup using a temporary Alpine container
        cmd = [
            "docker", "run", "--rm",
            "-v", f"{volume_name}:/source:ro",
            "-v", f"{BACKUP_DIR}:/backup",
            "alpine",
            "tar", "czf", f"/backup/{backup_file.name}",
            "-C", "/source", "."
        ]
        subprocess.run(cmd, check=True)
        print(f"✅ Backed up {volume_name} -> {backup_file}")
    finally:
        if container_name:
            subprocess.run(["docker", "start", container_name], check=True)

    return backup_file

def rotate_backups(volume_name):
    """Delete old backups, keeping only MAX_BACKUPS most recent."""
    backups = sorted(BACKUP_DIR.glob(f"{volume_name}_*.tar.gz"))
    while len(backups) > MAX_BACKUPS:
        oldest = backups.pop(0)
        oldest.unlink()
        print(f"🗑️  Removed old backup: {oldest}")

# Usage
backup_volume("pgdata", container_name="db")
rotate_backups("pgdata")

Schedule this script with cron to run daily:

# Add to crontab: crontab -e
0 2 * * * /usr/bin/python3 /home/hugo/scripts/docker-backup.py

Docker Compose Volume Patterns

Here's a production-ready docker-compose setup with all three volume types:

# docker-compose.yml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
      POSTGRES_DB: myapp
    volumes:
      - pgdata:/var/lib/postgresql/data    # Named volume — persistent DB
    secrets:
      - db_password
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 10s
      timeout: 5s
      retries: 5

  app:
    build: .
    depends_on:
      db:
        condition: service_healthy
    volumes:
      - uploads:/app/uploads              # Named volume — user files
      - ./config:/app/config:ro           # Bind mount — config (read-only)
    tmpfs:
      - /tmp:size=64m,exec                # tmpfs — temporary files
    environment:
      DATABASE_URL: postgresql://postgres:${DB_PASSWORD}@db:5432/myapp

  backup:
    image: alpine
    entrypoint: []
    volumes:
      - pgdata:/source:ro                 # Read the DB volume
      - ./backups:/backup                 # Write backups to host
    profiles:
      - maintenance                       # Only start manually

volumes:
  pgdata:
    driver: local
  uploads:
    driver: local

secrets:
  db_password:
    file: ./secrets/db_password.txt

Volume Driver Options

Docker supports volume drivers beyond the default local driver. Here's how to configure options:

volumes:
  pgdata:
    driver: local
    driver_opts:
      type: none
      o: bind
      device: /mnt/fast-ssd/postgres  # Mount from a specific disk
  uploads:
    driver: local
    driver_opts:
      type: nfs
      o: addr=nfs-server,port=2049,rw,nfsvers=4
      device: ":/exports/uploads"      # NFS shared storage

NFS volumes let multiple containers across different hosts share the same storage — useful for file uploads in a multi-node cluster.

Common Mistakes and How to Avoid Them

  • ❌ Mounting over important directories — Don't mount over / or /etc. Always mount to specific paths where data belongs.
  • ❌ Forgetting volume names in compose — If you don't declare a volume at the bottom of your docker-compose.yml, Docker creates an anonymous volume with a long hash name that's hard to manage.
  • ❌ Losing data on docker-compose down — By default, docker-compose down does NOT remove named volumes. You need docker-compose down -v to destroy volumes. Remember this!
  • ❌ Relying on bind mounts in production — Bind mounts tie your deployment to a specific host path. Named volumes are more portable and survive Docker reinstallation.
  • ❌ Not testing backups — A backup script is useless if you never verify restoration. Test your restore process monthly.

Best Practices Summary

  • Use named volumes for databases — PostgreSQL, MySQL, Redis, MongoDB all need persistent storage
  • Use bind mounts for development — Mount your code directory with :ro for configs, writable for source code
  • Use tmpfs for secrets and caches — Never store tokens or session data on disk
  • Automate backups — Daily tar.gz backups with rotation, stored outside Docker
  • Test your restore process — Regularly practice restoring from backups in a staging environment
  • Document your volume names — Keep a README mapping volumes to services so your team knows what's where
