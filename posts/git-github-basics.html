Git and GitHub for Beginners: Version Control Step by Step

June 24, 2026 · 12 min read

You're writing code. You made a change, and now something is broken. You wish you could go back to yesterday's version. Or maybe you're working on a new feature and don't want to break what already works. Or perhaps you want to collaborate with someone else on the same project.

Git solves all of these problems. It's a version control system — a time machine for your code. Every change you make is recorded, and you can revert to any previous state. GitHub is a platform that hosts your Git repositories online, enabling collaboration, code reviews, and project management.

In this tutorial, you'll learn everything from installing Git to collaborating with others — with practical examples you can follow along.

What Is Version Control?

Version control tracks changes to files over time. Without it, developers resort to naming files like:

script.py
script_v2.py
script_v2_FINAL.py
script_v2_FINAL_REAL.py
script_v2_FINAL_REAL_forreal.py

Sound familiar? 😅 Git eliminates this chaos by storing every change in a repository (short: repo). You can see the full history of every file, compare versions, and revert anything.

Installing Git

Git is free and available on all platforms:

# macOS (using Homebrew)
brew install git

# Ubuntu / Debian
sudo apt update
sudo apt install git

# Windows
# Download from https://git-scm.com/download/win
# The installer handles everything automatically

# Verify installation
git --version
# Output: git version 2.43.0 (or newer)

Configure Git for the First Time

Before using Git, tell it who you are. These details are attached to every commit:

# Set your name and email globally
git config --global user.name "Your Name"
git config --global user.email "you@example.com"

# Set a default text editor (optional)
git config --global core.editor "nano"

# Check your settings
git config --list

# Use a colored output (recommended)
git config --global color.ui auto

Your First Git Repository

A repository is a folder that Git tracks. Let's create one from scratch:

# 1. Create a project directory
mkdir my-first-project
cd my-first-project

# 2. Initialize a Git repository
git init
# Output: Initialized empty Git repository in /path/to/my-first-project/.git/

# 3. Create a file
echo 'print("Hello, Git!")' > hello.py

# 4. Check the status
git status
# Output:
# On branch main
# Untracked files:
#   hello.py
# nothing added to commit but untracked files present

# 5. Add the file to the staging area
git add hello.py

# 6. Commit the changes
git commit -m "Add hello.py script"
# Output:
# [main (root-commit) abc1234] Add hello.py script
#  1 file changed, 1 insertion(+)
#  create mode 100644 hello.py

Understanding the Three States

Git organizes files into three states:

  • Untracked: New files Git doesn't know about yet
  • Unstaged: Tracked files with uncommitted changes
  • Staged: Changes selected to be included in the next commit

The workflow is: modify → git add → git commit. Think of git add as marking which changes you want to save, and git commit as actually saving them to history.

Working with Commits

A commit is a snapshot of your project at a point in time. Here's how to work with them:

# Make a change to an existing file
# Edit hello.py to add a new line
echo 'print("Hello, World!")' >> hello.py

# Check what changed
git status
git diff
# Shows the exact differences (diffs) between the
# last commit and the current state

# Stage and commit
git add hello.py
git commit -m "Add second print statement to hello.py"

# View commit history
git log
# Shows all commits, newest first:
# commit abc1234 (HEAD -> main)
# Author: Your Name 
# Date:   Mon Jun 24 10:30:00 2026 +0000
#
#     Add second print statement to hello.py
#
# commit def5678
# Author: Your Name 
# Date:   Mon Jun 24 10:15:00 2026 +0000
#
#     Add hello.py script

# One-line log (compact view)
git log --oneline
# abc1234 (HEAD -> main) Add second print statement to hello.py
# def5678 Add hello.py script

Writing Good Commit Messages

Best practice: Write commit messages in the imperative tense — like you're giving a command. "Add login feature" not "Added login feature". Keep the first line under 50 characters. 
# ✅ Good commit messages
git commit -m "Add user authentication"
git commit -m "Fix typo in README"
git commit -m "Update Python version to 3.12"

# ❌ Bad commit messages
git commit -m "fix"
git commit -m "asdf"
git commit -m "changed stuff"

Branching: Work on Features Safely

Branches let you work on new features without touching the main code. Think of a branch as a parallel timeline:

# View current branches
git branch
# * main   (the * means you're on this branch)

# Create a new branch
git branch feature-login

# Switch to the new branch
git checkout feature-login
# or (Git 2.23+):
git switch feature-login

# Create AND switch in one command
git checkout -b feature-signup
# or:
git switch -c feature-signup

# Do your work on the branch...
echo '# Login page' > login.html
git add login.html
git commit -m "Add login page"

# Switch back to main
git switch main
# login.html is gone! (it's only on the feature branch)

# List all branches
git branch
# * main
#   feature-login
#   feature-signup

# Delete a branch (after merging, if needed)
git branch -d feature-login

Merging: Combining Branches

When your feature is ready, merge it back into main:

# Make sure you're on main
git switch main

# Merge the feature branch into main
git merge feature-login

# View the combined history
git log --oneline --graph
# *   abc1234 (HEAD -> main) Merge branch 'feature-login'
# |\
# | * def5678 Add login page
# |/
# * 1234567 Initial commit

Merge conflicts happen when both branches modify the same lines in a file. Git marks the conflicting areas and lets you resolve them manually:

# When a conflict occurs, Git tells you:
# CONFLICT (content): Merge conflict in file.py
# Automatic merge failed; fix conflicts and then commit

# Open the file and look for markers:
# <<<<<<< HEAD
# your code on main
# =======
# their code on the branch
# >>>>>>> feature-login

# Resolve by keeping what you want, remove the markers, then:
git add file.py
git commit -m "Resolve merge conflict in file.py"

Remote Repositories and GitHub

A remote is a copy of your repository on another server — usually GitHub. Here's the full workflow:

# 1. Create a repository on GitHub (via the website)
#    https://github.com/new
#    → Name: my-first-project
#    → Public, Initialize with NO README

# 2. Connect your local repo to the remote
git remote add origin https://github.com/username/my-first-project.git

# 3. Verify the connection
git remote -v
# origin  https://github.com/username/my-first-project.git (fetch)
# origin  https://github.com/username/my-first-project.git (push)

# 4. Push your code to GitHub
git push -u origin main
# -u sets "origin main" as the default for future pushes

# 5. Future pushes are simpler
git push

# 6. Pull updates from GitHub (fetch + merge)
git pull

# Clone an existing repo from GitHub
git clone https://github.com/username/my-first-project.git
cd my-first-project

The Complete Daily Workflow

Here's the typical workflow you'll use every day:

# Morning: pull latest changes
git switch main
git pull

# Create a feature branch
git switch -c fix-bug-123

# Work: edit files, test, repeat
# (make changes in your editor)

# Check what changed
git status
git diff

# Stage and commit
git add file1.py file2.py
git commit -m "Fix bug #123: handle null input"

# Push and create pull request
git push origin fix-bug-123

# Go to GitHub → "Compare & Pull Request"
# → Review → Merge → Delete branch

.gitignore: Files to Exclude

Some files should never be tracked — passwords, build artifacts, virtual environments. A .gitignore file tells Git to ignore them:

# File: .gitignore

# Python
__pycache__/
*.pyc
*.pyo
venv/
.env
*.egg-info/
dist/
build/

# IDE
.vscode/
.idea/
*.swp
*.swo

# OS files
.DS_Store
Thumbs.db

# Environment variables
.env
.env.local

Once a file is tracked, adding it to .gitignore won't stop Git from tracking it. You must remove it from tracking first:

# Remove a tracked file from Git (keep local copy)
git rm --cached filename

# Then add the .gitignore entry and commit
git add .gitignore
git commit -m "Add .gitignore for Python projects"

Undoing Mistakes

Git has safety nets for almost every mistake:

# Undo changes to a file (before committing)
git checkout -- filename.py
# or (Git 2.23+):
git restore filename.py

# Unstage a file (after git add, before git commit)
git restore --staged filename.py

# Amend the last commit (change message or add files)
git commit --amend -m "New commit message"

# Revert a commit (create a new commit that undoes it)
git revert abc1234

# WARNING: Only use on your own commits, never on shared history
git reset --hard abc1234  # Go back to a previous commit

Real Project: A Python CLI Tool

Let's put it all together with a real project:

# 1. Set up the project
mkdir todo-cli
cd todo-cli
git init

# 2. Create .gitignore
echo -e "venv/\n__pycache__/\n*.pyc\n.env" > .gitignore
git add .gitignore
git commit -m "Initialize project with .gitignore"

# 3. Create the main script
cat > todo.py << 'EOF'
#!/usr/bin/env python3
"""Simple command-line TODO list."""
import json
import sys

FILENAME = "todos.json"

def load_todos():
    try:
        with open(FILENAME, "r") as f:
            return json.load(f)
    except FileNotFoundError:
        return []

def save_todos(todos):
    with open(FILENAME, "w") as f:
        json.dump(todos, f, indent=2)

def add_todo(text):
    todos = load_todos()
    todos.append({"text": text, "done": False})
    save_todos(todos)
    print(f"✅ Added: {text}")

def list_todos():
    todos = load_todos()
    if not todos:
        print("No todos yet. Use: python todo.py add 'task'")
        return
    for i, todo in enumerate(todos, 1):
        status = "✅" if todo["done"] else "⬜"
        print(f"  {status} {i}. {todo['text']}")

def main():
    if len(sys.argv) < 2:
        print("Usage: python todo.py [add|list]")
        return

    command = sys.argv[1]

    if command == "add" and len(sys.argv) >= 3:
        add_todo(" ".join(sys.argv[2:]))
    elif command == "list":
        list_todos()
    else:
        print("Usage: python todo.py [add 'task'|list]")

if __name__ == "__main__":
    main()
EOF

git add todo.py
git commit -m "Add TODO CLI with add and list commands"

# 4. Test it
python todo.py add "Learn Git"
python todo.py add "Push to GitHub"
python todo.py list
# Output:
# ✅ Added: Learn Git
# ✅ Added: Push to GitHub
# ⬜ 1. Learn Git
# ⬜ 2. Push to GitHub

# 5. Create a feature branch for a new command
git switch -c feature-mark-done

# Add the mark-done command to todo.py
# (edit the file to add a complete() function...)

git add todo.py
git commit -m "Add mark-done command to complete todos"

# Switch back to main and merge
git switch main
git merge feature-mark-done

# 6. Push to GitHub
git remote add origin https://github.com/username/todo-cli.git
git push -u origin main

echo "🎉 Your first Git project is on GitHub!"

Git Commands Quick Reference

Command Purpose
git init Start a new repository
git clone URL Copy a remote repository
git status Check file states
git add FILE Stage changes for commit
git commit -m "msg" Save staged changes
git log View commit history
git branch List branches
git switch -c name Create and switch branch
git merge name Merge branch into current
git push Upload to remote
git pull Download and merge from remote

Summary

Git and GitHub are essential tools for every developer. Here's the essential flow:

  1. git init — Start tracking your project
  2. git add + git commit — Save your progress
  3. git branch + git switch — Work on features in isolation
  4. git merge — Combine changes back together
  5. git remote add + git push — Share on GitHub
  6. git pull — Stay in sync with the team

Start using Git for every project from day one. The habit pays dividends immediately.
