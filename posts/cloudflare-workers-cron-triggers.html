Cloudflare Workers Cron Triggers: Scheduled Tasks on the Edge

July 3, 2026 · 11 min read

Need to run a cleanup job every hour? Fetch data from an API every 10 minutes? Send daily digest emails? Traditionally, you'd set up a server with crontab, keep it running 24/7, and manage its uptime. Cloudflare Workers Cron Triggers eliminate all of that — you write a small script, and Cloudflare runs it on a schedule, for free (up to 500K invocations/month on the free tier).

This guide covers everything: setup, cron expressions, real-world patterns, Python integration via the Workers API, and production best practices.

What Are Cron Triggers?

Cron Triggers let your Cloudflare Worker execute on a schedule — just like crontab on Linux, but running on Cloudflare's global network. Your code executes at one of Cloudflare's edge locations, with no server to provision or maintain.

Key features:

  • Free tier: Up to 500,000 invocations per month (enough for a cron running every minute: ~43,800/month)
  • Execution time: Up to 15 minutes (Workers Paid: up to 30 minutes)
  • Cron syntax: Standard cron expressions with one caveat — you need at least one * or , in the minute or hour field
  • Global execution: Runs from the nearest edge location, low latency

Setup: Your First Cron Worker

Step 1: Install Wrangler CLI

# Install Wrangler (Cloudflare's CLI tool)
npm install -g wrangler

# Log in to your Cloudflare account
wrangler login

Step 2: Initialize a Worker Project

# Create a new project
mkdir cron-worker
cd cron-worker
wrangler init --name my-cron-worker

# This creates:
# └── src/
#     └── index.js    # Your Worker code
# └── wrangler.toml   # Configuration file

Step 3: Configure Cron in wrangler.toml

# wrangler.toml
name = "my-cron-worker"
main = "src/index.js"
compatibility_date = "2026-07-01"

# Define cron schedule(s)
triggers = { cron = ["*/10 * * * *", "0 9 * * 1"] }

This configuration runs the worker:

  • */10 * * * * — Every 10 minutes
  • 0 9 * * 1 — Every Monday at 9:00 AM UTC

Step 4: Write the Worker Code

// src/index.js

export default {
    // Regular HTTP request handler
    async fetch(request, env) {
        return new Response("Worker is alive!", {
            headers: { "Content-Type": "text/plain" }
        });
    },

    // Cron schedule handler — runs on schedule
    async scheduled(event, env, ctx) {
        console.log(`Cron triggered at ${new Date().toISOString()}`);
        console.log("Scheduled event:", JSON.stringify(event));

        // Your scheduled task logic here
        await doSomething(env);
    }
};

async function doSomething(env) {
    // Example: fetch data and store in Workers KV
    const response = await fetch("https://api.example.com/data");
    const data = await response.json();

    // Store in KV
    await env.MY_KV.put("latest-data", JSON.stringify(data));
    console.log("Data stored successfully");
}

Step 5: Deploy

# Deploy to Cloudflare
wrangler deploy

# Verify cron schedule
wrangler triggers cron list

# Test locally (simulate a cron trigger)
npx wrangler dev --test-scheduled

Understanding Cron Expressions

Cron expressions define when your job runs. Standard format: minute hour day-of-month month day-of-week

Schedule Expression
Every minute * * * * *
Every 5 minutes */5 * * * *
Every hour at :30 30 * * * *
Every Monday at 9 AM UTC 0 9 * * 1
Weekdays at 2 PM UTC 0 14 * * 1-5
1st of every month at midnight 0 0 1 * *
Every 30 minutes, 8 AM–6 PM UTC */30 8-18 * * *
Important limitation: Cloudflare requires at least one * or , in the minute or hour field. This means you can't use 30 14 * * * (specific time, no wildcard). Instead use 30 14 * * * — wait, that actually works because of the * in other fields. The real rule: you need a * or , in the minute field specifically. So 30 14 * * * works, but you can't do something like "exactly 2:30 PM only on Mondays" without adding flexibility.

Use crontab.guru to validate your expressions.

Real-World Use Cases

1. Health Check Monitor

Monitor your services and get alerted if they go down:

// src/index.js
export default {
    async scheduled(event, env, ctx) {
        const services = [
            { name: "API", url: "https://api.example.com/health" },
            { name: "Web App", url: "https://app.example.com" },
            { name: "Database Proxy", url: "https://db.example.com/status" },
        ];

        const results = [];

        for (const service of services) {
            const start = Date.now();
            try {
                const res = await fetch(service.url, {
                    signal: AbortSignal.timeout(5000),
                });
                const elapsed = Date.now() - start;

                results.push({
                    name: service.name,
                    status: res.status === 200 ? "healthy" : "degraded",
                    response_time_ms: elapsed,
                    http_status: res.status,
                });

            } catch (err) {
                results.push({
                    name: service.name,
                    status: "down",
                    error: err.message,
                });
            }
        }

        // Store results in KV for dashboard display
        await env.HEALTH_KV.put(
            `check-${Date.now()}`,
            JSON.stringify(results)
        );

        // Send alert if any service is down
        const anyDown = results.some(r => r.status === "down");
        if (anyDown) {
            await sendAlert(env, results);
        }
    }
};

async function sendAlert(env, results) {
    // Send to Discord webhook
    const failed = results.filter(r => r.status === "down");
    const message = {
        content: `🚨 Service Alert:\n${failed.map(f => `• ${f.name}: ${f.error || f.status}`).join("\n")}`,
    };

    await fetch(env.DISCORD_WEBHOOK_URL, {
        method: "POST",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify(message),
    });
}

2. Data Sync Between APIs

Periodically sync data from one service to another:

export default {
    async scheduled(event, env, ctx) {
        console.log("Starting data sync...");

        // Fetch new records from source
        const source = await fetch(
            `${env.SOURCE_API_URL}/items?since=${env.LAST_SYNC_TS}`,
            { headers: { "Authorization": `Bearer ${env.SOURCE_API_KEY}` } }
        );
        const items = await source.json();

        // Transform and send to destination
        for (const item of items) {
            await fetch(env.DEST_API_URL, {
                method: "POST",
                headers: {
                    "Content-Type": "application/json",
                    "Authorization": `Bearer ${env.DEST_API_KEY}`,
                },
                body: JSON.stringify(transformItem(item)),
            });
        }

        // Update last sync timestamp
        await env.MY_KV.put("last_sync", Date.now().toString());
        console.log(`Synced ${items.length} items`);
    }
};

function transformItem(item) {
    return {
        id: item.uid,
        title: item.name,
        price: item.cost * 1.1, // Add 10% margin
        category: item.type.toLowerCase(),
    };
}

3. Automated Report Generator

Generate and email daily/weekly reports:

export default {
    async scheduled(event, env, ctx) {
        // Build report from stored data
        const cursor = await env.STATS_KV.list({ limit: 1000 });
        const data = cursor.keys.map(k => ({ key: k.name }));

        const report = {
            date: new Date().toISOString(),
            total_entries: data.length,
            summary: data.slice(0, 100), // First 100 entries
        };

        // Store report in R2 for long-term storage
        await env.MY_R2.put(`reports/${new Date().toISOString().split('T')[0]}.json`,
            JSON.stringify(report, null, 2)
        );

        console.log("Report generated and stored in R2");
    }
};

Using Python with Workers Cron

Workers run JavaScript/TypeScript, but you can orchestrate Python scripts via the API. Here's a pattern for triggering Python jobs from a Worker cron:

Python Script (runs on your server or via GitHub Actions)

# process_data.py
import requests
import json

def process_data():
    """Fetch data, process it, send results back."""
    # Fetch from Cloudflare KV via API
    headers = {
        "Authorization": f"Bearer {CF_API_TOKEN}",
        "Content-Type": "application/json",
    }

    # Process and store results
    response = requests.post(
        "https://api.cloudflare.com/client/v4/accounts/"
        f"{ACCOUNT_ID}/storage/kv/namespaces/{NAMESPACE_ID}",
        headers=headers,
        data={"key": "processed-result", "value": json.dumps({"status": "ok"})}
    )
    print(f"Stored result: {response.status_code}")

if __name__ == "__main__":
    process_data()

Worker Cron that triggers a webhook

// This cron calls your Python endpoint
export default {
    async scheduled(event, env, ctx) {
        try {
            const res = await fetch(env.PYTHON_WEBHOOK_URL, {
                method: "POST",
                headers: {
                    "Content-Type": "application/json",
                    "X-Trigger": "cloudflare-cron",
                },
                body: JSON.stringify({
                    timestamp: new Date().toISOString(),
                    schedule: event.cron,
                }),
            });

            if (!res.ok) {
                console.error(`Webhook failed: ${res.status} ${res.statusText}`);
            }
        } catch (err) {
            console.error("Webhook error:", err);
        }
    }
};

Bindings: What Data Can Your Cron Access?

Cron triggers have the same bindings as regular Workers — your scheduled code can access:

  • Workers KV — Key-value storage (free tier: 100K reads, 1K writes/day)
  • D1 Database — SQLite database (free tier: 5MB storage, 5M reads/day)
  • R2 Storage — Object storage (free tier: 10GB storage, 1M reads/month)
  • Secrets — Secure environment variables
  • Fetch API — Call any HTTP endpoint
  • Hyperdrive — Database connection pooling

Configure these in wrangler.toml:

# wrangler.toml
kv_namespaces = [
    { binding = "MY_KV", id = "abc123" },
    { binding = "HEALTH_KV", id = "def456" }
]

d1_databases = [
    { binding = "DB", database_name = "my-db", database_id = "xyz789" }
]

r2_buckets = [
    { binding = "MY_R2", bucket_name = "reports" }
]

[vars]
DISCORD_WEBHOOK_URL = "https://discord.com/api/webhooks/..."

# Secrets are set via CLI, never stored in wrangler.toml
# wrangler secret put SOURCE_API_KEY
# wrangler secret put DEST_API_KEY

Error Handling and Reliability

Cron jobs can fail. Here's how to handle it gracefully:

export default {
    async scheduled(event, env, ctx) {
        const runId = crypto.randomUUID();
        console.log(`Run ${runId} started`);

        try {
            // Check if a previous run is still in progress (avoid overlap)
            const lastRun = await env.MY_KV.get("last_run_id");
            if (lastRun) {
                console.log(`Previous run ${lastRun} may still be running, skipping`);
                // Optional: send alert about overlap
                return;
            }

            // Mark this run as started
            await env.MY_KV.put("last_run_id", runId, {
                expirationTtl: 600, // Expire after 10 minutes
            });

            // Your main logic
            await doTheWork(env);

            // Clean up
            await env.MY_KV.delete("last_run_id");
            console.log(`Run ${runId} completed successfully`);

        } catch (error) {
            console.error(`Run ${runId} failed:`, error);
            // Log the error for investigation
            await env.MY_KV.put(`error-${runId}`, JSON.stringify({
                error: error.message,
                timestamp: new Date().toISOString(),
                cron: event.cron,
            }));
            // Optionally retry or alert
        }
    }
};

Best Practices

  • Keep jobs short: Design cron tasks to complete within seconds, not minutes. Use queues for long-running work.
  • Idempotent design: A cron job might run twice (rare but possible). Design so double-runs don't cause data corruption.
  • Use ctx for deferred work: The ctx parameter lets you defer non-critical work (like sending notifications) that runs after the response:
  • Store state externally: Workers are stateless. Use KV, D1, or R2 to persist data between runs.
  • Set timeouts: Always use AbortSignal.timeout() when fetching external APIs to avoid hanging.
  • Monitor failures: Set up alerts for failed cron runs so you catch issues early.
  • Use UTC: All cron schedules use UTC. Plan accordingly and document the timezone.

Example using ctx for deferred work:

export default {
    async scheduled(event, env, ctx) {
        // Critical path — must complete within timeout
        const data = await fetchAndProcessData(env);

        // Defer non-critical work — runs after the scheduled event "completes"
        ctx.waitUntil(sendNotification(env, data));

        console.log("Cron completed, notification sending in background");
    }
};
