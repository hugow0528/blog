Dockerfile Best Practices: Write Smaller, Safer, Faster Container Images — Complete Beginner's Guide

July 18, 2026 10 min read

A Dockerfile is a text file with step-by-step instructions for building a Docker image. It's the bridge between your source code and a deployable container. But a poorly written Dockerfile produces bloated, slow, and insecure images. This guide covers the best practices that turn a basic Dockerfile into a production-ready build — smaller images, faster builds, and no security surprises.

The Anatomy of a Dockerfile

Every Dockerfile is a sequence of instructions. Here's a minimal example:

# Base image
FROM python:3.12-slim

# Working directory inside the container
WORKDIR /app

# Copy dependency file first (see caching section)
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Copy application code
COPY . .

# Run the app
CMD ["python", "app.py"]

Each line creates a layer in the image. Docker caches each layer, so understanding layer order is the key to fast builds. Let's learn each best practice.

1. Choose the Right Base Image

The base image determines your starting size, security surface, and available tools. Always prefer slim or alpine variants:

# Bad — full image with build tools, ~1GB
FROM python:3.12

# Good — slim, no build tools, ~150MB
FROM python:3.12-slim

# Also good — alpine, smallest, ~50MB
FROM python:3.12-alpine

Rule of thumb: Use -slim for most cases (fewer compatibility issues). Use -alpine when image size is critical and you don't need GNU-specific tools. Avoid the untagged image — it's the full installation.

Always pin your tag. Never use FROM python:latest — it changes silently and breaks builds:

# Bad — which version?
FROM python:latest

# Good — reproducible
FROM python:3.12.3-slim

# Even better — use specific digests for CI
FROM python@sha256:a1b2c3...

2. Leverage Layer Caching

Docker caches each layer. If a layer's inputs haven't changed, Docker skips it. The trick is to put the least frequently changed files first:

# Good order — requirements.txt rarely changes
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Then copy everything else — changes often
COPY . .

# BAD order — invalidates cache every time you change app.py
COPY . .
RUN pip install --no-cache-dir -r requirements.txt

When you change app.py but not requirements.txt, the first version reuses the cached pip install layer (instant), while the bad version reinstalls all dependencies every time.

3. Use .dockerignore

Just like .gitignore, a .dockerignore file prevents unnecessary files from entering the image context:

# .dockerignore
__pycache__/
*.pyc
.git/
.env
*.md
tests/
.dockerignore
venv/
node_modules/

Without this, every COPY . . sends your entire project directory to the Docker daemon — including node_modules/, virtual environments, and local dotfiles. This bloats the build context and can accidentally leak secrets.

4. Combine RUN Commands

Each RUN creates a new layer. Combine related commands to reduce layers and clean up in the same layer:

# Bad — 4 layers, leftover build artifacts persist
RUN apt-get update
RUN apt-get install -y curl
RUN curl -sS https://setup.example.com | bash
RUN rm -rf /var/lib/apt/lists/*

# Good — 1 layer, cleaned up before the layer is committed
RUN apt-get update && \
    apt-get install -y --no-install-recommends curl && \
    curl -sS https://setup.example.com | bash && \
    apt-get purge -y curl && \
    rm -rf /var/lib/apt/lists/*

Key tips: use --no-install-recommends to skip unnecessary packages, and clean the apt cache in the same RUN command so the cached packages don't persist in the final layer.

5. Never Run as Root

Running containers as root is a security risk. If someone escapes the container, they have full system access. Create a non-root user:

# Create a non-root user
RUN useradd --create-home appuser

# Switch to that user
USER appuser

# Make sure they can access their files
WORKDIR /home/appuser/app
COPY --chown=appuser:appuser . .

# Now run the app as the non-root user
CMD ["python", "app.py"]

The --chown flag ensures the non-root user owns the copied files. Without it, the app might not be able to write to its own directory.

6. Use HEALTHCHECK

A HEALTHCHECK tells Docker how to verify your container is actually working:

# HTTP health check for web servers
HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
    CMD curl -f http://localhost:8080/health || exit 1

This runs every 30 seconds. If it fails 3 times in a row, Docker marks the container as unhealthy. Orchestrators like Kubernetes use this to restart broken containers automatically.

# Python app — check with a simple script
COPY healthcheck.py .
HEALTHCHECK --interval=30s --timeout=5s --retries=3 \
    CMD ["python", "healthcheck.py"]
# healthcheck.py
import urllib.request
import sys

try:
    response = urllib.request.urlopen("http://localhost:8080/health", timeout=5)
    if response.status == 200:
        sys.exit(0)
    sys.exit(1)
except Exception:
    sys.exit(1)

7. Use COPY --from for Multi-Stage Builds

Multi-stage builds let you use one image for building and a separate, minimal image for running:

# Stage 1: Build
FROM python:3.12-slim AS builder
WORKDIR /build
COPY requirements.txt .
RUN pip install --user --no-cache-dir -r requirements.txt

# Stage 2: Run
FROM python:3.12-slim
WORKDIR /app
COPY --from=builder /root/.local /root/.local
COPY . .
ENV PATH=/root/.local/bin:$PATH
CMD ["python", "app.py"]

The final image contains only your code and the installed packages — no build tools, no package manager cache, no intermediate files. Result: images that are 70-90% smaller than single-stage builds.

8. Use ARG vs ENV Wisely

ARG is for build-time variables (not stored in the final image). ENV is for runtime variables (stored in the image metadata).

# Build-time — not visible in the final image
ARG BUILD_ENV=production
RUN echo "Building for $BUILD_ENV"

# Runtime — visible in the final image and containers
ENV APP_PORT=8080
ENV LOG_LEVEL=info

Never use ARG for secrets. Args appear in the image history. Use build secrets with docker build --secret or Docker BuildKit's RUN --mount=type=secret for production.

Production-Ready Template

Here's a complete Dockerfile combining all best practices:

# syntax=docker/dockerfile:1

# ── Stage 1: Build ──
FROM python:3.12-slim AS builder

WORKDIR /build
COPY requirements.txt .
RUN pip install --user --no-cache-dir -r requirements.txt

# ── Stage 2: Runtime ──
FROM python:3.12-slim

# Labels for tracking
LABEL maintainer="hugo@example.com" \
      version="1.0.0"

# Create non-root user
RUN useradd --create-home appuser

# Copy built dependencies
COPY --from=builder /root/.local /home/appuser/.local

# Set environment
ENV PATH=/home/appuser/.local/bin:$PATH \
    PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1

# Copy app code
WORKDIR /home/appuser/app
COPY --chown=appuser:appuser . .

# Switch to non-root user
USER appuser

# Health check
HEALTHCHECK --interval=30s --timeout=5s --start-period=15s --retries=3 \
    CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:8080/health')" || exit 1

# Expose port
EXPOSE 8080

# Run
CMD ["python", "app.py"]

Quick Checklist

  • ✅ Use -slim or -alpine base images
  • ✅ Pin base image versions (no latest)
  • ✅ Copy dependency files before application code
  • ✅ Use .dockerignore to exclude unnecessary files
  • ✅ Combine RUN commands to minimize layers
  • ✅ Clean up package manager cache in the same RUN
  • ✅ Use --no-cache-dir with pip
  • ✅ Run as a non-root user
  • ✅ Add a HEALTHCHECK
  • ✅ Use multi-stage builds for final image size
  • ✅ Use ARG for build-time, ENV for runtime
  • ✅ Never store secrets in Dockerfiles

Summary

A well-written Dockerfile isn't just about getting the container to run — it's about build speed, image size, security, and reliability. Start with the right base image, order your layers for caching, run as non-root, and add health checks. The template above gives you a production-ready starting point. Tweak it for your language and stack, and your containers will be lean, fast, and secure.
