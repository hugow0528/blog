Python Error Handling: try/except, Custom Exceptions & Best Practices

June 22, 2026 · 10 min read

Every Python program encounters errors. A file that doesn't exist, a network request that times out, a JSON string that's malformed — if you don't handle these gracefully, your program crashes with a confusing traceback. Error handling is what separates toy scripts from production-quality code.

In this guide, we'll cover everything from the basics of try/except to custom exception classes and real-world patterns you'll use every day.

Why Error Handling Matters

Without error handling, your program stops dead at the first unexpected problem:

# This will CRASH if the file doesn't exist
data = open("config.txt").read()
print(data)

With error handling, your program recovers or tells the user what went wrong:

try:
    data = open("config.txt").read()
    print(data)
except FileNotFoundError:
    print("⚠️ config.txt not found. Using defaults...")
    data = "default_config"
Golden rule: Don't ignore errors — handle them. A bare except: pass hides bugs and makes debugging a nightmare. Always catch what you expect and handle it meaningfully.

The try/except Statement

The basic structure of error handling in Python:

try:
    # Code that might fail
    result = 10 / 0
except ZeroDivisionError as e:
    # What to do when it fails
    print(f"Error: {e}")
    result = 0  # fallback value

Here's what happens step by step:

  1. Python executes the try block
  2. If 10 / 0 raises a ZeroDivisionError, Python jumps to the matching except block
  3. The as e captures the exception object so you can read the error message
  4. After the except block runs, execution continues normally

Catching Multiple Exception Types

You can catch different errors with different responses:

import json

user_input = input("Enter JSON data: ")

try:
    data = json.loads(user_input)
    name = data["name"]
    print(f"Hello, {name}!")
except json.JSONDecodeError:
    print("❌ That's not valid JSON. Try: {\"name\": \"Hugo\"}")
except KeyError:
    print("❌ Missing 'name' field in the JSON.")
except Exception as e:
    # Catch-all for anything else
    print(f"❌ Unexpected error: {e}")

Order matters — Python checks except blocks top to bottom. Put specific exceptions first, general ones last.

else and finally Clauses

The full try statement has four optional blocks:

try:
    # Code that might raise an exception
    connection = open_database()
    result = connection.query("SELECT * FROM users")
except ConnectionError:
    # Runs ONLY if an exception occurs
    print("❌ Can't connect to the database!")
    result = []
else:
    # Runs ONLY if NO exception occurred
    print(f"✅ Found {len(result)} users")
finally:
    # Runs ALWAYS, whether or not an exception occurred
    connection.close()
    print("🔒 Database connection closed")

When to use else

Use else for code that should only run if the try block succeeded. This keeps your try block focused and makes it clear what can fail.

When to use finally

Use finally for cleanup code that must run — closing files, releasing locks, closing database connections. It runs even if you return or raise from inside the try or except blocks.

The with Statement (Context Manager)

For file handling, the with statement is cleaner than try/finally:

# ❌ Manual cleanup (error-prone)
f = open("data.txt")
try:
    content = f.read()
finally:
    f.close()

# ✅ Context manager (automatic cleanup)
with open("data.txt") as f:
    content = f.read()
# File is automatically closed here, even if an error occurred!

The with statement calls __enter__ when entering the block and __exit__ when leaving — guaranteeing cleanup.

Raising Exceptions

Sometimes you need to signal that something went wrong. Use raise:

def set_age(age):
    if not isinstance(age, int):
        raise TypeError(f"Age must be an integer, got {type(age).__name__}")
    if age < 0 or age > 150:
        raise ValueError(f"Age must be 0-150, got {age}")
    return age

# Using it:
try:
    set_age("thirty")
except (TypeError, ValueError) as e:
    print(f"Invalid input: {e}")
    # Output: Invalid input: Age must be an integer, got str

Re-raising with Additional Context

Caught an error but want to add more information before passing it up?

def load_config(path):
    try:
        with open(path) as f:
            return json.load(f)
    except FileNotFoundError:
        # Re-raise with more context
        raise RuntimeError(
            f"Configuration file not found at '{path}'. "
            "Have you run 'setup.sh' yet?"
        ) from None  # from None hides the original traceback

Custom Exception Classes

When your application has domain-specific errors, create custom exceptions:

# exceptions.py — Define your exception hierarchy
class AppError(Exception):
    """Base exception for our application"""
    pass

class ValidationError(AppError):
    """Raised when input validation fails"""
    def __init__(self, field, value, reason):
        self.field = field
        self.value = value
        self.reason = reason
        super().__init__(f"Invalid {field}: {value} — {reason}")

class DatabaseError(AppError):
    """Raised when a database operation fails"""
    def __init__(self, query, original_error):
        self.query = query
        self.original_error = original_error
        super().__init__(f"Query failed: {query} | Cause: {original_error}")

class NotFoundError(AppError):
    """Raised when a requested resource doesn't exist"""
    def __init__(self, resource, resource_id):
        self.resource = resource
        self.resource_id = resource_id
        super().__init__(f"{resource} with id {resource_id} not found")

Now use them throughout your code:

# Using custom exceptions
def validate_user(name, email):
    errors = []
    
    if not name or len(name) < 2:
        errors.append(ValidationError("name", name, "must be at least 2 characters"))
    
    if "@" not in email:
        errors.append(ValidationError("email", email, "must contain '@'"))
    
    if errors:
        # Raise the first validation error
        raise errors[0]
    
    return {"name": name, "email": email}

# Calling code catches them cleanly
try:
    user = validate_user("", "invalid-email")
except ValidationError as e:
    print(f"Form error on '{e.field}': {e.reason}")
    # Output: Form error on 'name': must be at least 2 characters

Real-World Project: Robust API Client

Let's build a practical example — a weather API client that handles every error gracefully:

import requests
import time

class WeatherError(Exception):
    """Base exception for weather API operations"""
    pass

class WeatherConnectionError(WeatherError):
    pass

class WeatherNotFoundError(WeatherError):
    pass

class WeatherRateLimitError(WeatherError):
    pass

class WeatherClient:
    def __init__(self, api_key, retries=3, timeout=10):
        self.api_key = api_key
        self.base_url = "https://api.openweathermap.org/data/2.5"
        self.retries = retries
        self.timeout = timeout
    
    def get_weather(self, city):
        """Fetch weather for a city with robust error handling"""
        for attempt in range(1, self.retries + 1):
            try:
                response = requests.get(
                    f"{self.base_url}/weather",
                    params={"q": city, "appid": self.api_key, "units": "metric"},
                    timeout=self.timeout
                )
                response.raise_for_status()
                data = response.json()
                
                return {
                    "city": data["name"],
                    "temp_c": data["main"]["temp"],
                    "humidity": data["main"]["humidity"],
                    "description": data["weather"][0]["description"],
                    "wind_kmh": data["wind"]["speed"] * 3.6
                }
                
            except requests.exceptions.ConnectionError:
                if attempt < self.retries:
                    wait = 2 ** attempt  # Exponential backoff: 2s, 4s, 8s
                    print(f"⚠️ Connection failed (attempt {attempt}/{self.retries}). "
                          f"Retrying in {wait}s...")
                    time.sleep(wait)
                else:
                    raise WeatherConnectionError(
                        f"Cannot reach weather API after {self.retries} attempts"
                    )
            
            except requests.exceptions.Timeout:
                if attempt < self.retries:
                    print(f"⏱️ Request timed out (attempt {attempt}/{self.retries}). Retrying...")
                    time.sleep(1)
                else:
                    raise WeatherConnectionError("Weather API requests keep timing out")
            
            except requests.exceptions.HTTPError as e:
                if response.status_code == 404:
                    raise WeatherNotFoundError(f"City not found: '{city}'. Check the spelling.")
                elif response.status_code == 429:
                    raise WeatherRateLimitError("API rate limit reached. Try again in a minute.")
                elif response.status_code == 401:
                    raise WeatherError("Invalid API key. Check your configuration.")
                else:
                    raise WeatherError(f"HTTP {response.status_code}: {e}")
            
            except KeyError as e:
                raise WeatherError(f"Unexpected API response format. Missing key: {e}")
        
        # Should never reach here, but just in case
        raise WeatherConnectionError("Failed to fetch weather data")


# Usage example
client = WeatherClient(api_key="your_api_key_here")

try:
    weather = client.get_weather("Tokyo")
    print(f"\n🌤️  {weather['city']}")
    print(f"   Temp: {weather['temp_c']}°C")
    print(f"   Humidity: {weather['humidity']}%")
    print(f"   Conditions: {weather['description']}")
    print(f"   Wind: {weather['wind_kmh']} km/h")
    
except WeatherNotFoundError as e:
    print(f"🔍 {e}")
except WeatherRateLimitError as e:
    print(f"🐌 {e}")
except WeatherConnectionError as e:
    print(f"🌐 {e}")
except WeatherError as e:
    print(f"❌ {e}")

Common Mistakes to Avoid

❌ Bare except

# BAD: Catches EVERYTHING including KeyboardInterrupt and SystemExit
try:
    do_something()
except:
    pass  # Silently hides all bugs!
# GOOD: Catch only what you expect
try:
    do_something()
except (FileNotFoundError, PermissionError):
    handle_file_error()
except Exception as e:
    # Log unexpected errors, don't ignore them
    print(f"Unexpected error: {e}")

❌ Too broad a try block

# BAD: Can't tell which line failed
try:
    user = get_user()
    db = connect_database()
    db.save(user)
except Exception:
    print("Something went wrong")  # Which line?!
# GOOD: Narrow try blocks
try:
    user = get_user()
except UserError:
    print("Invalid user data")

try:
    db = connect_database()
except ConnectionError:
    print("Database unavailable")

try:
    db.save(user)
except SaveError:
    print("Failed to save user")

❌ Catching and ignoring

# BAD: What if there's a critical error?
try:
    process_payment()
except Exception:
    pass  # Payment failed and you don't even know!
# GOOD: At least log it, or re-raise
try:
    process_payment()
except PaymentError as e:
    log_error(f"Payment processing failed: {e}")
    notify_admin(e)
    raise  # Don't hide the error

Summary: Error Handling Checklist

  • ✅ Catch specific exceptions, not bare except
  • ✅ Keep try blocks narrow — only wrap what can fail
  • ✅ Use else for code that depends on success
  • ✅ Use finally (or with) for cleanup
  • ✅ Create custom exceptions for domain-specific errors
  • ✅ Never silently ignore exceptions — log or re-raise
  • ✅ Implement retries with exponential backoff for network calls
  • ✅ Provide meaningful error messages to users
Final tip: Treat error handling like feature development. Write your except blocks with the same care as your main logic. A program that handles errors gracefully is a program users can trust.
