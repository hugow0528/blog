Python Packaging & Publishing: Share Your Code on PyPI

July 5, 2026 · 10 min read

You've written a Python module that's too useful to keep private. Maybe it's a set of utility functions, a library wrapper, or a tool you've refined over months. Now it's time to package it and publish it to PyPI — Python's official package index — so anyone can install it with pip install.

This guide walks you through the entire process: structuring your project, writing pyproject.toml, building a wheel, and publishing to PyPI. No outdated setup.py boilerplate — we'll use modern standards.

Project Structure

Start with this directory layout. Every field has a purpose:

my_package/
├── pyproject.toml          # Package configuration (modern standard)
├── README.md               # Describes your package
├── LICENSE                 # Choose one: MIT, Apache 2.0, GPL, etc.
├── src/
│   └── my_package/         # Your actual Python code
│       ├── __init__.py     # Makes it a package, exports public API
│       ├── core.py         # Main functionality
│       └── utils.py        # Helper functions
├── tests/                  # Unit tests
│   ├── __init__.py
│   └── test_core.py
└── .gitignore              # Ignore build artifacts

Notice the src/ layout? This is the recommended structure because it prevents accidental imports during development. When you work in the project root, Python won't import your package directly — you must install it in development mode first, which catches packaging issues early.

Writing pyproject.toml

Modern Python packaging uses pyproject.toml instead of the old setup.py. This single file declares your package name, version, dependencies, and build system. Create it in the project root:

[build-system]
requires = ["setuptools>=68.0", "wheel"]
build-backend = "setuptools.build_meta"

[project]
name = "my-awesome-package"
version = "0.1.0"
description = "A utility package that makes your life easier"
readme = "README.md"
license = {text = "MIT"}
requires-python = ">=3.9"
authors = [
    {name = "Your Name", email = "you@example.com"}
]
keywords = ["python", "utilities", "automation"]
classifiers = [
    "Programming Language :: Python :: 3",
    "Programming Language :: Python :: 3.9",
    "Programming Language :: Python :: 3.10",
    "Programming Language :: Python :: 3.11",
    "Programming Language :: Python :: 3.12",
    "License :: OSI Approved :: MIT License",
    "Operating System :: OS Independent",
]

# Runtime dependencies
dependencies = [
    "requests>=2.28.0",
    "pydantic>=2.0",
]

# Optional dependencies (extras)
[project.optional-dependencies]
dev = [
    "pytest>=7.0",
    "pytest-cov>=4.0",
    "black>=23.0",
    "ruff>=0.1.0",
]
docs = [
    "sphinx>=7.0",
]

[project.urls]
Homepage = "https://github.com/yourname/my-awesome-package"
Documentation = "https://my-package.readthedocs.io"
"Bug Tracker" = "https://github.com/yourname/my-awesome-package/issues"

[project.scripts]
# CLI entry point: `mytool` command after pip install
mytool = "my_package.core:main"

[tool.setuptools.packages.find]
where = ["src"]

[tool.pytest.ini_options]
testpaths = ["tests"]

Let me explain the key sections:

  • [build-system]: Tells pip which tools to use for building. Setuptools and wheel are the standard choice for most packages.
  • [project]: The core metadata — name, version, description, authors, supported Python versions.
  • dependencies: Packages required at runtime. Anyone who pip install your package automatically gets these.
  • optional-dependencies: Extra packages for specific use cases. Users install them with pip install my-awesome-package[dev].
  • [project.scripts]: Optional CLI command. After installation, users type mytool and it runs main() from my_package/core.py.
  • [tool.setuptools.packages.find]: Tells setuptools where to find your Python modules (under src/).

Your Package Code

Let's create a simple but real package. Here's the __init__.py that exposes your public API:

# src/my_package/__init__.py
"""my-awesome-package: A utility toolkit for everyday Python tasks."""

__version__ = "0.1.0"

from my_package.core import fetch_data, process_data
from my_package.utils import slugify, truncate

__all__ = ["fetch_data", "process_data", "slugify", "truncate"]

And here's core.py with actual functionality:

# src/my_package/core.py
"""Core functionality for my-awesome-package."""

import requests
from typing import Any, Dict, Optional


def fetch_data(url: str, timeout: int = 10) -> Dict[str, Any]:
    """Fetch JSON data from a URL with error handling.

    Args:
        url: The URL to fetch data from.
        timeout: Request timeout in seconds.

    Returns:
        Parsed JSON response as a dictionary.

    Raises:
        requests.RequestException: If the request fails.

    Example:
        >>> data = fetch_data("https://api.github.com")
        >>> print(data["message"])
        'Hello, World!'
    """
    response = requests.get(url, timeout=timeout)
    response.raise_for_status()  # Raise exception for 4xx/5xx
    return response.json()


def process_data(data: Dict[str, Any], 
                 key: Optional[str] = None) -> Any:
    """Process fetched data, optionally extracting a specific key.

    Args:
        data: The dictionary to process.
        key: Optional key to extract. Returns the whole dict if None.

    Returns:
        The value for the given key, or the entire dict.

    Example:
        >>> data = {"name": "Alice", "age": 30}
        >>> process_data(data, key="name")
        'Alice'
    """
    if key is not None:
        return data.get(key)
    return data


def main() -> None:
    """CLI entry point for mytool."""
    import sys
    if len(sys.argv) < 2:
        print("Usage: mytool ")
        print("Fetch and display JSON data from a URL.")
        sys.exit(1)
    
    url = sys.argv[1]
    try:
        data = fetch_data(url)
        print(f"Fetched from: {url}")
        for k, v in data.items():
            print(f"  {k}: {v}")
    except requests.RequestException as e:
        print(f"Error: {e}", file=sys.stderr)
        sys.exit(1)

And utils.py for helper functions:

# src/my_package/utils.py
"""Utility functions for my-awesome-package."""

import re
from typing import Union


def slugify(text: str) -> str:
    """Convert a string to a URL-friendly slug.

    Example:
        >>> slugify("Hello World!")
        'hello-world'
    """
    text = text.lower().strip()
    text = re.sub(r'[^\w\s-]', '', text)
    text = re.sub(r'[\s_-]+', '-', text)
    return text.strip('-')


def truncate(text: str, max_length: int = 100, 
             suffix: str = "...") -> str:
    """Truncate text to a maximum length.

    Example:
        >>> truncate("Hello World!", max_length=8)
        'Hello...  '
    """
    if len(text) <= max_length:
        return text
    return (text[:max_length - len(suffix)] + suffix).ljust(max_length)

Install in Development Mode

Before publishing, install your package locally in "editable" mode. This lets you make changes and test without reinstalling:

# From the project root directory
pip install -e ".[dev]"

The -e flag (editable) creates a symlink so changes to your source code take effect immediately. The [dev] installs the optional development dependencies (pytest, black, ruff).

Verify it works:

$ python
>>> import my_package
>>> my_package.slugify("Hello World!")
'hello-world'
>>> my_package.__version__
'0.1.0'

Write Tests

Don't skip this step. PyPI is a public platform — your package represents you. Write at least basic tests:

# tests/test_core.py
import pytest
from my_package.core import process_data
from my_package.utils import slugify, truncate


class TestSlugify:
    def test_basic_slug(self):
        assert slugify("Hello World!") == "hello-world"

    def test_already_slug(self):
        assert slugify("hello-world") == "hello-world"

    def test_special_characters(self):
        assert slugify("What's Up?") == "whats-up"


class TestTruncate:
    def test_no_truncation_needed(self):
        assert truncate("Hi", max_length=10) == "Hi"

    def test_truncation(self):
        result = truncate("Hello World!", max_length=10)
        assert len(result) == 10
        assert "..." in result


class TestProcessData:
    def test_extract_key(self):
        data = {"name": "Alice", "age": 30}
        assert process_data(data, key="name") == "Alice"

    def test_no_key_returns_all(self):
        data = {"x": 1}
        assert process_data(data) == data

Build Your Package

Python packages are distributed as two formats:

  • Source distribution (sdist): A tarball with your raw source code. Recompiles on the user's machine.
  • Wheel (.whl): A pre-built, binary-compatible package. Installs instantly — the format everyone prefers.

Build both:

# Install build tool
pip install build

# Build the package
python -m build

This creates a dist/ directory:

dist/
├── my_awesome_package-0.1.0-py3-none-any.whl    # Wheel
└── my_awesome_package-0.1.0.tar.gz              # Source dist

Publish to TestPyPI

Before going live, publish to TestPyPI — PyPI's testing ground. It uses the same process but won't affect real users.

  1. Create a TestPyPI account at test.pypi.org
  2. Get an API token from your account settings
  3. Install twine (the publishing tool): pip install twine
# Upload to TestPyPI
twine upload --repository testpypi dist/*
--username __token__
--password pypi-XXXXXXXXXXXXXXXX

Test the installation from a clean virtual environment:

python -m venv test_env
source test_env/bin/activate
pip install --index-url https://test.pypi.org/simple/ my-awesome-package
python -c "import my_package; print(my_package.slugify('Test!'))"
# Output: test

Publish to PyPI

When you're confident, publish for real:

  1. Create a PyPI account at pypi.org
  2. Get an API token from your account settings (under "Add API token")
  3. Upload:
# Upload to real PyPI
twine upload dist/*
--username __token__
--password pypi-XXXXXXXXXXXXXXXX

Within seconds, anyone can install your package:

pip install my-awesome-package

Bump the Version and Republish

Every new release needs a unique version number. Follow Semantic Versioning:

  • MAJOR (1.0.0 → 2.0.0): Breaking changes
  • MINOR (0.1.0 → 0.2.0): New features, backward compatible
  • PATCH (0.1.0 → 0.1.1): Bug fixes only
# Update version in pyproject.toml
version = "0.2.0"

# Also update __init__.py
__version__ = "0.2.0"

# Build and upload
python -m build
twine upload dist/*
--username __token__
--password pypi-XXXXXXXXXXXXXXXX

Automation with GitHub Actions

Stop publishing manually. Here's a GitHub Actions workflow that builds and publishes whenever you create a Git tag:

# .github/workflows/publish.yml
name: Publish to PyPI

on:
  push:
    tags:
      - 'v*'  # Trigger on tags like v0.1.0

jobs:
  publish:
    runs-on: ubuntu-latest
    permissions:
      id-token: write  # Needed for trusted publishing

    steps:
      - uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.12"

      - name: Install build
        run: pip install build

      - name: Build package
        run: python -m build

      - name: Publish to PyPI
        uses: pypa/gh-action-pypi-publish@release/v1

Now publishing is as simple as:

# Update version numbers
# Commit changes
git commit -am "Bump to 0.2.0"

# Tag and push
git tag v0.2.0
git push origin main --tags

Common Pitfalls to Avoid

1. Duplicate Upload Error

PyPI won't let you upload the same version twice. If you mess up, you must increment the version. There's no delete — well, PyPI has a withdrawal feature, but it's manual and slow. Always test on TestPyPI first.

2. Forgetting __init__.py

Without it, Python won't recognize your directory as a package. Even an empty __init__.py file works, but it's better to use it for clean imports as shown above.

3. Wrong requires-python

If your code uses match/case (Python 3.10+) or walrus operator (Python 3.8+), update requires-python accordingly. Users on older versions will see cryptic errors.

4. Missing py.typed for Type Hints

If you use type hints and want users to get IDE autocomplete, add an empty file:

# src/my_package/py.typed
# This file tells tools that your package supports type checking

Summary

Python packaging doesn't have to be painful. With pyproject.toml, build, and twine, you can go from code to published package in under an hour:

  1. Structure your project with the src/ layout
  2. Write a pyproject.toml with metadata and dependencies
  3. Add tests and run them
  4. Build with python -m build
  5. Test on TestPyPI first
  6. Publish to PyPI with twine
  7. Automate with GitHub Actions

Your first published package is a milestone. It means someone, somewhere, will find your code useful. Ship it.
