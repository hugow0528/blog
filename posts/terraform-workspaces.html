Terraform Workspaces & State Strategies: Manage Multiple Environments

2026-06-27 11 min read

Stop duplicating Terraform code for every environment. Learn how to use Terraform workspaces and smart state management strategies to handle dev, staging, and production from a single, maintainable codebase.

Why You Need Workspaces

Early on, every Terraform user hits the same problem: you have identical infrastructure that needs to exist in three places — development, staging, and production. The naive approach is to copy-paste your main.tf three times into separate folders. This quickly becomes a maintenance nightmare.

Terraform workspaces solve this by letting you maintain one codebase while creating separate state files for each environment. Think of workspaces as parallel universes for your infrastructure — same code, different reality.

Workspace Basics

Every Terraform project starts with a default workspace. Let's create and switch between environments:

# List current workspaces
$ terraform workspace list
  default

# Create a dev workspace
$ terraform workspace new dev
Created and switched to workspace "dev"!

# List again — notice the * marking the active workspace
$ terraform workspace list
  default
* dev

# Create staging too
$ terraform workspace new staging
Created and switched to workspace "staging"!

# Switch back to dev
$ terraform workspace select dev
Switched to workspace "dev".

Using Workspace Name in Configuration

The power of workspaces comes from referencing the workspace name inside your Terraform code. Use the terraform.workspace built-in variable to conditionally change resources:

resource "aws_instance" "web" {
  ami           = var.ami_id
  instance_type = terraform.workspace == "production" ? "t3.large" : "t3.micro"

  tags = {
    Name        = "web-${terraform.workspace}"
    Environment = terraform.workspace
    ManagedBy   = "terraform"
  }
}

resource "aws_db_instance" "main" {
  identifier     = "myapp-${terraform.workspace}"
  engine         = "mysql"
  instance_class = terraform.workspace == "production" ? "db.r5.large" : "db.t3.micro"

  # Production gets a larger allocated storage
  allocated_storage = terraform.workspace == "production" ? 100 : 20

  tags = {
    Environment = terraform.workspace
  }
}

Now a single codebase provisions t3.micro instances in dev/staging and t3.large in production. The database follows the same pattern. One terraform apply command behaves differently depending on your active workspace.

Workspace Variables in a Separate File

For more complex differences, use variable files named after each workspace. Terraform automatically loads terraform.tfvars and <workspace>.auto.tfvars:

# dev.auto.tfvars
instance_count = 1
environment    = "dev"
db_password    = "dev-password-not-secure"
enable_monitoring = false

# staging.auto.tfvars
instance_count = 2
environment    = "staging"
db_password    = "staging-password"
enable_monitoring = true

# production.auto.tfvars
instance_count = 4
environment    = "production"
db_password    = "PRODUCTION-PASSWORD-GOES-TO-VAULT"
enable_monitoring = true

Terraform reads the auto-named file based on your active workspace — no manual switching needed. When you run terraform workspace select production, Terraform automatically picks up production.auto.tfvars.

State File Separation

Each workspace maintains its own state. With local backend, Terraform stores these under terraform.tfstate.d/<workspace>/:

project/
├── main.tf
├── variables.tf
├── dev.auto.tfvars
├── staging.auto.tfvars
├── production.auto.tfvars
├── terraform.tfstate          ← default workspace state
└── terraform.tfstate.d/
    ├── dev/
    │   └── terraform.tfstate  ← dev workspace state
    ├── staging/
    │   └── terraform.tfstate  ← staging workspace state
    └── production/
        └── terraform.tfstate  ← production workspace state

Remote State with Workspaces

In a team setting, use a remote backend. S3 automatically isolates workspace state using prefixes:

terraform {
  backend "s3" {
    bucket         = "my-terraform-state"
    key            = "infrastructure/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "terraform-locks"
    encrypt        = true
  }
}

The resulting S3 structure looks like:

s3://my-terraform-state/
├── infrastructure/terraform.tfstate          ← default
└── env/
    ├── dev/
    │   └── terraform.tfstate
    ├── staging/
    │   └── terraform.tfstate
    └── production/
        └── terraform.tfstate

Workspace vs Directory Structure

Two teams, two philosophies. Here's the trade-off:

Option A: Workspaces (single directory)

infrastructure/
├── main.tf              ← shared config
├── dev.auto.tfvars      ← dev overrides
├── production.auto.tfvars ← production overrides
└── terraform.tfstate.d/  ← separate states

Pros: Single source of truth, easy to keep environments in sync, less duplication.
Cons: Harder to restrict access per environment, workspace switching is a manual step.

Option B: Directory Structure (separate folders)

infrastructure/
├── modules/
│   └── vpc/             ← shared modules
├── dev/
│   ├── main.tf
│   └── variables.tf
├── staging/
│   ├── main.tf
│   └── variables.tf
└── production/
    ├── main.tf
    └── variables.tf

Pros: Clear separation, easy to apply different permissions, works naturally with CI/CD.
Cons: Code duplication unless heavily modularized, harder to ensure environments match.

My recommendation: Use workspaces for small teams and simple infrastructure. Use directory structure for teams that need fine-grained access control or when environments diverge significantly.

Complete Working Example

Here's a full, working configuration you can adapt:

# main.tf
terraform {
  required_version = ">= 1.5"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
  backend "s3" {
    bucket         = "my-terraform-state"
    key            = "webapp/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "terraform-locks"
    encrypt        = true
  }
}

provider "aws" {
  region = var.aws_region
}

variable "aws_region" {
  default = "us-east-1"
}

variable "instance_count" {
  default = 1
}

variable "environment" {
  default = "dev"
}

# Auto-scaling group with workspace-aware sizing
resource "aws_autoscaling_group" "web" {
  name                = "web-${terraform.workspace}"
  desired_capacity    = var.instance_count
  min_size            = terraform.workspace == "production" ? 2 : 1
  max_size            = terraform.workspace == "production" ? 10 : 3

  launch_template {
    id      = aws_launch_template.web.id
    version = "$Latest"
  }

  vpc_zone_identifier = aws_subnet.private[*].id

  tag {
    key                 = "Environment"
    value               = terraform.workspace
    propagate_at_launch = true
  }
}

resource "aws_launch_template" "web" {
  name_prefix   = "web-"
  image_id      = var.ami_id
  instance_type = terraform.workspace == "production" ? "t3.large" : "t3.micro"

  tag_specifications {
    resource_type = "instance"
    tags = {
      Environment = terraform.workspace
    }
  }
}

Workspace Gotchas

Here are the traps that catch everyone:

1. Forgetting Which Workspace You're On

Always check your workspace before running apply. Accidentally applying production config to dev (or vice versa) is the most common mistake.

# Add this to your prompt or alias:
alias tf="terraform workspace show && terraform"

2. Workspace Name in Resource Names

Always include terraform.workspace in resource identifiers (names, labels, identifiers). Two workspaces with the same config will collide otherwise.

3. Shared Resources Between Environments

If dev needs to access production's DNS zone, you'll need Terraform's data sources for remote state. Workspaces don't share state automatically — each workspace is completely isolated.

# Read another workspace's state
data "terraform_remote_state" "production" {
  backend = "s3"
  config = {
    bucket = "my-terraform-state"
    key    = "networking/terraform.tfstate"
    region = "us-east-1"
  }
}

resource "aws_route53_record" "dev_endpoint" {
  zone_id = data.terraform_remote_state.production.outputs.dns_zone_id
  name    = "dev.example.com"
  type    = "A"
  ttl     = 300
  records = [aws_instance.dev.public_ip]
}

CI/CD Integration

Integrate workspaces into your pipeline by selecting the workspace at the start of each job:

# GitHub Actions example
name: Terraform Deploy
on:
  push:
    branches: [main]

jobs:
  deploy-dev:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init
      - run: terraform workspace select dev || terraform workspace new dev
      - run: terraform plan -out=dev.tfplan
      - run: terraform apply dev.tfplan

  deploy-production:
    needs: deploy-dev
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init
      - run: terraform workspace select production || terraform workspace new production
      - run: terraform plan -out=prod.tfplan
      - run: terraform apply -auto-approve prod.tfplan

Best Practices Summary

  • Name workspaces consistently: dev, staging, production — no surprises.
  • Always include workspace in resource names: prevents naming collisions.
  • Use auto.tfvars per workspace: Terraform picks them up automatically.
  • Use remote state with locking: S3 + DynamoDB is the gold standard.
  • Never use the default workspace in production: always be explicit.
  • Document workspace setup: new team members should know how to get started.
