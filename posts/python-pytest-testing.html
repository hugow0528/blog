Python Testing with pytest: Fixtures, Parametrization & Coverage — Complete Beginner's Guide

July 14, 2026

You've written a Python function that works — you tested it manually, maybe pasted values into a REPL, and it returned the right answer. Great. Now you refactor something three weeks later, accidentally break that function, and don't notice until your customer emails you. Tests prevent this.

pytest is the most popular testing framework in the Python ecosystem. It's simpler than Python's built-in unittest, doesn't require boilerplate classes, and discovers tests automatically. A pytest test is just a regular Python function with an assert statement. That's it.

In this guide, you'll learn pytest from scratch — writing your first test, organizing test files, using fixtures for setup, parametrizing tests with multiple inputs, mocking external dependencies, running with coverage, and building a complete test suite for a real project.

Why pytest Over unittest?

Python includes unittest in the standard library. It works, but pytest is more productive:

# unittest — verbose
import unittest

class TestAdd(unittest.TestCase):
    def test_add(self):
        self.assertEqual(add(2, 3), 5)

    def test_add_negative(self):
        self.assertEqual(add(-1, -1), -2)

# pytest — simple
def test_add():
    assert add(2, 3) == 5

def test_add_negative():
    assert add(-1, -1) == -2

No classes, no self, no importing unittest. pytest finds any function starting with test_ and runs it. The assert statement gives you detailed failure messages automatically.

Installation and Your First Test

Install pytest (and coverage, which we'll use later):

pip install pytest pytest-cov

Create a simple module to test:

# calculator.py
def add(a, b):
    return a + b

def divide(a, b):
    if b == 0:
        raise ValueError("Cannot divide by zero")
    return a / b

def factorial(n):
    if n < 0:
        raise ValueError("Factorial not defined for negative numbers")
    if n == 0 or n == 1:
        return 1
    result = 1
    for i in range(2, n + 1):
        result *= i
    return result

Create a test file. pytest expects test files to follow the naming convention test_*.py or *_test.py:

# test_calculator.py
from calculator import add, divide, factorial

def test_add_positive():
    assert add(2, 3) == 5

def test_add_negative():
    assert add(-1, -1) == -2

def test_add_zeros():
    assert add(0, 0) == 0

def test_divide():
    assert divide(10, 2) == 5.0

def test_divide_float():
    assert divide(7, 2) == 3.5

def test_divide_by_zero():
    try:
        divide(10, 0)
        assert False, "Should have raised ValueError"
    except ValueError:
        pass

Run the tests:

Testing Exceptions with pytest.raises

That test_divide_by_zero was ugly. pytest provides a context manager for testing exceptions:

import pytest
from calculator import divide, factorial

def test_divide_by_zero():
    with pytest.raises(ValueError, match="Cannot divide by zero"):
        divide(10, 0)

def test_factorial_negative():
    with pytest.raises(ValueError, match="negative"):
        factorial(-1)

The match parameter verifies the error message matches a regex pattern. Both the exception type AND the message must match for the test to pass.

Fixtures: Clean Test Setup and Teardown

Fixtures are pytest's way of managing test setup and teardown. Instead of repeating initialization code in every test, you define a fixture once and request it where needed.

A fixture is a function decorated with @pytest.fixture:

import pytest

@pytest.fixture
def sample_users():
    """Create a list of sample user dictionaries."""
    return [
        {"id": 1, "name": "Alice", "email": "alice@example.com", "active": True},
        {"id": 2, "name": "Bob", "email": "bob@example.com", "active": True},
        {"id": 3, "name": "Charlie", "email": "charlie@example.com", "active": False},
    ]

# Use the fixture by adding it as a parameter
def test_find_active_users(sample_users):
    active = [u for u in sample_users if u["active"]]
    assert len(active) == 2
    assert active[0]["name"] == "Alice"

def test_find_inactive_users(sample_users):
    inactive = [u for u in sample_users if not u["active"]]
    assert len(inactive) == 1
    assert inactive[0]["name"] == "Charlie"

def test_total_users(sample_users):
    assert len(sample_users) == 3

The fixture runs once per test that requests it. No manual setup code needed.

Fixture Scopes

By default, fixtures run once per test function. You can change this with the scope parameter:

# Function scope (default) — runs once per test function
@pytest.fixture
def user_data():
    ...

# Class scope — runs once per test class
@pytest.fixture(scope="class")
def class_wide_data():
    ...

# Module scope — runs once per test file
@pytest.fixture(scope="module")
def database_connection():
    conn = create_db_connection()
    yield conn
    conn.close()  # Teardown code runs after yield

# Session scope — runs once per entire test session
@pytest.fixture(scope="session")
def global_config():
    config = load_global_config()
    yield config

The yield keyword separates setup (before) from teardown (after). Everything before yield runs before the test; everything after runs after the test completes.

Organizing Fixtures in conftest.py

When you have many fixtures, extract them into conftest.py. pytest automatically discovers fixtures in this file without any imports:

# conftest.py
import pytest

@pytest.fixture
def sample_users():
    return [
        {"id": 1, "name": "Alice", "active": True},
        {"id": 2, "name": "Bob", "active": True},
        {"id": 3, "name": "Charlie", "active": False},
    ]

@pytest.fixture
def empty_database():
    """Fixture that provides a clean in-memory database."""
    db = InMemoryDatabase()
    yield db
    db.close()

@pytest.fixture
def populated_database(empty_database):
    """Build on another fixture."""
    empty_database.insert_many(sample_users())
    return empty_database

Fixtures can even depend on other fixtures! populated_database requests empty_database as a parameter, and pytest handles the ordering automatically.

Parametrization: One Test, Many Inputs

Instead of writing separate test functions for each input, parametrize a single test:

import pytest
from calculator import add, factorial

@pytest.mark.parametrize("a, b, expected", [
    (2, 3, 5),
    (-1, 1, 0),
    (0, 0, 0),
    (100, 200, 300),
    (-50, -50, -100),
])
def test_add_parametrized(a, b, expected):
    assert add(a, b) == expected

@pytest.mark.parametrize("n, expected", [
    (0, 1),
    (1, 1),
    (5, 120),
    (10, 3628800),
])
def test_factorial_parametrized(n, expected):
    assert factorial(n) == expected

pytest runs the test function once for each parameter set. In the output, you see:

test_calculator.py::test_add_parametrized[2-3-5] PASSED     [ 12%]
test_calculator.py::test_add_parametrized[-1-1-0] PASSED    [ 25%]
test_calculator.py::test_add_parametrized[0-0-0] PASSED     [ 37%]
test_calculator.py::test_add_parametrized[100-200-300] PASSED [ 50%]
test_calculator.py::test_add_parametrized[-50--50--100] PASSED [ 62%]

You can combine parametrization with fixtures:

@pytest.mark.parametrize("threshold", [0, 1, 2, 5])
def test_filter_by_count(sample_users, threshold):
    """Filter users list by a count threshold."""
    all_users = sample_users[:threshold]
    assert len(all_users) == min(threshold, len(sample_users))

Mocking External Dependencies

Real applications call external APIs, databases, file systems, and networks. Tests should be fast, deterministic, and not depend on external services. Mocking replaces these dependencies with controlled fakes.

pytest integrates with Python's built-in unittest.mock and provides the mocker fixture (from pytest-mock):

pip install pytest-mock

Example: testing a function that calls an external API:

# services.py
import requests

def fetch_user_profile(user_id):
    """Fetch user profile from an external API."""
    response = requests.get(f"https://api.example.com/users/{user_id}")
    response.raise_for_status()
    return response.json()

def get_user_age(user_id):
    """Get user age from the API."""
    profile = fetch_user_profile(user_id)
    return profile.get("age")
# test_services.py
import pytest
from unittest.mock import patch, MagicMock
from services import fetch_user_profile, get_user_age

def test_fetch_user_profile_success(mocker):
    """Test successful API response."""
    # Mock the requests.get call
    mock_response = MagicMock()
    mock_response.json.return_value = {"id": 1, "name": "Alice", "age": 30}
    mock_response.raise_for_status = MagicMock()

    mocker.patch("services.requests.get", return_value=mock_response)

    result = fetch_user_profile(1)

    assert result == {"id": 1, "name": "Alice", "age": 30}
    # Verify requests.get was called with the right URL
    from services import requests
    requests.get.assert_called_once_with("https://api.example.com/users/1")

def test_fetch_user_profile_not_found(mocker):
    """Test API returns 404."""
    mock_response = MagicMock()
    mock_response.raise_for_status.side_effect = requests.exceptions.HTTPError("404")

    mocker.patch("services.requests.get", return_value=mock_response)

    with pytest.raises(requests.exceptions.HTTPError):
        fetch_user_profile(999)

def test_get_user_age(mocker):
    """Test the dependent function."""
    mocker.patch("services.fetch_user_profile", return_value={
        "id": 1, "name": "Alice", "age": 30
    })

    assert get_user_age(1) == 30

The key insight: mocker.patch replaces the function at the point where it's used (in services), not where it's defined. If services.py says import requests, you patch services.requests. If it says from requests import get, you patch services.get.

Asserting with Confidence

pytest rewrites Python's assert to provide detailed failure messages. You don't need special assertion methods:

def test_assertions():
    # Equality
    assert 2 + 2 == 4

    # Membership
    assert "a" in "apple"
    assert 3 not in [1, 2, 4]

    # Truthiness
    assert True
    assert not False
    assert "hello"    # Non-empty string is truthy

    # Approximate equality (floating point)
    assert 1 / 3 == pytest.approx(0.333333)

    # Type checking
    assert isinstance("hello", str)

    # Exception testing
    with pytest.raises(ValueError, match="negative"):
        factorial(-1)

    # Any of multiple exceptions
    with pytest.raises((ValueError, TypeError)):
        divide("a", 0)

When an assertion fails, pytest shows the values involved:

# If add(2, 3) returned 6 instead of 5:
# E       assert 6 == 5
# E        +  where 6 = add(2, 3)

Test Organization and Structure

As your project grows, organize tests in a dedicated directory:

my_project/
├── src/
│   ├── __init__.py
│   ├── calculator.py
│   ├── services.py
│   └── models.py
├── tests/
│   ├── conftest.py           # Shared fixtures
│   ├── test_calculator.py    # Tests for calculator.py
│   ├── test_services.py      # Tests for services.py
│   └── test_models.py        # Tests for models.py
├── pytest.ini                # pytest configuration
└── pyproject.toml            # Dependencies

A minimal pytest.ini:

# pytest.ini
[pytest]
testpaths = tests
python_files = test_*.py
python_classes = Test*
python_functions = test_*
addopts = -v --tb=short
markers =
    slow: marks tests as slow (deselect with '-m "not slow"')
    integration: marks tests as integration tests

Use @pytest.mark.slow to tag long-running tests:

@pytest.mark.slow
def test_heavy_computation():
    """This test takes a while — skip in quick runs."""
    result = heavy_computation()
    assert result is not None

# Run without slow tests:
pytest -m "not slow"

# Run only slow tests:
pytest -m slow

Test Coverage

Coverage tells you what percentage of your code is exercised by tests. Install and run:

pip install pytest-cov

# Run tests with coverage report
pytest --cov=src --cov-report=term-missing

# Output:
# Name               Stmts   Miss  Cover   Missing
# ------------------------------------------------
# src/__init__.py        0      0   100%
# src/calculator.py      12      1    92%   15
# src/services.py        18      8    56%   8-12, 15-18
# ------------------------------------------------
# TOTAL                  30      9    70%

# HTML coverage report (open in browser)
pytest --cov=src --cov-report=html
# Opens htmlcov/index.html

Aim for 80%+ coverage on critical code paths, but don't obsess over 100%. Test behavior, not lines of code. A test that verifies correct output is worth more than a test that just touches a line.

Enforce a minimum coverage threshold in CI:

# Fail if coverage drops below 80%
pytest --cov=src --cov-fail-under=80

Complete Project Example

Here's a realistic module and its test suite:

# src/user_manager.py
class UserManager:
    """Manage a collection of users."""

    def __init__(self):
        self._users = {}

    def add_user(self, user_id, name, email):
        """Add a user to the manager."""
        if user_id in self._users:
            raise ValueError(f"User {user_id} already exists")
        if not email or "@" not in email:
            raise ValueError("Invalid email address")
        self._users[user_id] = {
            "id": user_id,
            "name": name,
            "email": email,
        }
        return self._users[user_id]

    def get_user(self, user_id):
        """Get a user by ID."""
        if user_id not in self._users:
            raise KeyError(f"User {user_id} not found")
        return self._users[user_id]

    def remove_user(self, user_id):
        """Remove a user. Returns the removed user."""
        if user_id not in self._users:
            raise KeyError(f"User {user_id} not found")
        return self._users.pop(user_id)

    def list_users(self, active_only=False):
        """List all users."""
        return list(self._users.values())

    def user_count(self):
        """Return the number of users."""
        return len(self._users)
# tests/test_user_manager.py
import pytest
from src.user_manager import UserManager

@pytest.fixture
def user_manager():
    """Provide a fresh UserManager for each test."""
    return UserManager()

@pytest.fixture
def manager_with_users(user_manager):
    """A manager pre-populated with users."""
    user_manager.add_user(1, "Alice", "alice@example.com")
    user_manager.add_user(2, "Bob", "bob@example.com")
    return user_manager

class TestAddUser:
    def test_add_single_user(self, user_manager):
        user = user_manager.add_user(1, "Alice", "alice@example.com")
        assert user["name"] == "Alice"
        assert user["email"] == "alice@example.com"

    def test_add_duplicate_raises(self, manager_with_users):
        with pytest.raises(ValueError, match="already exists"):
            manager_with_users.add_user(1, "Alice2", "alice2@example.com")

    @pytest.mark.parametrize("email", ["", "notanemail", "@missing.com", "no-at-sign"])
    def test_invalid_email_raises(self, user_manager, email):
        with pytest.raises(ValueError, match="Invalid email"):
            user_manager.add_user(1, "Test", email)

class TestGetUser:
    def test_get_existing_user(self, manager_with_users):
        user = manager_with_users.get_user(1)
        assert user["name"] == "Alice"

    def test_get_missing_user_raises(self, user_manager):
        with pytest.raises(KeyError, match="not found"):
            user_manager.get_user(999)

class TestRemoveUser:
    def test_remove_existing_user(self, manager_with_users):
        removed = manager_with_users.remove_user(1)
        assert removed["name"] == "Alice"
        assert manager_with_users.user_count() == 1

    def test_remove_missing_user_raises(self, user_manager):
        with pytest.raises(KeyError, match="not found"):
            user_manager.remove_user(999)

class TestListAndCount:
    def test_list_all_users(self, manager_with_users):
        users = manager_with_users.list_users()
        assert len(users) == 2

    def test_empty_list(self, user_manager):
        assert user_manager.list_users() == []

    def test_user_count(self, manager_with_users):
        assert manager_with_users.user_count() == 2

Running and Debugging Tests

Useful pytest commands:

# Run all tests
pytest

# Run with verbose output
pytest -v

# Run a specific test file
pytest tests/test_user_manager.py

# Run a specific test function
pytest tests/test_user_manager.py::TestAddUser::test_add_single_user

# Run tests matching a keyword
pytest -k "email"        # Tests with "email" in name
pytest -k "add and not duplicate"  # Boolean keywords

# Show print statements
pytest -s                 # Enable stdout

# Stop on first failure
pytest -x

# Run last-failed tests only
pytest --lf

# Watch mode (rerun on file changes)
pytest-watch

# Test with specific Python version
pytest --pyargs my_package

To debug failing tests, drop into the debugger:

# Install pytest-ipdb or pytest-pdb
pip install pytest-ipdb

# Add this in your test code to pause execution:
import ipdb; ipdb.set_trace()

# Or use the built-in breakpoint:
breakpoint()

Best Practices

  1. One assertion per concept — each test verifies one behavior
  2. Name tests descriptively — test_add_duplicate_raises is better than test_add2
  3. Use fixtures over setup methods — fixtures are reusable and composable
  4. Parametrize over duplication — test multiple inputs with one test function
  5. Mock external dependencies — no API calls, no databases, no file systems in unit tests
  6. Test edge cases — empty inputs, None values, boundary conditions, exceptions
  7. Run tests before committing — make it part of your workflow or use a pre-commit hook
  8. Aim for 80%+ coverage — but prioritize meaningful tests over line count
