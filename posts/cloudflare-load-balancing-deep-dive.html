Cloudflare Load Balancing: Distribute Traffic Across Multiple Servers

July 2, 2026 9 min read

When your application grows beyond a single server, you need a way to distribute incoming traffic across multiple backends. Cloudflare Load Balancing sits at the edge of Cloudflare's global network, routing each request to the healthiest, closest server in your pool. No need to manage your own load balancers, buy additional IP addresses, or configure DNS failover manually.

Load Balancing is part of Cloudflare's Pro plan and above ($20/month), but it includes health monitoring, automatic failover, geographic steering, and analytics — all managed from a single dashboard. Let's walk through setting it up from scratch.

How Cloudflare Load Balancing Works

The architecture has three components:

  1. Pools — A group of origin servers that can serve traffic. Each server in a pool has a weight (for traffic distribution) and metadata (for identification).
  2. Monitors — Health checks that continuously test your origin servers. Failed checks mark servers as down, removing them from rotation.
  3. Load Balancers — The routing rule that connects a DNS hostname to one or more pools, with steering policies that decide which pool handles each request.

When a request arrives, Cloudflare checks the Load Balancer configuration, evaluates health monitors against pool members, applies steering rules, and routes the request — all within Cloudflare's edge network with sub-50ms latency.

Setting Up Pools

A pool is a group of servers that serve the same application. Let's create two pools: a primary pool in the US and a failover pool in Europe.

Dashboard Method

Go to your Cloudflare dashboard → Load Balancing → Overview → Create Load Balancer.

First, create a pool:

  • Name: us-primary-pool
  • Origin 1: 192.168.1.10 (weight: 10)
  • Origin 2: 192.168.1.11 (weight: 10)
  • Origin 3: 192.168.1.12 (weight: 5) — maybe a smaller instance

Weights determine traffic distribution. With weights of 10/10/5, the first two servers get double the traffic of the third. Total weight = 25, so server 1 gets 40%, server 2 gets 40%, server 3 gets 20%.

API Method

You can also create pools via the Cloudflare API:

import requests

API_TOKEN = "your-api-token"
ACCOUNT_ID = "your-account-id"

headers = {
    "Authorization": f"Bearer {API_TOKEN}",
    "Content-Type": "application/json"
}

pool_data = {
    "name": "us-primary-pool",
    "description": "US East primary servers",
    "minimum_origins": 1,
    "origins": [
        {
            "name": "us-east-server-1",
            "address": "192.168.1.10",
            "enabled": True,
            "weight": 10
        },
        {
            "name": "us-east-server-2",
            "address": "192.168.1.11",
            "enabled": True,
            "weight": 10
        },
        {
            "name": "us-east-server-3",
            "address": "192.168.1.12",
            "enabled": True,
            "weight": 5
        }
    ]
}

resp = requests.post(
    f"https://api.cloudflare.com/client/v4/accounts/{ACCOUNT_ID}/load_balancers/pools",
    headers=headers,
    json=pool_data
)
pool_id = resp.json()["result"]["id"]
print(f"Pool created: {pool_id}")

Configuring Health Monitors

Monitors continuously check your origins. If a server fails health checks, Cloudflare stops sending it traffic — automatically, in seconds.

Create a monitor via the API:

monitor_data = {
    "method": "GET",
    "path": "/health",
    "port": 443,
    "protocol": "https",
    "header": {
        "Host": "app.example.com"
    },
    "expected_body": "ok",
    "expected_codes": "2xx",
    "interval": 30,
    "timeout": 10,
    "retries": 3,
    "allowed_zones": [
        "us-east-1",
        "us-west-2",
        "eu-west-1",
        "eu-central-1"
    ],
    "description": "Production health check"
}

resp = requests.post(
    f"https://api.cloudflare.com/client/v4/accounts/{ACCOUNT_ID}/load_balancers/monitors",
    headers=headers,
    json=monitor_data
)
monitor_id = resp.json()["result"]["id"]
print(f"Monitor created: {monitor_id}")

Monitor settings explained:

  • interval: 30 — Check every 30 seconds (minimum: 30s on most plans)
  • timeout: 10 — Fail if no response within 10 seconds
  • retries: 3 — Mark as down after 3 consecutive failures from different data centers
  • allowed_zones — Only these Cloudflare data centers will perform checks (reduces false positives from distant regions)
  • expected_body: "ok" — Response body must contain "ok" (custom health check)

Your application needs a simple health endpoint. Here's a Python example with Flask:

from flask import Flask

app = Flask(__name__)

@app.route("/health")
def health():
    # Check database connectivity, disk space, etc.
    status = check_database() and check_disk_space()
    if status:
        return "ok", 200
    return "fail", 500

def check_database():
    try:
        db = get_database_connection()
        db.execute("SELECT 1")
        return True
    except Exception:
        return False

def check_disk_space():
    import shutil
    total, used, free = shutil.disk_usage("/")
    return free > 1_073_741_824  # At least 1GB free

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=8080)

Creating the Load Balancer

Now connect your pools to a Load Balancer with steering policies:

lb_data = {
    "name": "lb.example.com",
    "description": "Production load balancer",
    "enabled": True,
    "ttl": 30,  # 30 seconds for quick failover
    "fallback_pool": "eu-failover-pool-id",
    "default_pools": [
        "us-primary-pool-id"
    ],
    "session_affinity": "cookie",  # Same user → same server
    "session_affinity_ttl": 600,  # 10 minutes
    "proxied": True,
    "steering": {
        "policy": "geo"  # Route to nearest geographic pool
    },
    "rules": [
        {
            "name": "eu-users-to-eu-pool",
            "match": {
                "and": [
                    {"name": "geo", "op": "eq", "value": "EU"}
                ]
            },
            "pool": "eu-failover-pool-id"
        },
        {
            "name": "api-path-to-api-pool",
            "match": {
                "and": [
                    {"name": "http.request.uri.path", "op": "contains", "value": "/api/"}
                ]
            },
            "pool": "api-pool-id"
        }
    ]
}

resp = requests.put(
    f"https://api.cloudflare.com/client/v4/accounts/{ACCOUNT_ID}/load_balancers",
    headers=headers,
    json=lb_data
)
print(f"Load balancer created: {resp.json()['result']['id']}")

Steering Policies Explained

Cloudflare offers four steering policies:

1. Off (Weight-based Round Robin)

Distributes traffic based on origin weights. Simple and fair. Use this when all your servers are in the same region.

2. Geographic (geo)

Routes each request to the pool closest to the user. Best for multi-region deployments. Combined with rules, you can route EU traffic to EU servers and everyone else to US servers.

3. Random

Randomly distributes traffic across origins. Useful for testing or when you want uniform distribution regardless of weight.

4. Latency-Based

Routes to the origin with the lowest current latency. Cloudflare measures round-trip time from each edge server to each origin and picks the fastest one. Automatically adapts to network conditions.

# Latency-based steering configuration
lb_data["steering"] = {
    "policy": "random"  # or "off", "geo"
}

# For latency-based, no special steering — just set:
lb_data["steering"] = {
    "policy": "off"  # Falls back to lowest latency when off
}

Session Affinity (Sticky Sessions)

If your application uses server-side sessions, you need sticky sessions so a user's requests always go to the same server. Cloudflare supports two modes:

# Cookie-based affinity
"session_affinity": "cookie",
"session_affinity_attributes": {
    "samesite": "lax",
    "secure": True,
    "ttl": 600  # Minutes
}

# Or use your own cookie name
"session_affinity": "cookie",
"session_affinity_ttl": 600,
"session_affinity_attributes": {
    "samesite": "strict"
}

The cookie name defaults to cf_lb. Cloudflare sets this cookie on the response and routes subsequent requests based on it. When the TTL expires, the user may be routed to a different server.

Monitoring and Analytics

Cloudflare provides real-time load balancing analytics. Check these metrics in your dashboard under Analytics → Load Balancing:

  • Traffic Distribution — How traffic is spread across pools and origins
  • Health Check Status — Real-time status of all origins with failure reasons
  • Steering — Which steering rules matched and why
  • Failovers — History of when and why servers were taken out of rotation

You can also query the analytics API programmatically:

# Query load balancer analytics
from datetime import datetime, timedelta

date = (datetime.utcnow() - timedelta(hours=1)).strftime("%Y-%m-%dT%H:00:00")

resp = requests.get(
    f"https://api.cloudflare.com/client/v4/accounts/{ACCOUNT_ID}/load_balancers/analytics/summarize",
    headers=headers,
    params={
        "since": date,
        "limit": 50
    }
)

for record in resp.json()["result"]:
    print(f"Pool: {record['pool_name']}")
    print(f"  Requests: {record['request_count']}")
    print(f"  Failures: {record['failed_count']}")
    print(f"  Avg latency: {record['avg_latency']}ms")

Load Balancing with Cloudflare Workers

For more advanced routing logic, combine Load Balancing with Cloudflare Workers:

addEventListener("fetch", event => {
    event.respondWith(handleRequest(event.request));
});

async function handleRequest(request) {
    const url = new URL(request.url);

    // Custom routing based on user tier
    const userTier = request.headers.get("X-User-Tier") || "standard";

    let pool;
    if (userTier === "premium") {
        pool = "premium-server-pool";
    } else {
        pool = "standard-server-pool";
    }

    // Pass request to the origin with pool selection
    const originUrl = `https://${pool}.internal.example.com${url.pathname}${url.search}`;

    return await fetch(originUrl, {
        method: request.method,
        headers: request.headers,
        body: request.body
    });
}

Best Practices

  1. Always have a fallback pool — Even if it's a maintenance page, never let the Load Balancer have zero healthy backends
  2. Set minimum_origins — Require at least N servers in a pool before it accepts traffic (prevents routing to a dying pool)
  3. Use realistic health checks — Check the database and dependencies, not just HTTP 200. A server can respond 200 while being completely broken
  4. Test failover regularly — Simulate server failures to verify your Load Balancer routes traffic correctly
  5. Use session affinity for stateful apps — If you have server-side sessions, enable cookie-based affinity
  6. Monitor failover events — Set up alerts for health check failures so you can respond before users are affected
  7. Keep TTL low — 30 seconds is a good default. Lower TTL means faster propagation of changes but more DNS queries

Cost Considerations

Cloudflare Load Balancing is $20/month per Load Balancer on the Pro plan, or included in Business ($200+/month) and Enterprise plans. Each Load Balancer can have multiple pools, so you typically only need one per domain.

For hobby projects or single-server setups, a simple DNS record is enough. Load Balancing makes sense when you have:

  • Multiple servers behind a single hostname
  • Need automatic failover (no manual DNS changes)
  • Multi-region deployments
  • Custom routing based on geography, path, or user attributes

Summary

Cloudflare Load Balancing gives you enterprise-grade traffic distribution with zero infrastructure to manage. Set up pools, configure health monitors, create a Load Balancer with steering rules, and you're done. Automatic failover happens in seconds, geographic routing reduces latency, and real-time analytics keep you informed.
