Docker Networking Deep Dive: Containers That Communicate — Complete Guide

July 9, 2026 10 min read

When containers can't reach each other, or your app can't access the internet, the culprit is almost always networking. Docker manages networks automatically, but understanding how they work is the difference between "it works on my machine" and production-ready deployments. This guide covers every Docker network driver, DNS resolution, port mapping, and the networking magic inside docker-compose.

1. Docker Network Drivers

Docker ships with five network drivers, each designed for a specific use case:

DriverUse CaseMulti-host?
bridgeDefault — containers on one hostNo
hostRemove isolation — use host networkN/A
noneNo networking at allNo
overlayContainers across multiple Docker hostsYes (swarm)
macvlanAssign real MAC addressesYes

2. The Default Bridge Network

When you run docker run without --network, Docker places the container on the default bridge network:

# See all networks
docker network ls

# Inspect the default bridge
docker network inspect bridge

# Run a container on the default bridge (implicit)
docker run -d --name web nginx

# Connect to it from the host
curl http://localhost

# But OTHER containers can't resolve it by name on the default bridge!

The default bridge provides NAT (containers can reach the internet) but containers cannot discover each other by name. You must use --link (deprecated) or IP addresses to communicate between containers on the default bridge.

3. Custom Bridge Networks — DNS Auto-Discovery

Custom bridge networks solve the name resolution problem. Containers on the same custom network can reach each other by container name:

# Create a custom bridge network
docker network create mynet

# Run containers on it
docker run -d --name db --network mynet postgres:15
docker run -d --name web --network mynet \
    -e DATABASE_HOST=db \
    nginx

# Now "web" can resolve "db" to its IP address
docker exec web ping db
# PING db (172.18.0.2): 56 data bytes

# Connect a running container to a network
docker network connect mynet existing_container

Key insight: Docker provides an embedded DNS server on every custom bridge network. Container names are automatically registered as DNS entries. This is the foundation of docker-compose service discovery.

4. Host Network Mode

Host mode removes all network isolation — the container shares the host's network namespace:

# Container uses the host's IP and ports directly
docker run -d --network host nginx

# The container IS the host — no port mapping needed
# If nginx listens on port 80, it's on host port 80
curl http://localhost

# Useful for: high-throughput apps, network tools, monitoring
# NOT useful for: running multiple services on same port

Host mode is faster (no NAT overhead) but you can't run two containers on the same port. It's common in monitoring stacks (Prometheus, cAdvisor) and high-performance scenarios.

5. Port Mapping: Publishing Container Ports

By default, containers are isolated. Port mapping bridges the gap:

# -p host_port:container_port
docker run -d --name web -p 8080:80 nginx

# Access on host:port
curl http://localhost:8080

# Bind to specific interface
docker run -d -p 127.0.0.1:8080:80 nginx
# Only accessible from localhost, not from other machines

# Multiple port mappings
docker run -d -p 8080:80 -p 8443:443 myapp

# Random host port (Docker picks one)
docker run -d -p 80 nginx
docker port web  # Shows which host port was assigned

# UDP ports
docker run -d -p 5353:5353/udp dns-server

6. Docker Compose Networking

docker-compose creates a network automatically and connects all services to it:

# docker-compose.yml
services:
  web:
    image: nginx
    ports:
      - "8080:80"
    depends_on:
      - api

  api:
    image: node:18
    command: node server.js
    environment:
      DB_HOST: db        # DNS resolves to the "db" container
      REDIS_HOST: redis  # DNS resolves to the "redis" container

  db:
    image: postgres:15
    environment:
      POSTGRES_PASSWORD: secret
    volumes:
      - db_data:/var/lib/postgresql/data

  redis:
    image: redis:7
    # No ports exposed — only accessible from other containers

volumes:
  db_data:

All four services are on the same network. web can reach api by hostname, api can reach both db and redis. Only web exposes a port to the host.

Multiple Networks in Compose

Isolate services with multiple networks — a common production pattern:

services:
  # Public-facing (accessible from host)
  web:
    image: nginx
    ports:
      - "8080:80"
    networks:
      - frontend
      - backend

  # Backend service (not directly exposed)
  api:
    image: node:18
    networks:
      - frontend
      - backend

  # Database (only accessible from backend)
  db:
    image: postgres:15
    networks:
      - backend

networks:
  frontend:  # web & api
  backend:   # web, api & db

The db container is on the backend network only. Even if someone attacks the web container on the frontend network, they cannot reach db. This is network segmentation — a core security practice.

7. Docker DNS Resolution Details

Docker's embedded DNS server provides more than basic name resolution:

# Get a container's IP address
docker inspect -f '{{range.NetworkSettings.Networks}}{{.IPAddress}}{{end}}' web

# Resolve DNS from inside a container
docker exec web nslookup api
# Server:    127.0.0.11
# Address:   127.0.0.11#53
# Name:      api
# Address:   172.19.0.3

# Containers resolve by:
# 1. Service name (docker-compose)
# 2. Container name (--name flag)
# 3. Full network alias
# 4. External DNS (falls through to /etc/resolv.conf)

Docker's DNS server listens at 127.0.0.11 inside containers. It resolves container names on the same network, then forwards to the host's DNS resolver for external domains.

Network Aliases

Give containers multiple DNS names for flexible naming:

# docker-compose.yml
services:
  db:
    image: postgres:15
    networks:
      backend:
        aliases:
          - database
          - postgres
          - db-primary

Now db, database, postgres, and db-primary all resolve to the same container. This lets you rename services without updating every connection string.

8. Network Isolation and Security

Docker provides several mechanisms to isolate and secure container networks:

# Create an isolated network (no internet access for containers)
docker network create --internal isolated

# Containers on this network can talk to each other
# but CANNOT reach the internet
docker run -d --network isolated --name app myapp

# Create with specific subnet (useful for IP-based rules)
docker network create \
    --driver bridge \
    --subnet 172.20.0.0/16 \
    --gateway 172.20.0.1 \
    appnet

# Disconnect a container from a network (runtime)
docker network disconnect mynet suspicious_container

# Inspect what's connected
docker network inspect mynet

9. Troubleshooting Docker Networks

When containers can't reach each other, follow this checklist:

# 1. Verify the container is on the right network
docker inspect --format='{{range $net, $config := .NetworkSettings.Networks}}{{$net}} {{end}}' container_name

# 2. Check DNS resolution from inside the container
docker exec web ping db
docker exec web nslookup api

# 3. Check port mappings
docker port web
docker ps --format "{{.Names}}: {{.Ports}}"

# 4. Verify the target service is actually running
docker logs db
docker exec db pg_isready

# 5. Check for firewall rules on the host
sudo iptables -L -n | grep docker

# 6. Test from the host
curl http://localhost:8080
curl http://db_ip:5432

# 7. Inspect full network config
docker network inspect mynet
docker network inspect bridge

10. Practical: Three-Tier Application Stack

Let's combine everything into a production-like docker-compose setup:

# docker-compose.yml — Three-tier with network isolation
services:
  # Reverse proxy + CDN
  nginx:
    image: nginx:alpine
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./nginx.conf:/etc/nginx/nginx.conf
    networks:
      - proxy
      - app
    depends_on:
      - app
    restart: unless-stopped

  # Application server
  app:
    build: ./app
    environment:
      DATABASE_URL: postgresql://user:pass@db:5432/myapp
      REDIS_URL: redis://cache:6379
    networks:
      - proxy
      - app
      - data
    depends_on:
      db:
        condition: service_healthy
      cache:
        condition: service_started
    restart: unless-stopped

  # Database (isolated — no public network)
  db:
    image: postgres:15-alpine
    environment:
      POSTGRES_DB: myapp
      POSTGRES_USER: user
      POSTGRES_PASSWORD: pass
    volumes:
      - pgdata:/var/lib/postgresql/data
    networks:
      - data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U user"]
      interval: 10s
      timeout: 5s
    restart: unless-stopped

  # Redis cache (isolated — no public network)
  cache:
    image: redis:7-alpine
    command: redis-server --maxmemory 256mb --maxmemory-policy allkeys-lru
    networks:
      - data
    restart: unless-stopped

networks:
  proxy:  # nginx & app — handles incoming traffic
  app:    # nginx & app — internal API calls
  data:   # app, db, cache — backend data layer

volumes:
  pgdata:

This setup gives you three security layers: the proxy network handles public traffic, app handles service-to-service communication, and data isolates your databases. An attacker on the proxy network cannot reach db or cache directly.

Summary

  • Default bridge: quick start, no DNS between containers
  • Custom bridge: automatic DNS resolution — use these!
  • docker-compose: creates custom bridge + DNS automatically
  • Host mode: maximum performance, no isolation
  • Multiple networks: segment traffic for security
  • Port mapping: -p host:container bridges external access
  • Internal networks: block internet access with --internal
  • Network aliases: give containers multiple DNS names

Docker networking transforms containers from isolated boxes into a connected system. Understanding these concepts means you can design secure, maintainable architectures instead of fighting mysterious connectivity issues. Start with custom bridge networks and docker-compose — they handle 95% of development and staging scenarios.
