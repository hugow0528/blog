Docker Health Checks & Container Monitoring: Know If Your Containers Are Actually Working

2026-06-30

When you run a container with docker run and see a green status, it means the process started — not that it's actually working. A web server might have started but be unable to connect to its database. An API might be running but returning 500 errors. A worker might be deadlocked. Without health checks, you're flying blind. Docker's HEALTHCHECK instruction and restart policies solve this problem. In this guide, you'll learn to configure health checks in Dockerfiles, compose files, and run commands so you always know the real state of your services.

The Problem: Running Doesn't Mean Healthy

Consider a typical stack: a Python web app, a PostgreSQL database, and a Redis cache. You run docker compose up and all three containers show as "Up". But what if PostgreSQL took 15 seconds to initialize and your app started trying to connect at second 2? The container is "running" but the app is failing silently — retrying, logging errors, and serving broken pages to users.

This is where health checks come in. They periodically verify that your container isn't just alive — it's actually functional.

Method 1: HEALTHCHECK in Dockerfile

The HEALTHCHECK instruction tells Docker how to check if your container is healthy. Add it to your Dockerfile:

FROM python:3.12-slim

WORKDIR /app
COPY . .
RUN pip install --no-cache-dir flask requests

EXPOSE 5000

# Health check: curl the app's /health endpoint every 30s
HEALTHCHECK --interval=30s --timeout=5s --retries=3 --start-period=10s \
    CMD curl -f http://localhost:5000/health || exit 1

CMD ["python", "app.py"]

HEALTHCHECK Parameters Explained

  • --interval — How often to run the check (default: 30s)
  • --timeout — How long to wait before considering the check itself failed (default: 30s)
  • --retries — How many consecutive failures before marking unhealthy (default: 3)
  • --start-period — Grace period after container starts before health checks begin (default: 0s)

The --start-period is critical. Without it, your app might be marked unhealthy during startup before it's even ready to serve requests. Set it to cover your worst-case startup time.

The Health Endpoint

Your app needs a /health endpoint. Here's a minimal Flask example that checks real dependencies:

from flask import Flask, jsonify
import psycopg2
import redis

app = Flask(__name__)

@app.route('/health')
def health():
    status = {"status": "healthy"}

    # Check database
    try:
        conn = psycopg2.connect("dbname=app user=postgres password=secret")
        conn.close()
        status["database"] = "ok"
    except Exception as e:
        status["database"] = f"error: {str(e)}"
        status["status"] = "unhealthy"

    # Check Redis
    try:
        r = redis.Redis(host="redis", port=6379)
        r.ping()
        status["redis"] = "ok"
    except Exception as e:
        status["redis"] = f"error: {str(e)}"
        status["status"] = "unhealthy"

    code = 200 if status["status"] == "healthy" else 503
    return jsonify(status), code

This endpoint returns HTTP 200 when everything is connected, and HTTP 503 when any dependency is down. Docker's curl -f treats 503 as a failure, triggering the unhealthy state.

Method 2: Health Check in Docker Compose

You can also define health checks directly in docker-compose.yml. This is useful when you don't control the Dockerfile (e.g., using official images):

version: "3.8"

services:
  app:
    build: .
    ports:
      - "5000:5000"
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_healthy
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:5000/health"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 15s
    restart: unless-stopped

  db:
    image: postgres:16
    environment:
      POSTGRES_DB: app
      POSTGRES_PASSWORD: secret
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 10s
    restart: unless-stopped

  redis:
    image: redis:7-alpine
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 3s
      retries: 3
      start_period: 5s
    restart: unless-stopped

The Magic of depends_on.condition: service_healthy

This is the killer feature. Instead of just starting the app after the database starts, Compose waits until the database reports healthy before starting the app. No more "connection refused" errors on startup:

  • Database starts → health checks run every 10s
  • After pg_isready succeeds → status becomes "healthy"
  • Only then does the app container start

Before this feature, developers used hacky workarounds like sleep 30 or custom init scripts to wait for databases. Now it's built in.

Method 3: Health Check via docker run

You can add a health check directly on the command line (no Dockerfile or compose needed):

docker run -d \
  --name myapp \
  --health-cmd "curl -f http://localhost:5000/health || exit 1" \
  --health-interval 30s \
  --health-timeout 5s \
  --health-retries 3 \
  --health-start-period 10s \
  -p 5000:5000 \
  myapp:latest

Useful for testing or quick deployments, but for production, prefer Dockerfile or compose definitions so the health check travels with your image.

Checking Health Status

Once your containers are running with health checks, monitor them:

# See health status in the container list
$ docker ps
CONTAINER ID  IMAGE        STATUS                   PORTS
abc123        myapp        Up 2 minutes (healthy)   0.0.0.0:5000->5000/tcp
def456        postgres     Up 3 minutes (healthy)
ghi789        redis        Up 3 minutes (healthy)

# Inspect a specific container's health details
$ docker inspect --format='{{json .State.Health}}' myapp | python -m json.tool
{
    "Status": "healthy",
    "FailingStreak": 0,
    "Log": [
        {
            "Start": "2026-06-30T10:00:30.123Z",
            "End": "2026-06-30T10:00:30.456Z",
            "ExitCode": 0,
            "Output": "{\"status\":\"healthy\",\"database\":\"ok\",\"redis\":\"ok\"}"
        }
    ]
}

Three possible states:

  • starting — Within the start-period grace window
  • healthy — Last check passed
  • unhealthy — Failed --retries consecutive times

Restart Policies: Auto-Recover from Crashes

Health checks tell you what's wrong. Restart policies tell Docker what to do about it:

# Never restart
docker run --restart=no myapp

# Always restart (even if the container exits normally)
docker run --restart=always myapp

# Restart only on non-zero exit (default for most setups)
docker run --restart=on-failure:5 myapp

# Restart unless explicitly stopped by the user
docker run --restart=unless-stopped myapp

In Docker Compose, add it as a service option:

services:
  app:
    restart: unless-stopped
  db:
    restart: on-failure:5

Combining Health Checks with Restart Policies

By default, Docker does not restart containers that become unhealthy. You need Docker Swarm or an external tool for that. However, you can use a wrapper script to bridge the gap:

# Dockerfile with health-check-based restart
FROM python:3.12-slim
WORKDIR /app
COPY . .
RUN pip install flask requests

EXPOSE 5000
CMD ["python", "app.py"]

# Use a custom entrypoint that monitors health
HEALTHCHECK --interval=30s --timeout=5s --retries=3 \
    CMD python -c "import requests; r=requests.get('http://localhost:5000/health'); r.raise_for_status()" || exit 1

For production-grade auto-recovery, consider running your containers with Docker Swarm (docker stack deploy), Kubernetes, or a process supervisor like systemd.

Health Checks for Non-Web Services

Not all services have HTTP endpoints. Here are common patterns for different service types:

Database (PostgreSQL)

HEALTHCHECK CMD pg_isready -U postgres || exit 1

Cache (Redis)

HEALTHCHECK CMD redis-cli ping || exit 1

Worker / Background Task

Workers don't have endpoints. Instead, check if the process is responsive:

HEALTHCHECK CMD python -c "import os; assert os.path.exists('/tmp/worker_heartbeat')" || exit 1

Your worker writes to /tmp/worker_heartbeat every few seconds. If the file doesn't exist, the worker is stuck or crashed:

# In your worker code
import time
while True:
    process_next_task()
    with open("/tmp/worker_heartbeat", "w") as f:
        f.write(str(time.time()))
    time.sleep(5)

API Service (No HTTP)

If your service communicates via TCP, sockets, or queues:

# Check TCP port is listening
HEALTHCHECK CMD python -c "import socket; s=socket.socket(); s.settimeout(3); s.connect(('localhost', 8080)); s.close()" || exit 1

# Check message queue
HEALTHCHECK CMD rabbitmqctl status || exit 1

# Check file-based communication
HEALTHCHECK CMD test -f /var/run/myapp.pid && kill -0 $(cat /var/run/myapp.pid) || exit 1

Disabling Health Checks

Some base images include health checks you might want to override:

# Disable an inherited health check
HEALTHCHECK NONE

Best Practices Summary

  1. Always use --start-period — Give your app time to boot before the first check
  2. Check real dependencies — Don't just ping the process; verify it can connect to its databases and services
  3. Keep checks fast — A health check that takes 10 seconds will slow down orchestration tools
  4. Use service_healthy conditions — Let Docker Compose handle startup ordering
  5. Combine with restart policies — Auto-recover from transient failures
  6. Log health check output — The Output field in inspect is valuable for debugging

Conclusion

Health checks transform your containers from "is the process running?" to "is the service actually working?" They're a small addition (one line in your Dockerfile or compose file) that gives you visibility into the real health of your infrastructure. Combined with restart policies and startup conditions, they eliminate the entire class of "it started but it's broken" problems that plague containerized deployments.
