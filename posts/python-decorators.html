Python Decorators: Add Functionality Without Changing Code

July 8, 2026 11 min read

Python decorators let you wrap a function with extra behavior — logging, timing, caching, authentication, retry logic — without touching the function's original code. They're one of Python's most elegant design patterns, and once you understand them, you'll see decorators everywhere in the wild.

The Problem: Repeating Yourself

Imagine you have three functions that all need timing and logging:

import time

def download_file():
    print("Starting download...")
    start = time.time()        # ← repeated
    time.sleep(2)              # simulate work
    print(f"Took {time.time() - start:.2f}s")  # ← repeated

def process_data():
    print("Starting processing...")
    start = time.time()        # ← repeated
    time.sleep(1)              # simulate work
    print(f"Took {time.time() - start:.2f}s")  # ← repeated

def send_email():
    print("Starting email...")
    start = time.time()        # ← repeated
    time.sleep(0.5)            # simulate work
    print(f"Took {time.time() - start:.2f}s")  # ← repeated

This is the Dry (Don't Repeat Yourself) violation. What if you could add timing to any function with a single line?

Decorator Basics: The @ Syntax

Here's the same code using a decorator:

import time

def timer(func):
    """A decorator that measures function execution time."""
    def wrapper(*args, **kwargs):
        start = time.time()
        result = func(*args, **kwargs)
        elapsed = time.time() - start
        print(f"{func.__name__} took {elapsed:.2f}s")
        return result
    return wrapper

@timer  # Apply the decorator
def download_file():
    time.sleep(2)

@timer
def process_data():
    time.sleep(1)

@timer
def send_email():
    time.sleep(0.5)

# Run them
download_file()  # download_file took 2.00s
process_data()   # process_data took 1.00s
send_email()     # send_email took 0.50s

Three functions, zero repeated timing code. The @timer syntax is just shorthand for download_file = timer(download_file).

How Decorators Work Under the Hood

A decorator is simply a function that takes a function and returns a function. Here's the manual version without @:

# These two are EXACTLY the same:

# With @ syntax:
@timer
def my_func():
    pass

# Without @ syntax:
def my_func():
    pass
my_func = timer(my_func)  # Replace my_func with timer's wrapper

The decorator timer receives the original function, creates a wrapper that adds extra behavior, and returns that wrapper. When you call the decorated function, you're actually calling the wrapper.

Key Insight

The args and **kwargs in the wrapper pass through ALL arguments to the original function. This is why decorators work with functions that have different signatures — the wrapper is completely transparent.

Real-World Decorator: Caching (Memoization)

One of the most useful decorators is a cache that remembers previous results:

def cache(func):
    """Cache function results to avoid repeated computation."""
    memo = {}

    def wrapper(*args):
        if args in memo:
            print(f"  [Cache HIT] {func.__name__}{args}")
            return memo[args]

        print(f"  [Computing] {func.__name__}{args}")
        result = func(*args)
        memo[args] = result
        return result

    return wrapper

@cache
def fibonacci(n):
    if n <= 1:
        return n
    return fibonacci(n - 1) + fibonacci(n - 2)

# Without cache, fibonacci(40) takes forever
# With cache, it's instant
print(fibonacci(5))
# [Computing] fibonacci(0)
# [Computing] fibonacci(1)
# [Computing] fibonacci(2)
# [Cache HIT] fibonacci(0)
# [Cache HIT] fibonacci(1)
# [Computing] fibonacci(3)
# [Cache HIT] fibonacci(1)
# [Cache HIT] fibonacci(2)
# ... and so on

# Python actually has this built-in!
from functools import lru_cache

@lru_cache(maxsize=128)
def fibonacci_fast(n):
    if n <= 1:
        return n
    return fibonacci_fast(n - 1) + fibonacci_fast(n - 2)

@lru_cache is a standard library decorator that caches up to maxsize results. It's perfect for pure functions (same input → same output) with expensive computation.

Real-World Decorator: Retry with Exponential Backoff

Network calls fail. APIs time out. A retry decorator handles this gracefully:

import time
import random

def retry(max_attempts=3, delay=1, backoff=2):
    """
    Retry a function on exception.
    Uses exponential backoff: delay, delay*2, delay*4, ...
    """
    def decorator(func):
        def wrapper(*args, **kwargs):
            current_delay = delay
            for attempt in range(1, max_attempts + 1):
                try:
                    return func(*args, **kwargs)
                except Exception as e:
                    if attempt == max_attempts:
                        raise
                    jitter = random.uniform(0, current_delay * 0.1)
                    wait = current_delay + jitter
                    print(f"  Attempt {attempt} failed: {e}")
                    print(f"  Retrying in {wait:.1f}s...")
                    time.sleep(wait)
                    current_delay *= backoff
        return wrapper
    return decorator

# Use it: @retry(max_attempts=3, delay=1, backoff=2)
@retry(max_attempts=3, delay=0.1, backoff=2)
def fetch_user_data(user_id):
    """Simulate an unreliable API call."""
    if random.random() < 0.7:  # 70% chance of failure
        raise ConnectionError("API timeout")
    return {"id": user_id, "name": "Alice"}

# Try it — eventually succeeds
result = fetch_user_data(42)
print(result)

This pattern is so common that libraries like tenacity provide production-ready retry decorators with advanced features.

Real-World Decorator: Input Validation

Decorators can validate arguments before the function even runs:

def validate_age(min_age=0, max_age=150):
    """Decorator that validates the age parameter."""
    def decorator(func):
        def wrapper(*args, **kwargs):
            # Check positional args
            for arg in args:
                if isinstance(arg, int) and not (min_age <= arg <= max_age):
                    raise ValueError(f"Age must be between {min_age} and {max_age}")
            # Check keyword args
            age = kwargs.get("age")
            if isinstance(age, int) and not (min_age <= age <= max_age):
                raise ValueError(f"Age must be between {min_age} and {max_age}")
            return func(*args, **kwargs)
        return wrapper
    return decorator

@validate_age(min_age=18, max_age=120)
def register_user(name, age, email):
    print(f"Registered: {name}, age {age}")
    return {"name": name, "age": age, "email": email}

register_user("Alice", 25, "alice@example.com")  # Works!
# register_user("Bob", 15, "bob@example.com")     # ValueError!

Decorator with Arguments: The Factory Pattern

When you write @retry(max_attempts=3), you're actually using a decorator factory — a function that returns a decorator. The nesting is three levels deep:

# The three-layer structure:
def decorator_factory(arg1, arg2):       # Layer 1: receives decorator args
    def decorator(func):                  # Layer 2: receives the function
        def wrapper(*args, **kwargs):     # Layer 3: runs when function is called
            # ... decorator logic ...
            return func(*args, **kwargs)
        return wrapper
    return decorator

# Usage:
@decorator_factory(value1, value2)  # decorator_factory() returns decorator
def my_function():
    pass

This three-level nesting is the most common source of confusion. Remember: arguments → decorator → wrapper.

Important: Use @functools.wraps

Without @functools.wraps, your decorated function loses its name and docstring:

from functools import wraps

# ❌ BAD — loses metadata
def bad_decorator(func):
    def wrapper(*args, **kwargs):
        return func(*args, **kwargs)
    return wrapper

@bad_decorator
def my_func():
    """Do something important."""
    pass

print(my_func.__name__)  # "wrapper" — not "my_func"!
print(my_func.__doc__)   # None — lost!

# ✅ GOOD — preserves metadata
def good_decorator(func):
    @wraps(func)  # ← copy name, docstring, signature
    def wrapper(*args, **kwargs):
        return func(*args, **kwargs)
    return wrapper

@good_decorator
def my_func():
    """Do something important."""
    pass

print(my_func.__name__)  # "my_func" ✓
print(my_func.__doc__)   # "Do something important." ✓

Always use @functools.wraps in your decorators. It preserves the original function's metadata, which matters for debugging, documentation tools, and frameworks.

Stacking Multiple Decorators

You can apply multiple decorators to one function. They execute bottom to top (innermost first):

def log_call(func):
    @wraps(func)
    def wrapper(*args, **kwargs):
        print(f"[LOG] Calling {func.__name__}")
        result = func(*args, **kwargs)
        print(f"[LOG] {func.__name__} returned {result}")
        return result
    return wrapper

def uppercase(func):
    @wraps(func)
    def wrapper(*args, **kwargs):
        result = func(*args, **kwargs)
        return str(result).upper()
    return wrapper

@log_call      # Applied second (outermost)
@uppercase     # Applied first (innermost)
def greet(name):
    return f"hello, {name}"

message = greet("Alice")
# [LOG] Calling greet
# [LOG] greet returned HELLO, ALICE
print(message)  # HELLO, ALICE

Execution order: uppercase wraps first, then log_call wraps the already-decorated function.

Built-in Decorators You Already Know

Python ships with several built-in decorators:

# @property — turn a method into an attribute
class Temperature:
    def __init__(self, celsius):
        self.celsius = celsius

    @property
    def fahrenheit(self):
        return self.celsius * 9/5 + 32

t = Temperature(100)
print(t.fahrenheit)  # 212.0 — no parentheses!

# @staticmethod — no access to instance or class
class Math:
    @staticmethod
    def add(a, b):
        return a + b

# @classmethod — receives the class as first argument
class Config:
    DEBUG = False

    @classmethod
    def production(cls):
        return cls()

# @functools.cache — simple caching (Python 3.9+)
from functools import cache

@cache
def expensive_computation(n):
    return sum(range(n))

# @dataclasses.dataclass — auto-generate class boilerplate
from dataclasses import dataclass

@dataclass
class Point:
    x: float
    y: float

p = Point(3, 4)  # Creates __init__, __repr__, __eq__ automatically

Class-Based Decorators

For complex decorators with state, use a class instead of a function:

class CountCalls:
    """A class-based decorator that counts how many times a function is called."""

    def __init__(self, func):
        self.func = func
        self.count = 0
        self.__name__ = func.__name__

    def __call__(self, *args, **kwargs):
        self.count += 1
        print(f"  {self.func.__name__} called {self.count} time(s)")
        return self.func(*args, **kwargs)

@CountCalls
def hello():
    print("Hello!")

hello()  # Hello! / hello called 1 time(s)
hello()  # Hello! / hello called 2 time(s)
hello()  # Hello! / hello called 3 time(s)

Class decorators use __init__ to receive the function and __call__ to make the instance callable. The instance itself acts as the wrapper.

Summary: Decorator Cheat Sheet

Decorator What It Does When to Use
@timer Measure execution time Profiling, performance debugging
@cache / @lru_cache Remember previous results Expensive pure functions, recursive algorithms
@retry Retry on failure with backoff Network calls, unreliable APIs
@validate Check arguments before execution API endpoints, user input processing
@property Method that looks like an attribute Computed properties, getters with logic
@wraps(func) Preserve function metadata Inside every custom decorator

Final Tips

  • Always use @functools.wraps to preserve function metadata
  • Use *args, **kwargs in wrappers to accept any function signature
  • Stack decorators bottom-to-top — order matters
  • Prefer @lru_cache from standard library over manual caching
  • For complex stateful decorators, consider class-based approach
  • Keep decorators single-purpose — one decorator, one responsibility

Decorators are Python's answer to the "separation of concerns" principle. Instead of scattering logging, timing, and error handling into every function, you pull that logic out into reusable decorators. Your core functions stay clean and focused on their actual job.
