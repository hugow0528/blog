Terraform State & Remote Backends: Team-Friendly Infrastructure

2026-06-25 10 min read New

In our Terraform Basics guide, you learned to define and provision infrastructure. But as soon as you start working with a team or managing real production systems, one concept becomes critical: Terraform state. State is Terraform's memory — it maps your code to real cloud resources. Lose or corrupt it, and you lose the ability to manage your infrastructure safely.

This guide covers everything you need to know about state management, remote backends, locking, and making Terraform work for teams.

1. What Is Terraform State?

When you run terraform apply, Terraform creates a state file called terraform.tfstate. This JSON file records:

  • Resource IDs — the actual cloud resource identifiers (AWS instance IDs, DNS record IDs, etc.)
  • Current attributes — what the real resource looks like right now (IP addresses, DNS names, etc.)
  • Dependency graph — which resources depend on which

Why does Terraform need this? Because every time you run plan or apply, it compares your configuration against the actual state of cloud resources. Without the state file, Terraform wouldn't know which EC2 instance belongs to your aws_instance.web resource.

# Example: What state actually stores (simplified)
{
  "version": 4,
  "resources": [
    {
      "type": "aws_instance",
      "name": "web",
      "provider": "provider[\"registry.terraform.io/hashicorp/aws\"]",
      "instances": [
        {
          "attributes": {
            "id": "i-0abc123def456",
            "public_ip": "54.123.45.67",
            "ami": "ami-0abcdef1234567890",
            "instance_type": "t3.micro"
          }
        }
      ]
    }
  ]
}
⚠️ Never edit the state file manually. Use terraform state commands instead. Hand-editing can corrupt your infrastructure mapping.

2. The Problem with Local State

By default, Terraform stores terraform.tfstate on your local machine. This causes three major problems:

  • Not shareable — only one person can manage the infrastructure
  • No locking — two people running apply simultaneously can corrupt state
  • No backup — delete the file or lose your laptop, and you can't manage your resources

3. Remote Backends: Share State Across a Team

A remote backend stores state in a shared, durable location. The most common setup uses AWS S3 for storage and DynamoDB for locking:

# backend.tf
terraform {
  backend "s3" {
    bucket         = "my-terraform-state-bucket"
    key            = "prod/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "terraform-locks"
    encrypt        = true
  }
}

What each setting does:

  • bucket — the S3 bucket that stores the state file
  • key — the path within the bucket (use prefixes like prod/ or staging/ to separate environments)
  • dynamodb_table — enables state locking so only one person can apply at a time
  • encrypt — encrypts state at rest (ALWAYS enable this)

Setting Up the Backend Infrastructure

You need to create the S3 bucket and DynamoDB table first. Here's the Terraform code:

# backend_setup.tf
resource "aws_s3_bucket" "terraform_state" {
  bucket = "my-terraform-state-bucket"

  # Critical: prevent accidental deletion
  lifecycle {
    prevent_destroy = true
  }
}

# Enable versioning — lets you restore previous state if something goes wrong
resource "aws_s3_bucket_versioning" "terraform_state" {
  bucket = aws_s3_bucket.terraform_state.id
  versioning_configuration {
    status = "Enabled"
  }
}

# Enable server-side encryption
resource "aws_s3_bucket_server_side_encryption_configuration" "terraform_state" {
  bucket = aws_s3_bucket.terraform_state.id
  rule {
    apply_server_side_encryption_by_default {
      sse_algorithm = "aws:kms"
    }
  }
}

# Prevent public access
resource "aws_s3_bucket_public_access_block" "terraform_state" {
  bucket = aws_s3_bucket.terraform_state.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

# DynamoDB table for state locking
resource "aws_dynamodb_table" "terraform_locks" {
  name         = "terraform-locks"
  billing_mode = "PAY_PER_REQUEST"
  hash_key     = "LockID"

  attribute {
    name = "LockID"
    type = "S"
  }
}

4. Initializing and Migrating State

After adding the backend block, you need to initialize and migrate your existing state:

# Step 1: Initialize with the new backend
terraform init

# Terraform detects the backend change and asks:
# "Do you want to copy existing state to the new backend?"
# Type: yes

# Step 2: Verify state was migrated
terraform state list

# Step 3: Remove local state file (it's now remote)
rm terraform.tfstate terraform.tfstate.backup

5. State Locking: Preventing Corrupted State

State locking prevents two people (or two CI/CD pipelines) from running terraform apply simultaneously. When using DynamoDB as a backend, locking happens automatically.

When a lock is active and someone else tries to apply:

Error: Error acquiring the state lock
Lock Info:
  ID:        a1b2c3d4-...
  Path:      my-terraform-state-bucket/prod/terraform.tfstate
  Operation: OperationTypeApply
  Who:       alice@company.com
  Version:   1.6.6
  Created:   2026-06-25 10:30:00 +0000 UTC
  Info:      ...

What to do if you see a stale lock:

# Force unlock only if you're sure the previous operation failed
terraform force-unlock a1b2c3d4-...

# NEVER force-unlock while someone is actively applying!

6. Working with State: Essential Commands

You'll need these commands regularly. Here's a practical guide:

# List all resources in state
terraform state list
# Output:
#   aws_instance.web
#   aws_s3_bucket.data
#   aws_security_group.web_sg

# Inspect a specific resource's details
terraform state show aws_instance.web

# Move a resource to a new address (after renaming in code)
terraform state mv aws_instance.web_server aws_instance.web

# Remove a resource from state (e.g., you manage it manually now)
terraform state rm aws_s3_bucket.orphan_bucket

# Import an existing cloud resource into Terraform state
# (Resource must be defined in code first!)
terraform import aws_instance.existing i-0abc123def456

Practical Import Example

Suppose you already have an AWS instance and want to manage it with Terraform:

# Step 1: Add the resource definition to your code
resource "aws_instance" "imported" {
  ami           = "ami-0abcdef1234567890"
  instance_type = "t3.micro"
  tags = {
    Name = "imported-server"
  }
}

# Step 2: Import the real resource into state
terraform import aws_instance.imported i-0abc123def456

# Step 3: Run plan to see if there are any differences
terraform plan
# If there are differences, update your code to match reality

7. Keeping Secrets Out of State

State files can contain sensitive values (passwords, API keys, private IPs). Even with encryption, follow these best practices:

# Mark values as sensitive
resource "aws_db_instance" "main" {
  username = "admin"
  password = var.db_password  # Reference a variable

  # Prevent the value from showing in plan/apply output
}

# In your variables.tf
variable "db_password" {
  type      = string
  sensitive = true  # Hides value from output
}

Additional security measures:

  • Enable server-side encryption (SSE-S3 or SSE-KMS) on your S3 backend
  • Restrict S3 bucket access with IAM policies
  • Enable S3 access logging to audit who reads the state
  • Never commit terraform.tfstate to Git (add to .gitignore)

8. Multiple Environments with Workspaces

Terraform workspaces let you manage multiple environments (dev, staging, prod) with the same code:

# Create workspaces
terraform workspace new dev
terraform workspace new staging
terraform workspace new prod

# Switch between workspaces
terraform workspace select dev

# List workspaces
terraform workspace list
#   dev
# * staging
#   prod

# Use workspace name in your backend key
terraform {
  backend "s3" {
    bucket = "my-terraform-state-bucket"
    key    = "terraform/${workspace}/terraform.tfstate"
    region = "us-east-1"
  }
}

# Use workspace in resource configuration
resource "aws_instance" "web" {
  instance_type = var.instance_type
  tags = {
    Name      = "web-${terraform.workspace}"
    Environment = terraform.workspace
  }
}

Now each workspace maintains its own state, so dev, staging, and prod resources are completely separate.

9. State File Structure for Large Teams

For bigger organizations, organize state files like this:

my-terraform-state-bucket/
├── network/
│   ├── dev/terraform.tfstate
│   ├── staging/terraform.tfstate
│   └── prod/terraform.tfstate
├── web-app/
│   ├── dev/terraform.tfstate
│   ├── staging/terraform.tfstate
│   └── prod/terraform.tfstate
└── database/
    ├── dev/terraform.tfstate
    └── prod/terraform.tfstate

Key principle: Split state by team or service, not by resource type. If two people frequently change the same resources together, they should share a state file.

Common Pitfalls & Fixes

  • "State file is out of date" → Run terraform refresh to sync with cloud reality
  • "Resource not found in state" → Run terraform import to bring it into state
  • Stale DynamoDB lock → Wait for the operation to finish, or force-unlock if it truly hung
  • Corrupted state → Restore from S3 versioning (previous versions are saved automatically)

Summary

Terraform state is the bridge between your code and your real infrastructure. Proper state management means:

  1. Always use a remote backend — S3 + DynamoDB is the gold standard
  2. Enable versioning and encryption on your state bucket
  3. Use state locking to prevent concurrent modifications
  4. Organize by team/service with workspaces or separate directories
  5. Never commit state to Git
  6. Mark sensitive values and restrict backend access

Get these right, and Terraform scales beautifully from solo projects to enterprise infrastructure.
