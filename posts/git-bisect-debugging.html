Git Bisect: Binary Search Through Your Commit History

July 5, 2026 · 9 min read

A bug appeared in production. The feature worked last week, but today it's broken. You have 83 commits between the working version and the broken one. Which commit introduced the regression?

Checking each commit one by one would take forever. Git has a built-in superpower for this: git bisect. It uses binary search to find the exact commit that introduced a bug in logarithmic time — 83 commits down to the culprit in about 7 steps.

That's not magic — it's math. log₂(83) ≈ 6.4. Git bisect cuts your search space in half each iteration. Instead of 83 checks, you need at most 7.

How Git Bisect Works

The algorithm is simple:

  1. You tell Git which commit is good (working) and which is bad (broken)
  2. Git checks out a commit roughly halfway between them
  3. You test and tell Git whether it's good or bad
  4. Git halves the remaining range and repeats
  5. When the range is one commit, Git names it as the first bad commit

Think of it like the "Guess the Number" game, where Git guesses and you answer "too high" or "too low." Git just happens to be incredibly fast at narrowing down.

Manual Bisect Step by Step

Let's walk through a real scenario. You know the bug was introduced somewhere in the last 2 weeks. Let's start:

# Step 1: Start bisect
git bisect start

# Step 2: Mark current (broken) state as bad
git bisect bad

# Step 3: Mark a known-good commit as good
# Could be a tag, a specific commit hash, or a branch
git bisect good v1.2.0
# or: git bisect good abc1234
# or: git bisect good main~20

Git immediately checks out a commit in the middle:

git bisect start
git bisect bad
git bisect good v1.2.0

Bisecting: 41 revisions left to test after this (roughly 6 steps)
[7f3a9b2e8c1d] Add pagination to user list API

Git says "41 revisions left, roughly 6 steps." That means from 83 commits, we're already down to a 6-step process. Now you test your code at this commit:

# Run your test or check the feature
python -m pytest tests/test_user_api.py
# or: curl http://localhost:8000/api/users | jq .

If the test passes (feature works):

git bisect good

If the test fails (feature broken):

git bisect bad

Git moves to the next midpoint:

Bisecting: 20 revisions left to test after this (roughly 4 steps)
[2e1b4c7d8a9f] Refactor authentication middleware

Repeat until Git finds the culprit:

git bisect good    # or bad
git bisect good    # or bad
git bisect bad     # or good
git bisect good    # or bad
git bisect bad     # or good
git bisect bad

# Git narrows it down...
Bisecting: 0 revisions left to test after this (roughly 0 steps)
[3c9d5e7f1a2b] Fix date formatting in user profile

git bisect good

3c9d5e7f1a2b is the first bad commit
commit 3c9d5e7f1a2b
Author: Dev Person <dev@example.com>
Date:   Mon Jun 28 14:22:03 2026

    Fix date formatting in user profile
    
    The change to utils.format_date() accidentally broke
    the comparison logic in the date range filter...

There it is. The exact commit. You can now see the diff, understand the mistake, and create a proper fix.

Clean Up After Bisect

When bisect is done, always return to your original branch:

git bisect reset

This restores your working directory to the branch and commit you were on before starting bisect. Forgetting this step is the #1 beginner mistake — you'll think you're on main but you're actually on some random commit in the middle of history.

Automated Bisect with a Test Script

The manual process works, but running tests after each checkout is tedious. Git bisect can automate this with git bisect run:

git bisect start
git bisect bad
git bisect good v1.2.0

# Run automatically with a test command
# Exit code 0 = good, 1-125 = bad, 125 = skip
git bisect run python -m pytest tests/test_user_api.py

That's it. Git will:

  1. Checkout each midpoint commit
  2. Run your test command
  3. Interpret the exit code (0 = good, non-zero = bad)
  4. Continue bisecting automatically
  5. Report the first bad commit
  6. Reset back to your original branch

The entire process takes seconds for most projects. Here's the full output:

git bisect run python -m pytest tests/test_user_api.py

running 'python -m pytest tests/test_user_api.py'
Bisecting: 41 revisions left to test after this (roughly 6 steps)
[7f3a9b2e8c1d] Add pagination...
running 'python -m pytest tests/test_user_api.py'
Bisecting: 20 revisions left to test after this (roughly 4 steps)
...
Bisecting: 0 revisions left to test after this (roughly 0 steps)
[3c9d5e7f1a2b] Fix date formatting...
running 'python -m pytest tests/test_user_api.py'
3c9d5e7f1a2b is the first bad commit
commit 3c9d5e7f1a2b
Author: Dev Person <dev@example.com>
...
bisect found first bad commit

Advanced: Shell Script for Complex Tests

Some bugs require more than a single test command. You might need to install dependencies, build the project, or run a server. Create a shell script:

#!/bin/bash
# scripts/bisect_test.sh

# Install dependencies for this commit
pip install -r requirements.txt

# Build if needed
# npm run build  (for frontend projects)

# Run the test
python -m pytest tests/test_user_api.py -x
# The exit code of this command determines good/bad
chmod +x scripts/bisect_test.sh
git bisect run ./scripts/bisect_test.sh

Exit Code Rules

When using git bisect run, the exit code of your command determines Git's behavior:

Exit code 0   → commit is GOOD
Exit code 1-125 → commit is BAD
Exit code 125  → SKIP this commit (can't test it)

Use Skip when a commit won't even compile or has missing dependencies. Git will work around it:

#!/bin/bash
# scripts/bisect_smart.sh
set -e

# Try to install deps
if ! pip install -r requirements.txt 2>/dev/null; then
    echo "Cannot install deps, skipping"
    exit 125  # Skip
fi

# Try to run tests
python -m pytest tests/test_user_api.py -x
exit_code=$?

if [ $exit_code -eq 0 ]; then
    exit 0  # Good
else
    exit 1  # Bad
fi

Real-World Example: Finding a Performance Regression

Bisect isn't just for bugs — it works for performance regressions too. Let's say your API went from 50ms to 500ms response time:

#!/bin/bash
# scripts/bisect_perf.sh

# Install deps
pip install -r requirements.txt

# Start server in background
python app.py &
SERVER_PID=$!
sleep 2

# Measure response time
RESPONSE_TIME=$(curl -s -o /dev/null -w "%{time_total}" \
    http://localhost:8000/api/users)

# Kill server
kill $SERVER_PID 2>/dev/null

# If response takes more than 200ms, it's bad
echo "Response time: ${RESPONSE_TIME}s"
if (( $(echo "$RESPONSE_TIME > 0.2" | bc -l) )); then
    echo "SLOW - marking as bad"
    exit 1
else
    echo "FAST - marking as good"
    exit 0
fi
git bisect run bash scripts/bisect_perf.sh

Git finds the exact commit where performance degraded. Maybe it was a change from SELECT * to fetching all records, or adding a synchronous HTTP call in the request path.

Common Gotchas

1. Dependencies Changed Between Commits

If requirements.txt changed, your bisect test might fail for the wrong reason. Always reinstall dependencies at each step (as shown in the scripts above).

2. The Bug Only Happens After Merge

Some bugs appear only when two branches merge. In this case, bisect might not find a single "bad" commit because the bug doesn't exist on either branch alone. Try bisecting a specific branch that contains the regression.

3. Forgetting git bisect reset

This puts you in a detached HEAD state. You can still commit, but those commits won't belong to any branch. Always reset when done.

4. The Range Is Too Broad

If you bisect from a year ago, Git has to handle thousands of commits. Use a narrower range when you roughly know when the bug appeared:

# Bisect only the last 30 commits
git bisect start HEAD HEAD~30
git bisect bad HEAD
git bisect good HEAD~30

Pro Tips

  • Use tags as good markers: Release tags (v1.0.0, v1.1.0) are reliable "known good" points. They represent tested, deployed code.
  • Combine with git log --oneline: Before starting, review recent commits to pick a smart "good" point: git log --oneline -30
  • Bisect multiple bugs: If you found commit A caused bug 1 and commit B caused bug 2, you can bisect again from the same starting point.
  • Use --first-parent: To follow only the main branch history, skipping feature branch noise: git bisect start --first-parent

Summary

Git bisect is one of those tools you'll never use... until you need it desperately. Then it becomes your best friend.

The workflow is simple:

git bisect start
git bisect bad           # current state is broken
git bisect good v1.2.0   # this tag was working
git bisect run ./test.sh # automated testing
git bisect reset         # return to normal

83 commits narrowed to 1 in 7 steps. That's the power of binary search. Next time a bug appears, don't guess — bisect.
