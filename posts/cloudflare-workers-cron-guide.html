Cloudflare Workers Cron Triggers: Serverless Scheduled Jobs — Complete Beginner's Guide

July 15, 2026 10 min read

What Are Cloudflare Workers Cron Triggers?

Cloudflare Workers Cron Triggers let you schedule your Workers scripts to run automatically at specified intervals — without managing servers, cron daemons, or background processes. Think of them as "serverless cron jobs" that run on Cloudflare's global edge network. Free tier gives you daily triggers, and paid plans unlock minute-level scheduling.

Unlike traditional cron that runs on a single server, Workers Cron executes your code at the edge — meaning your scheduled task starts in milliseconds, anywhere in the world. No cold starts, no server to maintain, no uptime to worry about.

How Cron Triggers Work

A Workers Cron Trigger is configured in your wrangler.toml file. When the scheduled time arrives, Cloudflare sends your Worker a scheduled event instead of a fetch event. Your code checks event.type to distinguish between HTTP requests and cron triggers:

export default {
    async fetch(request, env, ctx) {
        // Normal HTTP request handling
        return new Response("Hello from the Worker!");
    },

    async scheduled(event, env, ctx) {
        // Cron trigger — runs on schedule
        console.log("Cron triggered at:", new Date().toISOString());
        await runDailyCleanup(env);
        return new Response("Cron job completed!");
    }
};

Configuring Cron Schedules

Cron expressions use standard Unix cron syntax. Add your schedule to wrangler.toml:

[triggers]
crons = ["0 9 * * *", "*/15 * * * *", "0 0 * * 0"]

This configures three schedules:

  • 0 9 * * * — Every day at 9:00 AM UTC
  • */15 * * * * — Every 15 minutes (Business plan)
  • 0 0 * * 0 — Every Sunday at midnight UTC

Free tier supports daily triggers only (0 9 * * *). Paid plans (Pro/Business/Enterprise) unlock hourly, minute-level, and even sub-minute scheduling.

Deploying Your Cron Worker

Deploy with Wrangler CLI:

Real-World Example: Daily Database Cleanup

Here's a complete example that cleans expired records from a D1 database every morning:

export default {
    async scheduled(event, env, ctx) {
        const cutoff = new Date();
        cutoff.setDate(cutoff.getDate() - 30); // 30 days ago
        const cutoffStr = cutoff.toISOString();

        try {
            const result = await env.DB.prepare(
                "DELETE FROM sessions WHERE created_at < ?"
            ).bind(cutoffStr).run();

            console.log(`Deleted ${result.meta.changes} expired sessions`);

            // Optional: log to KV for monitoring
            await env.METRICS.put(
                `cleanup-${new Date().toISOString().split('T')[0]}`,
                JSON.stringify({ deleted: result.meta.changes })
            );
        } catch (err) {
            console.error("Cleanup failed:", err);
            // Retry logic or alerting would go here
        }
    }
};

Real-World Example: Health Check Monitor

Monitor external services by pinging them on a schedule:

const ENDPOINTS = [
    { name: "API", url: "https://api.example.com/health" },
    { name: "Web", url: "https://www.example.com" },
    { name: "Docs", url: "https://docs.example.com" }
];

export default {
    async scheduled(event, env, ctx) {
        const results = [];

        for (const endpoint of ENDPOINTS) {
            const start = Date.now();
            let status = "down";

            try {
                const resp = await fetch(endpoint.url, {
                    method: "GET",
                    cf: {
                        timeout: 10000 // 10 second timeout
                    }
                });
                const duration = Date.now() - start;
                status = resp.status === 200 ? "up" : `error_${resp.status}`;
            } catch (err) {
                status = "error";
            }

            results.push({ name: endpoint.name, status });

            if (status !== "up") {
                // Send alert via webhook
                await fetch("https://alerts.example.com/webhook", {
                    method: "POST",
                    headers: { "Content-Type": "application/json" },
                    body: JSON.stringify({
                        service: endpoint.name,
                        status,
                        timestamp: new Date().toISOString()
                    })
                });
            }
        }

        console.log("Health checks:", JSON.stringify(results));
    }
};

Error Handling and Retry Patterns

Cron triggers don't auto-retry on failure. Implement your own retry logic:

async function withRetry(fn, maxAttempts = 3, delayMs = 1000) {
    for (let attempt = 1; attempt <= maxAttempts; attempt++) {
        try {
            return await fn();
        } catch (err) {
            if (attempt === maxAttempts) throw err;
            console.warn(`Attempt ${attempt} failed, retrying...`);
            await new Promise(r => setTimeout(r, delayMs * attempt)); // exponential backoff
        }
    }
}

export default {
    async scheduled(event, env, ctx) {
        try {
            await withRetry(async () => {
                await env.DB.prepare("VACUUM").run();
            });
        } catch (err) {
            // Log to KV for later inspection
            await env.LOGS.put(
                `error-${Date.now()}`,
                JSON.stringify({ error: err.message, timestamp: new Date().toISOString() })
            );
        }
    }
};

Using ctx.waitUntil() for Background Work

Use ctx.waitUntil() to run async operations after the response returns — useful for long-running tasks:

export default {
    async scheduled(event, env, ctx) {
        // Return response immediately
        const promise = heavyBackgroundWork(env);
        ctx.waitUntil(promise);
        return new Response("Scheduled task started");
    }
};

Best Practices

  • Idempotency: Design jobs to be safe to run twice — clock drift can cause double execution
  • Timeout awareness: Free Workers timeout at 10s (HTTP) / 15min (streaming). Use Durable Objects or Queues for longer work
  • Logging: Write results to KV, D1, or an external service — console.log only goes to Cloudflare logs
  • Timezones: Cron schedules use UTC. Adjust your cron expression for local times
  • Rate limits: Your cron Worker still counts toward overall API rate limits if it calls external services

Monitoring Your Cron Jobs

Track execution in the Cloudflare Dashboard under Workers & Pages → your worker → Cron Triggers. You can view:

  • Last invocation time and duration
  • Error logs
  • Schedule configuration

Common Use Cases

Here are popular patterns for Workers Cron:

  • Data aggregation: Compile analytics daily from R2 or KV data
  • Cache warming: Pre-fetch expensive API responses on a schedule
  • Database maintenance: VACUUM, delete expired rows, archive old data
  • Notifications: Send daily/weekly email digests
  • Webhook retries: Poll failed webhook deliveries and retry
  • Report generation: Build and email PDF reports from D1 data

Summary

Cloudflare Workers Cron Triggers provide a dead-simple way to schedule tasks on the edge. No servers to manage, no cron daemon to configure — just write code, set a schedule in wrangler.toml, and deploy. Combine with KV for state, D1 for structured data, and Queues for background work to build powerful automation workflows.
