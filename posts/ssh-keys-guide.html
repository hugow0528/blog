SSH Keys: Secure Git, Servers, and Cloud Access — Complete Beginner's Guide

July 10, 2026 11 min read

SSH (Secure Shell) keys are the foundation of secure, passwordless access to remote servers, Git repositories, and cloud platforms. Instead of typing a password every time you push code or log into a server, SSH keys use cryptographic authentication — faster, more secure, and essential for automation. This guide walks you through everything from generating your first key to advanced SSH configuration.

1. What Are SSH Keys?

SSH keys come in pairs: a private key (kept secret on your machine) and a public key (shared with servers you want to access). When you connect to a server:

  1. The server sends a challenge encrypted with your public key
  2. Your private key decrypts the challenge and proves your identity
  3. The server verifies the response and grants access

This is more secure than passwords because:

  • The private key never leaves your machine
  • Keys are resistant to brute-force attacks
  • Each key can be named, scoped, and revoked independently

2. Generating Your First SSH Key

Check if you already have keys:

# List existing SSH keys
ls -la ~/.ssh/

ed25519 (Recommended)

The Ed25519 algorithm is the modern default — smaller keys, faster, and more secure:

# Generate an Ed25519 key
ssh-keygen -t ed25519 -C "your_email@example.com"

# You'll be prompted:
# Enter file in which to save the key (/home/user/.ssh/id_ed25519):
#   → Press Enter for default
# Enter passphrase (empty for no passphrase):
#   → Set a strong passphrase!
# Enter same passphrase again:
#   → Confirm it

RSA (Legacy)

Use RSA only if you need compatibility with older systems:

# Generate an RSA key with 4096 bits
ssh-keygen -t rsa -b 4096 -C "your_email@example.com"

Project-Specific Keys

For better organization, generate separate keys per project:

# Key for a specific project
ssh-keygen -t ed25519 -C "work@example.com" -f ~/.ssh/id_work

# Key for GitHub
ssh-keygen -t ed25519 -C "personal@example.com" -f ~/.ssh/id_github

# Key for a cloud server
ssh-keygen -t ed25519 -C "deploy@example.com" -f ~/.ssh/id_deploy

Your private key (id_ed25519) stays secret. Your public key (id_ed25519.pub) is what you share:

# View your public key
cat ~/.ssh/id_ed25519.pub
# ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAA... your_email@example.com

3. Managing Keys with ssh-agent

SSH agent stores your decrypted private keys in memory so you don't have to type your passphrase every time:

# Start the SSH agent (usually auto-started on Linux/Mac)
eval "$(ssh-agent -s)"

# Add your key to the agent
ssh-add ~/.ssh/id_ed25519

# List keys currently in the agent
ssh-add -l

# Remove a key from the agent
ssh-add -d ~/.ssh/id_ed25519

# Remove all keys
ssh-add -D

On most modern systems (macOS, recent Linux), the SSH agent starts automatically. On macOS, keys are automatically loaded into the secure enclave when you authenticate.

4. Setting Up SSH with GitHub

Add your public key to GitHub:

# 1. Copy your public key to clipboard
# Linux:
clip < ~/.ssh/id_ed25519.pub
# Or:
xclip -selection clipboard < ~/.ssh/id_ed25519.pub

# macOS:
pbcopy < ~/.ssh/id_ed25519.pub

# 2. Go to GitHub → Settings → SSH and GPG keys → New SSH key
# 3. Paste the key and save

# 3. Test the connection
ssh -T git@github.com
# Hi username! You've successfully authenticated...

Now clone repositories using SSH instead of HTTPS:

# HTTPS (requires password/token)
git clone https://github.com/user/repo.git

# SSH (uses your SSH key)
git clone git@github.com:user/repo.git

5. SSH Config File — Your Power Tool

The ~/.ssh/config file lets you define shortcuts and custom settings for each host. This is where SSH becomes truly powerful:

# ~/.ssh/config

# Default settings for all connections
Host *
    AddKeysToAgent yes
    UseKeychain yes          # macOS: use keychain
    ServerAliveInterval 60
    ServerAliveCountMax 3
    IdentitiesOnly yes

# GitHub — use specific key
Host github.com
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_github
    IdentitiesOnly yes

# Personal server shortcut
Host myserver
    HostName 192.168.1.100
    User deploy
    Port 22
    IdentityFile ~/.ssh/id_deploy

# Cloud server with different port
Host cloud
    HostName cloud.example.com
    User ubuntu
    Port 2222
    IdentityFile ~/.ssh/id_cloud

# AWS EC2 instance
Host my-ec2
    HostName ec2-12-34-56-78.compute-1.amazonaws.com
    User ec2-user
    IdentityFile ~/.ssh/aws_key.pem
    IdentitiesOnly yes

# Proxy through a bastion/jump host
Host internal-server
    HostName 10.0.1.50
    User admin
    ProxyJump bastion
    IdentityFile ~/.ssh/id_internal

Host bastion
    HostName bastion.example.com
    User jumpuser
    IdentityFile ~/.ssh/id_bastion

Now you can use these shortcuts:

# Instead of this:
ssh -i ~/.ssh/id_deploy -p 22 deploy@192.168.1.100

# Use this:
ssh myserver

# Or for Git, add to ~/.gitconfig:
# [url "git@github.com:"]
#     insteadOf = https://github.com/

6. Setting Up SSH on a Remote Server

To enable key-based login on a server:

# 1. Copy your public key to the server
ssh-copy-id deploy@192.168.1.100

# Or manually:
cat ~/.ssh/id_ed25519.pub | ssh deploy@192.168.1.100 "mkdir -p ~/.ssh && cat >> ~/.ssh/authorized_keys"

# 2. Verify you can log in without a password
ssh deploy@192.168.1.100

# 3. Harden SSH — edit /etc/ssh/sshd_config on the server:
#    sudo nano /etc/ssh/sshd_config

# Recommended settings in sshd_config:
# PasswordAuthentication no
# PermitRootLogin no
# PubkeyAuthentication yes
# AllowUsers deploy
# Port 2222              # Non-standard port
# MaxAuthTries 3
# ClientAliveInterval 300
# ClientAliveCountMax 2

# 4. Restart SSH service
sudo systemctl restart sshd

7. SSH Security Best Practices

File Permissions

# Private keys must be readable only by you
chmod 700 ~/.ssh
chmod 600 ~/.ssh/id_*
chmod 644 ~/.ssh/id_*.pub
chmod 600 ~/.ssh/config

# authorized_keys on server
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys

Use Passphrases

Always protect your private key with a passphrase. The SSH agent handles it for you, so there's no inconvenience:

# Change passphrase on an existing key
ssh-keygen -p -f ~/.ssh/id_ed25519

# Generate new key with passphrase
ssh-keygen -t ed25519 -C "you@example.com"
# When prompted, enter a strong passphrase

Key Restriction with authorized_keys

Restrict what a key can do on the server:

# In ~/.ssh/authorized_keys on the server, add restrictions:

# Only allow specific command (e.g., for git)
command="/usr/bin/git-shell" ssh-ed25519 AAAA...

# Restrict to specific IPs
from="192.168.1.0/24" ssh-ed25519 AAAA...

# No port forwarding, no X11, no agent forwarding
no-port-forwarding,no-X11-forwarding,no-agent-forwarding ssh-ed25519 AAAA...

# Combined restrictions
from="10.0.0.0/8",command="/usr/local/bin/deploy.sh",no-port-forwarding ssh-ed25519 AAAA...

8. SSH Tunneling and Port Forwarding

Local Port Forwarding

Access a service on the remote server through your local machine:

# Access remote PostgreSQL locally
ssh -L 5432:localhost:5432 myserver
# Now connect to localhost:5432 locally → goes to myserver:5432

# Access a web dashboard behind a firewall
ssh -L 8080:localhost:8080 myserver
# Open http://localhost:8080 in your browser

Remote Port Forwarding

Expose a local service through the remote server (useful for ngrok-like setups):

# Expose your local dev server on port 3000
ssh -R 8080:localhost:3000 myserver
# Anyone with access to myserver can reach your local dev at myserver:8080

Dynamic Port Forwarding (SSH SOCKS Proxy)

# Create a SOCKS proxy through a remote server
ssh -D 1080 myserver
# Configure your browser to use SOCKS proxy at localhost:1080
# All browser traffic routes through the remote server

9. SSH Agent Forwarding

Use your local SSH keys from a remote server (e.g., deploy from a CI server using your GitHub key):

# Enable agent forwarding for a specific host in ~/.ssh/config
Host myserver
    ForwardAgent yes

# Then SSH to your server
ssh myserver

# From the server, you can now use your LOCAL GitHub key:
git clone git@github.com:user/private-repo.git

Warning: Agent forwarding gives the remote server access to your keys. Only use it on trusted servers. Prefer deployment keys or SSH certificates for production.

10. Troubleshooting Common Issues

"Permission denied (publickey)"

# Debug SSH connection (run locally)
ssh -vT git@github.com
# Look for the line that says which key it's trying

# Make sure the correct key is in your agent
ssh-add -l

# Try specifying the key explicitly
ssh -i ~/.ssh/id_github -T git@github.com

# Check file permissions
ls -la ~/.ssh/
# Private key should be 600, not 644

"Host key verification failed"

# The server's fingerprint changed — common after server rebuild
# Check the current fingerprint
ssh-keyscan -H github.com >> ~/.ssh/known_hosts

# Or remove the old entry
ssh-keygen -R github.com

# Then reconnect
ssh -T git@github.com

Multiple Keys — Wrong Key Sent

# Force which key to use
ssh -i ~/.ssh/id_github git@github.com

# Or configure in ~/.ssh/config (recommended)
Host github.com
    IdentityFile ~/.ssh/id_github
    IdentitiesOnly yes    # Don't try other keys

Summary

SSH keys are essential for secure, efficient remote access. Here's the quick checklist:

  • Generate: Use ssh-keygen -t ed25519 with a passphrase
  • Manage: Add keys to ssh-agent to avoid repeated passphrase entry
  • Configure: Use ~/.ssh/config for host shortcuts and per-host settings
  • Deploy: Copy public keys with ssh-copy-id or authorized_keys
  • Secure: Lock down permissions, disable password auth, restrict key capabilities
  • Advanced: Use port forwarding, agent forwarding, and proxy jumps as needed

Set up your SSH config early — it pays dividends every single time you connect to a server or push code. The ~/.ssh/config file is your most used dev tool after your editor.
