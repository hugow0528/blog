Docker Compose for Local Development: Multi-Container Setups Made Easy

July 2, 2026 · 10 min read

Imagine this: you join a new project and need to set up a web app, PostgreSQL database, and Redis cache. With Docker Compose, it takes one command. No manual installs, no configuration conflicts, no "works on my machine" excuses.

This guide covers everything you need to spin up complete development environments locally using docker-compose.yml files. We'll go from a single service to a full-stack setup with databases, caches, and hot-reloading code.

What Is Docker Compose?

Docker Compose is a tool for defining and running multi-container Docker applications. You describe your entire stack in a single YAML file, then start everything with one command:

docker compose up

Think of it as infrastructure code for your local machine. Your docker-compose.yml file becomes the source of truth for how all your services connect, share data, and talk to each other.

Install Docker Compose

Docker Desktop (Mac/Windows)

Compose comes bundled with Docker Desktop. Just install it from docker.com.

Linux

# Modern Docker (Compose is a plugin)
docker compose version

# Or install separately
sudo apt install docker-compose-plugin

Note: Modern Docker uses docker compose (space, no hyphen) as a built-in plugin. The old docker-compose (hyphenated standalone binary) is deprecated but still works.

Your First docker-compose.yml

Create a file called docker-compose.yml in your project root:

services:
  web:
    image: nginx:alpine
    ports:
      - "8080:80"

That's the minimal file. Three lines of config that spin up an Nginx server. Run it:

docker compose up
# [+] Running 1/1
#  ✔ Container web-started               0.5s

# Open http://localhost:8080 — you'll see Nginx welcome page

Stop it with Ctrl+C or run docker compose down from another terminal.

Adding a Database: PostgreSQL

Most apps need a database. Here's how to add PostgreSQL alongside your app:

services:
  web:
    image: nginx:alpine
    ports:
      - "8080:80"
    depends_on:
      - db

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: devuser
      POSTGRES_PASSWORD: devpass
      POSTGRES_DB: myapp
    ports:
      - "5432:5432"
    volumes:
      - postgres_data:/var/lib/postgresql/data

volumes:
  postgres_data:

Let's break this down:

  • depends_on: Ensures the database starts before the web service. This only waits for the container to start, not for the database to be ready.
  • environment: Passes credentials and database name to PostgreSQL. These are the standard Postgres environment variables.
  • ports: Maps host port 5432 to container port 5432. Now you can connect with your local database client (pgAdmin, DBeaver, etc.).
  • volumes: Persists database data. Without this, your data disappears when the container stops. The named volume postgres_data is declared at the bottom.

Real Example: Python App with Postgres and Redis

Here's a realistic development setup for a Python web application:

# docker-compose.yml
services:
  # Python web application
  app:
    build:
      context: .
      dockerfile: Dockerfile.dev
    ports:
      - "8000:8000"
    environment:
      DATABASE_URL: postgresql://devuser:devpass@db:5432/myapp
      REDIS_URL: redis://redis:6379/0
      FLASK_ENV: development
    volumes:
      - .:/app
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_started
    restart: unless-stopped

  # PostgreSQL database
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: devuser
      POSTGRES_PASSWORD: devpass
      POSTGRES_DB: myapp
    ports:
      - "5432:5432"
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U devuser -d myapp"]
      interval: 5s
      timeout: 3s
      retries: 5

  # Redis cache
  redis:
    image: redis:7-alpine
    ports:
      - "6379:6379"
    volumes:
      - redis_data:/data

volumes:
  postgres_data:
  redis_data:

And the Dockerfile.dev for the Python app:

# Dockerfile.dev
FROM python:3.12-slim

WORKDIR /app

# Install system dependencies
RUN apt-get update && apt-get install -y --no-install-recommends \
    gcc \
    libpq-dev \
    && rm -rf /var/lib/apt/lists/*

# Install Python dependencies
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Copy application code
COPY . .

# Expose the development server port
EXPOSE 8000

# Run with auto-reload for development
CMD ["flask", "run", "--host=0.0.0.0", "--reload"]

Key Concepts Explained

Healthchecks

The healthcheck on the database service tells Docker how to verify PostgreSQL is actually ready to accept connections. Combined with depends_on using condition: service_healthy, this ensures the app doesn't start until the database is truly ready:

db:
  healthcheck:
    test: ["CMD-SHELL", "pg_isready -U devuser -d myapp"]
    interval: 5s      # Check every 5 seconds
    timeout: 3s       # Wait up to 3 seconds for response
    retries: 5        # Try up to 5 times before marking unhealthy

Volume Mounting for Code Hot-Reload

The line volumes: - .:/app mounts your entire project directory into the container. When you edit files on your host machine, the changes appear instantly inside the container. Combined with Flask's --reload flag, this gives you live code updates without rebuilding the container.

Environment Variables as Configuration

Notice how DATABASE_URL uses db as the hostname, not localhost. Inside Docker Compose, each service can reach others by their service name. The web app connects to PostgreSQL at db:5432 and Redis at redis:6379 because Docker Compose sets up internal DNS automatically.

Using .env Files for Secrets

Never hardcode passwords in docker-compose.yml. Use .env files instead:

# .env (add to .gitignore!)
POSTGRES_USER=devuser
POSTGRES_PASSWORD=supersecret123
POSTGRES_DB=myapp
REDIS_PASSWORD=redispass
FLASK_SECRET_KEY=random-string-here
# docker-compose.yml
services:
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: ${POSTGRES_DB}

  app:
    environment:
      DATABASE_URL: postgresql://${POSTGRES_USER}:${POSTGRES_PASSWORD}@db:5432/${POSTGRES_DB}
      FLASK_SECRET_KEY: ${FLASK_SECRET_KEY}

Docker Compose automatically loads .env files and substitutes the variables. Your actual passwords never end up in version control.

Common Docker Compose Commands

# Start everything (foreground)
docker compose up

# Start in background (detached)
docker compose up -d

# Start and rebuild images
docker compose up --build

# Stop and remove containers
docker compose down

# Stop and also remove volumes (⚠️ deletes data!)
docker compose down -v

# View logs
docker compose logs
docker compose logs -f          # Follow (like tail -f)
docker compose logs app         # Logs for specific service

# Execute a command inside a running container
docker compose exec app python manage.py migrate
docker compose exec db psql -U devuser -d myapp

# Restart a single service
docker compose restart app

# Check container status
docker compose ps

# View resource usage
docker compose top

Profiles: Optional Services

Some services you only want in certain environments. Use profiles to conditionally start them:

services:
  app:
    image: myapp:dev
    ports:
      - "8000:8000"

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: devuser
      POSTGRES_PASSWORD: devpass

  # Only starts with: docker compose --profile admin up
  adminer:
    image: adminer
    ports:
      - "8081:8080"
    profiles:
      - admin
    depends_on:
      - db

  # Only starts with: docker compose --profile test up
  test_db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: testuser
      POSTGRES_PASSWORD: testpass
    profiles:
      - test
# Start everything except profiled services
docker compose up -d

# Start with Adminer for database management
docker compose --profile admin up -d

# Start with test database
docker compose --profile test up -d

Extending with override.yml

Share a base docker-compose.yml with your team, but customize it locally with docker-compose.override.yml:

# docker-compose.yml (committed to git)
services:
  app:
    build: .
    ports:
      - "8000:8000"
    environment:
      DEBUG: "false"

# docker-compose.override.yml (in .gitignore)
services:
  app:
    environment:
      DEBUG: "true"
    volumes:
      - .:/app
    ports:
      - "9000:8000"   # Different port for my machine

Docker Compose automatically merges the override file. You get team-shared config plus personal customization without touching the base file.

Troubleshooting Checklist

  • Container keeps crashing? Run docker compose logs app to see the error. Common issue: the app can't connect to the database because it hasn't finished starting.
  • Port already in use? Change the host port mapping: "9000:8000" instead of "8000:8000". Or stop the conflicting process with lsof -i :8000.
  • Can't connect to database from host? Make sure the ports section maps the database port. Without it, the database is only accessible from other containers.
  • Data disappeared after down/up? You probably used docker compose down -v. Named volumes persist between runs — only -v removes them.
  • Old image being used? Force rebuild: docker compose up --build or docker compose up --build --force-recreate.

Summary

Docker Compose turns your entire local development environment into code. One docker-compose.yml file gives every developer on the team the exact same setup — databases, caches, queues, whatever your app needs. The key patterns are:

  • Services — Each container is a service
  • Volumes — Persist data across container restarts
  • Environment variables — Configure services without rebuilding
  • Healthchecks — Wait for dependencies to be truly ready
  • Profiles — Optional services for specific needs
  • Override files — Personal customization without affecting the team
