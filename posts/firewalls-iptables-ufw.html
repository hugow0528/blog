What Is a Firewall?

A firewall is a security system that monitors and controls network traffic. Think of it as a bouncer at a club — it decides who gets in and who stays out based on a set of rules.

On a Linux server, the firewall sits between the network interface and your applications. Every packet of data that arrives (or leaves) must pass through the firewall's rules before it reaches your web server, database, or SSH daemon.

Without a firewall, your server is completely open to the internet. Any IP address can try to connect to any port. A properly configured firewall blocks everything except what you explicitly allow.

Why this matters: Most servers are scanned constantly by bots looking for open ports. A simple firewall rule set can block millions of unwanted connection attempts per day.

How Firewalls Work

Linux firewalls evaluate packets against rules in order. Each rule checks one or more attributes of the packet:

  • Source IP — where is the packet coming from?
  • Destination IP — where is it going?
  • Source port — which port on the sender?
  • Destination port — which port on the receiver?
  • Protocol — TCP, UDP, ICMP, etc.
  • Interface — which network interface?

When a packet matches a rule, the firewall takes an action:

  • ACCEPT — allow the packet through
  • DROP — silently discard the packet (the sender hears nothing)
  • REJECT — send an error back to the sender
  • LOG — log the packet for analysis

Rules are evaluated top to bottom. The first matching rule wins. If no rule matches, the chain's default policy applies.

Linux provides three firewall tools: iptables (the classic), UFW (simple wrapper), and nftables (modern replacement). Let's cover all three.

iptables Basics

iptables is the original Linux firewall tool. It's available on virtually every Linux distribution and forms the foundation that UFW and nftables build upon.

Here's the basic command structure:

iptables [-t table] ACTION CHAIN CRITERIA -j TARGET

Let's break this down with a real example. To allow incoming SSH connections:

# Allow incoming SSH (port 22) on TCP protocol
sudo iptables -A INPUT -p tcp --dport 22 -j ACCEPT

# Breakdown:
# -A INPUT     → Append to the INPUT chain
# -p tcp       → Match TCP protocol
# --dport 22   → Match destination port 22
# -j ACCEPT    → Jump to ACCEPT (allow the packet)

Each rule is a filter that checks packet attributes and takes an action. Let's explore the chains first, then build up to a complete rule set.

iptables Chains and Policies

iptables has three built-in chains for packet filtering:

  • INPUT — packets destined for the server itself (incoming connections)
  • FORWARD — packets passing through the server (routed traffic)
  • OUTPUT — packets leaving the server (outgoing connections)

Each chain has a default policy — what happens to packets that don't match any rule. The recommended setup:

# Set default policies: drop everything unless explicitly allowed
sudo iptables -P INPUT DROP
sudo iptables -P FORWARD DROP
sudo iptables -P OUTPUT ACCEPT

# Verify current policies
sudo iptables -L -v --line-numbers

Warning: Never set INPUT to DROP before adding at least an SSH rule! You'll lock yourself out of your server. Always add your allow rules first, then set the default policy to DROP.

Here's the safe order of operations:

# Step 1: Allow SSH so you don't get locked out
sudo iptables -A INPUT -p tcp --dport 22 -j ACCEPT

# Step 2: Allow other services you need
sudo iptables -A INPUT -p tcp --dport 80 -j ACCEPT    # HTTP
sudo iptables -A INPUT -p tcp --dport 443 -j ACCEPT   # HTTPS

# Step 3: Set default policy to DROP
sudo iptables -P INPUT DROP

Building iptables Rules

Here are the most common rule patterns you'll need:

Allow Established Connections (Essential)

When your server sends a request out, the response comes back on the same connection. You must allow these "established" connections or your outgoing requests will fail:

# Allow traffic that's part of an existing connection
sudo iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT

This is the first rule you should add to any INPUT chain. Without it, even simple tasks like DNS resolution or package updates break.

Allow Loopback Traffic

Your server needs to talk to itself via the loopback interface (lo):

# Allow all traffic on the loopback interface
sudo iptables -A INPUT -i lo -j ACCEPT
sudo iptables -A OUTPUT -o lo -j ACCEPT

Allow Specific Ports

# Allow HTTP (80) and HTTPS (443)
sudo iptables -A INPUT -p tcp --dport 80 -j ACCEPT
sudo iptables -A INPUT -p tcp --dport 443 -j ACCEPT

# Allow DNS (53) — both TCP and UDP
sudo iptables -A INPUT -p udp --dport 53 -j ACCEPT
sudo iptables -A INPUT -p tcp --dport 53 -j ACCEPT

# Allow a range of ports (e.g., 8000-8080 for dev servers)
sudo iptables -A INPUT -p tcp --dport 8000:8080 -j ACCEPT

Restrict SSH to Specific IPs

Instead of allowing SSH from anywhere, restrict it to your known IP addresses:

# Allow SSH only from your home IP
sudo iptables -A INPUT -p tcp -s 203.0.113.5 --dport 22 -j ACCEPT

# Allow SSH from multiple IPs (use multiple rules)
sudo iptables -A INPUT -p tcp -s 203.0.113.5 --dport 22 -j ACCEPT
sudo iptables -A INPUT -p tcp -s 198.51.100.10 --dport 22 -j ACCEPT

# Allow SSH from an entire network (/24 = 256 IPs)
sudo iptables -A INPUT -p tcp -s 192.168.1.0/24 --dport 22 -j ACCEPT

Rate Limit SSH Brute-Force Attacks

Allow SSH but limit connection attempts to prevent brute-force attacks:

# Allow max 4 SSH connections per minute
sudo iptables -A INPUT -p tcp --dport 22 -m conntrack --ctstate NEW -m limit --limit 4/minute --limit-burst 4 -j ACCEPT

# Drop new SSH connections exceeding the rate
sudo iptables -A INPUT -p tcp --dport 22 -m conntrack --ctstate NEW -j DROP

Block Specific IPs or Networks

# Block a specific IP
sudo iptables -I INPUT -s 198.51.100.50 -j DROP

# Block an entire country's IP range (example)
sudo iptables -I INPUT -s 10.0.0.0/8 -j DROP

# Block all ICMP (ping) — optional
sudo iptables -A INPUT -p icmp -j DROP

Note: -I inserts at the top of the chain (position 1), while -A appends to the end. Use -I for block rules so they're evaluated before allow rules.

Log Dropped Packets

Before the final DROP policy, log rejected connections for analysis:

# Log dropped packets (rate limited to avoid log flooding)
sudo iptables -A INPUT -m limit --limit 5/min -j LOG --log-prefix "IPTABLES-DROP: " --log-level 4

# This goes just before the default DROP policy takes effect

Saving and Loading Rules

iptables rules are not persistent by default — they disappear on reboot. Save your rules:

# Debian/Ubuntu: install iptables-persistent
sudo apt install iptables-persistent
# During install, it asks if you want to save current rules — say Yes

# Or manually save and restore:
sudo iptables-save > /etc/iptables/rules.v4
sudo iptables-restore < /etc/iptables/rules.v4

# RedHat/CentOS:
sudo service iptables save

Complete iptables Rule Set

Here's a production-ready iptables script you can save as /usr/local/bin/setup-firewall.sh:

#!/bin/bash
# Production iptables firewall script

# Flush existing rules
iptables -F
iptables -X

# Set default policies
iptables -P INPUT DROP
iptables -P FORWARD DROP
iptables -P OUTPUT ACCEPT

# Allow loopback
iptables -A INPUT -i lo -j ACCEPT
iptables -A OUTPUT -o lo -j ACCEPT

# Allow established connections
iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT

# Allow SSH with rate limiting
iptables -A INPUT -p tcp --dport 22 -m conntrack --ctstate NEW \
  -m limit --limit 4/minute --limit-burst 4 -j ACCEPT

# Allow HTTP and HTTPS
iptables -A INPUT -p tcp --dport 80 -j ACCEPT
iptables -A INPUT -p tcp --dport 443 -j ACCEPT

# Allow ICMP (ping) — useful for diagnostics
iptables -A INPUT -p icmp --icmp-type echo-request -j ACCEPT

# Log dropped packets
iptables -A INPUT -m limit --limit 5/min \
  -j LOG --log-prefix "IPTABLES-DROP: " --log-level 4

echo "Firewall rules applied!"

Make it executable with chmod +x /usr/local/bin/setup-firewall.sh and run with sudo /usr/local/bin/setup-firewall.sh.

UFW: The Easy Firewall

UFW (Uncomplicated Firewall) is a front-end for iptables designed for simplicity. If you're on Ubuntu or any Debian-based system, UFW is likely pre-installed. It translates simple commands into iptables rules under the hood.

UFW is perfect for 90% of use cases. You don't need raw iptables unless you need very specific packet filtering.

Enable UFW:

# Check current status
sudo ufw status

# Enable UFW (this sets default policies to deny incoming, allow outgoing)
sudo ufw enable

# Check status with verbose info
sudo ufw status verbose

Important: On a remote server, make sure you've allowed SSH before enabling UFW, or you'll get locked out.

UFW Commands

UFW commands are intuitive and self-documenting:

Basic Allow/Deny

# Allow SSH
sudo ufw allow ssh        # or: sudo ufw allow 22

# Allow HTTP and HTTPS
sudo ufw allow http       # port 80
sudo ufw allow https      # port 443

# Allow a port with protocol specified
sudo ufw allow 3306/tcp   # MySQL (TCP only)

# Deny a port
sudo ufw deny 8080        # Block port 8080

Allow from Specific IP

# Allow SSH from a specific IP
sudo ufw allow from 203.0.113.5 to any port 22 proto tcp

# Allow a specific port from an IP range
sudo ufw allow from 192.168.1.0/24 to any port 8080

Delete Rules

# List rules with numbers
sudo ufw status numbered

# Delete by rule number
sudo ufw delete 3

# Delete a specific rule
sudo ufw delete allow 8080

Reset and Reload

# Reload without losing rules
sudo ufw reload

# Reset everything (disable + delete all rules) — DANGEROUS!
sudo ufw reset

UFW Advanced Rules

For more complex rules, UFW reads from configuration files. The main config is /etc/ufw/ufw.conf and app profiles go in /etc/ufw/apps/.

Create an App Profile

Create /etc/ufw/apps/nginx.profile:

[nginx]
title=Web Server
description=Nginx HTTP and HTTPS
ports=80,443/tcp

Then enable it:

sudo ufw app update nginx
sudo ufw allow nginx

Port Forwarding with UFW

Edit /etc/default/ufw and set DEFAULT_FORWARD_POLICY="ACCEPT", then add rules:

# In /etc/ufw/before.rules, add:
-A ufw-before-forward -i eth0 -p tcp --dport 80 -j ACCEPT
-A POSTROUTING -t nat -o eth0 -j MASQUERADE

Limit Connections (Anti-Brute-Force)

UFW has a built-in limit option:

# Limit SSH: allow 6 connections in 30 seconds, then block
sudo ufw limit ssh

# This is equivalent to the iptables rate-limit rule above

nftables: The Modern Way

nftables is the modern replacement for iptables. It's faster, cleaner, and uses a more intuitive syntax. It's available on Linux kernel 3.13+ and is becoming the default on newer distributions.

Unlike iptables' command-line chaos, nftables uses a single configuration file:

# /etc/nftables.conf

#!/usr/sbin/nft -f

# Flush existing rules
flush ruleset

# Create a table and chain
table inet filter {
    chain input {
        type filter hook input priority 0; policy drop;

        # Allow loopback
        iif lo accept

        # Allow established connections
        ct state established,related accept
        ct state invalid drop

        # Allow SSH with rate limiting
        tcp dport ssh ct state new limit rate 4/minute accept
        tcp dport ssh drop

        # Allow HTTP and HTTPS
        tcp dport { http, https } accept

        # Allow ping (rate limited)
        icmp type echo-request limit rate 5/second accept

        # Log and drop everything else
        log prefix "NFT-DROP: " drop
    }

    chain forward {
        type filter hook forward priority 0; policy drop;
    }

    chain output {
        type filter hook output priority 0; policy accept;
    }
}

Apply with sudo nft -f /etc/nftables.conf. The configuration is declarative — you describe the desired state, and nftables handles the rest. No more worrying about rule order with -I vs -A.

Key nftables Concepts

iptables nftables
-A INPUT chain input { ... }
-p tcp --dport 22 tcp dport ssh
-s 192.168.1.0/24 ip saddr 192.168.1.0/24
-j ACCEPT accept
-P INPUT DROP policy drop;

Tool Comparison

Feature iptables UFW nftables
Complexity High Low Medium
Performance Good Same as iptables Better
Config Format CLI commands Simple CLI Declarative file
Persistence Manual save Automatic File-based
Best For Advanced users Everyone else Future-proof setups

My recommendation: Use UFW for most servers. It's simple, safe, and gets the job done. Use iptables when you need granular control. Start learning nftables — it's the future.

Automate with Python

You can manage UFW rules programmatically from Python. Here's a utility class:

import subprocess

class Firewall:
    """Simple firewall management using UFW."""
    
    def __init__(self):
        self.sudo = "sudo ufw"
    
    def _run(self, command: str) -> str:
        """Run a UFW command and return output."""
        result = subprocess.run(
            f"{self.sudo} {command}",
            shell=True,
            capture_output=True,
            text=True,
            input="y\n"  # Auto-confirm prompts
        )
        return result.stdout.strip()
    
    def allow(self, port: int, proto: str = "tcp") -> None:
        """Allow traffic on a port."""
        self._run(f"allow {port}/{proto}")
        print(f"Allowed {port}/{proto}")
    
    def deny(self, port: int, proto: str = "tcp") -> None:
        """Deny traffic on a port."""
        self._run(f"deny {port}/{proto}")
        print(f"Denied {port}/{proto}")
    
    def allow_from(self, ip: str, port: int) -> None:
        """Allow traffic from a specific IP to a port."""
        self._run(f"allow from {ip} to any port {port} proto tcp")
        print(f"Allowed {ip} -> port {port}")
    
    def limit(self, service: str) -> None:
        """Rate limit a service (anti-brute-force)."""
        self._run(f"limit {service}")
        print(f"Limited {service}")
    
    def status(self) -> str:
        """Show current firewall status."""
        return self._run("status verbose")
    
    def reload(self) -> None:
        """Reload firewall rules."""
        self._run("reload")
        print("Firewall reloaded")
    
    def enable(self) -> None:
        """Enable the firewall."""
        self._run("enable")
        print("Firewall enabled")
    
    def disable(self) -> None:
        """Disable the firewall."""
        self._run("disable")
        print("Firewall disabled")


# --- Usage Example ---
fw = Firewall()

# Secure a new web server
fw.enable()
fw.allow(22)           # SSH
fw.allow(80)           # HTTP
fw.allow(443)          # HTTPS
fw.limit("ssh")        # Anti-brute-force
fw.deny(3306)          # Block MySQL from outside

print("\nCurrent status:")
print(fw.status())

This class wraps UFW commands in Python methods. Use it in deployment scripts to configure firewalls consistently across servers.

Best Practices

  1. Default deny everything — start with a closed firewall and open only what's needed.
  2. Allow SSH before enabling — always ensure you can SSH in before turning on the firewall, especially on remote servers.
  3. Restrict SSH by IP — if your IP is static, allow SSH only from your address. Otherwise, use rate limiting.
  4. Allow established connections — this rule is essential for any outbound connectivity to work.
  5. Test before locking yourself out — use a separate SSH session when testing firewall rules on remote servers.
  6. Log dropped packets — logging helps you identify legitimate traffic you may have accidentally blocked.
  7. Save your rules — iptables rules are lost on reboot. Use UFW (auto-persistent) or save iptables rules manually.
  8. Don't expose database ports — ports 3306 (MySQL), 5432 (PostgreSQL), 6379 (Redis) should never be accessible from the internet.
  9. Combine with Cloudflare — for web traffic, Cloudflare provides DDoS protection and WAF before traffic even reaches your firewall.

Summary

Linux firewalls are your first line of defense. Here's the quick reference:

  • iptables — powerful, verbose, everywhere. Use iptables -A INPUT -p tcp --dport PORT -j ACCEPT to allow ports.
  • UFW — simple, safe, beginner-friendly. Use sudo ufw allow PORT to allow ports.
  • nftables — modern, fast, declarative. Use tcp dport PORT accept in a config file.

For most servers, start with UFW: allow SSH, HTTP, and HTTPS, limit SSH connections, and deny everything else. That simple setup blocks the vast majority of automated attacks.

Remember: a firewall is only as good as its rules. Keep your rule set minimal, document what each rule does, and review it regularly.
