Terraform Basics: Infrastructure as Code for Beginners

June 23, 2026 · 10 min read

Manual cloud management — clicking through dashboards to create servers, databases, and networks — doesn't scale. Terraform solves this by letting you define your entire infrastructure in code files that you can version, share, test, and replay at any time. This is Infrastructure as Code (IaC), and it's one of the most valuable DevOps skills you can learn.

In this guide, we'll go from installing Terraform to provisioning real cloud resources — all through declarative configuration files. No clicking, no guessing, no "it works on my laptop" problems.

What Is Terraform?

Terraform is an open-source IaC tool by HashiCorp. You write configuration files in HCL (HashiCorp Configuration Language), describe the infrastructure you want, and Terraform handles the creation, updates, and destruction of resources across any cloud provider — AWS, Google Cloud, Azure, Cloudflare, and dozens more.

How Terraform works:

  1. You write config files (.tf) describing desired state
  2. terraform plan — shows what will change
  3. terraform apply — makes the changes
  4. State file (.tfstate) tracks what's been created
  5. Run again → Terraform only changes what's different

Key concepts:

  • Declarative — you describe what you want, not how to build it step by step
  • Idempotent — running the same config twice doesn't create duplicate resources
  • State-driven — Terraform keeps a state file to track real-world resources
  • Provider-agnostic — write once, deploy to any supported cloud

Installation

Terraform is a single binary — no dependencies, no runtime needed.

# macOS (Homebrew)
brew install terraform

# Ubuntu/Debian
sudo apt update && sudo apt install terraform

# Verify installation
terraform version
# Terraform v1.10.x

Your First Terraform Configuration

Let's create a simple project that provisions an S3 bucket and a Cloudflare DNS record. We'll use both AWS and Cloudflare providers.

First, create a project directory:

mkdir terraform-basics
cd terraform-basics

Step 1: Define the Providers

Providers are the plugins that let Terraform talk to cloud APIs. Create main.tf:

terraform {
  required_version = ">= 1.5.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
    cloudflare = {
      source  = "cloudflare/cloudflare"
      version = "~> 4.0"
    }
  }
}

# AWS Provider
provider "aws" {
  region = "us-east-1"
}

# Cloudflare Provider
# Set CLOUDFLARE_API_TOKEN environment variable
provider "cloudflare" {}

The terraform block declares version requirements. The provider blocks configure the cloud connections. Note that sensitive credentials (like API tokens) should go in environment variables, not in code.

Step 2: Define Variables

Variables make your configs reusable. Create variables.tf:

variable "environment" {
  description = "Environment name (e.g., dev, staging, prod)"
  type        = string
  default     = "dev"
}

variable "project_name" {
  description = "Name of the project"
  type        = string
  default     = "my-app"
}

variable "cloudflare_zone_id" {
  description = "Cloudflare zone ID for your domain"
  type        = string
  sensitive   = true
}

variable "allowed_cidr_blocks" {
  description = "CIDR blocks allowed to access the bucket"
  type        = list(string)
  default     = ["0.0.0.0/0"]
}

Variables can have types, defaults, descriptions, and a sensitive flag that hides values in terminal output.

Step 3: Define Resources

Resources are the actual cloud objects you create. Back in main.tf:

# Create an S3 bucket
resource "aws_s3_bucket" "app_bucket" {
  bucket = "${var.project_name}-${var.environment}-assets"

  tags = {
    Environment = var.environment
    Project     = var.project_name
    ManagedBy   = "terraform"
  }
}

# Block public access to the bucket
resource "aws_s3_bucket_public_access_block" "app_bucket" {
  bucket = aws_s3_bucket.app_bucket.id

  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

# Create an S3 bucket policy (optional — only allow Cloudflare to read)
resource "aws_s3_bucket_policy" "cloudflare_read" {
  bucket = aws_s3_bucket.app_bucket.id

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Effect = "Allow"
        Principal = {
          AWS = "arn:aws:iam::cloudfront:user/CloudFront Origin Access Identity"
        }
        Action   = "s3:GetObject"
        Resource = "${aws_s3_bucket.app_bucket.arn}/*"
      }
    ]
  })
}

# Create a Cloudflare DNS record pointing to the bucket
resource "cloudflare_record" "cdn" {
  zone_id = var.cloudflare_zone_id
  name    = "cdn.${var.project_name}.example.com"
  value   = aws_s3_bucket.app_bucket.bucket_regional_domain_name
  type    = "CNAME"
  proxied = true  # enable Cloudflare proxy (yellow cloud)

  comment = "Managed by Terraform"
}

Each resource block has:

  • Type — the resource kind (e.g., aws_s3_bucket)
  • Name — a local identifier (e.g., app_bucket)
  • Arguments — the configuration (bucket name, tags, etc.)
  • Interpolation — reference other resources with aws_s3_bucket.app_bucket.id

Step 4: Define Outputs

Outputs expose important values after deployment. Create outputs.tf:

output "bucket_name" {
  description = "The name of the S3 bucket"
  value       = aws_s3_bucket.app_bucket.bucket
}

output "bucket_arn" {
  description = "The ARN of the S3 bucket"
  value       = aws_s3_bucket.app_bucket.arn
}

output "cdn_url" {
  description = "The CDN URL for accessing assets"
  value       = "https://cdn.${var.project_name}.example.com"
}

Running Terraform

Now comes the actual workflow. Every Terraform project follows the same four steps:

# 1. Initialize — downloads providers, sets up backend
terraform init

# 2. Validate — checks syntax without making changes
terraform validate

# 3. Plan — preview what Terraform will create/modify/delete
terraform plan

# Output example:
# Terraform will perform the following actions:
#
#   + aws_s3_bucket.app_bucket will be created
#   + aws_s3_bucket_public_access_block.app_bucket will be created
#   + cloudflare_record.cdn will be created
#
# Plan: 3 to add, 0 to change, 0 to destroy.

# 4. Apply — execute the plan (requires confirmation)
terraform apply

# Or auto-approve (use carefully!):
# terraform apply -auto-approve

# Output:
# Apply complete! Resources: 3 added, 0 changed, 0 destroyed.
#
# Outputs:
#
# bucket_name = "my-app-dev-assets"
# bucket_arn  = "arn:aws:s3:::my-app-dev-assets"
# cdn_url     = "https://cdn.my-app.example.com"

Managing State

Terraform stores the real-world state of your resources in terraform.tfstate. This file is the single source of truth — never edit it manually.

# View the state file
terraform state list
# aws_s3_bucket.app_bucket
# aws_s3_bucket_public_access_block.app_bucket
# cloudflare_record.cdn

# Inspect a specific resource
terraform state show aws_s3_bucket.app_bucket

# For team projects, use remote state (S3 + DynamoDB):
terraform {
  backend "s3" {
    bucket         = "my-terraform-state"
    key            = "dev/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "terraform-locks"
    encrypt        = true
  }
}

The dynamodb_table provides state locking, preventing two people from applying changes simultaneously and corrupting the state.

Destroying Infrastructure

When you're done (or need to rebuild), Terraform can tear everything down:

# Preview what will be destroyed
terraform plan -destroy

# Destroy all managed resources
terraform destroy

# WARNING: This permanently deletes all resources!
# Always review the plan before confirming.

Terraform Modules: Reusable Infrastructure

Modules let you package and reuse configurations. Instead of rewriting the S3 bucket config for every project, wrap it in a module.

# modules/s3-bucket/main.tf
variable "bucket_name" {
  type = string
}

variable "environment" {
  type = string
}

resource "aws_s3_bucket" "this" {
  bucket = var.bucket_name

  tags = {
    Environment = var.environment
    ManagedBy   = "terraform"
  }
}

resource "aws_s3_bucket_public_access_block" "this" {
  bucket = aws_s3_bucket.this.id

  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

output "bucket_name" {
  value = aws_s3_bucket.this.bucket
}

output "bucket_arn" {
  value = aws_s3_bucket.this.arn
}

# --- Use the module in your main config ---
module "assets" {
  source      = "./modules/s3-bucket"
  bucket_name = "${var.project_name}-${var.environment}-assets"
  environment = var.environment
}

output "cdn_bucket" {
  value = module.assets.bucket_name
}

Best Practices

  1. Never commit .tfstate to Git — it may contain secrets. Add it to .gitignore or use remote state.
  2. Use variables for anything that changes between environments (dev, staging, prod).
  3. Tag every resource with environment, project, and team info for cost tracking.
  4. Use modules for repeated patterns — don't copy-paste resource blocks.
  5. Always run terraform plan before apply — review changes first.
  6. Use sensitive = true for variables containing passwords or tokens.
  7. Use remote state with locking when working in a team.
  8. Start small — manage one resource, verify it works, then expand.

Terraform Workflow Checklist

Day 1 (Learning):
  ✅ Install Terraform
  ✅ Write your first .tf file
  ✅ Run init → plan → apply → destroy cycle
  ✅ Practice with the AWS Free Tier

Week 1 (First Project):
  ✅ Provision a VPC with subnets
  ✅ Create an EC2 instance with a security group
  ✅ Add outputs and variables
  ✅ Use remote state (S3 + DynamoDB)

Week 2 (Going Further):
  ✅ Create a reusable module
  ✅ Set up a staging vs. prod environment with workspaces
  ✅ Add pre-commit hooks (terraform fmt, terraform validate)
  ✅ Integrate with GitHub Actions for CI/CD

What's Next?

Terraform is your gateway to infrastructure automation. After mastering the basics, explore:

  • Terraform Workspaces — manage multiple environments from one config
  • Terragrunt — reduce repetition with DRY HCL
  • Terraform Cloud — remote execution, team collaboration, policy-as-code
  • Pulumi — the alternative IaC tool that uses real programming languages (Python, TypeScript)

The key takeaway: if you build it once by clicking, you're doing it wrong. Write it in code, version it, and let Terraform handle the rest. Your future self will thank you.
