Python Packaging & Publishing: Share Your Code on PyPI

June 26, 2026 · 11 min read

You've written a useful Python module — a utility library, a data processor, or a handy CLI tool. Now you want to share it. Instead of emailing files or setting up a private Git repo, publish it to PyPI (the Python Package Index). Then anyone can install it with pip install my-awesome-tool.

This guide walks you through packaging a real Python project, building distribution files, and uploading to PyPI — from zero to published.

Why Package Your Code?

  • One-command install — pip install instead of "clone, cd, run setup"
  • Version control — users pin to ==1.2.3 for reproducibility
  • Dependency management — pip resolves and installs your dependencies automatically
  • Discoverability — thousands of developers search PyPI daily
  • Credit — your name on a package people use every day

Project Structure

A standard Python package looks like this:

my_tool/
├── pyproject.toml        # Project metadata & build config
├── README.md             # Package description
├── LICENSE               # Open source license
├── src/
│   └── my_tool/
│       ├── __init__.py   # Package entry point
│       ├── core.py       # Main logic
│       └── utils.py      # Helper functions
└── tests/
    └── test_core.py      # Unit tests

We'll use the src layout (putting code under src/) — it's the modern best practice recommended by the Python Packaging Authority (PyPA). It prevents accidentally importing your local development version instead of the installed one.

Step 1: Create pyproject.toml

The pyproject.toml file replaces the old setup.py and setup.cfg. It's a single, declarative file with everything your package needs.

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[project]
name = "my-awesome-tool"
version = "0.1.0"
description = "A handy utility tool for Python developers"
readme = "README.md"
license = "MIT"
requires-python = ">=3.9"
authors = [
    { name = "Hugo Wong", email = "hugo@example.com" },
]
keywords = ["python", "utility", "automation"]
classifiers = [
    "Programming Language :: Python :: 3",
    "License :: OSI Approved :: MIT License",
    "Operating System :: OS Independent",
]

dependencies = [
    "requests>=2.31.0",
    "click>=8.0.0",
]

[project.optional-dependencies]
dev = [
    "pytest>=7.0",
    "pytest-cov",
    "black",
    "mypy",
]

[project.urls]
Homepage = "https://github.com/hugow0528/my-tool"
Repository = "https://github.com/hugow0528/my-tool"
Issues = "https://github.com/hugow0528/my-tool/issues"

Key fields explained:

  • [build-system] — tells pip which tool to use for building (we use hatchling, the simplest modern option)
  • [project] — metadata that appears on PyPI
  • dependencies — packages auto-installed when someone runs pip install my-awesome-tool
  • optional-dependencies — extras installed with pip install my-awesome-tool[dev]

Step 2: Write the Package Code

Create src/my_tool/__init__.py — this is the package entry point:

"""my_tool — A handy utility for Python developers."""

from .core import fetch_data, process_data
from .utils import format_output

__version__ = "0.1.0"
__all__ = ["fetch_data", "process_data", "format_output"]

Create src/my_tool/core.py — your main logic:

import requests


def fetch_data(url: str, timeout: int = 10) -> dict:
    """Fetch JSON data from a URL.
    
    Args:
        url: The API endpoint to call
        timeout: Request timeout in seconds
        
    Returns:
        Parsed JSON response as a dictionary
        
    Raises:
        requests.RequestException: If the request fails
    """
    response = requests.get(url, timeout=timeout)
    response.raise_for_status()
    return response.json()


def process_data(raw_data: dict) -> list:
    """Process raw API data into a clean list.
    
    Args:
        raw_data: Dictionary from fetch_data()
        
    Returns:
        List of processed items
    """
    results = []
    for item in raw_data.get("items", []):
        results.append({
            "id": item.get("id"),
            "name": item.get("name", "Unknown"),
            "active": item.get("status") == "active",
        })
    return results

Create src/my_tool/utils.py — helper functions:

def format_output(items: list) -> str:
    """Format a list of items for terminal display.
    
    Args:
        items: List of dictionaries with id, name, active
        
    Returns:
        Formatted string for printing
    """
    lines = []
    for item in items:
        status = "✅" if item["active"] else "❌"
        lines.append(f"  {status} [{item['id']}] {item['name']}")
    return "\n".join(lines)

Step 3: Write Tests

Tests build confidence before publishing. Create tests/test_core.py:

import pytest
from my_tool.core import process_data


def test_process_data_empty():
    """Test processing an empty response."""
    result = process_data({})
    assert result == []


def test_process_data_single_item():
    """Test processing a single item."""
    raw = {"items": [{"id": 1, "name": "Test", "status": "active"}]}
    result = process_data(raw)
    assert len(result) == 1
    assert result[0]["name"] == "Test"
    assert result[0]["active"] is True


def test_process_data_inactive():
    """Test processing an inactive item."""
    raw = {"items": [{"id": 2, "name": "Old", "status": "inactive"}]}
    result = process_data(raw)
    assert result[0]["active"] is False

Run the tests:

cd /path/to/my_tool
pip install -e ".[dev]"
pytest tests/ -v

# test_process_data_empty PASSED
# test_process_data_single_item PASSED
# test_process_data_inactive PASSED

Step 4: Build the Package

Install the build tool and create distribution files:

pip install build
python -m build

# Created:
#   dist/my_awesome_tool-0.1.0-py3-none-any.whl  (wheel — fast install)
#   dist/my_awesome_tool-0.1.0.tar.gz             (source archive)

The wheel (.whl) is a pre-built package — users install it instantly. The source distribution (.tar.gz) lets users who need to compile things build from source.

Step 5: Test Upload to TestPyPI

Before uploading to the real PyPI, test on TestPyPI (a mirror for testing):

First, create an account at test.pypi.org.

Install twine (the upload tool):

pip install twine

Upload to TestPyPI:

twine upload --repository testpypi \
    dist/* \
    -u __token__ \
    -p pypi-YOUR_TEST_TOKEN

# Uploading my_awesome_tool-0.1.0-py3-none-any.whl
# Uploaded to https://test.pypi.org/

Test installing from TestPyPI:

pip install --index-url https://test.pypi.org/simple/ \
    --no-deps my-awesome-tool==0.1.0

# Try it:
python3 -c "from my_tool import process_data; print('Works!')"

Step 6: Publish to PyPI

Create an account at pypi.org. Then generate an API token in Settings → API tokens.

twine upload dist/* \
    -u __token__ \
    -p pypi-YOUR_REAL_TOKEN

# Uploading my_awesome_tool-0.1.0-py3-none-any.whl
# Uploading my_awesome_tool-0.1.0.tar.gz
# View at: https://pypi.org/project/my-awesome-tool/

Step 7: Version Bumping

Follow Semantic Versioning (SemVer):

  • MAJOR — breaking changes (2.0.0)
  • MINOR — new features, backward compatible (1.1.0)
  • PATCH — bug fixes only (1.0.1)

Update version in pyproject.toml and __init__.py, then rebuild and upload:

# Change version to 0.2.0 in pyproject.toml
# Fix a bug, rebuild:
python -m build
twine upload dist/* -u __token__ -p pypi-YOUR_TOKEN

Step 8: GitHub Actions Auto-Publish

Automate uploads on every git tag. Create .github/workflows/publish.yml:

name: Publish to PyPI

on:
  push:
    tags:
      - 'v*'

jobs:
  publish:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.12"

      - name: Install build tools
        run: pip install build twine

      - name: Build package
        run: python -m build

      - name: Publish to PyPI
        env:
          TWINE_USERNAME: __token__
          TWINE_PASSWORD: ${{ secrets.PYPI_TOKEN }}
        run: twine upload dist/*

Now every time you push git tag v1.0.0 && git push --tags, your package publishes automatically.

Common Mistakes to Avoid

1. Name Already Taken

Check pypi.org first. Package names can't be reused — even if the original is abandoned. Pick something unique.

2. Forgetting to Run Tests

Always run pytest before uploading. Broken packages damage your reputation.

3. Missing __init__.py

Without this file, Python doesn't recognize your directory as a package. It can be empty, but it should exist.

4. Including Secrets

Add a .gitignore and .packageignore to exclude .env files, credentials, and local config:

# .gitignore
.env
*.key
dist/
build/
__pycache__/

Quick Reference: Publishing Checklist

  1. Write code with proper __init__.py
  2. Create pyproject.toml with metadata and dependencies
  3. Add README.md and LICENSE
  4. Write tests and run pytest
  5. Build with python -m build
  6. Test on TestPyPI first
  7. Upload to PyPI with twine upload
  8. Set up GitHub Actions for auto-publishing
Pro tip: Start with a private package on your company's Git repo or a private PyPI index (like Cloudflare R2 + Warehouse) before going public.
