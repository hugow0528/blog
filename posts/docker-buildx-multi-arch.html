Docker Buildx: Multi-Architecture Image Builds Made Easy

July 10, 2026 11 min read New

Master Docker Buildx — build images for multiple CPU architectures from a single machine, leverage BuildKit's advanced caching and parallel builds, export to different formats, and set up CI/CD pipelines for production multi-arch deployments.

Most developers build Docker images on their laptop and push them to a registry. But what if your users run different CPU architectures? x86_64 on desktops, ARM64 on Macs with Apple Silicon, ARM on Raspberry Pis and cloud instances?

Docker Buildx solves this problem elegantly. It's a CLI plugin that supercharges Docker builds with BuildKit, supporting multi-architecture images, advanced caching, and export to formats beyond Docker.

What Is Docker Buildx?

Buildx is more than just "build for multiple architectures." It brings several powerful features:

  • Multi-arch builds — build for x86_64, ARM64, ARM/v7 from one machine
  • BuildKit engine — parallel build stages, better caching, interactive debugging
  • Bake files — declarative build configuration like Makefiles
  • Export to any format — Docker, OCI, tar, directory, even containerd
  • Secrets & SSH forwarding — pass credentials securely without baking them into images

1. Enable Buildx

Buildx comes bundled with Docker Desktop. For Linux, enable it:

# Check if Buildx is available
docker buildx version

# Create a new builder instance with QEMU for cross-platform builds
docker buildx create --name mybuilder --use --bootstrap

# Register QEMU for emulation (needed for cross-arch builds)
docker run --privileged --rm tonistiigi/binfmt --install all

# Verify you can build for multiple platforms
docker buildx inspect --bootstrap

2. Multi-Architecture Builds

The magic command — build for both x86_64 and ARM64 in one go:

# Build and push multi-arch images
docker buildx build \
    --platform linux/amd64,linux/arm64 \
    --tag myapp:latest \
    --push \
    .

Behind the scenes, Buildx uses QEMU emulation to run ARM64 build steps on your x86_64 machine (or vice versa). The resulting manifest list contains both architectures — Docker pull automatically picks the right one.

Dockerfile with Architecture Awareness

# Dockerfile
FROM --platform=$BUILDPLATFORM node:20-alpine AS builder

# TARGETPLATFORM is the platform being built FOR
# BUILDPLATFORM is the platform we're building ON
ARG TARGETPLATFORM
ARG BUILDPLATFORM

RUN echo "Building on ${BUILDPLATFORM} for ${TARGETPLATFORM}"

# Install architecture-specific dependencies
RUN case "${TARGETPLATFORM}" in \
    linux/amd64)  echo "x86_64 detected" ;; \
    linux/arm64)  echo "ARM64 detected" ;; \
    linux/arm/v7) echo "ARM v7 detected" ;; \
    *) echo "Unknown platform: ${TARGETPLATFORM}" ;; \
  esac

COPY package*.json ./
RUN npm ci --only=production

COPY . .
RUN npm run build

FROM node:20-alpine
COPY --from=builder /app/dist /app
WORKDIR /app
EXPOSE 3000
CMD ["node", "server.js"]

3. Advanced Caching Strategies

BuildKit provides powerful cache backends. Never rebuild what you've already built:

# Inline cache (stored in registry with the image)
docker buildx build \
    --cache-to type=inline \
    --cache-from type=registry,ref=myapp:cache \
    --tag myapp:latest \
    --push .

# GitHub Actions Cache (fastest for CI)
docker buildx build \
    --cache-to type=gha,mode=max \
    --cache-from type=gha \
    --tag myapp:latest \
    --load .

# Local directory cache (for development)
docker buildx build \
    --cache-to type=local,dest=/tmp/build-cache \
    --cache-from type=local,src=/tmp/build-cache \
    --tag myapp:latest \
    --load .

4. Build Secret Injection

Never bake secrets into your Docker image layers. Buildx supports secure secret injection:

# Dockerfile
FROM node:20-alpine
RUN --mount=type=secret,id=auth_token \
    npm config set //registry.npmjs.org/:_authToken $(cat /run/secrets/auth_token) && \
    npm ci

# Or with SSH agent forwarding
FROM golang:1.22
RUN --mount=type=ssh \
    git clone git@github.com:private/repo.git

# Build with secrets
docker buildx build \
    --secret id=auth_token,src=~/.npmrc \
    --ssh default \
    --tag myapp:latest \
    .

The secrets exist only during the build step and are never written to any image layer.

5. Docker Bake: Declarative Build Configuration

For complex projects with multiple images, use docker-bake.hcl:

// docker-bake.hcl
variable "TAG" {
  default = "latest"
}

target "api" {
  dockerfile = "api/Dockerfile"
  context    = "api"
  tags       = ["myapp/api:${TAG}"]
  platforms  = ["linux/amd64", "linux/arm64"]
}

target "web" {
  dockerfile = "web/Dockerfile"
  context    = "web"
  tags       = ["myapp/web:${TAG}"]
  platforms  = ["linux/amd64", "linux/arm64"]
}

target "db" {
  dockerfile = "db/Dockerfile"
  context    = "db"
  tags       = ["myapp/db:${TAG}"]
}
# Build all images
docker buildx bake

# Build with custom tag
docker buildx bake --set "*.TAG=v1.0.0"

# Push all
docker buildx bake --push

# Only build the API
docker buildx bake api

6. GitHub Actions CI/CD Pipeline

Put it all together in an automated pipeline:

# .github/workflows/build.yml
name: Build & Push Multi-Arch Images

on:
  push:
    tags: ["v*"]

jobs:
  build:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Set up QEMU
        uses: docker/setup-qemu-action@v3

      - name: Set up Buildx
        uses: docker/setup-buildx-action@v3

      - name: Login to GitHub Container Registry
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Build & Push
        uses: docker/build-push-action@v5
        with:
          context: .
          platforms: linux/amd64,linux/arm64
          push: true
          tags: |
            ghcr.io/${{ github.repository }}:${{ github.ref_name }}
            ghcr.io/${{ github.repository }}:latest
          cache-from: type=gha
          cache-to: type=gha,mode=max
          secrets: |
            "npm_token=${{ secrets.NPM_TOKEN }}"

7. Export to Different Formats

Buildx isn't limited to Docker images. Export to other formats:

# Export as OCI image (standard format, smaller)
docker buildx build --output type=oci,dest=image.tar .

# Export as Docker image
docker buildx build --output type=docker --load .

# Export as tarball
docker buildx build --output type=tar,dest=image.tar .

# Export to a directory (for local testing)
docker buildx build --output type=local,dest=./output .

# Export to containerd
docker buildx build --output type=containerd,name=myapp:latest .

Common Gotchas

  • QEMU emulation is slow — ARM builds on x86 can take 3-5x longer. Consider using cloud runners with native ARM support for production pipelines.
  • Some Dockerfiles assume x86 — check that your base image and dependencies support the target architecture.
  • Layer caching across platforms — BuildKit caches layers independently per platform. Share cache with --cache-from type=registry.
  • Manifest list vs manifest — multi-arch images use a manifest list. Verify with docker buildx imagetools inspect.

Summary

Docker Buildx transforms how you build container images. Multi-architecture builds mean your users on any platform get the right image automatically. BuildKit's caching and parallelism dramatically speed up CI/CD pipelines. And features like secret injection keep your builds secure.

Start with simple multi-arch builds for your existing Dockerfiles, then explore BuildKit caching, Bake files for complex projects, and automated CI/CD pipelines.

Key takeaway: One Dockerfile, one build command, images for every architecture. Buildx eliminates the "it works on my machine" problem by building natively for every target platform — your users get the right image automatically.
