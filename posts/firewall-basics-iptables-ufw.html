Firewall Basics: iptables and UFW for Linux Servers

July 1, 2026 12 min read New

You just spun up a fresh Linux server. You've configured SSH keys, set up your application, and it's listening on ports. But you've done one critical thing: you've exposed every open port to the entire internet. Automated bots scan all 65,535 ports on every IP address, multiple times per day, looking for vulnerabilities.

A firewall is your first and most important line of defense. It's a set of rules that controls which network traffic can reach your server. Without one, you're relying on application-level security alone — and if an application has a vulnerability, there's nothing between the attacker and your system.

In this guide, we'll cover Linux firewall fundamentals, the powerful (but complex) iptables, and the simpler UFW (Uncomplicated Firewall) — with practical configurations you can apply immediately.

How a Firewall Works

A firewall inspects every network packet that arrives at or leaves your server and decides whether to allow it, drop it, or reject it based on rules. Think of it as a security guard at a building:

  • Allow (ACCEPT) — The guard checks the visitor's name against an approved list and lets them in
  • Drop (DROP) — The guard ignores the visitor completely — no response, no acknowledgment
  • Reject (REJECT) — The guard tells the visitor "access denied" — the connection is actively refused

Drop vs Reject: Dropping is preferred for security. When you drop a connection, the attacker never knows your server exists. When you reject, the attacker knows a server is there — they just can't connect on that port. Dropping wastes attacker time; rejecting gives them information.

iptables: The Linux Firewall Foundation

iptables is the standard Linux firewall tool. It manages rules in the Linux kernel's netfilter framework. While modern systems often use frontends like UFW or firewalld, understanding iptables gives you insight into what's actually happening under the hood.

The Three Chains

iptables processes traffic through three default chains:

  • INPUT — Traffic destined for your server (e.g., someone connecting to your SSH port)
  • FORWARD — Traffic passing through your server (relevant if you're using the server as a router)
  • OUTPUT — Traffic originating from your server (e.g., your server making outbound API calls)

Most server configurations only need to worry about the INPUT chain. FORWARD is for routers, and OUTPUT is usually left open.

Basic iptables Commands

Check current rules:

# List all rules with line numbers
sudo iptables -L -n -v --line-numbers

# Check default policies
sudo iptables -L -n

The -n flag shows IPs instead of trying to resolve hostnames (much faster). The -v flag shows packet/byte counters.

Allow SSH (port 22):

# Allow new SSH connections
sudo iptables -A INPUT -p tcp --dport 22 -m conntrack --ctstate NEW,ESTABLISHED -j ACCEPT

# Allow established SSH connections (return traffic)
sudo iptables -A OUTPUT -p tcp --sport 22 -m conntrack --ctstate ESTABLISHED -j ACCEPT

Allow HTTP and HTTPS:

# Allow HTTP (port 80)
sudo iptables -A INPUT -p tcp --dport 80 -m conntrack --ctstate NEW,ESTABLISHED -j ACCEPT
sudo iptables -A OUTPUT -p tcp --sport 80 -m conntrack --ctstate ESTABLISHED -j ACCEPT

# Allow HTTPS (port 443)
sudo iptables -A INPUT -p tcp --dport 443 -m conntrack --ctstate NEW,ESTABLISHED -j ACCEPT
sudo iptables -A OUTPUT -p tcp --sport 443 -m conntrack --ctstate ESTABLISHED -j ACCEPT

Allow loopback traffic (localhost — required for many system services):

# Allow all traffic on the loopback interface
sudo iptables -A INPUT -i lo -j ACCEPT
sudo iptables -A OUTPUT -o lo -j ACCEPT

Set default policy to DROP everything not explicitly allowed:

# ⚠️ Warning: Set these LAST after adding your allow rules
# Otherwise you'll lock yourself out!
sudo iptables -P INPUT DROP
sudo iptables -P FORWARD DROP
sudo iptables -P OUTPUT ACCEPT

Complete iptables Configuration Example

Here's a production-ready iptables script. Save this as /usr/local/bin/setup-firewall.sh:

#!/bin/bash
# Complete iptables firewall configuration

echo "Setting up firewall rules..."

# Flush existing rules
iptables -F
iptables -X

# Allow loopback interface
iptables -A INPUT -i lo -j ACCEPT
iptables -A OUTPUT -o lo -j ACCEPT

# Allow established and related connections
iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
iptables -A OUTPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT

# Allow SSH (with rate limiting)
iptables -A INPUT -p tcp --dport 22 -m conntrack --ctstate NEW -m limit --limit 5/min --limit-burst 10 -j ACCEPT

# Allow HTTP and HTTPS
iptables -A INPUT -p tcp --dport 80 -j ACCEPT
iptables -A INPUT -p tcp --dport 443 -j ACCEPT

# Allow DNS (outbound)
iptables -A OUTPUT -p udp --dport 53 -j ACCEPT
iptables -A OUTPUT -p tcp --dport 53 -j ACCEPT

# Allow NTP (time sync)
iptables -A OUTPUT -p udp --dport 123 -j ACCEPT

# Allow ICMP (ping) with rate limiting
iptables -A INPUT -p icmp --icmp-type echo-request -m limit --limit 1/s -j ACCEPT

# Drop everything else
iptables -P INPUT DROP
iptables -P FORWARD DROP
iptables -P OUTPUT ACCEPT

echo "Firewall configured. Current rules:"
iptables -L -n -v

Make it executable and run:

sudo chmod +x /usr/local/bin/setup-firewall.sh
sudo /usr/local/bin/setup-firewall.sh

UFW: The Simple Alternative

Writing iptables rules by hand is error-prone. One typo and you lock yourself out of your server. UFW (Uncomplicated Firewall) is a frontend to iptables that provides a simpler interface. It comes pre-installed on Ubuntu and is easily installed on other distributions.

Install and Enable UFW

# Ubuntu/Debian
sudo apt update && sudo apt install -y ufw

# CentOS/RHEL/Fedora
sudo dnf install -y ufw

# Enable UFW
sudo ufw enable

# Check status
sudo ufw status verbose

Allow Specific Ports

# Allow SSH (CRITICAL: do this BEFORE enabling UFW)
sudo ufw allow 22/tcp

# Allow HTTP
sudo ufw allow 80/tcp

# Allow HTTPS
sudo ufw allow 443/tcp

# Allow a custom application port
sudo ufw allow 3000/tcp

# Allow a port range
sudo ufw allow 8080:8090/tcp

Allow from Specific IP Addresses

# Allow SSH only from your home IP
sudo ufw allow from 203.0.113.45 to any port 22 proto tcp

# Allow a subnet (e.g., your office network)
sudo ufw allow from 10.0.0.0/24 to any port 5432 proto tcp

Rate Limiting with UFW

# Limit SSH connections (auto-blocks after 6 connections in 30 seconds)
sudo ufw limit 22/tcp

# This is equivalent to iptables' recent module for brute-force protection

Complete UFW Setup for a Web Server

# Set default policies (deny incoming, allow outgoing)
sudo ufw default deny incoming
sudo ufw default allow outgoing

# Allow required services
sudo ufw allow 22/tcp    # SSH
sudo ufw allow 80/tcp    # HTTP
sudo ufw allow 443/tcp   # HTTPS

# Enable
sudo ufw enable

# Verify
sudo ufw status numbered

# Output:
#  Status: active
#
#     To                         Action      From
#     --                         ------      ----
#     [ 1] 22/tcp                ALLOW IN    Anywhere
#     [ 2] 80/tcp                ALLOW IN    Anywhere
#     [ 3] 443/tcp               ALLOW IN    Anywhere

Deleting Rules

# Delete by rule number (from 'ufw status numbered' output)
sudo ufw delete 1

# Delete by specification
sudo ufw delete allow 3000/tcp

Brute-Force Protection with fail2ban

A firewall controls which ports are open, but it doesn't stop someone from hammering port 22 with 10,000 failed SSH login attempts. For that, you need fail2ban:

# Install fail2ban
sudo apt install -y fail2ban

# Create configuration
sudo cp /etc/fail2ban/jail.conf /etc/fail2ban/jail.local

# Edit jail.local
sudo nano /etc/fail2ban/jail.local

Recommended jail.local settings:

[DEFAULT]
# Ban an IP after 5 failed attempts within 10 minutes
bantime  = 3600      # Ban for 1 hour
findtime  = 600      # Look back 10 minutes
maxretry = 5         # Maximum failed attempts

# Email notification (optional)
destemail = you@example.com
sender = fail2ban@your-server.com
action = %(action_mwl)s

[sshd]
enabled = true
port = ssh
filter = sshd
logpath = /var/log/auth.log
maxretry = 3

# Protect Nginx from login brute force (if you have login pages)
[nginx-http-auth]
enabled = true
port = http,https
filter = nginx-http-auth
logpath = /var/log/nginx/error.log

Start and enable fail2ban:

sudo systemctl enable --now fail2ban

# Check status
sudo fail2ban-client status sshd

# Output:
# Status for the jail: sshd
# |- Filter
# |  |- Currently failed: 0
# |  |- Total failed: 127
# |  `- File list: /var/log/auth.log
# `- Actions
#    |- Currently banned: 3
#    `- Total banned: 42

Firewall Rules for Common Services

Service Port UFW Command
SSH 22/tcp ufw allow 22/tcp
HTTP 80/tcp ufw allow 80/tcp
HTTPS 443/tcp ufw allow 443/tcp
PostgreSQL 5432/tcp ufw allow from 10.0.0.0/24 to any port 5432
Redis 6379/tcp ufw allow from 10.0.0.0/24 to any port 6379
MongoDB 27017/tcp ufw allow from 10.0.0.0/24 to any port 27017
Docker API 2376/tcp ufw allow from 10.0.0.0/24 to any port 2376

Notice the pattern: databases and internal services use allow from <subnet> to restrict access to trusted networks only. Never open database ports to "Anywhere."

Persistent Firewall Rules

iptables rules are lost on reboot. To persist them:

# Ubuntu/Debian
sudo apt install iptables-persistent
# Follow the prompts to save current rules

# Check that rules are saved
cat /etc/iptables/rules.v4

# CentOS/RHEL
sudo iptables-save > /etc/sysconfig/iptables

UFW rules persist automatically. When you enable UFW, it saves rules to disk and restores them on boot.

Cloud Provider Firewalls: The Second Layer

Most cloud providers (AWS, GCP, DigitalOcean, etc.) have their own network security groups or firewalls. These run at the hypervisor level, before traffic even reaches your VM. Always use both:

  1. Cloud firewall (Security Group) — Blocks traffic at the network edge
  2. Server firewall (UFW/iptables) — Blocks traffic at the OS level

If one layer is misconfigured, the other still provides protection. This is called defense in depth.

Emergency: Locked Yourself Out?

Accidentally blocked SSH? Most cloud providers have a console access feature:

  • DigitalOcean — Click "Console" in the control panel
  • AWS — Use EC2 Instance Connect or the serial console
  • GCP — Use "Browser SSH" or the serial port console

Once you have console access, reset your firewall:

# With UFW
sudo ufw disable
sudo ufw allow 22/tcp
sudo ufw enable

# With iptables
sudo iptables -P INPUT ACCEPT
sudo iptables -F
sudo iptables -A INPUT -p tcp --dport 22 -j ACCEPT
sudo iptables -P INPUT DROP

To prevent this in the future, always add your SSH allow rule before setting the default policy to DROP, and consider using a tool like tmux or screen so you have a backup session.

Security Checklist

After configuring your firewall, verify everything works:

# 1. Check firewall status
sudo ufw status verbose
# or
sudo iptables -L -n -v

# 2. Verify SSH still works (from another terminal!)
ssh user@your-server-ip

# 3. Test blocked ports
nmap -Pn your-server-ip
# Only SSH (22), HTTP (80), and HTTPS (443) should show as "open"

# 4. Check fail2ban
sudo fail2ban-client status

# 5. Test from external scanner (optional)
# https://www.grc.com/securityscan.htm

Summary

Firewalls are one of the most impactful security improvements you can make:

  • Use UFW for simplicity — it's designed for this exact use case
  • Default deny — Only allow traffic you explicitly need
  • Restrict by IP — Database ports should never face the internet
  • Add fail2ban — Protect against brute-force login attempts
  • Layer with cloud firewalls — Defense in depth means two independent protections
  • Test before relying — Always verify you can still SSH after changes

A properly configured firewall blocks the vast majority of automated attacks before they ever reach your applications. It's 5 minutes of setup that protects you 24/7. Don't skip it.
