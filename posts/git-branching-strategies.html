Git Branching Strategies: GitFlow, Trunk-Based & Feature Branches — Complete Guide

July 12, 2026 10 min read

If you've ever asked yourself, "Where should I make this change?" or "How do teams manage multiple features at once?", branching strategies are your answer. A branching strategy is the convention your team follows for creating, naming, and merging branches. It keeps collaboration organized, reduces conflicts, and makes code reviews manageable.

What Is a Branch?

A branch is an independent line of development. When you create a branch, you create a snapshot of the current state and start working from there. Changes on one branch don't affect other branches until you merge them.

# Create and switch to a new branch
git checkout -b feature/user-auth

# See all branches
git branch

# See all branches including remote
git branch -a

# Delete a branch
git branch -d feature/user-auth

The Main Branches

Most projects have at least two long-lived branches:

  • main (or master) — the production-ready code. This branch is always deployable.
  • develop — the integration branch where feature branches merge before release. Some strategies use this; others don't.
# Rename master to main (GitHub default now)
git branch -m master main

# Push the rename to remote
git push origin -u main

# Create a develop branch from main
git checkout -b develop main
git push -u origin develop

Strategy 1: Feature Branch Workflow

The simplest branching strategy. Everyone works on a feature branch, reviews via pull request (PR), then merges to main. This is the default for most open-source projects and small-to-medium teams.

How It Works

  1. Create a branch from main for each new feature or bug fix.
  2. Commit your changes to the feature branch.
  3. Open a pull request for review.
  4. After review and passing CI checks, merge to main.
  5. Delete the feature branch after merge.
# Start a new feature
git checkout main
git pull origin main
git checkout -b feature/dark-mode

# Work, commit, push
git add .
git commit -m "Add dark mode toggle"
git push -u origin feature/dark-mode

# Open PR on GitHub, get review, merge
# After merge:
git branch -d feature/dark-mode

Branch Naming Conventions

Consistent naming helps everyone understand what a branch does:

  • feature/what-you-do — new features
  • fix/what-you-fix — bug fixes
  • docs/update-readme — documentation changes
  • chore/update-deps — maintenance tasks
  • refactor/cleanup-utils — code refactoring
  • hotfix/critical-bug — urgent production fixes

Strategy 2: GitFlow

GitFlow is a more structured strategy designed for projects with scheduled releases. It defines specific branch types and their lifecycle. Popular in enterprise environments where releases happen on a fixed calendar.

The GitFlow Branches

  • main — production code. Tagged with version numbers (v1.0.0, v1.1.0).
  • develop — integration branch. Feature branches merge here.
  • feature/* — branches from develop, merge back to develop.
  • release/* — branched from develop when you're preparing a release. Used for final testing and bug fixes.
  • hotfix/* — branched from main for critical production fixes.
# Start developing a feature
git checkout develop
git checkout -b feature/payment-gateway

# ... work on feature ...
git add .
git commit -m "Add Stripe payment integration"
git push -u origin feature/payment-gateway

# Merge to develop via PR
git checkout develop
git merge --no-ff feature/payment-gateway

# Prepare for release v2.0.0
git checkout -b release/v2.0.0 develop
git tag -a v2.0.0-rc1 -m "Release candidate 1"

# Finalize release
git checkout main
git merge release/v2.0.0
git tag -a v2.0.0 -m "Release v2.0.0"

git checkout develop
git merge release/v2.0.0

When to Use GitFlow

GitFlow shines when you have:

  • Scheduled, versioned releases (v1.0, v1.1, etc.)
  • Multiple teams working on different features simultaneously
  • Need for stable release candidates before production
  • Desktop applications or libraries with formal release cycles

Avoid GitFlow if you deploy continuously (multiple times per day). It adds overhead that CI/CD teams don't need.

Strategy 3: Trunk-Based Development

The most streamlined strategy. Developers merge small changes to the main branch (main) multiple times per day. Branches exist only briefly — often less than a day. This is used by Google, Facebook, Netflix, and most high-velocity engineering teams.

How It Works

  1. Make small, incremental changes.
  2. Push to a short-lived branch (hours, not days).
  3. Automated CI runs tests on every commit.
  4. Merge to main as soon as CI passes.
  5. Use feature flags to hide incomplete features.
# Trunk-based: small changes, fast merges
git checkout main
git pull origin main
git checkout -b fix/typo-in-header

# One small commit
git add .
git commit -m "Fix typo in page header"
git push origin fix/typo-in-header

# CI passes? Merge immediately (squash merge on GitHub)
# Done. Branch deleted. Back to main in 5 minutes.

Feature Flags in Trunk-Based Development

Feature flags let you merge incomplete code without exposing it to users. You merge the code, but behind a flag that's disabled by default.

# Example: feature flag in Python (using a simple dict)
FEATURE_FLAGS = {
    "dark_mode": True,
    "new_dashboard": False,  # Code merged but not visible
    "beta_search": False,    # Merged for testing only
}

def show_dashboard(user):
    if FEATURE_FLAGS["new_dashboard"] or user.is_beta:
        return render_new_dashboard(user)
    return render_old_dashboard(user)

When to Use Trunk-Based

Choose trunk-based when you:

  • Deploy multiple times per day (CI/CD)
  • Have strong automated test coverage
  • Want to minimize merge conflicts
  • Build web services or SaaS products

Merge vs Rebase: Choosing Your Integration Style

When combining branches, you have two main options:

Merge (Default)

# Merge feature branch into main
git checkout main
git merge feature/dark-mode

# This creates a merge commit:
# A---B---C  main
#  \       /
#   D---E  feature/dark-mode
#        \
#         M (merge commit)

Merge preserves history exactly. You see when branches diverged and when they joined. Good for GitFlow and teams that value complete history.

Rebase

# Rebase feature branch onto main
git checkout feature/dark-mode
git rebase main

# This creates a linear history:
# A---B---C---D'---E'  feature/dark-mode
#                (rewritten commits)

Rebase produces a clean, linear history. No merge commits cluttering your log. Popular in trunk-based development.

⚠️ Golden Rule of Rebase: Never rebase commits that you've already pushed to a shared branch. Only rebase your local, unshared commits.

Interactive Rebase: Rewriting History

Before merging your feature branch, clean up your commit history with interactive rebase:

# Squash your last 3 commits into one clean commit
git rebase -i HEAD~3

# The editor opens with:
# pick a1b2c3d Add dark mode CSS
# pick e4f5g6h Fix typo in CSS class
# pick i7j8k9l Update dark mode README

# Change "pick" to "squash" for commits to combine:
# pick a1b2c3d Add dark mode CSS
# squash e4f5g6h Fix typo in CSS class
# squash i7j8k9l Update dark mode README

# Result: one clean commit with all changes
git push --force-with-lease

Choosing the Right Strategy

Here's a quick decision guide:

Team Size Release Cadence Recommended Strategy
1-5 Weekly+ Feature Branch Workflow
5-50 Daily/Continuous Trunk-Based Development
Any Scheduled (monthly, quarterly) GitFlow
Open Source Community-driven Feature Branch + Fork PR

Practical Exercise: Setting Up Your Project

Let's set up a new project with a solid branching strategy:

# 1. Initialize and connect to remote
mkdir my-project && cd my-project
git init
git remote add origin git@github.com:username/my-project.git

# 2. Create main branch with a basic README
echo "# My Project" > README.md
git add README.md
git commit -m "Initial commit"
git branch -M main
git push -u origin main

# 3. Set up branch protection (on GitHub)
#    Repository → Settings → Branches → Branch protection rules
#    - Require pull request reviews
#    - Require status checks to pass
#    - Require conversations to be resolved

# 4. Start your first feature
git checkout -b feature/user-signup
# ... build, commit, push ...
git push -u origin feature/user-signup
# Open PR → Review → Merge

Summary

Branching strategies are about finding the right balance between structure and speed. Start simple with the feature branch workflow, and adopt more complex strategies like GitFlow only when your release process demands it. If you're deploying continuously, trunk-based development with strong CI/CD is the way to go. The key is consistency — whatever strategy you choose, make sure the whole team follows it.
