Terraform Basics: Infrastructure as Code for Beginners — Complete Guide

July 11, 2026 13 min read

Imagine clicking buttons in a cloud console to create a server, then losing track of what you built three weeks later. Now imagine describing that server in a text file, version-controlled, reproducible, and shareable. That's Infrastructure as Code (IaC), and Terraform is the most popular tool to do it.

Terraform lets you define cloud infrastructure — servers, databases, networks, DNS records — in simple configuration files. You write what you want, and Terraform figures out how to build it. This guide teaches you everything from zero to deploying your first resource.

What Is Infrastructure as Code?

Traditionally, DevOps engineers managed infrastructure manually: logging into the AWS console, clicking "Create EC2 Instance", choosing a type, configuring security groups. This approach has problems:

  • No documentation — if someone leaves, no one knows what exists
  • Not reproducible — you can't recreate "the thing Bob set up" exactly
  • Error-prone — clicking the wrong option breaks production
  • Slow — provisioning takes minutes or hours per resource

Infrastructure as Code solves these by defining everything in code:

  • ✅ Version-controlled in Git — full history of every change
  • ✅ Reproducible — terraform apply creates identical infrastructure
  • ✅ Reviewable — changes go through pull requests
  • ✅ Fast — automated provisioning takes seconds

Why Terraform?

Terraform (by HashiCorp) is the leading IaC tool because:

  • Declarative syntax — you describe the desired state, not step-by-step commands
  • Multi-cloud — works with AWS, Azure, GCP, Cloudflare, and 300+ providers
  • State management — tracks what exists so it knows what to create/update/delete
  • Plan before apply — preview all changes before they happen
  • Large ecosystem — thousands of community modules and examples

Install Terraform

Install from the official site or use your package manager:

# macOS
brew install terraform

# Ubuntu/Debian
sudo apt update && sudo apt install -y terraform

# Verify installation
terraform version
# Terraform v1.10.x

Your First Terraform File

Let's create a local file to practice — no cloud account needed yet. Create a directory and a file called main.tf:

mkdir terraform-beginner
cd terraform-beginner

# Create your first Terraform config
cat > main.tf << 'EOF'
# This is a Terraform configuration file
# Comments start with #

terraform {
  required_version = ">= 1.0"
}

resource "null_resource" "example" {
  triggers = {
    value = "hello from terraform"
  }
}

output "greeting" {
  value = "Hello, Terraform!"
}
EOF

The null_resource is a practice resource — it doesn't create anything real but lets you learn Terraform syntax. Let's walk through the key blocks:

Terraform Block

terraform {
  required_version = ">= 1.0"
}

# The terraform block sets global configuration:
# - required_version: minimum Terraform version needed
# - required_providers: which cloud providers to use
# - backend: where to store the state file

Resource Block

resource "null_resource" "example" {
  triggers = {
    value = "hello from terraform"
  }
}

# Syntax: resource "TYPE" "NAME" { ... }
# TYPE  = the kind of thing (null_resource, aws_instance, etc.)
# NAME  = a local identifier (like a variable name)
# BODY  = configuration attributes for this resource

Output Block

output "greeting" {
  value = "Hello, Terraform!"
}

# Outputs display values after `terraform apply`
# Think of them as print() statements for your infrastructure

The Terraform Workflow: init → plan → apply

Every Terraform project follows the same three-step workflow:

Step 1: terraform init

Initializes the directory — downloads providers and plugins:

terraform init

# Output:
# Initializing the backend...
# Initializing provider plugins...
# - Installing hashicorp/null v3.2.1...
# Terraform has been successfully initialized!

Step 2: terraform plan

Shows what Terraform will do without making changes:

terraform plan

# Output:
# Terraform will perform the following actions:
#
#   # null_resource.example will be created
#   + resource "null_resource" "example" {
#       + id       = (known after apply)
#       + triggers = {
#           + value = "hello from terraform"
#         }
#     }
#
# Plan: 1 to add, 0 to change, 0 to destroy.

Step 3: terraform apply

Actually creates the resources:

terraform apply
# Type 'yes' to confirm

# Output:
# null_resource.example: Creating...
# null_resource.example: Creation complete after 0s
#
# Apply complete! Resources: 1 added, 0 changed, 0 destroyed.
#
# Outputs:
#
# greeting = "Hello, Terraform!"

Variables: Make Config Reusable

Hardcoding values makes configs brittle. Variables let you parameterize your infrastructure:

# variables.tf — Define input variables
variable "project_name" {
  description = "Name of the project"
  type        = string
  default     = "my-app"
}

variable "environment" {
  description = "Deployment environment"
  type        = string
  default     = "development"
}

variable "instance_count" {
  description = "Number of instances to create"
  type        = number
  default     = 1
}

# main.tf — Use variables
resource "null_resource" "server" {
  triggers = {
    name      = var.project_name
    env       = var.environment
    timestamp = timestamp()
  }
}

output "config" {
  value = "${var.project_name} in ${var.environment}"
}

# Set values via command line:
# terraform apply -var="project_name=production-app" -var="environment=staging"

# Or create a .tfvars file:
# terraform apply -var-file="production.tfvars"

The production.tfvars file looks like this:

# production.tfvars
project_name = "production-app"
environment  = "production"
instance_count = 3

Local Values: Computed Expressions

Use locals to create computed values derived from variables:

locals {
  common_tags = {
    Project     = var.project_name
    Environment = var.environment
    ManagedBy   = "terraform"
  }

  # Compose a name with environment prefix
  full_name = "${var.environment}-${var.project_name}"
}

output "full_name" {
  value = local.full_name
}

# Output: "development-my-app"

Data Sources: Read Existing Resources

Terraform can read existing cloud resources without managing them:

# Example: look up the latest Amazon Linux AMI
data "aws_ami" "amazon_linux" {
  most_recent = true
  owners      = ["amazon"]

  filter {
    name   = "name"
    values = ["amzn2-ami-hvm-*-x86_64-gp2"]
  }
}

# Reference the AMI ID
resource "aws_instance" "web" {
  ami           = data.aws_ami.amazon_linux.id
  instance_type = "t2.micro"
}

# data.* references read values but don't create resources

Modules: Reuse Configuration

Modules are reusable packages of Terraform configuration. Think of them as functions:

# Call a module from the registry
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "5.5.0"

  name = local.full_name
  cidr = "10.0.0.0/16"

  azs             = ["us-east-1a", "us-east-1b", "us-east-1c"]
  private_subnets = ["10.0.1.0/24", "10.0.2.0/24", "10.0.3.0/24"]
  public_subnets  = ["10.0.101.0/24", "10.0.102.0/24", "10.0.103.0/24"]

  enable_nat_gateway = true
  enable_vpn_gateway = false

  tags = local.common_tags
}

# Reference module outputs
output "vpc_id" {
  value = module.vpc.vpc_id
}

A Real Example: Cloudflare DNS with Terraform

Let's create a practical example — managing DNS records with the Cloudflare provider:

# providers.tf
terraform {
  required_version = ">= 1.0"

  required_providers {
    cloudflare = {
      source  = "cloudflare/cloudflare"
      version = "~> 4.0"
    }
  }
}

provider "cloudflare" {
  # Set via environment variables instead:
  # export CLOUDFLARE_EMAIL="you@example.com"
  # export CLOUDFLARE_API_TOKEN="your-api-token"
}

# variables.tf
variable "domain" {
  description = "The domain to manage DNS for"
  type        = string
  default     = "example.com"
}

variable "app_name" {
  description = "Application name"
  type        = string
  default     = "myapp"
}

# main.tf
resource "cloudflare_record" "app" {
  zone_id = data.cloudflare_zone.main.zone_id
  name    = "${var.app_name}.${var.domain}"
  type    = "A"
  content = "192.0.2.1"
  ttl     = 3600
  proxied = true  # Enable Cloudflare proxy (orange cloud)
}

resource "cloudflare_record" "www" {
  zone_id = data.cloudflare_zone.main.zone_id
  name    = "www.${var.domain}"
  type    = "CNAME"
  content = "${var.app_name}.${var.domain}"
  ttl     = 3600
  proxied = false
}

# Look up the zone ID automatically
data "cloudflare_zone" "main" {
  name = var.domain
}

# outputs.tf
output "app_url" {
  value       = "https://${var.app_name}.${var.domain}"
  description = "The URL of the application"
}

Run it:

terraform init
terraform plan   # See the 2 DNS records that will be created
terraform apply  # Create them on Cloudflare

Terraform State: How It Remembers Everything

Terraform tracks all resources in a terraform.tfstate file. This state file:

  • Maps Terraform resources to real cloud resources (via IDs)
  • Stores computed values and attributes
  • Enables safe plan/apply operations
# View state
terraform state list
# null_resource.example

# Show a specific resource's state
terraform state show null_resource.example

Never commit terraform.tfstate to Git — it may contain secrets. Use a remote backend instead:

terraform {
  backend "s3" {
    bucket = "my-terraform-state"
    key    = "prod/terraform.tfstate"
    region = "us-east-1"
  }
}

Destroying Infrastructure

When you're done, clean up everything:

# Preview what will be destroyed
terraform plan -destroy

# Destroy all resources
terraform destroy

# Output:
# Plan: 0 to add, 0 to change, 1 to destroy.
# Do you want to perform these actions?
# Terraform will perform the actions described above.
# Only 'yes' will be accepted to approve.
# Enter a value: yes

Common Terraform Commands

Command What It Does
terraform init Initialize the working directory
terraform plan Show what changes will be made
terraform apply Apply the planned changes
terraform destroy Delete all managed resources
terraform fmt Auto-format .tf files
terraform validate Check syntax without running
terraform state list List all tracked resources
terraform output Show defined outputs
terraform import Adopt existing resource into state

Best Practices for Beginners

  • Start small — manage one resource at a time
  • Always run terraform plan before apply
  • Use variables — never hardcode values
  • Use remote state — don't keep tfstate on your laptop
  • Use .tfvars files per environment (dev/staging/prod)
  • Run terraform fmt to keep code consistent
  • Use modules when you repeat patterns
  • Never commit state files or secrets to Git
  • Add .terraform and *.tfstate* to .gitignore

Key Takeaways

  • Terraform defines infrastructure as code — reproducible, version-controlled, reviewable
  • The core workflow: init → plan → apply
  • Use variables for input, locals for computed values, outputs for results
  • Modules let you reuse and share configuration patterns
  • State tracks what Terraform manages — keep it remote and never commit it
  • Terraform works with any cloud provider via plugins

Terraform transforms infrastructure from an art into an engineering discipline. Once you write your config, anyone can reproduce your entire cloud environment with terraform init && terraform apply. That's the power of Infrastructure as Code.
