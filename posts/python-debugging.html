Python Debugging: Stop Guessing, Start Finding Bugs Fast

2026-06-30

Every programmer spends more time debugging than writing new code. It's not a sign of bad code — it's just how software development works. The trick is finding bugs fast instead of staring at code for hours wondering why something doesn't work. In this guide, you'll learn five debugging techniques ranging from the simplest print() to powerful interactive debuggers, so you can fix problems quickly and move on.

Level 1: Strategic print() Statements

Before reaching for complex tools, print() is often the fastest way to understand what's happening. The key is being strategic — don't just print values, print enough context to diagnose the problem immediately.

Good vs Bad Print Debugging

# ❌ Bad: No context
print(x)
print(y)

# ✅ Good: Context-rich prints with labels
print(f"[DEBUG] Processing user {user_id}: name={name!r}, age={age}")
print(f"[DEBUG] API response: status={response.status_code}, length={len(data)}")

Notice the [DEBUG] prefix (makes grep easy later), the !r format specifier (shows repr, including quotes for strings), and variable names in the output. When you're scanning through output, you need to know what each line is without going back to the source code.

The "Rubber Duck" Print Technique

This is a real technique. Before adding any debug prints, write comments explaining what each line should do, line by line:

def calculate_discount(price, member, items):
    # Start with base price
    total = price
    # If member, apply 10% discount
    if member:
        total *= 0.9
    # If buying 3+ items, add 5% bulk discount on top
    if items >= 3:
        total *= 0.95
    # Round to 2 decimal places
    return round(total, 2)

# Bug: order matters! Member discount applied before bulk
# should be: total = price * (1 - member_discount - bulk_discount)

Writing the comments forces you to think through the logic — and often you'll spot the bug before you even add a single print statement.

Level 2: Using breakpoint() (Python 3.7+)

Python 3.7 added a built-in breakpoint() function. Drop it anywhere in your code and Python will pause execution at that line, giving you an interactive debugger (pdb) session:

def process_orders(orders):
    results = []
    for order in orders:
        # Pause here to inspect order
        breakpoint()
        total = sum(item["price"] for item in order["items"])
        results.append({"order_id": order["id"], "total": total})
    return results

# Run normally:
# python my_script.py
# When it hits breakpoint(), you'll see:
# > /path/to/my_script.py(14)process_orders()
# (Pdb)

Essential pdb Commands

Once you're in the debugger, here are the commands you'll use 90% of the time:

  • next (or n) — Execute the current line and move to the next line in the same function
  • step (or s) — Step into function calls
  • continue (or c) — Keep running until the next breakpoint
  • up (or u) / down (or d) — Move up/down the call stack
  • list (or l) — Show surrounding source code
  • pp variable — Pretty-print a variable
  • where (or w) — Show the full call stack
  • quit (or q) — Exit the debugger

Debugging Walkthrough

def find_max(numbers):
    max_val = numbers[0]
    for num in numbers:
        breakpoint()
        if num > max_val:
            max_val = num
    return max_val

# Run: python script.py
# (Pdb) n              # next line
# (Pdb) pp num         # pretty print current num: 5
# (Pdb) pp max_val     # current max: 3
# (Pdb) pp num > max_val  # evaluate expression: True
# (Pdb) c              # continue to next breakpoint
# (Pdb) q              # quit

The beauty of pdb is that you can evaluate any Python expression in the current context. If num and max_val are in scope, you can type num > max_val and get the result immediately — no need to guess.

Level 3: Conditional Breakpoints

You often want to pause only under specific conditions. Instead of stopping on every loop iteration, set a condition:

def find_errors(records):
    errors = []
    for i, record in enumerate(records):
        # Stop only when record fails validation
        breakpoint()  # In pdb: condition i == 42  OR
        # Use eval condition directly:
        if record.get("status") == "failed":
            breakpoint()
        errors.append(record)
    return errors

When you're at the breakpoint in pdb, you can set a persistent condition:

# In the pdb prompt:
(Pdb) condition 1 i == 42   # Only stop at breakpoint #1 when i==42
(Pdb) ignore 1               # Skip breakpoint #1 once
(Pdb) list breakpoints       # See all breakpoints

Level 4: Using logging for Production Debugging

You can't leave print() statements in production code. That's where the logging module shines:

import logging

# Configure logging once at startup
logging.basicConfig(
    level=logging.DEBUG,
    format="%(asctime)s [%(levelname)s] %(name)s: %(message)s",
    datefmt="%Y-%m-%d %H:%M:%S"
)

logger = logging.getLogger(__name__)

def connect_to_database(url):
    logger.debug("Attempting connection to: %s", url)  # Detailed info
    try:
        conn = database.connect(url)
        logger.info("Connected to database successfully")
        return conn
    except ConnectionError as e:
        logger.error("Connection failed: %s", e, exc_info=True)
        raise
    finally:
        logger.debug("Connection attempt completed")

Logging Levels — When to Use Each

  • DEBUG — Detailed info for diagnosing problems (variable values, loop iterations)
  • INFO — Confirmation that things are working as expected (connections, completions)
  • WARNING — Something unexpected happened but the app continues (deprecated feature used, retry attempt)
  • ERROR — A serious problem (function failed, API returned 500)
  • CRITICAL — The application may be unable to continue (database lost, config missing)

Production Logging Config

In production, you typically want less verbose output and JSON format for log aggregation tools:

import logging
import json
import os

class JsonFormatter(logging.Formatter):
    def format(self, record):
        return json.dumps({
            "timestamp": self.formatTime(record),
            "level": record.levelname,
            "logger": record.name,
            "message": record.getMessage(),
            "module": record.module,
            "line": record.lineno
        })

# Production config
handler = logging.StreamHandler()
handler.setFormatter(JsonFormatter())
logging.getLogger().addHandler(handler)
logging.getLogger().setLevel(os.environ.get("LOG_LEVEL", "WARNING"))

Now your logs appear as structured JSON that tools like Prometheus, Grafana, or ELK can easily parse and visualize.

Level 5: Post-Mortem Debugging with Tracebacks

When your program crashes, Python gives you a traceback. Most beginners just read the last line — but the entire traceback tells a story. Read it bottom-up to find the root cause:

Traceback (most recent call last):
  File "app.py", line 25, in <module>
    process_data(data)
  File "app.py", line 15, in process_data
    result = calculate_average(numbers)
  File "app.py", line 8, in calculate_average
    return sum(numbers) / len(numbers)
ZeroDivisionError: division by zero

The error is at line 8: dividing by zero because numbers is an empty list. But the real bug is at line 15 in process_data — why did it pass an empty list? That's where the fix belongs.

Auto-Debug with python -m pdb

When your script crashes, you can drop into pdb at the point of the crash:

# Run your script and auto-enter pdb on crash:
$ python -m pdb my_script.py
(Pdb) c                    # Continue running
# When crash happens:
> my_script.py(8)calculate_average()
    return sum(numbers) / len(numbers)
(Pdb) pp numbers           # [] — empty list!
(Pdb) up                   # Go up the stack to see where numbers came from

Bonus: VS Code Debugging

If you use VS Code, you get a visual debugger for free:

  1. Click the Debug icon (or press Ctrl+Shift+D)
  2. Create a .vscode/launch.json file
  3. Set breakpoints by clicking to the left of line numbers
  4. Press F5 to start debugging
// .vscode/launch.json
{
    "version": "0.2.0",
    "configurations": [
        {
            "name": "Python: Current File",
            "type": "debugpy",
            "request": "launch",
            "program": "${file}",
            "console": "integratedTerminal"
        }
    ]
}

VS Code lets you hover over variables to see values, add watches for complex expressions, and set conditional breakpoints with a UI — everything pdb offers but visually. For beginners, this is often the most accessible entry point to proper debugging.

Debugging Checklist

When you encounter a bug, work through this checklist instead of randomly trying things:

  1. Read the error message completely — especially the full traceback, not just the last line
  2. Reproduce it consistently — if you can't reproduce it, you can't fix it
  3. Isolate the problem — reduce the code to the smallest example that still triggers the bug
  4. Check your assumptions — "this variable should be a list" — is it really? print(type(x))
  5. Use a debugger — set a breakpoint and step through the code
  6. Google the error — but read the full context, not just the first result

Conclusion

Debugging is a skill that improves with practice. Start with strategic print() statements, graduate to breakpoint() and pdb, and adopt logging for production code. Each level gives you more power and precision. The goal isn't to avoid bugs — it's to find them quickly so you can fix them and move on.
