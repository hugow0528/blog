OAuth 2.0 and OpenID Connect: Authentication Explained — Complete Beginner's Guide

July 20, 2026 12 min read

OAuth 2.0 powers "Sign in with Google," "Log in with GitHub," and thousands of other login buttons you click daily. OpenID Connect (OIDC) extends OAuth 2.0 to handle user identity — who you are, not just what you can access. This guide walks through every concept with working Python code, from understanding authorization flows to building a complete login system.

Authentication vs Authorization: The Core Distinction

Before diving into OAuth 2.0, understand the fundamental difference:

  • Authentication (AuthN) — Who are you? Verifying identity via password, fingerprint, or a login provider like Google.
  • Authorization (AuthZ) — What can you do? Granting access to specific resources or actions.

OAuth 2.0 is an authorization framework — it lets you grant an app access to your data without sharing your password. OpenID Connect layers on authentication — proving who you are.

The OAuth 2.0 Players

OAuth 2.0 involves four key roles:

  • Resource Owner — The user (you). You own the data (your GitHub repos, Google Drive files).
  • Client — The application requesting access (a third-party app, your own service).
  • Authorization Server — The service that handles login and issues tokens (Google, GitHub, Auth0).
  • Resource Server — The service that hosts the data (GitHub API, Google Drive API).

In many setups, the authorization server and resource server are the same (e.g., Google does both).

The Authorization Code Flow: How "Sign in with Google" Works

The most common OAuth 2.0 flow for web and mobile apps is the Authorization Code flow. Here's the step-by-step process:

  1. User clicks "Sign in with Google" on your app.
  2. Your app redirects the user to Google's authorization URL with your client ID, redirect URI, requested scopes, and a state parameter.
  3. Google shows a consent screen — the user logs in and approves the requested permissions.
  4. Google redirects back to your redirect URI with an authorization_code in the URL.
  5. Your server exchanges the code for an access_token (and optionally a refresh_token) by sending a POST request to Google's token endpoint.
  6. Your server uses the access token to call Google's API on behalf of the user.

Building an OAuth 2.0 Client in Python

Let's implement the authorization code flow using Python's requests library. We'll use GitHub as our OAuth provider since it's free and easy to test:

import os
import secrets
import http.server
import urllib.parse
import requests

# Configuration
CLIENT_ID = "your_github_client_id"
CLIENT_SECRET = "your_github_client_secret"
REDIRECT_URI = "http://localhost:8000/callback"
SCOPES = ["user:email", "repo"]

def get_authorization_url():
    """Step 1: Build the URL to redirect the user to GitHub."""
    params = {
        "client_id": CLIENT_ID,
        "redirect_uri": REDIRECT_URI,
        "scope": " ".join(SCOPES),
        "state": secrets.token_urlsafe(16),  # CSRF protection
    }
    return "https://github.com/login/oauth/authorize?" + urllib.parse.urlencode(params)

def exchange_code_for_token(code, state):
    """Step 5: Exchange authorization code for access token."""
    response = requests.post(
        "https://github.com/login/oauth/access_token",
        data={
            "client_id": CLIENT_ID,
            "client_secret": CLIENT_SECRET,
            "code": code,
            "state": state,
        },
        headers={"Accept": "application/json"},
    )
    if response.status_code == 200:
        return response.json()["access_token"]
    raise Exception(f"Token exchange failed: {response.text}")

def get_user_info(access_token):
    """Step 6: Call the API with the access token."""
    response = requests.get(
        "https://api.github.com/user",
        headers={"Authorization": f"Bearer {access_token}"},
    )
    return response.json()

# Step 1: User clicks login → redirect to GitHub
auth_url = get_authorization_url()
print(f"Visit: {auth_url}")

A Simple HTTP Server for the Callback

Here's a complete working example with a local HTTP server to handle the OAuth callback:

import http.server
import json
import urllib.parse
import threading
import webbrowser
import requests

CLIENT_ID = "your_client_id"
CLIENT_SECRET = "your_client_secret"
REDIRECT_URI = "http://localhost:8000/callback"
STATE = None

class OAuthHandler(http.server.BaseHTTPRequestHandler):
    def do_GET(self):
        parsed = urllib.parse.urlparse(self.path)
        
        if parsed.path == "/":
            self.show_login_page()
        elif parsed.path == "/callback":
            self.handle_callback(parsed)
        else:
            self.send_error(404)
    
    def show_login_page(self):
        auth_url = get_authorization_url()
        html = f"""
        
        
            
Login with GitHub

            

        
        
        """
        self.send_response(200)
        self.send_header("Content-Type", "text/html")
        self.end_headers()
        self.wfile.write(html.encode())
    
    def handle_callback(self, parsed):
        params = urllib.parse.parse_qs(parsed.query)
        code = params.get("code", [None])[0]
        state = params.get("state", [None])[0]
        error = params.get("error", [None])[0]
        
        if error:
            self.send_error_response(f"OAuth error: {error}")
            return
        
        if state != STATE:
            self.send_error_response("State mismatch - possible CSRF attack!")
            return
        
        try:
            token = exchange_code_for_token(code, state)
            user = get_user_info(token)
            
            self.send_response(200)
            self.send_header("Content-Type", "text/html")
            self.end_headers()
            self.wfile.write(f"""
            
            
                
✅ Welcome, {user['login']}!

                
Email: {user.get('email', 'Not public')}

                
Access Token: {token[:15]}...

                
Token Type: {user.get('type', 'User')}

            
            
            """.encode())
        except Exception as e:
            self.send_error_response(f"Error: {str(e)}")
    
    def send_error_response(self, message):
        self.send_response(200)
        self.send_header("Content-Type", "text/html")
        self.end_headers()
        self.wfile.write(f"
Error
{message}
".encode())
    
    def log_message(self, format, *args):
        pass  # Suppress default logging

def get_authorization_url():
    global STATE
    STATE = secrets.token_urlsafe(16)
    params = {
        "client_id": CLIENT_ID,
        "redirect_uri": REDIRECT_URI,
        "scope": "user:email",
        "state": STATE,
    }
    return f"https://github.com/login/oauth/authorize?{urllib.parse.urlencode(params)}"

def exchange_code_for_token(code, state):
    resp = requests.post(
        "https://github.com/login/oauth/access_token",
        data={"client_id": CLIENT_ID, "client_secret": CLIENT_SECRET, "code": code, "state": state},
        headers={"Accept": "application/json"},
    )
    return resp.json()["access_token"]

def get_user_info(access_token):
    resp = requests.get("https://api.github.com/user", headers={"Authorization": f"Bearer {access_token}"})
    return resp.json()

# Start server and open browser
server = http.server.HTTPServer(("localhost", 8000), OAuthHandler)
print("Starting OAuth demo server on http://localhost:8000")
webbrowser.open("http://localhost:8000")
server.serve_forever()

Understanding OAuth 2.0 Tokens

OAuth 2.0 uses two types of tokens:

Access Tokens

Short-lived tokens used to access APIs. They expire after a set time (typically 1 hour for most providers). Sent in the Authorization header:

GET /api/user HTTP/1.1
Host: api.github.com
Authorization: Bearer gho_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx

Refresh Tokens

Long-lived tokens used to get new access tokens without requiring the user to log in again. Critical for keeping sessions alive:

import requests

def refresh_access_token(refresh_token):
    """Get a new access token using a refresh token."""
    response = requests.post(
        "https://github.com/login/oauth/access_token",
        data={
            "client_id": CLIENT_ID,
            "client_secret": CLIENT_SECRET,
            "grant_type": "refresh_token",
            "refresh_token": refresh_token,
        },
        headers={"Accept": "application/json"},
    )
    data = response.json()
    return {
        "access_token": data["access_token"],
        "token_type": data["token_type"],
        "scope": data["scope"],
    }

OpenID Connect: Adding Identity on Top of OAuth 2.0

OIDC is essentially OAuth 2.0 with an extra token called the ID token (a JWT). While OAuth 2.0 gives you an access token to call APIs, OIDC gives you an ID token that proves the user's identity.

The ID token is a JSON Web Token containing claims about the user:

{
  "iss": "https://accounts.google.com",
  "sub": "1234567890",          # Unique user ID
  "aud": "your_client_id",      # Your app
  "exp": 1721500000,            # Expiration timestamp
  "iat": 1721496400,            # Issued at timestamp
  "email": "user@example.com",  # Optional claim
  "name": "John Doe"            # Optional claim
}

PKCE: Securing Public Clients

For mobile apps, SPAs, or any client that can't securely store a client secret, use PKCE (Proof Key for Code Exchange). It prevents authorization code interception attacks:

import hashlib
import base64
import secrets

def generate_pkce_pair():
    """Generate PKCE code_verifier and code_challenge."""
    # Generate a random code_verifier
    code_verifier = secrets.token_urlsafe(64)
    
    # Create code_challenge from code_verifier (S256 method)
    code_challenge_bytes = hashlib.sha256(code_verifier.encode()).digest()
    code_challenge = base64.urlsafe_b64encode(code_challenge_bytes).rstrip(b'=').decode()
    
    return code_verifier, code_challenge

# Usage in authorization request
code_verifier, code_challenge = generate_pkce_pair()

auth_params = {
    "client_id": CLIENT_ID,
    "redirect_uri": REDIRECT_URI,
    "response_type": "code",
    "scope": "openid profile email",
    "code_challenge": code_challenge,
    "code_challenge_method": "S256",  # SHA-256
    "state": secrets.token_urlsafe(16),
}

# When exchanging the code, send the code_verifier
token_params = {

Scopes: Requesting Only What You Need

Scopes define what access you're requesting. Always request the minimum scopes needed:

# GitHub scopes
"user:email"      # Read email addresses
"repo"            # Full repo access
"read:org"        # Read org info only

# Google scopes  
"openid"          # Required for OIDC
"profile"         # Basic profile (name, picture)
"email"           # Email address
"https://www.googleapis.com/auth/drive.readonly"  # Read Drive files

# OAuth best practice: least privilege
# Don't request "repo" if you only need "public_repo"
# Don't request "drive" if you only need "drive.readonly"

Common Security Pitfalls

  • Never store client secrets in frontend code — they will be extracted. Use PKCE for SPAs and mobile apps.
  • Always validate the state parameter — prevents CSRF attacks by ensuring the callback matches the original request.
  • Always verify the iss and aud claims in ID tokens — ensures the token came from the expected provider and is meant for your app.
  • Store refresh tokens securely — use HTTP-only cookies or encrypted storage, never in localStorage.
  • Handle token expiration — implement automatic refresh before access tokens expire.
  • Use HTTPS everywhere — tokens in transit must be encrypted.

OAuth 2.0 vs OpenID Connect at a Glance

Here's a quick comparison:

Feature OAuth 2.0 OpenID Connect
Purpose Authorization Authentication + Authorization
Tokens Access Token, Refresh Token + ID Token (JWT)
Use Case API access ("read my calendar") Login ("Sign in with Google")
User Identity No built-in identity Standardized identity via ID token

Production Checklist

  • ✅ Use the Authorization Code flow with PKCE
  • ✅ Validate state on every callback
  • ✅ Verify ID token signature, iss, aud, and exp
  • ✅ Request minimum required scopes
  • ✅ Store tokens securely (HTTP-only cookies for web)
  • ✅ Implement token refresh logic
  • ✅ Use HTTPS for all OAuth endpoints
  • ✅ Log auth events (login success, failure, token refresh)
