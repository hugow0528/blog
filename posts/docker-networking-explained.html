Docker Networking Explained: Bridge, Host, None, and Custom Networks for Beginners

July 6, 2026 10 min read

Docker networking is one of those topics that seems mysterious until you understand the basics. How do containers talk to each other? How does the outside world reach a container? Why can one container "ping" another by name? This guide answers all of that with hands-on examples.

By the end, you'll understand Docker's built-in network drivers, how to create custom networks, DNS resolution between containers, and how to design network topologies for real applications.

Docker's Three Built-in Networks

When you install Docker, it creates three networks automatically:

$ docker network ls
NETWORK ID    NAME      DRIVER    SCOPE
abc123        bridge    bridge    local
def456        host      host      local
ghi789        none      null      local

1. Bridge Network (default)

When you run docker run without specifying a network, your container joins the bridge network. Each container gets its own private IP on a virtual network. The host can reach containers, but containers can't reach each other by name — only by IP.

# Two containers on the default bridge — can communicate by IP only
docker run -d --name web nginx
docker run -d --name db postgres

# The web container CAN'T ping "db" by name:
docker exec web ping db
# ping: db: Name or service not known

# But it CAN ping by IP:
docker exec web ping 172.17.0.3
# PING 172.17.0.3 — works!

The default bridge network assigns IPs dynamically, so the IP changes every time you restart a container. That's why it's fragile for multi-container apps.

2. Host Network

With the host network driver, a container shares the host's network stack entirely. No isolation, no port mapping needed, maximum performance:

# Container uses the host's IP and ports directly
docker run -d --network host nginx

# Access nginx directly on the host IP, no port mapping:
curl http://localhost:80

When to use host networking:

  • Performance-sensitive applications where NAT overhead matters
  • Monitoring agents that need to see all host traffic (Prometheus node exporter)
  • Applications that need access to the host's loopback interface

Downside: Port conflicts. You can't run two host-networked containers on the same port.

3. None Network

The none network gives a container no network interfaces. It's completely isolated — no external network, no DNS, nothing:

docker run --network none alpine ping google.com
# ping: bad address 'google.com' — no network at all

When to use none: Security-hardened containers that don't need network access, or containers where you'll set up custom networking via scripts.

Custom Bridge Networks: The Game Changer

Custom bridge networks solve the biggest problem with the default bridge: built-in DNS resolution. Containers on the same custom network can reach each other by container name.

# Step 1: Create a custom network
docker network create myapp-net

# Step 2: Run containers on that network
docker run -d --name web --network myapp-net nginx
docker run -d --name db --network myapp-net -e POSTGRES_PASSWORD=secret postgres

# Step 3: The web container can now reach "db" by name!
docker exec web ping db
# PING db (172.18.0.2): 56 data bytes — works!

# Even resolves in application code:
docker exec web wget -qO- http://db:5432
# Connection refused (expected — Postgres isn't on HTTP)
# But the DNS resolution worked!

Real-World Example: Three-Tier Application

Let's build a complete network topology with a frontend, API, and database:

# Create separate networks for isolation
docker network create frontend-net
docker network create backend-net

# Database — only on backend network (can't be reached from outside)
docker run -d \
  --name postgres \
  --network backend-net \
  -e POSTGRES_PASSWORD=supersecret \
  -e POSTGRES_DB=myapp \
  postgres:16-alpine

# API — on backend (to reach DB) AND frontend (to reach web server)
docker run -d \
  --name api \
  --network backend-net \
  --network frontend-net \
  -p 8000:8000 \
  python:3.12-slim \
  python -m http.server 8000

# Nginx frontend — on frontend network only
docker run -d \
  --name web \
  --network frontend-net \
  -p 80:80 \
  nginx:alpine

The network topology looks like this:

Internet → web (80) → api (8000) → postgres (5432)
              [frontend-net]   [backend-net]

Key security benefit: The database is unreachable from the internet and even from the web container. Only the API can talk to it because only the API shares the backend-net network.

Connecting Containers to Networks After Creation

You can add or remove containers from networks without recreating them:

# Connect a running container to a network
docker network connect backend-net some_other_container

# Disconnect a container from a network
docker network disconnect frontend-net some_other_container

# A container can be on multiple networks:
docker network connect backend-net web
# Now "web" can reach containers on both networks

Port Mapping Strategies

Understanding -p (publish) flag options gives you fine-grained control:

# Map host port 8080 to container port 80
docker run -d -p 8080:80 nginx
# Access at: http://localhost:8080

# Bind to a specific host interface (safer — not exposed on all interfaces)
docker run -d -p 127.0.0.1:8080:80 nginx
# Access at: http://localhost:8080 (NOT accessible from other machines)

# Publish all ports defined in the Dockerfile (EXPOSE)
docker run -d -P myapp

# Map to a random available port
docker run -d -p 80 nginx
docker port web  # Shows which random port was assigned

Docker Compose Networking

Docker Compose automatically creates a network for your stack. All services on the same Compose file can reach each other by service name:

# docker-compose.yml
services:
  web:
    image: nginx:alpine
    ports:
      - "80:80"
    depends_on:
      - api

  api:
    image: python:3.12-slim
    ports:
      - "127.0.0.1:8000:8000"  # Localhost only
    depends_on:
      - db

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: myapp
    volumes:
      - db-data:/var/lib/postgresql/data
    # No ports exposed — only reachable by other services

volumes:
  db-data:

Run it all:

docker compose up -d

# API can reach "db" by service name
# Web can reach "api" by service name
# Outside world can only reach "web" on port 80 and "api" on port 8000 (localhost)

Network Inspection and Debugging

Essential commands for troubleshooting:

# Inspect a network's configuration
docker network inspect myapp-net

# Get a container's IP address
docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' web

# Check DNS resolution from inside a container
docker exec web nslookup db

# Test connectivity
docker exec web curl -s http://db:5432 || echo "Cannot connect to db"

Best Practices Summary

  • Always use custom bridge networks instead of the default bridge — you get DNS resolution for free
  • Separate frontend and backend with different networks for security isolation
  • Don't expose database ports to the host — only API services should reach them
  • Bind to 127.0.0.1 when you only need local access (-p 127.0.0.1:8000:8000)
  • Use service names as DNS in Compose — they're stable across restarts
  • Avoid host networking in production unless you need raw performance — it removes isolation

Docker networking is simpler than it looks: create a network, put containers on it, and they can talk by name. Everything else — port mapping, multi-network setups, security isolation — builds on that foundation.
