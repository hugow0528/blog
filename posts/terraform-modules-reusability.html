Terraform Modules & Reusable Infrastructure: Stop Copy-Pasting Code

June 26, 2026 · 11 min read

You've learned Terraform basics and created some infrastructure. Now you notice a pattern: you keep writing the same VPC, the same S3 bucket, the same EC2 instance across different projects. Copy-pasting infrastructure code is a recipe for bugs, drift, and maintenance nightmares.

Terraform modules solve this. They let you package infrastructure into reusable, parameterized blocks — like functions in Python, but for your cloud resources. This guide walks you through building your own modules, using the public registry, and structuring modules for real teams.

What Is a Terraform Module?

A Terraform module is a self-contained set of .tf files that define infrastructure. Every Terraform configuration is technically a module — even a single main.tf file is called the root module. The real power comes when you call one module from another.

Think of it like Python imports: just as import requests gives you HTTP functionality without writing it yourself, a Terraform module gives you complete infrastructure blocks without duplicating the definition.

The Problem Without Modules

# Project A: main.tf
resource "aws_s3_bucket" "data" {
  bucket = "my-project-a-data"
  tags = {
    Environment = "production"
    Owner       = "team-frontend"
  }
}

# Project B: main.tf (copy-pasted!)
resource "aws_s3_bucket" "data" {
  bucket = "my-project-b-data"
  tags = {
    Environment = "production"
    Owner       = "team-backend"  # Different owner, but everything else the same
  }
}

Now imagine you need to add versioning, encryption, and lifecycle rules to every bucket. You'd have to edit every single copy. Modules centralize this.

Creating Your First Module

Let's build a reusable S3 bucket module. Create this directory structure:

modules/
└── s3_bucket/
    ├── main.tf
    ├── variables.tf
    └── outputs.tf

Step 1: Define Inputs (variables.tf)

# modules/s3_bucket/variables.tf
variable "bucket_name" {
  description = "Name of the S3 bucket"
  type        = string
}

variable "tags" {
  description = "Tags to apply to the bucket"
  type        = map(string)
  default     = {}
}

variable "enable_versioning" {
  description = "Enable versioning on the bucket"
  type        = bool
  default     = true
}

variable "enable_encryption" {
  description = "Enable server-side encryption"
  type        = bool
  default     = true
}

Step 2: Write the Resources (main.tf)

# modules/s3_bucket/main.tf
resource "aws_s3_bucket" "this" {
  bucket = var.bucket_name

  tags = merge(var.tags, {
    ManagedBy = "terraform"
    Module    = "s3_bucket"
  })
}

resource "aws_s3_bucket_versioning" "this" {
  count = var.enable_versioning ? 1 : 0

  bucket = aws_s3_bucket.this.id

  versioning_configuration {
    status = "Enabled"
  }
}

resource "aws_s3_bucket_server_side_encryption_configuration" "this" {
  count = var.enable_encryption ? 1 : 0

  bucket = aws_s3_bucket.this.id

  rule {
    apply_server_side_encryption_by_default {
      sse_algorithm = "aws:kms"
    }
  }
}

Step 3: Define Outputs (outputs.tf)

# modules/s3_bucket/outputs.tf
output "bucket_id" {
  description = "The ID of the S3 bucket"
  value       = aws_s3_bucket.this.id
}

output "bucket_arn" {
  description = "The ARN of the S3 bucket"
  value       = aws_s3_bucket.this.arn
}

output "bucket_domain_name" {
  description = "The domain name of the bucket"
  value       = aws_s3_bucket.this.bucket_domain_name
}

Using Your Module

Now call this module from your root configuration:

# main.tf
module "frontend_bucket" {
  source = "./modules/s3_bucket"

  bucket_name = "my-frontend-assets-prod"
  tags = {
    Environment = "production"
    Owner       = "team-frontend"
  }
  enable_versioning = true
}

module "backend_bucket" {
  source = "./modules/s3_bucket"

  bucket_name = "my-backend-data-prod"
  tags = {
    Environment = "production"
    Owner       = "team-backend"
  }
  enable_versioning = true
  enable_encryption = true
}

Two buckets, one module definition. Add logging support? Edit one file. Want to remove versioning for a test bucket? Override the variable for just that instance.

Accessing Module Outputs

# Use outputs from your modules
resource "aws_cloudfront_distribution" "cdn" {
  origin {
    domain_name = module.frontend_bucket.bucket_domain_name
    origin_id   = module.frontend_bucket.bucket_id
  }
}

Using the Terraform Public Registry

You don't always need to write your own modules. The Terraform Registry has thousands of community-built modules.

# Use a popular VPC module from the registry
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "5.1.0"

  name = "my-vpc"
  cidr = "10.0.0.0/16"

  azs             = ["us-east-1a", "us-east-1b", "us-east-1c"]
  private_subnets = ["10.0.1.0/24", "10.0.2.0/24", "10.0.3.0/24"]
  public_subnets  = ["10.0.101.0/24", "10.0.102.0/24", "10.0.103.0/24"]

  enable_nat_gateway = true
  single_nat_gateway = true

  tags = {
    Terraform   = "true"
    Environment = "production"
  }
}

This single module call creates a VPC with public/private subnets, NAT gateway, internet gateway, and route tables. What would be 200+ lines becomes 20.

Module Sources: Where Can Modules Come From?

# Local path
module "local" {
  source = "./modules/s3_bucket"
}

# Terraform Registry
module "registry" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "5.1.0"
}

# GitHub
module "github" {
  source = "git::https://github.com/org/module.git?ref=v1.0.0"
}

# Git with subdirectory
module "git_subdir" {
  source = "git::https://github.com/org/modules.git//networking?ref=v2.0.0"
}

# HTTP archive
module "http" {
  source = "https://example.com/modules/vpc.zip"
}

Module Design Best Practices

1. Keep Modules Focused (Single Responsibility)

Each module should do one thing well. An S3 module handles S3. A VPC module handles networking. Don't mix concerns — that's how you get unmaintainable mega-modules.

2. Use Sensitive Variables Properly

variable "db_password" {
  description = "Database master password"
  type        = string
  sensitive   = true  # Won't show in terraform plan output
}

3. Version Your Modules

Always pin versions for registry modules. For local modules, use Git tags:

# Pin to a specific version
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "~> 5.0"  # >= 5.0.0, < 6.0.0
}

# Use Git tag for self-hosted modules
module "network" {
  source = "git::https://github.com/myorg/infra-modules.git?ref=v1.2.0"
}

4. Write Readme Files

Every module deserves a README.md with inputs, outputs, and an example. This is non-negotiable for team usage.

5. Test With Terraform Validate

# Validate syntax without applying
terraform init
terraform validate

# Validate a specific module
terraform init -backend=false
cd modules/s3_bucket
terraform validate

Real-World Module Structure for Teams

Here's how production teams typically organize their Terraform code:

infrastructure/
├── modules/
│   ├── vpc/
│   ├── s3_bucket/
│   ├── rds/
│   └── ec2/
├── environments/
│   ├── dev/
│   │   ├── main.tf
│   │   ├── variables.tf
│   │   └── terraform.tfvars
│   ├── staging/
│   │   ├── main.tf
│   │   ├── variables.tf
│   │   └── terraform.tfvars
│   └── prod/
│       ├── main.tf
│       ├── variables.tf
│       └── terraform.tfvars
├── .gitignore
└── README.md

Each environment calls the same modules with different configurations. Change the module, and all environments get the improvement.

Example: Dev Environment

# environments/dev/main.tf
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = var.aws_region
}

module "vpc" {
  source = "../../modules/vpc"

  environment       = "dev"
  cidr              = "10.0.0.0/16"
  instance_count    = 1
  enable_nat        = false  # Save money in dev
}

module "app_bucket" {
  source = "../../modules/s3_bucket"

  bucket_name        = "myapp-dev-assets"
  enable_versioning  = false  # Don't need history in dev
  enable_encryption  = true
}

Module Dependencies and Count

Sometimes you need a variable number of resources. Combine count with module calls:

# Create 3 S3 buckets from a list
locals {
  bucket_names = ["uploads", "exports", "backups"]
}

module "buckets" {
  source = "./modules/s3_bucket"
  count  = length(local.bucket_names)

  bucket_name       = "${var.project}-${local.bucket_names[count.index]}"
  enable_versioning = true

  tags = {
    Purpose = local.bucket_names[count.index]
  }
}

# Access specific bucket outputs
output "uploads_arn" {
  value = module.buckets[0].bucket_arn
}

output "exports_arn" {
  value = module.buckets[1].bucket_arn
}

Common Pitfalls to Avoid

  • Too many variables: If your module has 30+ inputs, it's probably doing too much. Split it up.
  • Hardcoded values inside modules: Everything should be parameterized. Even the region.
  • Ignoring outputs: Always expose what downstream modules need. Better to have extra outputs than missing ones.
  • No version pinning: An unversioned module can silently break your infrastructure when it gets updated.
  • Creating resources without naming: Always include name or identifier variables so resources are recognizable in the cloud console.

Summary

Terraform modules transform your infrastructure from copy-paste scripts into clean, reusable code. The key takeaways:

  1. Structure: main.tf + variables.tf + outputs.tf
  2. Sources: local paths, Terraform Registry, Git, HTTP archives
  3. Best practices: single responsibility, version pinning, sensitive handling, documentation
  4. Team pattern: shared modules/ folder with per-environment directories

Start small — module-ize your most-repeated resource today. Your future self (and your team) will thank you.
