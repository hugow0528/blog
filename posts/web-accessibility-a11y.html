Web Accessibility (a11y): Build Sites Everyone Can Use

July 2, 2026 10 min read

Over 1 billion people worldwide live with some form of disability. That's roughly 15% of the global population. Yet most websites still don't work for them. Web accessibility (often abbreviated as a11y — "a" + 11 letters + "y") is the practice of making your websites usable by as many people as possible.

Accessibility isn't just a nice-to-have — it's often required by law (the ADA, EU Web Accessibility Directive, Section 508), and it improves your site for everyone. Clear navigation helps tourists. Captions help people watching videos on a noisy bus. Good contrast helps everyone reading in bright sunlight.

The Four Principles: POUR

The Web Content Accessibility Guidelines (WCAG) are built on four principles, known by the acronym POUR:

  • Perceivable — Content must be presentable in ways users can perceive (not all-zero for sight, hearing, etc.)
  • Operable — Users must be able to operate the interface (keyboard, voice, switch device)
  • Understandable — Content and UI operation must be understandable
  • Robust — Content must be robust enough for different user agents (browsers, screen readers)

1. Semantic HTML: The Foundation of Accessibility

The single biggest thing you can do for accessibility is use semantic HTML. Every HTML element has built-in accessibility information — a button knows it's a button, a heading knows it's a heading, a link knows it's a link.

Don't do this:

<!-- ❌ Bad: A div pretending to be a button -->
<div onclick="goToDashboard()" style="background: blue; padding: 10px;">
    Go to Dashboard
</div>

<!-- ❌ Bad: Using div for headings -->
<div style="font-size: 24px; font-weight: bold;">Page Title</div>

Do this instead:

<!-- ✅ Good: Real button, real heading -->
<button onclick="goToDashboard()">Go to Dashboard</button>
<h1>Page Title</h1>

Screen readers announce semantic elements to users. A <button> tells the user "button, go to dashboard, press space or enter to activate." A div tells them nothing useful.

Heading Hierarchy Matters

Use headings in order. Don't skip from <h1> to <h4>. Screen reader users often navigate by jumping between headings — it's their version of skimming.

<!-- ✅ Correct heading structure -->
<h1>Page Title</h1>
  <h2>Section One</h2>
    <h3>Subsection A</h3>
    <h3>Subsection B</h3>
  <h2>Section Two</h2>
    <h3>Subsection C</h3>
</h1>

2. Alternative Text for Images

Every image needs an alt attribute. The alt text should describe the information the image conveys, not the image itself.

<!-- ❌ Bad: Useless alt text -->
<img src="chart.png" alt="image">
<img src="chart.png" alt="chart showing data">

<!-- ✅ Good: Describes the information -->
<img src="chart.png" alt="Bar chart showing Q1-Q4 revenue: Q1 $12K, Q2 $15K, Q3 $11K, Q4 $18K">

<!-- ✅ Decorative images get empty alt -->
<img src="decorative-line.svg" alt="">

Complex images like charts need longer descriptions. Use <figure> with <figcaption>:

<figure>
    <img src="architecture.png" alt="System architecture diagram">
    <figcaption>
        The frontend connects to the API gateway, which routes to three microservices:
        auth-service, user-service, and payment-service. All services communicate via
        the message queue.
    </figcaption>
</figure>

3. Color and Contrast

Never use color as the only way to convey information. 1 in 12 men and 1 in 200 women have color blindness.

<!-- ❌ Bad: Color-only indicators -->
<span class="error">Please fix the following errors</span>
<!-- Only red color tells them it's an error -->

<!-- ✅ Good: Color + icon + text -->
<div class="error-message" role="alert">
    ⚠️ Please fix the following errors:
    <ul>
        <li>Email field is required</li>
        <li>Password must be at least 8 characters</li>
    </ul>
</div>

For text contrast, WCAG 2.1 requires:

  • Level AA (minimum): 4.5:1 ratio for normal text, 3:1 for large text (18px+ or 14px+ bold)
  • Level AAA (enhanced): 7:1 for normal text, 4.5:1 for large text

Test your contrast with browser DevTools (right-click → Inspect → Elements tab → Computed → check color contrast) or free tools like WebAIM Contrast Checker.

4. Keyboard Navigation

Every interactive element must be usable with a keyboard. The Tab key moves focus between elements, Enter/Space activates buttons and links, and arrow keys navigate menus and lists.

<!-- ✅ Make custom components keyboard accessible -->
<div
    role="button"
    tabindex="0"
    aria-pressed="false"
    onclick="toggleMenu()"
    onkeydown="if(event.key==='Enter'||event.key===' '){event.preventDefault();toggleMenu()}"
>
    Toggle Menu
</div>

Key rules for keyboard navigation:

  • Use tabindex="0" to make custom elements focusable
  • Never use tabindex values above 0 (it creates confusing tab orders)
  • Always show a visible focus indicator (don't set outline: none without a replacement)
  • Use <button> for actions, <a> for navigation

5. Forms: Labels and Error Messages

Forms are where accessibility matters most. Every input needs a properly associated label:

<!-- ❌ Bad: Placeholder as label -->
<input type="email" placeholder="Enter your email">

<!-- ❌ Bad: Visually hidden but unassociated label -->
<span style="display:none">Email</span>
<input type="email">

<!-- ✅ Good: Explicit label association -->
<label for="email">Email address</label>
<input type="email" id="email" name="email" autocomplete="email">

<!-- ✅ Good: Wrapping label (no id needed) -->
<label>
    Email address
    <input type="email" name="email" autocomplete="email">
</label>

Accessible Error Handling

<form novalidate>
    <label for="password">Password</label>
    <input
        type="password"
        id="password"
        aria-describedby="password-hint"
        aria-invalid="true"
    >
    <span id="password-hint">Must be at least 12 characters</span>
    <div role="alert" aria-live="polite">
        Password does not meet requirements
    </div>

    <!-- Group related fields with fieldset -->
    <fieldset>
        <legend>Shipping Address</legend>
        <label for="street">Street</label>
        <input type="text" id="street" name="street">
        <label for="city">City</label>
        <input type="text" id="city" name="city">
    </fieldset>
</form>

6. ARIA Attributes

ARIA (Accessible Rich Internet Applications) attributes add accessibility information when HTML alone isn't enough. But remember: the best ARIA attribute is no ARIA attribute. Use native HTML first.

Common ARIA attributes you'll use:

<!-- Live regions for dynamic content -->
<div aria-live="polite">
    Results updated: 3 new notifications
</div>

<!-- Landmark roles (mostly automatic in HTML5) -->
<nav aria-label="Main navigation">...</nav>
<main>...</main>
<aside aria-label="Related articles">...</aside>

<!-- State management -->
<button aria-expanded="false" aria-controls="dropdown-menu">
    Options
</button>
<div id="dropdown-menu" hidden>...</div>

<!-- Descriptions -->
<button aria-describedby="search-help">Search</button>
<span id="search-help">Press Enter to search all articles</span>

7. Skip Navigation Links

Keyboard users have to tab through every navigation item to reach content. A skip link lets them jump straight to the main content:

<!-- First element in your <body> -->
<a href="#main-content" class="skip-link">Skip to main content</a>

<header>...navigation...</header>
<main id="main-content">...content...</main>

<!-- CSS to show skip link only when focused -->
<style>
.skip-link {
    position: absolute;
    top: -40px;
    left: 0;
    background: #000;
    color: #fff;
    padding: 8px 16px;
    z-index: 100;
    transition: top 0.2s;
}
.skip-link:focus {
    top: 0;
}
</style>

8. Testing for Accessibility

Use these tools to audit your site:

  • Browser DevTools: Chrome, Firefox, and Edge all have built-in Lighthouse audits (right-click → Inspect → Lighthouse tab)
  • axe DevTools: Browser extension that identifies accessibility issues in real-time
  • WAVE: Web Accessibility Evaluation Tool — browser extension and online checker
  • NVDA (free) / VoiceOver (built-in to macOS): Actual screen readers — test your site using one
  • Keyboard-only testing: Unplug your mouse and try to use your entire site with Tab, Enter, Space, and arrow keys

Quick Accessibility Checklist

Before shipping any page, run through this checklist:

  1. ✓ All images have meaningful alt text (or empty alt if decorative)
  2. ✓ Headings are in logical order (h1 → h2 → h3)
  3. ✓ All form inputs have associated labels
  4. ✓ Text has sufficient color contrast (4.5:1 minimum)
  5. ✓ All interactive elements are keyboard accessible
  6. ✓ Focus indicators are visible
  7. ✓ Page has a skip navigation link
  8. ✓ Dynamic content updates use aria-live regions
  9. ✓ Content is readable at 200% zoom without horizontal scrolling
  10. ✓ Language is declared: <html lang="en">

Accessibility in JavaScript Frameworks

The same principles apply whether you're using vanilla HTML, React, Vue, or any framework:

// React example: accessible modal
import { useState, useEffect } from 'react';

function AccessibleModal({ isOpen, onClose, children }) {
    const [prevActiveElement, setPrevActiveElement] = useState(null);

    useEffect(() => {
        if (isOpen) {
            // Save the previously focused element
            setPrevActiveElement(document.activeElement);
            // Focus the modal
            document.querySelector('[role="dialog"]')?.focus();
            // Trap focus within the modal
            // Prevent background scrolling
            document.body.style.overflow = 'hidden';
        }
        return () => {
            document.body.style.overflow = '';
            prevActiveElement?.focus();
        };
    }, [isOpen]);

    // Close on Escape key
    useEffect(() => {
        const handleKeyDown = (e) => {
            if (e.key === 'Escape') onClose();
        };
        if (isOpen) window.addEventListener('keydown', handleKeyDown);
        return () => window.removeEventListener('keydown', handleKeyDown);
    }, [isOpen, onClose]);

    if (!isOpen) return null;

    return (
        <div className="modal-overlay" onClick={onClose}>
            <div
                role="dialog"
                aria-modal="true"
                aria-labelledby="modal-title"
                tabIndex={-1}
                onClick={(e) => e.stopPropagation()}
            >
                <h2 id="modal-title">Modal Title</h2>
                {children}
                <button onClick={onClose} aria-label="Close modal">
                    Close
                </button>
            </div>
        </div>
    );
}

Moving Forward

Accessibility isn't something you bolt on at the end — it's part of building a good website. Every principle of accessible design (clear structure, good contrast, keyboard support, descriptive labels) makes your site better for everyone, not just people with disabilities.

Start with semantic HTML. Add proper labels and alt text. Test with keyboard and screen reader. Run automated audits before deploying. You don't need to be an a11y expert — you just need to care enough to check.
