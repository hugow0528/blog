SSH Security: Secure Your Remote Server Access

June 23, 2026 · 10 min read

SSH (Secure Shell) is the most common way to access remote servers. It's powerful, ubiquitous, and — by default — surprisingly insecure. Attackers run automated SSH brute-force attacks 24/7, targeting port 22 across the internet. If you've ever left a server with default SSH settings connected to the internet, it's likely already been probed thousands of times.

This guide walks you through hardening your SSH configuration step by step — from setting up key-based authentication to deploying fail2ban. By the end, your server will be significantly harder for attackers to compromise, and you'll understand why each step matters.

Why SSH Security Matters

SSH gives you full shell access to a server. If an attacker gains access, they can read files, install malware, steal data, pivot to other servers, or use your machine for attacks. The consequences range from downtime to complete data loss.

Stat: On a typical cloud server, automated bots attempt SSH logins within seconds of the server coming online. A weak password means you're compromised almost instantly.

Let's build defense layers from the ground up.

Step 1: Set Up SSH Key-Based Authentication

Passwords are vulnerable to brute-force attacks. SSH keys use asymmetric cryptography — you generate a private key (never share it) and a public key (put it on servers). When you connect, the server proves it has your public key, and you prove you have the matching private key. No password guessing possible.

Generate an SSH key pair on your local machine:

# Generate a modern Ed25519 key (preferred over RSA)
ssh-keygen -t ed25519 -C "your-email@example.com"

# You'll see:
# Generating public/private ed25519 key pair.
# Enter file in which to save the key (/home/user/.ssh/id_ed25519): [press Enter]
# Enter passphrase (empty for no passphrase): [enter a strong passphrase]
# Enter same passphrase again: [confirm]

# Check your keys exist
ls -la ~/.ssh/id_ed25519 ~/.ssh/id_ed25519.pub

Copy the public key to your server:

# Method 1: Use ssh-copy-id (easiest)
ssh-copy-id -i ~/.ssh/id_ed25519.pub user@your-server-ip

# Method 2: Manual copy
cat ~/.ssh/id_ed25519.pub
# Copy the output, then on the server run:
mkdir -p ~/.ssh
chmod 700 ~/.ssh
echo "ssh-ed25519 AAAA...your-public-key... user@host" >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys

Test the connection before disabling passwords:

# Connect using your key
ssh user@your-server-ip

# If it works without asking for a password, keys are configured correctly
# (you may still be asked for the passphrase you set during key generation)

Step 2: Disable Password Authentication

Now that your keys work, prevent anyone from using passwords — this blocks brute-force attacks entirely.

Edit the SSH configuration on the server:

# Open the SSH config file
sudo nano /etc/ssh/sshd_config

# Find and change these lines:
PasswordAuthentication no
ChallengeResponseAuthentication no
PubkeyAuthentication yes

# Also ensure these are set:
PermitRootLogin no
X11Forwarding no

# Save and restart SSH
sudo systemctl restart sshd
⚠️ WARNING: Before restarting SSH, test your key authentication in a second terminal window. If you lock yourself out, you'll need console access (via your cloud provider's web console) to fix it.

Step 3: Change the Default SSH Port

Most automated scanners target port 22 exclusively. Changing the port won't stop a determined attacker, but it eliminates ~90% of noise from your logs.

# Edit SSH config again
sudo nano /etc/ssh/sshd_config

# Change this line:
Port 2222

# Save and restart
sudo systemctl restart sshd

# Now connect using the new port
ssh -p 2222 user@your-server-ip

Or add it to your local ~/.ssh/config so you don't have to type -p 2222 every time:

# ~/.ssh/config
Host myserver
    HostName your-server-ip
    User your-username
    Port 2222
    IdentityFile ~/.ssh/id_ed25519

# Now just type:
ssh myserver

Step 4: Install and Configure fail2ban

Even with keys and a custom port, you should monitor for suspicious activity. fail2ban scans log files for repeated failed login attempts and automatically bans the offending IP address.

# Install fail2ban
sudo apt update && sudo apt install -y fail2ban

# Create a custom jail config (don't edit the defaults directly)
sudo nano /etc/fail2ban/jail.local

# Add this content:
[sshd]
enabled = true
port = 2222          # your custom port
filter = sshd
logpath = /var/log/auth.log
maxretry = 3         # ban after 3 failed attempts
bantime = 3600       # ban for 1 hour (3600 seconds)
findtime = 600       # look at the last 10 minutes

[sshd-ddos]
enabled = true
port = 2222
filter = sshd-ddos
logpath = /var/log/auth.log
maxretry = 5
bantime = 3600

# Start and enable fail2ban
sudo systemctl start fail2ban
sudo systemctl enable fail2ban

# Check status
sudo fail2ban-client status sshd

Example output:

Status for the jail: sshd
|- Filter
|  |- Currently failed: 0
|  |- Total failed: 42
|  `- Journal matches: _SYSTEMD_UNIT=sshd.service + _COMM=sshd
`- Actions
   |- Currently banned: 3
   `- Total banned: 7

To unban an IP you accidentally locked yourself out with:

# Manually unban an IP
sudo fail2ban-client set sshd unbanip 192.168.1.100

# List all banned IPs
sudo fail2ban-client get sshd banip

Step 5: Restrict SSH Access with AllowUsers

Limit which users can SSH into the server. Even if someone obtains a key for a restricted account, they still can't log in via SSH.

# Edit SSH config
sudo nano /etc/ssh/sshd_config

# Add this line (list allowed users, space-separated):
AllowUsers your-username deploy-user

# Optionally restrict by IP/CIDR:
# AllowUsers your-username@192.168.1.0/24

sudo systemctl restart sshd

Step 6: Set Up Automatic Key Rotation Reminder

SSH keys can be compromised if your local machine is infected. Rotate keys periodically and check their fingerprint:

# Check your key fingerprint (compare when connecting to a new server)
ssh-keygen -lf ~/.ssh/id_ed25519.pub

# Check known hosts file for stale entries
cat ~/.ssh/known_hosts

# Remove a stale host entry
ssh-keygen -R old-server-ip

Bonus: Use UFW Firewall to Restrict SSH Access

The Uncomplicated Firewall (UFW) is the easiest way to set up a firewall on Ubuntu/Debian servers. You can restrict SSH to specific IP addresses:

# Install UFW
sudo apt install -y ufw

# Set default policies
sudo ufw default deny incoming
sudo ufw default allow outgoing

# Allow SSH only from your home IP
sudo ufw allow from YOUR_HOME_IP to any port 2222

# Or allow SSH from a range
sudo ufw allow from 203.0.113.0/24 to any port 2222

# Enable UFW
sudo ufw enable

# Check status
sudo ufw status verbose

Example output:

Status: active
To                         Action      From
--                         ------      ----
2222/tcp                   ALLOW IN    203.0.113.5
22/tcp                     ALLOW IN    Anywhere
22/tcp (v6)                ALLOW IN    Anywhere (v6)

Putting It All Together: The Hardened Checklist

  1. ✅ SSH key pair generated (Ed25519 preferred)
  2. ✅ Public key deployed to server
  3. ✅ Password authentication disabled
  4. ✅ Root login disabled
  5. ✅ Custom SSH port configured
  6. ✅ fail2ban installed and monitoring SSH
  7. ✅ AllowUsers restricting who can log in
  8. ✅ UFW firewall blocking SSH from unauthorized IPs

Common Mistakes to Avoid

  • Never share your private key. If it's compromised, generate a new pair and update all servers.
  • Always test in a second terminal. Before disabling password auth or restarting SSH, keep a backup session open.
  • Use a passphrase on your key. An unencrypted private key on disk is useless security if someone steals it.
  • Don't rely on port changing alone. It hides from scripts, not from attackers who scan all ports. Always use keys.
  • Update OpenSSH regularly. Run sudo apt update && sudo apt upgrade openssh-server to patch vulnerabilities.

Summary

SSH security is layered defense. Each step — keys, port changes, fail2ban, firewall rules, user restrictions — independently makes your server harder to compromise. Together, they create a formidable barrier against automated attacks.

Start with key-based authentication and disabling password login. Those two steps alone will stop the vast majority of attacks. Then layer on fail2ban and firewall rules for defense in depth.

The goal isn't to be unbreachable — no system is. The goal is to make yourself a boring target that attackers move on from because the effort outweighs the reward. Properly hardened SSH gets you remarkably close to that goal.
