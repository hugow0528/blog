JavaScript Closures and Scope: The Concept Every Developer Must Master

July 3, 2026 9 min read New

Interviewers ask about closures. Senior developers use closures every day. Build tools rely on closures. Yet closures remain one of the most misunderstood concepts in JavaScript. This guide will make them click — once and for all.

A closure is a function that retains access to variables from its parent scope, even after the parent function has finished executing. That's the textbook definition. Let's see what that actually means in practice.

Scope Basics: Where Variables Live

JavaScript has lexical scoping (also called static scoping). The scope of a variable is determined by where it's written in the code — not by where or when it's called.

// Global scope — accessible everywhere
const globalVar = "I'm global";

function outer() {
    // outer's scope — accessible in outer and inner
    const outerVar = "I'm in outer";

    function inner() {
        // inner's scope — accessible only here
        const innerVar = "I'm in inner";

        console.log(globalVar);  // ✅ Works — global is accessible
        console.log(outerVar);   // ✅ Works — parent scope is accessible
        console.log(innerVar);   // ✅ Works — local scope
    }

    console.log(innerVar);  // ❌ ReferenceError — inner's scope is not accessible here
}

outer();
console.log(outerVar);  // ❌ ReferenceError — outer's scope is not accessible here

The rule: a function can always access variables in its own scope and all parent scopes. It can never access variables from child scopes.

var vs let vs const: Block Scope Matters

Before ES6 (2015), JavaScript had only var, which creates function scope. ES6 added let and const, which create block scope.

// var is function-scoped (ignores blocks)
function example() {
    if (true) {
        var x = 10;
        let y = 20;
        const z = 30;
    }
    console.log(x);  // ✅ 10 — var ignores the if block
    console.log(y);  // ❌ ReferenceError — let is block-scoped
    console.log(z);  // ❌ ReferenceError — const is block-scoped
}

// let and const are also subject to TDZ (Temporal Dead Zone)
console.log(a);  // ❌ ReferenceError (not "undefined") — TDZ
let a = 5;

console.log(b);  // ✅ undefined — var is hoisted and initialized
var b = 5;

The Temporal Dead Zone (TDZ) means you can't access let/const variables before their declaration line, even though they're "hoisted." var is hoisted and initialized to undefined, so no TDZ error — just unexpected undefined values.

What Is a Closure? (With Examples)

A closure happens when an inner function remembers variables from its parent scope, even after the parent has returned.

function createCounter() {
    let count = 0;  // This variable "closes over" the inner functions

    return {
        increment: () => {
            count++;
            return count;
        },
        decrement: () => {
            count--;
            return count;
        },
        getCount: () => count,
    };
}

const counter = createCounter();
console.log(counter.increment());  // 1
console.log(counter.increment());  // 2
console.log(counter.decrement());  // 1
console.log(counter.getCount());   // 1

// Nobody can access 'count' directly — it's private!
console.log(counter.count);        // undefined

This is the module pattern. The variable count lives in a closure — protected from external access but fully available to the returned functions. This is how you create private state in JavaScript.

Real-World Pattern: Event Handlers

Closures are everywhere in event-driven JavaScript:

function setupButtons() {
    let clickCount = 0;

    const buttons = document.querySelectorAll('.my-button');

    buttons.forEach(button => {
        button.addEventListener('click', () => {
            clickCount++;
            console.log(`Button clicked ${clickCount} times total`);
        });
    });

    // clickCount keeps growing — it's in the closure of all handlers
}

setupButtons();

The clickCount variable survives long after setupButtons() returns. Every click handler shares the same clickCount because they all close over the same scope.

The Classic "Loop Closure" Bug

This is the most famous closure gotcha:

// ❌ THE BUG: All timeouts log 3
for (var i = 0; i < 3; i++) {
    setTimeout(() => {
        console.log(i);  // 3, 3, 3 (NOT 0, 1, 2)
    }, 100);
}

// ✅ FIX 1: Use let (block scope creates new i each iteration)
for (let i = 0; i < 3; i++) {
    setTimeout(() => {
        console.log(i);  // 0, 1, 2
    }, 100);
}

// ✅ FIX 2: Use an IIFE (Immediately Invoked Function Expression) with var
for (var i = 0; i < 3; i++) {
    (function(j) {
        setTimeout(() => {
            console.log(j);  // 0, 1, 2
        }, 100);
    })(i);  // Pass i as a parameter — creates a new scope each iteration
}

Why does var fail? Because var i is function-scoped — there's only ONE variable i. By the time the timeouts fire, the loop has finished and i equals 3. With let, each iteration gets its OWN i variable — the closure captures the right one.

Real-World Pattern: Function Factories

Create specialized functions by "baking in" configuration:

function createMultiplier(factor) {
    return function(number) {
        return number * factor;
    };
}

const double = createMultiplier(2);
const triple = createMultiplier(3);
const half = createMultiplier(0.5);

console.log(double(10));  // 20
console.log(triple(10));  // 30
console.log(half(10));    // 5

Each returned function remembers its own factor. This is essentially how functional programming's currying works.

Real-World Pattern: Memoization

Closures are perfect for caching — keeping a private cache that only the function can access:

function memoize(fn) {
    const cache = new Map();  // Private cache — nobody else can access this

    return function(...args) {
        const key = JSON.stringify(args);
        if (cache.has(key)) {
            console.log("Cache hit!");
            return cache.get(key);
        }
        console.log("Computing...");
        const result = fn(...args);
        cache.set(key, result);
        return result;
    };
}

// Create a memoized version of an expensive function
const slowAdd = (a, b) => {
    // Simulate expensive computation
    let sum = 0;
    for (let i = 0; i < 1000000; i++) sum++;
    return a + b;
};

const fastAdd = memoize(slowAdd);
console.log(fastAdd(2, 3));  // Computing... 5
console.log(fastAdd(2, 3));  // Cache hit! 5
console.log(fastAdd(2, 4));  // Computing... 6

The cache is private — only the memoized function can read or write it. No global variables, no object properties that can be modified externally.

Real-World Pattern: Data Hiding / Encapsulation

Before classes had private fields (# syntax), closures were the primary way to hide data:

function createBankAccount(initialBalance) {
    let balance = initialBalance;  // Private — not accessible from outside

    return {
        deposit(amount) {
            if (amount <= 0) throw new Error("Deposit must be positive");
            balance += amount;
            return balance;
        },
        withdraw(amount) {
            if (amount > balance) throw new Error("Insufficient funds");
            balance -= amount;
            return balance;
        },
        getBalance() {
            return balance;
        },
    };
}

const account = createBankAccount(100);
account.deposit(50);   // 150
account.withdraw(30);  // 120
console.log(account.balance);  // undefined — can't access directly!

// Compare with the modern private field syntax (ES2022)
class BankAccount {
    #balance = 0;  // Private field (ES2022+)

    constructor(initial) { this.#balance = initial; }
    deposit(amount) { this.#balance += amount; }
    withdraw(amount) {
        if (amount > this.#balance) throw new Error("Insufficient funds");
        this.#balance -= amount;
    }
    getBalance() { return this.#balance; }
}

Closures and Memory Leaks

Closures keep references alive. If a closure references a large object, that object won't be garbage collected as long as the closure exists:

function setupEventHandler() {
    const largeData = new Array(1000000).fill("data");

    document.getElementById("button").addEventListener("click", () => {
        // This closure references largeData
        console.log(`Data size: ${largeData.length}`);
    });
    // largeData stays in memory as long as the event listener exists
}

// ✅ FIX: Only reference what you need
function setupEventHandlerClean() {
    const largeData = new Array(1000000).fill("data");

    // Extract just the value you need
    const dataSize = largeData.length;

    document.getElementById("button").addEventListener("click", () => {
        console.log(`Data size: ${dataSize}`);  // Only closes over the number
    });
    // largeData can now be garbage collected
}

Always be mindful of what your closures capture. Remove event listeners when you're done:

function setupWithCleanup() {
    const handler = () => { /* ... */ };
    const button = document.getElementById("button");

    button.addEventListener("click", handler);

    // Return a cleanup function
    return () => {
        button.removeEventListener("click", handler);
    };
}

const cleanup = setupWithCleanup();
// Later, when the component is removed:
cleanup();

Common Interview Question

"What does this print?"

function outer() {
    let num = 0;
    const inner = () => {
        num++;
        return num;
    };
    return inner;
}

const fn = outer();
console.log(fn());  // 1
console.log(fn());  // 2
console.log(fn());  // 3

const fn2 = outer();
console.log(fn2());  // 1 (new closure, new num)
console.log(fn());   // 4 (original closure, original num)

Each call to outer() creates a new closure with its own num. fn and fn2 have separate num variables — they don't share state.

Summary

Closures are one of JavaScript's most powerful features. They enable:

  • Private state — data that only certain functions can access
  • Function factories — creating specialized functions with baked-in configuration
  • Memoization — caching expensive computations
  • Event handlers — maintaining state across events
  • Modules — the foundation of JavaScript's module system

Key takeaways:

  • Use let and const, not var, to avoid scope surprises
  • A closure captures variables by reference, not by value
  • Each function call creates a new closure with its own scope
  • Be aware of memory — closures prevent garbage collection
  • Closures are the mechanism behind JavaScript modules, callbacks, and event handling
