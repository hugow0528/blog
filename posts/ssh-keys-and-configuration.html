SSH Keys and Configuration: Connect to Servers Securely — Complete Guide

July 6, 2026 10 min read

If you're still typing passwords to log into servers or connect to GitHub, SSH keys are the most impactful productivity upgrade you can make. They're faster, more secure, and enable automation that passwords simply can't support.

This guide walks you through generating SSH keys, configuring shortcuts with ~/.ssh/config, setting up agent forwarding, and hardening your setup for everyday development work.

How SSH Keys Work

SSH uses asymmetric cryptography — a pair of keys where one is public and one is private:

  • Private key — stays on your computer, never shared. Think of it as an ultra-strong password.
  • Public key — placed on servers, GitHub, etc. It can verify your identity but can't be used to derive your private key.

When you connect, the server sends a challenge encrypted with your public key. Only your private key can solve it. No password needed.

Generate Your First SSH Key

Check if you already have keys:

# Check for existing keys
ls -la ~/.ssh/

# If you see id_ed25519 or id_rsa, you already have keys

Generate a new Ed25519 key (modern, fast, and secure — preferred over RSA for most use cases):

# Generate Ed25519 key with your email as comment
ssh-keygen -t ed25519 -C "your@email.com"

# Output:
# Generating public/private ed25519 key pair.
# Enter file in which to save the key (/home/you/.ssh/id_ed25519): [press Enter]
# Enter passphrase (empty for no passphrase): [type a strong passphrase]
# Enter same passphrase again: [retype]
# Your identification has been saved in /home/you/.ssh/id_ed25519
# Your public key has been saved in /home/you/.ssh/id_ed25519.pub

If your system is older and doesn't support Ed25519, use RSA with a strong key length:

# RSA alternative (2048 bit minimum, 4096 for extra security)
ssh-keygen -t rsa -b 4096 -C "your@email.com"

Add Your Public Key to GitHub

Copy your public key and add it to GitHub:

# Copy public key to clipboard
cat ~/.ssh/id_ed25519.pub

# Then on GitHub:
# 1. Go to Settings → SSH and GPG keys → New SSH key
# 2. Title: "My Laptop"
# 3. Paste the key content
# 4. Click "Add SSH key"

Test the connection:

ssh -T git@github.com

# Success output:
# Hi hugow0528! You've successfully authenticated, but GitHub
# does not provide shell access.

The Power of ~/.ssh/config

This is where SSH becomes genuinely convenient. Create a config file to define shortcuts for every server you connect to:

# Create or edit the config file
nano ~/.ssh/config

# Set correct permissions (SSH won't work without them)
chmod 600 ~/.ssh/config

Here's a practical config file:

# ~/.ssh/config

# GitHub — use a specific key instead of the default
Host github.com
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519
    IdentitiesOnly yes

# Production server shortcut
Host prod
    HostName 203.0.113.50
    User deploy
    Port 22
    IdentityFile ~/.ssh/id_ed25519
    ServerAliveInterval 60
    ServerAliveCountMax 3

# Staging server
Host staging
    HostName staging.example.com
    User ubuntu
    Port 2222
    IdentityFile ~/.ssh/staging_key
    ForwardAgent yes

# Cloudflare Tunnel for internal tools
Host internal-app
    HostName tunnel.example.com
    User admin
    IdentityFile ~/.ssh/id_ed25519

# Wildcard pattern — all AWS instances
Host ec2-*
    User ec2-user
    IdentityFile ~/.ssh/aws_key
    ServerAliveInterval 30

Now connect with simple names instead of full details:

# Instead of: ssh -i ~/.ssh/id_ed25519 -p 22 deploy@203.0.113.50
ssh prod                    # Connects to production
ssh staging                 # Connects to staging
scp file.txt prod:/tmp/     # Copy file to production
ssh prod "systemctl status nginx"  # Run a remote command

SSH Agent: Never Type Your Passphrase Again (Per Session)

If you used a passphrase (recommended), you'll be asked every time you connect. The SSH agent caches it for your login session:

# Start the agent (usually already running)
eval "$(ssh-agent -s)"

# Add your key to the agent
ssh-add ~/.ssh/id_ed25519

# Now connect — no passphrase needed for the rest of this session
ssh prod

On Linux, add ssh-agent to your shell profile so it starts automatically. On macOS, the system handles this via the keychain. On Windows, use the built-in OpenSSH client with the "OpenSSH Authentication Agent" service.

SSH Agent Forwarding

Agent forwarding lets you use your local keys from a remote server — useful when you need to clone a private GitHub repo from a deployment server:

# Enable in your config
Host staging
    ForwardAgent yes

# Then from your staging server:
ssh staging
git clone git@github.com:private/repo.git  # Works! Uses YOUR local keys

Security note: Only enable agent forwarding on servers you trust completely. A compromised server with agent forwarding can use your keys to access other systems.

SSH for Docker and DevOps Workflows

SSH is essential for deployment pipelines. Here are common patterns:

# Deploy with a one-liner
ssh prod "cd /var/www/app && git pull && docker-compose up -d"

# Copy your Docker Compose file and deploy
scp docker-compose.yml prod:/var/www/app/
ssh prod "cd /var/www/app && docker-compose up -d --build"

# Check server status remotely
ssh prod "docker ps && df -h && uptime"

# Port forwarding — access a database running on your server
ssh -L 5432:localhost:5432 prod
# Now connect to localhost:5432 and it routes to the remote database

Security Hardening Checklist

Protect your SSH setup with these practices:

# 1. Set correct file permissions
chmod 700 ~/.ssh/
chmod 600 ~/.ssh/id_ed25519
chmod 644 ~/.ssh/id_ed25519.pub
chmod 600 ~/.ssh/config

# 2. Use a strong passphrase
# When generating keys, always add a passphrase
ssh-keygen -t ed25519 -C "you@email.com"
# → Enter a passphrase with 12+ characters

# 3. Restrict SSH on the server side (in /etc/ssh/sshd_config)
PasswordAuthentication no          # Disable password login
PermitRootLogin no                 # Never log in as root
PubkeyAuthentication yes           # Require key-based auth
MaxAuthTries 3                     # Limit brute force attempts

# 4. Disable unused key types
PubkeyAcceptedAlgorithms ssh-ed25519,ssh-rsa

# 5. Use allowlist for users (optional)
AllowUsers deploy admin

After editing /etc/ssh/sshd_config, reload the SSH service:

# Reload SSH daemon
sudo systemctl reload sshd

Multiple Keys for Different Accounts

Separate keys for work and personal accounts keeps things organized:

# Generate separate keys
ssh-keygen -t ed25519 -C "personal@email.com" -f ~/.ssh/id_ed25519_personal
ssh-keygen -t ed25519 -C "work@company.com" -f ~/.ssh/id_ed25519_work

# Configure in ~/.ssh/config
Host github.com
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_personal

Host gitlab.company.com
    HostName gitlab.company.com
    User git
    IdentityFile ~/.ssh/id_ed25519_work

Troubleshooting

Common issues and fixes:

# Debug connection problems — shows exactly what's happening
ssh -v prod        # Verbose
ssh -vv prod       # More verbose
ssh -vvv prod      # Maximum detail

# Check if a specific key is being used
ssh -i ~/.ssh/id_ed25519 -T git@github.com

# Test if the server accepts your key
ssh -T deploy@203.0.113.50

# Common errors:
# Permission denied (publickey) → Wrong key or not added to server
# Agent admitted failure to sign → Run: ssh-add ~/.ssh/id_ed25519
# Bad owner or permissions → Run: chmod 600 ~/.ssh/id_ed25519
# Connection timed out → Check hostname, port, and firewall

Best Practices Summary

  • Use Ed25519 keys — faster, more secure, and shorter than RSA
  • Always use a passphrase — your private key file is worth protecting
  • Use ~/.ssh/config for every server — saves typing and reduces errors
  • Separate keys per purpose — personal, work, production, staging
  • Set correct permissions — SSH silently ignores keys with wrong permissions
  • Disable password auth on servers — keys only, no exceptions
  • Use ssh -v for debugging — verbose mode reveals the root cause of connection issues

SSH is one of those tools that, once configured properly, you never think about again. Your server logins become one command, your GitHub pushes are seamless, and your deployment scripts actually work. Spend 20 minutes setting it up today and save hours over the coming years.
