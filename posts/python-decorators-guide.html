Python Decorators: The Complete Guide — Functions That Modify Functions

July 4, 2026 12 min read

You've probably seen Python decorators before — those mysterious lines starting with @ sitting right above function definitions:

@my_decorator
def my_function():
    print("Hello!")

Decorators are one of Python's most powerful features. They let you modify or extend the behavior of a function or class without changing its source code. They're used everywhere: in web frameworks like Flask and FastAPI, in testing libraries, in caching systems, and in access control.

This guide walks you through decorators from the ground up — from understanding why they work to building production-grade decorators with arguments, logging, retry logic, and caching.

What Exactly Is a Decorator?

At its core, a decorator is just a function that takes another function as input and returns a modified version of it. That's it. No magic — just functions working with functions.

Python treats functions as first-class objects. This means you can:

  • Pass a function as an argument to another function
  • Return a function from another function
  • Assign a function to a variable
  • Nest functions inside other functions

Decorators rely on all four of these capabilities. Let's build one from scratch.

Your First Decorator (No @ Syntax Yet)

Before we use the @ syntax, let's see what's happening under the hood. Here's a simple decorator that prints a message before and after a function runs:

def simple_decorator(func):
    def wrapper():
        print(f"→ Calling: {func.__name__}")
        result = func()
        print(f"← Done: {func.__name__}")
        return result
    return wrapper

def say_hello():
    print("Hello, world!")

# Without the @ syntax:
decorated_hello = simple_decorator(say_hello)
decorated_hello()

# With the @ syntax (exactly the same thing):
@simple_decorator
def say_goodbye():
    print("Goodbye!")

say_goodbye()

Both calls produce:

→ Calling: say_hello
Hello, world!
← Done: say_hello

→ Calling: say_goodbye
Goodbye!
← Done: say_goodbye

See what happened? @simple_decorator is just shorthand for say_goodbye = simple_decorator(say_goodbye). The @ symbol applies the decorator immediately when the function is defined.

Preserving Function Metadata with functools.wraps

Our first decorator has a subtle problem. When you wrap a function, the wrapper replaces the original — so __name__, __doc__, and other attributes are lost:

@simple_decorator
def add(a, b):
    """Add two numbers together."""
    return a + b

print(add.__name__)  # "wrapper" — not "add"!
print(add.__doc__)   # None — our docstring is gone!

Python's functools.wraps decorator fixes this by copying the metadata from the original function to the wrapper:

from functools import wraps

def simple_decorator(func):
    @wraps(func)
    def wrapper(*args, **kwargs):
        print(f"→ Calling: {func.__name__}")
        result = func(*args, **kwargs)
        print(f"← Done: {func.__name__}")
        return result
    return wrapper

@simple_decorator
def add(a, b):
    """Add two numbers together."""
    return a + b

print(add.__name__)  # "add" ✓
print(add.__doc__)   # "Add two numbers together." ✓

Always use @wraps in your decorators. It's the professional standard and prevents bugs in frameworks that rely on function metadata.

Decorators That Accept Arguments

What if you want to configure a decorator? For example, a retry decorator where you specify how many times to retry:

@retry(times=3)  # passes argument!
def fetch_data():
    ...

When a decorator has arguments, it needs an extra layer — a function that returns the actual decorator:

import time
from functools import wraps

def retry(times=3, delay=1):
    """Retry a function N times with a delay between attempts."""
    def decorator(func):
        @wraps(func)
        def wrapper(*args, **kwargs):
            last_exception = None
            for attempt in range(1, times + 1):
                try:
                    return func(*args, **kwargs)
                except Exception as e:
                    last_exception = e
                    if attempt < times:
                        print(f"Attempt {attempt}/{times} failed: {e}. "
                              f"Retrying in {delay}s...")
                        time.sleep(delay)
                    else:
                        print(f"All {times} attempts failed.")
            raise last_exception
        return wrapper
    return decorator

# Usage examples:
@retry(times=5, delay=2)
def unreliable_api_call():
    import random
    if random.random() < 0.7:  # 70% chance of failure
        raise ConnectionError("Server is busy")
    return "Success!"

@retry(times=2)  # uses default delay=1
def fetch_user():
    raise TimeoutError("Request timed out")
    return {"name": "Hugo"}

# Try it:
result = unreliable_api_call()
print(result)

The three-layer structure is:

  1. retry(times, delay) — receives decorator arguments, returns...
  2. decorator(func) — receives the function, returns...
  3. wrapper(*args, **kwargs) — replaces the original function at runtime

Real-World Decorator: Timing and Profiling

One of the most practical decorators measures how long functions take to execute:

import time
from functools import wraps

def timer(func):
    """Measure execution time of a function."""
    @wraps(func)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = func(*args, **kwargs)
        elapsed = time.perf_counter() - start
        print(f"⏱ {func.__name__} took {elapsed:.4f}s")
        return result
    return wrapper

@timer
def process_large_file(filename):
    """Simulate processing a large file."""
    with open(filename, 'r') as f:
        data = f.read()
    return len(data)

@timer
def sort_numbers(numbers):
    """Sort a list of numbers."""
    return sorted(numbers)

# Usage:
result = sort_numbers(list(range(1000000, 0, -1)))
print(f"Sorted {len(result)} numbers")

This is invaluable for finding performance bottlenecks. Just drop @timer above any function and you instantly know how long it runs.

Real-World Decorator: Simple Caching (Memoization)

Caching expensive function results is a common pattern. Python has @functools.cache built-in, but building your own teaches the decorator pattern:

from functools import wraps

def memoize(func):
    """Cache function results based on arguments."""
    cache = {}
    @wraps(func)
    def wrapper(*args):
        if args not in cache:
            cache[args] = func(*args)
            print(f"  [computed] {func.__name__}{args}")
        else:
            print(f"  [cached]   {func.__name__}{args}")
        return cache[args]
    return wrapper

@memoize
def fibonacci(n):
    """Calculate the nth Fibonacci number (recursive)."""
    if n <= 1:
        return n
    return fibonacci(n - 1) + fibonacci(n - 2)

# Without caching, fibonacci(30) makes ~2.6 million calls
# With caching, each value is computed exactly once
for i in range(1, 11):
    print(f"fib({i}) = {fibonacci(i)}")

Output:

  [computed] fibonacci(0)
  [computed] fibonacci(1)
  [computed] fibonacci(2)
  [computed] fibonacci(3)
  [cached]   fibonacci(1)
  [cached]   fibonacci(2)
...
fib(10) = 55

Real-World Decorator: Access Control

Decorators shine for enforcing permissions. Here's a simple role-based access control example:

from functools import wraps

# Simple role check decorator
def require_role(required_role):
    """Restrict function access to users with a specific role."""
    def decorator(func):
        @wraps(func)
        def wrapper(user, *args, **kwargs):
            if user.get("role") != required_role:
                raise PermissionError(
                    f"Access denied. Requires '{required_role}' role, "
                    f"but user '{user['name']}' has '{user.get('role')}'."
                )
            return func(user, *args, **kwargs)
        return wrapper
    return decorator

# Define protected functions
@require_role("admin")
def delete_user(admin, target_id):
    print(f"Admin {admin['name']} deleted user {target_id}")
    return True

@require_role("editor")
def publish_article(editor, article_id):
    print(f"Editor {editor['name']} published article {article_id}")
    return True

# Test with different users:
admin = {"name": "Hugo", "role": "admin"}
regular_user = {"name": "Alice", "role": "viewer"}

# This works:
delete_user(admin, 42)
# Output: Admin Hugo deleted user 42

# This raises PermissionError:
try:
    delete_user(regular_user, 42)
except PermissionError as e:
    print(f"Blocked: {e}")
# Output: Blocked: Access denied. Requires 'admin' role,
#         but user 'Alice' has 'viewer'.

Stacking Multiple Decorators

You can apply multiple decorators to a single function. They execute from bottom to top (the one closest to the function runs first):

@timer
@retry(times=3)
@require_role("admin")
def critical_operation(user):
    """This function is timed, retried, and role-checked."""
    print("  → Executing critical operation...")
    return "done"

# Execution order:
# 1. require_role runs first (checks user)
# 2. retry wraps around that (handles failures)
# 3. timer wraps around everything (measures total time)

Think of it like wrapping a gift: the innermost decorator is applied first, then each outer layer wraps around the result.

Class-Based Decorators

For more complex decorators, you can use a class with __call__:

class LogCalls:
    """Track how many times a function is called."""
    def __init__(self, func):
        self.func = func
        self.call_count = 0
        self.last_result = None

    def __call__(self, *args, **kwargs):
        self.call_count += 1
        result = self.func(*args, **kwargs)
        self.last_result = result
        print(f"  [{self.func.__name__}] call #{self.call_count}")
        return result

@LogCalls
def search_database(query):
    """Simulate a database search."""
    return [f"result for {query}"]

# Usage:
search_database("python")
search_database("decorators")
print(f"Total calls: {search_database.call_count}")
# Output:
#   [search_database] call #1
#   [search_database] call #2
# Total calls: 2

Class-based decorators are great when you need to maintain state (like call counts, caches, or history) across multiple invocations.

Common Pitfalls

1. Forgetting to return the result

Always return func(*args, **kwargs) from your wrapper. If you don't, the decorated function returns None.

2. Losing *args and **kwargs

Always use *args, **kwargs in your wrapper signature. Otherwise, the decorator breaks when the decorated function takes arguments.

3. Forgetting @wraps

Without @wraps, debugging tools, documentation generators, and frameworks may fail because they can't find the original function's name or docstring.

Summary Cheat Sheet

# Basic decorator
def decorator(func):
    @wraps(func)
    def wrapper(*args, **kwargs):
        # Before
        result = func(*args, **kwargs)
        # After
        return result
    return wrapper

# Decorator with arguments
def decorator(arg1, arg2):
    def _decorator(func):
        @wraps(func)
        def wrapper(*args, **kwargs):
            return func(*args, **kwargs)
        return wrapper
    return _decorator

# Usage
@decorator
def my_func():
    pass

@decorator("value", 42)
def my_func2():
    pass

Next Steps

Decorators are used heavily in Flask routes (@app.route), FastAPI endpoints (@app.get), pytest fixtures (@pytest.fixture), and Django permissions (@login_required). Now that you understand the pattern, reading other people's decorators becomes straightforward.

Try building your own: a decorator that validates input types, one that rate-limits API calls, or one that automatically retries on specific exception types. The decorator pattern is one of those Python features that starts simple and grows with you.
