Cloudflare Workers: Build and Deploy Your First API — Complete Beginner's Guide

July 12, 2026 · 12 min read

Cloudflare Workers let you run JavaScript, TypeScript, or Python code on Cloudflare's global network — without provisioning servers, managing infrastructure, or worrying about scaling. Your code runs at the edge, close to users worldwide, with automatic HTTPS, DDoS protection, and instant deployment.

This guide walks you through everything from creating your first "Hello World" Worker to building a production-ready REST API with routing, JSON responses, CORS, and error handling. Let's build something that runs on 300+ data centers around the world.

Why Cloudflare Workers?

Workers solve several common problems with traditional server hosting:

  • No servers to manage — no EC2 instances, no containers, no uptime monitoring
  • Instant global deployment — code runs from the nearest edge location automatically
  • Generous free tier — 100,000 requests per day at no cost
  • Sub-millisecond cold starts — Workers are always ready (they reuse execution contexts)
  • Built-in security — DDoS protection and rate limiting out of the box
  • Works with existing sites — add Workers to any domain on Cloudflare without migration

Common use cases include API gateways, A/B testing, image processing, authentication proxies, and serving static content with dynamic logic.

Project Setup

First, install the Wrangler CLI — Cloudflare's official development tool:

# Install Wrangler (requires Node.js 18+)
npm install -g wrangler

# Log in to your Cloudflare account
wrangler login

Then, scaffold a new Worker project:

# Create a new Workers project
wrangler init my-api -- --site

# Navigate into the project
cd my-api

This creates a project with the following structure:

my-api/
├── src/
│   └── index.js          # Your Worker code
├── static/               # Static assets (optional)
├── wrangler.toml          # Configuration
└── package.json

Your First Worker

Open src/index.js and replace it with this:

export default {
    async fetch(request, env, ctx) {
        return new Response("Hello from the edge! 🌍", {
            status: 200,
            headers: { "Content-Type": "text/plain" }
        });
    }
};

That's it. This Worker intercepts every request and returns a text response. Let's break down the three parameters:

  • request — The incoming Request object (URL, method, headers, body)
  • env — Environment variables and bound resources (KV, D1, R2, secrets)
  • ctx — Context for deferred tasks (logging, background execution)

Local Development

Before deploying, test locally with the Wrangler dev server:

# Start local dev server
wrangler dev

# Your Worker is now running at http://localhost:8787
curl http://localhost:8787
# Hello from the edge! 🌍

The local server simulates the edge environment, so your code behaves the same locally and in production.

Deploying to Production

# Deploy your Worker
wrangler deploy

# Output:
# ⛅️ wrangler 3.70.0
# ✅ Deployed my-api triggers (1 routes)
#    my-api.my-subdomain.workers.dev

# Test it!
curl https://my-api.my-subdomain.workers.dev
# Hello from the edge! 🌍

Your code is now running on Cloudflare's entire network. Every request is served from the nearest data center.

Building a REST API

Let's build something more useful — a simple REST API with routing:

export default {
    async fetch(request, env) {
        const url = new URL(request.url);
        const path = url.pathname;
        const method = request.method;

        // Route: GET / — Health check
        if (path === "/" && method === "GET") {
            return jsonResponse({
                service: "My API",
                status: "healthy",
                timestamp: new Date().toISOString()
            });
        }

        // Route: GET /api/notes — List all notes
        if (path === "/api/notes" && method === "GET") {
            const notes = env.NOTES_STORE || [];
            return jsonResponse(notes);
        }

        // Route: POST /api/notes — Create a note
        if (path === "/api/notes" && method === "POST") {
            const body = await request.json();
            if (!body.text) {
                return jsonResponse({ error: "Missing 'text' field" }, 400);
            }

            const note = {
                id: crypto.randomUUID(),
                text: body.text,
                createdAt: new Date().toISOString()
            };

            // In production, you'd store this in D1 or KV
            console.log("New note:", note);

            return jsonResponse(note, 201);
        }

        // Route: GET /api/notes/:id — Get a single note
        const noteMatch = path.match(/^\/api\/notes\/(.+)$/);
        if (noteMatch && method === "GET") {
            const id = noteMatch[1];
            return jsonResponse({ error: "Not found" }, 404);
        }

        // 404 for everything else
        return jsonResponse({ error: "Not found", path }, 404);
    }
};

// Helper: Return JSON response with standard headers
function jsonResponse(data, status = 200) {
    return new Response(JSON.stringify(data), {
        status,
        headers: {
            "Content-Type": "application/json",
            "Access-Control-Allow-Origin": "*"
        }
    });
}

This Worker implements three endpoints:

MethodPathDescription
GET/Health check
GET/api/notesList all notes
POST/api/notesCreate a note

Understanding the Request Object

The request parameter is a standard Request object (same as the Fetch API). Here's how to work with it:

export default {
    async fetch(request, env) {
        const url = new URL(request.url);

        // Access URL components
        console.log(url.hostname);   // "my-api.workers.dev"
        console.log(url.pathname);   // "/api/notes"
        console.log(url.searchParams.get("q"));  // "search term"

        // Access HTTP method
        console.log(request.method);  // "GET", "POST", etc.

        // Access headers
        console.log(request.headers.get("Content-Type"));
        console.log(request.headers.get("Authorization"));
        console.log(request.headers.get("CF-IPCountry"));  // "US", "JP", etc.

        // Access request body (only once!)
        if (request.method === "POST") {
            const body = await request.json();
            // or: await request.text()
            // or: await request.formData()
        }

        // Check if the request is from a browser
        const isBrowser = request.headers.get("User-Agent").includes("Mozilla");

        return new Response("OK");
    }
};

Important: Cloudflare Workers automatically populate special headers like CF-IPCountry, CF-Region, CF-City, and CF-Connecting-IP with the client's geolocation data.

Adding CORS Headers

CORS (Cross-Origin Resource Sharing) is the most common hurdle when building APIs that frontend apps call from different domains. Here's a clean way to handle it:

export default {
    async fetch(request, env) {
        // Handle CORS preflight requests (OPTIONS)
        if (request.method === "OPTIONS") {
            return new Response(null, {
                status: 204,
                headers: {
                    "Access-Control-Allow-Origin": "*",
                    "Access-Control-Allow-Methods": "GET, POST, PUT, DELETE, OPTIONS",
                    "Access-Control-Allow-Headers": "Content-Type, Authorization",
                    "Access-Control-Max-Age": "86400"  // Cache preflight for 24 hours
                }
            });
        }

        // Your API logic here...
        const response = await handleRequest(request, env);

        // Add CORS headers to all responses
        response.headers.set("Access-Control-Allow-Origin", "*");
        response.headers.set("Access-Control-Allow-Methods", "GET, POST, PUT, DELETE, OPTIONS");
        response.headers.set("Access-Control-Allow-Headers", "Content-Type, Authorization");

        return response;
    }
};

async function handleRequest(request, env) {
    const url = new URL(request.url);

    if (url.pathname === "/api/data" && request.method === "GET") {
        return new Response(JSON.stringify({ message: "Hello!" }), {
            headers: { "Content-Type": "application/json" }
        });
    }

    return new Response("Not found", { status: 404 });
}

CORS Checklist:

  • Handle OPTIONS preflight requests explicitly
  • Add Access-Control-Allow-Origin to every response
  • Specify allowed methods with Access-Control-Allow-Methods
  • Specify allowed headers with Access-Control-Allow-Headers
  • Use Access-Control-Max-Age to reduce preflight requests
  • In production, restrict Allow-Origin to specific domains instead of *

Working with Request Bodies

Workers handle different body formats depending on your needs:

export default {
    async fetch(request, env) {
        if (request.method !== "POST") {
            return new Response("POST only", { status: 405 });
        }

        const contentType = request.headers.get("Content-Type");

        // Parse JSON body
        if (contentType === "application/json") {
            const data = await request.json();
            return new Response(JSON.stringify({ received: data }), {
                headers: { "Content-Type": "application/json" }
            });
        }

        // Parse form data
        if (contentType?.startsWith("multipart/form-data") ||
            contentType === "application/x-www-form-urlencoded") {
            const formData = await request.formData();
            const name = formData.get("name");
            const email = formData.get("email");
            return new Response(`Name: ${name}, Email: ${email}`);
        }

        // Parse plain text
        if (contentType === "text/plain") {
            const text = await request.text();
            return new Response(`Echo: ${text}`);
        }

        return new Response("Unsupported content type", { status: 415 });
    }
};

Error Handling

Always wrap your handler in try/catch to return meaningful errors instead of crashing:

export default {
    async fetch(request, env) {
        try {
            // Your API logic
            return await handleRequest(request, env);
        } catch (error) {
            console.error("Worker error:", error);

            // Never expose internal error details in production
            return new Response(JSON.stringify({
                error: "Internal server error",
                // Remove in production: message: error.message
            }), {
                status: 500,
                headers: { "Content-Type": "application/json" }
            });
        }
    }
};

Environment Variables and Secrets

Store configuration and secrets safely using Wrangler:

# Set a variable (visible in source)
wrangler secret put DB_HOST

# Set a secret (encrypted, never stored in plaintext)
wrangler secret put API_KEY

# Or add them to wrangler.toml
# [vars]
# APP_NAME = "My API"

# Access in your Worker
export default {
    async fetch(request, env) {
        const apiKey = env.API_KEY;      // Secret
        const appName = env.APP_NAME;    // Variable
        const dbHost = env.DB_HOST;      // Secret

        // Validate incoming API key
        const authHeader = request.headers.get("Authorization");
        if (authHeader !== `Bearer ${apiKey}`) {
            return new Response(JSON.stringify({ error: "Unauthorized" }), {
                status: 401,
                headers: { "Content-Type": "application/json" }
            });
        }

        return new Response(JSON.stringify({ app: appName }), {
            headers: { "Content-Type": "application/json" }
        });
    }
};

Never hardcode secrets in your Worker source code. Use wrangler secret put to store them encrypted in Cloudflare's infrastructure.

Using a Router Library

For larger APIs, manual string matching gets messy. Use a router like itty-router:

import { Router } from "itty-router";

const router = Router();

// Define routes
router
    .get("/", () => new Response("Welcome to the API"))
    .get("/api/notes", () => jsonResponse({ notes: [] }))
    .post("/api/notes", async (request) => {
        const body = await request.json();
        return jsonResponse({ id: crypto.randomUUID(), ...body }, 201);
    })
    .get("/api/notes/:id", ({ params }) => {
        return jsonResponse({ id: params.id, text: "Sample note" });
    })
    .all("*", () => jsonResponse({ error: "Not found" }, 404));

export default { fetch: router.handle };

function jsonResponse(data, status = 200) {
    return new Response(JSON.stringify(data), {
        status,
        headers: { "Content-Type": "application/json" }
    });
}

Install itty-router with npm install itty-router in your Worker directory.

Custom Domains

Instead of using the default .workers.dev subdomain, connect a custom domain:

# In wrangler.toml
name = "my-api"
compatibility_date = "2026-07-01"

routes = [
    "api.mydomain.com/*"
]
# Or register via Wrangler CLI
wrangler routes add api.mydomain.com/*

# Deploy — it now runs at api.mydomain.com
wrangler deploy

Performance Tips

  • Keep Workers stateless — each request runs independently on a random edge server
  • Avoid synchronous code — use async/await for all I/O operations
  • Minimize dependencies — each dependency increases cold start time
  • Use Cloudflare's built-in bindings — KV, D1, R2, and Queues are faster than external HTTP calls
  • Set appropriate cache headers — use Cache-Control for responses that don't change often
  • Profile with Workers Analytics — check the Cloudflare dashboard for latency and error rates
