Docker Compose Networking: Connect Containers Like a Pro

July 1, 2026 · 11 min read

You've learned Docker Compose basics and can spin up a web app with a database. But what happens when you need containers to talk to each other securely? How do you connect two different Compose projects? How do you expose services to the outside world without opening everything?

Docker networking is the invisible backbone of containerized applications. Understanding it transforms you from someone who can run containers to someone who can design reliable, secure multi-service architectures.

How Docker Compose Networks Work

By default, Docker Compose creates a bridge network for your project. Every service in your docker-compose.yml joins this network automatically. Containers can communicate using their service names as hostnames — Docker handles DNS resolution internally.

# docker-compose.yml — default networking (implicit)
services:
  web:
    image: nginx
    ports:
      - "8080:80"

  api:
    build: ./api
    # Can reach the database at http://db:5432

  db:
    image: postgres:15
    environment:
      POSTGRES_PASSWORD: secret

In this setup, all three services are on the same default network (projectname_default). The API container can reach PostgreSQL using just db:5432 — Docker's embedded DNS resolves db to the container's IP address.

💡 Key concept: Service names are DNS hostnames within the network. No need to use IP addresses — they change when containers restart anyway.

Custom Bridge Networks: Isolate Your Services

The default network works for simple apps, but real projects benefit from explicit custom networks. They give you isolation between frontend and backend services, and prevent containers that shouldn't communicate from even seeing each other.

# docker-compose.yml — explicit custom networks
services:
  # Frontend — public-facing
  nginx:
    image: nginx:alpine
    ports:
      - "80:80"
      - "443:443"
    networks:
      - frontend
      - backend

  # API — internal only, no ports exposed
  api:
    build: ./api
    networks:
      - backend
    environment:
      - DB_HOST=postgres
      - REDIS_HOST=redis

  # Database — backend only, never public
  postgres:
    image: postgres:15
    networks:
      - backend
    volumes:
      - pg_data:/var/lib/postgresql/data

  # Cache — backend only
  redis:
    image: redis:7-alpine
    networks:
      - backend

networks:
  frontend:
    driver: bridge
  backend:
    driver: bridge

volumes:
  pg_data:

Notice the network isolation:

  • nginx is on both frontend and backend — it can proxy requests to the API
  • api is only on backend — no direct internet access via ports
  • postgres and redis are only on backend — completely isolated from the outside

This means even if someone compromises the nginx container, they can't reach PostgreSQL directly because they're on different networks.

Internal Networks: No External Access

For maximum security, mark backend networks as internal: true. This prevents ANY container on that network from accessing the outside internet — perfect for databases that only need to talk to the API:

networks:
  frontend:
    driver: bridge
  backend:
    driver: bridge
    internal: true  # ← No external internet access
⚠️ Watch out: With internal: true, containers can't install packages, pull images, or make HTTP calls outside the network. Only use this for services that truly don't need internet access (databases, caches, message queues).

Port Mapping Strategies

Ports are how containers talk to the outside world. Docker Compose gives you several options:

services:
  web:
    image: nginx
    ports:
      # Host port : Container port
      - "8080:80"         # Maps host:8080 → container:80
      
      # Specific interface: host port : container port
      - "127.0.0.1:3000:3000"  # Only accessible from localhost
      
      # Container port only (Docker picks a random host port)
      - "5000"            # Random host port → container:5000
      
      # Different container ports
      - "8080:80"         # HTTP
      - "8443:443"        # HTTPS
      
      # UDP ports
      - "5353:5353/udp"   # UDP traffic

  admin:
    image: adminer
    ports:
      - "127.0.0.1:8081:8080"  # Localhost only — not accessible from other machines

Best Practices for Port Mapping

  • Bind to 127.0.0.1 for admin tools — Adminer, phpMyAdmin, etc. should never be exposed to the network
  • Use specific host ports — Avoid random ports so you know where your service is accessible
  • Only expose what's needed — Databases should have no port mappings; access them through the API
  • Use a reverse proxy — Put nginx or Traefik in front and only expose port 80/443

DNS Resolution and Service Discovery

Docker's embedded DNS makes service discovery automatic. Here's how it works in practice:

# Inside any container on the same network, you can resolve:
# Service name → container IP
ping db              # resolves to the db container's IP
ping api             # resolves to the api container's IP

# With port
curl http://api:3000/health
curl http://postgres:5432  # PostgreSQL default port

# DNS aliases for alternative names
services:
  api:
    image: my-api
    networks:
      backend:
        aliases:
          - api-server      # Alternative DNS name
          - internal-api    # Another alias

# Now these all resolve to the same container:
#   api, api-server, internal-api

Multiple Containers Per Service

When you scale a service (docker compose up --scale api=3), DNS returns all IP addresses in round-robin fashion:

# docker-compose.yml
services:
  api:
    image: my-api
    networks:
      - backend

# Scale to 3 instances:
docker compose up --scale api=3

# Now "api" resolves to one of 3 IPs, rotating each request
# Load balancing happens at the DNS level (basic round-robin)
💡 Pro tip: DNS-based round-robin is simple but doesn't do health checks. For production load balancing, use a reverse proxy (nginx, Traefik, HAProxy) instead.

Connecting to External Networks

Sometimes you need to connect containers from different Compose projects or share a network with standalone containers. External networks make this possible.

# Step 1: Create the external network
docker network create shared-network

# Step 2: Use it in project A's docker-compose.yml
# projectA/docker-compose.yml
services:
  api-a:
    image: api-a
    networks:
      - shared-network

networks:
  shared-network:
    external: true  # ← Don't create, just attach

# Step 3: Use it in project B's docker-compose.yml  
# projectB/docker-compose.yml
services:
  api-b:
    image: api-b
    networks:
      - shared-network

networks:
  shared-network:
    external: true

# Now api-a and api-b can communicate despite being in different projects!
# From api-a: curl http://api-b:3000/health

Network Drivers: Bridge vs Host vs None

# Default: bridge (isolated virtual network)
networks:
  default:
    driver: bridge

# Host networking — no isolation, uses host's network directly
# Useful for performance-critical apps or services that need host ports
networks:
  hostnet:
    driver: host

# None — completely isolated, no networking at all
# Useful for batch processing jobs that don't need network access
networks:
  isolated:
    driver: null

When to Use Each Driver

  • bridge (default): Most common. Isolated, secure, good for development and staging.
  • host: Maximum performance. Use when you need host-level network access (monitoring agents, network tools). Not available on Docker Desktop (Mac/Windows).
  • none: Air-gapped containers. Use for build steps or batch jobs that don't need network access.

Real-World Example: Complete Microservices Setup

Here's a production-like setup with proper network isolation:

# docker-compose.yml
services:
  # Reverse proxy — the only service with public ports
  caddy:
    image: caddy:2-alpine
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile
      - caddy_data:/data
    networks:
      - public
      - app

  # Web frontend (React/Vue/Next.js)
  frontend:
    build: ./frontend
    networks:
      - app
    environment:
      - API_URL=http://api:3000

  # API server
  api:
    build: ./api
    networks:
      - app
      - data
    environment:
      - DATABASE_URL=postgres://user:pass@postgres:5432/appdb
      - REDIS_URL=redis://redis:6379
      - RABBITMQ_URL=amqp://guest:guest@rabbitmq:5672

  # Worker processes (background jobs)
  worker:
    build: ./worker
    networks:
      - data
    environment:
      - RABBITMQ_URL=amqp://guest:guest@rabbitmq:5672
      - REDIS_URL=redis://redis:6379

  # PostgreSQL — only accessible from app and data networks
  postgres:
    image: postgres:15-alpine
    networks:
      - data
    volumes:
      - pg_data:/var/lib/postgresql/data
    environment:
      - POSTGRES_DB=appdb
      - POSTGRES_USER=user
      - POSTGRES_PASSWORD=pass

  # Redis cache
  redis:
    image: redis:7-alpine
    networks:
      - data

  # RabbitMQ message broker
  rabbitmq:
    image: rabbitmq:3-management-alpine
    networks:
      - data

  # Monitoring — visible on public network for dashboards
  grafana:
    image: grafana/grafana:latest
    ports:
      - "127.0.0.1:3000:3000"  # Localhost only
    networks:
      - public
      - data

networks:
  public:     # Internet-facing (Caddy, Grafana)
    driver: bridge
  app:        # Application layer (frontend, API)
    driver: bridge
  data:       # Data layer (DB, Redis, RabbitMQ) — internal
    driver: bridge
    internal: true

volumes:
  pg_data:
  caddy_data:

The network topology:

  • public: Caddy (HTTP/HTTPS) + Grafana (localhost only)
  • app: Frontend + API + Caddy (proxy)
  • data: PostgreSQL + Redis + RabbitMQ + Worker (internal, no internet)

Debugging Network Issues

When containers can't reach each other, these commands help diagnose the problem:

# List all networks
docker network ls

# Inspect a network — see which containers are attached
docker network inspect project_default

# Exec into a container to test connectivity
docker compose exec api ping db
docker compose exec api curl http://postgres:5432

# Check DNS resolution inside a container
docker compose exec api getent hosts db
docker compose exec api nslookup postgres

# View network configuration
docker compose exec api ip addr
docker compose exec api ip route
docker compose exec api cat /etc/hosts

# Common error: "Connection refused"
# → The service isn't running on the expected port inside the container
# Fix: Check the container's listening ports
docker compose exec api netstat -tlnp
# or
docker compose exec api ss -tlnp

Summary

Docker Compose networking gives you powerful tools for building secure, well-organized multi-container applications:

  • Default bridge network: Automatic, good for simple projects
  • Custom networks: Isolate services that shouldn't communicate
  • internal: true: Block all external internet access for data-tier services
  • Service name DNS: Containers find each other by name, not IP
  • Port mapping strategies: Expose only what's needed, bind admin tools to localhost
  • External networks: Share connectivity between different Compose projects
  • Network drivers: bridge (default), host (performance), none (isolation)

Security golden rule: Never expose database ports directly. Put a reverse proxy in front of your application and keep data services on internal networks.
