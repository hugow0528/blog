Cloudflare D1: Serverless SQLite Database at the Edge

June 26, 2026 · 11 min read

Cloudflare D1 is a fully managed, serverless SQLite database that runs on Cloudflare's edge network. It gives you the simplicity and SQL familiarity of SQLite with the scale and distribution of a managed cloud database — no provisioning, no patching, no downtime.

In this guide, we'll cover everything from creating your first D1 database to building a complete full-stack API with Cloudflare Workers. You'll learn schema design, query execution, migrations, and how to connect D1 to a Workers application.

What Is Cloudflare D1?

D1 is Cloudflare's answer to "how do I run a real database at the edge?" It uses SQLite as its underlying engine, which means you get a fully compliant SQL database that speaks the language you already know. But unlike a traditional SQLite file sitting on a single server, D1 distributes your data across Cloudflare's global network.

Traditional database:
  App → Single database server (one region)
  Problem: latency for users far from the server

Cloudflare D1:
  App → Workers → D1 (query routed to nearest region)
  Benefit: fast reads, low-latency writes, automatic scaling

Key features:

  • 📦 SQLite-compatible — standard SQL queries, familiar syntax
  • 🌍 Edge-ready — integrates seamlessly with Cloudflare Workers
  • 💰 Generous free tier — 5 million row reads, 100k writes/day
  • 🔄 Local development — run queries locally with Wrangler, no cloud needed
  • 📋 Migration support — define your schema in SQL files, version-controlled
  • 🔐 Secure — encrypted at rest, no direct public access

When to Use D1

D1 isn't the right tool for every job. Here's when it shines and when to consider alternatives:

✅ Great for:

  • Full-stack apps built on Cloudflare Workers
  • Small to medium datasets (millions of rows)
  • CRUD APIs, content management, user profiles
  • Prototypes and MVPs that need a real database
  • Edge-optimized read-heavy workloads

❌ Consider alternatives for:

  • Complex analytical queries (use a data warehouse)
  • Massive writes at high throughput (use a traditional RDS/Cloudflare Workers with external DB)
  • Blobs, images, files (use Cloudflare R2)
  • Key-value caching (use Cloudflare Workers KV)

Setup: Create Your First D1 Database

First, make sure you have Wrangler installed:

# Install Wrangler (if not already installed)
npm install -g wrangler

# Log in
wrangler login

Now create a Workers project with D1:

# Create a new Workers project
wrangler init my-app
cd my-app

# Create a new D1 database
wrangler d1 create my-database

# You'll see output like:
# ⛅ Created database "my-database" in US
# Database ID: abc123-def456-ghi789

Save the database ID — you'll need it in your wrangler.toml configuration:

# wrangler.toml
name = "my-app"
main = "src/index.js"
compatibility_date = "2026-06-26"

[[d1_databases]]
binding = "DB"              # Available in your Worker as env.DB
database_name = "my-database"
database_id = "abc123-def456-ghi789"

Define Your Schema with Migrations

D1 uses SQL migration files to define and evolve your database schema. Create a migrations directory:

mkdir migrations

# Create your first migration file
cat > migrations/001_create_users.sql << 'EOF'
CREATE TABLE IF NOT EXISTS users (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    username TEXT NOT NULL UNIQUE,
    email TEXT NOT NULL UNIQUE,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE IF NOT EXISTS posts (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id INTEGER NOT NULL,
    title TEXT NOT NULL,
    body TEXT NOT NULL,
    published INTEGER DEFAULT 0,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (user_id) REFERENCES users(id)
);

CREATE INDEX idx_posts_user_id ON posts(user_id);
CREATE INDEX idx_posts_published ON posts(published);
EOF

Apply migrations locally for testing:

# Run migrations against local D1 database
wrangler d1 execute my-database \
  --local \
  --file=migrations/001_create_users.sql

Push to the cloud database:

# Apply migrations to production D1
wrangler d1 execute my-database \
  --remote \
  --file=migrations/001_create_users.sql

Query D1 from Cloudflare Workers

Now let's build a Worker that interacts with our D1 database. Here's a complete CRUD API:

// src/index.js

export default {
    async fetch(request, env) {
        const url = new URL(request.url);
        const path = url.pathname;

        // Route: GET /api/users — List all users
        if (path === "/api/users" && request.method === "GET") {
            const result = await env.DB.prepare(
                "SELECT id, username, email, created_at FROM users ORDER BY created_at DESC"
            ).all();
            return Response.json(result);
        }

        // Route: POST /api/users — Create a user
        if (path === "/api/users" && request.method === "POST") {
            const body = await request.json();
            const { username, email } = body;

            // Validate input
            if (!username || !email) {
                return Response.json(
                    { error: "username and email are required" },
                    { status: 400 }
                );
            }

            const result = await env.DB.prepare(
                "INSERT INTO users (username, email) VALUES (?, ?)"
            ).bind(username, email).run();

            return Response.json(
                { id: result.meta.last_row_id, username, email },
                { status: 201 }
            );
        }

        // Route: GET /api/users/:id — Get a single user
        const userMatch = path.match(/^\/api\/users\/(\d+)$/);
        if (userMatch && request.method === "GET") {
            const userId = userMatch[1];
            const result = await env.DB.prepare(
                "SELECT id, username, email, created_at FROM users WHERE id = ?"
            ).bind(userId).first();

            if (!result) {
                return Response.json({ error: "User not found" }, { status: 404 });
            }
            return Response.json(result);
        }

        // Route: GET /api/posts — List published posts with author info
        if (path === "/api/posts" && request.method === "GET") {
            const result = await env.DB.prepare(`
                SELECT posts.id, posts.title, posts.body, posts.created_at,
                       users.username as author
                FROM posts
                JOIN users ON posts.user_id = users.id
                WHERE posts.published = 1
                ORDER BY posts.created_at DESC
                LIMIT 20
            `).all();
            return Response.json(result);
        }

        // Route: POST /api/posts — Create a post
        if (path === "/api/posts" && request.method === "POST") {
            const body = await request.json();
            const { user_id, title, body: postBody } = body;

            if (!user_id || !title || !postBody) {
                return Response.json(
                    { error: "user_id, title, and body are required" },
                    { status: 400 }
                );
            }

            const result = await env.DB.prepare(
                "INSERT INTO posts (user_id, title, body) VALUES (?, ?, ?)"
            ).bind(user_id, title, postBody).run();

            return Response.json(
                { id: result.meta.last_row_id, title, user_id },
                { status: 201 }
            );
        }

        // Route: PUT /api/posts/:id/publish — Publish a post
        const publishMatch = path.match(/^\/api\/posts\/(\d+)\/publish$/);
        if (publishMatch && request.method === "PUT") {
            const postId = publishMatch[1];
            await env.DB.prepare(
                "UPDATE posts SET published = 1 WHERE id = ?"
            ).bind(postId).run();

            return Response.json({ published: true, id: postId });
        }

        return Response.json({ error: "Not found" }, { status: 404 });
    }
};

Understanding the D1 Query API

D1 provides several query methods on the binding object (env.DB):

Execute a Query and Get Results

// .all() — Returns all rows as an array
const { results } = await env.DB.prepare("SELECT * FROM users").all();

// .first() — Returns only the first row
const user = await env.DB.prepare(
    "SELECT * FROM users WHERE username = ?"
).bind("alice").first();

// .run() — For INSERT/UPDATE/DELETE (no result rows)
const result = await env.DB.prepare(
    "UPDATE users SET email = ? WHERE id = ?"
).bind("new@email.com", 42).run();

// result.meta contains: { duration, rows_read, rows_written, last_row_id }

Parameterized Queries (Prevent SQL Injection)

Always use parameterized queries with .bind() — never concatenate user input into SQL:

// ✅ SAFE — parameterized query
const user = await env.DB.prepare(
    "SELECT * FROM users WHERE email = ?"
).bind(userInput).first();

// ❌ DANGEROUS — SQL injection vulnerability!
// const user = await env.DB.prepare(
//     `SELECT * FROM users WHERE email = '${userInput}'`
// ).first();

Bulk Operations

For multiple queries in a single round trip, use batch():

const results = await env.DB.batch([
    env.DB.prepare("SELECT COUNT(*) as total FROM users"),
    env.DB.prepare("SELECT COUNT(*) as total FROM posts"),
    env.DB.prepare("SELECT * FROM users ORDER BY created_at DESC LIMIT 5")
]);

// results[0].results — user count
// results[1].results — post count
// results[2].results — latest users

Local Development Workflow

Wrangler provides a local D1 simulator so you can develop and test without hitting the cloud:

# Start local development server with D1
wrangler dev

# Your Worker runs locally, using a local SQLite database
# Test with curl:
curl http://localhost:8787/api/users
curl -X POST http://localhost:8787/api/users \
  -H "Content-Type: application/json" \
  -d '{"username": "alice", "email": "alice@example.com"}'

The local database lives in .wrangler/state/v3/d1/miniflare-d1/ and is reset each time you stop the dev server. Great for development — but remember to run your migrations against the real database before deploying.

Deploy Your Application

# Deploy your Worker + D1 to production
wrangler deploy

That's it. Your Worker is now live, connected to a real distributed database, with SSL, DDoS protection, and global CDN baked in.

D1 Limitations to Know

D1 is great but has some boundaries worth understanding:

  • Write latency — writes are replicated, so they're slower than reads (typically 100-300ms)
  • Database size — free tier allows 5 GB, paid plans go higher
  • Query limits — no raw BLOB storage; use R2 for large files
  • No transactions — as of now, D1 doesn't support multi-statement transactions
  • SQLite dialect — some PostgreSQL/MySQL features won't exist (stored procedures, window functions in older versions)

Real-World Project: Blog Backend

Let's put it all together with a migration for a full blog system:

-- migrations/002_add_blog.sql
CREATE TABLE IF NOT EXISTS tags (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL UNIQUE
);

CREATE TABLE IF NOT EXISTS post_tags (
    post_id INTEGER NOT NULL,
    tag_id INTEGER NOT NULL,
    PRIMARY KEY (post_id, tag_id),
    FOREIGN KEY (post_id) REFERENCES posts(id),
    FOREIGN KEY (tag_id) REFERENCES tags(id)
);

CREATE TABLE IF NOT EXISTS comments (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    post_id INTEGER NOT NULL,
    username TEXT NOT NULL,
    body TEXT NOT NULL,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (post_id) REFERENCES posts(id)
);

And a query that uses joins for a rich blog feed:

// GET /api/blog/feed
const feed = await env.DB.prepare(`
    SELECT 
        posts.id,
        posts.title,
        posts.body,
        posts.created_at,
        users.username as author,
        GROUP_CONCAT(tags.name, ', ') as tags,
        (SELECT COUNT(*) FROM comments WHERE comments.post_id = posts.id) as comment_count
    FROM posts
    JOIN users ON posts.user_id = users.id
    LEFT JOIN post_tags ON posts.id = post_tags.post_id
    LEFT JOIN tags ON post_tags.tag_id = tags.id
    WHERE posts.published = 1
    GROUP BY posts.id
    ORDER BY posts.created_at DESC
    LIMIT 10
`).all();

Summary

Cloudflare D1 brings the simplicity of SQLite to the edge, paired perfectly with Workers for building full-stack applications. You get a real SQL database with zero infrastructure to manage, a generous free tier, and seamless local development.

The workflow is simple: define migrations in SQL files, test locally with wrangler dev, and deploy with wrangler deploy. Your application goes from local machine to global edge network in one command.

For your next project, consider D1 as your go-to database — especially when you're already working within the Cloudflare ecosystem with Workers, Pages, R2, and the rest of the platform.

Pro tip: Combine D1 with Cloudflare Workers KV for a powerful two-tier data layer — use KV for fast, cacheable data (configs, feature flags, counters) and D1 for structured, relational data (users, posts, orders).
