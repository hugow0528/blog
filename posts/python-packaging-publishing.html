Python Packaging and Publishing: Build & Share Your Library on PyPI — Complete Guide

July 11, 2026 11 min read

You've written a useful Python module and want to share it with the world — or at least make it importable across your projects. Python packaging turns your code into a reusable, installable distribution that anyone can grab with pip install. This guide walks you through the entire process from project structure to publishing on PyPI.

Why Package Your Code?

Instead of copying the same utility functions across five projects, packaging lets you:

  • Install once, use everywhere — pip install my-utils and you're done
  • Version your changes — bump to v0.2.0 when you add features
  • Declare dependencies — let pip handle all the imports
  • Share with the community — publish on PyPI for anyone to find

Step 1: Project Structure

Every Python package follows a standard layout. Create this directory structure:

my_package/
├── pyproject.toml          # Build config & metadata
├── README.md               # Project description
├── LICENSE                 # License file
├── src/
│   └── my_package/
│       ├── __init__.py     # Package entry point
│       ├── core.py         # Your main code
│       └── utils.py        # Helper functions
└── tests/
    ├── __init__.py
    └── test_core.py        # Your tests

Notice the src/ layout? This is the modern recommended approach. It prevents accidental imports from the source directory during development and makes testing cleaner. Your actual package lives in src/my_package/.

Step 2: Write Your Code

Start with your main module. For example, let's create a simple string utility library:

src/my_package/core.py
def slugify(text):
    """Convert text to URL-friendly slug.

    >>> slugify("Hello World!")
    'hello-world'
    """
    text = text.lower().strip()
    text = re.sub(r'[^\w\s-]', '', text)
    text = re.sub(r'[\s_-]+', '-', text)
    return text

def truncate(text, max_length=100, suffix='...'):
    """Truncate text to a maximum length.

    >>> truncate('Hello, World!', 8)
    'Hello,...'
    """
    if len(text) <= max_length:
        return text
    return text[:max_length - len(suffix)] + suffix

Then expose your functions in __init__.py:

src/my_package/__init__.py
from .core import slugify, truncate

__version__ = "0.1.0"
__all__ = ["slugify", "truncate"]

The __all__ list controls what gets imported with from my_package import *. It's best practice to always define it.

Step 3: Configure pyproject.toml

The pyproject.toml file is the single source of truth for your package. Replace the old setup.py and setup.cfg pattern:

pyproject.toml
[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[project]
name = "my-package"
version = "0.1.0"
description = "Simple string utility functions for Python"
readme = "README.md"
license = "MIT"
requires-python = ">=3.9"
authors = [
    {name = "Your Name", email = "you@example.com"}
]
keywords = ["string", "slug", "utils"]
classifiers = [
    "Development Status :: 3 - Alpha",
    "License :: OSI Approved :: MIT License",
    "Programming Language :: Python :: 3",
    "Programming Language :: Python :: 3.9",
    "Programming Language :: Python :: 3.10",
    "Programming Language :: Python :: 3.11",
    "Programming Language :: Python :: 3.12",
]

[project.urls]
Homepage = "https://github.com/you/my-package"
Repository = "https://github.com/you/my-package"
Issues = "https://github.com/you/my-package/issues"

[tool.hatch.build.targets.wheel]
packages = ["src/my_package"]

[tool.pytest.ini_options]
testpaths = ["tests"]

Key fields explained:

  • name — Must be unique on PyPI (use hyphens, not underscores)
  • version — Follow semantic versioning (MAJOR.MINOR.PATCH)
  • requires-python — Minimum Python version your package supports
  • classifiers — Help users find your package on PyPI
  • hatchling — A modern, fast build tool (alternatives: setuptools, poetry)

Step 4: Add a README and License

Your README.md becomes the project description on PyPI:

# my-package

Simple string utility functions for Python.

## Installation

```bash
pip install my-package
```

## Usage

```python
from my_package import slugify, truncate

slugify("Hello World!")    # > 'hello-world'
truncate("Long text...", 10)  # > 'Long te...'
```

## License

MIT

For your license, create a LICENSE file. The MIT license is simple and permissive:

MIT License

a copy of this software and associated documentation files...

Step 5: Install in Development Mode

Before publishing, test your package locally. Use editable installs so changes to your code are immediately available:

# Create a virtual environment
python -m venv .venv
source .venv/bin/activate   # On Windows: .venv\Scripts\activate

# Install in editable mode
pip install -e .

# Now test it
python -c "from my_package import slugify; print(slugify('Test!'))"
# Output: test

The -e flag creates a symlink to your source code. When you edit core.py, the changes are immediately reflected — no reinstall needed.

Step 6: Write Tests

Don't publish without tests. A simple pytest file:

tests/test_core.py
from my_package import slugify, truncate

def test_slugify_basic():
    assert slugify("Hello World") == "hello-world"

def test_slugify_special_chars():
    assert slugify("Hello, World!") == "hello-world"

def test_slugify_underscores_and_spaces():
    assert slugify("my_file name") == "my-file-name"

def test_truncate_short_text():
    assert truncate("Hi") == "Hi"

def test_truncate_long_text():
    assert truncate("Hello, World!", 8) == "Hello,..."

def test_truncate_custom_suffix():
    assert truncate("Hello", 3, "...") == "H..."

Run them with:

pip install pytest
pytest tests/ -v

Step 7: Build Your Distribution

Before uploading, build your package locally to verify everything works:

# Install build tool
pip install build

# Build source distribution and wheel
python -m build

This creates two files in the dist/ directory:

  • Source distribution (.tar.gz) — your source code packaged for distribution
  • Wheel (.whl) — pre-built binary distribution that installs faster

Test the wheel by installing it in a fresh virtual environment:

python -m venv test-env
source test-env/bin/activate
pip install dist/my_package-0.1.0-py3-none-any.whl
python -c "from my_package import slugify; print(slugify('Works!'))"

Step 8: Publish to TestPyPI First

Always test on TestPyPI before the real PyPI. It's a sandbox with no impact on production:

# Install twine for uploading
pip install twine

# Upload to TestPyPI
twine upload --repository testpypi dist/*

You'll need a TestPyPI account at test.pypi.org. You can also use an API token:

# Use environment variable for the token
export TWINE_PASSWORD=pypi-your-test-token

# Or pass it directly
twine upload --repository testpypi \
  --username __token__ \
  --password pypi-your-test-token \
  dist/*

Test the installation:

pip install --index-url https://test.pypi.org/simple/ my-package

Step 9: Publish to PyPI

Once everything checks out on TestPyPI, publish to the real PyPI:

# Create account at https://pypi.org/account/register/
# Generate an API token at https://pypi.org/manage/account/token/

# Upload
twine upload dist/*

Using an API token (recommended over passwords):

export TWINE_USERNAME=__token__
export TWINE_PASSWORD=pypi-your-real-token
twine upload dist/*

After successful upload, your package is live at https://pypi.org/project/my-package/ and anyone can install it with pip install my-package.

Step 10: Bump Version and Re-publish

When you release updates, follow semantic versioning:

  • MAJOR — Breaking changes (1.0.0 → 2.0.0)
  • MINOR — New features, backward compatible (0.1.0 → 0.2.0)
  • PATCH — Bug fixes (0.1.0 → 0.1.1)

Update the version in pyproject.toml, rebuild, and re-upload:

# Edit pyproject.toml, change version = "0.2.0"
python -m build
twine upload dist/*

Automation with GitHub Actions

Automate the build and publish process so every tagged release goes to PyPI:

.github/workflows/publish.yml
name: Publish to PyPI
on:
  release:
    types: [published]

jobs:
  publish:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
      - run: pip install build
      - run: python -m build
      - uses: pypa/gh-action-pypi-publish@release/v1
        with:
          password: ${{ secrets.PYPI_API_TOKEN }}

Add PYPI_API_TOKEN to your repository secrets at Settings → Secrets → Actions. Now every time you create a GitHub release, your package is automatically published.

Common Mistakes to Avoid

  1. Using an already-taken name — Check PyPI first before settling on a package name
  2. Forgetting __init__.py — Without it, Python won't recognize your directory as a package
  3. Uploading untested code — Always test on TestPyPI first
  4. Hardcoding version — Use the version in pyproject.toml as the single source
  5. Missing requires-python — Users on old Python versions will get confusing errors

Summary

Python packaging doesn't have to be scary. The modern toolchain — hatchling for building, twine for publishing, pyproject.toml for configuration — makes it straightforward. Start with a clean project structure, write some tests, test on TestPyPI, then publish to the world. Your future self (and other developers) will thank you.
