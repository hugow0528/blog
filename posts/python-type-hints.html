Python Type Hints and Type Checking: Write Cleaner, Safer Code

2026-06-24 10 min read New

Python is dynamically typed — variables don't declare their types, and type errors only appear at runtime when the bad code actually executes. Type hints change that. They let you specify expected types for function parameters and return values, enabling static analysis tools to catch bugs before your code runs.

Type hints don't slow down your code — Python ignores them at runtime. They're purely for developers and tooling. Think of them as documentation that your editor and linter can actually use.

Why Use Type Hints?

  • Catch bugs early: Find type mismatches during development instead of in production
  • Better IDE support: Auto-completion, inline documentation, and real-time error highlighting
  • Self-documenting code: Read a function signature and instantly know what it expects and returns
  • Refactoring confidence: Change a function's return type and get warnings everywhere it's used

Basic Type Hints

Function Parameters and Returns

Without type hints, this function's behavior isn't obvious:

def greet(name):
    return f"Hello, {name}!"

With type hints, it's crystal clear:

def greet(name: str) -> str:
    return f"Hello, {name}!"

# Works fine
print(greet("Hugo"))  # Hello, Hugo!

# A type checker will warn you about this:
print(greet(42))  # mypy error: Argument 1 to "greet" has incompatible type "int"

The : str after name means "this parameter must be a string." The -> str means "this function returns a string."

Common Built-in Types

def calculate_area(length: float, width: float) -> float:
    return length * width

def is_even(number: int) -> bool:
    return number % 2 == 0

def get_greeting() -> str:
    return "Hello!"

def print_message(message: str) -> None:
    print(message)

Key built-in types you'll use most:

  • str — text / strings
  • int — whole numbers
  • float — decimal numbers
  • bool — True or False
  • None — no value / void (use for functions that don't return anything)

Collection Types

Python has rich types for collections. Import them from the typing module:

from typing import List, Dict, Tuple, Set, Optional, Union

def get_names() -> list[str]:
    return ["Alice", "Bob", "Charlie"]

def student_scores(scores: dict[str, int]) -> float:
    return sum(scores.values()) / len(scores)

# Optional means the value can be None or the specified type
def find_user(user_id: int) -> str | None:
    users = {1: "Alice", 2: "Bob"}
    return users.get(user_id)

# Union means the value can be one of several types
def process_id(value: int | str) -> str:
    return str(value)

# Tuples with fixed size and specific types
def get_coordinates() -> tuple[float, float]:
    return (40.7128, -74.0060)

Note: In Python 3.9+, you can use list[str] and dict[str, int] directly. In older versions, you need List[str] and Dict[str, int] from the typing module.

Using mypy for Static Type Checking

mypy is the most popular Python type checker. Install it with pip:

pip install mypy

Create a file called example.py:

# example.py
def add(a: int, b: int) -> int:
    return a + b

# This is fine
result = add(2, 3)
print(result)

# mypy will catch this error:
result2 = add("hello", "world")

Run mypy:

mypy example.py
# Output:
# example.py:7: error: Argument 1 to "add" has incompatible type "str"; expected "int"
# example.py:7: error: Argument 2 to "add" has incompatible type "str"; expected "int"

mypy caught the error without running the code. That's the power of static type checking.

Type Hints in Classes

Type hints work great with object-oriented Python:

class User:
    def __init__(self, name: str, email: str, age: int | None = None) -> None:
        self.name = name
        self.email = email
        self.age = age

    def greet(self) -> str:
        return f"Hi, I'm {self.name}"

    def is_adult(self) -> bool:
        if self.age is None:
            return False
        return self.age >= 18

# Usage
user = User("Hugo", "hugo@example.com", 28)
print(user.greet())      # Hi, I'm Hugo
print(user.is_adult())   # True

user2 = User("Alice", "alice@example.com")
print(user2.is_adult())  # False (age is None)

The typing Module: Advanced Types

Any — When You Can't Specify a Type

from typing import Any

def debug(value: Any) -> None:
    """Print anything, no type restrictions"""
    print(f"Value: {value}, Type: {type(value)}")

debug("hello")
debug(42)
debug([1, 2, 3])

Generic Types with TypeVar

TypeVar lets you write functions that work with any type while keeping type safety:

from typing import TypeVar, List

T = TypeVar("T")

def first(items: list[T]) -> T | None:
    """Return the first item, or None if empty"""
    return items[0] if items else None

# mypy knows the return type matches the input type
name = first(["Alice", "Bob"])    # name is str | None
count = first([1, 2, 3])          # count is int | None

TypedDict for Structured Data

from typing import TypedDict

class Movie(TypedDict):
    title: str
    year: int
    rating: float

def rate_movie(movie: Movie) -> str:
    if movie["rating"] >= 8.0:
        return f"Excellent: {movie['title']} ({movie['year']})"
    return f"Okay: {movie['title']}"

movie = {"title": "Inception", "year": 2010, "rating": 8.8}
print(rate_movie(movie))  # Excellent: Inception (2010)

Setting Up a mypy Configuration

Create a mypy.ini in your project root for consistent checking:

[mypy]
python_version = 3.12
warn_return_any = True
warn_unused_configs = True
disallow_untyped_defs = True
disallow_incomplete_defs = True
check_untyped_defs = True
disallow_untyped_decorators = True
no_implicit_optional = True
strict_optional = True

The disallow_untyped_defs option enforces that every function has type hints — strict but excellent for team projects.

Integrating with Your Workflow

VS Code

Install the Python extension — mypy runs automatically as you type. No configuration needed if you have mypy.ini.

GitHub Actions CI Check

# .github/workflows/mypy.yml
name: Type Check
on: [push, pull_request]

jobs:
  mypy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install mypy
      - run: mypy .

Pre-commit Hook

# .pre-commit-config.yaml
repos:
  - repo: https://github.com/pre-commit/mirrors-mypy
    rev: v1.11.0
    hooks:
      - id: mypy
        additional_dependencies: []

When NOT to Use Type Hints

Type hints aren't always the right call:

  • Quick one-off scripts: A 20-line data processing script doesn't need types
  • Prototyping: Get working code first, add types when you stabilize the API
  • Dynamic data structures: When dealing with JSON or APIs that return unpredictable shapes, use Any or TypedDict selectively

Summary

Type hints make Python code more readable, maintainable, and reliable. They catch bugs at development time, improve IDE experience, and serve as living documentation. Start small — add types to your function signatures first, then grow your coverage. Tools like mypy make it easy to enforce consistency across a project.

For small personal scripts, they're optional. For anything shared, maintained, or production-critical, they're a must.
