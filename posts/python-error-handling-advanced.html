Python Error Handling: try/except, Custom Exceptions & Defensive Coding

July 8, 2026 10 min read

Every Python program encounters errors — invalid input, missing files, network failures, and unexpected data. The difference between a beginner and a professional developer is not whether their code has bugs, but how gracefully it handles them. This guide covers Python error handling from try/except basics to production-grade patterns including custom exceptions, retry logic, and context managers.

Why Error Handling Matters

Without proper error handling, a single unexpected value can crash your entire application:

# ❌ Crashes with ZeroDivisionError
def calculate_discount(price, percentage):
    return price / (1 - percentage / 100)

calculate_discount(100, 100)  # 💥 Crash!

With error handling, your program stays alive and gives useful feedback:

# ✅ Graceful handling
def calculate_discount(price, percentage):
    if percentage >= 100:
        raise ValueError("Discount must be less than 100%")
    if percentage < 0:
        raise ValueError("Discount cannot be negative")
    return price / (1 - percentage / 100)

try:
    result = calculate_discount(100, 100)
except ValueError as e:
    print(f"Invalid input: {e}")  # Invalid input: Discount must be less than 100%

The try/except/else/finally Structure

Python's exception handling has four parts that work together:

try:
    # Code that might raise an exception
    result = risky_operation()
except SpecificError as e:
    # Handle a specific type of error
    print(f"Got error: {e}")
except AnotherError:
    # Handle a different error type
    print("Something else went wrong")
except Exception as e:
    # Catch-all for any other exception
    print(f"Unexpected error: {e}")
else:
    # Runs ONLY if no exception was raised
    print("Operation succeeded!")
finally:
    # ALWAYS runs, whether exception or not
    print("Cleanup done")

Each block serves a specific purpose:

  • try — The code that might fail
  • except SpecificError — Handle expected errors
  • except Exception — Catch unexpected errors (use sparingly)
  • else — Code that should run on success (avoids accidentally catching exceptions)
  • finally — Cleanup that must always happen (closing files, releasing locks)

Catching Specific Exceptions

Always catch the most specific exception you can. Catching a broad Exception masks bugs:

import json

# ❌ BAD: Catches too much — hides bugs
try:
    data = json.loads(user_input)
except Exception:
    data = {}

# ✅ GOOD: Catch only what you expect
try:
    data = json.loads(user_input)
except (json.JSONDecodeError, TypeError) as e:
    print(f"Failed to parse JSON: {e}")
    data = {}

Multiple Exceptions in One Handler

When different exceptions need the same handling, group them:

def load_config(filepath):
    try:
        with open(filepath) as f:
            return json.load(f)
    except (FileNotFoundError, PermissionError) as e:
        # Same fallback for both errors
        print(f"Cannot read config: {e}")
        return {"debug": True, "port": 8080}
    except json.JSONDecodeError as e:
        # Different handling for malformed JSON
        print(f"Config file is not valid JSON: {e}")
        raise  # Re-raise — this is a critical error

The raise Statement

Use raise to signal that something went wrong:

def get_username(user_id):
    if user_id <= 0:
        raise ValueError(f"user_id must be positive, got {user_id}")
    
    user = database.find(user_id)
    if user is None:
        raise LookupError(f"No user found with ID {user_id}")
    
    return user.name

# Using it
try:
    name = get_username(-5)
except ValueError as e:
    print(e)  # user_id must be positive, got -5

You can also re-raise the current exception (useful in logging before propagation):

try:
    connect_to_database()
except ConnectionError as e:
    log_error(f"Database connection failed: {e}")
    # Clean up any partial state
    close_temp_files()
    raise  # Re-raise the original exception

Chaining Exceptions with raise from

When you catch one exception and raise another, use raise ... from to preserve the original traceback:

def parse_age(text):
    try:
        return int(text)
    except ValueError as original_error:
        raise ValueError(f"Age must be a number, got '{text}'") from original_error

try:
    age = parse_age("twenty")
except ValueError as e:
    print(e)           # Age must be a number, got 'twenty'
    print(e.__cause__) # The original ValueError: invalid literal...

The from clause creates a chain that shows both errors in the traceback. Without it, the original error is lost.

Custom Exception Classes

Create custom exceptions to make your error handling expressive:

# Define application-specific exceptions
class PaymentError(Exception):
    """Base exception for payment issues"""
    pass

class InsufficientFundsError(PaymentError):
    def __init__(self, balance, amount):
        self.balance = balance
        self.amount = amount
        super().__init__(
            f"Insufficient funds: balance=${balance:.2f}, "
            f"requested=${amount:.2f}"
        )

class CardExpiredError(PaymentError):
    def __init__(self, card_number, expiry_date):
        self.card_number = card_number
        self.expiry_date = expiry_date
        super().__init__(
            f"Card ending in {card_number[-4:]} expired on {expiry_date}"
        )

# Use them
def process_payment(account, amount):
    if account.is_expired():
        raise CardExpiredError(account.card, account.expires)
    if account.balance < amount:
        raise InsufficientFundsError(account.balance, amount)
    account.balance -= amount
    return True

# Handle specific subtypes
try:
    process_payment(my_account, 500)
except InsufficientFundsError as e:
    print(f"Ask user to add money: {e.balance - e.amount}")
except CardExpiredError as e:
    print("Redirect to card update page")
except PaymentError as e:
    # Catch any other payment error
    print(f"Payment failed: {e}")

💡 Best Practice: Create an Exception Hierarchy

Define a base exception for your application, then create specific subclasses. This lets callers catch everything with except AppError or handle specifics with except SpecificError.

Retry Logic with Exponential Backoff

Network calls and database connections fail temporarily. Retry with increasing delays:

import time

def retry_with_backoff(func, max_retries=3, base_delay=1):
    """Retry a function with exponential backoff"""
    for attempt in range(max_retries):
        try:
            return func()
        except (ConnectionError, TimeoutError) as e:
            if attempt == max_retries - 1:
                raise  # Last attempt — give up
            delay = base_delay * (2 ** attempt)  # 1s, 2s, 4s...
            print(f"Attempt {attempt + 1} failed: {e}. Retrying in {delay}s...")
            time.sleep(delay)
    raise RuntimeError("All retries exhausted")

# Usage
def fetch_data():
    response = requests.get("https://api.example.com/data", timeout=5)
    response.raise_for_status()
    return response.json()

# This will retry up to 3 times on connection errors
try:
    data = retry_with_backoff(fetch_data)
    print("Got data!", len(data))
except Exception as e:
    print(f"Failed after all retries: {e}")

The backoff pattern (1s, 2s, 4s, 8s...) prevents overwhelming a recovering server. Python's tenacity library provides a decorator-based version if you don't want to write it manually.

Context Managers for Resource Cleanup

The with statement ensures resources are cleaned up even when exceptions occur:

# ✅ File handling — always closes, even on error
with open("data.txt", "w") as f:
    f.write("hello")
    # if an exception happens here, f.close() still runs

# ✅ Database connection pattern
class DatabaseConnection:
    def __init__(self, url):
        self.url = url
        self.conn = None
    
    def __enter__(self):
        self.conn = create_connection(self.url)
        return self.conn
    
    def __exit__(self, exc_type, exc_val, exc_tb):
        if self.conn:
            if exc_type is not None:
                self.conn.rollback()  # Undo changes on error
            else:
                self.conn.commit()    # Save changes on success
            self.conn.close()
        return False  # Don't suppress exceptions

# Usage
with DatabaseConnection("sqlite:///mydb.db") as db:
    db.execute("INSERT INTO users VALUES (?, ?)", ("Alice", "alice@example.com"))
    # If any error occurs above, the transaction rolls back automatically

Assertion vs Exception

Don't use assert for input validation — it can be disabled:

# ❌ BAD: assert can be disabled with python -O flag
def divide(a, b):
    assert b != 0, "Cannot divide by zero"
    return a / b

# ✅ GOOD: Use exceptions for validation
def divide(a, b):
    if b == 0:
        raise ZeroDivisionError("Cannot divide by zero")
    return a / b

# ✅ assert is fine for internal invariants (bugs, not user errors)
def process_items(items):
    # This should NEVER be False — it indicates a bug
    assert len(items) > 0, "Internal error: empty items list"
    return [transform(item) for item in items]

Real-World Pattern: Safe API Client

Combining everything into a production-ready pattern:

import json
import time
import logging

logger = logging.getLogger(__name__)

class APIError(Exception):
    """Base API exception"""
    def __init__(self, message, status_code=None, response_body=None):
        super().__init__(message)
        self.status_code = status_code
        self.response_body = response_body

class RateLimitError(APIError):
    pass

class AuthenticationError(APIError):
    pass

class APIClient:
    def __init__(self, base_url, api_key):
        self.base_url = base_url
        self.api_key = api_key
        self.session = requests.Session()
        self.session.headers.update({
            "Authorization": f"Bearer {api_key}",
            "Content-Type": "application/json"
        })
    
    def request(self, method, endpoint, **kwargs):
        """Make a request with retry and proper error handling"""
        url = f"{self.base_url}/{endpoint.lstrip('/')}"
        
        for attempt in range(3):
            try:
                response = self.session.request(
                    method, url, timeout=10, **kwargs
                )
                
                if response.status_code == 429:
                    retry_after = int(response.headers.get("Retry-After", 5))
                    logger.warning(f"Rate limited. Waiting {retry_after}s...")
                    time.sleep(retry_after)
                    continue
                
                response.raise_for_status()
                
                if response.content:
                    return response.json()
                return None
                
            except requests.Timeout:
                logger.warning(f"Request timeout (attempt {attempt + 1})")
                if attempt == 2:
                    raise APIError("Request timed out after 3 attempts")
                time.sleep(2 ** attempt)
                
            except requests.ConnectionError:
                logger.warning(f"Connection error (attempt {attempt + 1})")
                if attempt == 2:
                    raise APIError("Cannot connect after 3 attempts")
                time.sleep(2 ** attempt)
        
        raise APIError("Unexpected request failure")
    
    def get_users(self):
        return self.request("GET", "/users")
    
    def create_user(self, name, email):
        return self.request("POST", "/users", json={
            "name": name,
            "email": email
        })

# Usage
try:
    client = APIClient("https://api.example.com", "sk-12345")
    users = client.get_users()
    print(f"Loaded {len(users)} users")
except AuthenticationError:
    print("Invalid API key — check your configuration")
except RateLimitError:
    print("Too many requests — slow down")
except APIError as e:
    print(f"API request failed: {e}")

Summary

Good error handling makes your Python programs robust and maintainable. Key takeaways:

  • Catch specific exceptions — Never use bare except: or broad except Exception:
  • Create custom exceptions — They make your API self-documenting
  • Use raise from — Preserve error chains for debugging
  • Implement retry logic — Temporary failures should be retried with backoff
  • Use context managers — with guarantees cleanup
  • Reserve assert for bugs — Use exceptions for user input validation
  • Log before raising — Especially in production, always log before re-raising

Mastering error handling transforms your code from "works on my machine" to "production-ready." The next time you write a function, ask yourself: "What can go wrong here?" Then write the code that handles it gracefully.
