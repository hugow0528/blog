Git Tags & Semantic Versioning: Release Management Made Simple

2026-06-30

You've learned Git basics and branching strategies. Now it's time to mark your progress with Git tags — the way you create immutable release points in your project history. Combined with semantic versioning, tags become the backbone of professional software releases. Whether you're deploying a Python package, releasing a web app, or shipping a CLI tool, tags are how you say "this is version 1.0" to the world.

What Are Git Tags?

Git tags are like bookmarks for specific commits. Unlike branches, which move forward as you commit, tags point forever to the exact commit you created them at. They're the standard way to mark releases, milestones, and production-ready snapshots.

There are two types of tags in Git:

  • Lightweight tags — Simple pointers to a commit. Think of them as a named branch that never moves.
  • Annotated tags — Full Git objects with a message, author, date, and optional GPG signature. Always use these for releases.

Creating Tags

Let's start with the basics. First, make sure you're on the commit you want to tag:

# List recent commits to find the one you want to tag
git log --oneline -10

# Create an annotated tag (recommended for releases)
git tag -a v1.0.0 -m "Release version 1.0.0: Initial stable release"

# Create a lightweight tag (for quick, informal marks)
git tag v1.0.0-beta

Always prefix release tags with v (e.g., v1.0.0). This is a universal convention — PyPI, npm, Docker Hub, and GitHub all expect it.

Viewing and Managing Tags

# List all tags
git tag

# List tags matching a pattern
git tag --list "v1.*"

# Show details of an annotated tag
git show v1.0.0

# Describe the most recent tag for current commit
git describe --tags
# Output: v1.0.0-3-ga1b2c3d (3 commits after v1.0.0)

Semantic Versioning (SemVer)

Semantic versioning is a simple scheme for version numbers that everyone understands. Your version is always MAJOR.MINOR.PATCH:

  • MAJOR (1.0.0 → 2.0.0): Breaking changes. APIs changed, old code won't work.
  • MINOR (1.0.0 → 1.1.0): New features, backwards-compatible.
  • PATCH (1.0.0 → 1.0.1): Bug fixes only, backwards-compatible.

Real-World Examples

# Bug fix in error handling
git tag -a v1.0.1 -m "Fix: Handle empty response from API"

# Add new feature: user authentication
git tag -a v1.1.0 -m "Feat: Add user authentication module"

# Breaking change: rename all API endpoints
git tag -a v2.0.0 -m "BREAKING: Rename /api/v1/ to /api/v2/ endpoints"

Pre-release and Build Metadata

# Alpha release (early testing)
git tag -a v2.0.0-alpha.1 -m "Alpha: New API v2 endpoints"

# Beta release (feature complete, testing)
git tag -a v2.0.0-beta.1 -m "Beta: Stable API v2, ready for testing"

# Release candidate (almost ready)
git tag -a v2.0.0-rc.1 -m "RC1: Final round of fixes before v2.0.0"

Pushing Tags to GitHub

Tags don't push automatically with git push. You need to push them explicitly:

# Push a single tag
git push origin v1.0.0

# Push all tags at once
git push origin --tags

# Delete a tag from remote (if you made a mistake)
git push origin --delete v1.0.0-rc.1
# Then delete locally
git tag -d v1.0.0-rc.1

Creating Releases from Tags on GitHub

Once your tag is on GitHub, you can create a release — which adds release notes, changelogs, and downloadable assets. You can do this through the GitHub web UI or the API:

# Using curl to create a GitHub release via API
curl -X POST https://api.github.com/repos/hugow0528/myapp/releases \
  -H "Authorization: token $GITHUB_TOKEN" \
  -H "Accept: application/vnd.github+json" \
  -d '{
    "tag_name": "v1.0.0",
    "name": "Release v1.0.0",
    "body": "### What's New\n- Initial stable release\n- User authentication\n- REST API endpoints\n\n### Bug Fixes\n- Fixed login timeout issue",
    "draft": false,
    "prerelease": false
  }'

Automating Tags with Python

You can automate version tagging in your Python projects. Here's a script that bumps your version number:

#!/usr/bin/env python3
"""bump_version.py - Automated version bumping for your projects"""
import re
import subprocess

VERSION_FILE = "VERSION.txt"

def read_version():
    """Read the current version from VERSION.txt"""
    with open(VERSION_FILE, "r") as f:
        return f.read().strip()

def write_version(version):
    """Write the new version to VERSION.txt"""
    with open(VERSION_FILE, "w") as f:
        f.write(version)

def bump_version(bump_type="patch"):
    """Bump version: major, minor, or patch"""
    version = read_version()
    parts = version.lstrip("v").split(".")
    major, minor, patch = int(parts[0]), int(parts[1]), int(parts[2])

    if bump_type == "major":
        major += 1
        minor = 0
        patch = 0
    elif bump_type == "minor":
        minor += 1
        patch = 0
    elif bump_type == "patch":
        patch += 1

    new_version = f"v{major}.{minor}.{patch}"
    write_version(new_version)
    print(f"Bumped {version} → {new_version}")
    return new_version

def create_tag(version):
    """Create an annotated Git tag"""
    subprocess.run(["git", "tag", "-a", version, "-m", f"Release {version}"])
    print(f"Created tag: {version}")

def push_tag(version):
    """Push the tag to remote"""
    subprocess.run(["git", "push", "origin", version])
    print(f"Pushed tag: {version}")

if __name__ == "__main__":
    import sys
    bump_type = sys.argv[1] if len(sys.argv) > 1 else "patch"
    version = bump_version(bump_type)
    create_tag(version)
    push_tag(version)

Usage:

# Bump patch version (1.0.0 → 1.0.1)
python bump_version.py patch

# Bump minor version (1.0.1 → 1.1.0)
python bump_version.py minor

# Bump major version (1.1.0 → 2.0.0)
python bump_version.py major

Auto-Tagging with GitHub Actions

Connect your versioning to CI/CD with a GitHub Actions workflow that auto-tags releases:

# .github/workflows/release.yml
name: Release on Merge

on:
  push:
    branches: [main]

jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Read version
        run: echo "VERSION=$(cat VERSION.txt)" >> $GITHUB_ENV

      - name: Check if tag exists
        id: check-tag
        run: |
          if git ls-remote --tags origin | grep -q "refs/tags/${VERSION}"; then
            echo "exists=true" >> $GITHUB_OUTPUT
          else
            echo "exists=false" >> $GITHUB_OUTPUT
          fi

      - name: Create release
        if: steps.check-tag.outputs.exists == 'false'
        uses: softprops/action-gh-release@v2
        with:
          tag_name: ${{ env.VERSION }}
          name: Release ${{ env.VERSION }}
          generate_release_notes: true
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}

This workflow automatically creates a GitHub release whenever you push to main with a new version in VERSION.txt.

Tagging Checklist for Production Releases

Before you push that tag, run through this checklist:

  1. ✅ All tests pass — run your full test suite
  2. ✅ Version number updated in your code (VERSION.txt, pyproject.toml, etc.)
  3. ✅ Changelog updated with what changed
  4. ✅ No debugging code or print() statements left
  5. ✅ Dependencies locked (requirements.txt or pip freeze)
  6. ✅ Annotated tag created with clear release message
  7. ✅ Tag pushed to remote repository
  8. ✅ GitHub release notes written

Conclusion

Git tags and semantic versioning might seem simple, but they're the foundation of professional software releases. Every library you pip install, every Docker image you docker pull, every GitHub release — they all use this exact same pattern. Master tags now, and you'll save yourself from versioning confusion later.

Quick reference:

# Your daily tag workflow
git tag -a v1.1.0 -m "Add new features"    # Create
git tag --list                              # List
git push origin --tags                      # Push
git describe --tags                         # Check current
