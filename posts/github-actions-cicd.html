GitHub Actions CI/CD: Automate Your Workflow

June 22, 2026 · 10 min read

GitHub Actions lets you automate your development workflow directly in your repository. Run tests on every commit, build Docker images, deploy to servers — all triggered automatically. This guide takes you from zero to a full CI/CD pipeline with working YAML examples.

What Is CI/CD?

CI (Continuous Integration) means automatically building and testing your code every time you push changes. CD (Continuous Deployment) means automatically deploying passing code to production.

Without CI/CD, your workflow might look like this: push code → remember to run tests manually → remember to build → email the team → someone deploys. With CI/CD, GitHub handles all of that automatically.

Golden rule of CI/CD: Any change that breaks the build should be caught within minutes, not days. Automation is your safety net.

GitHub Actions Anatomy

GitHub Actions uses YAML files stored in .github/workflows/ in your repository. Every file defines a workflow, which contains one or more jobs, which contain steps.

  • Workflow — The automation process (a YAML file)
  • Trigger (event) — When the workflow runs (push, pull request, schedule, etc.)
  • Job — A set of steps that run on the same machine (runner)
  • Step — An individual task (run a command or use a pre-built action)
  • Runner — The virtual machine that executes the job
  • Action — A reusable package (like a npm package for workflows)

Your First Workflow: Hello World

Create .github/workflows/hello.yml in your repository:

# .github/workflows/hello.yml
name: Hello World

on: push  # Trigger on every push

jobs:
  greet:
    runs-on: ubuntu-latest  # Run on the latest Ubuntu VM

    steps:
      - name: Say Hello
        run: echo "Hello from GitHub Actions! 🚀"

      - name: Check the Date
        run: date

      - name: Show Repository Info
        run: |
          echo "Repo: ${{ github.repository }}"
          echo "Branch: ${{ github.ref_name }}"
          echo "Actor: ${{ github.actor }}"

Push this file to your repository and check the Actions tab. You'll see your workflow run automatically. Each step's output is visible in the logs.

The ${{ }} syntax accesses GitHub context variables. Common ones:

  • github.repository — Owner/repo name
  • github.ref_name — Branch or tag name
  • github.actor — User who triggered the workflow
  • github.event_name — The trigger event (push, pull_request, etc.)

Trigger Events You'll Use

# Run on push to main branch only
on:
  push:
    branches: [main]

# Run on pull requests to main
on:
  pull_request:
    branches: [main]

# Run on push or pull requests
on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

# Run on a schedule (every Monday at 9 AM UTC)
on:
  schedule:
    - cron: '0 9 * * 1'

# Run manually from the Actions tab
on:
  workflow_dispatch:

# Combine multiple triggers
on:
  push:
    branches: [main]
  workflow_dispatch:
  schedule:
    - cron: '0 0 * * *'

Workflow #1: Python Test Pipeline

Let's build a real CI pipeline that installs dependencies, runs tests, and reports results for a Python project:

# .github/workflows/test.yml
name: Python Test Suite

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest

    # Test against multiple Python versions
    strategy:
      matrix:
        python-version: ["3.10", "3.11", "3.12"]

    steps:
      # 1. Check out the repository code
      - name: Checkout code
        uses: actions/checkout@v4

      # 2. Set up Python
      - name: Set up Python ${{ matrix.python-version }}
        uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python-version }}

      # 3. Cache pip dependencies (speeds up subsequent runs)
      - name: Cache pip packages
        uses: actions/cache@v4
        with:
          path: ~/.cache/pip
          key: ${{ runner.os }}-pip-${{ hashFiles('**/requirements.txt') }}
          restore-keys: |
            ${{ runner.os }}-pip-

      # 4. Install dependencies
      - name: Install dependencies
        run: |
          python -m pip install --upgrade pip
          pip install -r requirements.txt
          pip install pytest pytest-cov

      # 5. Run tests with coverage report
      - name: Run tests
        run: |
          pytest tests/ \
            --cov=src \
            --cov-report=xml \
            --cov-report=term-missing \
            -v

      # 6. Upload coverage report as artifact
      - name: Upload coverage
        uses: actions/upload-artifact@v4
        with:
          name: coverage-${{ matrix.python-version }}
          path: coverage.xml

This workflow does several important things:

  • Matrix strategy — Tests against Python 3.10, 3.11, and 3.12 simultaneously. If it fails on one version, you'll know immediately.
  • Caching — The pip cache key includes the hash of requirements.txt, so dependencies are re-downloaded only when they change.
  • Coverage — pytest-cov generates a coverage report showing which lines of code are tested.
  • Artifacts — Coverage XML files are uploaded so you can download them after the run.

Workflow #2: Docker Build & Push

After running tests, let's build and publish a Docker image:

# .github/workflows/docker.yml
name: Build and Push Docker Image

on:
  push:
    branches: [main]
    tags: ["v*"]  # Also trigger on version tags like v1.0.0

jobs:
  build:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3

      - name: Log in to Docker Hub
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKER_USERNAME }}
          password: ${{ secrets.DOCKER_PASSWORD }}

      - name: Extract metadata (tags, labels)
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: yourusername/myapp
          tags: |
            type=ref,event=branch
            type=ref,event=pr
            type=semver,pattern={{version}}
            type=sha

      - name: Build and push
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

This workflow uses Docker secrets for credentials. To set them up:

  1. Go to your repository → Settings → Secrets and variables → Actions
  2. Click "New repository secret"
  3. Add DOCKER_USERNAME and DOCKER_PASSWORD (use a Docker personal access token, not your real password)

The docker/metadata-action automatically generates tags: main for the main branch, v1.0.0 for version tags, and the git SHA for traceability.

Workflow #3: Deploy with Cloudflare Tunnel

Chain the test and Docker workflows together to auto-deploy:

# .github/workflows/deploy.yml
name: Deploy to Server

on:
  # Trigger only after the Docker workflow succeeds
  workflow_run:
    workflows: ["Build and Push Docker Image"]
    types:
      - completed
    branches: [main]

jobs:
  deploy:
    # Only deploy if the previous workflow succeeded
    if: ${{ github.event.workflow_run.conclusion == 'success' }}
    runs-on: ubuntu-latest

    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Set up SSH
        uses: webfactory/ssh-agent@v0.7.0
        with:
          ssh-private-key: ${{ secrets.SSH_PRIVATE_KEY }}

      - name: Deploy via SSH
        env:
          SERVER_USER: ${{ secrets.SERVER_USER }}
          SERVER_HOST: ${{ secrets.SERVER_HOST }}
          DOCKER_IMAGE: ${{ secrets.DOCKER_USERNAME }}/myapp
        run: |
          ssh -o StrictHostKeyChecking=no ${SERVER_USER}@${SERVER_HOST} \
          "docker pull ${DOCKER_IMAGE}:main && \
           docker compose -f /opt/myapp/docker-compose.yml up -d && \
           docker image prune -f"

This workflow:

  • Only runs after the Docker build succeeds
  • Uses SSH to connect to your server
  • Pulls the latest image, restarts containers, and cleans up old images

Useful Built-in Actions

GitHub provides many built-in actions. Here are the most useful ones:

# Checkout repository code
- uses: actions/checkout@v4

# Set up Python
- uses: actions/setup-python@v5
  with:
    python-version: '3.12'

# Set up Node.js
- uses: actions/setup-node@v4
  with:
    node-version: '20'

# Cache dependencies
- uses: actions/cache@v4
  with:
    path: ~/.cache/pip
    key: ${{ runner.os }}-pip-${{ hashFiles('**/requirements.txt') }}

# Upload artifacts (test results, builds, etc.)
- uses: actions/upload-artifact@v4
  with:
    name: test-results
    path: test-reports/

# Download artifacts from another job
- uses: actions/download-artifact@v4

# Create a GitHub Release
- uses: softprops/action-gh-release@v2
  with:
    files: dist/*
    tag_name: v1.0.0
  env:
    GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}

Conditional Logic and Branch-Specific Steps

Run steps only on certain conditions:

# Only on main branch
- name: Deploy to production
  if: github.ref == 'refs/heads/main'
  run: echo "Deploying to production..."

# Only on pull requests
- name: Comment on PR
  if: github.event_name == 'pull_request'
  run: echo "This is a PR build"

# Only when specific files change
on:
  push:
    paths:
      - 'src/**'
      - 'tests/**'
      - 'requirements.txt'
      - '.github/workflows/**'

Passing Data Between Jobs with Environment Files

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Build version
        run: |
          VERSION="1.0.${{ github.run_number }}"
          echo "version=$VERSION" >> $GITHUB_ENV
          echo "Built version: $VERSION"

  test:
    needs: build  # Wait for build job to finish
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Use version from build
        run: echo "Testing version $VERSION"

Quick Reference

  • uses: actions/checkout@v4 — Clone the repo
  • uses: actions/setup-python@v5 — Install Python
  • uses: actions/cache@v4 — Cache dependencies
  • needs: [build] — Job dependency (wait for another job)
  • if: github.ref == 'refs/heads/main' — Conditional execution
  • strategy.matrix — Run the same job with different configurations
  • ${{ secrets.NAME }} — Access encrypted secrets
  • on.schedule — Run on a cron schedule
  • on.workflow_run — Trigger after another workflow completes
