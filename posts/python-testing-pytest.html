Python Testing with pytest: Write Reliable Code from Day One

2026-06-25 10 min read New

Writing tests might feel optional when you're just starting out — but untested code is code you can't trust to change. In Python, the pytest framework makes testing fast, readable, and enjoyable. By the end of this guide, you'll be writing automated tests that catch bugs before they reach production.

Testing isn't about proving your code works. It's about building confidence that your code keeps working when you inevitably refactor it three months from now.

Why pytest Over unittest?

Python ships with unittest, but pytest is the community favorite for good reasons:

  • Simpler syntax — use plain assert instead of self.assertEqual()
  • Better error messages — pytest tells you exactly what went wrong and why
  • Auto-discovery — just run pytest and it finds your tests
  • Huge plugin ecosystem — coverage, parallel runs, web testing, and more

Install pytest with pip:

pip install pytest

Your First Test

Let's start with a simple function and test it. Create calculator.py:

# calculator.py
def add(a, b):
    return a + b

def divide(a, b):
    if b == 0:
        raise ValueError("Cannot divide by zero")
    return a / b

Now create test_calculator.py in the same directory. pytest requires test files to start with test_ or end with _test.py:

# test_calculator.py
from calculator import add, divide
import pytest

def test_add():
    assert add(2, 3) == 5
    assert add(-1, 1) == 0
    assert add(0, 0) == 0

def test_add_floats():
    assert add(0.1, 0.2) == pytest.approx(0.3)

def test_divide():
    assert divide(10, 2) == 5.0
    assert divide(7, 2) == pytest.approx(3.5)

def test_divide_by_zero():
    with pytest.raises(ValueError, match="Cannot divide by zero"):
        divide(10, 0)

Run the tests:

$ pytest test_calculator.py
==================== test session starts ====================
collected 4 items

test_calculator.py ....                                    [100%]

===================== 4 passed in 0.01s =====================

That's it. No classes, no setUp methods, no boilerplate. Four tests, four dots.

Understanding Assertions

The heart of pytest is the assert statement. Unlike other languages, pytest rewrites assert at runtime to give you detailed failure info:

def test_string_methods():
    text = "  Hello, World!  "
    
    # Strip whitespace
    assert text.strip() == "Hello, World!"
    
    # Check case
    assert text.upper() == "  HELLO, WORLD!  "
    assert text.startswith("  ")
    assert text.endswith("  ")
    
    # String containment
    assert "World" in text
    assert "Python" not in text
    
    # Truthiness
    assert bool(text) == True
    assert bool("") == False

If any assertion fails, pytest shows you the actual values:

$ pytest
==================== test session starts ====================
FAILED test_strings.py::test_string_methods - AssertionError
assert "Hello" in "Goodbye"
 +  where "Hello" in "Goodbye"

===================== 1 failed in 0.01s =====================

Fixtures: Shared Setup Without Repetition

Fixtures replace setUp/tearDown. They let you define reusable setup code that multiple tests can share:

# test_users.py
import pytest

@pytest.fixture
def sample_users():
    """Return a list of user dictionaries for testing"""
    return [
        {"id": 1, "name": "Alice", "email": "alice@example.com", "active": True},
        {"id": 2, "name": "Bob", "email": "bob@example.com", "active": True},
        {"id": 3, "name": "Charlie", "email": "charlie@example.com", "active": False},
    ]

@pytest.fixture
def active_users(sample_users):
    """Build on another fixture — only active users"""
    return [u for u in sample_users if u["active"]]

def test_user_count(sample_users):
    assert len(sample_users) == 3

def test_all_names_present(sample_users):
    names = [u["name"] for u in sample_users]
    assert "Alice" in names
    assert "Bob" in names
    assert "Charlie" in names

def test_active_filter(active_users):
    assert len(active_users) == 2
    assert all(u["active"] for u in active_users)

The magic is simple: if a test function takes sample_users as a parameter, pytest finds the matching fixture and passes its result. No imports needed.

Parametrized Tests

When you have the same test logic with different inputs, use @pytest.mark.parametrize to avoid repeating yourself:

# test_calculator_advanced.py
from calculator import add, divide
import pytest

@pytest.mark.parametrize("a, b, expected", [
    (1, 2, 3),
    (-1, -1, -2),
    (0, 0, 0),
    (100, 200, 300),
    (-5, 5, 0),
])
def test_add_various_cases(a, b, expected):
    """One test, five data sets — runs as 5 separate tests"""
    assert add(a, b) == expected

@pytest.mark.parametrize("a, b, expected", [
    (10, 2, 5.0),
    (9, 3, 3.0),
    (1, 1, 1.0),
    (7, 3, pytest.approx(2.333333333)),
])
def test_divide_various_cases(a, b, expected):
    assert divide(a, b) == expected

Running this produces 9 test results from just 2 test functions. Each parameter combination is its own test with its own pass/fail status.

Mocking External Dependencies

Real-world code calls APIs, reads files, and hits databases. You don't want your tests to depend on all that — use mocks instead:

# test_mock_api.py
import pytest
from unittest.mock import patch, MagicMock

def get_weather(city):
    """Simulates calling an external weather API"""
    import requests
    response = requests.get(f"https://api.weather.com/{city}")
    response.raise_for_status()
    return response.json()

@patch("requests.get")
def test_get_weather_success(mock_get):
    """Mock a successful API response"""
    mock_response = MagicMock()
    mock_response.json.return_value = {"temp": 22, "city": "Tokyo"}
    mock_response.raise_for_status = MagicMock()
    mock_get.return_value = mock_response
    
    result = get_weather("tokyo")
    
    assert result["temp"] == 22
    assert result["city"] == "Tokyo"
    mock_get.assert_called_once_with("https://api.weather.com/tokyo")

@patch("requests.get")
def test_get_weather_failure(mock_get):
    """Mock an API error"""
    mock_get.side_effect = requests.exceptions.ConnectionError("Timeout")
    
    with pytest.raises(requests.exceptions.ConnectionError):
        get_weather("somewhere")

Mocks let you test your code's logic in isolation — no network, no database, no flaky external services.

Organizing Tests with conftest.py

As your test suite grows, put shared fixtures in conftest.py. pytest automatically discovers this file without any imports:

# conftest.py — shared fixtures for ALL tests
import pytest

@pytest.fixture
def db_connection():
    """Simulated database connection"""
    connection = {"data": [], "connected": True}
    yield connection
    # Cleanup runs after each test
    connection["connected"] = False

@pytest.fixture
def api_client():
    """Simulated API client"""
    return {"base_url": "https://api.example.com", "headers": {}}

Directory structure for a real project:

my_project/
├── calculator.py
├── users.py
├── api_client.py
├── tests/
│   ├── conftest.py          # shared fixtures
│   ├── test_calculator.py
│   ├── test_users.py
│   └── test_api_client.py
└── pytest.ini               # configuration

Running Tests with Useful Flags

# Run all tests
pytest

# Verbose output — show each test name
pytest -v

# Run a specific test file
pytest tests/test_calculator.py

# Run a specific test function
pytest tests/test_calculator.py::test_add

# Run tests matching a keyword
pytest -k "add"

# Stop on first failure
pytest -x

# Show prints and verbose
pytest -v -s

# Generate coverage report
pytest --cov=my_project

# Run only failed tests from last run
pytest --lf

Quick-Start Checklist

  • Install pytest: pip install pytest
  • Name test files test_*.py and test functions test_*
  • Use plain assert for checking results
  • Use @pytest.fixture for shared setup
  • Use @pytest.mark.parametrize for multiple inputs
  • Mock external calls with unittest.mock
  • Put shared fixtures in conftest.py
  • Run pytest -v to see what's happening

Next Steps

Once you're comfortable with basic pytest, explore:

  • pytest-cov — measure code coverage so you know what's tested
  • pytest-xdist — run tests in parallel for faster feedback
  • pytest-mock — a simpler API for creating mocks
  • hypothesis — property-based testing that generates inputs for you

Testing isn't overhead — it's the safety net that lets you code faster with confidence. Start small, test your most important functions first, and build the habit early.
