Git Rebase vs Merge: Which Should You Use? — Complete Guide

July 8, 2026 · 10 min read

You've been using git merge for months. It works fine — your feature branch gets combined with main, and everything ships. But then a senior developer rewrites your entire commit history with git rebase, and suddenly you have to force-push.

What happened? What's the difference? And more importantly — when should you use each one?

This guide walks through both operations with visual examples, shows real-world workflows, and gives you a decision framework so you never second-guess your git strategy again.

Quick Answer

  • git merge — preserves history exactly as it happened. Creates a merge commit. Safe for shared branches.
  • git rebase — rewrites history to look linear. Moves your commits on top of another branch. Great for cleaning up before merging.

1. The Problem: Diverging Branches

Imagine this scenario. You start a feature branch from main, but while you're working, someone else merges new commits to main:

# Current state — two branches diverged
main:     A --- B --- C
                  \
feature:           D --- E

# C was added to main while you were writing D and E

Now you need to integrate C into your feature. Two options: merge or rebase. Let's see what each produces.

2. git merge: The Honest History

When you git merge main into your feature branch:

# Inside your feature branch
git checkout feature
git merge main

# Result: a new merge commit is created
main:     A --- B --- C
                  \       \
feature:           D --- E --- M (merge commit)

The merge commit M has two parents — both C and E. This faithfully records that your feature branch branched off, diverged, and then was brought back together.

Pros of merging:

  • ✅ Preserves true history — everyone can see the branching timeline
  • ✅ No rewriting — no one else's commits are changed
  • ✅ Safe for shared branches — never creates confusion
  • ✅ Easy to undo — git revert a merge commit

Cons of merging:

  • ❌ Creates merge commits — history gets noisy with many features
  • ❌ Branching diamonds — git log --oneline --graph becomes a web

3. git rebase: The Clean History

When you git rebase main on your feature branch:

# Inside your feature branch
git checkout feature
git rebase main

# Result: your commits are replayed ON TOP of main
main:     A --- B --- C --- D' --- E'
                             (feature rebased)

Notice D became D' and E became E'. They have the same content but different commit hashes. Git rebase literally copied your commits and placed them on top of C.

Pros of rebasing:

  • ✅ Linear history — git log --graph is a straight line
  • ✅ Easy to read — commit sequence tells a clean story
  • ✅ No merge noise — no extra merge commits cluttering history

Cons of rebasing:

  • ❌ Rewrites history — changes commit hashes
  • ❌ NEVER rebase shared branches — confuses collaborators
  • ❌ Can lose commits — if you're not careful with force-push

4. The Golden Rule of Rebasing

Memorize this:

Only rebase local, private branches that no one else has fetched. 
# ✅ SAFE to rebase
# - You're the only one who has the branch
# - Nobody else has based work on it
git checkout feature-login
git rebase main

# ❌ NEVER rebase
# - Others are working on this branch
# - It's already been reviewed/merged
# - It's main, develop, or any shared branch
git checkout main  # DON'T rebase this!
git rebase feature-login  # THIS IS DANGEROUS

Why? When you rebase, you change commit hashes. If someone else has those old commits, their local history no longer matches yours, and you'll need to git pull --rebase or git push --force — which is a team coordination nightmare.

5. Interactive Rebase: Clean Up Your Commits

Here's where rebasing gets powerful. Before you open a pull request, clean up your messy work-in-progress commits:

# Your messy history
git log --oneline
7a3f2b1 Fix typo
2c9e1a0 Add login form validation
1b4d09f WIP - almost done
0e8c37f Update login page
3f2a190 Add login API endpoint

# Interactive rebase — squash and reword
git rebase -i HEAD~5

Git opens an editor with your 5 commits. You can:

# Editor opens with:
pick 3f2a190 Add login API endpoint
pick 0e8c37f Update login page
pick 1b4d09f WIP - almost done
pick 2c9e1a0 Add login form validation
pick 7a3f2b1 Fix typo

# Change to:
pick 3f2a190 Add login API endpoint
squash 0e8c37f Update login page
squash 1b4d09f WIP - almost done
squash 2c9e1a0 Add login form validation
squash 7a3f2b1 Fix typo

Now your 5 messy commits become one clean commit:

# Clean result
git log --oneline
a1b2c3d Add login feature with API, page, and validation

Interactive rebase commands:

  • pick — keep the commit as-is
  • squash — combine with the previous commit
  • reword — keep the commit but change the message
  • edit — stop and amend the commit (add files, fix code)
  • drop — delete the commit entirely
  • fixup — like squash but discard the commit message

6. Real-World Workflow: Feature Branch → Main

Here's the workflow I recommend for solo developers and small teams:

# 1. Create your feature branch from main
git checkout main
git pull origin main
git checkout -b feature/user-auth

# 2. Do your work, commit often
git add . && git commit -m "Add login form HTML"
git add . && git commit -m "Add login validation"
git add . && git commit -m "Connect login API"
git add . && git commit -m "Fix login redirect bug"

# 3. Before pushing: rebase onto latest main
git checkout main
git pull origin main
git checkout feature/user-auth
git rebase main

# 4. Clean up commits with interactive rebase
git rebase -i HEAD~4
# → squash into 1-2 meaningful commits

# 5. Push and create PR
git push -u origin feature/user-auth
# Open pull request on GitHub

The pull request shows a clean, linear diff — reviewers see exactly what changed without merge noise.

7. Handling Rebase Conflicts

Rebase conflicts work the same as merge conflicts, but with one twist: you might resolve the same conflict multiple times (once per commit being replayed).

# Start the rebase
git rebase main
# CONFLICT (content): conflict in app.py
# Auto-merging app.py

# Step 1: Fix the conflict in app.py
# Edit the file, resolve <<<<<<< markers

# Step 2: Mark as resolved
git add app.py

# Step 3: Continue rebase
git rebase --continue

# If you need to stop and fix more conflicts, repeat steps 1-3

# If you want to ABORT the whole rebase:
git rebase --abort

Pro tip: If you have many commits and hit conflicts on every one, consider merging instead (git merge main) and then cleaning up with git rebase -i afterward.

8. Merge Strategies

When you're ready to bring your feature into main, you have three strategies:

# Strategy 1: Regular merge (creates merge commit)
git checkout main
git merge feature/user-auth
# Result: main now has a merge commit with two parents

# Strategy 2: Squash merge (one commit, no history)
git checkout main
git merge --squash feature/user-auth
git commit -m "Add user authentication feature"
# Result: all feature commits become ONE commit on main

# Strategy 3: Rebase then fast-forward (linear history)
git checkout feature/user-auth
git rebase main
git checkout main
git merge feature/user-auth
# Result: main just fast-forwards — no merge commit at all

Which strategy to pick?

  • Squash merge — for features where only the final result matters. GitHub's default for PRs.
  • Fast-forward (rebase + merge) — for a clean linear history on the team repo.
  • Regular merge — when you want to preserve the exact branching timeline.

9. Practical Examples

Scenario A: Hotfix on production

# Emergency fix — merge directly (preserves when it happened)
git checkout main
git checkout -b hotfix/critical-bug
# ... fix the bug ...
git commit -m "fix: critical login bypass"
git checkout main
git merge hotfix/critical-bug  # merge, not rebase
git push origin main

Scenario B: Feature branch with 20 WIP commits

# Clean up before PR
git checkout feature/dashboard
git rebase -i HEAD~20
# → squash into 3-4 meaningful commits
# → reword messages to be clear
git rebase main  # get latest main
git push --force-with-lease  # update the PR

Note: Use --force-with-lease instead of --force. It's safer — it refuses to push if someone else pushed new commits since your last fetch.

Scenario C: Staying in sync with main daily

# Your daily routine
git fetch origin
git checkout feature/search
git rebase origin/main
# Resolve conflicts if any
# Continue working...

10. Comparison Table

Aspect git merge git rebase
History Preserved (non-linear) Rewritten (linear)
New commits Creates merge commit No extra commits
Safety Always safe Only on private branches
Undo git revert <commit> git rebase --abort
Best for Shared branches, main Local feature branches
Force push needed? Never Yes, after rebasing

Summary

Use git merge for shared branches and when you need to preserve exact history. Use git rebase for cleaning up your local feature branches before sharing. Interactive rebase (git rebase -i) is a superpower for turning messy WIP commits into clean, reviewable changes.

The rule of thumb:

  • 📌 Private branch → rebase freely to keep it clean
  • 📌 Shared branch → always merge, never rebase
  • 📌 Before PR → rebase onto main + interactive squash
  • 📌 Hotfix → merge directly for clear timeline
