SSH Config File: Manage Multiple Servers Like a Pro — Complete Guide

July 15, 2026 10 min read

If you manage more than two servers, you've probably memorized long SSH commands with custom ports, key files, and jump hosts. Something like:

ssh -i ~/.ssh/prod_key -p 2222 deploy@192.168.1.100

This works — until you need to do it five times a day across ten different machines. The SSH config file (~/.ssh/config) lets you define all these connections once, then access them with simple aliases like ssh prod.

This guide covers everything from basic host aliases to advanced features like multiplexing, proxy jumping, and local port forwarding.

Where Is the SSH Config File?

The SSH config file lives at ~/.ssh/config in your home directory. There's no config file by default — you create it:

# Create the .ssh directory (usually already exists)
mkdir -p ~/.ssh

# Create/edit the config file
nano ~/.ssh/config

# ⚠️ IMPORTANT: Set correct permissions
chmod 600 ~/.ssh/config

The chmod 600 step is critical. SSH will refuse to use a config file with permissions that are too open (no one else should be able to read your SSH settings). You'll get the error: Permissions 0644 for '~/.ssh/config' are too open if you skip this.

Basic Host Entries

The simplest config entry maps a friendly name to a server:

# ~/.ssh/config
Host prod
    HostName 192.168.1.100
    User deploy
    Port 2222
    IdentityFile ~/.ssh/prod_key

Now instead of typing the full command, you just type:

ssh prod

This connects as user deploy to 192.168.1.100 on port 2222 using the key at ~/.ssh/prod_key. The entire verbose command is reduced to two words.

Managing Multiple Servers

Define every server you use. Here's a realistic config for a developer managing a small infrastructure:

# ~/.ssh/config

# Development server
Host dev
    HostName dev.example.com
    User ubuntu
    IdentityFile ~/.ssh/id_ed25519

# Staging environment
Host staging
    HostName staging.example.com
    User deploy
    IdentityFile ~/.ssh/staging_key
    Port 22

# Production — restricted access
Host prod
    HostName 10.0.0.50
    User deploy
    IdentityFile ~/.ssh/prod_key
    Port 2222
    ServerAliveInterval 60
    ServerAliveCountMax 3

# Database server (SSH-tunneled)
Host db-prod
    HostName 10.0.0.100
    User postgres
    IdentityFile ~/.ssh/prod_key
    Port 2222

Each Host block defines everything needed to connect. The ServerAliveInterval and ServerAliveCountMax settings send a keep-alive ping every 60 seconds and disconnect after 3 missed responses — preventing stale connections from hanging.

Wildcards and Patterns

Use wildcards (*) and question marks (?) to match multiple hosts:

# All web servers share the same settings
Host web-*
    User deploy
    IdentityFile ~/.ssh/web_key
    ServerAliveInterval 60

# Each web server
Host web-1
    HostName 10.0.1.10

Host web-2
    HostName 10.0.1.11

Host web-3
    HostName 10.0.1.12

Now ssh web-1 connects as deploy using web_key with keep-alive enabled — all inherited from the web-* pattern. If you later add web-4, it automatically inherits the same settings.

You can also use the Host * pattern to set global defaults that apply to every connection:

# Global defaults — applied to every SSH connection
Host *
    ServerAliveInterval 60
    ServerAliveCountMax 3
    AddKeysToAgent yes
    IdentitiesOnly yes
    ForwardAgent no
    Compression yes

Proxy Jump (Bastion Host)

Many production setups require you to connect to an internal server through a bastion host (also called a jump box). Instead of manually chaining SSH sessions, use ProxyJump:

# Bastion / jump host
Host bastion
    HostName jump.example.com
    User ubuntu
    IdentityFile ~/.ssh/bastion_key

# Internal servers accessed through bastion
Host internal-*
    ProxyJump bastion
    User deploy
    IdentityFile ~/.ssh/internal_key

Now ssh internal-db automatically connects to the bastion first, then jumps through to the internal database server — all in one command. The ProxyJump directive handles the entire chain.

You can also chain multiple jumps:

Host deep-internal
    HostName 10.10.0.50
    ProxyJump bastion, internal-jump
    User deploy

This connects: your laptop → bastion → internal-jump → deep-internal. Three hops, one command.

Local Port Forwarding

SSH can tunnel network traffic. A common use case is accessing a database or admin panel that only listens on localhost on a remote server:

# PostgreSQL on prod, accessible locally
Host prod-db-tunnel
    HostName 10.0.0.50
    User deploy
    IdentityFile ~/.ssh/prod_key
    LocalForward 5432 localhost:5432
    NLazyConnect yes
# Start the tunnel in the background
ssh -fN prod-db-tunnel

# Now connect to PostgreSQL locally
psql -h localhost -p 5432 -U myuser mydb

The LocalForward 5432 localhost:5432 directive forwards your local port 5432 to the remote server's localhost:5432. The -f flag puts SSH in the background, and -N tells it not to execute any remote commands (tunnel only).

Other common forwarding scenarios:

# Django admin panel on prod
Host prod-admin
    HostName prod.example.com
    User deploy
    LocalForward 8080 localhost:8000

# Redis on staging
Host staging-redis
    HostName staging.example.com
    User deploy
    LocalForward 6379 localhost:6379

Remote Port Forwarding

Remote forwarding does the opposite — it exposes your local service on the remote server. Useful for exposing a local development server to teammates:

# Expose local dev server on remote machine
Host dev-share
    HostName dev.example.com
    User ubuntu
    RemoteForward 8080 localhost:3000
# Start the tunnel
ssh -fN dev-share

# Your local port 3000 is now accessible at dev.example.com:8080

Connection Multiplexing

Every SSH connection performs a handshake (key exchange, authentication) that takes 1-3 seconds. If you frequently open new connections to the same server — say, running ssh prod, then scp file.txt prod:~/, then ssh prod again — each one repeats the full handshake.

Connection multiplexing reuses a single TCP connection for multiple sessions:

# ~/.ssh/config
Host *
    # Master socket file location
    ControlMaster auto
    ControlPath ~/.ssh/control-%r@%h-%p
    ControlPersist 10m

How it works:

  • ControlMaster auto: SSH automatically creates a master connection when the first session starts
  • ControlPath: Defines where the Unix socket file lives. The variables expand to the username, hostname, and port — ensuring each server gets a unique socket
  • ControlPersist 10m: The master connection stays alive for 10 minutes after the last session closes, ready for the next connection

After the first connection, subsequent SSH sessions to the same server are nearly instant — they piggyback on the existing master connection. SCP, SFTP, and SSH all benefit.

To check active multiplexed connections:

# List active SSH control connections
ssh -O check prod

# Stop the master connection
ssh -O exit prod

# List all control socket files
ls -la ~/.ssh/control-*

SCP and SFTP with Config

Both scp and sftp read ~/.ssh/config, so your host aliases work for file transfer too:

# Copy a file to prod
scp app.tar.gz prod:/opt/deploy/

# Download logs from staging
scp staging:/var/log/app.log ./app.log

# Interactive file browser on prod
sftp prod

# Copy recursively
scp -r ./dist prod:/var/www/html/

Since you've already defined the user, port, and key in your config, these commands work with zero extra arguments.

Security Settings

Add these settings to your config to harden your SSH connections:

Host *
    # Only use protocol 2 (protocol 1 is insecure)
    Protocol 2

    # Don't add keys to the agent unless explicitly allowed
    AddKeysToAgent no

    # Don't forward your SSH agent (prevent credential theft)
    ForwardAgent no

    # Only use the specified key, not all loaded keys
    IdentitiesOnly yes

    # Hash known hosts to prevent hostname leaks
    HashKnownHosts yes

    # Strict host key checking
    StrictHostKeyChecking ask

    # Don't save known hosts interactively
    UpdateHostKeys no

    # Set a per-connection timeout
    ConnectTimeout 10

    # Keep-alive to detect dead connections
    ServerAliveInterval 60
    ServerAliveCountMax 3

Exception for ForwardAgent: You might need ForwardAgent yes for proxy jumps or when you need to access GitHub from the remote server using your local keys. Only enable it when necessary and on trusted servers:

Host bastion
    HostName jump.example.com
    User ubuntu
    ForwardAgent yes  # Only on the jump host

Complete Example Config

Here's a comprehensive config you can use as a starting point:

# ~/.ssh/config

# ── Global Defaults ──────────────────────────────────────
Host *
    ServerAliveInterval 60
    ServerAliveCountMax 3
    AddKeysToAgent yes
    IdentitiesOnly yes
    ForwardAgent no
    Compression yes
    ConnectTimeout 10
    HashKnownHosts yes
    StrictHostKeyChecking ask

    # Connection multiplexing
    ControlMaster auto
    ControlPath ~/.ssh/control-%r@%h-%p
    ControlPersist 10m

# ── Personal Keys ────────────────────────────────────────
Host *
    IdentityFile ~/.ssh/id_ed25519
    IdentityFile ~/.ssh/id_ed25519_work

# ── Development ──────────────────────────────────────────
Host dev
    HostName dev.example.com
    User ubuntu
    LocalForward 3000 localhost:3000
    LocalForward 5432 localhost:5432

# ── Staging ──────────────────────────────────────────────
Host staging
    HostName staging.example.com
    User deploy
    IdentityFile ~/.ssh/staging_key

# ── Production ───────────────────────────────────────────
Host prod
    HostName 10.0.0.50
    User deploy
    IdentityFile ~/.ssh/prod_key
    Port 2222

Host prod-db
    HostName 10.0.0.100
    User postgres
    IdentityFile ~/.ssh/prod_key
    Port 2222
    LocalForward 5432 localhost:5432

# ── Bastion / Jump Host ─────────────────────────────────
Host bastion
    HostName jump.example.com
    User ubuntu
    ForwardAgent yes

# Internal servers accessed through bastion
Host internal-*
    ProxyJump bastion
    User deploy
    IdentityFile ~/.ssh/internal_key

Summary

The SSH config file transforms a collection of long, hard-to-remember commands into simple, consistent aliases. Key features covered:

  • Host entries — Define aliases with hostname, user, port, and key
  • Wildcards — Share settings across groups of servers with Host web-*
  • ProxyJump — Chain connections through bastion hosts transparently
  • LocalForward — Access remote services on your local machine
  • RemoteForward — Expose local services to remote machines
  • Multiplexing — Reuse connections for instant subsequent sessions
  • Security settings — Harden connections with agent forwarding controls, key policies, and timeouts

Once your config is set up, commands like ssh prod, scp logs.txt prod:~/, and sftp dev become second nature. Spend an hour building your config, save minutes every day.
