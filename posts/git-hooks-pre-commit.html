Git Hooks and Pre-commit: Automate Code Quality Checks

July 11, 2026 · 9 min read

Every developer has committed code with trailing whitespace, missing imports, or unformatted files. Then the CI pipeline fails, the PR gets rejected, and you start the awkward blame dance. Git hooks solve this problem by automatically running checks before you commit.

The pre-commit framework makes it dead simple to set up automated checks that run across any language, shared with your team via version control. In this guide, you'll learn how Git hooks work, set up pre-commit from scratch, and configure a battery of checks for any project.

What Are Git Hooks?

Git hooks are scripts that Git executes automatically at specific points in its lifecycle. They live in the .git/hooks/ directory and are triggered by events like committing, pushing, or merging.

Common hooks include:

  • pre-commit — Runs before git commit. Most useful for linting and formatting.
  • prepare-commit-msg — Modifies the default commit message.
  • commit-msg — Validates the commit message format.
  • pre-push — Runs before git push. Good for running tests.
  • post-merge — Runs after a merge. Useful for running dependency installs.

The Problem with Raw Git Hooks

You can write a raw hook by creating a script in .git/hooks/pre-commit:

#!/bin/sh
# .git/hooks/pre-commit

echo "Running linting..."
flake8 --select=E9,F63,F7,F82 .
black --check .
echo "All checks passed!"
exit 0

Then make it executable: chmod +x .git/hooks/pre-commit

This works fine for a single developer. But it breaks down in teams because:

  1. .git/ isn't tracked — hooks aren't shared with teammates.
  2. Different developers have different tools installed.
  3. Hooks drift apart — someone updates the script but forgets to share it.

The Solution: pre-commit Framework

The pre-commit framework solves all these problems. It uses a single .pre-commit-config.yaml file that lives in your repo. Everyone who clones the repo gets the same hooks, the same versions, running in isolated virtual environments.

Install pre-commit

# Option 1: pip (Python required)
pip install pre-commit

# Option 2: Homebrew (macOS/Linux)
brew install pre-commit

# Option 3: pipx (recommended, isolated)
pipx install pre-commit

Your First pre-commit Config

Create a .pre-commit-config.yaml file in your project root:

# .pre-commit-config.yaml
repos:
  # Fix common issues automatically
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v5.0.0
    hooks:
      - id: trailing-whitespace
      - id: end-of-file-fixer
      - id: check-yaml
      - id: check-json
      - id: check-merge-conflict
      - id: detect-private-key
      - id: check-added-large-files
        args: ['--maxkb=1024']

  # Auto-format Python code
  - repo: https://github.com/psf/black
    rev: 24.8.0
    hooks:
      - id: black
        args: ['--line-length=88']

  # Sort Python imports
  - repo: https://github.com/pycqa/isort
    rev: 5.13.2
    hooks:
      - id: isort
        args: ['--profile', 'black', '--line-length=88']

  # Lint Python for errors
  - repo: https://github.com/pycqa/flake8
    rev: 7.1.1
    hooks:
      - id: flake8
        args: ['--max-line-length=88', '--extend-ignore=E203']

Then install the hooks:

# Install the hook script into .git/hooks/
pre-commit install

# Run against all files (first time only)
pre-commit run --all-files

# Future commits will run automatically!
git add .
git commit -m "add pre-commit config"

Multi-Language Configuration

pre-commit works with any language. Here's a config for a full-stack project:

# .pre-commit-config.yaml
repos:
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v5.0.0
    hooks:
      - id: trailing-whitespace
      - id: end-of-file-fixer
      - id: check-yaml
      - id: check-json
      - id: check-merge-conflict
      - id: detect-private-key

  # Python tools
  - repo: https://github.com/psf/black
    rev: 24.8.0
    hooks:
      - id: black

  - repo: https://github.com/pycqa/flake8
    rev: 7.1.1
    hooks:
      - id: flake8

  # JavaScript / TypeScript tools
  - repo: https://github.com/pre-commit/mirrors-prettier
    rev: v4.0.0-alpha.8
    hooks:
      - id: prettier
        types_or: [javascript, jsx, ts, tsx, json, css, markdown, yaml]
        additional_dependencies:
          - prettier@3.3.3

  - repo: https://github.com/pre-commit/mirrors-eslint
    rev: v9.12.0
    hooks:
      - id: eslint
        types: [file]
        files: \.[jt]sx?$
        additional_dependencies:
          - eslint@9.11.1
          - '@typescript-eslint/parser'
          - '@typescript-eslint/eslint-plugin'

  # Markdown
  - repo: https://github.com/igorshubovych/markdownlint-cli
    rev: v0.41.0
    hooks:
      - id: markdownlint
        args: ['--disable', 'MD013', '--']

  # Shell scripts
  - repo: https://github.com/shellcheck-py/shellcheck-py
    rev: v0.10.0.1
    hooks:
      - id: shellcheck

Custom Hooks

pre-commit can also run your own scripts. Create a local hook for project-specific checks:

# .pre-commit-config.yaml
repos:
  # ... other repos ...

  - repo: local
    hooks:
      # Run project tests on commit
      - id: run-tests
        name: Run unit tests
        entry: pytest tests/unit/ -v
        language: system
        pass_filenames: false
        stages: [pre-push]  # Only runs on push, not commit

      # Custom Python check
      - id: check-migrations
        name: Check for uncommitted migrations
        entry: python check_migrations.py
        language: system
        pass_filenames: false
        always_run: true

In this example, check_migrations.py might look like:

#!/usr/bin/env python3
"""Check that there are no uncommitted database migrations."""
import subprocess
import sys

result = subprocess.run(
    ["python", "manage.py", "makemigrations", "--check", "--dry-run"],
    capture_output=True,
    text=True
)

if result.returncode != 0:
    print("❌ Uncommitted migrations detected!")
    print(result.stdout)
    sys.exit(1)

print("✅ No uncommitted migrations.")
sys.exit(0)

Hook Stages

Hooks can run at different stages of the Git workflow:

# .pre-commit-config.yaml
repos:
  - repo: local
    hooks:
      - id: fast-checks
        name: Fast auto-fix
        entry: black
        language: system
        stages: [commit]  # Default — runs on git commit

      - id: slow-tests
        name: Integration tests
        entry: pytest tests/integration/
        language: system
        stages: [pre-push]  # Runs on git push (slower)

      - id: post-commit-cleanup
        name: Cleanup temp files
        entry: find . -name "*.pyc" -delete
        language: system
        stages: [post-checkout]  # After git checkout

Available stages: commit, merge-commit, prepare-commit-msg, commit-msg, post-commit, manual, pre-push, pre-rebase, post-checkout.

Common Workflow Tips

Run Against All Files

# First time setup — check every file in the repo
pre-commit run --all-files

# After adding a new hook — run it against everything
pre-commit run black --all-files

Skip Hooks (When You Really Need To)

# Skip ALL hooks for one commit
git commit --no-verify -m "emergency fix"

# Skip a specific hook
pre-commit run --hook-stage commit --hook-id flake8

# Temporarily disable in config by commenting out the hook
Warning: Use --no-verify sparingly. It defeats the purpose of hooks and can introduce problems that CI would have caught.

Autoupdate All Hook Versions

# Update all repos to their latest release
pre-commit autoupdate

# This edits .pre-commit-config.yaml with new versions
# Always review the diff before committing!

Integrating with CI/CD

Even with pre-commit locally, you should run it in CI as a safety net:

# .github/workflows/pre-commit.yml
name: Pre-commit
on: [pull_request]

jobs:
  pre-commit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
      - uses: pre-commit/action@v3.0.1

This ensures that anyone who clones the repo and forgets to run pre-commit install still has their code checked by CI.

pre-commit vs CI: When to Use Each

Check Where to Run Why
Formatting (black, prettier) pre-commit Auto-fixes are fast and improve developer experience
Linting (flake8, eslint) Both Catch early locally, enforce in CI
Type checking (mypy, tsc) Both Fast feedback locally, gate in CI
Unit tests CI Can be slow; developers should run manually
Integration tests CI Require external services / slow
Secret scanning Both Never let secrets reach the repo

Best Practices

  1. Auto-fix over manual warnings — Use formatters (black, prettier) that automatically fix code. Fewer warnings to argue about in code reviews.
  2. Keep hooks fast — Pre-commit hooks should finish in seconds. Slow checks belong in CI.
  3. Pin hook versions — Always use a specific rev in your config. Never use master or main.
  4. Run pre-commit in CI — Catch developers who skip local hooks.
  5. Use pass_filenames: false for global checks — Don't pass file lists to commands that need the whole project.
  6. Add hooks gradually — Start with basic checks, then add language-specific tools.

Popular Hook Repos

The pre-commit ecosystem has thousands of repos. Here are the most useful:

  • pre-commit-hooks — Core hooks: whitespace, YAML/JSON validation, conflict detection
  • black — Python code formatter
  • isort — Python import sorter
  • flake8 — Python linter
  • prettier — Universal code formatter
  • eslint — JavaScript/TypeScript linter
  • gitleaks — Secret detection
  • shellcheck — Shell script static analysis

Next Steps

Add .pre-commit-config.yaml to your next project. Start with the basic pre-commit-hooks repo and black, then gradually add more checks as you find pain points. Your future self — and your teammates — will thank you when every commit is automatically clean.
