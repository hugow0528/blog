Docker Compose for Multi-Container Development: Local Environments Made Easy — Complete Beginner's Guide

July 14, 2026

Running a single container with docker run is fine for a quick experiment. But real applications need databases, caches, message queues, and more. Typing long docker run commands for each service gets unwieldy fast — and recreating your local environment for a new team member becomes a nightmare of copy-pasted commands.

Docker Compose solves all of this. You describe your entire stack in a single docker-compose.yml file, then start everything with one command: docker compose up. Your web app, database, Redis cache, and monitoring tools spin up together, properly networked and configured.

In this guide, you'll learn Docker Compose from scratch — the YAML syntax, service dependencies, networking, volumes, environment variables, health checks, and building a complete multi-service development environment. Every example includes working configuration you can adapt for your own projects.

What Is Docker Compose?

Docker Compose is a tool for defining and running multi-container Docker applications. Instead of manually running each container, you write a docker-compose.yml file that describes:

  • Services — each container in your application (web, database, cache, etc.)
  • Networks — how containers communicate with each other
  • Volumes — persistent data storage that survives container restarts

It's part of Docker Desktop by default, so you probably already have it. Check with:

docker compose version
# Docker Compose version v2.29.1

Note: the old syntax docker-compose (with hyphen) still works but Docker recommends docker compose (V2 plugin) going forward. We'll use the V2 syntax throughout.

Your First docker-compose.yml

Let's start with the simplest possible example: a Python web app paired with a PostgreSQL database. Create a file called docker-compose.yml in a new directory:

# docker-compose.yml
services:
  web:
    build: .
    ports:
      - "8000:8000"
    environment:
      - DATABASE_URL=postgresql://appuser:secret@db:5432/appdb
    depends_on:
      - db

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: appuser
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: appdb
    volumes:
      - pgdata:/var/lib/postgresql/data

volumes:
  pgdata:

That's your entire application stack. Break it down:

  • services.web — builds a container from the current directory (build: .) and maps port 8000
  • services.db — runs a PostgreSQL 16 container with environment variables for setup
  • depends_on — ensures the database starts before the web service
  • volumes — persists database data on disk so it survives container restarts

Start everything:

# Build and start in the foreground (you see logs)
docker compose up

# Start in the background (detached mode)
docker compose up -d

# Stop everything
docker compose down

# Stop and remove volumes (destroy all data!)
docker compose down -v

Understanding the Compose File Structure

A docker-compose.yml file has three top-level sections:

services:       # Your application containers
  web:
    ...
  db:
    ...

networks:       # Optional — custom network configuration
  ...

volumes:         # Optional — named volumes for persistent data
  ...

Essential Service Options

Each service accepts many configuration options. Here are the most important ones:

services:
  myservice:
    # How to get the container image
    image: nginx:latest              # Use an existing image
    # OR
    build:                           # Build from a Dockerfile
      context: .                     # Build context directory
      dockerfile: Dockerfile.dev     # Optional: non-default Dockerfile

    # Container identification
    container_name: my-web-app       # Fixed name (default: random)
    hostname: web                    # Container hostname

    # Port mapping: host_port:container_port
    ports:
      - "8000:8000"                 # Localhost only
      - "0.0.0.0:8000:8000"         # Bind to all interfaces
      - "8080:80/tcp"               # Specify protocol

    # Environment variables (multiple syntaxes)
    environment:
      - KEY=value                   # List syntax
      DEBUG: "true"                  # Dict syntax
    env_file:
      - .env                        # Load from file

    # Volume mounts: host_path:container_path[:ro]
    volumes:
      - ./src:/app/src               # Bind mount (live code changes)
      - data:/var/lib/data           # Named volume
      - ./config.yml:/app/config.yml:ro  # Read-only mount

    # Dependencies
    depends_on:
      - db                           # Simple: wait for container to start
      db:                            # Extended: wait for condition
        condition: service_healthy   # Wait until health check passes

    # Resource limits
    deploy:
      resources:
        limits:
          cpus: "1.0"
          memory: 512M
        reservations:
          cpus: "0.25"
          memory: 128M

    # Restart behavior
    restart: unless-stopped         # Options: no, always, on-failure, unless-stopped

    # Health check
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8000/health"]
      interval: 10s
      timeout: 5s
      retries: 3
      start_period: 30s

Networking Between Containers

By default, Docker Compose creates a network for your project. All services on this network can reach each other by service name. In our first example, the web service connects to the database using the hostname db — that's Docker's built-in DNS resolving the service name to its container IP.

# In your Python app, connect to the database by service name:
import os

DATABASE_URL = os.environ["DATABASE_URL"]
# "postgresql://appuser:secret@db:5432/appdb"
#                                    ^^
#                             This resolves via Docker DNS

You can also define custom networks for more complex setups:

services:
  web:
    image: nginx
    networks:
      - frontend
      - backend

  api:
    image: my-api:latest
    networks:
      - backend

  db:
    image: postgres:16
    networks:
      - backend

networks:
  frontend:
  backend:

In this setup, the web service can reach both the API and database, but the API and database can only reach each other — the frontend network is isolated from the backend. This is useful for separating public-facing services from internal infrastructure.

Volume Strategies for Development

Understanding volumes is critical for a good development experience. Here are the three main approaches:

1. Bind Mounts for Live Code Editing

Bind mounts sync your local filesystem into the container. Edit a file on your machine, and it's immediately available inside the container. Essential for development:

services:
  web:
    build: .
    volumes:
      - ./src:/app/src    # Your code is live-mounted
    # Edit files in ./src → changes appear in /app/src instantly

2. Named Volumes for Database Persistence

Named volumes are managed by Docker and stored in its managed directory (/var/lib/docker/volumes/ on Linux). Use these for databases and anything that needs to survive docker compose down:

services:
  db:
    image: postgres:16
    volumes:
      - pgdata:/var/lib/postgresql/data

volumes:
  pgdata:  # Docker manages this volume lifecycle

3. Shared Volumes for Data Exchange

Multiple containers can mount the same named volume, allowing data sharing:

services:
  uploader:
    image: python:3.12
    volumes:
      - uploads:/data/uploads

  processor:
    image: python:3.12
    volumes:
      - uploads:/data/uploads   # Same volume, same data

volumes:
  uploads:

Complete Development Stack Example

Let's build a realistic development environment with a Python FastAPI backend, PostgreSQL, Redis, and an admin dashboard:

# docker-compose.yml
services:
  # === API Service ===
  api:
    build:
      context: .
      dockerfile: Dockerfile.dev
    ports:
      - "8000:8000"
    volumes:
      - ./app:/app          # Live mount your code
    environment:
      - DATABASE_URL=postgresql://admin:secret@db:5432/devdb
      - REDIS_URL=redis://cache:6379
    depends_on:
      db:
        condition: service_healthy
      cache:
        condition: service_healthy
    restart: unless-stopped

  # === Database ===
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: admin
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: devdb
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U admin"]
      interval: 5s
      timeout: 3s
      retries: 5
    ports:
      - "5432:5432"

  # === Redis Cache ===
  cache:
    image: redis:7-alpine
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 5
    ports:
      - "6379:6379"

  # === Admin Dashboard ===
  adminer:
    image: adminer:latest
    ports:
      - "8081:8080"
    depends_on:
      - db

volumes:
  pgdata:

This single file gives you:

  • A live-reloading API at http://localhost:8000
  • PostgreSQL with persistent data at localhost:5432
  • Redis cache at localhost:6379
  • An admin dashboard at http://localhost:8081 to manage the database
  • Automatic health checks so the API waits for the database and cache to be ready

New team member? Just git pull && docker compose up -d. Everything works identically.

Environment File Management

Instead of hardcoding environment variables, use .env files. Docker Compose automatically loads .env from the project root and substitutes values using ${VARIABLE} syntax:

# .env
DATABASE_USER=admin
DATABASE_PASSWORD=supers3cret
DATABASE_NAME=devdb
DEBUG=true
# docker-compose.yml
services:
  api:
    environment:
      - DATABASE_URL=postgresql://${DATABASE_USER}:${DATABASE_PASSWORD}@db:5432/${DATABASE_NAME}
      - DEBUG=${DEBUG}
    env_file:
      - .env

For different environments, use separate files:

# Start with development config
docker compose --env-file .env.dev up

# Start with staging config
docker compose --env-file .env.staging up

Important: Always add .env files to .gitignore. They often contain secrets:

# .gitignore
.env
.env.local
.env.*.local
.env.dev
.env.staging

Multi-Compose File: Overriding Configuration

You can split your compose configuration across multiple files and override settings. This is great for maintaining a base configuration that gets extended:

# docker-compose.yml (base config)
services:
  api:
    build: .
    ports:
      - "8000:8000"
    environment:
      - DEBUG=false

  db:
    image: postgres:16
    volumes:
      - pgdata:/var/lib/postgresql/data

volumes:
  pgdata:

---

# docker-compose.override.yml (dev overrides — automatically loaded)
services:
  api:
    volumes:
      - ./src:/app/src        # Add live code mounting
    environment:
      - DEBUG=true             # Override to enable debug
    ports:
      - "8000:8000"
      - "5678:5678"           # Add debugger port

  db:
    ports:
      - "5432:5432"           # Expose DB port for local tools

Docker Compose automatically loads docker-compose.override.yml when present. You can also merge files explicitly:

# Merge two specific files
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d

# Merge three files (later files override earlier ones)
docker compose -f base.yml -f network.yml -f volumes.yml up

Useful Docker Compose Commands

Master these commands and you'll handle 95% of your workflow:

# Start services
docker compose up -d                # Detached (background)
docker compose up                   # Foreground (see all logs)
docker compose up -d --build        # Rebuild before starting
docker compose up -d api            # Start only the 'api' service

# Stop services
docker compose stop                 # Stop without removing containers
docker compose down                 # Stop and remove containers
docker compose down -v              # Stop and remove volumes (data loss!)

# View logs
docker compose logs                 # All services
docker compose logs -f              # Follow (like tail -f)
docker compose logs -f api          # Follow one service
docker compose logs --tail=100 api  # Last 100 lines

# Execute commands in running containers
docker compose exec api python manage.py migrate
docker compose exec db psql -U admin -d devdb
docker compose exec api bash        # Interactive shell

# Manage builds
docker compose build                # Build all services
docker compose build api            # Build one service
docker compose build --no-cache     # Force full rebuild

# Resource inspection
docker compose ps                   # Running containers
docker compose top                  # Container processes
docker compose stats                # CPU, memory, network usage

# Scale services
docker compose up -d --scale api=3  # Run 3 API instances

Profiling and Debugging Your Compose Setup

When things go wrong (and they will), here's how to diagnose:

# Check if containers are healthy
docker compose ps

# Inspect network connectivity
docker compose exec api ping db
docker compose exec api curl http://db:5432

# Check environment variables inside container
docker compose exec api env

# Validate your compose file syntax
docker compose config

# Check volume mounts
docker compose exec api ls -la /app/src

Production Considerations

Docker Compose excels at local development, but be cautious about using it in production. Here are key differences:

  • No auto-scaling — use Kubernetes or a platform like ECS
  • No service discovery — use a load balancer or proxy
  • Limited logging — integrate with a logging platform
  • No rolling updates — use CI/CD pipelines with zero-downtime strategies

That said, Docker Compose can run in production for simple, single-server deployments. Just ensure you're using health checks, proper restart policies, resource limits, and external secrets management.
