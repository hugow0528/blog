Kubernetes Basics: Containers at Scale

2026-06-27 11 min read New

You've mastered Docker and Docker Compose. You've even explored Docker Swarm for orchestration. Now it's time to meet Kubernetes (or k8s) — the industry-standard container orchestrator that powers millions of applications worldwide.

Kubernetes might look intimidating at first — there's a lot of YAML and terminology. But the core concepts are simple once you see them in action. This guide takes you from zero to deploying a real application, one concept at a time.

What Problem Does Kubernetes Solve?

Docker Compose is great for development and small deployments. But what happens when you need to:

  • 🔄 Auto-restart a crashed container?
  • 📈 Scale from 1 to 10 instances during a traffic spike?
  • 🔄 Update your app without any downtime?
  • 🔗 Connect services across multiple servers?

That's where Kubernetes steps in. It's a platform that manages containers at scale — handling deployment, scaling, networking, and self-healing automatically.

Kubernetes Architecture in Plain English

Every Kubernetes cluster has two parts:

Control Plane (The Brain)

  • API Server — The front door. Every command goes through here
  • etcd — The database. Stores the entire cluster state
  • Scheduler — Decides which node runs each container
  • Controller Manager — Watches for problems and fixes them

Worker Nodes (The Muscle)

  • Kubelet — The agent on each node, talks to the control plane
  • Container Runtime — Actually runs the containers (containerd, Docker)
  • Kube-proxy — Handles networking and routing traffic

Core Concepts (The Big Five)

1. Pod — The Smallest Unit

A Pod is the smallest deployable unit in Kubernetes. Think of it as a wrapper around one (or more) containers. You almost never create pods directly — higher-level resources manage them for you.

# See your pods
kubectl get pods

# Describe a pod in detail
kubectl describe pod my-pod

# Get logs from a pod
kubectl logs my-pod

2. Deployment — Manage Your Pods

A Deployment defines how many copies of your app should run and how to update them. It's the most commonly used resource.

# deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 3  # Run 3 copies
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
      - name: my-app
        image: my-app:1.0
        ports:
        - containerPort: 8080

Deploy it with kubectl apply -f deployment.yaml. Kubernetes will create 3 pods running your app. If one crashes, it automatically starts a replacement.

3. Service — Expose Your Pods

Pods get random IP addresses and can come and go. A Service gives you a stable network endpoint to reach your pods.

# service.yaml
apiVersion: v1
kind: Service
metadata:
  name: my-app-service
spec:
  selector:
    app: my-app  # Routes to pods with this label
  ports:
  - port: 80       # Service port
    targetPort: 8080  # Pod port
  type: ClusterIP  # Internal only

Three service types:

  • ClusterIP (default) — internal network only
  • NodePort — opens a port on every node
  • LoadBalancer — provisions a cloud load balancer

4. ConfigMap & Secret — Configuration

Never hardcode configuration in your container image. Use ConfigMaps for non-sensitive data and Secrets for sensitive data:

# configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  DATABASE_HOST: "postgres.default.svc.cluster.local"
  DATABASE_PORT: "5432"
  LOG_LEVEL: "info"

---
# secret.yaml
apiVersion: v1
kind: Secret
metadata:
  name: app-secrets
type: Opaque
data:
  # Base64 encoded! Use: echo -n "password" | base64
  DATABASE_PASSWORD: cGFzc3dvcmQxMjM=
  API_KEY: c2VjcmV0LWtleQ==

Reference them in your deployment:

spec:
  template:
    spec:
      containers:
      - name: my-app
        image: my-app:1.0
        envFrom:
        - configMapRef:
            name: app-config
        - secretRef:
            name: app-secrets

5. Namespace — Organize Resources

Namespaces let you split a cluster into virtual clusters — perfect for separating dev, staging, and production:

# Create namespaces
kubectl create namespace development
kubectl create namespace staging
kubectl create namespace production

# Deploy to a specific namespace
kubectl apply -f deployment.yaml -n development

# List resources in a namespace
kubectl get all -n development

Hands-On: Deploy a Full Application

Let's deploy a complete web application with a frontend, backend, and database. We'll use kubectl and Minikube (a local Kubernetes cluster for development).

Step 1: Set Up Minikube

# Install Minikube (https://minikube.sigs.k8s.io/docs/start/)
minikube start --driver=docker

# Verify it's running
kubectl cluster-info
kubectl get nodes

Step 2: Create the Database (StatefulSet)

# postgres.yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
spec:
  serviceName: postgres
  replicas: 1
  selector:
    matchLabels:
      app: postgres
  template:
    metadata:
      labels:
        app: postgres
    spec:
      containers:
      - name: postgres
        image: postgres:16
        ports:
        - containerPort: 5432
        env:
        - name: POSTGRES_DB
          value: "appdb"
        - name: POSTGRES_USER
          value: "admin"
        - name: POSTGRES_PASSWORD
          valueFrom:
            secretKeyRef:
              name: db-secret
              key: password
        volumeMounts:
        - name: postgres-data
          mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:
  - metadata:
      name: postgres-data
    spec:
      accessModes: ["ReadWriteOnce"]
      resources:
        requests:
          storage: 1Gi
---
apiVersion: v1
kind: Service
metadata:
  name: postgres
spec:
  selector:
    app: postgres
  ports:
  - port: 5432
  clusterIP: None  # Headless service for StatefulSet

Why StatefulSet instead of Deployment? Databases need persistent storage with stable names. A StatefulSet guarantees that pod-0 always gets the same disk, even after restarts.

Step 3: Create the Backend API

# backend.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend
spec:
  replicas: 2
  selector:
    matchLabels:
      app: backend
  template:
    metadata:
      labels:
        app: backend
    spec:
      containers:
      - name: backend
        image: python:3.12-slim
        command: ["python", "app.py"]
        ports:
        - containerPort: 8000
        env:
        - name: DATABASE_HOST
          value: "postgres"  # Kubernetes DNS!
        - name: DATABASE_PORT
          value: "5432"
        - name: DATABASE_NAME
          value: "appdb"
        readinessProbe:
          httpGet:
            path: /health
            port: 8000
          initialDelaySeconds: 5
          periodSeconds: 10
        livenessProbe:
          httpGet:
            path: /health
            port: 8000
          initialDelaySeconds: 10
          periodSeconds: 30
---
apiVersion: v1
kind: Service
metadata:
  name: backend
spec:
  selector:
    app: backend
  ports:
  - port: 8000
    targetPort: 8000
  type: ClusterIP

Notice the probes: readinessProbe tells Kubernetes when the app is ready to receive traffic. livenessProbe restarts the app if it stops responding. Both are essential for reliable deployments.

Step 4: Create the Frontend

# frontend.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend
spec:
  replicas: 2
  selector:
    matchLabels:
      app: frontend
  template:
    metadata:
      labels:
        app: frontend
    spec:
      containers:
      - name: frontend
        image: nginx:alpine
        ports:
        - containerPort: 80
        volumeMounts:
        - name: html
          mountPath: /usr/share/nginx/html
      volumes:
      - name: html
        configMap:
          name: frontend-html
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: frontend-html
data:
  index.html: |
    <!DOCTYPE html>
    <html>
    <head>
      <title>My App</title>
      <style>
        body { font-family: sans-serif; text-align: center; padding: 50px; }
        h1 { color: #2563eb; }
      </style>
    </head>
    <body>
      <h1>🚀 Hello from Kubernetes!</h1>
      <p>Served from a frontend pod.</p>
    </body>
    </html>
---
apiVersion: v1
kind: Service
metadata:
  name: frontend
spec:
  selector:
    app: frontend
  ports:
  - port: 80
    targetPort: 80
  type: NodePort

Step 5: Deploy Everything

# Apply all resources
kubectl apply -f postgres.yaml
kubectl apply -f backend.yaml
kubectl apply -f frontend.yaml

# Watch everything come up
kubectl get all
kubectl get pods -w

# Access the frontend
minikube service frontend

Scaling Made Easy

One of Kubernetes' biggest advantages: scaling is a single command.

# Scale manually
kubectl scale deployment backend --replicas=5

# Auto-scale based on CPU usage
kubectl autoscale deployment backend \
  --min=2 --max=10 --cpu-percent=70

# Check the autoscaler
kubectl get hpa

The Horizontal Pod Autoscaler (HPA) automatically adds pods when CPU goes above 70% and removes them when it drops below 65%. Zero manual intervention.

Zero-Downtime Deployments

Updating your app without any downtime is one click in Kubernetes:

# Update the image version
kubectl set image deployment/backend \
  backend=my-app:2.0

# Watch the rollout
kubectl rollout status deployment/backend
kubectl rollout history deployment/backend

# Oops, need to roll back?
kubectl rollout undo deployment/backend

Kubernetes uses a rolling update strategy by default: it creates new pods with the updated image, then gradually replaces old ones. Your app stays online the entire time.

Essential kubectl Commands

# Cluster overview
kubectl cluster-info
kubectl get nodes

# Resources
kubectl get pods -A              # All pods in all namespaces
kubectl get services
kubectl get deployments
kubectl get all -n default

# Debugging
kubectl logs pod-name           # View logs
kubectl logs -f pod-name        # Follow logs (like tail -f)
kubectl describe pod pod-name   # Detailed info + events
kubectl exec -it pod-name -- sh # Shell into a pod

# Manage resources
kubectl apply -f file.yaml      # Create/update resources
kubectl delete -f file.yaml     # Delete resources
kubectl get -f file.yaml -o yaml  # See what's deployed

Kubernetes vs Docker Compose vs Docker Swarm

Feature Docker Compose Docker Swarm Kubernetes
Learning curve Easy Medium Steep
Auto-scaling No Basic Advanced (HPA/VPA)
Self-healing Restart only Yes Yes (advanced)
Ecosystem Docker Hub Docker Hub Massive (Helm, Istio...)
Best for Development Small teams Production at scale

Next Steps After Basics

  • Helm — Package manager for Kubernetes (like pip for K8s)
  • Ingress — Route external traffic to services
  • Persistent Volumes — Storage that survives pod restarts
  • Kustomize — Manage configurations without templates
  • Service Mesh (Istio/Linkerd) — Advanced traffic management
  • Kubernetes on Cloud — EKS (AWS), GKE (Google), AKS (Azure)

Summary

Kubernetes is the standard for container orchestration. The key concepts are simple:

  • 📦 Pods — containers in a wrapper
  • 🔄 Deployments — manage and update pods
  • 🌐 Services — stable network endpoints
  • ⚙️ ConfigMaps/Secrets — external configuration
  • 📂 Namespaces — virtual clusters
  • 📈 HPA — automatic scaling

Start with Minikube locally, learn the basics with kubectl, then graduate to managed Kubernetes on cloud providers. It's a journey worth taking — Kubernetes skills open doors to virtually every DevOps role.
