Docker Compose: Multi-Container Applications

2026-06-24 9 min read

If you've learned Docker basics (containers, images, Dockerfiles), you know that running a single container is straightforward. But real applications need multiple services working together — a web server, a database, a cache, a message queue. That's where Docker Compose comes in. Instead of typing long docker run commands, you define everything in a simple YAML file and launch your entire stack with one command.

What is Docker Compose?

Docker Compose is a tool for defining and running multi-container Docker applications. You use a docker-compose.yml file to configure your application's services, networks, and volumes. Then with a single command, Compose creates and starts all the containers from your configuration.

"Docker Compose is the best way to manage multi-container Docker applications. What used to require 10+ docker run commands can be handled with a single YAML file." — Docker Docs

Installing Docker Compose

On most modern Docker installations, Compose is included as a Docker CLI plugin. Check your version:

docker compose version
# Output: Docker Compose version v2.27.0

Note the space: it's docker compose (v2), not docker-compose (v1, deprecated). If you don't have it, install it following the official installation guide.

Your First docker-compose.yml

Let's start with a minimal example — a web app and a Redis cache:

# docker-compose.yml
services:
  web:
    build: .
    ports:
      - "3000:3000"
    environment:
      - REDIS_HOST=redis
      - REDIS_PORT=6379
    depends_on:
      - redis

  redis:
    image: redis:7-alpine
    ports:
      - "6379:6379"

That's it! To start everything:

# Start all services (foreground)
docker compose up

# Start in the background
docker compose up -d

# Stop all services
docker compose down

# View logs
docker compose logs

# Restart a specific service
docker compose restart web

Understanding the YAML Structure

Services

Each service defines a container. Key configuration options:

services:
  my-service:
    # Build from Dockerfile
    build:
      context: .
      dockerfile: Dockerfile
    
    # Or pull an image
    image: node:20-alpine
    
    # Map ports (host:container)
    ports:
      - "8080:80"
    
    # Environment variables
    environment:
      NODE_ENV: production
      DB_HOST: postgres
    
    # Or load from a .env file
    env_file:
      - .env
    
    # Volume mounts
    volumes:
      - ./src:/app/src        # Bind mount
      - db-data:/var/lib/postgres  # Named volume
    
    # Container depends on another starting first
    depends_on:
      - postgres
    
    # Restart policy
    restart: unless-stopped
    
    # Container name
    container_name: my-web-app
    
    # Resource limits
    deploy:
      resources:
        limits:
          cpus: '1.0'
          memory: 512M

Volumes

Volumes persist data beyond container lifecycles:

services:
  postgres:
    image: postgres:16
    environment:
      POSTGRES_DB: myapp
      POSTGRES_USER: admin
      POSTGRES_PASSWORD: secret123
    volumes:
      - pgdata:/var/lib/postgresql/data  # Named volume

# Define the named volume
volumes:
  pgdata:

Networks

By default, all services in a Compose file share a network and can reach each other by service name. You can create custom networks for isolation:

services:
  web:
    image: nginx:alpine
    networks:
      - frontend
      - backend

  api:
    build: ./api
    networks:
      - backend

  redis:
    image: redis:7
    networks:
      - backend

networks:
  frontend:
  backend:

In this example, web can talk to both api and redis, but redis cannot be reached from outside the backend network.

Complete Example: Full-Stack Application

Here's a realistic three-tier application with a frontend, backend API, and database:

# docker-compose.yml
services:
  # Nginx reverse proxy
  nginx:
    image: nginx:alpine
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./nginx.conf:/etc/nginx/nginx.conf
      - ./frontend/dist:/usr/share/nginx/html
    depends_on:
      - api
    restart: unless-stopped

  # Python backend API
  api:
    build:
      context: ./api
      dockerfile: Dockerfile
    ports:
      - "8000:8000"
    environment:
      - DATABASE_URL=postgresql://app:secret@db:5432/myapp
      - REDIS_URL=redis://cache:6379
      - SECRET_KEY=${SECRET_KEY}
    volumes:
      - ./api:/app
    depends_on:
      db:
        condition: service_healthy
      cache:
        condition: service_started
    restart: unless-stopped

  # PostgreSQL database
  db:
    image: postgres:16-alpine
    environment:
      - POSTGRES_DB=myapp
      - POSTGRES_USER=app
      - POSTGRES_PASSWORD=secret
    volumes:
      - pgdata:/var/lib/postgresql/data
      - ./init.sql:/docker-entrypoint-initdb.d/init.sql
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app"]
      interval: 10s
      timeout: 5s
      retries: 5
    restart: unless-stopped

  # Redis cache
  cache:
    image: redis:7-alpine
    volumes:
      - redis-data:/data
    restart: unless-stopped

volumes:
  pgdata:
  redis-data:

Notice the healthcheck on the database. This ensures the API container waits for the database to be truly ready, not just started.

Using .env Files

Never hardcode secrets. Use a .env file:

# .env (add to .gitignore!)
SECRET_KEY=my-super-secret-key
DATABASE_URL=postgresql://app:secret@db:5432/myapp
REDIS_URL=redis://cache:6379

Compose automatically loads variables from .env. Reference them in your YAML with ${VARIABLE}.

Useful Compose Commands

# Start everything
docker compose up -d

# Stop everything
docker compose down

# Stop and remove volumes (clears database data!)
docker compose down -v

# View all logs
docker compose logs -f

# Logs from a specific service
docker compose logs -f api

# Run a one-off command inside a service
docker compose exec api python manage.py migrate
docker compose exec db psql -U app -d myapp

# Build images from scratch (ignore cache)
docker compose build --no-cache

# Scale a service to multiple containers
docker compose up -d --scale api=3

# Check service status
docker compose ps

# View resource usage
docker compose top

# Generate a docker run command from Compose config
docker compose run --rm api --help

Development vs Production Profiles

Docker Compose supports profiles to run different sets of services:

services:
  api:
    build: ./api
    ports:
      - "8000:8000"

  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: dev
    volumes:
      - pgdata:/var/lib/postgresql/data

  # Only in production
  nginx:
    image: nginx:alpine
    ports:
      - "80:80"
    profiles:
      - production

  # Only in development
  pgadmin:
    image: dpage/pgadmin4
    ports:
      - "5050:80"
    environment:
      PGADMIN_DEFAULT_EMAIL: admin@dev.com
      PGADMIN_DEFAULT_PASSWORD: admin
    profiles:
      - development

volumes:
  pgdata:
# Start with development services
docker compose --profile development up -d

# Start with production services
docker compose --profile production up -d

# Start all services (ignore profiles)
docker compose up -d

Overriding Configuration with Compose Files

Use a base file and an override file for different environments:

# docker-compose.yml (base)
services:
  api:
    build: ./api
    environment:
      - DEBUG=false

# docker-compose.override.yml (auto-loaded in dev)
services:
  api:
    environment:
      - DEBUG=true
    volumes:
      - ./api:/app  # Hot reload in development

Docker Compose automatically loads docker-compose.override.yml when present. In production, deploy with only the base file.

Common Pitfalls

  • depends_on is not a health check — it only waits for the container to start, not for the service to be ready. Use healthchecks for true dependency management.
  • Forgetting to .gitignore .env — secrets in your .env file will be pushed to GitHub if you forget. Always add .env to your .gitignore.
  • Not using Alpine images — when possible, use -alpine variants of images for smaller sizes and faster pulls.
  • Leaving volumes on the host — docker compose down doesn't remove volumes by default. Use -v flag to clean them.
  • Running everything as root — add a non-root user in your Dockerfiles for security.
