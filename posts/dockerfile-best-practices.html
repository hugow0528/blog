Dockerfile Best Practices: Build Smaller, Faster, Secure Images

June 26, 2026 · 12 min read

You've learned Docker basics and Docker Compose. Now you need to write Dockerfiles that actually work well in production. A bad Dockerfile gives you bloated 1.5 GB images that take forever to build and push. A great one gives you a 45 MB image that deploys in seconds.

This guide covers proven Dockerfile best practices with real before/after examples — multi-stage builds, layer caching, security hardening, and image optimization techniques used by teams running containers in production.

1. Start with the Right Base Image

The base image is the foundation of everything. Choose wisely — your image size and security start here.

Use minimal base images:

# ❌ BAD — 800 MB just for the base image
FROM python:3.11

# ✅ GOOD — 130 MB
FROM python:3.11-slim

# ✅ BEST for production — 45 MB
FROM python:3.11-alpine

Python image sizes:

  • python:3.11 — 894 MB (full Ubuntu)
  • python:3.11-slim — 130 MB (minimal Debian)
  • python:3.11-alpine — 45 MB (Alpine Linux)

Always pin exact versions instead of using latest tags. Reproducible builds are non-negotiable in production:

# ❌ BAD — non-deterministic, breaks at any time
FROM python:latest
FROM node:18

# ✅ GOOD — pinned to exact digests or versions
FROM python@sha256:abc123...
FROM python:3.11.7-slim

2. Multi-Stage Builds: Keep Only What You Need

Multi-stage builds let you compile or install dependencies in one stage and copy only the final artifacts into a lean runtime image. This is the #1 technique for reducing image size.

Before (single stage, bloated):

FROM python:3.11
WORKDIR /app

# Installs build tools (gcc, make, etc.) permanently
RUN apt-get update && apt-get install -y \
    gcc \
    libpq-dev \
    build-essential

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .
CMD ["python", "app.py"]

After (multi-stage, 80% smaller):

# Stage 1: Builder — install dependencies + compile
FROM python:3.11-slim AS builder
WORKDIR /build
RUN apt-get update && apt-get install -y --no-install-recommends \
    gcc libpq-dev && rm -rf /var/lib/apt/lists/*
COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

# Stage 2: Runtime — copy only compiled packages
FROM python:3.11-slim
WORKDIR /app
COPY --from=builder /install /usr/local
COPY . .
CMD ["python", "app.py"]

The final image contains only the Python runtime and your compiled packages — no compilers, no build tools, no extra OS packages. Typical reduction: 894 MB → 150 MB.

Go example (even more dramatic):

# Stage 1: Compile the Go binary
FROM golang:1.22 AS builder
WORKDIR /build
COPY go.mod go.sum .
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -o /app

# Stage 2: Run the compiled binary in a scratch image
FROM scratch
COPY --from=builder /app /app
EXPOSE 8080
CMD ["/app"]

The final image is just your compiled binary — no OS, no shell, no runtime. Typically 10-15 MB instead of 800+ MB.

3. Leverage Layer Caching for Faster Builds

Docker caches each FROM, COPY, and RUN layer. If a layer hasn't changed, Docker skips rebuilding it. The trick is to order your commands from least-changing to most-changing.

# ✅ GOOD — dependencies rarely change, cache is reused
FROM python:3.11-slim
WORKDIR /app

# Layer 1: Change only when dependencies change (cached most of the time)
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Layer 2: Changes every time you code (always rebuilt, but fast)
COPY . .

CMD ["python", "app.py"]

---

# ❌ BAD — code changes invalidate the pip install cache every time
FROM python:3.11-slim
WORKDIR /app

COPY . .
RUN pip install --no-cache-dir -r requirements.txt

CMD ["python", "app.py"]

Real-world impact: With the good ordering, your daily code changes take 2 seconds to build (just COPY). With bad ordering, every change triggers a full pip install that takes 30-60 seconds.

Advanced tip — hash-based caching: For Node.js projects, copy only the lockfile to get maximum cache hits:

FROM node:20-alpine
WORKDIR /app

# Only reinstall when package.json or package-lock.json changes
COPY package.json package-lock.json ./
RUN npm ci --production

# Install dev dependencies in a separate layer for testing
COPY package.json package-lock.json ./
RUN npm ci

COPY . .
RUN npm run build

CMD ["npm", "start"]

4. Keep Images Small with Clean Commands

Each RUN command creates a new layer. Combine related commands and clean up in the same layer to avoid wasting space.

# ❌ BAD — each RUN creates a layer with the packages staying
RUN apt-get update
RUN apt-get install -y curl
RUN apt-get install -y git
RUN curl -sL https://deb.nodesource.com/setup_20.x | bash -
RUN apt-get install -y nodejs

# ✅ GOOD — one layer, cleaned up before committing
RUN apt-get update && apt-get install -y --no-install-recommends \
    curl \
    git \
    ca-certificates \
    && curl -fsSL https://deb.nodesource.com/setup_20.x | bash - \
    && apt-get install -y --no-install-recommends nodejs \
    && apt-get purge -y --auto-remove curl git \
    && apt-get clean \
    && rm -rf /var/lib/apt/lists/*

Notice the && chaining — all commands run in a single layer, and cleanup happens before the layer is committed. The temporary files never end up in your image.

5. Security Hardening for Production

Running containers as root is the #1 Docker security anti-pattern. Here's how to lock down your images:

Create a Non-Root User

FROM python:3.11-slim
WORKDIR /app

# Create a dedicated user and group
RUN groupadd -r appuser && useradd -r -g appuser -d /app -s /sbin/nologin appuser

# Copy files and set ownership
COPY --chown=appuser:appuser . .

# Switch to the non-root user
USER appuser

CMD ["python", "app.py"]

Set Read-Only Root Filesystem

At runtime, mount the root filesystem as read-only (via Docker run or Docker Compose):

# Docker Compose example
services:
  app:
    build: .
    read_only: true
    tmpfs:
      - /tmp
      - /app/cache
    volumes:
      - ./data:/app/data:ro

Scan for Vulnerabilities

Add vulnerability scanning to your pipeline. trivy is a free, fast scanner:

# In CI/CD
docker build -t myapp:latest .
trivy image --severity HIGH,CRITICAL myapp:latest

# Or integrate in pre-commit or GitHub Actions
- name: Scan image
  uses: aquasecurity/trivy-action@master
  with:
    image-ref: 'myapp:latest'
    format: 'table'
    exit-code: '1'
    severity: 'HIGH,CRITICAL'

6. Use .dockerignore to Exclude Unnecessary Files

Just like .gitignore, a .dockerignore file prevents unnecessary files from being sent to the Docker daemon. This speeds up builds and keeps images clean.

# .dockerignore
.git
.gitignore
*.md
.env
.venv
__pycache__
*.pyc
node_modules
.dockerignore
Dockerfile
docker-compose.yml
tests/
.venv/
.vscode/
.idea/

Without this, Docker sends everything in your build context — including your .git directory, virtual environments, and test files — potentially adding hundreds of megabytes to the build.

7. HEALTHCHECK for Production Reliability

Add a health check so Docker (and your orchestrator) knows if your container is actually working:

FROM python:3.11-slim
WORKDIR /app
COPY . .
RUN pip install --no-cache-dir -r requirements.txt

# Health check — Docker restarts the container if this fails 3 times
HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
    CMD curl -f http://localhost:8000/health || exit 1

CMD ["python", "app.py"]

Complete Production Dockerfile Example

Here's a full Dockerfile combining all these best practices for a Python Flask API:

# Build stage
FROM python:3.11-slim AS builder
WORKDIR /build
RUN apt-get update && apt-get install -y --no-install-recommends \
    gcc libpq-dev && rm -rf /var/lib/apt/lists/*
COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

# Runtime stage
FROM python:3.11-slim

# Security: non-root user
RUN groupadd -r appuser && useradd -r -g appuser -d /app -s /sbin/nologin appuser

WORKDIR /app
COPY --from=builder /install /usr/local
COPY --chown=appuser:appuser . .

# Environment
ENV PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1 \
    PORT=8000

EXPOSE 8000

# Health check
HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
    CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:8000/health')" || exit 1

USER appuser
CMD ["gunicorn", "--bind", "0.0.0.0:8000", "--workers", "4", "app:app"]
