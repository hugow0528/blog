Terraform Workspaces: Manage Multiple Environments from One Codebase

June 28, 2026

One of the most common infrastructure challenges is managing separate environments — development, staging, and production — from a single Terraform codebase. You want the same configuration, but different servers, different databases, and different settings for each environment.

Terraform workspaces solve this elegantly. They let you maintain separate state files for each environment while sharing the same configuration code. No more duplicating your Terraform files across directories or getting confused about which environment you're deploying to.

The Problem: Multiple Environments, One Codebase

Without workspaces, teams often use one of these messy approaches:

  • Copy directories: terraform/dev/, terraform/staging/, terraform/prod/ — leads to drift and duplication
  • Manual state file management: terraform state push/pull — error-prone and slow
  • One big state file: all environments in one state — changes to dev might accidentally affect prod

Workspaces give you a clean, built-in solution. Each workspace has its own state file but shares the same configuration. Switching between environments is a single command.

Creating and Switching Workspaces

Every Terraform project starts with a default workspace. Let's create workspaces for our environments:

# List all workspaces (you'll see 'default')
$ terraform workspace list

  default

# Create a dev workspace
$ terraform workspace new dev
Created and switched to workspace "dev"!

# Create staging and production
$ terraform workspace new staging
$ terraform workspace new prod

# List all workspaces
$ terraform workspace list

  default
  dev
* staging
  prod

# Switch to a workspace
$ terraform workspace select dev
Switched to workspace "dev".

The asterisk (*) shows which workspace is currently active. Any terraform plan or terraform apply you run will operate on that workspace's state.

Environment-Specific Variables

Workspaces truly shine when combined with terraform.tfvars files. Terraform automatically loads files named terraform.<workspace>.tfvars based on the current workspace.

Here's a practical project structure:

terraform/
├── main.tf              # Shared resources
├── variables.tf         # Variable definitions
├── terraform.tfvars     # Default values
├── terraform.dev.tfvars  # Dev overrides
├── terraform.staging.tfvars # Staging overrides
└── terraform.prod.tfvars  # Production overrides

variables.tf — define your variables:

variable "environment" {
  description = "Deployment environment"
  type        = string
}

variable "instance_type" {
  description = "EC2 instance type"
  type        = string
  default     = "t3.micro"
}

variable "db_password" {
  description = "Database password"
  type        = string
  sensitive   = true
}

terraform.dev.tfvars:

environment   = "dev"
instance_type = "t3.micro"
db_password   = "dev-password-not-secret"

terraform.prod.tfvars:

environment   = "prod"
instance_type = "t3.xlarge"
db_password   = "managed-by-aws-secrets-manager"

Now when you switch workspaces, the correct configuration loads automatically:

# Apply to dev
$ terraform workspace select dev
$ terraform apply

# Apply to production
$ terraform workspace select prod
$ terraform apply

Using workspace.name in Your Configuration

The terraform.workspace built-in variable gives you the current workspace name. Use it to dynamically set resource names, tags, and other environment-specific values:

resource "aws_instance" "web" {
  ami           = var.ami_id
  instance_type = var.instance_type

  tags = {
    Name        = "${var.environment}-web-server"
    Environment = terraform.workspace
    ManagedBy   = "terraform"
  }
}

resource "aws_db_instance" "main" {
  identifier = "${terraform.workspace}-main-db"

  engine         = "mysql"
  engine_version = "8.0"
  instance_class = var.instance_type
  username       = "admin"
  password       = var.db_password

  tags = {
    Environment = terraform.workspace
  }
}

Each workspace creates resources with its own naming. The dev workspace creates dev-web-server and dev-main-db, while prod creates prod-web-server and prod-main-db. Zero duplication in your code.

Conditional Configuration with Workspaces

Some resources should only exist in certain environments. Use conditional expressions to control creation:

# Only create monitoring in staging and prod
resource "aws_cloudwatch_metric_alarm" "cpu" {
  count = terraform.workspace != "dev" ? 1 : 0

  alarm_name          = "${terraform.workspace}-high-cpu"
  comparison_operator = "GreaterThanThreshold"
  evaluation_periods  = "2"
  metric_name         = "CPUUtilization"
  namespace           = "AWS/EC2"
  period              = "120"
  statistic           = "Average"
  threshold           = "80"
  alarm_description   = "CPU utilization above 80%"
}

# Production gets extra security groups
resource "aws_security_group" "waf" {
  count = terraform.workspace == "prod" ? 1 : 0

  name        = "waf-protection"
  description = "WAF integration for production"
  vpc_id      = var.vpc_id
}

The count parameter with a ternary expression means the resource is created only when the condition is true. No dev alarms, no production-only resources in staging.

Workspaces with Remote State

When using a remote backend (S3, GCS, Terraform Cloud), workspaces are stored in separate paths automatically:

terraform {
  backend "s3" {
    bucket         = "my-terraform-state"
    key            = "infrastructure/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "terraform-lock"
    workspace_dir  = "envs"
  }
}

Terraform stores states like this in S3:

  • infrastructure/terraform.tfstate — default workspace
  • infrastructure/envs/dev/terraform.tfstate — dev workspace
  • infrastructure/envs/staging/terraform.tfstate — staging workspace
  • infrastructure/envs/prod/terraform.tfstate — prod workspace

State locking via DynamoDB still works per-workspace, so two people can safely deploy to dev and staging at the same time without conflicts.

Importing Existing Resources

Already have resources running? Import them into a workspace:

# Select the workspace
$ terraform workspace select dev

# Initialize
$ terraform init

# Import an existing EC2 instance
$ terraform import aws_instance.web i-0abc123def456

# Import a database
$ terraform import aws_db_instance.main dev-main-db

# Verify the import
$ terraform plan

No changes. Your infrastructure matches the configuration.

Each workspace can import its own set of resources. The dev workspace imports dev resources, the prod workspace imports prod resources. Everything stays separated.

Workspace Workflow for Teams

Here's a recommended team workflow:

  1. Develop locally: Use the default workspace on your machine for testing
  2. Push to dev: terraform workspace select dev && terraform apply
  3. Test: Run integration tests against the dev environment
  4. Approve: Promote changes through a PR/ci pipeline
  5. Deploy to staging: terraform workspace select staging && terraform apply
  6. Deploy to prod: terraform workspace select prod && terraform apply (with approval gates)

Workspaces vs Separate Directories

When should you use workspaces vs separate directories?

Use Workspaces When... Use Directories When...
Environments share most config Environments have very different resources
You want to avoid code duplication Teams need independent version control
Differences are mainly variable values Each environment has unique architectures
Small to medium infrastructure Large, complex infrastructure per env

Rule of thumb: If your environments differ only in instance sizes, passwords, and resource counts — use workspaces. If they have entirely different resource sets, consider directories or Terraform modules.

Common Pitfalls

  • Forgetting to check your workspace: Always run terraform workspace show before terraform apply. Nobody wants to accidentally destroy production.
  • State drift between workspaces: If you change a resource in dev, remember to update staging and prod configs too. Workspaces share code, not state changes.
  • Default workspace pollution: Use the default workspace only for local testing. Never apply to it in CI/CD.
  • Provider configs: Each workspace uses the same provider configuration. If environments use different AWS regions or accounts, you'll need provider aliases or workarounds.

Summary

Terraform workspaces give you a clean way to manage multiple environments from a single codebase. Key takeaways:

  1. terraform workspace new <name> — create an environment workspace
  2. terraform workspace select <name> — switch environments
  3. terraform.<workspace>.tfvars — auto-loaded environment variables
  4. terraform.workspace — use in configs for dynamic naming and conditionals
  5. Remote backends store workspace states in separate paths automatically
  6. Workspaces are ideal when environments differ mainly in variable values

With workspaces, your infrastructure code stays DRY, your environments stay isolated, and your team stays confident about which environment they're deploying to.
