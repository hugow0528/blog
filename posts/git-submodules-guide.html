Have you ever needed to use another Git repository as part of your project? Maybe a shared library, a common configuration, or a tool you're contributing to? Git submodules let you embed one repository inside another, keeping them as separate repos while tracking exactly which commit you're using.

Submodules have a reputation for being confusing. This guide demystifies them with practical examples, explains the common pain points, and shows you when to use submodules versus alternatives like Git subtrees.

Why Use Submodules?

Here are common scenarios where submodules make sense:

  • Shared libraries — A Python package used across multiple projects, maintained in its own repo
  • Common configurations — Terraform modules, Dockerfiles, or CI configs shared across repositories
  • External tools — Embedding a CLI tool you're developing alongside a project that uses it
  • Forked dependencies — Using a fork of an open-source project while tracking the upstream

Without submodules, you'd either copy the code (and fall out of sync) or install it as a package (and lose the ability to make local changes that immediately affect your project). Submodules give you the best of both worlds.

Setting Up a Submodule

Adding a submodule is straightforward. Here's the basic command:

# Add a submodule to your project
git submodule add https://github.com/example/shared-config.git config

# This creates:
# - A new directory called 'config' with the repo contents
# - A .gitmodules file tracking the submodule
# - A gitlink entry in your main repo

Let's walk through a real example:

# Start a new project
mkdir my-project && cd my-project
git init

# Add a shared utility library as a submodule
git submodule add https://github.com/hugow0528/shared-utils.git lib/shared-utils

# Check what was created
ls lib/shared-utils/    # The actual repository contents
cat .gitmodules         # Config file tracking submodules

The .gitmodules file is just a config file — it looks like this:

[submodule "lib/shared-utils"]
    path = lib/shared-utils
    url = https://github.com/hugow0528/shared-utils.git

Important: .gitmodules is human-readable and committed to your repo. The actual submodule state is stored in the Git index as a special gitlink entry that points to a specific commit hash.

The Clone That Breaks Everyone

Here's the #1 thing that trips people up. When someone clones your repo with submodules, the submodule directories are created but they're empty:

# Someone clones your project:
git clone https://github.com/example/my-project.git
cd my-project

ls lib/shared-utils/
# → empty directory! The files aren't there.

To actually get the submodule contents, they need to run:

# Option 1: Initialize and update submodules after cloning
git submodule init
git submodule update

# Option 2: The modern one-liner
git submodule update --init

# Option 3: Clone everything at once (recommended for new clones)
git clone --recurse-submodules https://github.com/example/my-project.git

Best practice: Always tell your team (or document) to use --recurse-submodules when cloning. Add it to your README:

# Clone with submodules
git clone --recurse-submodules https://github.com/example/my-project.git

# Or if you already cloned:
git submodule update --init --recursive

Working with Submodules

Updating a Submodule to a Newer Commit

When the external repo gets new changes, you can update your project to use them:

# Enter the submodule directory
cd lib/shared-utils

# Fetch and pull latest changes
git pull origin main

# Go back to the main project
cd ../..

# Commit the new submodule pointer
git add lib/shared-utils
git commit -m "Update shared-utils to latest version"

This is clean because your project now points to a specific, tested commit of the submodule.

Making Changes Inside a Submodule

Submodule directories are regular Git repos. You can make changes, commit, and push normally:

# Navigate into the submodule
cd lib/shared-utils

# Make your changes
echo "new_feature = True" >> config.py
git add config.py
git commit -m "Add new feature flag"

# Push the submodule to its own remote
git push origin main

# NOW go back to the parent repo and commit the new reference
cd ../..
git add lib/shared-utils
git commit -m "Update shared-utils: add feature flag"

Remember the two commits: one in the submodule repo, and one in the parent repo updating the gitlink.

Common Submodule Commands

# See all submodules and their status
git submodule status
# → abc123 lib/shared-utils (v1.2.0-12-gabc123)
#   ↑abc123 means the submodule is ahead of the parent's pointer

# See which branch each submodule is on
git submodule foreach 'git branch --show-current'

# Update all submodules to their tracked commits
git submodule update --init --recursive

# Sync submodule URLs (if the remote URL changed)
git submodule sync

# Remove a submodule (tedious, but necessary sometimes)
git submodule deinit -f lib/shared-utils
git rm lib/shared-utils
rm -rf .git/modules/lib/shared-utils
git commit -m "Remove shared-utils submodule"

Automation: Using git submodule foreach

The foreach command runs any shell command in every submodule. This is incredibly useful:

# Pull latest changes in ALL submodules
git submodule foreach 'git pull origin $(git branch --show-current)'

# Check status of all submodules
git submodule foreach 'git status --short'

# Show the last commit in each submodule
git submodule foreach 'git log -1 --oneline'

# Update all submodules to latest main
git submodule foreach 'git checkout main && git pull'

This is especially handy in monorepo-style setups where you have many submodules that need to stay in sync.

Python Project Example: Using Submodules as Libraries

Here's a practical setup for a Python project that uses a shared utility library:

# Project structure:
my-project/
├── main.py
├── lib/
│   └── shared-utils/    # submodule
│       ├── utils.py
│       └── __init__.py
├── .gitmodules
└── setup.py

To use the submodule as an importable library, create a symlink or use the path directly:

# main.py
import sys
sys.path.insert(0, 'lib/shared-utils')

from utils import format_date, send_email

# Use the library normally
today = format_date("2026-07-04")
print(today)

Or, for a cleaner approach, add the submodule to your project's setup.py or pyproject.toml as a path dependency:

# pyproject.toml
[project]
name = "my-project"
version = "0.1.0"

[tool.setuptools.package-data]
"my-project" = ["lib/shared-utils/*"]

Submodules vs. Subtrees: When to Use What

Git subtrees is an alternative that embeds another repo's contents directly into your project's directory tree (without tracking a separate gitlink):

Feature Submodules Subtrees
Clone complexity Needs --recurse-submodules Normal git clone
Separate repo history Preserved Embedded in parent
Multiple parents Same commit in many projects Each parent has its own copy
Learning curve Steep Moderate
Best for Shared libraries, many consumers Single-project dependencies

Rule of thumb: Use submodules when the same repo is shared across multiple projects. Use subtrees when you want simplicity and don't need to share the exact same commit across many projects.

Troubleshooting Common Issues

Issue: "Empty directory" after cloning

Run git submodule update --init --recursive. This is the most common first-time issue.

Issue: Submodule points to a different commit

Git status shows modified submodules. Use git submodule status to see the mismatch, then git submodule update to reset to the tracked commit.

Issue: "fatal: no submodule mapping found"

The .gitmodules file and .git/config are out of sync. Run git submodule sync to fix.

Issue: GitHub can't see submodule content

GitHub displays submodule links, not contents. If a submodule repo is private, clone the parent repo with your credentials (SSH token or HTTPS auth) so Git can access the private submodule.

GitHub-Specific Tips

# If using SSH, configure submodule URLs to use SSH
git submodule foreach 'git config url.git@github.com:.insteadOf https://github.com/'

# Check if submodules are on the correct branch
git submodule foreach 'echo $name; git branch --show-current'

# Update all submodules to latest on their respective branches
git submodule foreach 'git pull origin $(git symbolic-ref --short HEAD)'

Summary

Git submodules are powerful but need a bit of upfront knowledge:

  1. Adding: git submodule add URL path
  2. Cloning: git clone --recurse-submodules
  3. Initializing: git submodule update --init --recursive
  4. Updating: cd into submodule, git pull, then git add + git commit in parent
  5. Batching: git submodule foreach 'command'

Once you know the workflow, submodules become a reliable way to manage shared code across projects without the copy-paste trap.
