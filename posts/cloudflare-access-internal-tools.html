Cloudflare Access: Secure Internal Tools Without VPNs

July 1, 2026 9 min read New

You built an internal dashboard, admin panel, or monitoring tool. It works great locally. Now you need to share it with your team. What do you do?

Old way: Set up a VPN, manage certificates, handle NAT routing, deal with "why can't I connect" tickets at 2 AM.

New way: Point Cloudflare at it, enable Access, and your team logs in with Google/GitHub/Okta. Done in 20 minutes. Zero VPN configuration.

This guide walks you through setting up Cloudflare Access for internal tools — from the free tier basics to production-ready configurations with custom policies.

What is Cloudflare Access?

Cloudflare Access is a zero-trust authentication service that sits between the internet and your internal applications. Instead of exposing your admin panel with a password or building custom login pages, Access:

  • Intercepts requests to your application
  • Challenges users to authenticate via Google, GitHub, Okta, SAML, or other identity providers
  • Applies policies (e.g., "only people with @company.com email")
  • Forwards authorized requests to your application with identity headers
  • Blocks everyone else before they even reach your server

Your application code never touches authentication. Cloudflare handles it all at the edge.

Architecture: How Access Works

Here's what happens when someone visits admin.yourdomain.com:

User → Cloudflare Edge → Access Policy Check → Your Server

If not authenticated:
  → Redirect to Google/GitHub/Okta login
  → After login, issue a session token (JWT)
  → User gets 12-hour authenticated session

If authenticated:
  → Forward request with user identity headers
  → Your app receives X-Auth-Email, X-Auth-Name, etc.

The key insight: your server never sees unauthorized traffic. Access evaluates and authenticates at Cloudflare's edge network — before the request traverses the internet to your server.

Step 1: Connect Your App via Cloudflare Tunnel

Before Access can protect your app, Cloudflare needs to route traffic to it. We use Cloudflare Tunnel (zero-trust networking) — no open ports, no public IP needed.

# Install cloudflared
curl -L https://github.com/cloudflare/cloudflared/releases/latest/download/cloudflared-linux-amd64 -o cloudflared
chmod +x cloudflared
sudo mv cloudflared /usr/local/bin/

# Authenticate with your Cloudflare account
cloudflared tunnel login

# Create a tunnel
cloudflared tunnel create my-admin-tunnel

# Save the tunnel ID (from the output)

Create a configuration file at ~/.cloudflared/config.yml:

# ~/.cloudflared/config.yml
tunnel: my-admin-tunnel
credentials-file: /root/.cloudflared/<TUNNEL_ID>.json

ingress:
  - hostname: admin.yourdomain.com
    service: http://localhost:8080
    originRequest:
      noTLSVerify: true
  - service: http_status:404

Start the tunnel:

cloudflared tunnel run my-admin-tunnel

Now admin.yourdomain.com is accessible — but not yet protected. Let's add Access.

Step 2: Enable Access in the Dashboard

Navigate to Zero Trust → Access → Applications in the Cloudflare dashboard and click Add an application.

Configure the application:

Setting Value
Application name Admin Dashboard
Domain admin.yourdomain.com
Public URL include rules *
Authentication duration 12 hours

This creates the Access application. Now configure the identity provider.

Step 3: Set Up an Identity Provider

Cloudflare Access supports multiple identity providers. For most small teams and solo developers, Google or GitHub are the easiest.

Google (recommended for most teams):

  1. Go to Google Cloud Console → APIs & Services → Credentials
  2. Create an OAuth 2.0 Client ID (Web application type)
  3. Add authorized redirect URI: https://yourdomain.com/cdn-cgi/access/callback
  4. Copy the Client ID and Client Secret

In Cloudflare Zero Trust → Access → Settings → Identity Providers:

Setting Value
Name Google
Domain yourdomain.com
Client ID (from Google Console)
Client Secret (from Google Console)

Step 4: Create Access Policies

Policies define who can access your application. Each application can have multiple policies — the first matching policy wins.

Basic: Allow specific email domain

Rule Operator Value
Email Ends with @company.com

Advanced: Allow specific team + group

Rule Operator Value
Google Group Membership Is dev-team@company.com
Device Posture Is Compliant

For personal projects: Allow specific emails

Rule Operator Value
Email Is you@yourdomain.com

Step 5: Read User Identity in Your Application

Once Access authenticates the user, Cloudflare adds identity headers to every forwarded request. Your application can read these headers to know who is logged in.

Python (Flask example):

from flask import Flask, request

app = Flask(__name__)

@app.route("/")
def admin_dashboard():
    # Cloudflare Access adds these headers
    user_email = request.headers.get("X-Auth-Email")
    user_name = request.headers.get("X-Auth-Name")
    user_groups = request.headers.get("X-Auth-User-Groups")

    return f"""
    <h1>Welcome, {user_name}!</h1>
    <p>Email: {user_email}</p>
    <p>Groups: {user_groups or 'None'}</p>
    """

if __name__ == "__main__":
    app.run(host="127.0.0.1", port=8080)

Python (FastAPI example):

from fastapi import FastAPI, Request

app = FastAPI()

@app.get("/")
async def dashboard(request: Request):
    email = request.headers.get("x-auth-email", "Unknown")
    name = request.headers.get("x-auth-name", "Unknown")

    return {
        "message": f"Welcome, {name}!",
        "email": email,
        "authenticated": True
    }

Node.js (Express example):

const express = require("express");
const app = express();

app.get("/", (req, res) => {
    const email = req.headers["x-auth-email"];
    const name = req.headers["x-auth-name"];

    res.send(`
        <h1>Welcome, ${name}!</h1>
        <p>Email: ${email}</p>
    `);
});

app.listen(8080, "127.0.0.1");

The available headers include:

Header Description
X-Auth-Email User's email address
X-Auth-Name User's display name
X-Auth-User-Groups Comma-separated list of groups
X-Auth-User-Id Unique user identifier
Cf-Access-Jwt-Assertion Full JWT token (for advanced use)

Step 6: Run the Tunnel as a System Service

For production, you want your tunnel to survive reboots. Use systemd:

# Create the systemd service
sudo tee /etc/systemd/system/cloudflared-tunnel.service > /dev/null << 'EOF'
[Unit]
Description=Cloudflare Tunnel for Admin Dashboard
After=network-online.target

[Service]
Type=simple
ExecStart=/usr/local/bin/cloudflared --config /root/.cloudflared/config.yml tunnel run my-admin-tunnel
Restart=on-failure
RestartSec=5
KillMode=process

[Install]
WantedBy=multi-user.target
EOF

# Enable and start
sudo systemctl enable cloudflared-tunnel
sudo systemctl start cloudflared-tunnel

# Check status
sudo systemctl status cloudflared-tunnel

Advanced: Service Tokens for API Access

Not all users access your tool through a browser. Monitoring scripts, CI/CD pipelines, and automation tools need machine-to-machine authentication.

Cloudflare Access Service Tokens solve this. Create one in the Access application settings:

# Generate a service token (Cloudflare dashboard)
# You get: Client ID and Client Secret

# Use it in your automation scripts
curl -H "Cf-Access-Client-Id: <CLIENT_ID>" \
     -H "Cf-Access-Client-Secret: <CLIENT_SECRET>" \
     https://admin.yourdomain.com/api/health

Python example for automated access:

import requests
from requests.auth import HTTPBasicAuth
import base64

# Service token auth via Cloudflare's challenge flow
CLIENT_ID = "your-client-id"
CLIENT_SECRET = "your-client-secret"
AUDIENCE = "your-audience-from-dashboard"
SERVICE_URL = "https://your-account.cloudflareaccess.com/cdn-cgi/access/service-token"

# Step 1: Get a JWT token from Cloudflare
token_resp = requests.post(SERVICE_URL, json={
    "client_id": CLIENT_ID,
    "client_secret": CLIENT_SECRET,
    "audience": AUDIENCE
})
jwt_token = token_resp.json()["token"]

# Step 2: Use the token to access your protected app
response = requests.get(
    "https://admin.yourdomain.com/api/health",
    headers={"Authorization": f"Bearer {jwt_token}"}
)

print(response.json())

Cost: Free Tier Coverage

Cloudflare's Free tier includes:

  • Unlimited Cloudflare Tunnels
  • Cloudflare Access for up to 50 monthly active users (free)
  • Google, GitHub, and other SSO providers
  • Session tokens and basic policies
  • Service tokens

For personal projects and small teams, the free tier covers everything. You only pay if you need enterprise features like device posture, MFA enforcement, or advanced logging (50+ users).

Troubleshooting Common Issues

Issue: "403 Forbidden" after login

Your Access policy is too restrictive. Check that your email matches the policy exactly. For testing, temporarily set the policy to "Email ends with" your domain.

Issue: Tunnel won't start

Check that your credentials file matches the tunnel ID. Run cloudflared tunnel info to verify the tunnel is active.

Issue: Identity headers missing

Make sure your application is accessed through the Cloudflare domain, not directly. If you bypass Cloudflare, the headers won't be present.

Issue: Google OAuth redirect fails

Verify your redirect URI in Google Cloud Console exactly matches https://yourdomain.com/cdn-cgi/access/callback. Even a trailing slash difference will break it.

Summary

Cloudflare Access replaces VPNs for internal tool access with a simpler, more secure model:

  1. Tunnel — Connect your local app to Cloudflare without opening ports
  2. Identity Provider — Let users log in with Google/GitHub/Okta
  3. Policies — Define who can access (email domain, groups, etc.)
  4. Headers — Your app gets user identity via HTTP headers
  5. Service Tokens — Machine-to-machine auth for automation

For solo developers and small teams, this setup takes under 30 minutes and costs nothing on the free tier. Your internal tools get enterprise-grade authentication without writing a single line of login code.
