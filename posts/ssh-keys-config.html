SSH Keys & ssh_config: Passwordless Login and Secure Remote Access

2026-06-29

Password-based SSH login is slow and vulnerable to brute-force attacks. SSH key-based authentication is faster, more secure, and the standard way developers connect to remote servers. In this guide, you'll learn how to generate SSH keys, set up passwordless login, configure ssh_config with aliases for easy access, and harden your SSH setup for production use. Everything is explained with real commands you can run right now.

Why SSH Keys Are Better Than Passwords

SSH keys use asymmetric cryptography — a public key (shared with servers) and a private key (kept secret on your machine). When you connect, the server challenges your private key to prove you own it. No password is sent over the network.

The benefits are clear:

  • Security: Private keys are 2048-4096 bits long. Brute-forcing an SSH key is computationally impossible with current technology.
  • Convenience: No typing passwords — just ssh myserver.
  • Automation: Scripts, CI/CD pipelines, and deployment tools need key-based auth.
  • Granular control: You can restrict keys to specific commands, users, or source IPs.

Let's walk through the complete setup.

Step 1: Generate Your SSH Key Pair

Open your terminal and run:

ssh-keygen -t ed25519 -C "your_email@example.com"

This generates an Ed25519 key pair — the modern recommended algorithm. It's faster and more secure than RSA. When prompted:

  • File location: Press Enter to accept the default (~/.ssh/id_ed25519).
  • Passphrase: Enter a strong passphrase. This encrypts your private key at rest — if someone steals your key file, they still need the passphrase.

After running the command, you'll have two files:

~/.ssh/id_ed25519        # Private key — NEVER share this
~/.ssh/id_ed25519.pub    # Public key — you add this to servers

Which Algorithm Should You Use?

Here's the current recommendation as of 2026:

  • ed25519 — Best choice. Fast, secure, short keys.
  • rsa (4096-bit) — Good for compatibility with very old systems. Use only if ed25519 isn't supported.
  • ecdsa — Generally avoided due to patent concerns and limited adoption.

Step 2: Copy Your Public Key to the Server

The easiest way is using ssh-copy-id:

ssh-copy-id -i ~/.ssh/id_ed25519.pub user@server.example.com

This appends your public key to ~/.ssh/authorized_keys on the server. You'll be asked for your password one last time.

Manual Method (if ssh-copy-id isn't available)

If you're on Windows or ssh-copy-id isn't installed:

# On your local machine, print the public key
cat ~/.ssh/id_ed25519.pub
# Copy the output (it starts with ssh-ed25519 AAAA...)

# SSH into the server with password, then:
mkdir -p ~/.ssh
chmod 700 ~/.ssh
echo "ssh-ed25519 AAAA... your_email@example.com" >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys

Test it:

ssh user@server.example.com
# You should log in without a password prompt!

If you set a passphrase, you'll still be prompted for that. Read on to eliminate even that.

Step 3: Set Up ssh-agent for Passphrase Management

If your key has a passphrase, typing it every time defeats the convenience of SSH keys. ssh-agent solves this by caching your decrypted key in memory:

On Linux (with systemd, most modern distros)

# The agent usually starts automatically. Check:
echo $SSH_AUTH_SOCK

# Add your key (you type the passphrase once):
ssh-add ~/.ssh/id_ed25519

# Verify it's loaded:
ssh-add -l

On macOS

# macOS uses a keychain integration. Add your key once:
ssh-add --apple-use-keychain ~/.ssh/id_ed25519

# It will auto-load from now on.

On Windows (Git Bash / WSL)

# Pageant is part of PuTTY and acts as an SSH agent
# Or in WSL/Git Bash:
eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519

Step 4: Configure ssh_config for Easy Access

This is where SSH becomes genuinely powerful. The ~/.ssh/config file lets you define shortcuts, set defaults, and manage multiple servers effortlessly.

Here's a practical example:

# ~/.ssh/config

# Default settings for all connections
Host *
    AddKeysToAgent yes
    UseKeychain yes              # macOS only
    IdentityFile ~/.ssh/id_ed25519
    ServerAliveInterval 60       # Send keepalive every 60 seconds
    ServerAliveCountMax 3        # Disconnect after 3 missed keepalives
    StrictHostKeyChecking ask    # Warn about unknown hosts
    VisualHostKey yes            # Show host key fingerprint

# Production server
Host prod
    HostName 203.0.113.10
    User deploy
    Port 22
    IdentityFile ~/.ssh/id_ed25519

# Staging server
Host staging
    HostName 203.0.113.20
    User deploy
    Port 2222

# Database server (different key)
Host db-server
    HostName db.example.com
    User dbadmin
    IdentityFile ~/.ssh/db_key
    Port 22

# GitHub (uses a specific key)
Host github.com
    AddKeysToAgent yes
    IdentitiesOnly yes
    IdentityFile ~/.ssh/github_key

# Development VM
Host dev
    HostName 192.168.1.100
    User hugo
    ForwardAgent yes

# Jump host (connect through a bastion server)
Host internal-server
    HostName 10.0.0.50
    User admin
    ProxyJump bastion

Host bastion
    HostName 203.0.113.1
    User jumpuser

After saving this file, use the aliases:

ssh prod          # Connects to deploy@203.0.113.10
ssh staging       # Connects to deploy@203.0.113.20:2222
ssh db-server     # Connects to dbadmin@db.example.com with db_key
scp file.txt prod:/var/www/  # Copy files using the alias

No need to remember IPs, usernames, or ports — everything is in your config file.

Step 5: Security Hardening

Now that your SSH is set up, let's make it more secure.

On the Server: Harden sshd_config

Edit /etc/ssh/sshd_config on the server:

# Disable password authentication entirely (only keys allowed)
PasswordAuthentication no

# Disable root login via SSH
PermitRootLogin no

# Use only strong key algorithms
PubkeyAcceptedAlgorithms ssh-ed25519,rsa-sha2-512,rsa-sha2-256

# Limit who can log in (allowlist approach)
AllowUsers deploy admin hugo

# Change default port (reduces automated scanning noise)
Port 2222

# Limit authentication attempts
MaxAuthTries 3

# Set connection timeout
LoginGraceTime 30

# Disable unused features
X11Forwarding no
PermitEmptyPasswords no
ChallengeResponseAuthentication no

# After editing, restart the service:
sudo systemctl restart sshd

Important: Before disabling password authentication, verify that key-based login works. Open a new terminal and test your SSH connection — don't lock yourself out!

File Permissions Matter

SSH is strict about file permissions. Wrong permissions can cause "Permission denied" errors even with correct keys:

# On your local machine
chmod 700 ~/.ssh                    # Directory
chmod 600 ~/.ssh/id_ed25519         # Private key
chmod 644 ~/.ssh/id_ed25519.pub     # Public key
chmod 600 ~/.ssh/config             # Config file

# On the server
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys

Use sshd's allow/deny lists

# Restrict access by source IP in sshd_config
# Only allow connections from specific networks
ListenAddress 203.0.113.10

# Or use firewall rules:
sudo ufw allow from 203.0.113.0/24 to any port 2222
sudo ufw deny 22  # Block old default port

Step 6: Useful SSH Commands and Tricks

Now that your SSH setup is solid, here are practical commands that save time:

File Transfer with SCP and SFTP

# Copy file to server
scp myfile.txt prod:/home/deploy/

# Copy entire directory (recursive)
scp -r ./website/ staging:/var/www/

# Copy from server to local
scp prod:/var/log/app.log ./

# Using a custom port
scp -P 2222 myfile.txt staging:/tmp/

# SFTP for interactive file management
sftp prod
# Inside sftp: get, put, ls, cd, mkdir, rm

SSH Tunneling for Port Forwarding

# Local port forwarding — access a remote database locally
ssh -L 5432:localhost:5432 prod
# Now connect to localhost:5432 on your machine → it routes to prod's PostgreSQL

# Remote port forwarding — expose a local service
ssh -R 8080:localhost:3000 prod
# Now prod:8080 routes to your local:3000 (useful for tunneling local dev)

# Dynamic port forwarding (SOCKS proxy)
ssh -D 1080 prod
# Configure your browser to use SOCKS proxy at localhost:1080
# All traffic routes through the server

Agent Forwarding

# If you need to SSH from server A to server B using your local keys:
ssh -A staging
# Then from staging:
ssh prod  # Uses your forwarded agent, no need to copy keys to staging

# Or set ForwardAgent yes in your ssh_config (see above)

Warning: Agent forwarding means anyone on the intermediate server could potentially use your keys. Only use ForwardAgent on servers you trust.

SSH Multiplexing (Faster Connections)

# Add to ~/.ssh/config:
Host *
    ControlMaster auto
    ControlPath ~/.ssh/sockets/%r@%h-%p
    ControlPersist 10m

# First SSH connection opens a master socket
# Subsequent connections reuse it — instant login!
mkdir -p ~/.ssh/sockets

Managing Multiple Keys for Different Services

You'll likely need separate keys for GitHub, your servers, Docker Hub, etc. Here's the recommended approach:

# Generate separate keys
ssh-keygen -t ed25519 -f ~/.ssh/github_key -C "github"
ssh-keygen -t ed25519 -f ~/.ssh/work_key -C "work"
ssh-keygen -t ed25519 -f ~/.ssh/personal_key -C "personal"

# Configure ~/.ssh/config:
Host github.com
    IdentityFile ~/.ssh/github_key
    IdentitiesOnly yes

Host work-*
    IdentityFile ~/.ssh/work_key

Host personal-*
    IdentityFile ~/.ssh/personal_key

The IdentitiesOnly yes directive tells SSH to use ONLY the specified key for that host, preventing it from trying all keys and getting rejected.

Troubleshooting Common Issues

SSH problems are common. Here's how to debug them:

# Run SSH with verbose output (up to -vvv for maximum detail)
ssh -v user@server

# Common errors and fixes:

# "Permission denied (publickey)"
# → Check that your public key is in authorized_keys
# → Verify file permissions (600 for authorized_keys)
# → Run ssh -vvv to see which key is being tried

# "Host key verification failed"
# → The server's key changed. Check if it's legitimate, then:
ssh-keygen -R old.server.com

# "Connection timed out"
# → Check firewall rules on the server
# → Verify the port is correct
# → Try ping server.example.com

# "Too many authentication failures"
# → Too many keys in ssh-agent. Remove unnecessary ones:
ssh-add -D  # Clear all keys
ssh-add ~/.ssh/id_ed25519  # Add only the one you need

Summary

SSH key-based authentication is the foundation of secure remote server management. You've learned to:

  1. Generate Ed25519 keys with ssh-keygen
  2. Copy public keys to servers with ssh-copy-id
  3. Manage passphrases with ssh-agent
  4. Configure ~/.ssh/config with aliases and defaults
  5. Harden server SSH with sshd_config
  6. Use port forwarding, agent forwarding, and multiplexing
  7. Manage multiple keys for different services
  8. Debug connection issues with ssh -vvv

With this setup, connecting to your servers is as simple as ssh prod — no passwords, no remembering IPs, and significantly more secure than before. The time invested in setting this up pays off every single day.
