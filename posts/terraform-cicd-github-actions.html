Terraform CI/CD with GitHub Actions: Automate Infrastructure as Code

July 8, 2026 · 11 min read

You've written Terraform code and run terraform apply from your laptop. But in a team, running Terraform manually is risky — someone might forget to run plan, skip reviews, or accidentally apply to production. A CI/CD pipeline automates the entire workflow: lint, format, plan, review, and deploy.

This guide walks through building a complete Terraform CI/CD pipeline with GitHub Actions. You'll get automated quality checks, human approval gates, and safe deployments — all from a single workflow file.

The Terraform CI/CD Workflow

Here's the standard workflow most teams use:

  1. Pull request opened → lint + format + validate + plan
  2. Plan output posted as PR comment → team reviews changes
  3. Approval + merge to main → apply to production

Let's build this step by step.

Step 1: Project Structure

Organize your Terraform repo like this:

terraform/
├── .github/
│   └── workflows/
│       └── terraform.yml
├── main.tf
├── variables.tf
├── outputs.tf
├── providers.tf
└── .tflint.hcl

Step 2: The CI Workflow File

Create .github/workflows/terraform.yml:

name: Terraform CI/CD

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

permissions:
  contents: read
  pull-requests: write

env:
  TF_IN_AUTOMATION: "true"
  TF_INPUT: "false"

jobs:
  # Job 1: Lint and validate on every PR
  validate:
    name: Validate Terraform
    runs-on: ubuntu-latest
    if: github.event_name == 'pull_request'
    
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Setup Terraform
        uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: "1.7.5"

      - name: Terraform Format Check
        id: fmt
        run: terraform fmt -check -recursive
        continue-on-error: true

      - name: Terraform Init
        run: terraform init -backend=false

      - name: Terraform Validate
        run: terraform validate -json

      - name: Terraform Docs
        uses: terraform-docs/terraform-docs-cli@v1
        with:
          configfile: .terraform-docs.yml
          paths: "."

What this does:

  • terraform fmt -check — ensures consistent formatting (fails if not formatted)
  • terraform init -backend=false — initializes providers without remote state
  • terraform validate — checks for syntax and type errors
  • terraform-docs — auto-generates README documentation

Step 3: Generate and Post a Plan

The most valuable part of Terraform CI is posting the plan output as a PR comment. Everyone can see exactly what will change before merging.

  # Job 2: Plan and post to PR
  plan:
    name: Terraform Plan
    needs: validate
    runs-on: ubuntu-latest
    if: github.event_name == 'pull_request'
    
    environment:
      name: staging
      url: https://app.terraform.io/app
    
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Setup Terraform
        uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: "1.7.5"

      - name: Terraform Init
        run: |
          terraform init \
            -backend-config="bucket=${{ secrets.TF_STATE_BUCKET }}" \
            -backend-config="key=${{ vars.TF_STATE_KEY }}" \
            -backend-config="region=${{ vars.TF_STATE_REGION }}"

      - name: Terraform Plan
        id: plan
        run: |
          terraform plan \
            -var-file=vars/staging.tfvars \
            -no-color \
            -out=tfplan

      - name: Post Plan as PR Comment
        uses: actions/github-script@v7
        with:
          script: |
            const fs = require('fs');
            const planOutput = fs.readFileSync('tfplan', 'utf8');
            
            const truncated = planOutput.length > 60000
              ? planOutput.substring(0, 60000) + '\n... plan truncated'
              : planOutput;
            
            github.rest.issues.createComment({
              issue_number: context.issue.number,
              owner: context.repo.owner,
              repo: context.repo.repo,
              body: `## Terraform Plan\n\`\`\`\n${truncated}\n\`\`\``
            });

Key details:

  • The plan job depends on validate — linting must pass first
  • Plan output is truncated to 60K characters (GitHub comment limit is 65K)
  • Using -out=tfplan saves the plan for later apply (safe — can't be modified)
  • Secrets and variables are used for backend configuration (never hardcoded)

Step 4: Apply on Merge to Main

Now add the deployment job that runs when code is merged to main:

  # Job 3: Apply on merge to main
  apply:
    name: Terraform Apply
    needs: [validate, plan]
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    
    environment:
      name: production
      url: https://app.terraform.io/app
    
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Setup Terraform
        uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: "1.7.5"

      - name: Terraform Init
        run: |
          terraform init \
            -backend-config="bucket=${{ secrets.TF_STATE_BUCKET }}" \
            -backend-config="key=${{ vars.TF_STATE_KEY }}" \
            -backend-config="region=${{ vars.TF_STATE_REGION }}"

      - name: Terraform Apply
        run: |
          terraform apply \
            -auto-approve \
            -var-file=vars/production.tfvars

      - name: Notify Slack on Success
        if: success()
        uses: slackapi/slack-github-action@v1
        with:
          channel-id: ${{ secrets.SLACK_CHANNEL_ID }}
          slack-message: "✅ Terraform applied successfully to production"
        env:
          SLACK_BOT_TOKEN: ${{ secrets.SLACK_BOT_TOKEN }}

      - name: Notify Slack on Failure
        if: failure()
        uses: slackapi/slack-github-action@v1
        with:
          channel-id: ${{ secrets.SLACK_CHANNEL_ID }}
          slack-message: "❌ Terraform apply failed — check the logs!"
        env:
          SLACK_BOT_TOKEN: ${{ secrets.SLACK_BOT_TOKEN }}

Step 5: GitHub Environments for Approval Gates

The environment block is a powerful safety feature. In GitHub Settings → Environments:

  1. Go to Settings → Environments
  2. Create a production environment
  3. Add Required reviewers (1 or more people)
  4. Add Wait timer (e.g., 5 minutes cooldown)

Now the apply job waits for a human to approve before running. No more accidental deploys!

Step 6: Secret Management

Terraform workflows need cloud credentials. Store them as GitHub Secrets:

# In GitHub: Settings → Secrets and variables → Actions
# Add these repository secrets:
TF_STATE_BUCKET         # S3 bucket for state
TF_STATE_KEY            # State file path
TF_STATE_REGION         # S3 region (us-east-1)
AWS_ACCESS_KEY_ID       # AWS credentials
AWS_SECRET_ACCESS_KEY   # AWS credentials
AWS_REGION              # e.g., us-east-1
SLACK_BOT_TOKEN         # For notifications
SLACK_CHANNEL_ID        # e.g., C0123456789

Security note: Use OIDC (OpenID Connect) instead of static access keys when possible. Terraform 1.7+ supports OIDC natively for AWS, Azure, and GCP:

# providers.tf — use OIDC instead of access keys
provider "aws" {
  region = var.aws_region
  
  assume_role {
    role_arn     = "arn:aws:iam::123456789:role/terraform-ci"
    session_name = "github-actions"
  }
}

Step 7: TFLint for Advanced Checks

Add tflint to catch provider-specific issues that terraform validate misses:

      - name: Setup TFLint
        uses: terraform-linters/setup-tflint@v4
        with:
          tflint_version: v0.50.3

      - name: TFLint Init
        run: tflint --init

      - name: TFLint
        run: tflint --config .tflint.hcl

And create .tflint.hcl to configure rules:

plugin "aws" {
    enabled = true
    version = "0.29.0"
    source  = "github.com/terraform-linters/tflint-ruleset-aws"
}

rule "terraform_comment_syntax" {
    enabled = true
}

rule "terraform_deprecated_index" {
    enabled = true
}

rule "terraform_required_providers" {
    enabled = true
}

Putting It All Together

Here's the complete workflow file that combines everything:

name: Terraform CI/CD

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

permissions:
  contents: read
  pull-requests: write

jobs:
  validate:
    name: Lint & Validate
    runs-on: ubuntu-latest
    if: github.event_name == 'pull_request'
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: "1.7.5"
      - run: terraform fmt -check -recursive
      - run: terraform init -backend=false
      - run: terraform validate -json

  plan:
    name: Plan
    needs: validate
    runs-on: ubuntu-latest
    if: github.event_name == 'pull_request'
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: "1.7.5"
      - run: terraform init -backend-config="bucket=${{ secrets.TF_STATE_BUCKET }}"
      - run: terraform plan -no-color -out=tfplan
      - name: Post Plan
        uses: actions/github-script@v7
        with:
          script: |
            const fs = require('fs');
            github.rest.issues.createComment({
              issue_number: context.issue.number,
              owner: context.repo.owner,
              repo: context.repo.repo,
              body: `## Terraform Plan\n\`\`\`\n${fs.readFileSync('tfplan','utf8').substring(0,60000)}\n\`\`\``
            });

  apply:
    name: Apply
    needs: [validate, plan]
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    environment: production
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: "1.7.5"
      - run: terraform init -backend-config="bucket=${{ secrets.TF_STATE_BUCKET }}"
      - run: terraform apply -auto-approve

Summary

A Terraform CI/CD pipeline transforms your infrastructure management from a risky manual process into a safe, repeatable workflow:

  1. Lint + validate on PR — catch formatting and syntax errors early
  2. Post plan as PR comment — everyone reviews before merging
  3. GitHub Environments — require human approval for production deploys
  4. Secret management — use GitHub Secrets or OIDC, never hardcode
  5. Slack notifications — get alerts on success or failure

Start with the basic validate + plan workflow, add TFLint when you're ready, and gradually build up to the full pipeline. The safety gates pay for themselves the first time they prevent an accidental production change.
