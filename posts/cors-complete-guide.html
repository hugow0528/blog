Cross-Origin Resource Sharing (CORS): How It Works and How to Fix Errors — Complete Guide

July 14, 2026

If you've ever built a frontend that talks to a backend API, you've probably seen the dreaded CORS error in your browser console:

Access to fetch at 'https://api.example.com/data' from origin 
'https://myapp.com' has been blocked by CORS policy: No 
'Access-Control-Allow-Origin' header is present on the requested resource.

It looks like a frontend problem, but CORS is actually a server-side security mechanism. Understanding how it works will save you hours of debugging. Let's demystify CORS from the ground up.

What Is CORS?

CORS (Cross-Origin Resource Sharing) is a browser security mechanism that controls how resources on a web server can be requested from a domain different from the one that served the resource. It extends — and adds complexity to — the browser's Same-Origin Policy.

The Same-Origin Policy

The Same-Origin Policy is the browser's default security rule: a webpage loaded from one origin (protocol + domain + port) cannot make requests to a different origin. Three things must match for two URLs to share an origin:

Component Example 1 Example 2 Same Origin?
Protocol https http No ❌
Domain myapp.com api.myapp.com No ❌
Port 443 3000 No ❌
— https://myapp.com:443 Yes ✅ (all match)

During local development, http://localhost:3000 and http://localhost:8000 are different origins — this is the most common cause of CORS errors when starting out.

How CORS Works

CORS introduces a negotiation process between the browser and the server. The browser adds extra headers to requests, and the server responds with permissions headers. There are two types of CORS requests:

1. Simple Requests

A "simple" request must meet ALL of these criteria:

  • Method is GET, HEAD, or POST
  • Headers are limited to "safe" headers: Accept, Accept-Language, Content-Language, Content-Type (with limited values), Sec-Fetch-*
  • Content-Type must be one of: application/x-www-form-urlencoded, multipart/form-data, or text/plain

For simple requests, the browser sends the request normally with an Origin header. The server must respond with Access-Control-Allow-Origin:

# Request (browser adds automatically)
GET /api/users HTTP/1.1
Host: api.example.com
Origin: https://myapp.com

# Response (server must include)
HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://myapp.com
Content-Type: application/json

{"users": [...]}

2. Preflight (CORS-preflight) Requests

Any request that is NOT "simple" triggers a preflight. The browser first sends an OPTIONS request to ask "can I make this type of request?" before sending the actual request.

# Preflight request (sent automatically by browser)
OPTIONS /api/users HTTP/1.1
Host: api.example.com
Origin: https://myapp.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: Content-Type, Authorization

# Preflight response
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://myapp.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE, OPTIONS
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Max-Age: 86400

# Only then does the browser send the actual request
PUT /api/users/1 HTTP/1.1
Host: api.example.com
Origin: https://myapp.com
Content-Type: application/json
Authorization: Bearer token123

{"name": "Alice"}

The Access-Control-Max-Age header tells the browser how long to cache the preflight response, avoiding redundant OPTIONS requests.

Essential CORS Headers Reference

Header Direction Purpose
Origin Request Tells server which origin is making the request
Access-Control-Allow-Origin Response Specifies which origins are allowed
Access-Control-Request-Method Preflight Request Asks if a specific HTTP method is allowed
Access-Control-Allow-Methods Preflight Response Lists allowed HTTP methods
Access-Control-Request-Headers Preflight Request Asks if specific headers are allowed
Access-Control-Allow-Headers Preflight Response Lists allowed request headers
Access-Control-Allow-Credentials Response Whether cookies/authorization can be sent
Access-Control-Max-Age Preflight Response How long to cache the preflight response

Configuring CORS on Popular Servers

Python Flask

from flask import Flask, jsonify
from flask_cors import CORS

app = Flask(__name__)

# Option 1: Allow all origins (development only!)
CORS(app)

# Option 2: Allow specific origins (production)
CORS(app, resources={
    r"/api/*": {
        "origins": ["https://myapp.com", "https://admin.myapp.com"],
        "methods": ["GET", "POST", "PUT", "DELETE"],
        "allow_headers": ["Content-Type", "Authorization"],
        "max_age": 86400,
    }
})

@app.route('/api/users')
def get_users():
    return jsonify([{"id": 1, "name": "Alice"}])

# Option 3: Manual headers (no extra dependency)
@app.after_request
def add_cors_headers(response):
    response.headers['Access-Control-Allow-Origin'] = 'https://myapp.com'
    response.headers['Access-Control-Allow-Methods'] = 'GET, POST, PUT, DELETE, OPTIONS'
    response.headers['Access-Control-Allow-Headers'] = 'Content-Type, Authorization'
    return response

Python FastAPI

from fastapi import FastAPI
from fastapi.middleware.cors import CORSMiddleware

app = FastAPI()

app.add_middleware(
    CORSMiddleware,
    allow_origins=["https://myapp.com", "https://admin.myapp.com"],
    allow_credentials=True,
    allow_methods=["GET", "POST", "PUT", "DELETE", "OPTIONS"],
    allow_headers=["Content-Type", "Authorization"],
    max_age=86400,
)

@app.get("/api/users")
def get_users():
    return [{"id": 1, "name": "Alice"}]

Node.js Express

const express = require('express');
const cors = require('cors');
const app = express();

// Option 1: Allow specific origins
app.use(cors({
    origin: ['https://myapp.com', 'https://admin.myapp.com'],
    methods: ['GET', 'POST', 'PUT', 'DELETE'],
    allowedHeaders: ['Content-Type', 'Authorization'],
    credentials: true,
    maxAge: 86400,
}));

// Option 2: Dynamic origin check
app.use(cors({
    origin: function(origin, callback) {
        const allowedOrigins = [
            'https://myapp.com',
            'https://admin.myapp.com'
        ];
        // Allow requests with no origin (like curl, Postman)
        if (!origin || allowedOrigins.includes(origin)) {
            callback(null, true);
        } else {
            callback(new Error('Not allowed by CORS'));
        }
    }
}));

app.get('/api/users', (req, res) => {
    res.json([{ id: 1, name: 'Alice' }]);
});

app.listen(3000);

Nginx

server {
    listen 80;
    server_name api.example.com;

    location /api/ {
        # Handle preflight OPTIONS request
        if ($request_method = 'OPTIONS') {
            add_header 'Access-Control-Allow-Origin' 'https://myapp.com';
            add_header 'Access-Control-Allow-Methods' 'GET, POST, PUT, DELETE, OPTIONS';
            add_header 'Access-Control-Allow-Headers' 'Content-Type, Authorization';
            add_header 'Access-Control-Max-Age' 86400;
            add_header 'Content-Length' 0;
            return 204;
        }

        # Add CORS headers to actual responses
        add_header 'Access-Control-Allow-Origin' 'https://myapp.com' always;
        add_header 'Access-Control-Allow-Methods' 'GET, POST, PUT, DELETE, OPTIONS' always;
        add_header 'Access-Control-Allow-Headers' 'Content-Type, Authorization' always;

        proxy_pass http://backend:8000;
    }
}

Cloudflare Workers

            headers: {
                'Content-Type': 'application/json',
                'Access-Control-Allow-Origin': 'https://myapp.com',
            },
        });

        return response;
    }
};

Credentials and Cookies

If your frontend needs to send cookies or authorization headers (like Authorization: Bearer...), you need to configure both the client and server:

// Frontend: Include credentials
fetch('https://api.example.com/user', {
    method: 'GET',
    credentials: 'include'  // Send cookies
});

// Server: Allow credentials (Python Flask example)
@app.after_request
def add_cors_headers(response):
    response.headers['Access-Control-Allow-Origin'] = 'https://myapp.com'
    response.headers['Access-Control-Allow-Credentials'] = 'true'
    return response
Important: When Access-Control-Allow-Credentials is true, the Access-Control-Allow-Origin header cannot be *. You must specify the exact allowed origin. This is a security requirement.

Common CORS Errors and Fixes

Error: "No 'Access-Control-Allow-Origin' header is present"

Fix: Your server isn't sending CORS headers. Add the headers to your server configuration (see examples above).

Error: "The value of the 'Access-Control-Allow-Origin' header must not be the wildcard '*' when the request's credentials mode is 'include'"

Fix: Replace * with the actual origin: Access-Control-Allow-Origin: https://myapp.com

Error: "Request header field Content-Type is not allowed by Access-Control-Allow-Headers in preflight response"

Fix: Add Content-Type to the allowed headers list on your server.

Error: "Response to preflight request doesn't pass access control check"

Fix: Your server isn't properly handling OPTIONS requests. Make sure it returns the right CORS headers with a 200 or 204 status code.

Should You Use a CORS Proxy?

During development, you might encounter CORS issues that seem hard to fix. A CORS proxy sits between your frontend and backend, adding CORS headers. Never use a public CORS proxy in production — it creates security vulnerabilities.

// Example: Vite dev server proxy (safe for development)
// vite.config.js
export default {
    server: {
        proxy: {
            '/api': {
                target: 'http://localhost:8000',
                changeOrigin: true,
            }
        }
    }
};

The correct production solution is always to properly configure CORS on your backend server.

Security Best Practices

  1. Never use * in production — specify exact allowed origins
  2. Only allow methods you need — don't open all methods if your API only needs GET and POST
  3. Validate the Origin header on the server side, even if the browser enforces CORS
  4. Set Access-Control-Max-Age to reduce preflight overhead
  5. Don't expose Access-Control-Allow-Credentials unless you need cookies/auth headers
  6. Combine CORS with other security measures — rate limiting, authentication, input validation

Summary

CORS is a browser security feature that prevents unauthorized cross-origin requests. The key takeaways:

  • CORS errors are server-side — add the right headers to your API
  • Simple requests (GET, safe POST) send just the Origin header
  • Complex requests trigger a OPTIONS preflight — your server must handle it
  • For credentials, never use * — specify exact origins
  • Every framework has built-in CORS support — use it instead of manual headers

Once you understand the Origin header flowing between browser and server, CORS stops being a mystery and becomes a straightforward configuration task.
