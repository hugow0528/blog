Vibe Coding Best Practices: Write Better Prompts for Better Code

July 2, 2026 · 8 min read

You've heard about vibe coding. You've tried Cursor, Claude Code, or Copilot. But there's a big difference between getting something that runs and getting good code that you'd actually ship. The gap? Your prompts.

After spending hundreds of hours prompting AI to write production code, I've distilled a set of practices that consistently produce better results. These aren't theoretical — they're field-tested techniques used by developers who ship AI-assisted code daily.

Rule 1: Give Context, Don't Just Describe Features

The most common mistake is treating AI like a Google search. You type a feature request and hope for the best. Instead, think of AI as a junior developer who's been hired for the day but hasn't read the codebase.

Bad prompt:

Write a Python API endpoint that handles user login.

Good prompt:

We have a FastAPI application with PostgreSQL. Users are stored in a users table with email, password_hash (bcrypt), and is_active fields. We use Pydantic for validation and SQLAlchemy async for database access. Write a POST /auth/login endpoint that:
  1. Accepts email and password as JSON
  2. Validates the email format
  3. Checks the password against the stored hash
  4. Returns a JWT token if successful
  5. Returns appropriate HTTP error codes (401, 422)
Here's our existing models.py: 
class User(Base):
    __tablename__ = "users"
    id = Column(Integer, primary_key=True)
    email = Column(String(255), unique=True, nullable=False)
    password_hash = Column(String(255), nullable=False)
    is_active = Column(Boolean, default=True)
Write the endpoint using our existing patterns.

Notice the difference? The second prompt gives the AI your tech stack, data models, existing code patterns, and specific requirements. The AI doesn't need to guess — it fills in the blanks.

Rule 2: Build Incrementally, Not Monolithically

Never ask AI to build an entire application in one prompt. It's like hiring a developer and saying "build me Instagram" without any discussion. Break your project into focused steps:

# Step 1 — Foundation
"Set up a FastAPI project structure with these folders:
/app
  /routers
  /schemas
  /models
  /services
  /config
  main.py
  database.py
Include a requirements.txt with fastapi, uvicorn, sqlalchemy[asyncio], 
alembic, and pydantic-settings."

# Step 2 — Database
"Now add a SQLAlchemy async setup in database.py that connects to a 
PostgreSQL database using settings from a .env file. Include the engine, 
async session factory, and a get_db dependency."

# Step 3 — Models
"Create a User model with email (unique), hashed_password, full_name, 
is_active, and is_superuser fields. Use UUIDs for the primary key."

# Step 4 — Schema
"Write Pydantic v2 schemas for UserCreate, UserUpdate, UserResponse, 
and UserLogin. Include field validators where appropriate."

# Step 5 — Service Layer
"Create a UserService class with methods for create_user, get_by_email, 
authenticate, and deactivate. Handle bcrypt hashing and proper error cases."

# Step 6 — Router
"Now build the auth router using the service layer. Endpoints: register, 
login, get_me (with auth). Add proper error handling."

Each step is small enough that the AI can produce quality code, and you can review it before moving on. If step 3 has an issue, you fix it before it propagates into steps 4-6.

Rule 3: Review Every Line of AI-Generated Code

This isn't about not trusting AI — it's about being a responsible engineer. AI makes mistakes that are easy to miss if you just copy-paste:

  • Security issues: SQL injection, missing input validation, hardcoded secrets
  • Logic bugs: Off-by-one errors, incorrect conditionals, missing edge cases
  • API hallucinations: Using methods that don't exist or calling functions with wrong arguments
  • Inefficient patterns: N+1 queries, unnecessary loops, loading everything into memory

Real example: I once asked Claude to write a file upload handler. It generated this:

# AI-generated (has issues!)
@app.post("/upload")
async def upload(file: UploadFile):
    content = await file.read()  # Loads entire file into memory!
    path = f"uploads/{file.filename}"  # No sanitization!
    with open(path, "wb") as f:
        f.write(content)
    return {"filename": file.filename}

Two problems: (1) loading the entire file into memory is a DoS vector, and (2) file.filename is user-controlled input — path traversal attack. The fixed version:

import os
import shutil
from fastapi import UploadFile, HTTPException

MAX_FILE_SIZE = 10 * 1024 * 1024  # 10MB
ALLOWED_TYPES = {".jpg", ".jpeg", ".png", ".gif", ".pdf"}

@app.post("/upload")
async def upload(file: UploadFile):
    ext = os.path.splitext(file.filename)[1].lower()
    if ext not in ALLOWED_TYPES:
        raise HTTPException(400, "File type not allowed")
    
    safe_name = f"{uuid.uuid4()}{ext}"
    path = f"uploads/{safe_name}"
    
    with open(path, "wb") as buffer:
        while chunk := await file.read(8192):
            if os.path.getsize(path) > MAX_FILE_SIZE:
                os.remove(path)
                raise HTTPException(413, "File too large")
            buffer.write(chunk)
    
    return {"filename": safe_name}

Rule 4: Use AI as Your Rubber Duck, Not Just Your Writer

Before asking AI to write code, use it to think through the problem:

"I want to build a rate limiter for my API. I need to track requests per 
user per minute, with a limit of 100. I'm using Redis. Walk me through 
the design before writing any code:
1. What data structure should I use in Redis?
2. How do I handle the sliding window vs fixed window tradeoff?
3. What happens if Redis is down?
4. How do I communicate rate limit info to the client?"

This "thinking step" catches architectural issues before they become bugs. AI might suggest using a simple counter when you actually need a sliding window, or point out that you should serve cached responses when Redis is unavailable.

Rule 5: Debug With AI — But Feed It Error Messages

When code breaks, don't just say "it's not working." Paste the actual error, the relevant code, and describe what you expected:

"My FastAPI endpoint is returning a 500 error. Here's the stack trace:

  File 'app/routers/users.py', line 15, in create_user
    db_user = User(**user_data.model_dump())
  File 'sqlalchemy/orm/decl_base.py', line 1285, in __init__
    TypeError: User.__init__() got an unexpected keyword argument 'hashed_password'

My model uses 'password_hash' as the column name, but my Pydantic schema 
uses 'hashed_password'. Here are both files:

# models.py
class User(Base):
    password_hash = Column(String, nullable=False)

# schemas.py  
class UserCreate(BaseModel):
    hashed_password: str

How do I fix this mapping?"

The AI can immediately spot the mismatch and suggest using Pydantic's model_config with field aliases, or mapping fields manually in the service layer.

Rule 6: Build Your Own Prompt Library

As you refine your prompts, save the ones that work. Create a prompts.md file in your project with reusable templates:

# Prompt Templates

## Write a FastAPI endpoint
"Write a [METHOD] endpoint for [RESOURCE] that:
- Uses FastAPI with Pydantic v2 schemas
- Connects to PostgreSQL via SQLAlchemy async
- Includes proper error handling with HTTPException
- Returns appropriate status codes
- Here are our existing patterns: [paste relevant code]"

## Add tests to existing code
"Write pytest tests for this function. Cover:
- Happy path cases
- Edge cases (empty input, None, invalid types)
- Error conditions
- Use async fixtures where needed
Here's the code: [paste]"

## Refactor for clarity
"Review this code and suggest improvements for:
- Readability (naming, structure, comments)
- Performance (avoid N+1, unnecessary loops)
- Security (input validation, error exposure)
Don't change the API surface — keep the same inputs/outputs.
Here's the code: [paste]"

Bonus: The "Two-Pass" Review Technique

After AI generates code, don't merge it immediately. Run a two-pass review:

Pass 1: "What's wrong?"

"Review this AI-generated code. List every bug, security issue, 
performance problem, and deviation from best practices. Be specific 
about line numbers and explain why each issue matters."

Pass 2: "Fix everything."

"Now fix all the issues you identified. Show the corrected code 
with comments explaining each fix."

This catches 80% more issues than a single review pass. AI is remarkably good at finding problems in its own output when you explicitly ask it to be critical.

Vibe coding isn't about being lazy — it's about being smart. The developers who benefit most from AI aren't the ones who ask the fanciest questions. They're the ones who give precise context, build incrementally, and review carefully. Master these practices and AI becomes a genuine force multiplier.
