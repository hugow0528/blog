Environment Variables & Secrets Management: Python, Docker & GitHub Actions Guide

July 3, 2026 · 9 min read

Hardcoding passwords, API keys, and database credentials directly in your source code is the most common mistake beginners make. It leads to leaked credentials, security breaches, and the nightmare of updating secrets across every file in your project. The professional solution? Environment variables and secrets management.

This guide covers the complete picture: reading env vars in Python, using .env files for local development, managing secrets in Docker containers, and securing secrets in GitHub Actions CI/CD pipelines. By the end, you'll have a bulletproof secrets workflow for any project.

What Are Environment Variables?

Environment variables are key-value pairs stored outside your application code, in the operating system's environment. They provide configuration data like database URLs, API keys, and feature flags without hardcoding them into your source files.

Setting an environment variable in your terminal:

# Set for the current shell session
export DATABASE_URL="postgresql://user:pass@localhost:5432/mydb"
export API_KEY="sk-1234567890abcdef"

# Verify it was set
echo $DATABASE_URL

Environment variables are isolated per session and per process. Setting export VAR=value in one terminal doesn't affect another. When your Python script starts, it inherits the environment variables from the process that launched it.

Reading Environment Variables in Python

Python's built-in os module lets you access environment variables:

import os

# Direct access — returns None if not found
db_url = os.environ.get("DATABASE_URL")
api_key = os.environ.get("API_KEY")

# Access with a default value
debug_mode = os.environ.get("DEBUG", "false").lower() == "true"
port = int(os.environ.get("PORT", "8000"))

# Access that raises an error if missing
try:
    secret = os.environ["REQUIRED_SECRET"]
except KeyError:
    print("FATAL: REQUIRED_SECRET environment variable is not set!")
    exit(1)

print(f"Database: {db_url}")
print(f"Debug: {debug_mode}")
print(f"Port: {port}")

The Dotenv Pattern for Local Development

In development, you don't want to type export commands every time. The python-dotenv library reads a .env file in your project root and loads those values into the environment automatically.

First, install it: pip install python-dotenv

Create a .env file in your project root:

# .env file
DATABASE_URL=postgresql://user:password@localhost:5432/mydb
API_KEY=sk-test-key-for-development-only
DEBUG=true
PORT=8000
SECRET_KEY=my-super-secret-key-change-in-production

Load it in your Python code:

# app.py
from dotenv import load_dotenv
import os

# Load .env file (must be called before os.environ.get())
load_dotenv()

# Now these values are available as environment variables
db_url = os.environ.get("DATABASE_URL")
debug = os.environ.get("DEBUG", "false") == "true"

print(f"Connected to: {db_url}")  # PostgreSQL URL from .env
print(f"Debug mode: {debug}")       # True

Critical rule: Always add .env to your .gitignore file. Never commit secrets to version control.

# .gitignore
.env
.env.local
.env.production

Instead, create a .env.example file with placeholder values so teammates know what variables are needed:

# .env.example
DATABASE_URL=postgresql://user:password@host:5432/dbname
API_KEY=your-api-key-here
DEBUG=false
PORT=8000
SECRET_KEY=generate-a-random-secret-key

Using Environment Variables with FastAPI

FastAPI makes secrets management clean with Pydantic settings:

# config.py
from pydantic_settings import BaseSettings
from typing import Optional

class Settings(BaseSettings):
    """Application settings loaded from environment variables."""
    app_name: str = "My API"
    database_url: str
    api_key: str
    debug: bool = False
    port: int = 8000
    cors_origins: str = "http://localhost:3000"

    class Config:
        env_file = ".env"
        env_file_encoding = "utf-8"

# Create a single instance used throughout your app
settings = Settings()

# main.py
from fastapi import FastAPI
from config import settings

app = FastAPI(title=settings.app_name)

@app.get("/health")
def health_check():
    return {
        "status": "healthy",
        "app": settings.app_name,
        "debug": settings.debug
    }

This approach gives you type validation, default values, and a centralized configuration object. If DATABASE_URL is missing, Pydantic raises a clear error at startup instead of failing mysteriously later.

Managing Secrets in Docker

Docker containers need access to secrets too. Here are the three main approaches, from simplest to most secure:

Method 1: Environment Variables via docker-compose.yml

# docker-compose.yml
services:
  web:
    build: .
    ports:
      - "8000:8000"
    environment:
      - DATABASE_URL=postgresql://user:pass@db:5432/mydb
      - DEBUG=true
    depends_on:
      - db

  db:
    image: postgres:16
    environment:
      - POSTGRES_USER=user
      - POSTGRES_PASSWORD=password
      - POSTGRES_DB=mydb
    volumes:
      - postgres_data:/var/lib/postgresql/data

volumes:
  postgres_data:

Method 2: .env File with Docker Compose

Docker Compose automatically reads a .env file in the same directory. Use ${VAR} syntax to reference them:

# .env (for Docker Compose — different from Python's .env)
POSTGRES_USER=myuser
POSTGRES_PASSWORD=strongpassword123
POSTGRES_DB=production_db
API_KEY=sk-live-key

# docker-compose.yml
services:
  web:
    build: .
    environment:
      - DATABASE_URL=postgresql://${POSTGRES_USER}:${POSTGRES_PASSWORD}@db:5432/${POSTGRES_DB}
      - API_KEY=${API_KEY}
      - DEBUG=false

  db:
    image: postgres:16
    environment:
      - POSTGRES_USER=${POSTGRES_USER}
      - POSTGRES_PASSWORD=${POSTGRES_PASSWORD}
      - POSTGRES_DB=${POSTGRES_DB}

Method 3: Docker Secrets (Production-Grade)

For production Docker Swarm deployments, use Docker Secrets — encrypted, file-based secrets that mount directly into the container:

# Create secrets from files
echo "my-super-password" | docker secret create db_password -
echo "sk-live-api-key" | docker secret create api_key -

# docker-compose.yml (Swarm mode)
services:
  web:
    image: myapp:latest
    secrets:
      - db_password
      - api_key

secrets:
  db_password:
    external: true
  api_key:
    external: true

Inside the container, secrets are mounted as files under /run/secrets/:

# Python code reading Docker secrets
import os

def get_secret(name):
    """Read a Docker secret from /run/secrets/."""
    path = f"/run/secrets/{name}"
    if os.path.exists(path):
        with open(path) as f:
            return f.read().strip()
    # Fallback to environment variable for local dev
    return os.environ.get(name, "")

db_password = get_secret("db_password")
api_key = get_secret("api_key")

Secrets in Dockerfiles (Build-Time)

Sometimes you need secrets during the build phase (e.g., authenticating with a private npm registry). Never bake secrets into image layers:

# BAD — secret is visible in docker history
RUN echo "sk-my-api-key" > /app/.env

# GOOD — Use build-time secrets (Docker BuildKit)
# Dockerfile
# syntax=docker/dockerfile:1

FROM python:3.12-slim

# Declare secret mount point
RUN --mount=type=secret,id=api_key \
    cp /run/secrets/api_key /app/.env && \
    rm /run/secrets/api_key

# Build with:
# docker build --secret id=api_key,src=./.env .

GitHub Actions Secrets

When your CI/CD pipeline needs secrets (deploying to production, accessing private registries, running tests against real APIs), use GitHub Actions encrypted secrets.

Setting Up GitHub Secrets

Go to your repository → Settings → Secrets and Variables → Actions → New repository secret. Add your secrets (they're stored encrypted, never visible in logs).

Using Secrets in a Workflow

# .github/workflows/deploy.yml
name: Deploy

on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.12"

      - name: Install dependencies
        run: pip install -r requirements.txt

      - name: Run tests
        run: pytest
        env:
          DATABASE_URL: ${{ secrets.TEST_DATABASE_URL }}
          API_KEY: ${{ secrets.TEST_API_KEY }}

      - name: Deploy to production
        run: ./deploy.sh
        env:
          DATABASE_URL: ${{ secrets.PROD_DATABASE_URL }}
          API_KEY: ${{ secrets.PROD_API_KEY }}
          DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }}

Notice the ${{ secrets.SECRET_NAME }} syntax — GitHub injects the secret value at runtime. It never appears in the workflow file or commit history.

Masked Secrets in Logs

GitHub automatically masks secret values in logs. Even if your script accidentally prints a secret, GitHub replaces it with ***:

# Output in GitHub Actions logs:
# DATABASE_URL=postgres://***:***@localhost/db
# API_KEY=sk-****
# (The actual values are never shown)

Security Checklist for Secrets

Follow these rules to keep your secrets safe:

  1. Never commit .env files — Add .env to .gitignore immediately
  2. Use .env.example — Document required variables with placeholder values
  3. Rotate secrets regularly — Change API keys and passwords periodically
  4. Use different secrets per environment — Never share dev and prod credentials
  5. Prefer secret managers over env vars in production — AWS Secrets Manager, Vault, etc.
  6. Set minimum required permissions — Don't give API keys more access than needed
  7. Scan for accidentally committed secrets — Use tools like gitleaks or GitHub's secret scanning
  8. Use HTTPS everywhere — Secrets transmitted over HTTP can be intercepted

Detecting Leaked Secrets with gitleaks

If you accidentally committed a secret, you need to find and revoke it immediately. Install gitleaks and scan your git history:

# Install gitleaks (Homebrew on macOS)
brew install gitleaks

# Scan your entire git history
gitleaks detect --source . -v

# Output example:
# Finding: API Key detected
# Secret: sk-1234567890abcdef
# File: src/config.py
# Line: 42
# Commit: abc1234
# Author: developer@example.com

If gitleaks finds leaked secrets, follow these steps:

  1. Revoke the secret immediately — Generate a new API key, change the password
  2. Remove from git history — Use git filter-branch or BFG Repo-Cleaner
  3. Force push — Rewrite history and force push to the remote
  4. Notify your team — Everyone needs to pull the clean history

Complete Project Structure Example

Here's how a production-ready project organizes its configuration:

my-project/
├── .env                  # Local dev secrets (gitignored)
├── .env.example          # Template with placeholders (committed)
├── .gitignore            # Excludes .env files
├── config.py             # Pydantic settings loader
├── app.py                # Main application
├── docker-compose.yml    # Docker setup with ${ENV_VAR} syntax
├── Dockerfile            # Build instructions
└── .github/
    └── workflows/
        └── deploy.yml    # GitHub Actions with ${{ secrets.XXX }}

Summary

Environment variables are the standard way to separate configuration from code. Use python-dotenv for local development, Docker Compose .env files for local containers, Docker Secrets for Swarm production, and GitHub Actions encrypted secrets for CI/CD pipelines.

The golden rule is simple: secrets never live in source code. They live in environment variables, secret managers, and CI/CD configuration — always encrypted, always access-controlled, and always rotated when compromised. Follow the checklist above and you'll avoid 99% of the security incidents that plague development teams.
