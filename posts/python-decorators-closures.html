Python Decorators and Closures: Extend Function Behavior — Complete Guide

July 12, 2026 · 11 min read

You've been using decorators since the moment you wrote @app.route in Flask or @pytest.fixture in your tests. But have you ever stopped to understand how they work under the hood? Decorators are one of Python's most elegant features — they let you wrap a function with extra behavior without modifying its code.

At the heart of every decorator are two concepts: closures and first-class functions. Mastering these will transform how you write Python. This guide takes you from understanding closures to building production-ready decorators for logging, timing, caching, and authentication.

Python Functions Are First-Class Objects

In Python, functions are objects. You can assign them to variables, pass them as arguments, and return them from other functions. This is the foundation that makes decorators possible:

# Assign a function to a variable
def greet(name):
    return f"Hello, {name}!"

handler = greet  # Just a reference, not a call
print(handler("Hugo"))  # "Hello, Hugo!"

# Pass a function as an argument
def shout(func, name):
    result = func(name)
    return result.upper()

print(shout(greet, "Hugo"))  # "HELLO, HUGO!"

Notice that greet without parentheses is a reference to the function itself. With (), it's a call. This distinction is crucial for understanding decorators.

Understanding Closures

A closure is a function that remembers variables from the scope in which it was created. Python functions carry their enclosing scope with them:

def make_multiplier(factor):
    """Return a function that multiplies by factor"""
    def multiply(x):
        return x * factor  # remembers 'factor'
    return multiply

double = make_multiplier(2)
triple = make_multiplier(3)

print(double(10))  # 20
print(triple(10))  # 30

The multiply function inside make_multiplier captures the factor variable. Even after make_multiplier finishes executing, double still remembers that factor = 2. This is a closure.

Closures are incredibly useful for creating factories — functions that produce other functions with specific behavior configured at creation time.

Closures with Mutable State

Closures can also maintain mutable state across calls:

def counter():
    count = [0]  # Use a list (mutable) instead of int
    def increment():
        count[0] += 1
        return count[0]
    return increment

c = counter()
print(c())  # 1
print(c())  # 2
print(c())  # 3

We use a list [0] because integers are immutable in Python. Alternatively, Python 3 offers nonlocal for this exact purpose:

def counter_v2():
    count = 0
    def increment():
        nonlocal count  # Access the variable from enclosing scope
        count += 1
        return count
    return increment

c = counter_v2()
print(c())  # 1
print(c())  # 2

Your First Decorator

Now, let's build a decorator. A decorator is simply a function that takes another function, adds behavior, and returns a new function:

def my_decorator(func):
    def wrapper():
        print(f"📢 Before calling {func.__name__}")
        func()  # Call the original function
        print(f"✅ After calling {func.__name__}")
    return wrapper

@my_decorator
def say_hello():
    print("Hello, World!")

say_hello()
# Output:
# 📢 Before calling say_hello
# Hello, World!
# ✅ After calling say_hello

The @my_decorator syntax is shorthand for say_hello = my_decorator(say_hello). The decorator replaces the original function with the wrapper function, which adds extra behavior before and after the original call.

What Happens Under the Hood

# These two are EXACTLY the same:

# Version A: Decorator syntax
@my_decorator
def say_hello():
    print("Hello, World!")

# Version B: Manual assignment
def say_hello():
    print("Hello, World!")
say_hello = my_decorator(say_hello)

The decorator receives the function object, wraps it, and returns a new function. Python then rebinds the name to the wrapped version.

Preserving Metadata with functools.wraps

There's a problem with our basic decorator. The wrapper function replaces the original, so metadata like __name__ and __doc__ is lost:

@my_decorator
def say_hello():
    """Say hello to the world."""
    print("Hello, World!")

print(say_hello.__name__)  # "wrapper" — oops!
print(say_hello.__doc__)   # None — the docstring is gone!

Use functools.wraps to copy the original function's metadata to the wrapper:

from functools import wraps

def my_decorator(func):
    @wraps(func)  # Copies __name__, __doc__, etc. from func to wrapper
    def wrapper(*args, **kwargs):
        print(f"📢 Before calling {func.__name__}")
        result = func(*args, **kwargs)  # Forward all arguments
        print(f"✅ After calling {func.__name__}")
        return result  # Preserve return value
    return wrapper

@my_decorator
def say_hello():
    """Say hello to the world."""
    print("Hello, World!")

print(say_hello.__name__)  # "say_hello" ✓
print(say_hello.__doc__)   # "Say hello to the world." ✓

Always use @wraps in your decorators. It preserves introspection, helps debugging, and works correctly with tools that inspect function signatures.

Decorators with Arguments and Return Values

Our decorator needs to handle functions that accept arguments and return values:

from functools import wraps

def log_calls(func):
    @wraps(func)
    def wrapper(*args, **kwargs):
        args_repr = [repr(a) for a in args]
        kwargs_repr = [f"{k}={v!r}" for k, v in kwargs.items()]
        signature = ", ".join(args_repr + kwargs_repr)
        print(f"📞 Calling {func.__name__}({signature})")
        result = func(*args, **kwargs)
        print(f"↩️ {func.__name__} returned {result!r}")
        return result
    return wrapper

@log_calls
def add(a, b):
    """Add two numbers."""
    return a + b

add(3, 5)
# Output:
# 📞 Calling add(3, 5)
# ↩️ add returned 8

The *args, **kwargs pattern captures all positional and keyword arguments, forwarding them to the original function. This makes the decorator work with any function signature.

Parameterized Decorators

Sometimes you want to configure your decorator with arguments. This requires three nested functions:

from functools import wraps

def repeat(times):
    """Decorator that repeats a function call N times"""
    def decorator(func):
        @wraps(func)
        def wrapper(*args, **kwargs):
            for i in range(times):
                print(f"  Attempt {i + 1}/{times}")
                result = func(*args, **kwargs)
            return result
        return wrapper
    return decorator

@repeat(times=3)  # Note: called with parentheses!
def greet(name):
    print(f"  Hello, {name}!")

greet("Hugo")
# Output:
#   Attempt 1/3
#   Hello, Hugo!
#   Attempt 2/3
#   Hello, Hugo!
#   Attempt 3/3
#   Hello, Hugo!

The structure is: repeat(times) → returns decorator → receives func → returns wrapper.

Real-World Decorator: Timing

A timing decorator is one of the most practical tools in your toolkit:

import time
from functools import wraps

def timer(func):
    """Measure execution time of a function"""
    @wraps(func)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = func(*args, **kwargs)
        elapsed = time.perf_counter() - start
        name = func.__name__
        print(f"⏱️ {name}: {elapsed:.4f}s")
        return result
    return wrapper

@timer
def slow_function():
    time.sleep(0.5)
    return "done"

slow_function()
# Output: ⏱️ slow_function: 0.5003s

Use this during development to identify slow functions without adding timing code everywhere.

Real-World Decorator: Caching (Memoization)

Caching expensive function results is a classic decorator use case:

from functools import wraps

def cache(func):
    """Simple memoization decorator"""
    memo = {}
    @wraps(func)
    def wrapper(*args):
        if args not in memo:
            memo[args] = func(*args)
            print(f"  🆕 Computed {func.__name__}{args}")
        else:
            print(f"  💾 Cache hit for {func.__name__}{args}")
        return memo[args]
    return wrapper

@cache
def fibonacci(n):
    if n < 2:
        return n
    return fibonacci(n - 1) + fibonacci(n - 2)

fibonacci(10)
# Shows cache hits for repeated sub-problems!
# 💾 Cache hit for fibonacci(1)
# 💾 Cache hit for fibonacci(0)
# ...

Python actually includes @functools.lru_cache for this exact purpose, but building it yourself teaches you the pattern:

from functools import lru_cache

@lru_cache(maxsize=128)
def fibonacci(n):
    if n < 2:
        return n
    return fibonacci(n - 1) + fibonacci(n - 2)

# Check cache stats
print(fibonacci.cache_info())
# CacheInfo(hits=18, misses=11, maxsize=128, currsize=11)

Real-World Decorator: Retry with Exponential Backoff

For network calls or flaky operations, a retry decorator is invaluable:

import time
from functools import wraps

def retry(max_attempts=3, delay=1, backoff=2):
    """Retry decorator with exponential backoff"""
    def decorator(func):
        @wraps(func)
        def wrapper(*args, **kwargs):
            current_delay = delay
            for attempt in range(1, max_attempts + 1):
                try:
                    return func(*args, **kwargs)
                except Exception as e:
                    if attempt == max_attempts:
                        raise
                    print(f"  ⚠️ {func.__name__} failed (attempt {attempt}/{max_attempts}): {e}")
                    time.sleep(current_delay)
                    current_delay *= backoff
        return wrapper
    return decorator

@retry(max_attempts=3, delay=0.5, backoff=2)
def unstable_api_call():
    """Simulates a flaky API call"""
    import random
    if random.random() < 0.6:
        raise ConnectionError("Connection refused")
    return "API response"

# Run multiple times to see retries in action
for _ in range(5):
    result = unstable_api_call()
    print(f"  ✅ Got: {result}")

This pattern is essential for production code that interacts with external services. It handles transient failures gracefully without crashing.

Real-World Decorator: Rate Limiter

Control how often a function can be called:

import time
from functools import wraps

def rate_limit(max_calls=5, period=60):
    """Limit function calls to max_calls per period seconds"""
    def decorator(func):
        calls = []  # Track timestamps of recent calls
        @wraps(func)
        def wrapper(*args, **kwargs):
            now = time.time()
            # Remove old timestamps outside the window
            calls[:] = [t for t in calls if now - t < period]
            if len(calls) >= max_calls:
                wait_time = period - (now - calls[0])
                raise RuntimeError(
                    f"Rate limit exceeded! Wait {wait_time:.1f}s"
                )
            calls.append(now)
            return func(*args, **kwargs)
        return wrapper
    return decorator

@rate_limit(max_calls=3, period=10)
def send_email(to, subject, body):
    print(f"  📧 Email sent to {to}")

# First 3 calls succeed
for i in range(3):
    send_email(f"user{i}@example.com", "Hello", "Hi!")

# Fourth call fails
send_email("user3@example.com", "Hello", "Hi!")
# RuntimeError: Rate limit exceeded! Wait 9.0s

Class-Based Decorators

Decorators can also be classes using the __call__ method:

from functools import wraps

class CountCalls:
    """Decorator that counts how many times a function is called"""
    def __init__(self, func):
        wraps(func)(self)  # Preserve metadata
        self.func = func
        self.call_count = 0

    def __call__(self, *args, **kwargs):
        self.call_count += 1
        print(f"  Call #{self.call_count} to {self.func.__name__}")
        return self.func(*args, **kwargs)

@CountCalls
def greet(name):
    return f"Hello, {name}!"

greet("Hugo")   # Call #1 to greet
greet("Alice")  # Call #2 to greet
greet("Bob")    # Call #3 to greet

Class decorators shine when the decorator needs to maintain state across calls, like our call counter above.

Decorators on Classes and Methods

Decorators work on classes too — the most common example is @staticmethod and @classmethod:

class Pizza:
    def __init__(self, size):
        self.size = size

    @classmethod
    def from_diameter(cls, diameter):
        """Create a Pizza from diameter"""
        return cls(size=diameter / 2)

    @staticmethod
    def is_valid_size(size):
        """Check if size is reasonable"""
        return 6 <= size <= 24

    def __repr__(self):
        return f"Pizza(size={self.size})"

# Class method receives the class, not an instance
large = Pizza.from_diameter(16)  # Pizza(size=8)
print(Pizza.is_valid_size(8))    # True

Stacking Decorators

Apply multiple decorators to a single function. They execute bottom-to-top on decoration, and top-to-bottom on execution:

@timer
@retry(max_attempts=2)
@log_calls
def fetch_data(url):
    """Fetch data with logging, retry, and timing"""
    import random
    if random.random() < 0.5:
        raise ConnectionError("Network error")
    return f"Data from {url}"

fetch_data("https://api.example.com")
# Execution order:
# 1. log_calls: prints arguments
# 2. retry: attempts the call (up to 2 times)
# 3. timer: measures total execution time

When NOT to Use Decorators

Decorators are powerful, but overusing them makes code harder to read and debug. Avoid them when:

  • The logic can be expressed clearly in a few lines inside the function
  • Debugging becomes difficult (stack traces show wrapper instead of the real function)
  • The decorator has side effects that aren't obvious from the decorator's name
  • You're nesting more than 3 decorators on a single function

Summary

Decorators and closures are fundamental Python patterns:

  • Closures let functions remember variables from their enclosing scope
  • Decorators wrap functions with extra behavior using the @ syntax
  • @wraps preserves function metadata — always use it
  • *args, **kwargs forward any arguments to the original function
  • Parameterized decorators use three levels of nesting
  • Real-world patterns: timing, caching, retry, rate limiting

Once you internalize how decorators work, you'll start seeing opportunities everywhere — adding logging, enforcing permissions, memoizing results, and more — all without cluttering your core business logic.
